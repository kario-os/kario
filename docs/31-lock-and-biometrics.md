# 锁屏与生物识别：锁屏 PIN 码、指纹解锁、指纹支付

> 状态：**原型 ✓（开发机）**。锁屏 PIN 码、息屏即锁、锁屏上的紧急呼叫和隐藏通知内容、指纹录入和解锁、连续失败停用、指纹支付和录入新指纹后支付密钥作废，在开发机自测的 9 个用例里通过（文本和像素渲染器都跑过）；`keystore`、`hal/fingerprint` 单元测试 ✓。指纹传感器是**模拟的**；真机传感器**未实现**（依赖硬件和厂商的 TEE，见 §4.1）；模板、匹配和令牌放进 TEE **未实现**（R15），现在由 phone-keystored 代替。QEMU 上自测 ✓（锁屏的 9 个用例），未上真机。恢复出厂设置和防盗锁（§11）2026-11-21 实现：单元测试 ✓，开发机自测 2 个用例 ✓，设备上开机时的清除：宿主机上测过脚本，QEMU 用例 ✓（2026-11-27 夜间链 r86；在临时目录里清空一遍，多次开机的测试**未实现**），**未上真机**。

## 0. 结论

- 没设锁屏 PIN 码时一切照旧：键盘锁是诺基亚式的，按左软键再按 `*` 就解开，不需要秘密。
- 在「设置 › 安全」设了 PIN 码（4 到 16 位数字）后，键盘锁变成安全锁，做法和 Android、iOS 一样：息屏就锁（可以设宽限时间），开机也是锁着的；锁屏挡住原来在前台的应用，通知只显示应用名和条数（可以在设置里打开内容）；只有 PIN 码或录入的指纹能解开。
- 锁着也能做的事：拨紧急号码、接听来电、关闭闹钟；NFC 的门禁卡和快捷交通卡息屏、锁着时不按键就能刷，连按两下电源键打开快速选卡（[30](30-nfc.md) §5）。别的功能可以在锁屏上加自己的快捷键（§2.3）。
- PIN 码只在系统界面上输入，交给 phone-keystored 校验：存的是加盐的慢哈希（PBKDF2，叠加由设备密钥派生的密钥），PIN 码本身不落盘、不进日志，Shell 也不留；连续输错 5 次要等 30 秒，错得越多等得越久，重启也不清零。
- 指纹走 `hal/fingerprint`：开发机和 QEMU 上是模拟传感器，自测用 `finger <名字>` 碰它。模板和匹配在 phone-keystored 里（TEE 的替身），匹配成功只给出一个认证令牌（照 Android 的 HardwareAuthToken），Shell 只负责转交。
- 未成年人模式的家长 PIN 码（[19](19-core-apps.md) §1.2）也在 phone-keystored 里，和锁屏 PIN 码分开保存、分开计数，校验和输错后的等待一样；忘了时，关联了家长账号的手机经家长在网页上确认后重设，没关联的只能刷机（§10）。
- 恢复出厂设置在「设置 › 更多设置」里：要锁屏 PIN 码（未成年人模式开着时要家长 PIN 码）和系统自己的最后确认，手机重启后在服务启动之前清除数据；系统和它的更新、手机的出厂身份（设备密钥和证书）留下。登录了 Kario 账号的手机有防盗锁（像安卓的 FRP）：不是机主用 PIN 码清除的（锁屏上忘了 PIN 码、刷了数据分区），清除后要这个账号的验证码才能用（§11）。
- 指纹支付：`auth.confirm` 多了 `bio_key`，绑定指纹的密钥只在指纹匹配后签名，录入或删除指纹后作废（iOS 的 biometryCurrentSet、Android 的 setInvalidatedByBiometricEnrollment）；系统确认框写「触碰指纹传感器确认，或输入支付密码」，签名照旧覆盖显示的文字，服务端照旧用 `keystore.VerifyConfirm` 验签。

## 2. 锁屏

### 2.1 什么时候锁

`c.keylock` 是唯一的锁状态，`c.locked()` 是它的判断；PIN 码只决定怎么解开（`c.secureLocked()`）。

| 情况 | 没设 PIN 码 | 设了 PIN 码 |
|------|-------------|-------------|
| 待机界面左软键再按 `*` | 键盘锁 | 安全锁 |
| 自动键盘锁（设置 › 键盘锁） | 键盘锁 | 安全锁 |
| 息屏 | 不锁（和以前一样） | 过了宽限时间就锁（默认立即）：「立即」在息屏的同一次例行检查里就锁上；宽限时间按息屏时 5 秒一次的例行检查算，按键唤醒前先补查一次 |
| 开机、Shell 重启 | 不锁 | 锁；Shell 先按记下的状态锁上，再听 phone-keystored 的 |

安全锁锁上时，Shell 关掉屏幕上的菜单和对话框（来电、闹钟、SIM 卡 PIN 码界面留着），把前台应用和待机之上的系统页面藏起来，只留待机界面；解锁后原样还回去。

### 2.2 锁着能做什么

| 按键或事件 | 安全锁 |
|------------|--------|
| 数字键、OK、左软键 | 叫出 PIN 码界面（数字键直接算第一位） |
| 通话键 | PIN 码界面上打的是紧急号码（112、110、119、120、122、911、999）时直接拨出，不用解锁；打的数字不显示，PIN 码开头像紧急号码也不泄露。锁屏上直接按通话键也叫出这个界面 |
| 指纹 | 录入过的手指解锁（息屏时一碰也先点亮屏幕）；认不出提示「未能识别指纹」 |
| 来电 | 系统接听界面照常；接通后只有通话界面能用，菜单、任务切换、返回这些出不了通话界面；挂断后回到锁屏。通话中息屏上锁时，在前面的通话界面留着不藏，点亮屏幕就是它（照 Android、iOS），同样只能用通话界面，右软键「最小化」锁着时不起作用。通话还在、人却回到了锁屏时（通话转到了后台再上锁，或通话界面被别的应用换掉），锁屏提示「通话键 回到通话」，按通话键回到通话界面，不用解锁；蜂窝通话和 VoIP 通话都是这样（单元测试 `TestLockReturnsToCall`、`TestLockDuringACall`，开发机自测「锁屏：通话中息屏上锁……」，**未上真机**；通话的前后台见 [19](19-core-apps.md) §5） |
| 闹钟 | 照常响，照常关 |
| 通知 | 待机界面只写「飞钱：1 条通知」这样的应用名和条数，横幅只写应用名；设置里打开「锁定时显示通知内容」后照常显示 |
| 挂断键 | 回到锁屏（紧急电话打完后）；没有电源键的机型在锁屏上停一下再连按两下：快速选卡（[18](18-nokia-form-factors.md) §5.1） |
| 电源键 | 息屏、亮屏（息屏照 §2.1 的规则上锁）；连按两下打开快速选卡，盖在锁屏上，不用解锁，选的卡出示 60 秒，付款卡要先解锁（[30](30-nfc.md) §5）；按住打开电源菜单 |

### 2.3 锁屏快捷键（给其他功能用）

锁屏上可以加不用解锁就能用的系统功能（比如手电筒）。列在 `shell/lock.go` 的 `lockShortcuts` 里，一个功能加一行，可以写在自己的文件的 `init` 里。现在没有功能注册：NFC 原来的 → 快捷键去掉了，卡不用按键就能刷，快速选卡由电源键打开（[30](30-nfc.md) §5）。

```go
lockShortcuts = append(lockShortcuts, lockShortcut{Key: KeyF2, Label: "Torch", Run: (*Core).torch})
```

规则：`Run` 被调用时手机还锁着，只能弹出系统的弹层，别的都在锁后面；`Label` 写英文，锁屏提示里翻译后显示。锁屏自己占用的键：数字、OK、左软键、`*`、通话键、挂断键、返回（电源键不经过锁屏）；空着的是右软键和方向键。

## 3. PIN 码

| 环节 | 做法 |
|------|------|
| 设置、修改、删除 | 设置 › 安全；PIN 码在系统自己的界面上输入（设置应用调 `settings.set lock_pin`，回复等用户办完），设置应用拿不到；修改要先输现在的，新的输两遍；删除要输现在的，指纹一并删除 |
| 保存 | phone-keystored 的 `keystore/lock.json`：随机盐、PBKDF2-SHA256（10 万轮）、算前先用设备密钥派生的密钥做 HMAC（文件拿到别的设备上没用；派生时加上数据区的随机盐，恢复出厂设置后换一份，§11.3；量产换成 TEE 的硬件密钥）；还有「安全用户 ID」，设 PIN 码时生成，令牌里带着它 |
| 不留明文 | PIN 码只在系统界面里打到一半时在 Shell 内存里，交出去就清掉；不写盘、不进日志 |
| 输错 | 连续 1–4 次：提示还能错几次；5–9 次：每次之后等 30 秒；10–14 次 1 分钟；15–19 次 5 分钟；20–29 次 30 分钟；30–39 次 1 小时；之后 1 天。次数写在 `lock.json`，重启后从头再等一遍当前的时长（不会因为重启变短） |
| 和支付密码的关系 | 锁屏 PIN 码和可信确认里的支付密码是两样东西（像支付宝的支付密码和手机锁屏密码）；合成一个是以后的取舍，**未实现** |

## 4. 指纹

### 4.1 HAL 与传感器

`hal/fingerprint` 定义 `Sensor`：`Capture` 等一次触碰并读出特征，`Enroll` 开始录入（`Add` 一次次加触碰、报进度，够了给出模板），`Match` 比对特征和模板。整个包只在 phone-keystored 里用，读数和模板出不了这个进程。

| 后端 | 状态 |
|------|------|
| 模拟（`Sim`，开发机和 QEMU） | ✓：每个名字是一根不同的手指，每次触碰读数略有不同；录入要碰 5 次，换了手指不算；自测命令 `finger <名字>` 经 Shell 交给 phone-keystored（`fp.sim_touch`，和模拟基带的 `sim.ring` 一样，是测试钩子） |
| 手机上的 SPI 传感器（FPC、汇顶） | **未实现**，依赖硬件：主线内核没有驱动，厂商在 TEE 的可信应用里驱动它，录入和比对也在那里做，所以后端是那个可信应用的客户端，要厂商的 TEE。测试机红米 Note 4X 是 FPC 的传感器，没有主线驱动 |
| USB 传感器（libfprint 支持的） | **未实现**；libfprint 是 LGPL，只能放在单独的进程里，后端经进程间接口和它说话，不能链接进平台 |
| 没有可用传感器的机型 | 主板配置不写 `fingerprint`（[24](24-sku-framework.md)），phone-keystored 就没有传感器，设置里写「没有指纹传感器」 |

phone-keystored 的后端按主板配置（`sku.json` 的 `fingerprint`）选：模拟器的主板写 `sim`，真机的主板在传感器有驱动之前不写，就没有指纹；没有 `sku.json` 的开发机用模拟后端；`--fingerprint` 可以改。真机上传感器的中断应当是唤醒源，碰一下就从挂起里醒来（**未实现**）；开发机上 `finger` 命令先点亮屏幕。

### 4.2 模板与匹配（keystored 代 TEE）

| 环节 | 做法 |
|------|------|
| 录入 | 先在系统界面输一次 PIN 码：phone-keystored 发一个挑战，PIN 码校验通过给出带这个挑战的令牌，录入要这个令牌，10 分钟内有效（Android 的做法）；然后系统的录入界面按进度一格格点亮，碰到已经录过的手指提示换一个 |
| 保存 | `keystore/fingerprints.json`：名字和模板，模板用设备密钥派生的密钥（AES-GCM）加密；还有「指纹集合 ID」，每次增删指纹都换一个 |
| 比对 | 只在 phone-keystored 里；成功给令牌，不给模板也不给读数 |
| 改名、删除 | 设置 › 安全 › 指纹（进来要先输 PIN 码）；删除也要那个令牌 |

### 4.3 认证令牌

照 Android 的 HardwareAuthToken：PIN 码校验和指纹比对各出一个，要用户在场的操作（录入指纹、用绑定指纹的密钥签名）收它。MAC 的密钥在 phone-keystored 每次启动时随机生成，只有它能出、能验，重启后旧令牌全部失效；Shell 只转交。

```
版本(1) | 挑战(8) | 安全用户 ID(8) | 认证者 ID(8) | 类型(4：1 PIN、2 指纹) | 时间(8：启动后的毫秒) | HMAC-SHA256(32)
```

### 4.4 规则

| 规则 | 做法 |
|------|------|
| 最多 5 个指纹 | 第 6 个录不进 |
| 连续 5 次认不出 | 指纹停用，锁屏提示要 PIN 码；输对 PIN 码后恢复（解锁和支付共用这个计数） |
| 重启后 | 第一次解锁要 PIN 码（phone-keystored 启动后还没见过 PIN 码时拒绝指纹） |
| 48 小时没输 PIN 码 | 同上 |
| 删除 PIN 码 | 指纹全部删除，绑定指纹的密钥随之作废 |
| 用途开关 | 设置 › 安全 › 指纹：「解锁手机」（默认开）、「支付」（默认关） |

### 4.5 传感器只在要指纹时通电；OK 键上的传感器

传感器由 phone-keystored 管电：有等待（录入、`fp.auth`）时才通电，等待结束后再留 1.5 秒（连着重试不用反复上电；OK 键上的传感器不留，见下表），`fp.cancel` 立即断电；不通电时碰了也不读，那次触碰丢掉、不留到下次（`Sensor.SetPower`，模拟传感器照做）。`lock.status` 的 `powered` 说现在通没通电，自测命令 `fingerprint-power on|off` 等它。

键盘机可以把传感器做在导航键中间的 OK 键上：键帽表面下的一块面阵传感器，在键帽允许的范围内尽量大，手指放上去就读，不用按下。SKU 键盘配置写 `fingerprint = "ok-key"`，它是 `fingerprint = { at = "ok-key", sensor = "area", read = "touch" }` 的简写（[24](24-sku-framework.md)）；`tools/sku.py` 只收这两种写法，按下才读的（`read = "press"`，那样 OK 就成了指纹键）、别种传感器、别的位置、少写或多写的键都拒绝，还要求键盘矩阵里有 OK 键；`sku.json` 里两种写法都是 `fingerprint_at = "ok-key"`。OK 键一天按几百次，每按一下都碰到传感器，所以：

| 规则 | 做法 |
|------|------|
| 只为系统的指纹框读 | Shell 只在系统的确认框（`auth.confirm` 带 `bio_key`）和录入界面开着时发起等待，传感器只在这时通电；待机、锁屏、应用里碰或按 OK 都不读。等待一结束就断电，不留 1.5 秒：留着的话，付完款后的那一下 OK 会被读到，还会留到下一个指纹框里当回答（`TestOKKeySensorOffOutsideThePrompt`，在原来的代码上失败） |
| 确认框开了 500 毫秒才通电 | 和系统确认框收键的规则一样（`overlayArmDelay`，[11](11-platform-architecture.md) §16.1）：叫出确认框的那一下 OK 不是回答，那时还放在 OK 上的手指也不是；Shell 等确认框开了 500 毫秒才发 `fp.auth`。真机驱动还要只认通电之后才落下的手指（`hal/fingerprint` 的要求，§9） |
| 不用来解锁 | 锁屏不等指纹，锁屏提示里没有「触碰指纹传感器」；手指放在 OK 上什么也不发生，按下 OK 才叫出 PIN 码界面；设置里没有「解锁手机」开关，写明传感器在 OK 键的键帽下、手指放上去不用按就读、只在系统要指纹时通电；phone-keystored 也拒绝不为密钥的匹配（`ErrPromptOnly`），Shell 出错也解不了锁 |
| 怎么确认 | 确认框写「把录入过的手指放在 OK 键上确认（不用按下），或输入支付密码」；录入界面写「把同一个手指放在 OK 键上，每次抬起再放，让整个指纹都被读到；不用按下」 |
| 谁说了算 | phone-keystored 读 `sku.json` 的 `fingerprint_at`，`lock.status` 的 `place` 告诉 Shell；自测的 `fingerprint-at ok-key|own`（`fp.sim_place`，只在模拟传感器上）在开发机上换位置 |

**按下和触碰谁算数。** 手指放在 OK 上就被读到，按下 OK 时手指也一定在键帽上，所以两样常常一起来：

- 确认框开着的头 500 毫秒：都不算。传感器没通电，OK 也不收（上表）。
- 之后，读到的指纹匹配了就是回答：签名、关框。按 OK 照旧是一个键，交给确认框，它不读指纹、不确认、也不取消；已经输了几位支付密码时提示「请输入完整的 6 位支付密码」，没输时什么也不做。所以单按 OK 永远付不了款。
- 两样都有时，读到的指纹算数，跟着它的那一下 OK 归系统：框还开着时由框收下（上一条），框因为指纹关掉后 500 毫秒内的那一下 OK 丢掉一次（`okAfterFinger`），不落到框下面的页面上（比如付款结果页，或者录完指纹后设置里的「添加指纹」）。
- 为什么这样：只有读数能证明是谁，OK 不带身份，谁按都一样，让它确认就等于没有指纹这一步。而 OK 在确认框里的意思本来就是「确认」，和放上手指是同一个意图，所以按下不必像 Android 的侧边指纹那样取消认证：Android 的电源键意思是「息屏」，和认证相反，所以 BiometricPrompt 进行中按电源键会让侧边指纹的认证失败（`BIOMETRIC_ERROR_POWER_PRESSED`，[提交 eac8784](https://github.com/aosp-mirror/platform_frameworks_base/commit/eac8784630f6c2db499983bc3b200ef440180db8)），认证成功后一小段时间内按电源键也算取消（`config_sidefpsBpPowerPressWindow`，[提交 ae84de6](https://github.com/aosp-mirror/platform_frameworks_base/commit/ae84de69b07e8b1dd062bf4fd267e26c90a9912d)）。Android 同样在 BiometricPrompt 开着时吃掉电源键的单按（[`SideFpsEventHandler.shouldConsumeSinglePress`](https://android.googlesource.com/platform/frameworks/base/+/master/services/core/java/com/android/server/policy/SideFpsEventHandler.java)），Kario 丢掉跟着指纹的那一下 OK 是同一个做法。

单元测试 `TestOKKeyReadsATouchNotAPress`（`shell`，phone-keystored 经套接字、真的密钥库和模拟传感器）按这几条走一遍；它在原来的代码上失败（原来锁屏上碰一下就按了 OK、叫出 PIN 码界面）。以上只在模拟传感器上跑过：OK 键上真传感器的驱动**未实现**、**未上真机**；OK 的键码和触碰不论谁先到 Shell，上面的规则都成立，这点**未验证**（§9）。

**安全级别说实话。** `lock.status`、密钥证明（`KeyProof`）和设备认证（`Attestation`）都带 `security`：`software`（现在：phone-keystored 进程代 TEE，[22](22-developer-api.md) §4.1）或 `tee`（量产时由 TEE 里的可信应用给）。确认框在 `software` 时加一行「这台手机没有安全硬件（TEE）：密钥由系统的密钥服务保管，指纹也由它比对」，飞钱的结果页和安全页也写出密钥在哪里。这个字段**不在签名里**：软件实现里签名的密钥和报告级别的是同一个进程，签了也证明不了什么；要让服务端能信，得由 TEE 的认证密钥签（SOTER、IFAA 的做法，§9）。

## 5. 指纹支付

1. 应用调 `auth.confirm{key, bio_key, prompt, payload}`（飞钱：`key: "pay"`、`bio_key: "pay-bio"`）。用户打开了「指纹用于支付」并且录了指纹时，系统确认框写「触碰指纹传感器确认，或输入支付密码」，同时等指纹和支付密码。
2. 指纹匹配：phone-keystored 先核对 `bio_key` 这把密钥还在、绑的是当前的指纹集合，再等触碰；匹配后给一个只对这把密钥这一次签名有效的令牌（30 秒内）；Shell 把令牌转给 `confirm_bio`，密钥对「显示的文字 + 载荷」签名。证明里 `key_alias` 是 `pay-bio`、`bio: true`。
3. 支付密码：和以前一样用 `key` 签名；签完 phone-keystored 顺带把 `bio_key` 做出来（没有、或者已经作废时），绑到当前的指纹集合。所以绑定指纹的密钥**只在支付密码确认之后**才会生成：知道锁屏 PIN 码的人录了自己的指纹，旧密钥作废，他也付不了款。
4. 录入或删除指纹后：确认框说明「开通指纹支付后指纹有变动，请用支付密码确认，指纹支付随之重新开通」，只收支付密码；确认后新密钥生成，下一次又能用指纹。第一次用也是这样（「先用支付密码确认一次，之后就能用指纹支付」）。
5. 服务端（飞钱里的模拟商户）照旧用 `keystore.VerifyConfirm` 逐级验签：厂商根 → 设备证书 → 应用密钥证书 → 签名 → 内容核对。绑定指纹的密钥的证书写明它是「指纹绑定」（`keystore.AppKeyCertMsgBio`），`VerifyConfirm` 按证明里的 `bio` 选证书格式，所以服务端知道这次是指纹确认的；飞钱收 `pay` 和 `pay-bio` 两把。

| 密钥 | 怎么确认 | 证书里写的 |
|------|----------|-----------|
| `key`（如 `pay`） | 支付密码 | `user_auth` |
| `bio_key`（如 `pay-bio`） | 指纹，匹配后 30 秒内、只用一次 | 指纹绑定；指纹集合一变就作废 |

小程序宿主照旧只传 `key`，不受影响。

## 6. 设置 › 安全

| 项 | 做法 |
|----|------|
| 锁屏 PIN 码 | 设置、修改、删除，都在系统界面输入（`settings.set` 的 `lock_pin`：1 设置或修改，0 删除） |
| 息屏后多久锁定 | 立即、5 秒、30 秒、1 分钟、5 分钟（`lock_grace`，秒） |
| 锁定时显示通知内容 | 开关（`lock_show_content`） |
| 指纹 | 进来先在系统界面输 PIN 码（`fingerprint_auth`）；列出指纹，改名（`fingerprint_rename`，值是 ID，`text` 是名字）、删除（`fingerprint_delete`）；添加（`fingerprint_enroll`，系统的录入界面）；「解锁手机」「支付」两个开关（`fingerprint_unlock`、`fingerprint_pay`） |

`settings.get` 的 `security` 里有：是否设了 PIN 码、宽限时间和选项、是否显示通知内容、传感器、指纹列表（只有 ID 和名字）、最多几个、两个开关、指纹为什么暂时不能用（`restart`、`timeout`、`lockout`）。设置应用的代码在 `apps/settings/security.go`，Shell 这边在 `shell/lock.go`、`shell/lockpad.go`、`shell/biometric.go`。

## 7. 接口

phone-keystored 的方法（只有 Shell 调，`keystore/methods.go`）：

| 方法 | 做什么 |
|------|--------|
| `lock.status` | PIN 码、等待、传感器、指纹列表、为什么要 PIN 码 |
| `lock.set_pin` / `lock.clear_pin` / `lock.verify` | 设置或修改、删除、校验 PIN 码；校验带挑战，对了给令牌 |
| `fp.challenge` / `fp.enroll` / `fp.enroll_next` | 录入：挑战、开始（要 PIN 令牌）、等下一次触碰并报进度 |
| `fp.auth` | 等一次触碰并比对；带 `app`、`key` 时是为那把绑定指纹的密钥签名 |
| `fp.cancel` | 结束等待（和录入） |
| `fp.rename` / `fp.remove` | 改名、删除（删除要 PIN 令牌） |
| `confirm` 的 `bio_key` / `confirm_bio` | 支付密码确认后做出绑定指纹的密钥；拿指纹令牌用它签名 |
| `fp.sim_touch` | 模拟传感器的测试钩子；回 `{read}`：传感器没通电时是 `false`（§4.5） |
| `fp.sim_place` | 模拟传感器的测试钩子：把它放进 OK 键（`ok-key`）或拿出来（空） |
| `parent.status` / `parent.set_pin` / `parent.clear_pin` / `parent.verify` | 家长 PIN 码（§10）：有没有、等待；设置或修改（要现在的）、删除（要它）、校验；对了只回「对」，不给令牌 |
| `parent.reset_pin` | 不要现在的家长 PIN 码就换成新的（输错的次数清零）；Shell 只在验过账号服务器签名的重设之后调（§10） |

## 10. 家长 PIN 码（未成年人模式）

未成年人模式（[19](19-core-apps.md) §1.2）由家长 PIN 码守着：设了它就打开，关掉要它；改未成年人模式和屏幕使用时间、从商店安装、开发者模式、解锁设备、改日期时间、多给时间都要它。

| 环节 | 做法 |
|------|------|
| 输入 | 只在系统自己的界面上输入（`shell/minor.go` 的 `parentPadOverlay`，和锁屏 PIN 码的界面同一种画法）；设置应用调 `settings.set minor_mode` / `parent_pin`，或改一项被守着的设置，回复等用户办完，设置应用拿不到 PIN 码。设置时输两遍；修改先输现在的 |
| 保存 | phone-keystored 的 `keystore/parent.json`，和 `lock.json` 分开：随机盐、PBKDF2-SHA256（10 万轮），算前用设备密钥派生的另一把密钥（`kario-parental-pin`）做 HMAC。PIN 码本身不落盘、不进日志；Shell 在界面上打到一半时才在内存里，交出去就清掉；设置的文件、Shell 的 `minor.json`、`settings.json` 里都没有 |
| 输错 | 和锁屏 PIN 码同一张表（§3）：1–4 次提示还能错几次，5 次后 30 秒，越错越久，次数写在 `parent.json`，重启不变短；两个 PIN 码各算各的 |
| 校验的结果 | 对了只回「对」，不给令牌：执行未成年人模式的是 Shell 自己；Shell 也不留「输对过」的凭据，只在设置一直在前台时 10 分钟内接着改不用再输 |
| 开着还是关着 | phone-keystored 里有家长 PIN 码就是开着；Shell 开机先照自己记下的，`parent.status` 回来后听它的 |
| 和锁屏 PIN 码 | 两样东西：锁屏 PIN 码是孩子的（锁屏照常），家长 PIN 码是家长的；界面上建议不要用同一个 |
| 忘了怎么办 | 关联了家长的账号时（[19](19-core-apps.md) §1.2「忘记家长 PIN 码」）：手机向账号服务器申请，家长在网页上 10 分钟内用邮箱验证码登录过后确认，服务器签一份只给这台手机、这次申请、10 分钟有效的重设（`family.Reset`）；Shell 验签后在系统自己的界面上让人输两遍新的，交出去前再验一次没过期，phone-keystored 的 `parent.reset_pin` 换掉 `parent.json` 里的哈希（新的盐、输错次数和等待清零），旧的随即失效，重设只能用一次。phone-keystored 自己不验签名：它只有 Shell 一个调用方，而执行未成年人模式的本来就是 Shell，验签放在 Shell 里不多给它什么。没关联家长账号时只能刷机，刷机连同手机上的数据一起清掉（恢复出厂设置也要家长 PIN 码，§11.1） |

没做的：放进 TEE（同 §9 的 R15）；没关联家长账号时忘了家长 PIN 码的找回（只能刷机）**未实现**；家长远程管理 2026-11-20 实现（[19](19-core-apps.md) §1.2「家长远程管理」：远程能收紧和放宽规则，关不掉未成年人模式、改不了 PIN 码）；经家长的账号重设 PIN 码同一天第二轮实现（上表「忘了怎么办」），**未上真机**、账号服务器**没有部署**、微信内置浏览器里的家长网页**未验证**。

## 11. 恢复出厂设置与防盗锁

> 2026-11-21 实现，11-25 加了退出登录后绑定留在服务器上的提示和绑定被拒（401）时停下重试，同一天又加了退出登录的确认框里事先说防盗锁会留在账号上、绑定回 409 时设置里的说明和「重试开启防盗锁」（§11.4）。单元测试（`keystore`、`wipe`、`antitheft`、`shell`、`apps/settings`，账号服务器 `kario-accountsrv` 的 6 个）✓；开发机自测「恢复出厂设置：……」「防盗锁：……」两个用例 ✓，「Kario 账号：网页上让手机退出登录后，在手机上退出登录」✓，「Kario 账号：这台手机还锁在别的 Kario 账号上」✓（这两个不用重启，但要持久区：`require-persist`，`go test ./shell` 的分组里没有持久区，跳过）（文本渲染器；重启是 `phone-shell` 停掉应用和服务后在原地重新执行自己，清除的是自测的状态目录；账号服务器是 Shell 里模拟的）。`go test ./shell` 的分组测试不能原地重启，这两个用例在那里跳过。设备上开机时的清除（initramfs 重做数据分区、`phone-wipe.service`）只有宿主机上对脚本的测试（`wipe` 包运行 yocto 的 `data-wipe`，格式化那条路的 mount、mkfs 是替身）和 QEMU 专用用例「恢复出厂设置（设备）」（QEMU ✓，2026-11-27 夜间链 r86），多次开机的 QEMU 测试（像 `make yocto-ota-test` 那样）**未实现**；**未上真机**；账号服务器**没有部署**。

放在这里而不是 [19](19-core-apps.md)：恢复出厂设置由锁屏 PIN 码（§3）和家长 PIN 码（§10）守着，忘了 PIN 码时的出路从锁屏开始（§2），防盗锁和设备密钥（[11](11-platform-architecture.md) §7）是同一套信任；[19](19-core-apps.md) §1.2 只写未成年人模式要它的那道门。

### 11.1 恢复出厂设置

| 环节 | 做法 |
|------|------|
| 在哪 | 设置 › 更多设置 › 恢复出厂设置（安卓在「系统 › 重置选项 › 清除所有数据」，小米 MIUI 12 在「更多设置 › 备份和重置」，HyperOS 移到「我的设备」）；命令面板「设置 · 恢复出厂设置」。代码在 `apps/settings/reset.go`、`shell/reset.go` |
| 页面写明 | 会清除：所有应用的数据和设置、商店装的应用；账号和系统替它们封存的密码（CardDAV 的应用专用密码、家长远程管理的设备令牌）；通讯录、短信、通话记录；照片、视频、音乐和「文件」；Wi-Fi 网络和蓝牙配对；锁屏 PIN 码和指纹；未成年人模式和家长 PIN 码。会保留：系统和装上的更新（两个系统槽不动）；手机的出厂身份（设备密钥和设备证书，§11.3）。登录着 Kario 账号时有「保留防盗锁」开关（默认关）；最后写着要输什么 |
| 确认 | 未成年人模式开着时要家长 PIN 码，每次都要输（在设置里输过一次后 10 分钟内接着改不用再输的那一条，在这里不算）；否则设了锁屏 PIN 码就要它；都在系统自己的界面上输入。然后是系统自己的最后确认「清除这台手机上的全部数据？」，写明清除什么、留下什么、防盗锁怎样。电脑经开发者通道注入的按键答不了这两步（[27](27-usb-typec.md) §4）。没设锁屏 PIN 码的手机只有最后确认：拿着解锁的手机的人都能清除它，页面上照实写着 |
| 清除 | Shell 在持久区写下请求（`wipe.Request`：`/var/lib/slots/wipe/request`，先写临时文件再改名、fsync），再改防盗锁的记录（§11.4），给账号服务器最多 5 秒（解除防盗锁的绑定、家长远程管理的关联，尽力而为），显示「正在清除手机…」，然后重启。下次开机时在服务启动之前清除（下表）。设置 `settings.set factory_reset`（1；2 是保留防盗锁），`settings.get` 的 `reset` |
| 开机以后 | 和新手机一样：待机界面，没有账号、PIN 码、联系人（开发机和自测里有示例联系人），设置都是默认，产品自带的系统应用还在。开机向导 Kario 没有，**未实现** |

清除在哪里做：

| 环境 | 怎么清除 |
|------|----------|
| A/B 磁盘（QEMU 的磁盘镜像；量产照这个分区，[25](25-system-update.md) §1） | initramfs（`slot-init` 用 `phone-wipe` 的 `data-wipe`）在打开系统槽之后、挂数据分区之前看状态分区里的请求：先把设备的身份（`phone/factory/`、`phone/keystore/device.key`、`device-sm2.key`）拷到状态分区（`wipe/keep/`，拷完写 `kept`），再 `mkfs.ext4` 重做数据分区（mke2fs 先丢弃分区上的块，存储支持时等于擦掉），挂上、拷回身份、写新的数据盐，最后删请求。中途断电，下次开机从拷好的身份接着做。数据分区挂不上时身份保不住，日志里写明。initramfs 因此多了 e2fsprogs 的 mke2fs（initramfs 的大小**未验证**） |
| 根文件系统和数据在一起的板子（一加 6T） | `phone-wipe.service`（`DefaultDependencies=no`，排在 `sysinit.target` 和 `systemd-tmpfiles-setup.service` 之前，有请求时才运行）：同样先保存身份，再清空 `/var/lib/phone`、`/var/lib/iwd`（Wi-Fi 网络）、`/var/lib/bluetooth`（配对），拷回身份、写数据盐、删请求。它也是 initramfs 没做成时的后备。清空不是擦除：删掉的块要等存储自己回收 |
| 开发机 | `phone-shell` 在启动服务之前调 `wipe.Boot`：持久区是基目录下的 `persist/`（和 `state/`、`run/` 并列），步骤同上；重启是 phone-shell 停掉应用和服务后在原地重新执行自己（`Config.Reboot`），自测从重启前那一行接着跑（`rebooted` 步骤） |

两份实现（Go 的 `wipe` 包、yocto 的 `data-wipe` 脚本）步骤和保留的路径一样；`wipe` 包的测试用同样的检查跑脚本的两条路。

### 11.2 忘了锁屏 PIN 码

Kario 没有安卓那样的 recovery（[27](27-usb-typec.md) §4.1），刷机走板子的工具。所以锁屏 PIN 码忘了时，出路放在锁屏上，照 iOS 15.2 起锁定界面上的「抹掉 iPhone」：连续输错 5 次（第一次要等 30 秒）以后，PIN 码界面多一行「忘了 PIN 码？按 # 清除这台手机和上面的一切」；按 # 是系统自己的确认「不用 PIN 码清除这台手机？」，写明登录着的 Kario 账号之后会被要求。未成年人模式开着时先要家长 PIN 码（不然孩子输错几次就能把未成年人模式清掉）。这样的清除没有机主的锁屏 PIN 码，防盗锁不解除。

| 不用锁屏 PIN 码清除的途径 | 现状 |
|------|------|
| 锁屏上「忘了 PIN 码」 | ✓（上面），防盗锁不解除 |
| 开机时按键进的清除界面（安卓 recovery 的 Wipe data） | **未实现**：要在 initramfs 里读按键、画界面；做的时候和锁屏这条一样算不受信任的清除 |
| 输错太多次自动清除（iOS 的「抹掉数据」选项） | **未实现**；现在是越等越久，最长一天（§3） |
| 刷机工具重写数据分区（fastboot、高通 EDL） | 挡不住清除；状态分区没被重写时防盗锁照样锁（§11.4：数据区里没有记录的令牌） |

### 11.3 密钥：出厂身份留下，数据区的密钥换掉

phone-keystored 的设备密钥（Ed25519 和 SM2）是设备证书证明的东西：产线上认证方的 CA 给这两把公钥签证书（[11](11-platform-architecture.md) §7、[22](22-developer-api.md) §11），推送网关注册、更新服务器的回报、支付的可信确认都靠这条链认出「这是一台认证过的真手机」。换了设备密钥，证书就作废，而证书只有产线工站能再签，机主没有办法。所以恢复出厂设置**留下**设备密钥、设备证书和根（`keystore/device.key`、`device-sm2.key`、`factory/`），设备号不变，`wipe.Keep` 列着这几项。安卓也这样：出厂灌装在 Keymaster 里的认证密钥不随恢复出厂设置清除，清掉的是用户数据的密钥。

清掉的：所有应用密钥（`keystore/apps/`，含小程序的）、推送密钥、支付密码（回到默认）、锁屏和家长 PIN 码、指纹模板、系统封存的秘密；「解锁设备」的状态也清掉（换上去的自己编的组件在数据区里，随之没了，设备认证又报正常启动）。

只删文件不够：用同一把设备密钥派生的密钥（PIN 码的胡椒、指纹模板的密钥、封存秘密的密钥）不变的话，清除前拷走的数据（比如封好的应用专用密码）在这台手机上还能打开。所以派生时再加一份数据区的随机盐（`keystore/data.salt`，`keystore.DataSaltPath`）：新的密钥库生成时写一份，清除时随数据区删掉，清除的最后一步写新的一份；清除前封存的秘密从此打不开、PIN 码的哈希对不上（`TestDataSaltAfterAReset`）。这一版之前就有的手机没有这个盐，照旧派生（`TestStoreWithoutADataSalt`），第一次恢复出厂设置后才有。量产时盐该在 TEE 的安全存储里、清除时销毁（**依赖硬件**）；现在它在数据分区上，删除不是擦除（§11.1）。

### 11.4 防盗锁

照安卓的 FRP（Factory Reset Protection）和 iPhone 的激活锁：登录了 Kario 账号的手机，不是机主用 PIN 码清除的，清除后要登录这个账号才能用。代码在 `shell/antitheft.go`，协议是 `antitheft` 包（kario-antitheft/1）。

| 环节 | 做法 |
|------|------|
| 什么时候开 | 设置 › 账号里登录了 Kario 账号（产品的 `PHONE_ACCOUNT_SERVER`）就开：Shell 向账号服务器绑定这台手机（`POST /v1/antitheft/bind`：账号的邮箱和应用专用密码（用验证码登录时是服务器给这台手机建的那一个，退出登录时先解除绑定、再吊销它，[19](19-core-apps.md) §1.1「用验证码登录」），加上设备对服务器一次性挑战的设备认证），服务器记下这台手机（按设备公钥）归这个账号；成功后 Shell 在持久区写记录（`/var/lib/slots/antitheft.json`：账号的 ID、打了码的邮箱如 `l***i@example.com`、设备号、随机令牌），在数据区写同一个令牌（`<状态目录>/shell/antitheft.json`，先写这个）。没成功时 1 分钟起每次加倍、至多 6 小时再试；退出了账号就不再等，再登录的账号马上绑定。绑定本身回 401（服务器不认密码：比如还没绑上时手机就在账号的网页上被退出登录了）时不再重试，这个账号算登录被拒绝（设置里「登录被拒绝」，同步也停下，[19](19-core-apps.md) §1.1「出错和退避」），等用户「立即同步」或重新登录；挑战之类别的请求回 401 不算。绑定回 409（服务器上这台手机还绑在别的账号上：前一个机主没解除的绑定，或者这台手机退出别的账号时留下的；回答不说是哪个账号）时也不再重试，日志里记着设备号；设置 › 账号的列表上写着这个账号的防盗锁没有开、这台手机还锁在另一个 Kario 账号上、要由原来的机主在那个账号网页的「防盗锁」里移除它（带设备号），下面一行「重试开启防盗锁」：按它马上再绑一次，还是 409 时说原来的机主还没移除；按「已在账号的网页上移除？」查到这台手机自己留下的绑定没了、或者重新登录时也马上再绑（[19](19-core-apps.md) §1.1「用验证码登录」的「防盗锁绑定回 409」）。恢复出厂设置的页面上写着它 |
| 什么时候关 | 退出 Kario 账号时（设了锁屏 PIN 码就先要它：不然拿到解锁着的手机的人能先退出账号，再从锁屏清除）；用 PIN 码从设置恢复出厂设置、没打开「保留防盗锁」时；锁着时服务器签了解除时。都删记录，并告诉服务器解除绑定（尽力而为）。退出账号前，解除不成时确认框事先就说：现在没有网络（Shell 在网络一变时、设置的账号页开着时至多每 30 秒看一次网络），或者服务器已不认这个账号的密码（同步、日历或绑定收到过 401）时，确认框写着防盗锁会在账号上一直开着、退出后要到账号网页的「防盗锁」里移除这台手机，替掉「会吊销这台手机的登录」那一句；能解除时确认框和原来一样。退出账号时没解除成（这台手机已在账号的网页上被退出登录，解除回 401；或者连不上）：服务器那边留着绑定，这台手机以后绑别的账号是 409，所以设置在退出的结果里说防盗锁在账号上还开着，账号列表上一直留着提示，写明要到账号网页的「防盗锁」里移除这台手机（带账号的邮箱和设备号），直到手机用设备认证问 `status` 得知没绑着了（列表开着时至多每分钟一次、按「已在账号的网页上移除？」时马上），或者这台手机又绑定成功（[19](19-core-apps.md) §1.1「用验证码登录」的「退出登录」） |
| 什么时候锁 | 开机时（`startTheft`）：持久区有记录，而记录写着锁（从锁屏清除、机主保留了防盗锁），或者数据区里没有这个令牌（数据区被换过：刷机、Shell 没要的清除）。所以从锁屏清除和刷数据分区一样锁上 |
| 锁着时 | 系统自己的界面盖在一切之上：写着「这台手机是在没有机主 PIN 码的情况下清除的。它原来登录着 Kario 账号 l***i@example.com」；左软键让服务器往那个邮箱发 6 位验证码，输入后按 OK；没输验证码时按 OK 是问服务器机主有没有在账号网页上移除这台手机；通话键只拨紧急号码（和锁屏同一条路，没有单独的用例），通话中挂断键挂断。别的键都不起作用，电脑注入的按键也不行 |
| 解除 | 服务器核对验证码（10 分钟、5 次），或者看到机主移除了这台手机，就用账号服务器的签名钥签一份解除 `{设备号, 账号, 手机这一次的随机数, 签发, 过期}`，签的是 `kario-antitheft-release/1\n` 加 JSON（`antitheft.Release`）。解除里带着签它的钥匙编号（`key`，[11](11-platform-architecture.md) §15.1 的换钥）。手机只认签名对得上产品给的公钥（`PHONE_FAMILY_KEY`，按编号挑其中一把：同一把钥签未成年人模式的策略，前缀各不相同）、设备号是自己的、账号是记录里的、随机数是这一次自己生成的解除（`antitheft.Verify`；不看手机的时钟：清除后的时钟不可信，只用一次的随机数就够防重放）。通过后删记录，手机像新的一样 |

协议（`antitheft` 包；每个请求前先拿一次性挑战；设备认证的应用名是 `system.antitheft`，覆盖 `antitheft.Nonce(用途, 账号, 挑战, 手机的随机数)`）：

| 请求 | 凭据 | 回答 |
|------|------|------|
| `POST /v1/antitheft/challenge` | — | `{challenge, expires_in}`（5 分钟，只用一次） |
| `POST /v1/antitheft/bind` | Basic：邮箱、应用专用密码；设备认证 | `{account, email}`；已绑在别的账号上 409（`error` 只说要那个账号的机主先移除它，不说是哪个账号） |
| `POST /v1/antitheft/unbind` | 同上 | 204 |
| `POST /v1/antitheft/status` | 设备认证（账号 ID、手机的随机数）；锁着的手机，和退出后留着绑定的手机 | `{bound, email}`；机主移除了时带 `release`；账号没了 404 |
| `POST /v1/antitheft/code` | 同上 | 202 `{email}`；每台手机每小时 5 次、每个账号 10 次，多了 429 |
| `POST /v1/antitheft/release` | 同上，加验证码 | 签好的解除；验证码不对 401 |
| `GET /v1/antitheft/devices`、`DELETE /v1/antitheft/devices/{设备号}` | 账号网页的会话（移除要 10 分钟内用验证码登录过，不然 403 带 `reauth`） | 绑着的手机；移除一台，它下次问时拿到解除 |

服务器一侧（kario-internal 的 `kario-accountsrv`）见内部文档 63 §9、64 §3.2。

威胁模型：

| 威胁 | 怎么挡 |
|------|--------|
| 偷了锁着的手机，从锁屏清除 | 清除后锁在防盗锁上，要账号邮箱收到的验证码；服务器的绑定和手机上的记录都还在 |
| 偷了解锁着的手机 | 从设置清除要锁屏 PIN 码，退出 Kario 账号也要；没设锁屏 PIN 码的手机挡不住（安卓的 FRP 也只在有锁屏凭据时起作用） |
| 刷数据分区 | 状态分区里的记录还在、数据区里没有令牌，照样锁。原型的设备密钥在数据分区里，刷掉后设备号变了：验证码照样能解除（解除写的是现在的设备号和记录里的账号），但出厂证书也没了（量产的设备密钥在 TEE 里，**依赖硬件**） |
| 连状态分区一起刷，或者改记录 | 挡不住：没有记录就不锁。要靠锁住的 bootloader 不让刷机，量产时记录放进 RPMB 或 TEE 的安全存储（**依赖硬件**）；服务器上的绑定还在，但开机时去问服务器这台手机是否还绑着**未实现** |
| 拿自己的账号绑别人的手机、替别人的手机要解除 | 每个请求都要那台手机的设备密钥签设备认证，覆盖用途、账号、一次性挑战；服务器按设备公钥记绑定，另一把钥冒充同一个设备号找不到这台手机；手机只认带自己这一次随机数的解除。量产时服务器带认证方的根（`--device-root`），只收灌装过证书的手机；内测手机没灌装，只能证明手里有那把钥 |
| 中间人（含终止 TLS 的反向代理）伪造解除 | 解除有账号服务器的签名，手机只认产品镜像里的公钥 |
| 重放旧的解除 | 解除里有手机这一次生成的随机数，只认这一个 |
| 刷验证码、猜验证码 | 每台手机每小时 5 次、每个账号 10 次；每个验证码 10 分钟、5 次，只对这台手机有效；验证码只发到账号的邮箱 |
| 偷到账号的邮箱 | 能解除这个账号的手机，也能在网页上移除；更强的登录（手机号、两步验证）**未实现** |
| 账号网页的登录留在别人的电脑上 | 移除手机要 10 分钟内用验证码登录过的会话，旧的会话移除不了被偷的手机（重新登录要账号邮箱里的验证码）；在网页上让手机退出登录不碰防盗锁 |
| 账号服务器的签名钥泄露 | 能给任何手机签解除；换钥要随系统更新换公钥，流程**未实现**；和未成年人模式的签名钥分开**未实现**（现在共用一把，前缀分开） |
| 注销账号 | 绑在它上面的手机都算机主移除了，下次问就解除，不会锁死 |

## 12. 为什么还要 TEE 厂商：TrustZone 是 CPU 的模式，不是软件

> 2026-11-26 调研。带链接的是来源里写着的；标 **推断** 的是从来源推出来、来源没有直说的；标 **未验证** 的要拿到模组厂或高通的资料才知道。

ARM 的应用处理器都有 TrustZone，那为什么 §4.1、§9 说指纹、PIN 码校验和 SOTER、IFAA 要「厂商的 TEE」？因为 TrustZone 只是硬件：CPU 的一种状态加上总线上的一位。安全世界里跑什么软件、谁能往里放软件，是芯片厂和整机厂用安全启动的钥匙定的，Kario 自己写的代码进不去。

### 12.1 TrustZone：CPU 的状态和总线上的一位

| 层 | 是什么 |
|----|--------|
| CPU | 处理器有安全和非安全两种状态。EL3（跑安全监控程序的那一级）总是安全的；EL3 以下是哪一种，由 `SCR_EL3.NS` 这一位定，只有 EL3 能改它。两种状态各有自己的物理地址空间（[Arm：Security states](https://support.arm.com/documentation/102418/0102/TrustZone-in-the-processor/Security-States)） |
| 总线和外设 | 每次访问在总线上带着安全属性（AXI 的 `AxPROT[1]`），内存前面的 TZASC 这类过滤器按它放行或拒绝，一段内存、一个外设（比如指纹传感器的 SPI）就这样只给安全世界用（[Arm：Completers, peripherals, and memories](https://support.arm.com/documentation/102418/0102/System-architecture/Completers--peripherals--and-memories)） |
| 软件 | TrustZone 不带软件：EL3 的监控程序、安全世界里的 TEE 操作系统、它上面的可信应用（TA），都要有人写、签名、随启动链加载。启动链从芯片的 ROM 开始，谁的钥匙能签这些镜像，谁就决定安全世界里有什么（下面两节） |

### 12.2 跑在里面的 TEE 操作系统

| TEE 操作系统 | 谁的 | 说明 |
|--------------|------|------|
| QTEE（原来叫 QSEE） | 高通 | 高通芯片上的，QCM6490 也是；Linux 经 `smcinvoke` 和它说话（内核的 `qcomtee` 驱动、用户态的 [libqcomtee](https://github.com/quic/quic-teec)，[内核文档](https://docs.kernel.org/tee/qtee.html)）。小米的高通机型用它（[Check Point](https://research.checkpoint.com/2022/researching-xiaomis-tee/)） |
| Kinibi | Trustonic | 三星 Exynos 等用它（[Project Zero](https://projectzero.google/2017/07/trust-issues-exploiting-trustzone-tees.html)）；系统级的 TA 要芯片厂、整机厂或 Trustonic 签（[Kinibi 510A 安全目标](http://www.commoncriteriaportal.org/files/epfiles/Trustonic-Kinibi-510A-ST-1.2.pdf)） |
| ISEE（豆荚，Beanpod） | 豆荚科技 | 国产的 TEE，联发科和它合作（[联发科新闻稿](https://www.mediatek.com/zh-cn/press-room/doujia_tee)、[豆荚白皮书](https://www.beanpodtech.com/en/whitepapers/isee-tee-security-foundation/)）；小米的联发科机型用它或 Mitee（[Check Point](https://research.checkpoint.com/2022/researching-xiaomis-tee/)） |
| OP-TEE | 开源（TrustedFirmware.org） | TA 用自己的钥匙签：编译时的 `default_ta.pem` 是公开的，产品要换成自己的、在线下或 HSM 里签（[OP-TEE 文档](https://optee.readthedocs.io/en/latest/building/trusted_applications.html)） |

### 12.3 可信应用要谁签

- 高通的安全启动：芯片的 ROM 里有高通的根，整机厂的根公钥的哈希在出厂时烧进熔丝（OTP），之后每一级镜像都要验过签名才加载；QTEE 的镜像可以由高通和整机厂各签一次，哪些镜像必须两家都签，是「高通按产品线预先配置的」（[高通：Secure Boot and Image Authentication](https://www.qualcomm.com/content/dam/qcomm-martech/dm-assets/documents/secure-boot-and-image-authentication-version_final.pdf)）。
- QTEE 只加载这条链认的 TA：高通公开的 [qtee-tas](https://github.com/qualcomm/qtee-tas) 是用测试钥匙签的、按芯片分（有 qcm6490），改了签名就失效；开了安全启动的设备上，整机厂要用自己的证书经 sectools 重新签 TA，再把根证书的哈希烧进熔丝，高通的工程师在 [meta-qcom #1454](https://github.com/qualcomm-linux/meta-qcom/issues/1454) 里这样说，同时说安全配置文件当时还没公开。高通 Linux 的文档也是整机厂用 sectools 签 `tz.mbn`，用 kodiak 的 fuse-blower 烧熔丝（[Sign and flash images](https://docs.qualcomm.com/doc/80-70020-11/topic/sign-and-flash-images.html)）。
- 所以「往 TEE 里放一个指纹 TA」要的是：能在这台手机的链上签 TA 的钥匙（整机厂的，熔丝里是它的哈希），和能写这个 TA 的 SDK、文档。熔丝一烧就改不了：Kario 拿到的模组要是已经烧了模组厂的根，就只有模组厂能签（**推断**，从上面两条来源）。
- 小米这样的整机厂能往 QSEE、豆荚的 TEE 里放自己签的 TA（[Check Point](https://research.checkpoint.com/2022/researching-xiaomis-tee/)），它们也是整机厂、手里有那把钥匙。

### 12.4 SOTER、IFAA 要什么

| | SOTER（腾讯，微信支付） | IFAA（支付宝牵头的联盟） |
|---|---|---|
| TEE 里的代码 | 腾讯不给 TEE 里的代码，由芯片厂或整机厂在 TEE 里实现 SOTER 的 TA，三级钥匙（ATTK、ASK、AuthKey）都在 TEE 里；小米就自己写了 soter TA（[Check Point](https://research.checkpoint.com/2022/researching-xiaomis-tee/)） | IFAA 的 TA，和指纹的 TA 在 TEE 里说话，密钥放在 RPMB 里（[专利 CN107133794A](https://patents.google.com/patent/CN107133794A/zh)） |
| 产线 | 出厂前在 TEE 里生成设备的根钥匙 ATTK，整机厂把公钥交给腾讯的服务器；应用的 ASK、每个场景的 AuthKey 由它往下派生（[SOTER wiki](https://github.com/Tencent/soter/wiki/%E5%8E%9F%E7%90%86)）；产线上用命令写进去、存在 RPMB（[腾讯云文章](https://cloud.tencent.com/developer/article/1005987)） | 产线上灌钥匙（[腾讯云文章](https://cloud.tencent.com/developer/article/1043697)）；每个机型一把（[腾讯云文章](https://cloud.tencent.com/developer/article/1043485)） |
| 认证 | 整机厂要过腾讯、微信支付的验收（[腾讯云文章](https://cloud.tencent.cn/developer/article/1030885)） | 先在泰尔实验室测，再过支付宝的测试（[腾讯云文章](https://cloud.tencent.com/developer/article/1043485)）；分 1–4 级（[博客](https://chujian521.github.io/blog/2024/12/07/IFAA%E6%8C%87%E7%BA%B9%E6%94%AF%E4%BB%98%E5%8D%8F%E8%AE%AE%E5%88%86%E6%9E%90/)） |

两样都要：TEE 里的 TA（要那把签名钥匙）、产线上灌的钥匙（要工站和 RPMB）、设备的认证（要整机厂去申请）。Kario 一个软件做不了任何一样；§4.5 说的 `security` 字段只有在这条链上才能签出来让服务端信。上面 SOTER、IFAA 的流程大多来自第三方文章，不是腾讯、支付宝的正式文档（**未验证**，正式的接入文档要以整机厂的身份去要）。

### 12.5 QCM6490 上能不能换成 OP-TEE

| 问题 | 现在知道的 |
|------|-----------|
| 有没有这条路 | 有：TF-A 的 RB3 Gen 2（QCM6490，Kodiak）移植里，TF-A 的 BL2 替掉 `tz.mbn`（XBL 照样从 tz 分区加载它），OP-TEE 当 BL32（[TF-A 文档](https://tf-a.docs.trustedfirmware.org/en/latest/plat/qti/rb3gen2.html)）；OP-TEE 的 Kodiak 平台 2025-10-31 合进主线（[optee_os #7547](https://github.com/OP-TEE/optee_os/pull/7547)）；meta-qcom 里有它的配方（[trusted-firmware-a-qcom.inc](https://github.com/qualcomm-linux/meta-qcom/blob/bbac4fd1/dynamic-layers/meta-arm/recipes-bsp/trusted-firmware-a/trusted-firmware-a-qcom.inc)） |
| 谁签 TZ 镜像 | TF-A 文档原话：`bl2.elf` 要「当作 TZ 镜像签名，有高通参与签名」；`fip.elf` 用 qtestsign 只放整机厂的测试签名，只能在没开安全启动的设备上用，开了要用 sectools v2 签。OSFC 2026 的报告里 BL2 是用 sectools 的测试模式签的（[OSFC 2026](https://talks.osfc.io/osfc-2026/talk/JQNFL3/)） |
| 量产的、烧了整机厂根的 QCM6490 认不认只有整机厂签的 BL2 | **未验证**。「有高通参与」和白皮书里「哪些镜像要两家都签由高通按产品线配置」放在一起看，可能要高通签（**推断**）；要问高通或模组厂 |
| 换了以后少什么 | TF-A 自己的驱动不做系统挂起（只有 WFI），要挂起得链接高通的 QTISECLIB 二进制库（TF-A 文档）；QTEE 和 OP-TEE 的设备树有冲突，给 DSP 启动用的 PAS 要在 OP-TEE 里做一个早期 TA（OSFC 2026）。QTEE 里别的服务（类 Keymaster 的 TA、DRM 等）跟着没了，要不要自己做**未验证** |
| 对 Kario 意味着 | 开发板上（没开安全启动）现在就能跑 OP-TEE，可以把 phone-keystored 的 PIN 码、模板、令牌搬进一个 OP-TEE 的 TA，验证做法（R15）；量产手机上能不能这样，看高通让不让、模组厂给不给签名（**未验证**）。就算能，OP-TEE 也不是 SOTER、IFAA 认证过的 TEE，认证还要重新做（**推断**） |

### 12.6 Kario 要模组厂给什么

| 要的 | 为什么 |
|------|--------|
| 安全启动的钥匙归谁、谁来签 | 熔丝里是谁的根，谁才能签 TZ、TA 和后面的镜像（§12.3）；要么模组出货时不烧、由 Kario 的整机厂烧自己的，要么模组厂替我们签 |
| 签好的 TZ/QTEE 镜像，或让我们换 OP-TEE 的签名 | §12.5；还要说清每一版的更新怎么签、谁签（系统更新里要带 TZ 的更新，[25](25-system-update.md)） |
| 在 QTEE 里签 TA 的权利，或 TA 的 SDK 和文档 | 指纹的匹配、PIN 码校验、令牌的钥匙放进 TEE（R15）；高通的 TA SDK 给不给模组厂的客户**未验证** |
| 指纹传感器的 TA 和 SPI 归安全世界 | 传感器厂（FPC、汇顶）的 TA 驱动它（§4.1）；SPI 和中断要在 TZ 的访问控制里划给安全世界；OK 键上的面阵传感器要传感器厂和模组厂一起做（§9） |
| RPMB 的灌装 | 产线上写 RPMB 的钥匙，SOTER、IFAA 和防盗锁的记录（§11.4）都要 |
| 产线上灌 SOTER 的 ATTK、IFAA 的钥匙，和认证 | §12.4；要整机厂的身份去和腾讯、支付宝谈 |
| 可信界面（Trusted UI） | PIN 码经可信输入路径进 TEE（§9 的 R15）；键盘和屏幕在安全世界里能不能用，看芯片和模组（**未验证**） |
