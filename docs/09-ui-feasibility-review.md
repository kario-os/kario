# 综合评审：TUI 能否撑起复杂 App · 两版方案合并

> 输入：本目录 01–14（全键盘机身 + telephonyd + 开源 Go TUI + 闭源 Slint GUI）与新稿「小屏专属 TUI 混合智能操作系统」（原文存档：90-draft-small-screen-tui-os.md（内部文档））。
> 状态：评审结论，**全部未实现**。§8 的 D1–D5 已确认，按本文建议执行。

## 0. 结论先行

1. **悲观对了一半。** 「在这台机器上用原版微信 / B站」确实做不到——但卡住的不是 TUI，是生态：它们是闭源的 Android / iOS 应用，就算做出最好的 GPU GUI，也一样跑不了。
2. **另一半不成立。** 「每个窗口都有选项入口、长按还有菜单」属于**交互结构**，键盘完全能表达：S60 的「选项」软键、BlackBerry 的菜单键、Android TV 的方向键焦点、桌面软件的右键菜单都证明过。**长按 = 对焦点元素按菜单键。** 详细语法见 [10-keyboard-interaction-model.md](10-keyboard-interaction-model.md)。
3. **TUI 真正的硬伤是图文混排**，新稿自己在「短板」里也承认了。可现代内容 App 的核心恰恰是图文混排：B站首页是缩略图流，微信聊天里有图片和表情，朋友圈是九宫格。只能「弹窗看图」的系统做不出这类应用。
4. **方案（D2 已定）：保留「按键优先」，放弃「字符网格」。** 交互按 TUI 的精神设计（文字优先、焦点驱动、没有隐藏手势），渲染用像素 GPU（已有的 Slint 路线），应用用**语义 UI 模型**描述（列表 / 菜单 / 表单 / 图片 / 媒体，每个元素带动作列表），由系统统一渲染。开源 `phone-tui` 保留为同一模型的文本渲染器（SSH / 串口 / 调试）。
5. **定位（D1 已定）：第二台手机 / 专注手机**（电话、短信、通讯录、笔记、音乐播客、阅读、终端），微信留在主力机上。若「必须能用微信」，现实路线是基于 AOSP 做键盘系统（多亲 Qin、Mudita Kompakt 都这么做），那会推翻当前的 Linux + telephonyd 栈（§5）。

## 1. 把问题拆成三层

两份文档都把三件事混在了一起：

| 层 | 问的是 | 决定因素 |
|----|--------|----------|
| **交互模型** | 用户怎么操作：焦点、选项菜单、长按、返回、搜索 | 设计规范；与渲染方式无关 |
| **渲染模型** | 屏幕上画什么：字符网格 vs 任意像素 | 字符网格画不了行内缩略图、比例字体、表情 |
| **应用生态** | 有没有微信 / B站 / 支付宝 | 厂商意愿 + 平台规模；与 TUI / GUI 都无关 |

把 B站 / 微信的典型界面元素放进去：

| 界面元素 | 所在层 | 按键 + 字符 TUI | 按键 + 像素 GUI |
|----------|--------|:---:|:---:|
| 每页「⋮ 更多」入口、多级设置 | 交互 | ✓ | ✓ |
| 长按消息 / 视频弹出菜单 | 交互 | ✓（菜单键） | ✓ |
| 底部 Tab、左右滑切换 | 交互 | ✓（数字键 / 左右键） | ✓ |
| 多选、批量删除 | 交互 | ✓（标记模式） | ✓ |
| 缩略图信息流（B站首页） | 渲染 | ✗ | ✓ |
| 聊天里的图片、表情包、头像 | 渲染 | ✗（只能 `[图片]` 占位） | ✓ |
| 朋友圈九宫格、评论区带图 | 渲染 | ✗ | ✓ |
| 视频播放 + 弹幕 | 渲染 | △（新稿的媒体图层可以做） | ✓ |
| 公众号文章、小程序（H5） | 渲染 + 生态 | ✗ | ✗（需要浏览器引擎 + 厂商） |
| 微信 / B站 / 支付宝的账号与内容 | 生态 | ✗ | ✗ |

读法：交互那几行键盘都能做；渲染那几行字符网格是瓶颈；生态那几行换什么 UI 技术都没用。

## 2. 先例

| 先例 | 说明了什么 |
|------|-----------|
| **诺基亚 S60、BlackBerry OS** | 2.4–3 寸、全键盘、无触屏，照样跑邮件、浏览器、IM、社交客户端；「选项软键 / 菜单键 + 焦点」就够了 |
| **B站 TV 版「云视听小电视」** | 官方为遥控器方向键重做的版本，长按 OK / 菜单键调出选项。但它是**厂商专门做的子集**（遥控器发不了弹幕；早期版本看不了 UP 主视频）。键盘化可行，前提是厂商愿意做 |
| **Android TV、桌面软件、读屏软件** | 只要每个元素声明「动作列表」，再复杂的 App 也能被方向键 / Tab + 菜单完全操作（读屏器把长按暴露为「自定义动作」） |
| **KaiOS** | 上亿出货的功能机系统，WhatsApp、YouTube 也是在 Google / Facebook 投入之后才有的——大厂只为有规模的平台适配 |
| **微信手表版** | 腾讯确实做过小屏版（Apple Watch、华为手表），都是体量巨大的平台 |
| **多亲 Qin 系列** | 国内「小屏 + 按键 + 要用微信」的产品跑的是 Android，市场已经验证过这条路 |
| **Mudita** | Pure 用自研 FreeRTOS 系统 MuditaOS（开源）；第二款 Kompakt 改为 **AOSP 12 深度定制** |
| **微信风控** | 模拟器 / 虚拟机环境登录会触发限制甚至封号（MuMu 模拟器官方帮助页有说明），Android 容器路线对重要账号有实际风险 |
| **Sxmo（postmarketOS）、Beepy** | Linux 上「按键 + 菜单 + 平铺」的小屏系统已有社区实践，可以直接借鉴；也说明「全球首款」类表述不成立 |

### 3.2 需要修正

| 新稿说法 | 实际情况 | 修正 |
|----------|----------|------|
| Notcurses「原生支持 DRM 直接输出，不依赖 TTY」 | **不成立**。Notcurses 只能跑在终端或 Linux 控制台上，DRM/KMS 后端的 issue（#1955）至今未实现。Linux 控制台最多 256/512 个字形，**显示不了中文** | 要在 DRM 上显示中文 TUI，得自己写像素渲染器——那已经是 GUI 了。见 §4 |
| DRM 双硬件图层是「零 CPU 开销的黑科技」 | 硬件图层（plane）是所有合成器（Android HWC、Wayland）都在用的省电优化；数量只有个位数，不可能每张缩略图各占一个。仍然需要 GPU 合成 | 图层直通保留为视频 / 相机的优化，不作为架构卖点 |
| Yocto Kirkstone / Mickledore | Kirkstone LTS 已于 **2026-04 停止维护**；Mickledore 2023-11 就停了 | 用 **Wrynose 6.0（LTS 至 2030-04）**，或 Scarthgap 5.0（LTS 至 2028-04） |
| 推荐 i.MX8MM | i.MX8M Mini 的 3D GPU 只支持 **OpenGL ES 2.0**，与 [06](06-gui-architecture.md) / [08](08-display-adaptive-refresh.md) 的 GLES3 / Vulkan 要求冲突 | 当时改为 RK3566 / i.MX8M Plus；**已改**为集成手机 SoC（61（内部文档）） |
| 「TUI 极低功耗、超长续航」 | 静态画面下 TUI 和 GUI 都不重绘，功耗几乎一样。耗电大头是屏幕背光、蜂窝模组、SoC 待机和后台唤醒。按 PinePhone、Librem 5 等 Linux 手机的社区经验，AP + 外置 LTE 模组认真调休眠后通常是「一到几天」，到不了功能机的「几周」 | 续航靠：无后台常驻、无轮询、积极 suspend、基带 DRX、留在 4G（61（内部文档） §1）、可选低功耗屏（反射 / 记忆 LCD，代价是不适合视频） |
| 6 个阶段约 13 周 | 一人业余开发不现实；光「打电话 + 音频路由 + 休眠唤醒」就要数月 | 见 §7 的粗估：到「能日常用的第二台手机」约 1.5–3 年 |
| 全文没有电话功能 | 只写了 Wi-Fi / 蓝牙，没有蜂窝、通话、短信 | 合并 01–11 的 telephonyd 栈 |
| 「全球首款 / 全球唯一」「已无传统 TUI 任何短板」 | 先例很多（§2）；图文混排的短板新稿自己也承认 | 对外表述去掉；评估类文字一律标「未实现 / 未验证」 |

### 3.3 不采纳或推迟

| 新稿内容 | 原因 | 处理 |
|----------|------|------|
| 预留接口，等微信 / 支付宝官方适配 | 没有商业动机；大厂只为有规模的平台适配（§2） | 不作为任何计划的前提 |
| 支付接口 | 支付需要央行 / 银行 / 卡组织认证与安全芯片 | 移出范围 |
| PC 低代码设计器 + QuickJS | 体量相当于再做一个产品，而且解决不了「没有微信」 | 推迟到 v2 之后；语义 UI 模型（§4）本身会让「拖拽生成 App」简单很多 |
| `.tapp` 原生动态库加载 | 第三方库进系统 UI 进程，一崩全崩 | 沿用 [07](07-ecosystem-and-store.md)：每个应用独立进程 |
| i3 平铺分屏 | 2.4–3.5 寸屏切成两半，每格每行只剩约 10 个汉字 | 不做通用平铺；只做固定场景分区（视频 + 评论、通话 + 笔记） |

## 4. 推荐方案：按键优先交互 + 像素渲染 + 语义 UI 模型

```
┌──────────────────────────────────────────────────────────────┐
│ 应用（独立进程）：只描述「有什么内容、每个元素能做什么」      │
│   电话 / 短信 / 通讯录 / 设置 / 第三方 .phoneapp             │
└───────────────┬──────────────────────────────────────────────┘
                │ phone.Ui：语义树 + 动作列表（草案，未实现）
┌───────────────▼──────────────────────────────────────────────┐
│ 系统 Shell：焦点、按键映射、选项菜单、软键、返回栈、搜索、任务 │
│   ├─ 像素渲染器 phone-gui（Rust + Slint，GPU，闭源）← 量产    │
│   └─ 文本渲染器 phone-tui（Go，开源）← SSH / 串口 / 调试      │
├──────────────────────────────────────────────────────────────┤
│ 媒体服务（按需启动）：图片 / 视频硬解 / PDF / 相机            │
│   → 向 Shell 提供画面；视频、相机可走硬件图层直通             │
├──────────────────────────────────────────────────────────────┤
│ 系统服务：telephonyd (C++23) · audio · power · display · pkg  │
├──────────────────────────────────────────────────────────────┤
│ Linux + BSP（Yocto）                                          │
└──────────────────────────────────────────────────────────────┘
```

为什么这么分：

1. **按键交互由系统统一负责，应用做不出「只能靠手势」的界面。** 应用只声明元素和动作；OK 键执行主动作，菜单键列出其余动作，快捷键显示在菜单项右侧。B站 / 微信那种复杂度就这样解：复杂度进菜单，不进手势。
2. **像素渲染解决图文混排。** 列表项里放缩略图、聊天里放图片和表情、评论里放 [doge]，都只是语义树里多一个 `Image` 节点。
3. **TUI 不白做。** 同一棵语义树，文本渲染器把图片降级为 `[图]`，就能在 SSH、串口、开发机终端里操作整台手机，也是开源社区的参与入口。新稿的「TUI 精神」变成**设计语言**：文字优先、栅格对齐、高对比、焦点永远可见、没有隐藏手势。
4. **留逃生口。** 相机、地图、游戏这类自由画布应用，用 Slint 直接画（[07](07-ecosystem-and-store.md) 的第二档应用），但必须处理按键事件，上架人工审核。

`phone.Ui` 的节点、动作和走查示例见 [10-keyboard-interaction-model.md](10-keyboard-interaction-model.md)。

## 5. 微信 / B站：三条现实路线

| 路线 | 做法 | 能得到 | 代价 / 风险 | 建议 |
|------|------|--------|-------------|------|
| **A. 不兼容（第二台 / 专注手机）** | 原生应用 + 开放协议 | 电话、短信、通讯录、笔记、日历、音乐 / 播客、阅读、邮件、终端 / SSH；开放协议 IM（Matrix、XMPP、SIP） | 国内社交只能留在主力机上；目标用户变窄 | **已定**（D1） |
| **B. Linux + Android 容器（Waydroid）** | 在本系统里开一个 Android「兼容窗口」 | 部分 APK 能跑 | 需要 4GB+ 内存（2–3GB 时 Android 会频繁杀前台应用）、触屏或虚拟光标、明显更耗电；微信对容器环境有封号风险；手机尺寸的界面塞进 3 寸屏体验差 | 不进 v1 / v2；最多作为高配 SKU 的实验项 |
| **C. 基于 AOSP 做键盘系统** | 像 Qin、Mudita Kompakt：AOSP + 自研 launcher 与系统应用 | 微信大概率可用（但仍是手机界面） | 推翻当前 Linux + telephonyd 栈；与「精简 Linux」理念冲突 | 只有「必须能用微信」时才选 |

路线 A 的补充（均 **未验证**）：

- **通知镜像**：主力机装一个伴侣应用（类似 KDE Connect），把微信通知转到这台机器上看；能否回复取决于对方应用的通知是否支持直接回复。不碰微信协议，风险低。
- **B站**：存在非官方 API 和第三方客户端，但属于服务条款灰区、随时可能失效——只能个人折腾，不作为产品功能。
- **Telegram**：官方开源的 TDLib 可以合法做原生客户端，但国内网络不可用。

## 7. 下一步：先花一个月，用最便宜的方式回答「行不行」

买板子、画 PCB 之前，先在电脑上验证交互语法：

1. 开一个与目标屏同分辨率的窗口（例如 320×240 横屏、480×640 竖屏各一套），只允许键盘操作。
2. 用假数据做两个「样本应用」：**B站式**（推荐流 → 视频页 → 弹幕开关 → 评论 → 回复）和 **IM 式**（会话列表 → 聊天 → 长按消息菜单 → 发图 → 看大图），外加电话三屏（待机 / 来电 / 通话中）。
3. 两种渲染各做一遍：像素版（Slint 桌面窗口）和文本版（终端里的 Bubble Tea）。
4. 自己连续用一周，记录每个任务的按键次数、有没有「找不到入口」的死角、文本版在哪些页面不可用。

**判定门槛**：两个样本应用的全部动作都能用按键完成且没有死角 → 交互模型成立，进入 [05](05-implementation.md) 的阶段 A / B；文本版不可用的页面清单 → 就是像素 GUI 必要性的证据。

工作量粗估（一人业余、每周 10–15 小时，仅供排期参考）：

| 里程碑 | 粗估 |
|--------|------|
| 桌面交互原型（本节） | 1 个月 |
| 开发板打电话 + telephonyd + phone-tui | 2–3 个月 |
| Shell + 语义模型 v0 + 电话 / 短信 / 通讯录 / 设置 | 4–8 个月 |
| 图片 / 视频 / 相机媒体服务 | 2–4 个月 |
| 定制 PCB + 外壳（可与软件并行） | 6–12 个月 |
| 到「能日常使用的第二台手机」 | 约 1.5–3 年 |

| D2 | 渲染：纯字符 TUI（新稿），还是像素渲染 + TUI 风格 + 语义 UI 模型 | **像素渲染 + TUI 风格 + 语义 UI 模型**；开源 TUI 为文本前端 |
| D3 | 显示：坚持 120Hz 硬约束，还是 60Hz 基线 + 120Hz 可选 | **60Hz 基线**，有合适的小尺寸 120Hz 屏再上 |
| D5 | 顶层应用的构建方式 | **语义 UI 应用 + JS 小程序为顶层；Web 引擎只作按需启动的 H5 组件（第 4 档），不作应用底座。** 依据：实测同一聊天应用 Web 路线内存约 8–10 倍、Web 版 57% 代码是自建按键交互层（[15](15-web-vs-semantic-benchmark.md)、[14](14-tui-route-and-app-framework.md)） |
| D4 | 平台愿景 | **平台提供超级应用所需的全部系统能力**（含 TUI 内视频通话、可信支付），厂商可用 SDK 发布 `phone.Ui`（TUI）版应用；见 [11](11-platform-architecture.md)、[12](12-super-app-capabilities.md) |

已写入 56-product-strategy.md（内部文档） §8 决策记录。

D4 与 D1 不冲突：D1 是近期定位（没有厂商应用时它就是第二台手机），D4 是平台目标。§5 的结论依然成立——不逆向、不做 Android 容器；微信等能否上架取决于厂商基于平台能力自己发布（技术之外的门槛见 [12](12-super-app-capabilities.md) §8）。D4 也澄清了 D2 的用词：「TUI 应用」指用 `phone.Ui` 写的应用，在终端里由文本渲染器显示（媒体用半块字符像素），在量产设备上由像素渲染器显示。
