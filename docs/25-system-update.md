# 系统更新（OTA）：A/B 系统槽与 dm-verity

> 状态：**原型 ✓**（QEMU）：A/B 槽、RAUC、更新包签名、系统槽的 dm-verity 与签名的 root hash、设置里的「系统更新」、增量（自适应）更新、分批推送与暂停、健康检查（Shell、渲染器、应用都起来）、启动失败与校验失败的自动回滚，`make yocto-ota-test` 在 QEMU 上验证（57（内部文档） 验证基线）。按版本的增量包（安卓 A/B 更新的做法：按块的操作加二进制差分，§5）：宿主机上单元测试 ✓、两对真实版本的槽映像上生成和应用逐字节核对 ✓；模拟器上经设置安装 ✓（`make yocto-ota-delta`，§5.5），未上真机。真机的引导方式、引导链的安全启动和基带固件更新随 R16。

## 0. 结论

- **两套系统分区（A/B 槽）**：更新写进没在运行的那个槽，写的过程中手机照常用，断电也只是这次更新作废；装完重启进新槽。
- **RAUC** 负责写槽：更新包是 verity 格式的 RAUC 包，签名用我们的更新密钥（开发密钥由 `yocto/ota-keys.sh` 生成，不进仓库；量产在 HSM 里签），镜像只信任自己密钥环里的 CA；包里写明适用的机型，别的机型拒装。从网址安装时边下边写（流式），不需要先存整包；为此更新服务器（以及中间的 CDN）必须支持 HTTP Range 请求，不支持时 RAUC 直接报错，不会退回整包下载。
- **系统槽只读、逐块校验（dm-verity）**：槽里是 ext4 加上它的哈希树；槽的「描述」（块数、哈希树位置、盐、root hash）用更新密钥签名，放在状态分区。开机时 initramfs 先用内置的 CA 证书验描述的签名，再经 dm-verity 以只读方式挂上系统；之后读到的每个块都和 root hash 对得上，改过一个字节的块读出来就是 I/O 错误。离线改系统分区、换一个自己算的 root hash 都过不了。
- **增量更新**：更新包带着槽映像每 4 KiB 一块的哈希（RAUC 的 `block-hash-index` 自适应模式）；流式安装时，两个槽里已经有的块直接从本机磁盘拷，只下载其余的块。不用为每对新旧版本另做差分包，一个包对所有旧版本都是增量。可每次重新链接的 Go 程序几乎整个都变，一轮开发要下载约半个包，所以发布时另为最近几个版本各做一个**增量包**（§5）：按块的操作（从本机的槽拷、二进制差分、写入新数据、写零），在手机上重建槽、重算哈希树，root hash 和签名的描述一致才让它启动；`latest.json` 按起始版本列出，手机取自己版本的那个，没有就用整包（自适应）。宿主机上，从 `c6b9001` 到 `be494c0` 这一轮（自适应在模拟器上实际下载 65.3 MB）的增量负载是 6.7 MB。
- **不降级**：发布版的镜像在 RAUC 的 `system.conf` 里写 `min-bundle-version=<自己的版本>`，比它旧的更新包（版本写在签名的清单里）一律拒装，不管更新服务器给的是什么；「设置 › 系统更新」也只提供比当前版本新的（`已是最新版本`）。所以要撤回一个坏版本，得用更高的版本号重新发。开发构建没有版本号，不做这项检查。
- **`latest.json` 的签名**（产品层给了公钥时，`PHONE_UPDATE_KEY`，[11](11-platform-architecture.md) §15）：更新服务器每次用在线密钥现签，响应头带 `X-Offer-Issued`（签发时间）和 `X-Offer-Signature`（Ed25519，签的是 `kario-offer/1`、签发时间和 `latest.json` 的原样内容）。设备不接受没签名的、签名不对的、签发超过 7 天的、比上次接受的还旧的。这样别人冒充或截住更新服务器，既改不了推送比例，也不能拿一份旧的 `latest.json` 让手机一直停在旧版本上。签名的是更新服务器（不开源，D11；签名和回报的格式在 `ota` 包里，手机和服务器共用）；分批推送的工具照常改文件，不用管签名。
- **系统数据也从更新服务器来**：节假日日历 `holidays.json`（每个地区的法定节假日和调休上班的周末，`ota.Holidays`；按使用时间选门禁卡时用，[30](30-nfc.md) §4）和 `latest.json` 放在一起，签法一样，只是签的是 `kario-data/1`、文件名、签发时间和原样内容（`ota.DataMessage`），一份签名挪不到别的文件上。有更新服务器时手机每天取一次（失败了一小时后再试），同样不接受没签名的、签名不对的、签发超过 7 天的、比手里的旧的，存在 `<状态目录>/shell/holidays.json`；更新服务器只在文件能按格式读通时才发。平台不带日历：日期是政府定的（中国是国务院办公厅每年的通知），要核对后放到更新服务器上，真的日历数据**未实现**；自测用测试日历（[30](30-nfc.md) §7）。
- **分批推送**：`latest.json` 里的 `rollout` 是这个版本已推给的设备比例（%），`paused` 让推送暂停。每台设备第一次检查时抽一个 0–9999 的随机分桶，存在两套系统共用的数据分区里，按它决定轮没轮到；服务器不知道哪台设备在哪一批。没轮到时设置里写明原因，不提供安装。
- **装得怎么样，告诉服务器**：手机装了更新，记下装进哪个槽、哪个版本；新槽被标记为好，或者已经回到旧槽，Shell 就向更新服务器 `POST /report`（版本、`good` 或 `rollback`、分桶），没送到下次启动再送。更新服务器的分批推送工具定时运行：按时间一档档调高 `rollout`（默认 1% → 10% → 50% → 100%，每档一天），某个版本的报告够多（默认 20 份）且回滚的超过阈值（默认 5%），或者一天后的回报够多且有应用崩溃的手机超过阈值（默认 10%），就把它设成 `paused`，暂停后要人手放开。
- **一天后再报一次**：新槽被标记为好满一天，Shell 再发一份回报（`kind: "day"`），带上这一天里应用崩溃的次数（崩溃记录里新槽好了以后的条数）；中间关了机就在下次启动时补发。装得上但跑起来老崩的版本也会因此停下来。
- **回报的签名**：密钥服务给每份回报做一次设备认证（`attest`，应用名记作 `system.ota-report`，随机数是版本、结果、分桶、种类和崩溃次数的 SHA-256（`kario-report/2`）；`system.` 开头的应用 ID 不让安装，别的应用冒充不了），随回报一起发。更新服务器配了认证方的根（`--device-root`）时只收这个根签过的回报，别的一律 403：伪造的「成功」冲淡不了回滚率。同一台手机同一版本的安装结论和一天后的回报各只算第一份（服务器存的是版本、种类加设备号的哈希，`reports.jsonl` 里不出现设备号）；解锁的手机（认证里的启动状态是 `unlocked`，可能跑着自己编的系统）照收，标上 `unlocked`，分批推送不计入。不给 `--device-root` 时照旧收不签名的回报。没灌装设备证书的手机，认证根是自己第一次开机时生成的，每台一个，服务器没法统一核对：要等产线灌装（[22](22-developer-api.md) §11）以后才能在真正的服务器上打开。开源的这一侧有 `ota.VerifyReport` 和命令行的 `phone-ota-verify`，谁都能核对回报。
- **新槽要「自证健康」**：新槽启动后，系统服务在运行，并且 Shell 带着渲染器起来、一个应用（设置）能启动并讲通协议，才标记为好；没被标记前每次启动扣一次机会，三次用完就回到上次好的槽。新槽在开机时就校验不过（描述的签名不对、数据和 root hash 不符），本次开机直接回到好的槽，不再给它机会。
- 整个选择由一个很小的 initramfs（busybox、veritysetup、openssl 和一个脚本，解压后约 16 MB）在内核启动后、系统启动前做，不依赖具体的 bootloader；它也负责挂上状态分区和数据分区。没有 A/B 分区的磁盘（开发用的单根文件系统镜像）走同一个 initramfs，按内核命令行的 `root=` 以读写方式启动，没有 dm-verity。
- 用户在「设置 › 系统更新」里看到当前版本和正在运行的槽，检查、安装、重启；签名不可信、不是给这台设备的包都会被拒绝并说明原因。

## 1. 分区

| 分区（GPT 名） | 内容 |
|------|------|
| `state` | 槽的启动状态和两个槽的签名描述（16 MB），initramfs 挂在 `/var/lib/slots` |
| `rootfs_a`、`rootfs_b` | 两套系统（各 1 GB，给以后更大的版本留余量），出厂时相同；只读 |
| `data` | 系统和用户的可写数据，两套系统共用，initramfs 挂在整个 `/var/lib`（应用数据在 `/var/lib/phone`）；挂不上时 `/var/lib` 只读，日志里说明 |

`/var/lib/slots/boot` 是四行文本：`slot`（下次启动哪个槽）、`good`（上次标记为好的槽）、`tries`（新槽剩几次启动机会）、`booted`（正在运行的槽）。只按格式解析、从不执行：槽只认 a、b，次数只认数字，坏掉的文件当作「启动 A」。`rootfs_<槽>.verity` 和 `.verity.sig` 是槽的描述和签名（CMS）。

挂载放在 initramfs 而不是 systemd 的 mount 单元里：mount 单元要先等设备出现，在没有这两个分区的磁盘上会白等 90 秒。系统的 fstab 里没有 `/` 这一行，systemd 不会去把只读的根重新挂成读写。initramfs 里的 `/dev/console`、`/dev/kmsg` 和挂载点由镜像的设备表（`phone-initramfs-devices.txt`）预先建好，内核在运行 `/init` 之前就要打开控制台。

## 2. 一次更新的过程

1. 设置里「检查更新」：Shell 读更新服务器的 `latest.json`（版本、说明、大小、更新包地址；可选的 `rollout`、`paused`），配置了公钥时先核对签名。暂停推送、分桶不在 `rollout` 之内、或者版本不比当前的新时，不提供这个版本，设置里显示原因（`system.update` 的 `held`）。
2. 「安装」：Shell 运行 `rauc install <地址>`。RAUC 先校验签名和机型，再把另一个槽标为不可启动、写入槽映像（ext4 加哈希树，原样写入；按块哈希，两个槽里已有的块从本机拷，其余经 HTTP Range 下载）；包里的钩子把这个槽的签名描述放进状态分区；最后设为下次启动（`slot` 换成新槽，`tries=3`）。`latest.json` 里有从本机版本出发的增量包时，地址是它：写槽的换成包里的安装钩子（§5.3），其余各步一样；它装不上就接着装整包。
3. 重启：initramfs 看到 `slot ≠ good` 且还有机会，扣一次（`tries=2`）；验描述的签名、用 veritysetup 打开槽、只读挂上，从新槽启动。任何一步不过，本次就从 `good` 那个槽启动，并让它继续当下次启动的槽。
4. 系统起来后 `phone-ota-good` 检查健康（`ota-healthy`）：telephonyd 在运行；显示服务在跑时（手机上总在跑，模拟器上要 `phone.gui=1`），还要等 Shell 写出 `/run/phone/healthy`（最多 120 秒）。Shell 在渲染器握手成功后，在后台启动设置应用，它讲通协议就写这个文件（Shell 版本、渲染器、应用、启动耗时），再结束它。通过就 `rauc status mark-good`：`good` 换成新槽，`tries=0`。渲染器起不来时 Shell 不断退出重启，文件不会出现。
5. 若新槽一直没标记为好（起不来、反复崩溃、健康检查不过），三次机会用完后 initramfs 回到 `good` 那个槽。

构建时 `phone-verity.bbclass` 给镜像加一种类型 `ext4.verity`：ext4 用 4 KiB 的块（dm-verity 按 4 KiB 校验），后面接上 veritysetup 算的哈希树（不带 verity 超级块，参数全在签名的描述里），描述用更新密钥签成 CMS；出厂磁盘（`phone-ab.wks.in`）两个槽都写入这份映像，状态分区预先放好两个槽的描述。RAUC 用自定义的引导后端（`rauc-boot`）读写同一份状态：`get-primary`、`set-primary`、`get-state`、`set-state`、`get-current`。

## 3. 验证

- `tools/slots_test.py`（`make test` 的一部分）：在临时目录里跑 RAUC 后端和 initramfs 的选择逻辑——更新后健康、更新后一直不健康（三次后回滚）、好槽被标坏、校验不过的槽当场被拒、状态文件损坏。
- `make yocto-ota-test`：更新包由支持 Range 的小 HTTP 服务（`yocto/ota-www.py`，记下每次请求发了多少字节）提供，在 QEMU 的 A/B 磁盘镜像上连开 11 次机，每次做一步再关机——A 上先对着分批推送为 0% 和暂停推送的两个服务器检查更新，设置里都不提供安装并说明原因；再拒装不受信任密钥签的包，再经「设置 › 系统更新」装好包到 B；B 带着显示服务起来（Shell、渲染器、设置应用），被标记为好；从 B 装到 A；A 在没有显示设备的模拟器上（`novga`）连开三次，渲染器起不来、健康检查不过；第七次回到 B；再装到 A，关机后在磁盘上改坏 A 的文件系统，下次开机 A 校验不过、当场回到 B；再装一次 A，关机后把状态分区里 A 的描述换成另一个 root hash（签名还是旧的），下次开机签名不对、当场回到 B。核对每次启动的槽、两次不提供、四次拒装、四次安装、每次安装的下载量不到包的四分之一、B 的健康记录、B 被标记为好以后向服务器报了 `good`，而且是签了名的（第一次开机后手机打印自己的认证根；`ota-www.py` 把回报原样存下，最后 `phone-ota-verify` 用这个根核对每一份，有一份不对测试就不过）、每次系统都经 dm-verity 只读运行、两次篡改各自被识别出的原因。拒装必须是因为签名（RAUC 的报错里提到签名或证书），下载失败之类的别的原因判为失败。不开源的产品仓库跑同一个测试时换上正式的更新服务器和分批推送工具（`OTA_SERVER`、`OTA_ROLLOUT`）：服务器当场核对、去重（同一台手机同一版本的后两份照收、不再计入），推送比例跟着回报调整。
- 测试里每次装的都是同一份映像，槽里已有绝大多数块，所以下载量是自适应模式的下限：每次约 4.2 MB，是 130.7 MB 更新包的 3%（几乎全是块哈希索引本身：每 4 KiB 一个 32 字节的哈希）。
- **跨版本**（`make yocto-ota-base` 存下一次构建的 A/B 磁盘、槽映像和文件清单，改动、重新构建后 `make yocto-ota-delta` 从它开机装新的更新包；现在它在基础磁盘的两份拷贝上各装一次，一次用对着基础做的增量包、一次用整包自适应，比较两边的下载量，§5.5）：从 `5da8671` 到 `88dc389`，中间是一轮开发（协议加了通知动作的字段、SDK 加了回调，商店、通知、音乐、云端服务都改了），实际下载 55.5 MB，是 142.4 MB 更新包的 38%，新槽起来后健康、回报送到。新槽映像 490.6 MB 里有 23065 个 4 KiB 块是手机上两个槽都没有的（90.1 MB，下载的是压缩后的）；变了的文件 38 个、145.6 MB，几乎全是 Go 程序：改了每个程序都链接的包（`ui`、`sdk`），所有程序都要重新链接，而 Go 程序里一处变化会让后面的代码整体移位，所以一个程序差不多整个都变了（phone-shell 22.8 MB、小程序宿主 16.9 MB、phone-cts-verify 14.3 MB……）。只改一个程序的修补版本，下载量大约就是这个程序压缩后的大小加 4.4 MB 的索引。
- 要再小，有三条路：把系统程序编成一个多入口的程序（像 busybox，按调用名分派），系统服务已经这样做了（下几条），但它省的是镜像大小，不是每轮的增量；按文件发二进制差分（安卓的做法；RAUC 自己不支持，现在由增量包的安装钩子来做，§5）；按内容分块下载（RAUC 的 casync 包），**未实现**。
- **多入口程序的估算**（2026-11，只编译、没上设备）：把产品镜像里的 27 个 Go 程序原样改成库、加一个按调用名分派的入口，和配方一样编成 arm64 静态 PIE、去掉符号：

  | 做法 | 未压缩 | gzip -9（近似更新包） | 每个进程启动时要重定位的页 |
  |------|------|------|------|
  | 现在：27 个程序各自链接 | 162 MB | 58 MB | 小应用 0.3 MB，Shell 2.0 MB（27 个合计 14.6 MB） |
  | 全部合成一个（PIE） | 31 MB | 11 MB | 每个进程都是 2.5 MB |
  | 只合 8 个系统服务（Shell、pushd、keystored、imed、audiod、mediad、sandbox、cts-verify；应用照旧） | 62 MB → 23 MB | 23 MB → 8 MB | 每个服务进程 2.0 MB |
  | 任一种改成非 PIE | 同上 | 同上 | 0 |

  只合服务几乎是白赚：Shell 本来就包含了其它服务的大部分代码，镜像少 39 MB，一轮开发的增量大约少 15 MB（55.5 MB → 约 40 MB）；代价是 pushd、imed 这些小服务每个多重定位约 1.5 MB，共享的运行时代码页能抵掉一部分，要在设备上量。全部合成一个时增量能降到约 10–15 MB，但两件事要先定：PIE 下 19 个 Go 进程每个都多出约 2 MB 私有页（合计约多 37 MB），改成非 PIE 就没有这项开销（还能共享代码页），代价是程序本身的地址不再随机（堆、栈、mmap 仍随机，Go 是内存安全的）；系统应用也会并进系统程序，不再是独立的包（它们本来就跟系统一起更新，商店装的应用不受影响）。
- **系统服务合成了一个程序 `kario-system`**（R45，学 k3s 和 busybox）：Shell、pushd、keystored、imed、audiod、mediad、沙箱启动器和 `phone-cts-verify` 的代码在 `programs/` 下各是一个包（`Main()`），`cmd/kario-system` 按调用名分派；镜像里 `bin/phone-shell` 等是指向它的链接，`lib/phone/bin/phone-sandbox` 也是，systemd 单元和启动应用的路径都没变。开发用的 `cmd/phone-*` 还在，各自三行，照样能单独编。仍是 PIE（程序地址随机）；应用照旧各是一个程序，它们是一个个单独装、单独验签的包。两处要小心：Shell 重新执行自己时用启动它的那个链接（进程名照旧是 `phone-shell`，不会变成 `kario-system`）；沙箱启动器的包级 `init` 锁线程只在以 `phone-sandbox` 名字启动时做，不会在别的服务里生效。
- **上设备量的结果**（2026-11，qemuarm64）：产品镜像里的 Go 程序从 27 个 156.2 MB 变成 20 个 116.4 MB（`kario-system` 23.7 MB，替下的 8 个原来共 62 MB），更新包 139.1 MB → 125.7 MB，每次安装的下载量 4.4 → 4.1 MB。内存没有省下来（公开镜像自测里的 PSS，合并前后各一次完整的自测）：Shell 28.2 → 18.4 MB，imed 11.2 → 14.4，audiod 10.0 → 11.8，pushd 9.0 → 11.0，keystored 4.7 → 8.5，五个合计 63.1 → 64.1 MB。从程序文件映射的代码页因为共享少了 14.4 MB，私有页多了 15.4 MB，比估算的每个服务 1.5 MB 多：除了 PIE 的重定位，每个进程还要跑链接进来的所有包的初始化（`GODEBUG=inittrace=1`：keystored 单独编时初始化分配 0.14 MB，合进来 1.5 MB，大头是 goja、goldmark、bubbletea 这些库自己的包级数据）。mediad 的堆随播放的视频变（三次自测 14.2–23.4 MB），没算进去。
- **合并之后再量一轮跨版本**：从 `c6b9001`（合并之后）到 `be494c0`，中间加了墓碑、画布节点、Wi-Fi 和蓝牙（镜像多了 iwd、BlueZ，内核加了无线和蓝牙）、USSD、商店的分批发布和自动更新，`ui` 和 `sdk` 都改了。实际下载 65.3 MB，是 130.7 MB 更新包的 50%，新槽健康、回报送到。新槽映像 457.1 MB 里有 30270 个块手机上没有（118.2 MB，未压缩）；变了和新加的文件 112 个、123.4 MB：重新链接的 Go 程序 19 个、107.0 MB（`kario-system` 23.8 MB、小程序宿主 16.9 MB、各个应用），新的贪吃蛇 2.5 MB，iwd 和 BlueZ 3.7 MB，其他新库 7.3 MB，内核模块 0.4 MB。所以合并没有让一轮的增量变小：应用不在 `kario-system` 里，`ui`、`sdk` 一改就全部重新链接，每个都几乎整个变了；之前估的「一轮约 40 MB」不对。真正能省的是按文件发二进制差分，或者按内容分块（RAUC 支持 casync：块的边界跟着内容走，前面的代码移了位，后面的块照样认得出）。前者现在有了（§5）：同一对版本在宿主机上做出的增量负载是 6.7 MB，约为这次实际下载的十分之一（这一对没在模拟器上装过，模拟器上装过的是 §5.5 里的另一对）；后者**未实现**。

- 宿主机自测用例「系统更新」：没有 A/B 分区的机器上，设置里说明不能在线更新。

- 真机的引导：高通 ABL 有自己的 A/B 槽机制（boot_a / boot_b），展锐用 U-Boot，各需要一个 RAUC 后端或让 initramfs 方案接在它们之后，**未实现**（随 R16）。
- 基带固件随厂商分区更新（随 R16）。
- 电量这类信号还不参与暂停，**未实现**。设备上的更新测试只覆盖了 `good` 的报告（回滚的那几次开机没有起显示服务，Shell 不在）；一天后的回报只在宿主机测试里（`TestDayReport`）。
- 增量包（§5）：模拟器上装过，含回滚、B 到 A、断电、损坏的包退回整包（§5.5）；安装时下载的比包本身多约 17%，是 RAUC 流式安装没有缓存、有的块读了两次（§5.5），**未改进**。设置里写的是选中的增量包的大小（`available.delta` 的 `size`，后面括号里是整包多大；服务器没给大小时只写「增量更新」，不写整包的）✓（单元测试）。应用器也装进了系统镜像（`/usr/bin/phone-ota-delta`），钩子问它 `can-apply`，它读得了这个负载就用它，流式安装就不下载包里那份；发布工具给已有合适应用器的旧版本做的包不放应用器（§5.3、§5.4）：模拟器上用镜像里的应用器装过不带应用器的包 ✓。改名前的 0.6.0、0.7.0 没有更新路径（机型串不同，§5.4）。

## 5. 按版本的增量包

> 状态：宿主机 ✓（各部分的单元测试；两对真实版本的槽映像上生成、应用、逐字节核对）；模拟器上经设置安装 ✓（`make yocto-ota-delta`：RAUC 运行安装钩子，给别的版本做的包被钩子拒绝；装上后不健康就回滚、B 到 A、写的时候断电、损坏的包退回整包，§5.5），未上真机。

自适应模式按块找，Go 程序重新链接后几乎每一块都变了，所以一轮开发约要下载半个更新包（§3）。安卓的 A/B 更新（`update_engine` 的负载，`delta_generator` 生成）为每对新旧版本做一个负载：按块的操作，没变的块从本机的旧槽拷，变了的文件发二进制差分。这里照它的模型做，代码在 `ota/delta`（负载格式、生成、应用）、`ota/delta/bsdiff`、`ota/delta/xz`、`ota/delta/ext4`、`ota/verity` 和命令 `phone-ota-delta`，都只用 Go 标准库和自己写的代码，没有新的依赖。

### 5.1 负载格式

负载是一个头（`KDLT`、格式版本、清单长度）、一份 JSON 清单和各操作的数据，数据按操作的顺序一段接一段，所以从头读到尾就能边下边写。清单写明起始映像（版本、字节数、SHA-256、它的 verity root hash）、目标映像（字节数、SHA-256）和目标的 verity 描述（块数、哈希树位置、盐、root hash）。映像指槽里 dm-verity 覆盖的那部分（ext4），哈希树不在负载里，手机上重算。每个操作写明读哪些块、写哪些块（4 KiB 块的区段，按顺序各当作一条流），以及数据的、读到的源数据的、写出结果的 SHA-256：

| 操作 | 做什么 |
|------|------|
| `REPLACE` | 写入操作带的数据：xz 压缩的或原样的 |
| `SOURCE_COPY` | 从起始槽拷块，块在哪儿都行（不必在原位置） |
| `SOURCE_BSDIFF` | 起始槽的块加二进制差分得出新块 |
| `ZERO` | 写零 |

- 压缩用 xz（LZMA2）：标准库里没有 zstd 也没有 xz，解压器是自己写的（`ota/delta/xz`，xz 文件格式加 LZMA2，按 xz 程序的输出测过，宿主机上解一个 Go 程序约为 xz 程序速度的七成）；压缩在构建机上调用 xz 程序（`-9e`，字典按数据大小）。不加 Go 模块。
- 二进制差分是自己写的 bsdiff（`ota/delta/bsdiff`）：用 Colin Percival 公开的方法（BSD 许可的思路，代码和补丁格式是我们的），旧数据的后缀数组（SA-IS 算法），找到的精确匹配在至少一半字节相同的范围里向两边延伸，存成逐字节的差（代码只是移了位或地址变了时几乎全是零，压得很小），配不上的存原样；补丁是控制、差、额外三条流，各自 xz 压缩。
- 清单在用之前整份核对：操作认得、区段都在映像里、目标的每一块恰好由一个操作写、数据按顺序紧挨着、每个哈希都在。

### 5.2 生成

`phone-ota-delta generate --source <旧> --target <新的槽映像> --out rootfs.kdelta [--report report.json]`，在构建机上跑。旧的可以是槽映像（`<文件>.desc` 是它的描述），也可以是一个发布版的 A/B 磁盘（`.wic` 或 `.wic.gz`：取 `rootfs_a`，描述从状态分区读）。ext4 自己解析（`ota/delta/ext4`：超级块、组描述、inode、extent 树和老式的块映射、目录），得出每个文件的数据在哪些块。

1. 目标的每一块：全零的写零；起始槽里哪儿有一样的块就从那儿拷（先看上一块拷的后一块、再看同一位置、再按哈希找）；剩下的是新的。
2. 有新块的文件：起始槽里同一路径的文件（没有就找同名的唯一一个；新加的程序找同一目录里大小最接近的程序）做二进制差分，补丁比只写这个文件的新块小就用它（整个文件一个 `SOURCE_BSDIFF`），否则写新块。
3. 小文件的新块和文件系统的元数据（inode 表、目录、位图……）一起压缩，写成每个最多 4 MiB 的 `REPLACE`。
4. 生成器在写出之前，先在内存里把负载应用到起始映像上，结果必须就是目标映像、哈希树算出签名的 root hash。报告给出负载和整个映像、和自适应安装的估计（块哈希索引加上含有起始槽里没有的块的那些 128 KiB 包内块，按 mksquashfs 的 gzip 压缩）的对比，和每个变了的文件怎么发、多大。

### 5.3 安装

增量包是一个 RAUC 包（verity 格式），和整包用同一把更新密钥签名，同样写机型和版本（所以 `min-bundle-version` 照样拒绝降级）。槽的映像是负载 `rootfs.kdelta`，标了 `hooks=install`：RAUC 验完签名、把另一个槽标为不可启动后，不自己写槽，而是运行包里的钩子 `delta-hook`；包里还有目标的签名描述和为机器编的 `phone-ota-delta`。选安装钩子而不是让 Shell 自己应用：签名、机型、不降级、标记槽、流式下载全是 RAUC 现成的，钩子失败 RAUC 就不把槽设为下次启动；Shell 只是换一个地址装。应用器有两份：系统镜像里一份（`/usr/bin/phone-ota-delta`，单独的程序，只链接更新的代码，一个版本里很少变），包里一份（和负载同一次构建，格式总对得上，给镜像里还没有应用器、或者它不读这个格式的旧系统用）。钩子问系统的应用器 `phone-ota-delta can-apply <负载>`：它自己读负载头里的格式号（`KDLT` 后面的 4 个字节），读得了就打出格式号、退出 0，钩子就用系统的，流式安装时包里那份（压缩后约 1.2 MB）不会被读、不会下载；读不了（退出 3，或者是不认这条命令的旧应用器）就用包里的；包里也没有就失败，RAUC 不标记这个槽，Shell 接着装整包。系统的应用器在 dm-verity 之下，和包里那份一样可信。格式号不让钩子自己读：手机上的 busybox 没开 `CONFIG_DESKTOP`，它的 `od` 不认 `-A -t -j -N`，早先的钩子用 `od` 读，在模拟器上读出空的格式号，从不用系统的应用器，不带应用器的包全都装不上（每次都退回整包，§5.5）；宿主机的测试用的是 GNU 的 `od`，没发现。现在钩子的测试只给它 busybox 也有的几个命令（`sed`、`mv`、`sync`、`tee`、`tail`、`rm`、`cp`、`grep`）。应用器的输出另存一份在 `/run/phone-ota-delta.log`：用的是哪个应用器、用了多久、内存峰值，或者停在哪一步。

钩子：读状态分区里正在运行的槽，先删掉要写的槽的旧描述（写了一半的槽没有描述可用），然后运行应用器：

1. 写之前全部核对：清单有效；清单里的 verity 描述和包里签名的描述一字不差；起始映像就是正在运行的槽（清单里的 root hash 和状态分区里这个槽的描述比，没有 root hash 时把整个槽读一遍算 SHA-256），不是就报「这个包是给别的系统版本的」，什么都不写。
2. 逐个操作：读它的数据，核对 SHA-256；读源块，经正在运行的槽的 dm-verity 设备（`/dev/mapper/root_a`），每一块都由内核校验过，再核对源数据的 SHA-256；算出结果，核对 SHA-256，写进另一个槽。
3. 全部写完后同步、丢掉页缓存，从设备读回整个映像：SHA-256 必须是目标映像的，重算的哈希树的 root hash 必须是签名描述里的；再把哈希树写在映像后面。

任何一步不对，应用器退出失败，钩子失败，RAUC 不标记这个槽，它也没有描述，initramfs 不会用它。都对了钩子才把签名描述放进状态分区（和整包的 `verity-hook` 一样），RAUC 再把它设为下次启动；下次开机 initramfs 照常验描述的签名、经 dm-verity 打开。负载从头到尾只读一遍：RAUC 流式安装时经 HTTP Range 只下载包里被读到的部分，也就是负载（用包里的应用器时还有它）。下载量比包本身多约 17%：RAUC 的流式安装（NBD → dm-verity → squashfs）没有下载缓存，读了两次的块就下载两次（§5.5 的测量）。

### 5.4 发布和选择

`latest.json`（照旧整体签名）多一项 `deltas`，每项是一个增量包和它的起始版本：

```json
{"version": "0.8.0", "size": 130652032, "url": "phone-bundle-0.8.0.raucb", "rollout": 10,
 "deltas": [{"from": "0.7.0", "from_root_hash": "c02eb5fb3706f7eb78f84a8da06a82fbaf6d6b4eb8bac681ea546fd2a0f93579", "size": 7900000, "url": "phone-delta-0.7.0-0.8.0.raucb"}]}
```

手机（`shell/update.go`）在提供这个版本时挑增量包：有 `from_root_hash` 的，只有正在运行的槽的 root hash（状态分区里它的描述）就是它时才用（这就是那个映像）；没有的，按发布版本号（`from` 等于本机版本）。挑中的放在 `system.update` 的 `available.delta`，安装时先装它，装不上就接着装整包。没有合适的增量包就装整包（自适应）。

发布工具（kario-internal 的 `tools/release.py`）为 `dist/` 里最近的 `--deltas` 个（默认 3）有 A/B 磁盘的发布版各做一个增量包：经 `make yocto-bundle OTA_DELTA_FROM="<版本>=<磁盘>…"` 进构建容器，`yocto/qemu-ota-delta.sh bundle` 对每个版本生成负载、用 `phone-bundle-delta` 配方打包签名，放进 `dist/v<版本>/phone-delta-<旧>-<新>.raucb`，写进 `latest.json`。更新服务器 `kario-otasrv` 不用为增量包改（它提供所有 `*.raucb`）。

每个发布版的 `MANIFEST.json` 记下它的镜像里的应用器读哪些负载格式（`ota_delta_formats`：发布工具在 kario 正是构建用的那个提交、没有本地改动时编出 `phone-ota-delta` 问 `formats`；问不了就不记）。从记了格式的旧版本出发的增量包，`OTA_DELTA_FROM` 里写成 `<版本>@<格式,…>=<磁盘>`，`qemu-ota-delta.sh bundle` 生成负载后读它的格式号，在其中就不往包里放应用器（`phone-bundle-delta` 配方只在 `PHONE_DELTA_DIR` 里有应用器时才带上它），并记下由谁来应用（`<标签>.raucb.applier`：`system` 或 `bundle`）；别的照旧带着，`--bundle-applier` 让每个包都带。没有这项记录的旧版本（0.7.1，它的镜像里也没有应用器），从它出发的增量包照旧带应用器；0.6.0、0.7.0 的机型串不同，不做增量包（下面）。

**机型串（RAUC 的 `compatible`）发布以后不能改。** RAUC 只装 `compatible` 和本机 `system.conf` 里一字不差的包，整包、增量包都一样。改名（J1J → Kario）时它从 `j1j-qemuarm64` 变成了 `kario-qemuarm64`，所以 0.6.0、0.7.0 的手机装不了之后任何一版：模拟器上 0.7.0 装 0.7.1 的整包，RAUC 报 `Compatible mismatch: Expected 'j1j-qemuarm64' but bundle manifest has 'kario-qemuarm64'`（§5.5）。这两版只是试发布，没有发到手机上，所以不做迁移（迁移的做法：给旧机型另做一个写旧机型串的整包，装上后新系统就是新机型串；但 0.7.0 的 Shell 只认 `latest.json` 的 `url`，新老手机要分开给地址）。发布工具（`tools/release.py`）从每个包末尾的签名里读出机型串，记进 `MANIFEST.json` 的 `compatible`：和这一版不同的旧版本不做增量包（做了也装不上）；紧挨着的上一版就不同时停下来不发，除非加 `--compatible-change`，明知那一版的手机从此收不到更新。

增量包还要加上应用器（压缩后约 1.2 MB）和包本身的开销。模拟器上实测的那一对：增量安装下载 2.76 MB，是自适应（17.1 MB）的 16%、整包的 2%。`c6b9001` 的基础磁盘出自另一个构建目录（另一套更新密钥），只能量负载，不能在这次构建的模拟器上装。

**下载量为什么比包大**（测试服务器按请求记下每段的起点，`ota-delta.py ranges` 按包的结构分开算）：`0a4ff0b` → 第 5 轮的增量包 6.6 MiB，一次安装发了 95 个请求、7.7 MiB，包里每个字节都下载过，其中 1.1 MiB（17%）下载了两次：负载 5.4 MiB 里重复 0.7 MiB，squashfs 的其余部分（应用器、钩子、描述、元数据）重复 0.4 MiB，dm-verity 的哈希树整个读了两遍。RAUC 的流式安装是 NBD 设备上叠 dm-verity 再挂 squashfs，没有下载缓存，内核读了两次的块就下载两次（是哪个读者读了第二次，**未细查**）。这是一个比例上的开销，不随包的大小翻倍；包很小时固定的几十 KB 显得多（18 KB 的包下载 51 KB）。
