## 0. 结论

- **两套系统分区（A/B 槽）**：更新写进没在运行的那个槽，写的过程中手机照常用，断电也只是这次更新作废；装完重启进新槽。
- **RAUC** 负责写槽：更新包是 verity 格式的 RAUC 包，签名用我们的更新密钥（开发密钥由 `yocto/ota-keys.sh` 生成，不进仓库；量产在 HSM 里签），镜像只信任自己密钥环里的 CA；包里写明适用的机型，别的机型拒装。从网址安装时边下边写（流式），不需要先存整包；为此更新服务器（以及中间的 CDN）必须支持 HTTP Range 请求，不支持时 RAUC 直接报错，不会退回整包下载。
- **系统槽只读、逐块校验（dm-verity）**：槽里是 ext4 加上它的哈希树；槽的「描述」（块数、哈希树位置、盐、root hash）用更新密钥签名，放在状态分区。开机时 initramfs 先用内置的 CA 证书验描述的签名，再经 dm-verity 以只读方式挂上系统；之后读到的每个块都和 root hash 对得上，改过一个字节的块读出来就是 I/O 错误。离线改系统分区、换一个自己算的 root hash 都过不了。
- **增量更新**：更新包带着槽映像每 4 KiB 一块的哈希（RAUC 的 `block-hash-index` 自适应模式）；流式安装时，两个槽里已经有的块直接从本机磁盘拷，只下载其余的块。不用为每对新旧版本另做差分包，一个包对所有旧版本都是增量。可每次重新链接的 Go 程序几乎整个都变，一轮开发要下载约半个包，所以发布时另为最近几个版本各做一个**增量包**（§5）：按块的操作（从本机的槽拷、二进制差分、写入新数据、写零），在手机上重建槽、重算哈希树，root hash 和签名的描述一致才让它启动；`latest.json` 按起始版本列出，手机取自己版本的那个，没有就用整包（自适应）。宿主机上，从 `c6b9001` 到 `be494c0` 这一轮（自适应在模拟器上实际下载 65.3 MB）的增量负载是 6.7 MB。负载格式 2 里大文件的补丁分块（每块做出新文件的 4 MiB），每块有自己的 SHA-256，边下边核对、边打，内存里一次只有一块；旧文件也不整个读进内存，打的时候经几个窗口从正在运行的槽按需读（§5.1）。
- **断点续装**：增量包装到一半断电或断网，下次装同一个包时应用器从它记下的检查点接着装，做过的那部分负载不再读、不再下载；最后照样整个核对，检查点错了只会让这次安装失败（§5.6）；检查点也可以落在一个分块的补丁中间（格式 2）；负载读不下去（断网）或被叫停时，应用器在停下的地方再记一个，不靠几秒前的那个。下载断了 Shell 过一会儿自己再试，最多三次。
- **自动更新**：「设置 › 系统更新」里打开（开源镜像默认关，产品可以在配置里默认打开）后，Shell 每天查一次，只在连着不计费的 Wi-Fi（§6.1）、电量过半或在充电、不在通话时在后台以低优先级下载安装；装的时候条件没了（来了电话、拔了充电器而电量不到一半、换到计费网络或离开 Wi-Fi）就停下，条件回来后接着装（增量包从检查点接着装，整包从槽里拿已经写好的块），停着的时候写了一半的槽不会启动；下载只走开始时的那个 Wi-Fi，离开它就断，不会接着走移动数据（§6）；装好后通知「现在重启」或「今晚」；选了今晚，夜里息屏、不在通话、近期没有闹钟时才重启（§6）。
- **计费网络**：Wi-Fi 网络可以是按流量计费的（手机热点）：自动检测（网络的 DHCP 服务器发安卓的 `ANDROID_METERED`，或者地址在手机热点的网段里），也可以在「设置 › Wi-Fi」里给每个网络选「是」「否」，默认自动；移动数据总是计费的。系统更新、商店的自动更新和要求不计费网络的应用后台任务在计费网络上等着，下载到一半换到计费网络时停下，用户自己开始的照常下载（§6.1）。
- **不降级**：发布版的镜像在 RAUC 的 `system.conf` 里写 `min-bundle-version=<自己的版本>`，比它旧的更新包（版本写在签名的清单里）一律拒装，不管更新服务器给的是什么；「设置 › 系统更新」也只提供比当前版本新的（`已是最新版本`）。所以要撤回一个坏版本，得用更高的版本号重新发。开发构建没有版本号，不做这项检查。
- **`latest.json` 的签名**（产品层给了公钥时，`PHONE_UPDATE_KEY`，[11](11-platform-architecture.md) §15）：更新服务器每次用在线密钥现签，响应头带 `X-Offer-Issued`（签发时间）、`X-Offer-Signature`（Ed25519，签的是 `kario-offer/1`、签发时间和 `latest.json` 的原样内容）和 `X-Offer-Key`（签它的钥的钥号；`ota.SignHeaders`、`ota.VerifyHeaders`）。`PHONE_UPDATE_KEY` 的文件一行一把公钥：平时一把，换钥时是签名的那一把和下一把，手机按钥号挑出那一把验，没有钥号（旧的服务器）就每把都试；更新服务器的钥能换，换的步骤和没跟上的手机会怎样见 [11](11-platform-architecture.md) §15.1。设备不接受没签名的、签名不对的、钥号不在文件里的、签发超过 7 天的、比上次接受的还旧的。这样别人冒充或截住更新服务器，既改不了推送比例，也不能拿一份旧的 `latest.json` 让手机一直停在旧版本上。签名的是更新服务器（不开源，D11；签名和回报的格式在 `ota` 包里，手机和服务器共用）；分批推送的工具照常改文件，不用管签名。
- **系统数据也从更新服务器来**：节假日日历 `holidays.json`（每个地区的法定节假日和调休上班的周末，`ota.Holidays`；按使用时间选门禁卡时用，[30](30-nfc.md) §4；日历标「休」「班」也用它，应用经 `holidays.get` 读，[22](22-developer-api.md) §4.4）和 `latest.json` 放在一起，签法一样，只是签的是 `kario-data/1`、文件名、签发时间和原样内容（`ota.DataMessage`），一份签名挪不到别的文件上。有更新服务器时手机每天取一次（失败了一小时后再试），同样不接受没签名的、签名不对的、签发超过 7 天的、比手里的旧的，存在 `<状态目录>/shell/holidays.json`；更新服务器只在文件能按格式读通时才发。平台不带日历：日期是政府定的（中国是国务院办公厅每年的通知），要核对后放到更新服务器上，真的日历数据**未实现**；自测用测试日历（[30](30-nfc.md) §7）。
- **分批推送**：`latest.json` 里的 `rollout` 是这个版本已推给的设备比例（%），`paused` 让推送暂停。每台设备第一次检查时抽一个 0–9999 的随机分桶，存在两套系统共用的数据分区里，按它决定轮没轮到；服务器不知道哪台设备在哪一批。没轮到时设置里写明原因，不提供安装。
- **装得怎么样，告诉服务器**：手机装了更新，记下装进哪个槽、哪个版本；新槽被标记为好，或者已经回到旧槽，Shell 就向更新服务器 `POST /report`（版本、`good` 或 `rollback`、分桶），没送到下次启动再送。更新服务器的分批推送工具定时运行：按时间一档档调高 `rollout`（默认 1% → 10% → 50% → 100%，每档一天），某个版本的报告够多（默认 20 份）且回滚的超过阈值（默认 5%），或者一天后的回报够多且有应用崩溃的手机超过阈值（默认 10%），就把它设成 `paused`，暂停后要人手放开。
- **一天后再报一次**：新槽被标记为好满一天，Shell 再发一份回报（`kind: "day"`），带上这一天里应用崩溃的次数（崩溃记录里新槽好了以后的条数）；中间关了机就在下次启动时补发。装得上但跑起来老崩的版本也会因此停下来。
- **回报的签名**：密钥服务给每份回报做一次设备认证（`attest`，应用名记作 `system.ota-report`，随机数是版本、结果、分桶、种类和崩溃次数的 SHA-256（`kario-report/2`）；`system.` 开头的应用 ID 不让安装，别的应用冒充不了），随回报一起发。更新服务器配了认证方的根（`--device-root`）时只收这个根签过的回报，别的一律 403：伪造的「成功」冲淡不了回滚率。同一台手机同一版本的安装结论和一天后的回报各只算第一份（服务器存的是版本、种类加设备号的哈希，`reports.jsonl` 里不出现设备号）；解锁的手机（认证里的启动状态是 `unlocked`，可能跑着自己编的系统）照收，标上 `unlocked`，分批推送不计入。不给 `--device-root` 时照旧收不签名的回报。没灌装设备证书的手机，认证根是自己第一次开机时生成的，每台一个，服务器没法统一核对：要等产线灌装（[22](22-developer-api.md) §11）以后才能在真正的服务器上打开。开源的这一侧有 `ota.VerifyReport` 和命令行的 `phone-ota-verify`，谁都能核对回报。
- **新槽要「自证健康」**：新槽启动后，系统服务在运行，并且 Shell 带着渲染器起来、一个应用（设置）能启动并讲通协议，才标记为好；没被标记前每次启动扣一次机会，三次用完就回到上次好的槽。新槽在开机时就校验不过（描述的签名不对、数据和 root hash 不符），本次开机直接回到好的槽，不再给它机会。
- 整个选择由一个很小的 initramfs（busybox、veritysetup、openssl 和一个脚本，解压后约 16 MB）在内核启动后、系统启动前做，不依赖具体的 bootloader；它也负责挂上状态分区和数据分区。没有 A/B 分区的磁盘（开发用的单根文件系统镜像）走同一个 initramfs，按内核命令行的 `root=` 以读写方式启动，没有 dm-verity。
- 用户在「设置 › 系统更新」里看到当前版本和正在运行的槽，检查、安装、重启；签名不可信、不是给这台设备的包都会被拒绝并说明原因。

## 1. 分区

| 分区（GPT 名） | 内容 |
|------|------|
| `state` | 槽的启动状态和两个槽的签名描述（16 MB），initramfs 挂在 `/var/lib/slots`；恢复出厂设置的请求和防盗锁的记录也在这里，清除碰不到它（[31](31-lock-and-biometrics.md) §11） |
| `rootfs_a`、`rootfs_b` | 两套系统（各 1 GB，给以后更大的版本留余量），出厂时相同；只读 |
| `data` | 系统和用户的可写数据，两套系统共用，initramfs 挂在整个 `/var/lib`（应用数据在 `/var/lib/phone`）；挂不上时 `/var/lib` 只读，日志里说明；恢复出厂设置时 initramfs 先重新格式化它，只拷回设备的身份（[31](31-lock-and-biometrics.md) §11.1） |

`/var/lib/slots/boot` 是四行文本：`slot`（下次启动哪个槽）、`good`（上次标记为好的槽）、`tries`（新槽剩几次启动机会）、`booted`（正在运行的槽）。只按格式解析、从不执行：槽只认 a、b，次数只认数字，坏掉的文件当作「启动 A」。`rootfs_<槽>.verity` 和 `.verity.sig` 是槽的描述和签名（CMS）。

挂载放在 initramfs 而不是 systemd 的 mount 单元里：mount 单元要先等设备出现，在没有这两个分区的磁盘上会白等 90 秒。系统的 fstab 里没有 `/` 这一行，systemd 不会去把只读的根重新挂成读写。initramfs 里的 `/dev/console`、`/dev/kmsg` 和挂载点由镜像的设备表（`phone-initramfs-devices.txt`）预先建好，内核在运行 `/init` 之前就要打开控制台。

## 2. 一次更新的过程

1. 设置里「检查更新」：Shell 读更新服务器的 `latest.json`（版本、说明、大小、更新包地址；可选的 `rollout`、`paused`），配置了公钥时先核对签名。暂停推送、分桶不在 `rollout` 之内、或者版本不比当前的新时，不提供这个版本，设置里显示原因（`system.update` 的 `held`）。
2. 「安装」：Shell 运行 `rauc install <地址>`。RAUC 先校验签名和机型，再把另一个槽标为不可启动、写入槽映像（ext4 加哈希树，原样写入；按块哈希，两个槽里已有的块从本机拷，其余经 HTTP Range 下载）；包里的钩子把这个槽的签名描述放进状态分区；最后设为下次启动（`slot` 换成新槽，`tries=3`）。`latest.json` 里有从本机版本出发的增量包时，地址是它：写槽的换成包里的安装钩子（§5.3），其余各步一样；它装不上就接着装整包。下载断了（RAUC 报下载、连接、超时之类的错，或者增量包的应用器说负载读不下去了）不算装不上：Shell 过 30 秒、2 分钟、8 分钟各再装一次同一个包，增量包从检查点接着装（§5.6），三次都不行才算失败。装的时候设置里显示进度：RAUC 打印的百分比，增量包是应用器做到第几步；等着重试时写明第几次、几点再试。
3. 重启：initramfs 看到 `slot ≠ good` 且还有机会，扣一次（`tries=2`）；验描述的签名、用 veritysetup 打开槽、只读挂上，从新槽启动。任何一步不过，本次就从 `good` 那个槽启动，并让它继续当下次启动的槽。
4. 系统起来后 `phone-ota-good` 检查健康（`ota-healthy`）：telephonyd 在运行；显示服务在跑时（手机上总在跑，模拟器上要 `phone.gui=1`），还要等 Shell 写出 `/run/phone/healthy`（最多 120 秒）。Shell 在渲染器握手成功后，在后台启动设置应用，它讲通协议就写这个文件（Shell 版本、渲染器、应用、启动耗时），再结束它。通过就 `rauc status mark-good`：`good` 换成新槽，`tries=0`。渲染器起不来时 Shell 不断退出重启，文件不会出现。
5. 若新槽一直没标记为好（起不来、反复崩溃、健康检查不过），三次机会用完后 initramfs 回到 `good` 那个槽。

构建时 `phone-verity.bbclass` 给镜像加一种类型 `ext4.verity`：ext4 用 4 KiB 的块（dm-verity 按 4 KiB 校验），后面接上 veritysetup 算的哈希树（不带 verity 超级块，参数全在签名的描述里），描述用更新密钥签成 CMS；出厂磁盘（`phone-ab.wks.in`）两个槽都写入这份映像，状态分区预先放好两个槽的描述。RAUC 用自定义的引导后端（`rauc-boot`）读写同一份状态：`get-primary`、`set-primary`、`get-state`、`set-state`、`get-current`。

## 3. 验证

- 要再小，有三条路：把系统程序编成一个多入口的程序（像 busybox，按调用名分派），系统服务已经这样做了（下几条），但它省的是镜像大小，不是每轮的增量；按文件发二进制差分（安卓的做法；RAUC 自己不支持，现在由增量包的安装钩子来做，§5）；按内容分块下载（RAUC 的 casync 包），**未实现**。
- **多入口程序的估算**（2026-11，只编译、没上设备）：把产品镜像里的 27 个 Go 程序原样改成库、加一个按调用名分派的入口，和配方一样编成 arm64 静态 PIE、去掉符号：

  | 做法 | 未压缩 | gzip -9（近似更新包） | 每个进程启动时要重定位的页 |
  |------|------|------|------|
  | 现在：27 个程序各自链接 | 162 MB | 58 MB | 小应用 0.3 MB，Shell 2.0 MB（27 个合计 14.6 MB） |
  | 全部合成一个（PIE） | 31 MB | 11 MB | 每个进程都是 2.5 MB |
  | 只合 8 个系统服务（Shell、pushd、keystored、imed、audiod、mediad、sandbox、cts-verify；应用照旧） | 62 MB → 23 MB | 23 MB → 8 MB | 每个服务进程 2.0 MB |
  | 任一种改成非 PIE | 同上 | 同上 | 0 |

  只合服务几乎是白赚：Shell 本来就包含了其它服务的大部分代码，镜像少 39 MB，一轮开发的增量大约少 15 MB（55.5 MB → 约 40 MB）；代价是 pushd、imed 这些小服务每个多重定位约 1.5 MB，共享的运行时代码页能抵掉一部分，要在设备上量。全部合成一个时增量能降到约 10–15 MB，但两件事要先定：PIE 下 19 个 Go 进程每个都多出约 2 MB 私有页（合计约多 37 MB），改成非 PIE 就没有这项开销（还能共享代码页），代价是程序本身的地址不再随机（堆、栈、mmap 仍随机，Go 是内存安全的）；系统应用也会并进系统程序，不再是独立的包（它们本来就跟系统一起更新，商店装的应用不受影响）。
- **系统服务合成了一个程序 `kario-system`**（R45，学 k3s 和 busybox）：Shell、pushd、keystored、imed、audiod、mediad、沙箱启动器和 `phone-cts-verify` 的代码在 `programs/` 下各是一个包（`Main()`），`cmd/kario-system` 按调用名分派；镜像里 `bin/phone-shell` 等是指向它的链接，`lib/phone/bin/phone-sandbox` 也是，systemd 单元和启动应用的路径都没变。开发用的 `cmd/phone-*` 还在，各自三行，照样能单独编。仍是 PIE（程序地址随机）；应用照旧各是一个程序，它们是一个个单独装、单独验签的包。两处要小心：Shell 重新执行自己时用启动它的那个链接（进程名照旧是 `phone-shell`，不会变成 `kario-system`）；沙箱启动器的包级 `init` 锁线程只在以 `phone-sandbox` 名字启动时做，不会在别的服务里生效。
- **上设备量的结果**（2026-11，qemuarm64）：产品镜像里的 Go 程序从 27 个 156.2 MB 变成 20 个 116.4 MB（`kario-system` 23.7 MB，替下的 8 个原来共 62 MB），更新包 139.1 MB → 125.7 MB，每次安装的下载量 4.4 → 4.1 MB。内存没有省下来（公开镜像自测里的 PSS，合并前后各一次完整的自测）：Shell 28.2 → 18.4 MB，imed 11.2 → 14.4，audiod 10.0 → 11.8，pushd 9.0 → 11.0，keystored 4.7 → 8.5，五个合计 63.1 → 64.1 MB。从程序文件映射的代码页因为共享少了 14.4 MB，私有页多了 15.4 MB，比估算的每个服务 1.5 MB 多：除了 PIE 的重定位，每个进程还要跑链接进来的所有包的初始化（`GODEBUG=inittrace=1`：keystored 单独编时初始化分配 0.14 MB，合进来 1.5 MB，大头是 goja、goldmark、bubbletea 这些库自己的包级数据）。mediad 的堆随播放的视频变（三次自测 14.2–23.4 MB），没算进去。
- **合并之后再量一轮跨版本**：从 `c6b9001`（合并之后）到 `be494c0`，中间加了墓碑、画布节点、Wi-Fi 和蓝牙（镜像多了 iwd、BlueZ，内核加了无线和蓝牙）、USSD、商店的分批发布和自动更新，`ui` 和 `sdk` 都改了。实际下载 65.3 MB，是 130.7 MB 更新包的 50%，新槽健康、回报送到。新槽映像 457.1 MB 里有 30270 个块手机上没有（118.2 MB，未压缩）；变了和新加的文件 112 个、123.4 MB：重新链接的 Go 程序 19 个、107.0 MB（`kario-system` 23.8 MB、小程序宿主 16.9 MB、各个应用），新的贪吃蛇 2.5 MB，iwd 和 BlueZ 3.7 MB，其他新库 7.3 MB，内核模块 0.4 MB。所以合并没有让一轮的增量变小：应用不在 `kario-system` 里，`ui`、`sdk` 一改就全部重新链接，每个都几乎整个变了；之前估的「一轮约 40 MB」不对。真正能省的是按文件发二进制差分，或者按内容分块（RAUC 支持 casync：块的边界跟着内容走，前面的代码移了位，后面的块照样认得出）。前者现在有了（§5）：同一对版本在宿主机上做出的增量负载是 6.7 MB，约为这次实际下载的十分之一（这一对没在模拟器上装过，模拟器上装过的是 §5.5 里的另一对）；后者**未实现**。

- 宿主机自测用例「系统更新」：没有 A/B 分区的机器上，设置里说明不能在线更新。另两个用例在模拟的 A/B 手机上（自测的 `ota` 命令，§6）：经设置安装，下载断了自己再试，设置里显示进度和重试时间；自动更新的条件、通知和夜里重启。

## 4. 还没做的

- 运行中发现坏块现在只返回 I/O 错误；是否改成重启并回到另一个槽（dm-verity 的 `restart_on_corruption`）要等真机上有了引导链再定。

- 后台自动更新（§6）：装的时候条件没了（拔了充电器而电量低、来了电话、换到计费网络或离开 Wi-Fi）就停下、条件回来后接着装（RAUC 没有暂停，update_engine 可以挂起）：宿主机单元测试和自测 ✓；增量包由停止文件让应用器停在检查点，RAUC 不把这个槽设为下次启动，再装从检查点接着装，在 QEMU 上跑过（§5.5 的 s1）；整包经 Shell 的回环代理下载、停下时断开它，只在宿主机上测过（单元测试、自测里模拟的 RAUC），**未上 QEMU**；代理到更新服务器的连接都从第一条的地址出去，Wi-Fi 没了这个地址也没了，下载就断，不会改走移动数据（宿主机单元测试 ✓，真机上**未试**）；用户把连着的网络改成计费时当场停下，不等下一次看网络（宿主机单元测试和自测 ✓）；Shell 看着条件决定停下和接着装也只在宿主机上测过，QEMU 上那一步是直接建停止文件；计费网络（§6.1）宿主机 ✓；模拟的 A/B 手机上的用例在 QEMU 镜像里通过，真的 RAUC 在 A/B 磁盘上的自动更新 2026-11-25 在 QEMU 上跑过 ✓（§3：计费时不装、改成不计费后在后台装好，没有在装到一半时停它），真机上**未跑**。
- 断点续装（§5.6）：断电后接着装 2026-11-15 在 QEMU 上跑过（§5.5 第 2 条）；断网后接着装 2026-11-19 在 QEMU 上跑过（§5.5 的 n1），前两次**没过**：第一次装到一半网断了，Shell 认出来，30 秒后再装；可网要断 90 秒，这次 RAUC 连包头都取不到，钩子没跑，RAUC 只说「安装失败」，Shell 没当成下载断了，接着装整包（自适应，下载 4.5 MB，照样装好），没等到 2 分钟后的那次。现在重试时钩子没跑、RAUC 也没说出签名、版本、机型这些原因的失败，也算下载断了（`stillDown`，测试先确认旧代码失败；RAUC 的「Failed to stream bundle」也认作下载）。重跑：第二次重试时从第 89 个操作里第 5 个的第 5 块接着装，0.9 MB 负载没再读，装好，没碰整包；但这次一共下载了增量包的 1.76 倍（10.5 MB，要不到 1.5 倍）：断网前已经下了包的 60%，检查点才记到第 5 个操作。查下来（§5.5「谁读了第二次」）：断网前发出的 3.59 MB 里 1.39 MB 是装之前 udev 的探测和内核的预读，检查点比应用器读到的地方落后约 0.7 MB（周期的检查点），重试时探测和预读又来一遍；改掉以后（udev 不探测网络块设备、负载全从设备读、断网时在停下的地方记检查点）再跑：从第 30 个操作接着装，3.1 MB 负载没再读，一共下载包的 1.31 倍；再加上读设备从一个块开始翻倍、包里垫的文件（§5.5），是 1.15 倍 ✓。设备上应用器读到的确实是 I/O 错误（钩子的日志说负载读不下去）。

## 5. 按版本的增量包

> 状态：宿主机 ✓（各部分的单元测试；两对真实版本的槽映像上生成、应用、逐字节核对）；模拟器上经设置安装 ✓（`make yocto-ota-delta`：RAUC 运行安装钩子，给别的版本做的包被钩子拒绝；装上后不健康就回滚、B 到 A、写的时候断电、损坏的包退回整包，§5.5），未上真机。

自适应模式按块找，Go 程序重新链接后几乎每一块都变了，所以一轮开发约要下载半个更新包（§3）。安卓的 A/B 更新（`update_engine` 的负载，`delta_generator` 生成）为每对新旧版本做一个负载：按块的操作，没变的块从本机的旧槽拷，变了的文件发二进制差分。这里照它的模型做，代码在 `ota/delta`（负载格式、生成、应用）、`ota/delta/bsdiff`、`ota/delta/xz`、`ota/delta/ext4`、`ota/verity` 和命令 `phone-ota-delta`，都只用 Go 标准库和自己写的代码，没有新的依赖。

### 5.1 负载格式

负载是一个头（`KDLT`、格式号、清单长度）、一份 JSON 清单和各操作的数据，数据按操作的顺序一段接一段，所以从头读到尾就能边下边写。清单写明起始映像（版本、字节数、SHA-256、它的 verity root hash）、目标映像（字节数、SHA-256）和目标的 verity 描述（块数、哈希树位置、盐、root hash）。映像指槽里 dm-verity 覆盖的那部分（ext4），哈希树不在负载里，手机上重算。每个操作写明读哪些块、写哪些块（4 KiB 块的区段，按顺序各当作一条流），以及数据的、读到的源数据的、写出结果的 SHA-256：

| 操作 | 做什么 |
|------|------|
| `REPLACE` | 写入操作带的数据：xz 压缩的或原样的 |
| `SOURCE_COPY` | 从起始槽拷块，块在哪儿都行（不必在原位置） |
| `SOURCE_BSDIFF` | 起始槽的块加二进制差分得出新块；格式 2 里大文件的补丁分块（下面） |
| `ZERO` | 写零 |

- 压缩用 xz（LZMA2）：标准库里没有 zstd 也没有 xz，解压器是自己写的（`ota/delta/xz`，xz 文件格式加 LZMA2，按 xz 程序的输出测过，宿主机上解一个 Go 程序约为 xz 程序速度的七成）；压缩在构建机上调用 xz 程序（`-9e`，字典按数据大小）。不加 Go 模块。
- 二进制差分是自己写的 bsdiff（`ota/delta/bsdiff`）：用 Colin Percival 公开的方法（BSD 许可的思路，代码和补丁格式是我们的），旧数据的后缀数组（SA-IS 算法），找到的精确匹配在至少一半字节相同的范围里向两边延伸，存成逐字节的差（代码只是移了位或地址变了时几乎全是零，压得很小），配不上的存原样；补丁是控制、差、额外三条流，各自 xz 压缩。
- **分块的补丁**（格式 2，`ota/delta/bsdiff` 的 `Pieces`）：比一块（默认 4 MiB）大的文件，补丁按新文件每 4 MiB 切开，每块写明它在旧文件里从哪儿开始，带着自己的控制、差、额外三条流（各自 xz），不依赖别的块；清单里这个操作写明每块做多少字节（`piece`，4 KiB 的整数倍，至多 16 MiB）和每块的长度、SHA-256（`pieces`）。应用器一块一块地读，先核对这块的 SHA-256 再打、写进目标，内存里只有一块解压后的流（原来是整个补丁解压后的全部，差不多和新文件一样大）；块与块之间可以记检查点（§5.6）。一块装得下的文件照旧是整个的补丁。格式号是 2：应用器读 1 和 2，生成器默认写 2，`--format 1` 给只读 1 的应用器（§5.4）。宿主机上分块和不分块打出的结果逐字节相同；固定的合成系统（`TestPayloadSize`：一个 5.9 MB 的程序重新链接、两个应用重新链接、一个新应用、900 个小文件里改、加、删一些）的负载格式 1 是 309328 字节、格式 2 是 310465 字节（多 0.37%：每块的流单独压缩，清单多了每块的哈希），测试要求不超过 330000 字节。
- **旧文件不整个读进内存**（`bsdiff.Patcher`、`ApplyAt`）：应用器先把这个操作的源块顺着读一遍、核对 SHA-256，打补丁时再按补丁要的位置从源槽读，经几个窗口（4 个，每个至多 256 KiB）：顺着一个窗口的末尾往下读时一次读 256 KiB，跳到别处（挪了位置的代码）只读这一步要的（至少 4 KiB），不把待会儿回来要用的窗口挤掉。读的是正在运行的槽的 dm-verity 设备，每块照样由内核校验，结果另有哈希。一块解压后的三条流和这些窗口在块与块之间重用，不再每块重新分配。负载格式不变：格式 1、2 照旧，整个的补丁也这样读旧文件（只是它的三条流仍整个解压）。宿主机上量的（`TestBigFilePatchMemory`：两个槽里各一个 32 MiB 的程序，新的是旧的重新链接的样子，补丁分成 8 块；应用器在单独的进程里跑，量它自己的 VmHWM）：内存峰值原来 90–91 MiB（32 MiB 的旧文件整个在内存里，加上每块的流），现在 16 MiB 上下（几次量的是 15.8–16.3 MiB），不随文件变大；源槽读了 64.1 MiB（48.4 MiB 的映像，程序核对哈希读一遍、打补丁再读一遍）；结果和目标逐字节相同。改动很密的数据（2 MiB 里 1500 处：改字节，插入、删掉、挪动一段）旧文件约读 1.5 遍，整段挪动的约 1.07 遍（`TestStreamedOldData`）。
- 清单在用之前整份核对：操作认得、区段都在映像里、目标的每一块恰好由一个操作写、数据按顺序紧挨着、每个哈希都在、分块的块数盖住目标、各块的长度加起来就是这个操作的数据。上限：清单至多 64 MiB（生成器也不写更大的），映像至多 2²⁴ 块（64 GiB），一个操作至多 65536 块（256 MiB）、数据至多 1 GiB，一块至多 4 倍块大小加 2 MiB（最坏是三条流都原样存），所以一个负载清单后面的数据至多 2⁵⁴ 字节。

### 5.2 生成

`phone-ota-delta generate --source <旧> --target <新的槽映像> --out rootfs.kdelta [--report report.json]`，在构建机上跑。旧的可以是槽映像（`<文件>.desc` 是它的描述），也可以是一个发布版的 A/B 磁盘（`.wic` 或 `.wic.gz`：取 `rootfs_a`，描述从状态分区读）。ext4 自己解析（`ota/delta/ext4`：超级块、组描述、inode、extent 树和老式的块映射、目录），得出每个文件的数据在哪些块。

1. 目标的每一块：全零的写零；起始槽里哪儿有一样的块就从那儿拷（先看上一块拷的后一块、再看同一位置、再按哈希找）；剩下的是新的。
2. 有新块的文件：起始槽里同一路径的文件（没有就找同名的唯一一个；新加的程序找同一目录里大小最接近的程序）做二进制差分，补丁比只写这个文件的新块小就用它（整个文件一个 `SOURCE_BSDIFF`），否则写新块。
3. 小文件的新块和文件系统的元数据（inode 表、目录、位图……）一起压缩，写成每个最多 4 MiB 的 `REPLACE`。
4. 生成器在写出之前，先在内存里把负载应用到起始映像上，结果必须就是目标映像、哈希树算出签名的 root hash。报告给出负载和整个映像、和自适应安装的估计（块哈希索引加上含有起始槽里没有的块的那些 128 KiB 包内块，按 mksquashfs 的 gzip 压缩）的对比，和每个变了的文件怎么发、多大。

### 5.3 安装

增量包是一个 RAUC 包（verity 格式），和整包用同一把更新密钥签名，同样写机型和版本（所以 `min-bundle-version` 照样拒绝降级）。槽的映像是负载 `rootfs.kdelta`，标了 `hooks=install`：RAUC 验完签名、把另一个槽标为不可启动后，不自己写槽，而是运行包里的钩子 `delta-hook`；包里还有目标的签名描述和为机器编的 `phone-ota-delta`，dm-verity 的预读会伸进镜像时还有一个谁也不读的垫的文件（`zz-verity-pad`，至多 252 KiB，§5.5）。选安装钩子而不是让 Shell 自己应用：签名、机型、不降级、标记槽、流式下载全是 RAUC 现成的，钩子失败 RAUC 就不把槽设为下次启动；Shell 只是换一个地址装。应用器有两份：系统镜像里一份（`/usr/bin/phone-ota-delta`，单独的程序，只链接更新的代码，一个版本里很少变），包里一份（和负载同一次构建，格式总对得上，给镜像里还没有应用器、或者它不读这个格式的旧系统用）。钩子问系统的应用器 `phone-ota-delta can-apply <负载>`：它自己读负载头里的格式号（`KDLT` 后面的 4 个字节；在挂上的包里从包的设备读，不经挂载的文件，§5.5），读得了就打出格式号、退出 0，钩子就用系统的，流式安装时包里那份（压缩后约 1.2 MB）不会被读、不会下载；读不了（退出 3，或者是不认这条命令的旧应用器）就用包里的；包里也没有就失败，RAUC 不标记这个槽，Shell 接着装整包。系统的应用器在 dm-verity 之下，和包里那份一样可信。格式号不让钩子自己读：手机上的 busybox 没开 `CONFIG_DESKTOP`，它的 `od` 不认 `-A -t -j -N`，早先的钩子用 `od` 读，在模拟器上读出空的格式号，从不用系统的应用器，不带应用器的包全都装不上（每次都退回整包，§5.5）；宿主机的测试用的是 GNU 的 `od`，没发现。现在钩子的测试只给它 busybox 也有的几个命令（`sed`、`mv`、`sync`、`tee`、`tail`、`rm`、`cp`、`grep`）。应用器的输出另存一份在 `/run/phone-ota-delta.log`：用的是哪个应用器、用了多久、内存峰值，或者停在哪一步；还有进度（做到第几步）和从哪个检查点接着装的（§5.6），设置读它显示进度。钩子给应用器 `--checkpoint <状态分区>/rootfs_<槽>.progress`，镜像里旧的应用器不认这个选项，钩子先问 `phone-ota-delta can-resume`，不认就不给，照旧从头装；它的回答里有 `stop` 时还给 `--stop /run/phone-ota-delta.stop`：这个文件一出现，应用器在下一个操作或下一块之前停下、记下检查点、退出失败（Shell 停下自动更新时建它，§6）。整包的钩子（`verity-hook`）在 RAUC 写槽之前也删掉这个槽的旧描述（和检查点），装到一半失败或被停下的槽同样没有描述可用。

钩子：读状态分区里正在运行的槽，先删掉要写的槽的旧描述（写了一半的槽没有描述可用），然后运行应用器：

1. 写之前全部核对：清单有效；清单里的 verity 描述和包里签名的描述一字不差；起始映像就是正在运行的槽（清单里的 root hash 和状态分区里这个槽的描述比，没有 root hash 时把整个槽读一遍算 SHA-256），不是就报「这个包是给别的系统版本的」，什么都不写。
2. 逐个操作：读它的数据，核对 SHA-256；读源块，经正在运行的槽的 dm-verity 设备（`/dev/mapper/root_a`），每一块都由内核校验过，再核对源数据的 SHA-256（顺着读一遍，不留在内存里；拷贝和补丁用的时候再从设备读，§5.1）；算出结果，核对 SHA-256，写进另一个槽。
3. 全部写完后同步、丢掉页缓存，从设备读回整个映像：SHA-256 必须是目标映像的，重算的哈希树的 root hash 必须是签名描述里的；再把哈希树写在映像后面。

任何一步不对，应用器退出失败，钩子失败，RAUC 不标记这个槽，它也没有描述，initramfs 不会用它。都对了钩子才把签名描述放进状态分区（和整包的 `verity-hook` 一样），RAUC 再把它设为下次启动；下次开机 initramfs 照常验描述的签名、经 dm-verity 打开。负载从头到尾只读一遍：RAUC 流式安装时经 HTTP Range 只下载包里被读到的部分，也就是负载（用包里的应用器时还有它）。经 squashfs 读负载时下载量比包本身多约 17%：RAUC 的流式安装（NBD → dm-verity → squashfs）没有下载缓存，读了两次的块就下载两次（§5.5 的测量）；所以应用器现在不经 squashfs 读负载，而是从包的设备直接读（§5.5「改成从包的设备直接读」）。

### 5.4 发布和选择

`latest.json`（照旧整体签名）多一项 `deltas`，每项是一个增量包和它的起始版本：

```json
{"version": "0.8.0", "size": 130652032, "url": "phone-bundle-0.8.0.raucb", "rollout": 10,
 "deltas": [{"from": "0.7.0", "from_root_hash": "c02eb5fb3706f7eb78f84a8da06a82fbaf6d6b4eb8bac681ea546fd2a0f93579", "size": 7900000, "url": "phone-delta-0.7.0-0.8.0.raucb"}]}
```

手机（`shell/update.go`）在提供这个版本时挑增量包：有 `from_root_hash` 的，只有正在运行的槽的 root hash（状态分区里它的描述）就是它时才用（这就是那个映像）；没有的，按发布版本号（`from` 等于本机版本）。挑中的放在 `system.update` 的 `available.delta`，安装时先装它，装不上就接着装整包。没有合适的增量包就装整包（自适应）。

发布工具（kario-internal 的 `tools/release.py`）为 `dist/` 里最近的 `--deltas` 个（默认 3）有 A/B 磁盘的发布版各做一个增量包：经 `make yocto-bundle OTA_DELTA_FROM="<版本>=<磁盘>…"` 进构建容器，`yocto/qemu-ota-delta.sh bundle` 对每个版本生成负载、用 `phone-bundle-delta` 配方打包签名，放进 `dist/v<版本>/phone-delta-<旧>-<新>.raucb`，写进 `latest.json`。更新服务器 `kario-otasrv` 不用为增量包改（它提供所有 `*.raucb`）。

发布版从提交构建（`SRC=git`，kario 在标签上、没有本地改动）：进 bitbake 之前，`make yocto-src` 核对 phone-fw 的 Go 模块清单是这个提交的 go.mod、go.sum 的；不是的话，工作树的这两个文件和提交的一样就先重新生成，不一样就停下说明，不会带着过期的清单构建到一半才失败（[13](13-prototype.md) §5.1）。

每个发布版的 `MANIFEST.json` 记下它的镜像里的应用器读哪些负载格式（`ota_delta_formats`：发布工具在 kario 正是构建用的那个提交、没有本地改动时编出 `phone-ota-delta` 问 `formats`；问不了就不记）。从记了格式的旧版本出发的增量包，`OTA_DELTA_FROM` 里写成 `<版本>@<格式,…>=<磁盘>`，`qemu-ota-delta.sh bundle` 生成负载后读它的格式号，在其中就不往包里放应用器（`phone-bundle-delta` 配方只在 `PHONE_DELTA_DIR` 里有应用器时才带上它），并记下由谁来应用（`<标签>.raucb.applier`：`system` 或 `bundle`）；别的照旧带着，`--bundle-applier` 让每个包都带。生成负载时用起始系统的应用器读得了的最新格式（它读 2 就写 2，只读 1 就写 1，不分块），这样包里可以不带应用器；不知道它读什么时写 2、带上应用器。没有这项记录的旧版本（0.7.1，它的镜像里也没有应用器），从它出发的增量包照旧带应用器；0.6.0、0.7.0 的机型串不同，不做增量包（下面）。

**机型串（RAUC 的 `compatible`）发布以后不能改。** RAUC 只装 `compatible` 和本机 `system.conf` 里一字不差的包，整包、增量包都一样。改名（J1J → Kario）时它从 `j1j-qemuarm64` 变成了 `kario-qemuarm64`，所以 0.6.0、0.7.0 的手机装不了之后任何一版：模拟器上 0.7.0 装 0.7.1 的整包，RAUC 报 `Compatible mismatch: Expected 'j1j-qemuarm64' but bundle manifest has 'kario-qemuarm64'`（§5.5）。这两版只是试发布，没有发到手机上，所以不做迁移（迁移的做法：给旧机型另做一个写旧机型串的整包，装上后新系统就是新机型串；但 0.7.0 的 Shell 只认 `latest.json` 的 `url`，新老手机要分开给地址）。发布工具（`tools/release.py`）从每个包末尾的签名里读出机型串，记进 `MANIFEST.json` 的 `compatible`：和这一版不同的旧版本不做增量包（做了也装不上）；紧挨着的上一版就不同时停下来不发，除非加 `--compatible-change`，明知那一版的手机从此收不到更新。

**下载量为什么比包大**（测试服务器按请求记下每段的起点，`ota-delta.py ranges` 按包的结构分开算）：`0a4ff0b` → 第 5 轮的增量包 6.6 MiB，一次安装发了 95 个请求、7.7 MiB，包里每个字节都下载过，其中 1.1 MiB（17%）下载了两次：负载 5.4 MiB 里重复 0.7 MiB，squashfs 的其余部分（应用器、钩子、描述、元数据）重复 0.4 MiB，dm-verity 的哈希树整个读了两遍。RAUC 的流式安装是 NBD 设备上叠 dm-verity 再挂 squashfs，没有下载缓存，内核读了两次的块就下载两次（是谁读了第二次见下一段）。这是一个比例上的开销，不随包的大小翻倍；包很小时固定的几十 KB 显得多（18 KB 的包下载 51 KB）。

**谁读了第二次**（2026-11-19，基础 `8000e19`、发布的 `f6cea8e`；测试服务器记下每个请求的起点和长度，按包的结构对：c3 是 5990264 字节的包重复下载了 1785860 字节，n1 一共下载了 10522410 字节）：

- udev 的 blkid：RAUC 一接上网络块设备，udev 就照 `60-persistent-storage.rules`（设备名里有 `nbd*`）用 blkid 探测它上面的文件系统和 RAID 签名，经页缓存读了包的开头、2 的幂那些偏移（64K、128K、256K……4M）和结尾附近，每次至少 64 KiB，一次安装约 1.26 MB；应用器经 dm-verity 读负载时（不经 NBD 设备的页缓存）又下载一遍。现在镜像里有一条规则（`59-rauc-nbd.rules`，RAUC 的 bbappend 装）给 `nbd*` 设 `UDEV_DISABLE_PERSISTENT_STORAGE_RULES_FLAG`，udev 不再探测它；手机上没有谁用它的链接。规则在正在运行的系统里，所以只对已经装上这一版的手机起作用，从更早的系统出发的安装（下面的 i1、i2、f1）照旧被探测。
- 内核的预读：钩子的 `can-apply` 经挂载的文件读负载的头，内核读了整个第一块（压缩的，约 108 KB），还在页上留下预读的标记；应用器接着经文件读第一块（压缩的块原来都经文件读），碰到标记，内核就把后面三块（约 393 KB）预读进页缓存（文件设了 `FADV_RANDOM` 也挡不住这种异步预读），而应用器读这三块用的是设备。现在负载一个字节也不经挂载的文件读（碎片块里的尾巴除外，这个包没有）：应用器连压缩的块也从设备读、自己解压（gzip 边读边解，xz 整块），`can-apply` 也从包的设备读头，只解压到格式号（gzip 一次解 32 KiB，读一到几个设备块）。
- 压缩了的块本身：mksquashfs 只要 gzip 能省下一个字节就存压缩的，负载的数据已经是 xz 压过的，可 46 块里还是有 7 块被省下了几十字节；它们经内核读时，和两边原样存放的块共用的那个设备块各下载两次。
- squashfs 的表：应用器解析超级块和表时每个小读都重新读一次同一个设备块（O_DIRECT 不经缓存），一次安装 6 次；现在留着上一次读的那块。
- 断网那次（n1）还有：检查点落在应用器读到的地方后面约 0.7 MB（周期的检查点，§5.6），应用器每次从设备读 1 MiB，网断时这一段读了一半的也白下了；重试时上面这些开销又来一遍。
- 剩下的：dm-verity 预读哈希树。它读叶子那一层的哈希块时按 `dm_verity_prefetch_cluster`（默认 256 KiB）成簇地预读，簇按设备上的绝对块号对齐，所以从哈希树开头往前伸进了 squashfs 镜像：这个包的哈希树从 6000640 字节（第 1465 块）开始，叶子在第 1466–1477 块，簇对齐到第 1408 块，读的正是 5767168–6029312 这 256 KiB，接着是叶子剩下的 24 KiB；前面 233 KB 是镜像的尾巴，其中约 230 KB 是负载最后几块，放在 dm-bufio 里（不在页缓存），应用器读到负载的尾巴时又下载一遍，是改了以后 c3 重复下载的大部分（见下）。每挂一次包都有，至多 63 块（252 KiB），不随包变大而变多（哈希树只有一层时没有：内核只预读顶层以下的各层，镜像至多 128 块时就一层）。起先在负载至少 1 MiB 的包里垫一个 256 KiB 的文件：簇伸进去的换成了它，负载的尾巴只下载一次，可簇读的块一样要下载，下载的照旧，包还大了 256 KiB；负载不到 1 MiB 的包没有它，尾巴照样下载两次（2026-11-25，见下）。现在让镜像在簇不伸出哈希树的地方结束（`phone-verity-pad.py`，`phone-bundle-delta.bb` 在 `rauc bundle` 之后跑，不看负载多大）：叶子从哈希树开头往后 u 块起（u 是叶子上面各层的块数，镜像不到 64 MiB 时是 1），镜像的块数是 64 的倍数、或者它前面那 u 个数之一时，叶子的第一个簇就不早于哈希树的开头；别的块数就写一个 `zz-verity-pad`（压不了的字节，后面补零到一整个 squashfs 块：mksquashfs 把它存成数据块、最后一块压缩，不放进碎片块，钩子读的那几个小文件在碎片块里；内容每次构建都一样），把镜像垫到下一段这样的块数的正中，再跑一次 `rauc bundle`（一般一次就够：这个文件在镜像里占多少估得到几百字节以内，两边各有 4 KiB 的余地；没到就按差的改了再跑，至多 4 次，还不行构建失败）。谁也不读这个文件，镜像也一块不被预读：每挂一次包少下载至多 63 块（接着装的那次又挂一次）；包大 0–252 KiB，镜像落在簇里 64 个位置上平均 126 KiB，比原来的 256 KiB 小。也可以把 `dm_verity.prefetch_cluster` 调小，但那是整个系统的设置，系统槽读哈希也跟着变，也只对装上了那个内核的手机有用，没这么做。宿主机测试（`yocto/verity-pad-test.py`：照 RAUC 1.15 做包，mksquashfs 用 RAUC 的参数、哈希树紧跟着镜像、签名；流式安装照内核的 dm-verity 算出向网络块设备要的块，挂载读超级块和表，应用器从设备把负载的块各读一次）：2026-11-25 那样 1.0 MB 的负载，镜像 246 块，预读拿走最后 54 块，53 块是负载的尾巴；垫 40 KiB 到 256 块以后预读一块镜像也不拿，下载少 216 KiB；镜像落在簇里每隔 4 块的 16 个位置上，不垫时 16 个都有负载的块下载两次，垫了都没有，包大不到 63 块；5.4 MB 的负载垫原来那 256 KiB 时预读拿走 40 块（那个文件的），下载的和不垫一样多，现在少 39 块，包也小 160 KiB；镜像至多 128 块时不垫、不再构建；再跑一次 `do_bundle` 时先拿掉上次垫的再量；构建总不带上垫的文件时失败。拿原来的做法（不到 1 MiB 不垫，垫就是 256 KiB）跑这些用例，1.0 MB 和 5.4 MB 的都失败。

**改成从包的设备直接读**（`ota/delta/squashfs`，`phone-ota-delta apply` 的 `--direct`，默认开）：原来以为重复下载的是经 squashfs 读的块（squashfs 每次读一整块 128 KiB，按设备块对齐；预读的窗口和 squashfs 的块对不齐时，同一块会被读第二次，下面没有缓存，就下载第二次），量了才知道大头是上一段那几样。应用器打开负载后看它所在的文件系统是不是 squashfs（`fstatfs`），是就经 `/sys/dev/block/<主:次>` 找到挂载用的设备（RAUC 的 dm-verity 设备，流式安装时在 NBD 上），自己解析 squashfs 的超级块、inode 表和目录表（gzip 或 xz 压缩的元数据），找到负载这个文件（inode 号和大小都要和打开的文件一样）的每个数据块，用 `O_DIRECT` 从设备按 4 KiB 对齐顺序读，一个设备块只读一次，也不读过负载这一段块的末尾：原样存放的块照原样，压缩的块（放清单的第一块，和 gzip 碰巧省下几个字节的块）读出来自己解压，全是零的块（稀疏的）直接给零；只有碎片块里的尾巴和这里解压不了的块经挂载的文件读（`POSIX_FADV_RANDOM`，不预读）。每次读多少从一个 squashfs 块开始，顺着往下读就翻倍，到 1 MiB 为止，跳过一段（接着装）以后又从一个块开始：接着装的先读清单、再跳到检查点，第一次就读 1 MiB 的话，跳过的那段也下载了。读的仍是 dm-verity 设备，每块照样经内核校验；整个负载的完整性照旧靠清单里每个操作、每块的 SHA-256。哪一步不对（不是 squashfs、压缩方式不认识、文件对不上）就照旧当文件读，日志里写明。断点续装跳过的部分不读设备。宿主机测试（mksquashfs 照 RAUC 的参数做的包，gzip、xz、64 KiB 和 1 MiB 的块、不用碎片、总用碎片，有稀疏块）：读出的和文件逐字节相同，没有一个设备块读两次，只有碎片块里的尾巴经文件读；只读头（`can-apply`）时 gzip 的包只读开头几个设备块；跳过一段之前不会读得比一个 squashfs 块多；设备读不下去（断网）时报错，不改经文件读（那又要经内核下载一遍）；压缩的块从头就解不了时经文件读，解到一半出错时报错（已经交出去的字节收不回来，负载的哈希也会拦下它）。应用器最后一行写出从设备和经文件各读了多少（`payload read: …`）。QEMU 上的结果见下面的 c3。

### 5.6 断点续装

> 状态：宿主机 ✓（`ota/delta` 的单元测试：一次安装里每隔几次写或同步就断一次电，断电时还没同步的写随机丢掉一部分，接着装的结果都和目标逐字节相同；断网后接着装；对不上的检查点被忽略；`cmd/phone-ota-delta` 的钩子测试：只给 busybox 那几个命令，断网后再装一次接着装）；模拟器上断电后接着装 ✓（2026-11-15，§5.5 第 2 条）；模拟器上断网后接着装 ✓（2026-11-19，§5.5 的 n1：第一次跑时重试碰上网还没回来，Shell 没认出下载断了，装了整包；改后重跑从检查点接着装好），下载量起初是包的 1.76 倍，断网时在停下的地方记检查点（下面）这些改了以后是 1.15 倍；断网时检查点记在停下的那个操作（或那一块）上：宿主机 ✓（`TestNetworkLossCheckpointsWhereItStopped`）；被叫停后接着装（停止文件，§6）：宿主机 ✓（`TestStopAndResume`、钩子的测试），模拟器上 ✓（2026-11-19，§5.5 的 s1）；未上真机。

安卓的 update_engine 装到一半断了，下次从记下的那一步接着装，这里照它做。应用器（`phone-ota-delta apply --checkpoint`，钩子给它的是状态分区里槽描述旁边的 `rootfs_<槽>.progress`）每写 32 MiB 或每过 5 秒，在一个操作做完以后先同步目标槽（fsync），再记一个检查点：负载是哪个（头和清单的 SHA-256，清单里有每个操作的哈希）、起始映像（root hash，没有时是 SHA-256）、目标的 root hash、目标分区的字节数、下一个操作的序号和它的数据在负载里的位置，最后一行是前面几行的 SHA-256。写的时候先写临时文件、fsync、改名，再 fsync 目录，断电后留下的要么是旧的要么是新的。

下次装同一个包（同一个负载、同一个起始映像、写同一个槽、分区一样大）时，应用器跳过检查点之前的操作，不读它们的数据：负载是挂上的包里的一个文件，应用器在文件里往后 seek，RAUC 流式安装时这部分就不下载。哪一项对不上（别的负载、别的起始版本、别的分区大小、检查点坏了或者不完整，数据位置超过负载能有的 2⁵⁴ 字节也算坏了），先删掉它再从头装，因为它担保的块会被这次安装覆盖。

为什么跳过是安全的：

- 检查点只在目标同步以后写，它之前的操作都已经在盘上。断电落在写数据和下一个检查点之间时，那几个操作下次重做：每个操作只读起始槽（正在运行的槽，经 dm-verity）和自己的数据，从不读目标槽，写的是同样的块，重做的结果一样。
- 跳过的块最后照样整个读回来核对：整个映像的 SHA-256、重算的哈希树的 root hash 都必须是签名描述里的。检查点就算错了，也只会让这次安装失败，不会让一个坏槽能启动；核对失败时检查点删掉，Shell 接着装整包。
- 别的东西写了这个槽，检查点就作废：整包的钩子（`verity-hook` 的 `slot-pre-install`）在 RAUC 写槽之前删掉它。

检查点什么时候删：装完删，读回核对没过删，数据、源块对不上这类错误也删；只有负载读不下去（网断了、包没了）和被叫停（`--stop` 的停止文件，§6）时留着，而且先在停下的地方再记一个：目标槽还在，停下之前写完的操作（分块的补丁是写完的块）同步以后就是检查点，下次不用再下载最后一个周期检查点以来的数据（周期的检查点最多落后 32 MiB 槽数据或 5 秒，QEMU 上断网那次落后了约 0.7 MB 负载，§5.5）。应用器在日志里写 `the payload stopped arriving` 或 `stopped on request`，Shell 据此知道是网络的事或者是自己叫停的，过一会儿再装同一个增量包（§2、§6），不马上改装整包。

整包（自适应）不需要另做：RAUC 本来就在两个槽里按块哈希找，上次写到一半的目标槽里已有的块也不再下载（没有单独测过）。

**分块补丁里的检查点**（格式 2）：一个操作分块时，每块做完后也可以记检查点（照样每 32 MiB 或每 5 秒），检查点多一项 `next_piece`（检查点格式 2；旧格式的检查点读不懂，删掉从头装）。接着装时跳过这块之前的数据；这个操作已经写好的部分不重读负载，而是从目标槽读回来算这个操作的结果哈希（检查点之前已同步）；之后每块照样先核对再打，最后这个操作的结果哈希、整个槽照样核对。块的数据没读到时（断网）检查点照旧留着。宿主机上（`TestResumeMidPiece`，补丁分成 64 KiB 的块）121 次写和同步里每隔四次断一次电，31 次里 18 次是从一个操作的中间接着装的，都和目标逐字节相同，读的负载少了跳过的部分；损坏的一块在打之前就被拒（`TestDamagedPieceRejected`），它的块不写，检查点删掉。

测得的（宿主机，`TestResumeAfterPowerCut`、`TestResumeAfterNetworkLoss`）：一个 24 MB 的小映像、7 个操作，一次安装 93 次写和同步，每隔 3 次断一次电，31 次里 20 次是从检查点接着装的，都和目标逐字节相同；一半的情况负载按文件 seek，读的就是负载减去跳过的那部分（断网的例子：11445 字节的负载读了 5382 字节），另一半按流读，跳过的部分读了丢掉。

## 6. 自动更新

> 状态：宿主机自测 ✓（模拟的 A/B 手机：Shell 照常检查、安装、通知、重启，RAUC、槽、网络和重启是模拟的）；单元测试 ✓（用户改成计费时当场停下：`TestAutoInstallStopsOnMeteredWifi`，旧代码上失败；下载只走开始时的地址：`TestInstallProxyKeepsItsNetwork`）；QEMU 镜像里的同一个用例（模拟的 A/B 手机）也通过；真的 RAUC 在 A/B 磁盘上的自动更新 2026-11-25 在 QEMU 上跑过 ✓（§3），未上真机。

安卓在后台查更新、下载安装，只在不计费的网络上、电量够或在充电时，装好后请用户重启（或者夜里重启）；这里照它做，由 Shell 来做（`shell/updateauto.go`）：

- **开关**：「设置 › 系统更新」的选项里「切换自动更新」（`settings.set` 的 `auto_system_update`，[22](22-developer-api.md)）。开源镜像默认关：自己编的系统不该在用户不知道时自己装；产品在配置层的 `settings` 里写 `"auto_system_update": true` 就默认开。
- **每天一次**：在 Shell 自己的定时里，和节假日日历一样（商店的「充电时自动更新」用的是应用的后台任务 `job.schedule`，系统更新不经过应用）。检查失败或者条件不满足，一小时后再看；没有新版本、装好了或者彻底失败，第二天再查。
- **条件**：连着不计费的 Wi-Fi（§6.1；移动数据总算计费），电量至少 50% 或在充电，不在通话。
- **低优先级**：RAUC 在 `rauc.service` 里装，`rauc install` 只是叫它干活，所以优先级写在服务的 drop-in 里（`phone-priority.conf`：Nice=10、CPUWeight=20、I/O 用 best-effort 的最低档、IOWeight=20），增量包的应用器是钩子的子进程，跟着一样。手动装也是这个优先级，反正装的时候照常用手机。I/O 不用 idle：前台一直有 I/O（录像）时 idle 会让安装一直等着；IOWeight 要 BFQ 或 io.cost 才起作用，设备上用的是哪个 I/O 调度器**未核实**。ota-test 每次安装后打印 rauc.service 的这几项，`make yocto-ota-delta` 核对（2026-11-15 在 QEMU 上通过）。
- **装好以后**：通知「系统更新已安装」，「现在重启」或「今晚」。选了今晚，在夜里 2:00–5:00 之间、息屏、不在通话、一小时内没有闹钟时重启，那晚没赶上就下一晚；不选就不重启，设置里照样有「重启」。重启后照常是新槽的健康检查和三次机会（§2）。
- **下载断了**（手动、自动都一样）：30 秒、2 分钟、8 分钟后各再试一次，增量包接着装（§5.6）；自动装的重试前先再看一遍条件，不满足就推迟到下一次检查。
- **装到一半条件没了**（只管自动更新；用户自己开始的照常装完）：装的时候 Shell 照样看着条件：来了电话、拔了充电器而电量不到一半，当场就停；网络每 30 秒看一次，换到了计费网络或者不在 Wi-Fi 上也停。RAUC 既不能暂停也不能取消，所以「停」是故意让这次安装失败、已经写好的留着：增量包由 Shell 建停止文件（`/run/phone-ota-delta.stop`，钩子给应用器的 `--stop`，§5.3），应用器在下一个操作或下一块之前停下、记下检查点、退出，钩子失败，RAUC 不把这个槽设为下次启动；整包的下载走 Shell 在本机回环上的代理（`shell/updateproxy.go`：自动更新让 RAUC 从 `http://127.0.0.1:<端口>/<随机串>/<包名>` 取包，代理再从更新服务器取，Range 照传），停下就是代理断开所有连接、之后的请求一律拒绝，RAUC 当作网断了，照断网时那样失败、收拾；应用器 30 秒内没停下（比如镜像里不认 `--stop` 的旧应用器）也这样断它的下载。不直接停 RAUC 的流式下载子进程（带 `RAUC_NBD_SERVER` 的那个 `rauc`）：RAUC 收拾时要往它的套接字写断开请求，而主进程没忽略 SIGPIPE，停掉它可能让 RAUC 自己也退出、包挂着没卸。之后这次更新「暂停」：`system.update` 的状态回到 `idle`，带着 `paused`（为什么等着，设置里显示「自动更新在通话中暂停，通话结束后继续」这类话），提供的版本留着，用户也可以马上点安装（用户开始的不再停）；Shell 每分钟看一次条件，满足了就接着装同一个包：增量包从检查点接着装，整包的自适应安装从槽里拿已经写好的块，不再下载。
- **离开 Wi-Fi、改成计费**：自动更新经代理下载，代理到更新服务器的连接都从第一条连接的本机地址出去，也就是开始时条件满足的那个 Wi-Fi（安卓也是把下载绑在一个网络上：更新客户端在 `applyPayload` 的头里给 `NETWORK_ID`，update_engine 只经那个网络下载）。Wi-Fi 断了它的地址也就没了，之后的连接建不起来，RAUC 照断网时那样失败，Shell 按断网重试，重试前看条件不在 Wi-Fi 上就暂停；不会在 Shell 下一次看网络（至多 30 秒后）之前改走移动数据接着下。用户在「设置 › Wi-Fi」里改了某个网络算不算计费，或者连上、忘记了网络，Shell 当场再看一次网络，不等 30 秒。
- **写了一半的槽不会启动**：RAUC 写之前经引导后端把目标槽标为坏（`rauc-boot set-state <槽> bad`；下次启动的槽 `slot` 留在好的那个上），只在所有槽都装成功后才 `set-primary`；两个钩子在写之前都删掉这个槽的描述，initramfs 没有描述就不打开它。正在试用、还没标为好的新系统不做自动更新：那时要写的另一个槽正是回退用的好槽，RAUC 把它标坏时 `good` 仍指着它，写到一半就没有能回退的系统了。
- **没做的**：Wi-Fi 断了时自动更新的下载不改走移动数据，只在宿主机上测过（单元测试：代理的地址没了就一个字节也不取），真机上 Wi-Fi 断开后内核多快删掉它的地址、留着的旧连接多久失败，**未试**；手动安装的照旧直接从更新服务器下载，不经代理，不看计费，也不会被停（用户自己决定，安卓在移动数据上手动更新也只是先问一声）。

自测的模拟（`shell/update_headless.go`，`ota` 命令）：A/B 槽的启动状态、代替 `rauc install` 的程序（按 Range 一段段下载、照 RAUC 的格式打印进度、装好后把另一个槽设为下次启动）、重启、所在的网络（`ota net wifi|mobile` 说了才用它，不说时是手机自己的网络，按 §6.1 算计费），和本机上的一个更新服务器（用自己的密钥给 `latest.json` 签名，给出 9.0.0）；`ota cut` 让下载在一半断掉。自动更新经 Shell 的代理下载，和手机上一样，停下时断的就是它：第三个用例在装到一半时把电量设成 30%、不充电，Shell 停下，设置里写「自动更新已暂停：电量低，充电时继续」，插上充电器一分钟后接着装好；第四个用例在装到一半时在「设置 › Wi-Fi」里把连着的网络设成按流量计费，Shell 当场停下（3 秒内，不等 30 秒后再看网络），改回不按流量计费，一分钟后接着装好。机器自己的槽和 RAUC 不动，`ota off` 全部还原。真的 RAUC 和槽在模拟器上测（§3、§5.5）。

### 6.1 计费网络

> 状态：宿主机单元测试 ✓（`metered`、`shell` 的 `TestMeteredDetection`、`TestAutoUpdateMetered`、`TestMeterProbeAskedAgain`、`TestUnmeteredJob`、`TestUnmeteredJobStops`，`apps/store` 的 `TestAutoFetchStops`）；宿主机自测「Wi-Fi 计费网络」✓（模拟的手机热点，DHCP 带 `ANDROID_METERED`）、「后台任务遇到计费网络」✓（模拟的 Wi-Fi；同一个用例在 QEMU 的 iwd 上**还没跑过**）；商店的后台自动更新的自测改成先连上 Wi-Fi ✓；QEMU 上真的 RAUC 的自动更新的一步（§3：iwd 的接入点，用户设成计费时不装、改成不计费后装好）2026-11-25 跑过 ✓；问 DHCP 服务器**未上真机**。

安卓把 Wi-Fi 网络分成计费和不计费：自动的时候看 DHCP 里的提示（安卓的热点发 `ANDROID_METERED`），用户也可以给每个网络选；移动数据总是计费的。系统更新（GMS）、应用商店的自动更新、要求不计费网络的后台任务（`JobScheduler` 的 `NETWORK_TYPE_UNMETERED`）在计费网络上等着。这里照它做（`metered` 包、`shell/metered.go`）：

- **自动检测**：iwd 是手机的 DHCP 客户端，它不把厂商信息（选项 43）交出来，所以 Shell 连上一个网络后自己再问一次：在包套接字上广播一个 DHCPREQUEST（RFC 2131 的续租：带着手机已有的地址，不带请求的地址和服务器标识，客户端标识和 iwd 的一样是硬件类型加 MAC，要选项 43），收到的 DHCPACK 的选项 43 里有 `ANDROID_METERED` 就是计费的；服务器只是把租约续一下，回答的事务号是别人的，iwd 不理。只等 1.5 秒，没回答先当不计费，5 分钟后再问（原来一直当不计费到换地址为止：丢了一个包，手机热点就一直算不计费，自动更新会在上面下载）。地址在 172.20.10.0/28（iPhone 的个人热点）或 192.168.43.0/24（旧的安卓手机和 Kario 自己的热点）里的也算计费，不用问。回答按网络和地址记下，换了地址再问。要 root（包套接字），开发机上不问。
- **用户的选择**：「设置 › Wi-Fi」里保存过的或连着的网络有一项「按流量计费：自动检测 / 是 / 否」（按 `m` 换），存在 Shell 的设置里（`wifi_metered`，按网络名），先于自动检测；忘记这个网络时一起删掉。连着的网络下面写明算不算计费、为什么：「按流量计费：手机热点」（DHCP 说的）、「按流量计费：像是手机热点」（按地址）、「按流量计费（你的设置）」、「不按流量计费（你的设置）」。
- **谁等着**：后台自动的系统更新（§6，原因写「on a metered network (<网络名>)」）；应用的后台任务登记时带 `unmetered: true` 的（[22](22-developer-api.md) §4.7），只在不计费的 Wi-Fi 上跑，Shell 用最近 30 秒内看过的网络（旧了就在循环外再看一次），商店的「充电时自动更新」就是这样的任务；它跑着时 Shell 每 2 秒看一次网络，离开了不计费的 Wi-Fi 就停掉它（`job.stop`，5 秒后这次唤醒结束），回到不计费的 Wi-Fi 后马上重跑，商店收到就断开后台的下载、重跑时再下（[22](22-developer-api.md) §4.7）。用户自己开始的照常下载：设置里点安装系统更新、商店里点下载，不看计费。
- 应用的 `wifi.state` 里每个网络多了 `metered_choice`、`metered`（连着的那个是最后的结论）和 `metered_hint`（`dhcp` 或 `hotspot`），`wifi.set` 带 `{ssid, metered}`（`auto`、`metered`、`unmetered`）改选择（只给系统应用，[22](22-developer-api.md) §4.5）。

### 7.1 设计备注：Virtual A/B、puffdiff 和 zucchini、FEC

这一轮照 update_engine 补上了几件小而明确的事：补丁分块边下边打（update_engine 也是边读边用操作的数据，一个操作的数据有上限）；断点续装可以落在一个大操作中间（update_engine 记的是已读负载的哈希状态，这里每块有自己的哈希，记块号就够，这个操作做好的部分从目标槽读回来重算，不用存哈希的内部状态）；负载每块只下载一次（update_engine 自己下载负载；Kario 的负载在 RAUC 包里，应用器从包的设备直接读）；计费网络（update_engine 不管，由更新客户端按网络是否计费决定；这里由 Shell 管，§6.1）；打补丁不把旧文件整个读进内存（update_engine 的 bspatch 也是按区段读源分区，§5.1）；自动更新的下载绑在开始时的网络上（update_engine 的 `NETWORK_ID`，§6）。下面三件没做，原因和代价：

- **Virtual A/B**（安卓 11 起）：每个分区只留一份，更新写进快照（dm-snapshot 的 COW，安卓 12 起可压缩），新系统起来后在后台合并。省下一个槽的空间（这里是 1 GB），代价是合并完之前不能再装更新、断电后要接着合并，开机时要先把快照拼起来（安卓在第一阶段的 init 里做）；Kario 的槽签名的是 dm-verity 的描述，换成快照要改 initramfs 整个的选择逻辑和回滚。存储有几十 GB 的手机上这 1 GB 不值这个复杂度，现在不做；存储小的手机上它是存储的一大块（8 GB 里的八分之一），值得以后做：2026-11-26 定下，和低端九宫格 SKU 的存储挂钩（[43](43-phone-partitions.md) §7.3），**未实现**。
- **puffdiff、zucchini**：puffdiff 先把 deflate 压缩的文件（APK、zip）解开再差分；Kario 的系统槽里几乎没有 deflate 的大文件（系统应用是 Go 程序，商店装的应用不在系统槽里），用不上。zucchini 认得可执行文件里的相对跳转，代码移了位时差分更小，ARM64 上近似于先把 `BL` 的相对地址换成绝对地址（xz 的 BCJ 过滤器的做法）再做 bsdiff。Go 程序重新链接后 bsdiff 的补丁已经只有程序的约 4–9%（§5.5：`kario-system` 23.8 MB 的补丁约 1 MB，28.3 MB 的 2.6 MB）；还能省多少要在真的 arm64 Go 程序上量了再定，**未实现**（要加的是生成器和应用器两边各一个可逆的变换，负载格式加一种操作）。
- **FEC**：安卓在设备上算 dm-verity 的纠错码（Reed-Solomon，约占分区的 0.8%），读到坏块先纠错，纠不了才报错。它防的是存储的位翻转，不是篡改（篡改由 root hash 管）；代价是装完要多算一遍、多写约 8 MB。Kario 现在坏块读出来是 I/O 错误（§4），真机的存储（UFS、eMMC）自己有 ECC；要等真机上有了坏块的统计再定，**未实现**。纠错码可以放在哈希树后面、描述里加两项，不影响现在的槽。

## 8. 手机上的 A/B 槽
