# 超级应用能力目录：微信 / 支付宝用到的能力 → 平台能力

> 目的：把「微信、支付宝要用到的所有能力」逐项落到平台接口上，标明原型状态和量产依赖。架构见 [11](11-platform-architecture.md)，原型见 [13](13-prototype.md)。
> 状态列：**✓** 原型已实现并有自测用例；**模拟** 原型跑通但数据源是模拟的；**设计** 只有设计，未实现。

## 1. 界面与交互

| 能力 | 谁在用 | 平台接口 | 状态 |
|------|--------|----------|------|
| 语义界面：列表、气泡、表单、按钮、图片、媒体面 | 全部 | `phone.Ui` v0 节点 | ✓ |
| 上下文菜单（= 长按）、命令面板、返回栈、软键 | 全部 | Shell 统一提供 | ✓ |
| 中英文输入法（全键盘 / 九宫格，候选、联想） | 聊天、搜索、转账备注 | 系统输入法，应用只收到上屏文字；输入框声明 `keyboard`（number / phone / email）（[16](16-input-method.md)） | ✓（原型，自研引擎 + AOSP 词库，用户词库、调频、模糊音，[16](16-input-method.md) §5.1） |
| 文章富文本（公众号文章） | 微信 | `doc` 节点（Markdown + Mermaid 图，系统渲染）；完整 H5 走 Web 视图组件 | ✓（Markdown、Mermaid、代码高亮、公式）；Web 视图设计 |

| 应用自产帧（厂商自研编解码） | 微信 | `media.surface.produce`：共享缓冲，系统合成 | 设计 |
| 录音、语音消息 | 微信 | `audio.record`：运行时授权「麦克风」、状态栏指示、只限前台或通话中（[20](20-audio.md) §3.1） | ✓（模拟麦克风；鸿雁语音消息可录可放） |

| 音频路由（听筒 / 扬声器 / 蓝牙） | 通话 | `audio.route` | 部分（接口 ✓；真机路由要 ALSA UCM / PipeWire） |
| 音乐播放、后台播放 | 音乐 | `media.list` + `audio.play / control / state`；`background: ["audio"]` | ✓（合成示例曲目；解码器随媒体库做） |
| 应用自带音频流（VoIP 解码后的声音） | 微信通话 | `audio.stream`：共享内存环形缓冲区，经 fd 传递交给应用，数据不经过 Shell | ✓ |
| 视频播放 | B站 | `media.play` | 设计 |

## 4. 支付与安全

| 能力 | 谁在用 | 平台接口 | 状态 |
|------|--------|----------|------|
| 设备认证（风控判断「真机、未篡改」） | 微信、支付宝登录风控 | `attest.get{nonce}` | ✓（软件密钥） |
| 用户确认的签名（支付、转账） | 支付宝、微信支付 | `auth.confirm{key, prompt, payload}` | ✓（软件密钥） |
| 无需确认的签名（付款码） | 付款码 | `keystore.sign` | ✓ |
| 可信输入（支付密码） | 支付 | 系统可信确认界面 | ✓（量产需 TEE 可信输入路径） |
| 服务端验证库 | 厂商服务端 | `keystore.VerifyAttestation / VerifyConfirm / VerifySign` | ✓ |
| 安全画面（防截屏、录屏、投屏） | 付款码、密码 | 节点 `secure: true` | ✓ |
| 扫码（只给结果，不给画面） | 扫一扫 | `scan.qr` | 模拟（识别结果由合成画面直接给出） |
| 生物识别支付 | 指纹支付 | `auth.confirm{key, bio_key, prompt, payload}`：用户打开「指纹用于支付」后，指纹匹配了用绑定指纹的密钥签名，支付密码照样能用；录入或删除指纹后这把密钥作废，用支付密码确认一次再生成（[31](31-lock-and-biometrics.md) §5）；对接 IFAA / SOTER 类标准**未实现** | ✓（模拟传感器、keystored 代 TEE）；真机传感器和 TEE **未实现** |
| 国密算法 SM2 / SM3 / SM4 | 金融合规 | keystore 算法套件：应用密钥可选 SM2（`alg: "sm2"`，SM3 摘要） | SM2、SM3、SM4 ✓（软件实现，SM4 是恒定时间的）；放进 TEE **未实现** |
| NFC 卡模拟（公交卡、门禁、付款） | 支付宝、微信 | 清单的 `nfc`（AID 组、类别）+ `nfc.apdu` 事件 / `nfc.reply`；系统卡包、复制门禁卡、快捷交通卡、默认付款应用（[30](30-nfc.md)） | 模拟（模拟控制器和读卡器；真机的 NCI 后端**未实现**） |
| 应用间调起支付（系统证明调用方身份） | 第三方应用拉起支付 | `intent.invoke` / `intent.reply`（[22](22-developer-api.md) §4.10） | ✓（鸿雁转账请飞钱付款） |
| 可重置、按应用隔离的设备标识 | 风控、广告 | `device.id`（类似 OAID） | 设计 |

## 7. 厂商移植路径（设想，未验证）

以微信这类应用为例，移植工作分三块：

| 部分 | 现状（公开信息） | 在本平台上 |
|------|------------------|-----------|
| 核心逻辑：网络、存储、协议 | 大型 IM 的核心多为跨平台 C++；腾讯开源过 Mars（网络）、WCDB（数据库） | 经 C ABI SDK 直接编译复用 |
| 界面层 | 各平台各写一套 | 用 `phone.Ui` 重写：按 [10](10-keyboard-interaction-model.md) 的按键语法描述页面和动作，不画像素 |
| 小程序 | 自有 JS 运行时：逻辑层（V8 / JavaScriptCore）+ 视图层（WebView 或自研 Skyline） | 逻辑层照搬；视图层把组件映射成 `phone.Ui` 节点（原型 `apps/miniapp` 演示了这一结构）；子树委托（[11](11-platform-architecture.md) §10） |

## 8. 技术之外的门槛

| 门槛 | 说明 | 平台能做的 |
|------|------|-----------|
| 用户规模 | 大厂只为有规模的平台适配（KaiOS、手表版微信的先例，见 [09](09-ui-feasibility-review.md) §2） | 先用自有原生应用与开放协议应用把产品做出来 |
| 金融安全认证 | 支付需要 TEE、国密、生物认证标准对接和检测 | 信任平面按这些要求设计（§4、[11](11-platform-architecture.md) §7） |
| 分发与签名 | 应用商城、签名协议、更新 | `.phoneapp` 签名体系（[07](07-ecosystem-and-store.md)） |
| 合规 | APP 备案、个人信息保护 | 系统级权限提示与隐私面板，降低厂商合规成本 |
