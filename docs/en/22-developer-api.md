# Developer documentation: capabilities and interfaces

> For vendors and individual developers building apps on this platform (the system is called Kario, see 58 (internal document) §1).
> - This document matches the code: the capability catalog corresponds to `ui/caps.go` and the Shell's permission table, and `shell/apidoc_test.go` checks that every capability appears in this document. Add a capability without documenting it and the test fails.
> - Items marked "**not implemented**" are plans.
> - The protocol version is `phone.ui/0`. It is not frozen yet; for the compatibility policy see [11](11-platform-architecture.md) §11.

## 0. Why develop on this platform

| What you get | Details |
|------------|------|
| **Write the UI once, run it on every form factor** | The app only describes "what content there is and what can be done" (semantic UI); focus, menus, soft keys, back, input method and layout are all handled by the system. The same app, without changing a single line, runs on three kinds of device (portrait with a T9 keypad, candybar with a full keyboard, landscape with a wide keyboard), and it also runs in a terminal |
| **Write it in any language** | Apps and the system talk over a JSON-lines protocol on fd 3. Go has an SDK; Python needs only a few dozen lines even without an SDK (`apps/hello-py`); mini-programs use JS or TypeScript |
| **Light on resources** | The same chat app takes 66 MB of memory and starts in 1.1 seconds on the device as a semantic UI app; the web version takes 413 MB and 6.7 seconds ([15](15-web-vs-semantic-benchmark.md)). It runs even on low-cost devices |
| **The system does the hard parts for you** | Trusted payment confirmation (what you see is what you sign), the device attestation certificate chain, code scanning that returns only the result, the system incoming-call screen, push (your app does not need to stay resident), shared-memory audio, the photo picker. Your server can check signatures with the verification library the system provides |
| **Secure by default** | Every app has its own uid and sandbox. Other apps cannot touch your data, and they cannot spoof the system UI either |
| **Easy to test** | The same key script runs the full flow in a terminal on your development machine, on the pixel renderer and on a real device (§10) |
| **Open source** | The platform and SDK are open source under Apache-2.0 (58 (internal document) §3.1). You can build closed-source apps on top of it, and no single company can lock you in |

## 1. What an app consists of

An app is a directory: `manifest.json`, an executable (for a TypeScript app, the compiled `main.js`, §9.2), and an optional icon `icon.png`.

| Manifest field | Description |
|----------|------|
| `id` | Reverse domain name, globally unique, e.g. `com.example.notes`; IDs starting with `system.` are reserved for the system |
| `name` / `icon` / `icon_image` | Name; single-character icon for the text UI; PNG for the pixel UI (inside the app directory, ≤ 512 KB, ≤ 256×256) |
| `description` | One-sentence description |
| `exec`, `args` | Program to launch and its arguments |
| `runtime`, `main` | `"runtime": "js"` is a TypeScript app (§9.2): no `exec`; the system runs the module `main` (default `main.js`) in the package root with `kario-jsrt`; the package may hold no executable file and no bytecode, and machine code only as the modules `native` declares. Without `runtime` the app brings its own program |
| `native` | A TypeScript app's native modules (§9.3): `["imgproc"]`, at most 32, names `[a-z][a-z0-9_]*` of at most 32 characters; each is `lib/<arch>/<name>.so` in the package. An app with it is reviewed as a native app, every version by a human |
| `permissions` | Permissions the app uses (§6); capabilities that are not declared are always denied |
| `purposes` | Each runtime permission's purpose: `{"camera": "Scan to pay"}`, 1–80 characters, shown in the grant dialog; an app that declares a runtime permission without a purpose does not install (§6) |
| `privacy` | The privacy label: which data leaves the phone and what for (`collects`), which is used on the phone only (`local`); shown on the store's Details page; when given it must match the permissions; an app that goes online (`net`) without one is refused by the official store (updates of apps already listed have a grace period, and what is listed in it shows "not provided"), and still installs on the device ([33](33-app-guidelines.md) §3) |
| `background` | Background mode: `voip` (requires the `voip` permission), `audio` (not frozen while playing), `location` (not frozen while it watches the location with the user's "allow all the time", §4.7) |
| `requires` | Runtime dependencies, e.g. `["python3"]`; if one is missing, the app is not shown |
| `order` | Position in the main menu |
| `share` | What the app can receive from the share sheet: a combination of `text`, `image`, `link`, `file` (§4.9) |
| `intents` | What the app can do on behalf of other apps: `[{"action", "label"}]`, at most 8; `action` is a lowercase name (e.g. `pay`), `label` is 1–8 characters (§4.10) |
| `commands` | Entries contributed to the command palette: `[{"id", "label", "arg"}]`, at most 8, labels 1–16 characters (checked when an app is installed; Settings in the system image has one per item, labelled with the item's title, up to 32 characters). The palette lists them ("app name · label") only once something is typed, so they do not bury the page's actions. When the user picks one, the system opens the app with `arg` as the deep link (e.g. Phone's 「最近通话」 (Recent calls) is `log`); an app already running gets an `open` event, which counts as an action: keys pressed before the app has handled it wait for it ([11](11-platform-architecture.md), "One action at a time") |
| `settings` | The app's settings: `[{"key", "title", "type", "default", ...}]`. `type` is `toggle` (switch), `choice` (options, with `choices`), `number` (number, with `min`, `max` and an optional `step`; the system provides two actions, + and −) or `text` (one line of text; `max_len` defaults to 64 characters; no newlines or tabs). The system presents them uniformly under 「设置 › 应用设置」 (Settings › App settings), saves them and checks their types and ranges, so the app does not draw its own settings page. After the user changes one, the app gets a `settings` event and reads the current values with `app.settings`: an app frozen in the background is thawed for a few seconds for it (as for a push, not counted in the hourly wakes), so its idle-screen widget follows at once; an app not running reads them when it starts |
| `widget` | When `true`, the app can use `widget.set` to put one line of text on the idle screen (at most 32 characters, shown as 「应用名：内容」 (App name: content), at most 3 apps). When the user selects this line on the idle screen with ↓ and presses OK, the system opens the app with the line's `arg` as the deep link |
| `version` | Version number, written into the signature at packaging time (§12); the store takes dotted numbers only (`1.0`, `2.13.1`, at most 8 parts of at most 9 digits) and compares versions by them; the phone's Store app also lists only entries whose app ID and version have these shapes (they make up the downloaded file's name and the request's path) |
| `min_platform` | The lowest platform level the app runs on (§2.2), a whole number; absent or `0` is any level. One newer than the system's: the installer refuses the app and the store does not list it; `kario new` writes the SDK's level |
| `capabilities` | The capability versions the app cannot work without (§2.3): `["media.list@2"]`; absent is none. When this phone does not serve one of them (a newer version, a removed one, no such capability) the installer refuses the app, and one already installed does not start; `kario manifest check`, `kario build` and the store also require each version's level to be no higher than `min_platform`. The broker does not limit the app to them |
| `notify_actions` | Actions attached to a notification when the system displays a push notification on the app's behalf (a push with only a title and body): `[{"id", "label", "key", "input"}]`, e.g. Hongyan's 「回复」 (Reply). When the user selects one in the notification center, the system delivers `notif_action` to the app in the background without bringing it to the foreground; an action with `input` first brings up the system input screen (quick reply), and the text goes in the message's `text`. Notifications the app sends itself (`notify`) carry the same kind of actions in `actions` |
| `nfc` | The app's contactless cards (NFC card emulation, [30](30-nfc.md) §6): `[{"id", "category", "description", "aids", "requires_unlock", "express", "locales"}]`, at most 8; `category` is `payment` (for the default payment app only, answering only unlocked) or `other`; `aids` are AIDs in hex (5 to 16 bytes, an AID in one card only, the PPSE in payment cards only); an `other` card with `express: true` may be made the express transit card by the user (it works with the screen off and locked); `locales` gives the card's name by language. Needs the `nfc` permission |
| `filing` | The app's ICP filing number in China (e.g. `京ICP备2026001234号-1A`). The store backend checks the format and displays it publicly on the app page; in stores open to the public in China, apps without a filing number cannot be listed ([07](07-ecosystem-and-store.md) §4.1) |
| `lang`, `locales` | `lang`: the language the manifest's text is written in (`zh-Hans`, `zh-Hant`, `en`, `es`; `zh-Hans` when absent). `locales`: the same text in other languages, by language, leaving out what is not translated: `{"es": {"name": "Notas", "description": "…", "settings": {"sort": {"title": "Orden", "choices": ["Fecha", "Nombre"]}}, "purposes": {"camera": "…"}, "commands": {"log": "…"}, "intents": {"pay": "…"}, "notify_actions": {"reply": "…"}}}`. `settings` gives, by setting key, the `title` and display names matching `choices` one to one (the values the app stores do not change); `commands` and `notify_actions` go by `id`, `intents` by `action`. The system picks by the device language's fallback chain (§9.1): the main menu, Switch apps, the permission dialog and Settings › App settings show the name in the device's language, and the choices their translated names too (`labels` in `settings.apps`). The installer and the store backend both check: only these four languages, the same length limits as the manifest itself (names 1–32 characters), no translation of a setting, permission, command, intent or notification action the manifest does not declare; the store catalogue's entries carry the name, summary and purposes in each language |
| `granted` | Pre-granted permissions, **only valid for apps in the system image**; the installer rejects this field |

## 2. Protocol

When the system launches an app, it puts a Unix socket on fd 3 (environment variable `PHONE_UI_FD`) and also provides `PHONE_APP_ID`, `PHONE_DATA_DIR` (the app's own data directory, which is also `HOME`), `PHONE_LANG` (the UI language, §9.1), `PHONE_PLATFORM` (the system's platform level, §2.2) and `TZ` (the time zone, an IANA name such as `America/Mexico_City`). The device's clock itself runs in UTC; the zone is given when the app starts; when it changes while the app runs (the user changed it, the phone moved to another network), the system sends the `time.zone` event (§5), and the Go and C SDKs and the TypeScript runtime put the new zone into `TZ` (so `localtime` and `Date` follow) before the app hears of it (kario-jsrt through the C interface it links, the runtime itself under Node.js: `TestTimeZoneEvent` and `TestNodeTimeZoneEvent` in `jsrt`). When a selftest moves the Shell's clock (`timeshift`, `clock-at`, [40](40-testing.md) §2), the clock the apps read follows it: `PHONE_CLOCK_OFFSET_MS` at the start (how many milliseconds ahead of the machine's clock, negative behind; unset when not moved), and the `time.clock` event (§5) when it moves while the app runs; the Go SDK's `sdk.Now()` and `Date` under kario-jsrt and Node.js (`new Date()`, `Date()`, `Date.now()`) add that offset, before the app hears of the event (`TestClockEvent` in `sdk` and `jsrt`, `TestNodeClockEvent` in `jsrt`, `TestClockTellsApps` in `shell`); the C, Rust and Python SDKs do not add it yet (**not implemented**), nor does a Go app that calls `time.Now()` directly (the weather app, Hongyan, Feiqian, the dialer, the browser and the mini-app runtime still do, mostly for durations and IDs). Measure durations with the monotonic `time.Now()` and `time.Since`, not `sdk.Now()`. Each message is one line of JSON, and the `t` field gives its type:

| Direction | `t` | Purpose |
|------|-----|------|
| App → system | `hello` | First message, with `proto: "phone.ui/0"`; an app that speaks several major versions adds `protos` (§2.1; all four SDKs can) |
| | `reset` / `push` / `replace` / `update` / `pop` | Manage the page stack: reset, push, replace the top, update by `id`, pop. `update` only changes a page on the stack; the Go SDK does not send one for a page that is not, so refreshing many pages does not use up the rate the Shell reads the app at (§8.1) and does not slow the app's answers to pings |
| | `toast` / `notify` | Toast; notification (`kind: "call"` is an incoming call and requires the `voip` permission) |
| | `req` | Request a capability: `req` (request number), `cap`, `args` |
| | `pong` | Answer to `ping`, with the same `value` |
| | `state` | `data`: what is needed to rebuild the pages (at most 64 KB of JSON). If the system ended the app in the background because memory was tight, it hands this back unchanged at the next launch (`data` of `start`, [17](17-app-sandbox.md) §5.3); the Go SDK calls `OnSave` and sends it every time the app leaves the foreground |
| System → app | `start` | Launch; `value` is the launch argument (deep link); `data` is the `state` handed over by the previous process (present only when the system ended it and the user came back; the Go SDK's `Restore`); `proto` is the protocol version the system chose (§2.1) |
| | `action` | The user triggered an action: `screen`, `node`, `action`, `value`, `fields` (the values of all input fields on the screen) |
| | `popped` / `lifecycle` | The screen was closed with the back key; foreground / background |
| | `res` | Capability result: `req`, `ok`, `data` or `err`; when files are attached, there is also `fds` (§7) |
| | `event` / `notif_action` | System event (§5); the user's action on a notification |
| | `ping` | The system checks whether the app is stuck: sent after a user action. The app must reply `pong` in the same loop that handles actions (the Go SDK replies automatically). If a foreground app does not reply within 5 seconds, the system shows the dialog 「没有响应」 (Not responding), and the user can wait or close the app |
| | `resync` | Sent by a new Shell that takes over this connection (the previous Shell crashed or restarted while the app process kept running): the app must resend its page stack, first a `reset` with the first page, then a `push` for each further page. Requests sent earlier that have not been answered yet will never get an answer. The Go SDK handles this automatically (it remembers the page stack; state outside the pages can be refreshed in `OnResync`); the C SDK passes it on to the app |

Minimal example (Python, no SDK; the page title `你好` means "Hello" and the button text `点我` means "Press me"):

```python
send({"t": "hello", "app": os.environ["PHONE_APP_ID"], "proto": "phone.ui/0"})
for line in rx:
    msg = json.loads(line)
    if msg["t"] == "ping":
        send({"t": "pong", "value": msg.get("value", "")})
    elif msg["t"] == "start":
        send({"t": "reset", "screen": {"id": "main", "title": "你好", "body": [
            {"kind": "button", "id": "inc", "text": "点我",
             "actions": [{"id": "inc", "label": "点我", "primary": True}]}]}})
```

### 2.1 Compatibility rules

Handshake: `proto` in `hello` is `phone.ui/<major>[.<minor>]`; this system speaks `phone.ui/0`. The system accepts any minor version of a major it speaks (`phone.ui/0`, `phone.ui/0.3`); an app that names no version is taken to speak the system's own major (one log line). An app that speaks several majors lists them all in `protos`, with the oldest of them in `proto` (all an older system that does not negotiate reads), and the system takes the newest both sides speak; with no major in common the system ends the app, its crash record says "protocol version", and the user is told 「与当前系统版本不兼容」 (does not work with this system version). The system says which it took in `start`'s `proto` (an older system leaves the field out: then it is `hello`'s `proto`), and from then on both sides speak it. A repeated `hello` is ignored. The handshake itself (`hello`'s `proto` and `protos`, `start`'s `proto`) is the same in every major.

| Change | Allowed in a minor version | Only in a new major version |
|------|------|------|
| Message types, fields, capabilities, events, node kinds, error texts | Additions (new fields are always optional) | Renaming, removing |
| A field's JSON type and meaning | Unchanged | Changing them, or making an optional field required |

When a capability's arguments or result have to change as the right-hand column says, that need not wait for a new major: the capability gets a new version (`name@2`), and the old one stays served (§2.3).

How unknown things are treated:

- Unknown fields: ignored by the Shell and the Go SDK; extra fields are never rejected.
- A message type from an app the system does not know: ignored, one log line per type and run, not counted as an error, and the app is not ended for it; a newer app on an older system cannot use the new message, but keeps running. Apps must ignore message types from the system they do not know as well (the Go SDK does).
- An unknown capability: `res` with `err: "unknown capability \"…\""` (a version not served and a removed version start the same, followed by the versions served, §2.3); an unknown node kind: neither renderer draws it; an unknown event name: the app ignores it.
- Lines that are not JSON, have a field of the wrong JSON type or nest deeper than 10000 levels: dropped and logged; at the 16th in one run the system ends the app (§8.1).

Major versions: the Shell's own form (`ui.Msg` and the types of package `ui`) is always the newest major (`ui.ProtoMajor`). During a transition the Shell also speaks the major before it, for at least one release: its entry in `protoVersions` in `shell/protover.go` turns the older major's messages from an app into the Shell's form and the Shell's into the older major's (`in`, `out`, on the message's fields as JSON); an app's message that cannot be turned is dropped as a malformed one (counted as in §8.1); an app speaking the older major gets a log line naming the differences. When a restarted Shell takes over the apps (systemd's fd store, an in-place restart), a connection's name carries the older major its app speaks (`app-<app>-<pid>.v<major>`), so the new Shell turns its messages too; one whose major the new Shell does not speak is closed.

| Major | What differs from the Shell's own form | Accepted by the system |
|------|------|------|
| `phone.ui/0` | It is the Shell's own form, nothing is turned | Now, the only major |

There has been no major change yet, so the table has one row. The mechanism has been gone through on the developer machine with a `phone.ui/1` made up in the tests only (three differences: `toast` is `notice`, its text in `body`; `action` names the page in `page`; `resync` is `resend`), see "Verification" below.

The SDKs (Go's `sdk`, C's `sdk/c` (which kario-jsrt speaks the protocol through as well) and the runtime under Node.js, `sdk/ts/node/runtime.mjs`) negotiate too: how a major differs from the SDK's own form (package `ui`'s, `PHONEUI_PROTO`) is written as renaming rules (`ui.ProtoForm`: a rule renames the message type `t` to `as` and, in messages of that type (every message when there is no `t`), fields from the SDK's names to the major's), the same JSON for all four SDKs. An SDK that speaks more than one major puts the oldest in `hello`'s `proto` and all of them, newest first, in `protos`; what it sends before `start` arrives is held (it does not know yet which the system chose); the major `start`'s `proto` names gives the renaming: what it sends goes from its own form into that major's, what it receives back, and a message type that major does not have is dropped; a `start` without `proto` (an old system that does not negotiate) means `hello`'s `proto`. Speaking one major only changes nothing: only `proto` is sent, nothing is held or renamed. There is one major today, so the SDKs carry no other major's rules; tests hand them the `phone.ui/1` made up in the tests in the environment variable `PHONE_UI_TEST_FORMS` (`ui.EnvTestForms`, which the system never sets). At a real major change the SDKs build the old major's rules in (step 4 below), and the Shell's `protoVersions` can use the same rules (`ui.ProtoForm`'s `FromMajor` and `ToMajor` are `in` and `out`). Changes renaming cannot express (a field's type or meaning) need code in each SDK, **not implemented** (there is no such change yet).

Introducing a new major (`phone.ui/1`, say):

1. Write what changes into this document, marking what is to be removed as "deprecated" first (below); a new major is a new platform level too (§2.2).
2. Change package `ui` to the new major's form (`ui.Proto`, `ui.ProtoMajor`, the changed types), and the Shell and the system's own apps with it; put the old major second in `protoVersions` in `shell/protover.go`, with `changes`, `in` and `out`; add a row to the table above.
3. The old major's recordings in `shell/testdata/compat/` must still be accepted through `in` (`TestCompatTranscripts`), and `make compat-old` runs an older commit's apps against the new Shell.
4. The SDKs move to the new major and speak both during the transition: `hello` with `proto: "phone.ui/0"` and `protos: ["phone.ui/1", "phone.ui/0"]`, then what `start`'s `proto` says (without the field the system is an older one: `phone.ui/0`).
5. At least one release later, drop the old entry from `protoVersions`: apps that speak only the old major are refused from then on (crash record and toast as above).

Deprecation: a message type, field or capability to be removed is first marked "deprecated" in this document, kept for at least one major version, and removed only in the next. A capability version a newer one replaced is removed by the rules of §2.3.

Verification: `shell/testdata/compat/` holds what the system's own apps sent during a selftest run (one file per app, deduplicated by message structure; re-recorded with `PHONE_COMPAT_RECORD=1 go test ./shell -run '^TestCompatRecord$'`), and `TestCompatTranscripts` in `make test` sends them unchanged to the current Shell: no line may be taken as malformed or as an unknown message, every capability must be known, every request answered, and the app must not be ended; `TestProtoVersions` checks the handshake's version rule; `ui`'s `TestNegotiate` the version names and the negotiation; `shell`'s `TestProtoTransition` uses the `phone.ui/1` above that exists only in the tests: a fake app (a process the test binary starts) learns in `start` that it is `phone.ui/1`, its messages are turned into the Shell's form and the Shell's into its own, a `toast` it sends in the Shell's form is dropped as malformed, an app speaking both gets the newer, and with one major only the same app is refused; `TestProtoAdopted`: a connection taken over is turned on by the major in its name, and one of a major the new Shell does not speak is closed; `TestSDKProtoMajors`: one app per SDK (Go's, a C program built there and then with `sdk/c`, the same `main.js` on kario-jsrt and under Node.js) speaking `phone.ui/0` and `phone.ui/1` through `PHONE_UI_TEST_FORMS` speaks `phone.ui/0` to a Shell of `phone.ui/0` only and `phone.ui/1` to a Shell in the transition; either way its toast arrives, it reads an action's page and sends its pages again after `resync`, and no line is taken as malformed. Each SDK's own tests: `ui`'s `TestProtoForm` (turned there and back a message is unchanged, a type the major does not have is an error), `sdk`'s `TestProtoMajors`, `sdk/c`'s `test_phoneui.c`, `jsrt`'s `TestProtoMajors` and `TestNodeProtoMajors` (`hello` with both majors, what is sent before `start` held until after it, each of three `start`s answered in the right form). `make compat-old OLD_REV=<commit>` builds the apps of an older commit from its sources and starts each on the current Shell and services, pressing a few keys: a binary compatibility check (Go apps and the Python sample; TypeScript and C++ apps are not included).

### 2.2 Platform level

After Android's `minSdkVersion`: the system has a platform level (`ui.PlatformLevel`, 2 in this release), and an app's manifest names the lowest level it runs on, `min_platform`.

- How the level rises: the first release after a level shipped that adds to the protocol (a capability, a capability's new version, message type, field, event, node kind or error text: what §2.1 allows in a minor version) or removes a capability version (§2.3) raises the level by one, and whatever else that release adds has the same level; a release that adds nothing keeps it, and the level never falls. A major version change (`phone.ui/1`) is a new level too.
- Each version of each capability records the level it came in at (`CapLevels` in `ui/caps.go`; in TypeScript `CapLevel` and `PlatformLevel` in `ui.d.ts`); a new capability or version gets the new level, and without one `ui`'s test (every `Cap…` constant in `ui`) and `shell`'s (every capability the broker serves) fail, and `tools/tsgen` does not generate. Level 2 is `media.list@2`, added in this release (§2.3); every other capability is level 1.
- Installing: the installer refuses a package whose `min_platform` is above the system's level ("needs a newer system"); one already installed (the system went back to an older slot) does not start. The same goes for a capability version in the manifest's `capabilities` this phone does not serve (§2.3). The store backend takes only levels it knows; the phone's Store app asks for the catalogue with the phone's level (`GET /v1/catalog?platform=`), the backend leaves out the apps no release of which runs there, and the system (`pkg.catalog`) leaves out the rest this phone cannot run: when a staged version needs a higher level, the phone is offered the previous release.
- Running: the broker does not hold an app to its `min_platform`. `min_platform` only promises that the system it is installed on has that level's capabilities; a newer capability is the app's to use where the system has it, after looking at `PHONE_PLATFORM` (the Go SDK's `App.Platform`; a system without the variable is level 1) or by taking an older system's answer `unknown capability` (§2.1). There is nothing like Android's `targetSdkVersion`: §2.1 does not allow an existing capability's behaviour to change within a major version, so there is no new behaviour for an app to opt in to.
- `kario new` writes the SDK's level as a new project's `min_platform`; `kario manifest check` and `kario build` refuse a level newer than the SDK's, and a version in `capabilities` of a higher level than `min_platform`.

Status: unit tests on the development machine ✓ (`ui`'s capability level table, installing and starting in `shell`, the catalogue in `pkg`, `?platform=` in `appstore`, `apps/store`, `cmd/kario`'s template, `sdk`). Level 2 (`media.list@2`) is the first time the level rose: the tables, the tests, `tools/tsgen` and `kario new`'s template followed, and unit tests, the selftest and the compatibility test pass on the development machine ✓; no system of level 2 has been released yet, and a phone of level 1 meeting an app of level 2 has been gone through in unit tests only (`pkg`, `appstore`, `apps/store`), **not tried on a phone**.

### 2.3 Capability versions

When a capability's arguments or result have to change in a way older apps do not understand (what the table of §2.1 allows only in a new major: renaming, removing a field, changing a type, making an optional field required, a result of another shape), the capability is not changed: it gets a new version, with argument and result types of its own, served beside the old one (`ui/capver.go`).

- **Names**: an app asks for `name` or `name@N` (`N` a decimal number from 1, without leading zeros). The bare name is version 1, so `media.list@1` and `media.list` are the same: the bare name is what systems before capability versions know too, so the SDKs send it for version 1. The broker first resolves the name (`ui.ResolveCap`), and from then on the permissions, runtime grants, the location switch, the dialog quota, the product's capability providers, the capabilities web pages may call and the compatibility test's counts all go by the resolved key (the bare name for version 1, `name@N` for later ones): `sms.send@1` needs the permission `sms.send` does.
- **Which versions are served**: `ui.CapLevels` has a key per version, with the level it came in at; a capability's versions are served side by side. One capability has two versions today:

| Capability | Level | How it differs from the other version |
|------|------|------|
| `media.list` (version 1) | 1 | The whole library in one array; its arguments `MediaArgs` are shared with `media.pick` and `media.delete`, and an unknown `kind` is taken for `audio` |
| `media.list@2` | 2 | A page: `{kind?, offset?, limit?}` (`ui.MediaListArgs`, `limit` 1–500, default 100) answered with `{items, total, next?}` (`ui.MediaPage`; `next` is the next page's `offset`, absent on the last page), in version 1's order; arguments of the wrong type or range or an unknown `kind` are errors. Why: with a large music library (thousands of tracks, a few hundred bytes each) one answer of version 1 goes past the longest message (`wire.MaxLine`, 4 MB), and a bare array cannot take a field like `total` |

- **A version not served**: the answer is `unknown capability "media.list@3" (served: media.list@1, media.list@2)`; without such a capability it is `unknown capability "…"`, as before. Both start with `unknown capability`, so an app that takes an older system's answer as §2.2 says takes a new version's on an older system too. A version not served is not counted in the compatibility test's calls.
- **Removal**: a version a later version exists of is superseded (`ui.d.ts` says so above it) and stays served for at least `ui.CapKeepLevels` (3) more platform levels: when the next version came in at level L, it may go at level L+3 at the earliest (`media.list` at level 5). Removing changes the protocol too, so that release raises the level; the removed version moves from `CapLevels` to `ui.CapRemoved` (with the level that removed it), and `ui`'s test holds both tables to these rules (`CheckCapTables`: removed too early, with no later version, still served, or at a level not reached all fail). Once removed, a call to it is answered `unknown capability "media.list@1": removed at platform level 5 (served: media.list@2)`, and an app with it in `capabilities` is not installed, nor started if already installed. Once version 1 is removed the bare name is refused with it and does **not** move on to the oldest version still served: an app using the bare name was written for version 1 and sends version 1's arguments. No version has been removed so far (`CapRemoved` is empty).
- **The manifest**: `capabilities` (§1) names the versions the app cannot work without. The installer can only check whether this phone serves them (what the app actually calls it cannot know): it refuses the app when it does not, and an installed app the system stopped serving one of does not start ("“…” needs …, which this phone does not have"). `kario manifest check`, `kario build` and the store backend also check that each version's level is no higher than `min_platform` (`ui.CheckCapabilities`): an app naming `media.list@2` has `min_platform` 2 at least. For a newer version not in `capabilities` the app looks at the level first, or takes `unknown capability`, as §2.2 says.
- **SDKs**: Go uses the constants of `ui` (`ui.CapMediaList2`) and `App.Platform`. TypeScript keeps `call`, and a later version is a key of its own in `CapArgs`, `CapResult` and `CapLevel`: `call("media.list@2", { kind: "audio", limit: 50 })` resolves to a `MediaPage`, `call("media.list")` still to `MediaItem[]`; no function per capability is generated (`kario.media.list()` and the like): `call` already types by the capability's name, and a later version is one more key that reads as plainly. A superseded version carries a note in `ui.d.ts` (which version replaces it, until which level it is served at least), which an editor shows on hover; `ui.d.ts` does not list `name@1` (write the bare name, which systems of level 1 know). TypeScript apps cannot read `PHONE_PLATFORM` yet (**not implemented**) and `catch` the `unknown capability`. C's `sdk/c`: `phoneui_call_version(ui, "media.list", 2, args, &res, &err)` (version 1 goes as the bare name) and `phoneui_platform()` for the level (1 without the variable); `phoneui_call` takes `"media.list@2"` as it is too.
- **Compatibility test**: each version served counts as one capability, so `media.list` and `media.list@2` must each be called at least once (the report's capabilities go from 137 to 138); calls of `media.list@1` count for `media.list`. The probe app checks that `media.list@2` pages, that `@1` is the bare name, and that a version the system lacks is refused (§11).
- **Adding a version**: in `ui/caps.go` a constant (`CapXxx2 = "xxx@2"`) and its argument and result types, and the new level in `CapLevels` (with `PlatformLevel` up by one if this release has not raised it yet); the broker's `capPerms` and dispatch take it (its permissions usually the old version's; where a permission depends on the arguments, as `media.list` needs `photos` for photos, both versions are listed); its types in `capTypes` of `tools/tsgen`, then `go run ./tools/tsgen`; a row each in this document's catalogue and in the table above; the probe app calls it. The old version's code stays as it is.

Verification: `ui`'s `TestParseCap`, `TestResolveCap`, `TestCapTables`, `TestCheckCapabilities`; `shell`'s `TestCapVersionDispatch` (answers and counts of the bare name, `@1` and `@2`, a version not served), `TestCapVersionChecks` (`@1` and `@2` need the permissions the bare name does), `TestCapVersionRemoved` (once version 1 is removed the bare name and `@1` are refused, `@2` still answers), `TestMediaPage`, `TestManifestCapabilities`; `cmd/kario`'s `TestManifestCapabilities`, `appstore`'s `TestSubmitCapabilities`; `tools/tsgen`'s `TestTypes`; `sdk/c`'s `test_phoneui.c`; the probe app's "capability versions" check.

Status: unit tests, the selftest and the compatibility test pass on the development machine ✓, **not tried on a phone**; removing a version has been gone through on test tables only (**not verified**).

**Action**:
- `id`, `label`, `key`;
- `primary` (OK runs it);
- `group: "danger"` or `confirm` (the system shows a confirmation dialog first);
- `hidden` (responds only to its shortcut key, not shown in the menu);
- `input` (only for actions on notifications): first lets the user type some text; the value is the hint shown in the input field, and the text is delivered to the app with `notif_action` (`OnNotifText` in the Go SDK).

**Left and right arrow keys**: actions on the focused element or on the screen whose `key` is `left` / `right` are triggered by ← → (volume down / up, the player's previous / next track, the image viewer's previous / next image). When nothing is bound, ← goes back one level and → opens the focused item (same as OK). In grids the arrow keys move as usual; in an input field with text they move the caret and stop at its ends ([18](18-nokia-form-factors.md) §4.2).

**Fields for the screen reader**: any node may carry `role` (`switch`, `checkbox`, `radio` for a radio button, `button`, `link`, `heading`), `checked` (a switch's, checkbox's or radio button's state) and `a11y_label` (what the screen reader reads instead of the node's text: an item that is only a symbol or an icon; a calculator's "×" could be labelled "times"); the screen does not show them (Settings › Accessibility's screen reader, [19](19-core-apps.md) §1.4). Without `role` the reader reads by kind (edit box, button, progress bar…), and a list item by its title, subtitle, `trailing`, `badge` and its place in the list. KarioUI's components have no properties for them yet (**not implemented**); TypeScript apps write these fields on the nodes directly.

**Action naming conventions**: a few action IDs are bound to hardware keys, so the app does not need to handle key presses itself.
- `call` / `dial`: triggered by the call key (green key). The actions on the focused element are checked first, then the screen actions; when the `submit` of a dial input field is `dial`, the call key dials directly.
- `hangup`: the end key (red key) triggers this action on the screen; if the screen has no such action, the end key hangs up a call in the background (Nokia's red key), else returns to the idle screen.
- `hide` (`ui.ActionHide`): handled by the system and not sent to the app: the app goes to the background with this page, and the app that was in front before it came to the front is shown again (with none, the system's screens, the idle screen). With this action on the page, Back does the same instead of leaving the page. Meant for pages that must stay while something goes on, such as a call screen (Phone's call screen has it as the right soft key 「最小化」 (Minimize), [19](19-core-apps.md) §5). It does nothing while the secure lock is on.
- With no `call` / `dial` on the page, the call key goes back to the call in progress (Phone's call screen, a VoIP app's call); only without a call does it open the recent calls.
- The incoming-call screen is drawn by the system, and answering with the call key and rejecting with the end key are handled by the system too.

Apps never draw pixels and cannot see other apps' screens. Images are decoded and displayed by the system: `media:<id>` is only displayed for apps that can access that photo (§4.6), `contact:<photo>` only for apps with the `contacts` permission.

**Capabilities in web pages**: a page inside a `web` node has `phone.call(capability, params)`, which returns a Promise; results and errors are the same as for an app's `req`. Requests are handled by the capability broker under the host app's identity, with the origin 「网页 <主机>」 (web page <host>): grants are recorded under that origin, and the system UI states which web page is asking (the same mechanism as a mini-program's `origin`). Only `share.open`, `clipboard.set`, `location.get` and `auth.confirm` are available; all other capabilities return an error.

When the phone leaves unmetered Wi-Fi while such a job runs (within its wake; the system looks at the network every 2 seconds meanwhile) for mobile data, a metered Wi-Fi or no network at all, the system stops it as Android's JobScheduler does: the app gets a `job.stop` event (§5) and should stop its download and keep its progress; 5 seconds later the run's wake ends (an app in the background is frozen; one in the foreground, or with another job running, is not). The job keeps its period and its conditions and runs again as soon as the phone is back on unmetered Wi-Fi (waking the phone for it), without waiting for the next period. A `charging` job that runs when the charger is pulled is stopped the same way (the system looks at the power with its housekeeping, about once a second): the app gets `job.stop` (reason `unplugged`), the run's wake ends 5 seconds later, and the job runs again as soon as the phone is plugged in. The store, told so (whatever the reason), ends the update packages it is downloading in the background and downloads them on the next run. A `network: true` job needs a network: it waits while there is none, and for Wi-Fi (a metered one too) while the app's mobile data is blocked in the background (background data off, Data Saver, its own limit used up, [19](19-core-apps.md) §1.3), as Android's JobScheduler holds a restricted app's jobs; running, it is stopped the same way when the phone moves to a network it may not use (`job.stop`'s `reason` is `blocked` or `offline`). Jobs share the hourly wake-up budget with push; runs beyond the budget wait until the app returns to the foreground. Registering the same `id` again replaces the old job; jobs survive reboots | — |
| `net.state` | — | The network the phone is on and whether the app's mobile data is blocked ([19](19-core-apps.md) §1.3): `{network, metered?, background_data, data_saver?, blocked?, limit?, used?}`; `network` is `wifi`, `mobile` or `none`, `metered` mobile data or a metered Wi-Fi, `background_data` whether it may use mobile data in the background (false when the user turned its background data off, or Data Saver is on and it is not among those unrestricted), `blocked` why its mobile data is blocked now, whatever network the phone is on: `wifi_only` (Wi-Fi only in App permissions), `app_limit` (its own limit for this cycle is used up), `background_data` (it is not on the screen and its background data is off); on mobile data while `blocked` its connections fail at once (EPERM from the firewall on the device; fetch rejects). `limit` is its own limit a cycle (bytes), `used` what it used of it (mobile data at home and abroad). When the block changes, an app that runs and is not frozen gets a `net.state` event (§5). The dev machine has no firewall: the block is the Shell's policy alone and the app's connections go through; so on a phone whose kernel lacks the per-app firewall | `net` |
| `job.cancel` | `{id}` | Cancel one of the app's own jobs | — |
| `net.keepalive` | `{host, port, every_s}` / `{close: true}` | One long connection of the app's own ([21](21-push.md) §8; platform level 2): the system connects to the server as the app (TCP; an error when it cannot within 10 seconds), hands the app the socket with the reply (§7) and answers `{every_s, push_s, addr}` (`push_s` is the push connection's heartbeat interval now, 0 while not known). By default location is for the foreground app only: a background app's request returns `location is for the foreground app only`, refused before the system would ask the user for the grant (no location dialog comes up over another app), and a `location.get` waiting for a fix ends the same way when its app leaves the foreground. While the location switch in system settings (`location`, §4.5) is off, both requests return `location is off in Settings` and the receiver goes off at once; an app watching at that moment gets a `location.off` event, and its watch stays but sends nothing until location is on again. A phone with neither a location receiver nor a network location (or with it turned off) returns `this phone has no location receiver`. While an app watches, a `location.get` waits for a fix, or a fix was handed out in the last 3 seconds, the status bar shows the location icon; which apps used the location in the last 24 hours (and which of them in the background) is listed in 「设置 › 位置」 (Settings › Location).

**Precise and approximate location** (Android 12): the first time an app asks, the system's grant dialog offers three answers: 「精确」 (Precise), 「大致」 (Approximate) and 「拒绝」 (Deny) (Precise by default, the arrow keys move), and the precision chosen is kept for the app; for a request with `approximate: true` the dialog offers only Approximate and Deny. An app given only the approximate location (by the user, or because its request asks for no more) gets the centre of a cell about 2 km on a side (Android's LocationFudger uses 2000 m): the grid is shifted randomly per device, and one place always falls in the same cell, so fixes averaged over time give nothing finer than the cell; at a cell's edge the noise of the fixes does not flip it between two cells (a fix less than 0.15 of a cell past the cell last given keeps that cell), which would otherwise show where the edge, and so the person, is; `approximate: true`, `accuracy_m` at least 2000, and no altitude, speed, bearing or satellites. The user can change the precision later in 「设置 › 位置」 or in 「设置 › 应用权限」 (Settings › App permissions; the `p` key).

**Background location** (Android 10/11, iOS's "Always"): an app declares `location_background` in its manifest (a runtime permission, with a `purposes` entry; the installer and the store refuse it without one, and without `location` declared too; `location.background` is a platform level 2 capability, §2.2). The first dialog never asks for it, only for the location "while in use"; all the time is a step of its own (since Android 11 it cannot be asked with the location): the app calls `location.background` later, and the system asks in a dialog of its own (the table above; like the other grant dialogs it takes only keys pressed after it showed, and in its first 500 ms only the arrow keys and Back, [11](11-platform-architecture.md) §16.1), or the user changes it to "allow all the time" in 「设置 › 位置」 (the `b` key) or in 「设置 › 应用权限」 (the 「后台使用位置」 (Location in the background) row). Given, the app has the location also out of the foreground while it is not frozen (in a background job's wake window, in the grace period before it is frozen), and its watch does not pause; without it such a request is refused as before (no dialog). An app declaring the `location` background mode is not frozen while it watches the location, allowed all the time (iOS's location background mode). Mini-programs have no background location.

The user sees a use in the background: while an app watches the location in the background, waits there for a fix, or was handed one there in the last 3 seconds, the middle of the status bar says 「● <app> · 后台定位」 ("● <app> · location in the background"; with several apps, how many; `mid_kind` is `location`, [23](23-renderer-protocol.md) §4), and the location icon at the top right shows as usual. While an app watches in the background, the system keeps a notification up in Settings' name, 「「<app>」正在后台使用你的位置」 ("“<app>” is using your location in the background"; Android's foreground service notification; no banner, no sound, not counted unread); it goes when the app comes to the foreground, is frozen, stops watching or loses the grant, and comes again the next time it watches in the background; one the user cleared from the notification center stays away until then. The notification's 「停止」 (Stop, the `s` key) keeps the app from the location in the background until it is next in the foreground: its watch stays but sends nothing, a `location.get` it waits with in the background returns `location is for the foreground app only`, its requests in the background are refused, and the `location` background mode no longer keeps it from being frozen (so it no longer uses mobile data with background data off as a foreground service would, [19](19-core-apps.md) §1.3); the app gets a `location.stopped` event (§5). Coming to the foreground, or the user allowing it all the time again in Settings, ends that; the stop is kept in memory only, and a restarted Shell forgets it. Opening the notification shows 「设置 › 位置」, where the app is marked 「正在后台使用」 (in the background) under 「正在使用」 (In use now) (`settings.get`'s `location.using_background`). Every use in the background is recorded in the recent access (`bg_at`); the system looks once an hour and reminds of apps that used the location in the background with a notification in Settings' name (「有应用在后台使用了你的位置」, "Apps used your location in the background"), each app at most once a week and only if it used it again since it was last named; opening it shows 「设置 › 位置」. An app not opened for 90 days loses this grant with its other runtime grants.

The receiver comes from the hardware SKU (`gnss` in [24](24-sku-framework.md) §2): the developer machine has a simulated receiver, which writes real NMEA 0183 sentences through the same parser as a phone (`location/`); QEMU reads a named pipe in the Shell's run directory, which the selftest writes NMEA into; a phone reads the kernel GNSS subsystem's `/dev/gnssN` or a serial port, or the modem's GPS through ModemManager's Location interface (**not yet tried on a real device**). The receiver is on only while someone needs a fix and goes off 5 seconds after the last request ends; when it fails (no device, ModemManager has no modem) it is tried again after 5 seconds up to a minute.

**Assisted GNSS (A-GNSS)**: when the receiver is a modem through ModemManager, it gets assistance data each time before it comes on (`location.ModemManager`): if the modem can do A-GPS (`AGPS_MSB` or `AGPS_MSA` in `Capabilities`) and the product names a SUPL server, `SetSuplServer` sets it (unless it is set already) and A-GPS comes on with the GPS (MSB where it can); if `Setup` refuses A-GPS, only the GPS comes on. If the modem takes predicted orbits (XTRA in `SupportedAssistanceData`), the data is downloaded from its `AssistanceDataServers` (http or https only, at most 1 MB) into the state directory (`shell/gnss/`, 0600), again once a day, data up to a week old is used while no server answers, and the servers are not tried again within an hour of failing; `InjectAssistanceData` injects it, the same data not again within a day. Whatever of this fails, the receiver comes on all the same. The modem's location sources are put back as they were at the end. What it was last given is in `settings.get`'s `location.assistance`, and shown on the Settings page. The product's composition layer (`profile.d`, [14](14-tui-route-and-app-framework.md) §2.1) sets it under `location`: `supl_server` (`host:port`; empty: no SUPL) and `no_assistance_data` (true: no predicted orbits downloaded). The calls and their order are tested against a simulated ModemManager; **not tried on a phone**, and real SUPL and XTRA servers are **not verified**.

**Network location**: while the receiver has no fix (none 5 seconds after location is first needed, or lost), the network location service is asked by the Wi-Fi access points in range and the cell the phone is on, at most every 30 seconds; once the satellites fix, it is not asked. It is asked only while the location switch is on and an app allowed the location needs a fix, and only with what `location.Observation.Usable` lets go: no hidden network (no name), none whose name contains `_nomap` or `_optout` (the owner opted out), no randomised or multicast address, the strongest 20 at most, and no Wi-Fi at all with fewer than 2; a cell only with its whole identity (MCC, MNC, LAC/TAC, CI). The request asks not to be placed by its IP address (`considerIp: false`, `fallbacks` off). The answers are kept on the phone (the state directory's `shell/netloc.json`, 0600, a week): the same networks heard again (at least 2 access points in common, and at least half of them; for a cell alone the same cell) are answered from there, and "not known" is believed for an hour; the service is asked at most 60 times an hour (a product may set fewer), at least 10 seconds apart, and after it fails, again after a minute, doubling up to 30 minutes. The fix has `source: "network"` and no altitude, speed or satellites; an app given only the approximate location gets only its cell. The user can turn 「Wi-Fi 和移动网络定位」 (Wi-Fi and mobile network location) off in 「设置 › 位置」, which deletes the answers kept on the phone too. The service is the product composition layer's `location.network`: `provider` is `http` (a service speaking the Geolocation API's JSON: Google's geolocate, Mozilla's Ichnaea and those running it such as BeaconDB; `url` must be https, or http to the loopback address), `fake` or `none`; a service that needs an API key (Chinese map providers' location APIs and most others do) gets it from `key_file` (the path of a file on the device) or `key_env` (an environment variable's name): the phone's owner gets the key and keeps it out of the image and the repository; the system ships no key and never writes it into a log or an error. `max_per_hour` lowers the rate to the service's quota. Without a configuration, a simulated phone (the developer machine, QEMU with its simulated modem) uses the fake service (`location.FakeProvider`: where the simulated receiver is, ±25 m with Wi-Fi, ±1200 m with a cell alone), and a phone has no network location. The Wi-Fi comes from iwd (the address of each BSS in a network's `ExtendedServiceSet`, with the network's signal; a known network's `Hidden` marks it hidden) or the simulated Wi-Fi; the cell from the 3GPP source of ModemManager's Location interface (`MCC,MNC,LAC,CI,TAC`, turned on first if it is off), and on a simulated phone a simulated cell. The Chinese map providers' own API formats (not the Geolocation API's JSON) are **not implemented**: one more implementation behind `location.Provider` would add one, which also has to turn their GCJ-02 coordinates back into WGS-84. Real services, iwd's BSS addresses and ModemManager's cell are **not tried on a phone** and **not verified**.

Reference: the weather app (`apps/weather`) gets the location in the foreground; its scheduled background refresh tries for the location (`max_age_s` 1800), which it gets if the user allowed it all the time, else it refreshes for the last place; it asks for all the time with `location.background` only when the user picks 「后台也跟着我的位置」 (Follow me in the background, the `b` key); its 「我的位置」 (My location) page shows the coordinates, accuracy, altitude, speed, heading and satellites live through `location.watch`, says when the network placed the phone and when the user stopped its location in the background from the notification, and calls `location.stop` on Back.

| `media` | `next` / `previous` | The user pressed a media key (headset remote, keyboard); sent to the app that is playing. Play / pause is handled directly by the system |

| `nfc.apdu` | `{session, card, aid, apdu}` | A reader sent a command for one of the app's cards (hex); the app answers with `nfc.reply` (§4.11, `nfc` permission) |

## 6. Permissions and background

| Category | Permissions | Notes |
|------|------|------|
| Runtime (asked on first use; the user can revoke them in Settings) | `camera`, `microphone`, `contacts`, `photos`, `location`, `nfc_reader` (reading NFC cards held to the phone), `location_background` (the location in the background too: not asked for with the location; the app asks later with `location.background` in a dialog of its own, or the user gives it in Settings) | The grant dialog is drawn by the system, and apps cannot spoof it; when an app installed from the store has not been opened for 90 days, the system revokes these grants and asks again next time; the `location` dialog offers the precise or the approximate location, which the user can change later in 「设置 › 位置」 (Settings › Location) and 「设置 › 应用权限」 (Settings › App permissions) (§4.7) |
| Granted when declared | `keystore`, `attest`, `notifications`, `voip`, `net`, `phone`, `sms`, `nfc`, `keepalive` (one connection of its own kept while frozen; `net` has to be declared too) | Automated store review only rejects `system`, `install` and pre-grants, and new apps and updates that request more permissions go into manual review; `keepalive` needs its purpose in `purposes`, and **every version** of an app with it goes into manual review (it spends the whole phone's standby); `phone` and `sms` still do not let store apps place calls or send SMS on their own: the system asks the user to confirm every time (§4.2). Runtime permissions need their purpose in the manifest's `purposes`, shown in the grant dialog and checked at the staff desk |
| System apps only | `system`, `install` (app store) | The installer rejects packages that declare them; installed apps do not get them even if they declare them |

Background rules ([17](17-app-sandbox.md) §5):
- The process is paused (frozen) 10 seconds after leaving the foreground.
- When memory is tight, the system may end apps in the background (this does not count as a crash). When the user comes back, the app is on its earlier page: the system first shows the earlier pages, and the new process receives at startup the `state` it handed up when it left the foreground (Go SDK: `OnSave` returns what to save, `Restore` reads it back) and rebuilds its pages from it; on pages whose screen ID stays the same, the system restores the unsent text in input fields and the focus.
- Exceptions: the `voip` background mode; the `audio` mode while playing; the `location` mode while it watches the location, allowed all the time; during a call. An app with the `keepalive` permission is frozen all the same; only its one connection stays (`net.keepalive` in §4.7).
- To receive messages in the background, use push (the steps for partners are in [21](21-push.md) §8.1): pushes with only a title and body are shown by the system without waking the app; pushes with data wake the app briefly within a budget (at most 20 times per app per hour). When the server sends a push with `collapse_id`, a new push with the same key replaces an older push that has not been delivered yet, along with its notification (for content where only the latest value matters, such as unread counts and scores).
- After a VoIP push wakes the app, the app must report the incoming call within 10 seconds (a notification with `kind: "call"`); after 3 failures to report within 24 hours, subsequent VoIP pushes are treated as ordinary data pushes.
- When a push has `priority: "normal"`, its data does not wake a frozen app immediately; it is delivered when the app wakes up for some other reason (returning to the foreground, another wake-up), and at the latest the system does one batched wake-up after 15 minutes.
- Audio streams and recordings an app opens during a call (VoIP or phone) count as the "call" category: they have priority during the call and are not stopped when the app leaves the foreground ([20](20-audio.md)).
- Notifications: each app gets at most 5 notifications per minute with a banner and an alert sound; the rest only go into the notification center. The notification center keeps at most 24 per app, deleting the oldest first. The user can turn off an app's notifications in 「设置 › 应用权限」 (Settings › App permissions) (`notifications`, like the network, has only two settings, 「允许」 (Allow) and 「关闭」 (Off)); once they are turned off, the app's notifications are dropped outright, and incoming calls are not affected. Scheduled notifications (§4.4) follow the same rules when they come due: within the banner budget, and not shown once turned off.
- Actions on notifications (quick reply): when the user selects an app's action in the notification center, the system delivers it to the app in the background (a frozen app is resumed first, an app that is not running is launched in the background, and this does not count against the push wake-up budget), and then clears the notification.
- For periodic sync, use background jobs (§4.7); they share the same wake-up budget with push.
- Reference: how Hongyan does it ([21](21-push.md) §4): it is not resident; when it comes online, it gives its push token to its own server; messages from the other party come down as "notification + data" pushes carrying the conversation `thread`; incoming calls use VoIP push.
- How a TypeScript app does it: the tutorial [34](34-app-tutorial.md) §7.1 (push) and §7.2 (background jobs), the sample `examples/karioui-notes`.

## 7. Files and shared memory (fd passing)

The replies of some capabilities come with open files attached; the message's `fds` field says how many:

| Capability | Attached file | What you can do |
|------|------------|------------|
| `audio.stream`, `audio.record` | A memfd holding a ring buffer of 48 kHz mono 16-bit audio, with its size sealed | Map it and read/write samples; for the format see `audio/ring.go`; in the Go SDK it is `app.GoAudio`, in TypeScript the result's `ring` (§9.2) |
| `media.pick` | Read-only file of the selected photo (PNG or JPEG, see the entry's `mime`) | Read it, upload it; you cannot write to it, and you cannot reach any other file in the gallery. In the Go SDK it is `app.CallFile`, in TypeScript the result's `files[0]` (§9.2) |
| `file.pick`, `file.open` | The file the user picked, or one handed to this app before, read-only (§4.9) | The same |
| `net.keepalive` | The TCP socket the system connected for the app (§4.7) | Speak your own protocol on it (TLS included); in the Go SDK `app.CallFile` with `net.FileConn`. The system keeps a copy of its own, which it only looks at for data and never reads; Go's `FileConn` turns TCP keep-alive on, turn it off (`SetKeepAlive(false)`); the system turns it off too when the app freezes. A TypeScript app's runtime takes it, for the keepalive WebSocket (§9.4) |

Rules:
- **There is no rule of one fd per message.** A message carries at most 8, which is only a cap against oversized messages. What really needs to be controlled is the following:
- **Receiving**: files arrive with the first byte of their message, so once the whole line is there its files are too; the message's `fds` says how many to take, in the order they arrived. The Go SDK (`wire`'s `TakeFiles`), the C SDK (`phoneui_fds` / `phoneui_take_fd`; what is not taken is closed at the next message) and kario-jsrt all take them so; at most 32 files no message claimed are kept, the rest closed.
- **Direction**: files only flow from the system to apps. fds an app sends to the system are closed immediately, so an app cannot exhaust the system's file descriptor table by stuffing fds into it.
- **Count**: each app can have at most 4 audio streams open at the same time, of which only 1 can be a recording; system services have an overall cap as well. The number of open files of the app process itself is limited by the sandbox (1024).
- **Type**: the system only sends objects it has verified itself, such as size-sealed memfds and files opened read-only. The receiving side checks again too; for example, it refuses to map a ring buffer that is not sealed.

## 8. Sandbox restrictions

- Apps can only read and write `PHONE_DATA_DIR`. There is no shared `/tmp`; temporary files go in `$TMPDIR` (under the data directory).
- Files in the data directory cannot be executed, i.e. apps cannot download code and run it. Mini-programs should use the JS runtime provided by the host. A TypeScript app's native modules (§9.3) load from its package only; Landlock covers `execve`, not native code mapping a file into executable pages, so once the modules are loaded kario-jsrt seals executable memory with seccomp (§9.3).
- Without the `net` permission there is no network; even with it, apps cannot listen on ports.
- Apps cannot see other processes or debug them, and dangerous system calls are blocked.
- The memory limit is 192 MB (no swap), and processes and threads combined are limited to 128. When the memory limit is exceeded, the system ends only your app and tells the user 「超出内存上限」 (Memory limit exceeded); an app whose tasks, over 2 s at its limit, spend more than half of the time waiting on memory (the kernel reclaiming your program's pages and reading them back) is ended the same way ([17](17-app-sandbox.md) §5.4). Page cache filled by reading files does not count: the kernel reclaims it. Save data promptly. Go programs get `GOMEMLIMIT=144MiB`, so garbage collection works harder before the hard limit is reached.
- When system memory is tight, apps in the background are ended first, least recently used first; foreground apps, apps in a call and apps playing in the background are never picked. An app that was ended cold-starts the next time it is opened, so save data as soon as you get `lifecycle: background`.
- A page has at most 1000 nodes; the excess is cut off. The page stack is at most 32 deep; pushing beyond that replaces the top. For pages whose title contains the word for System in any of the four UI languages (「系统」, 「系統」, System, Sistema, as in Spanish "…del sistema"), the system prefixes the title with the app name, so apps cannot impersonate system dialogs.
- For apps with the `net` permission, the user can turn off their network in 「设置 › 应用权限 › 网络」 (Settings › App permissions › Network): the system ends the app, and the next time it starts without a network.
- When an app exits on its own with a non-zero exit code (crash, panic, killed by a signal), the system records the time, the reason and the last 20 lines of the log, which can be viewed under 「设置 › 关于本机 › 应用崩溃记录」 (Settings › About phone › App crash records). After 3 crashes within 10 minutes, the system temporarily stops launching the app in the background (pushes and background jobs are held until the user opens it).
- About 10 seconds after leaving the foreground, the whole app is frozen together with its child processes; in the background its CPU share is also lower than in the foreground.

### 8.1 Middleware robustness

The Shell keeps a budget for every app: a buggy or hostile app only slows down or brings down itself, the system UI and the other apps stay responsive, and the Shell's memory stays bounded. An app over a limit is slowed down, refused, or ended with a crash record that names the reason (「设置 › 关于本机 › 应用崩溃记录」, Settings › About phone › App crash records). The limits are named constants, most in `shell/guard.go`.

| Limit | Value | When exceeded |
|------|----|--------|
| One message (one line) | 4 MB | The app is ended at once; crash record "protocol violation: a message over 4 MB" |
| Malformed lines | 16 per run | Dropped and logged; at the 16th the app is ended, with a crash record saying so |
| Message rate | 250 a second on average, bursts of 500 | The Shell reads the app's socket more slowly, so the app's own writes block; one log line, counted in `phone-shell --dump` |
| Messages waiting for the event loop | 8 units of 64 KB (a message counts at least one) | The Shell stops reading the app until the loop catches up: one app cannot fill the system's event queue, nor memory with large messages |
| Event loop time | About a fifth; up to 50 ms of it at once first (a start's first pages, the answer to a key), past that it rests until its share covers what it took (`loopShare` in `shell/guard.go`, since 2026-11-27; before, it rested 4 times each 1 ms used, and the app's next page waited behind the rest) | As above |
| Messages to the app it has not read | 256 (plus the socket buffer) | The Shell never blocks writing. An app that is not frozen is ended, crash record "not reading its connection"; a frozen app is ended the way the low-memory killer ends one (it keeps its tombstone; thawed and asked to end first, killed only if still there after 3 s, [17](17-app-sandbox.md) §5.5) |
| Unanswered capability requests | 64 per app | Further requests get `err: "too many requests in flight"` at once (`ui.ErrBusy`) |
| Keys pressed after an action went to the app and before it handled it | Held, at most 32 and 500 ms (until the app answers a ping, [11](11-platform-architecture.md) §16.1) | Then they go on as they are; the app only gets them later |
| Keys pressed before a system dialog that asks for a decision came up, and its confirming keys in the first 500 ms | Not an answer ([11](11-platform-architecture.md) §16.1) | Dropped and logged; the arrow keys, Fn + ◀ ▶ (`first`, `last`) and Back act at once |
| Requests that open a system dialog (`auth.confirm`, `scan.qr`, `camera.capture`, `media.pick`, `file.pick`, `file.save`, `media.delete`, `share.open`, `nfc.read`, `wallpaper.set`, `tel.dial`) | 1 at a time per app | As above |
| Consent dialogs | One per app (mini-program) and set of permissions | Later requests wait for the same answer |
| Text of one node | 64 KB (a doc node's Markdown too: it is parsed when the page arrives and laid out again for every frame, each about 0.5 ms a KB); titles, labels, IDs and the other short fields 4 KB | Cut, ending in "…"; logged once per run |
| Actions | 64 per node and per page | The rest are left out |
| Canvases | 8 per page; each canvas's shapes are clipped to it first and may visit 8×320×320 pixels in all, a polygon has at most 1024 points | Further canvases and shapes are not drawn |
| Toasts, notifications | Toast 300 characters; notification title 200, body 2000 characters, 8 actions | Cut |
| Log lines one app causes | 20 per 10 seconds | Only counted ("N more lines not logged") |
| Connection closed, process still alive | 5 seconds | The process is killed |
| Process exited, a child still holds the socket | No wait | The Shell closes its end and kills the process group before it reaps the process (developer machine; on the device the pid namespace and cgroup do this) |

System services: every call the Shell makes to a service has a deadline, 15 seconds by default; methods that wait for the outside world have their own: dialling and USSD 60 seconds, sending an SMS 120 seconds, waiting for an NFC card 75 seconds; methods that wait for the user or the hardware (a finger to unlock, the next touch while enrolling a fingerprint, the result of a QR scan) have none and end with their cancel method or with the service's connection. A call past its deadline fails (`service did not answer in time`), the app's `res` carries that error, the request no longer counts as waiting, and the not-responding check carries on; a broken connection (the service crashed, or answered with a line that is not JSON or is too long) is dropped and the next call connects again (systemd restarts the service; on the developer machine phone-shell or the test does). The input method (phone-imed) gets 2 seconds a call; after a failure the built-in engine takes over for 2 seconds, doubling with each failure in a row up to a minute, so a stuck imed does not stall the system for 2 seconds at every key.

Verification (all in `make test`, run on the developer machine):

- `TestHostileApps` has fake apps attack the real Shell over real sockets: flooding messages, messages close to 4 MB, an over-long line, malformed lines and deep nesting, unknown messages, a wrong protocol version, never reading, passing many file descriptors, requesting capabilities in a tight loop, absurd pages, forking children, closing the connection without exiting; meanwhile a well-behaved app requests a capability every 20 ms. Bounds: event loop p99 latency ≤ 250 ms, the well-behaved app's round trip p99 ≤ 500 ms, Shell heap growth ≤ 96 MB, the offending app slowed down or ended with a reason, no Shell crash.
- `TestServiceFaults` has a fake service hang, answer garbage, answer with the wrong id, answer an over-long line (a whole answer, only longer than `wire.MaxLine`, also one that takes longer than a call's deadline to arrive), crash, disappear and come back: calls to the hung service and those answered with the wrong id fail at their deadline, the others with the broken connection's error, not by the deadline (judged by how the call ends, not by how fast the machine is), the event loop is unaffected, no goroutine leaks, and the service is used again once it is back.

Soak test: `make soak` (`SOAK=30m` by default) runs `shell/soak.script` round after round on the full service stack (app launches and exits, end-to-end encrypted chat over push, video calls out and in, a banner and the notification centre, a tombstone and its revival, a cellular call, SMS out and in, music in the background, the TypeScript calculator) and after each round records the Shell's descriptors, goroutines, heap and RSS and each system service's descriptors and RSS into `SOAK_OUT` (CSV, `build/soak.csv` by default). When the lowest value of the last third exceeds the highest of the first third by more than a limit (Shell: 16 descriptors, 64 goroutines, 16 MB heap, 48 MB RSS; each service: 8 descriptors, 16 MB RSS), it counts as a leak and the test fails; a sawtooth (garbage collection, caches filling once) does not.

### 9.1 UI text and translations

Code is written in English only (comments too; `scripts/no-chinese.py` checks it in `make test`); the UI's words are written as English messages, English being the source that needs no catalog, and their translations go next to them in `locale/<lang>.json` (`{"English": "translation"}`). The system offers four UI languages:

| Language | Tag | Where a missing message comes from |
|------|------|------|
| 简体中文 | `zh-Hans` | English |
| 繁體中文 | `zh-Hant` | Simplified Chinese, then English |
| English | `en` | (the source) |
| Español | `es` | English |

`PHONE_LANG` picks the language: the Shell hands it to every app (one of these four values; a process that gets none uses `zh-Hans`). A message a language's catalog lacks is looked up along the fallback chain in the table, ending with the English source, so a partly translated catalog still works. A message with arguments uses `%s` and `%d`, and its translation in every language keeps the same placeholders in the same order; for text whose word order differs between languages, such as dates, the Shell uses layout messages without placeholders (e.g. `{weekday}, {month} {day}`, which Spanish translates as `{weekday}, {day} de {month}`).

The user chooses in Settings › Language (or "Automatic": by region, CN Simplified Chinese; TW, HK, MO Traditional Chinese; the Spanish-speaking countries Spanish; everything else English; on a developer machine the Shell's own `PHONE_LANG` takes the place of automatic). On a change the Shell's own text switches at once (`i18n.SetLang`; every catalog made with `i18n.New` in a Go package follows), and apps restart as on iOS: the system ends them with their tombstones ([17](17-app-sandbox.md) §5.3), the app in the foreground comes back at once, on the page it was on, those in the background when the user opens them, and each new process gets the new `PHONE_LANG`; an app in a call or working in the background (playing music, VoIP) is not interrupted and switches when it next starts. The renderer and the web processes restart too. An app that wants to come back on its page hands over its page state in `OnSave` (that is how Settings comes back on its Language page).

`scripts/i18n-check.py` checks that every call has a Simplified Chinese translation, that every translation in every language is still used and keeps the placeholders, and reports for each catalog how much of Traditional Chinese and Spanish is translated and how much is missing (missing messages are not errors for now; `--strict zh-Hant` makes them so). The catalogs of the Shell, the Settings app, the terminal front end (`programs/shellcmd`) and the other system apps, the mini-program host and its built-in mini-programs, the samples, the renderers, the web view, the input method, the sandbox self-check, USB sharing, the compatibility test app, Feiqian (`apps/wallet`), the TypeScript calculator, samples and `kario` project template are fully translated; only the `jsrt` test app (test data) still lacks Traditional Chinese and Spanish, `i18n-check.py`'s report being the reference. The Traditional Chinese and Spanish translations are machine translations **not yet reviewed by native speakers**.

| Language | How | Catalog |
|------|------|------|

### 9.2 TypeScript apps

TypeScript is the main language for apps ([29](29-app-development.md)). An app is written in TypeScript only: the `kario` command line (written in Go, with esbuild built in, so no Node needed) compiles it into one ES2023 module, and the system's `kario-jsrt` (QuickJS-ng plus the `kario` module, speaking the protocol of §2 through the C interface `sdk/c`) runs it in the app's sandbox. The code can `import` one module, `"kario"` (and the app's own native modules, `"native:<name>"`, §9.3): there is no QuickJS `std` or `os` module, and it opens no file, socket or process of its own (its files are only those a capability's reply hands over, §7; the network only through `fetch` and `WebSocket`, §9.4); capabilities still go through the broker (permissions, purposes, system UI), and the app's data is reached only through `storage`. Unit tests and the selftest pass on the developer machine; the QEMU selftest ✓ ([29](29-app-development.md) §5), **not run on a real phone**.

```bash
kario new notes            # manifest.json, src/main.ts, src/locale/zh-Hans.json, tsconfig.json, types/kario/ (the types)
kario build notes          # → notes/build/: manifest.json, main.js, locale/, the icon; the manifest is checked first by the installer's rules
kario package -key dev.key -cert dev.cert -o notes.phoneapp notes   # builds, then signs and packages; key and certificate as phone-pkg's (§12)
kario package -devstore DIR -o notes.phoneapp notes                 # signed by a development store, which phones in developer mode trust
kario device install -open notes                                    # in developer mode over a trusted cable: sign, install on the phone, open
kario device logs -f com.example.notes                              # what the app writes (standard output and error), followed
kario device reload com.example.notes                               # reload (back on its pages through the tombstone); restart starts it afresh, uninstall removes it
kario device push seed.json com.example.notes:files/seed.json       # a file into the data of an app installed in developer mode; pull gets it back
kario device screenshot -o shot.png                                 # a screenshot (secure screens masked); key and type press keys and type
kario device syslog -f                                              # the system's log (the system services' and the Shell's), like logcat
kario device forward 9229 9229                                      # a port of the computer to the phone's loopback (ssh -L); reverse the other way
kario symbolize -symbols notes.phonesym crash.json                  # a crash's main.js stack mapped back to the TypeScript (symbol files, §12)
```

`kario device` runs `phone-dev` over SSH to the phone's address on the cable (`root@10.71.0.1`, the development image's dropbear), and the Shell decides: with developer mode off, this computer not trusted, or a request that did not come over the cable, it refuses; it only touches installed apps; a package goes through the installer's own checks ([29](29-app-development.md) §3, [27](27-usb-typec.md) §4). Developer machine ✓, QEMU ✓ (over real SSH), **not on a real phone**. The tools for the system (files to and from the phone, screenshots, keys and typing, the system's log, port forwarding, restarts, sideloading a system update, bug reports) and how they compare with Android's adb and fastboot are in [27](27-usb-typec.md) §4.1 (developer machine ✓; the emulator cases over real SSH (pushing and pulling files, keys, the system's log, port forwarding) QEMU ✓, 2026-11-27 night chain r86; **not on a real phone**).

Debugging on a real phone: Kario Studio's "Kario: Debug on the Phone" (the debug type `kario`, in launch.json `"type": "kario"` and `"project"`; the adapter is `kario dap`) builds the project unminified, installs it signed by the development store, and restarts the app under kario-jsrt's debugger over the same cable (`phone-dev debug`); "Debug the App Already on the Phone" (`"request": "attach"` in launch.json) installs nothing and joins the app as it runs, without a restart (`phone-dev debug -attach`, the app's state all there; one not running starts under the debugger). Breakpoints, conditional breakpoints, hit counts, logpoints, function breakpoints, step over, in and out, pause, the call stack, locals and closure variables, evaluating and setting variables in a frame, `debugger` statements and pausing on uncaught (or all) exceptions work as under Node, the positions in the `.ts` through the source map. Only for apps installed in developer mode (signed by the development store), not store apps or system apps; what is missing is in [29](29-app-development.md) §5.5. Developer machine ✓ (unit tests), **not on a real phone**.

A package carries JavaScript only (one with `main.jsc` does not install): once a TypeScript app is installed, the system precompiles it to bytecode on the device, in a system directory the app cannot write, keyed by the module's digest in the package's signature, checked before every start (if it does not match, the app runs its source and the cache is built again), and removed on update and uninstall ([29](29-app-development.md) §5.1). The developer does nothing for it.

### 9.3 Native modules

The slow parts of a TypeScript app (codecs, image processing, cryptography, a database, its own network protocol) can be written in C, C++ or Rust as shared libraries, signed with the package, which the JavaScript calls in the same process, like HarmonyOS's NAPI or React Native's TurboModules. Unit tests and the selftest pass on the developer machine; the C interface and the sample have run on QEMU (the selftest case 「原生模块」 (Native modules), QEMU ✓ (2026-11-27 night chain r86)). Sealing executable memory went on with that case on QEMU (arm64): kario-jsrt does not run the app when it cannot seal, so the case would fail; that the sealed calls return `EPERM` is checked only by the unit tests on the developer machine (x86_64), and is **not verified** on arm64 (the case tries none of those calls and would pass with no seal at all). The C++ and Rust wrappers, native stacks and thinning by architecture are tested on the developer machine only; **not run** on a real phone ([29](29-app-development.md) §5.3).

```ts
import { blur } from "native:imgproc";              // lib/<arch>/imgproc.so in the package
blur(pixels, 320, 240, 4);                           // synchronous: changes the bytes of pixels in place
const out = await blurAsync(pixels, 320, 240, 4);    // KARIO_ASYNC: on a worker thread, a new ArrayBuffer
const mod = await import("native:imgproc").catch(() => undefined);   // falls back to TypeScript when it cannot load
```

```cpp
#include "kario_native.hpp"                          // C++17, header only
static double add(kario::call &c) { return c.arg<double>(0) + c.arg<double>(1); }   // a wrong argument throws, JS gets an Error
KARIO_NATIVE_CPP_MODULE([](kario::module &m) { m.function("add", add); })
```

```rust
// the crate sdk/rust/kario-native; the module's Cargo.toml says crate-type = ["cdylib"]
fn add(c: &mut kario_native::Call) -> Result<f64, kario_native::Error> { Ok(c.arg::<f64>(0)? + c.arg::<f64>(1)?) }
kario_native::module!(|m: &mut kario_native::Module| m.function("add", add));
```

| Aspect | Rule |
|------|------|
| Manifest and package | The manifest says `"native": ["imgproc"]`; the library is `lib/<arch>/<name>.so` in the package, the architecture `arm64` (phones; the store takes no package without it) or `x86_64` (the developer machine), mode 0644 (a library, not a program); `lib/` holds nothing else, and no ELF file sits anywhere else in the package. The installer, the store's review and `kario build` apply the same `jsrt.Check`: a 64-bit little-endian shared library of the right machine, exporting `kario_native_abi` and `kario_native_init`, built for the interface's version, without an executable stack; the installer wants its own architecture, the store `arm64`. A package may carry several architectures (`kario package` puts in every one that is built by default, `-arch arm64,x86_64` names them, each required): the store sends each device its own only (`GET /v1/packages/…?arch=arm64`, the catalogue's `thinned` giving that one's size and digest), and the device checks it against the developer's signature as it is, letting only another architecture's `lib/<arch>/` be missing; any other file missing or changed is still refused |
| Loading | `kario-jsrt` loads from the app's own directory only: a valid name, declared in the manifest, a path that resolves inside the package (no symbolic links), an ELF of this machine, the interface's major version and a minor one no newer than the runtime's; otherwise the import fails with the reason (such as `native:imgproc: lib/x86_64/imgproc.so is a library for arm64, not x86_64`). A static import that fails keeps the app from starting; to fall back, catch the error of `import()`. kario-jsrt loads all declared modules before the app's code runs, in the manifest's order (`init` runs then), and one that does not load throws its sentence at `import`; then executable memory is sealed (What it may not do). The developer writes the module's types in a `.d.ts` (`declare module "native:imgproc"`) |
| C interface | `sdk/c/include/kario_native.h` (in the image, `phone-capi`'s `-dev` package): the library exports its entry point with `KARIO_NATIVE_MODULE(init)`, and `init` registers the names with `export_fn`, `export_number`, `export_string`; functions take their arguments and set their results through a table of functions (`kario_api`), link nothing of the runtime and never touch a JavaScript object, so the same `.so` loads in kario-jsrt and in Node, and a new engine version needs no rebuild. Values are numbers, booleans, strings, bytes (an `ArrayBuffer` or a typed array) and JSON; native code never calls into JavaScript |
| C++ and Rust | Both sit on the same C interface, and the module is the same kind of `.so`. C++: `sdk/c/include/kario_native.hpp` (C++17, header only; `c++ -std=c++17 -shared -fPIC -I sdk/c/include`); inside `KARIO_NATIVE_CPP_MODULE`, `m.function(name, f[, kario::async])` and `m.value` export, `f` being a function or lambda taking `kario::call&` whose return value is the result; `c.arg<T>(i)` takes an argument by type and throws `kario::error` otherwise; whatever a function throws becomes JavaScript's `Error` at the boundary (the rejection, for an asynchronous one), and `m.events()` lets its own threads `emit`. Rust: the crate `sdk/rust/kario-native` (no dependencies, with its `Cargo.lock`); the module's `Cargo.toml` says `crate-type = ["cdylib"]` and depends on it; `kario_native::module!`, `Module::function` / `function_async`, `Call::arg::<T>()`, functions returning `Result<R, Error>`, an `Err` and a panic both becoming an `Error`, `Module::emitter()` for its own threads. The `lib<name>.so` built goes in as `native/<arch>/<name>.so`. Neither has been cross-compiled for phones yet |
| Memory | The strings, bytes and JSON the accessors give belong to the runtime and are valid until the function returns: do not `free` or keep them; what `ret_string`, `ret_json`, `fail` and `emit` take is copied; `ret_bytes(len)` gives zeroed memory that becomes the result's `ArrayBuffer` once the function returns. A synchronous function's bytes are the JavaScript memory itself (it may change them in place), an asynchronous one's a copy |
| Threads | The engine has one thread. A plain function runs on it synchronously, and meanwhile the app answers neither keys nor the system (after 5 s in the foreground the system offers to close it): keep it short; a `KARIO_ASYNC` function runs on one of the runtime's worker threads (at most 4 per app, more calls wait), and JavaScript gets a Promise settled on the engine's thread; a module may start threads of its own (counted in the app's 128 processes and threads), which hand events to JavaScript only through `emit(event, json)` (each module's own `on(event, handler)`, at most 1024 queued). The table's other functions are for inside a call, on the thread it runs on |
| What it may not do | Native code runs in the app's process under the same sandbox (uid, namespaces, seccomp, Landlock, the per-app firewall), with no right of its own: system capabilities are still asked for only through JavaScript's `kario.*` and the broker. Once the modules are loaded the system seals executable memory: `mmap` and `mprotect` with `PROT_EXEC`, `dlopen` and `exec` all return `EPERM`, so no code from outside the package can be loaded or generated (downloaded libraries, files of the data directory, a JIT), and no other program started; a module whose `init` leaves executable memory that could still change (writable and executable, shared, anonymous) keeps the app from starting. Name lookups get only what libc has built in (files and DNS). The guidelines also require (the review checks; the system cannot stop it all): no touching the runtime's descriptors (the protocol on fd 3, the workers' eventfd) or memory, no changing signal handlers, no child processes, no `exit`. A crash ends the process, recorded as any app's: the log and the crash record (`backtrace`) have the module, the function, the signal and each frame (`kario-jsrt: #0 native:imgproc +0x1139 build-id …`), which go to the developer with the record |
| Developer machine | `kario build` compiles no C: developers build with their own tools (`cc -shared -fPIC -I sdk/c/include`; for phones `aarch64-linux-gnu-gcc` or the SDK Yocto exports) into the project's `native/<arch>/<name>.so` (`-native DIR` names another place); `kario build` copies them into `lib/<arch>/` and notes a missing `arm64`, `kario package` refuses one. `kario run` (Node) and `kario test` load the same `.so` through `kario-native.node` (`sdk/ts/node/native.c`, Node-API, compiled by `kario` with this machine's C compiler), and VS Code's debugger still stops in the TypeScript; `kario run -engine jsrt` runs on kario-jsrt, with gdb attached for the C code. Keep the unstripped libraries (`-g`, linked with a build-id, most toolchains' default): `kario symbolize -so native/ crash.json` turns the frames of a crash record (or a log, or the store's list of crashes) into functions and `file:line`, finding each library by its build-id, with no external tool. Under Node executable memory is not sealed and a crash has no stack |
| Review | Every version of an app with `native` goes to the human review, as a native app ([33](33-app-guidelines.md) §2.2); the store's Details page and the install dialog say the app brings native code; an update that brings new native modules is not installed in the background but asks the user |

Sample: `examples/imgproc` (a box blur in C and the same in TypeScript, 4 `kario test` cases, installed from the store in the selftest, which compares the two).

### 9.4 The network (`fetch`, `WebSocket`)

A TypeScript app reaches the network itself with the `kario` module's `fetch` and `WebSocket` (`import { fetch, WebSocket } from "kario"`, which KarioUI exports too), with `Blob`, `File`, `FormData`, `Headers`, `Request` and `Response` (the table further on), subsets of the web's interfaces. On the device `kario-jsrt` goes through libcurl (`jsrt/src/net.c`, `ws.c`: each request and each connection on a worker thread of its own, waking the event loop through an eventfd when there is news); under Node on the developer machine Node's own `fetch` and sockets do (`sdk/ts/node/net.mjs`), with the same rules, limits and error texts, which `jsrt`'s `TestFetch` and `TestNodeFetch`, `TestNet` and `TestNodeNet` check with the same cases. The request leaves the app's own process: the app's uid, network namespace, per-app firewall rules and traffic accounting, as a Go app's own connections, not relayed by the Shell. A plain request has run on QEMU with the selftest case "the tutorial's sample"; bodies streamed both ways, cancelling, cookies and `WebSocket` are tested on the developer machine (unit tests ✓, kario-jsrt both on this machine's libcurl 7.61 and on a libcurl 8.19.0 built as the image's is: oe-core wrynose's recipe, without WebSocket, HTTP/2 or the public suffix list); on QEMU the selftest 「TypeScript 应用自己的网络在真的沙箱里」 (A TypeScript app's own networking in the real sandbox) ✓ (2026-11-27 night chain r86: a streamed response read, cancelling, cookies, a `WebSocket` echo), a streamed upload body **not run on QEMU yet**; all **not on a real phone**.

| Aspect | Rule |
|------|------|
| Permission | The manifest needs `net` (granted at install; the user can turn it off in Settings › App permissions › Network); without it every `fetch` is refused (`fetch: the app's manifest does not ask for the "net" permission`), and `new WebSocket` throws the same words; with the network turned off nothing gets out |
| URL | `https://` only; `http://` only to the device's own loopback (`localhost`, `127.x`, `[::1]`), for development; no user name or password, no spaces or control characters, at most 8 KB |
| Certificates | The system's CAs (the image's `ca-certificates`); checking cannot be turned off |
| Methods | `GET` (the default), `HEAD`, `POST`, `PUT`, `PATCH`, `DELETE`, `OPTIONS`; `GET` and `HEAD` take no body |
| Headers | An object of strings, `Headers` or `[name, value]` pairs; at most 64, names that are tokens, values without line breaks; not `Host`, `Content-Length`, `Transfer-Encoding`, `Connection` and the others the network sets |
| Body | A string goes as UTF-8, `text/plain;charset=UTF-8` unless `Content-Type` says otherwise; an `ArrayBuffer` or typed array as it is; a `Blob` as it is, with its `type` unless `Content-Type` says otherwise; a `FormData` as `multipart/form-data` (its `Content-Type` with the boundary); at most 4 MB. A `ReadableStream` of `Uint8Array`s (with `duplex: "half"`, as the web's fetch wants) goes chunked as the network takes it, of any length: the runtime reads it ahead of the network only while less than 256 KB of it waits (so it holds that much and the chunk that went over it), so a stream that never ends, sent to a server that does not read, is read only as far as the network takes it; a response's `body` may go on as another request's. A chunk that is not bytes (`fetch: the body's stream gave a chunk that is not bytes …`), a stream that fails (`fetch: the body's stream failed: …`, its error the `cause`), a locked stream, no `duplex` and `GET` or `HEAD` reject; the stream is cancelled (with the reason) when the request fails or is aborted, or when its answer is done before all of it went. A `Request` may also be given whole: `fetch(request, options)`, the options over its own |
| Redirects | `GET`, `HEAD` and `POST` follow at most 5, only to `https://`; `POST` becomes `GET` without a body on 301, 302 and 303 (as browsers do); the other methods get the 3xx itself, and so does a request whose body is a stream (it goes once) |
| What comes back | A `Response` (the table below): `ok`, `status`, `url`, `redirected`, `headers`, `body`, `text()`, `json()`, `arrayBuffer()`, `bytes()`, `blob()`, settled as soon as the response's headers are in; `headers` is a read-only `Headers` with lower-case names, a header sent twice its values joined with ", ", and each header still a property by its lower-case name too (`res.headers["content-type"]`; a header named like one of `Headers`' methods only through `get()`; `__proto__` and `constructor` are headers like any other). A response whose headers hold a NUL fails the fetch (`fetch: Nul byte in header`, on both engines), as does one with another control character, a name that is not a token, a line without a colon or a folded line (in words that differ between the engines); still different: kario-jsrt takes up to 64 KB of response headers and Node 16 KB (Node's own limit), kario-jsrt takes a response with bare LF line ends and Node refuses it, and bytes outside ASCII in a header read as UTF-8 on kario-jsrt and as Latin-1 under Node ([17](17-app-sandbox.md) §9.4); `statusText` is "", `type` is `basic`, and it is not cloned. The body one way or the other: whole (`text()`, `json()`, `arrayBuffer()`, at most 8 MB, as often as asked), or as a stream (`res.body` is a `ReadableStream`: `res.body.getReader().read()`, `for await (const chunk of res.body)`, chunks of at most 64 KB, any length in all); once one is chosen the other rejects. The runtime reads at most 256 KB ahead of the app and stops taking from the network while the app is slower (TCP back-pressure), so a download of any length holds that much memory; `body.cancel()` stops the transfer. A response nobody holds any more stops its transfer when it is collected |
| Time, concurrency | `timeout` (ms, 1 to 120000, 30000 by default) runs until the response's headers are in, and with the body read whole until it has all come (both from when the request went; with a body sent from a stream, from its last bytes sent, so a stream that goes quiet that long fails: `fetch: no data from the body's stream for the timeout`); for a body read as a stream it turns into a limit on silence: while the app waits for the next chunk, that long without a byte fails it (`fetch: no data for the timeout while the body was read`). At most 8 at a time, each until read, cancelled, failed or collected |
| Cancelling | `signal` (an `AbortController`'s, `AbortSignal.timeout(ms)`, or several joined by `AbortSignal.any([...])`): at any point, while sending or reading the body too; the transfer stops at once wherever it is (looking up the name, connecting, waiting for the server, moving data: each request's worker drives its transfer on a libcurl multi handle of its own, woken through an eventfd), and the request's connection and its place among the 8 go with it (they used to stay until libcurl's next progress callback, up to a second on libcurl 8.19, where the case of 8 requests aborted while connecting and a 9th fails on the old code); a body sent from a stream is cancelled with the reason; `fetch` and the body's reads reject with `signal.reason`: by default an `Error` named `AbortError` (`This operation was aborted`), a `TimeoutError` for `timeout`, or the reason the app gave |
| Cookies | None sent or kept by default: `credentials` defaults to `same-origin` (the browser's default), and an app is no web origin, so it is as `omit`, as in Node's `fetch`. `credentials: "include"` uses the app's own cookie jar, with libcurl's rules (RFC 6265; Node's jar, `net.mjs`, keeps those of the image's libcurl 8.19): `Domain` (without it the cookie is the host's alone; one naming another domain, or a single label, is refused), `Path` (by default the request's directory; the longer path is sent first), `Secure` (kept and sent only over `https://` and, with the image's libcurl and under Node, to the loopback, `localhost`, `127.0.0.1`, `[::1]`, as browsers treat it), `Expires` and `Max-Age` (`Max-Age=0` removes the cookie), the `__Secure-` and `__Host-` prefixes (an older libcurl, such as a developer machine's 7.61, keeps neither these nor the loopback rule); a cookie from an origin that is not secure does not overlay a `Secure` one. Matching cookies go out and `Set-Cookie` is kept at every hop of a redirect too. `SameSite` does not apply (an app has no sites: every request is its own), nor does `HttpOnly` (no page scripts). The image's libcurl has no public suffix list (`--without-libpsl`), so a `Domain` naming a public suffix with a dot (`co.uk`) is taken, only ever into this app's own jar. The jar is in the data directory (`kario-cookies.txt`, libcurl's Netscape format, its path out of JavaScript's sight), so no other app sees it ([17](17-app-sandbox.md)); cookies with an expiry outlive the process, session cookies live as long as it does. A WebSocket's handshake carries none. There is no call that empties the jar, and Settings has no per-app data clear to empty it with (only the factory reset); uninstalling the app deletes it with the data directory, and a server removes a cookie with an expired `Set-Cookie` |
| Failures | A request against the rules, no connection, a timeout, a bad certificate, too much data: all reject with a `TypeError` whose message starts with `fetch: `; a 404 and the like is an ordinary response (`ok` is false); cancelling as above |
| Tests | `kario test` does not reach the network: `launch({ fetch: (req) => ({ status, headers, body }) })` gives the answers, the `body` may also be an async iterator of chunks (to test reading as a stream), and an answer's `Set-Cookie` goes into the jar; `app.fetches` holds what the app sent (a `FormData` body as the multipart bytes that went, a body from a stream as all its bytes); without it `fetch` fails. A WebSocket connects to the test's own server (the `WebSocket` table below) |

`WebSocket` is the browser's interface, with one argument more:

| Aspect | Rule |
|------|------|
| Interface | `new WebSocket(url, protocols?, { headers?, signal?, keepalive? })`; `readyState`, `protocol`, `bufferedAmount`, `send()`, `close(code?, reason?)`, `onopen` / `onmessage` / `onerror` / `onclose` and `addEventListener`; messages are strings or `ArrayBuffer`s (`binaryType` is `arraybuffer` only: what comes is no `Blob`, and `send` takes none). The third argument, which browsers lack: headers for the handshake (fetch's rules, no `Sec-WebSocket-*`; protocols go in the second argument), cancelling and keeping it alive (below) |
| Permission, URL | As fetch: `net` needed; `wss://` only, `ws://` only to the device's own loopback; no fragment (`#`); the system's CAs. A wrong URL, protocol (a token, no repeats, at most 16) or header throws from the constructor (`SyntaxError`, `TypeError`); failing to connect is an asynchronous `error` and `close` |
| How it connects | kario-jsrt: libcurl only connects (`CONNECT_ONLY`, fetch's TLS and CAs, speaking HTTP/1.1 only), and the runtime does the handshake and the framing itself (`jsrt/src/wsframe.c`), so it does not depend on libcurl's WebSocket, which the image's lacks (oe-core's curl 8.19.0 recipe leaves its `websockets` PACKAGECONFIG off: `--disable-websockets`); under Node through `node:tls` with the same framing. No cookies; the server's pings are answered with pongs |
| Limits | At most 4 at a time; a message received (its fragments together) at most 4 MB, a frame header that says more failing the connection (1009) before anything is allocated; a message sent at most 4 MB, at most 16 MB waiting to be sent (`bufferedAmount`), `send` throwing a `RangeError` beyond; at most 8 MB received and not yet handed to the app, past which the socket is not read (TCP back-pressure), so a server flooding a busy app cannot fill its memory; the handshake 30 seconds, its answer's headers at most 64 KB; the closing handshake 5 seconds |
| A server that breaks the rules | A masked frame, reserved bits, an unknown opcode, a fragmented control frame or one over 125 bytes, text that is not UTF-8, an invalid close code: first `error` (its `message` says which), then `close` (1002, 1007 or 1009, `wasClean` false), the runtime sending the server the same close code; a wrong handshake (no 101, a wrong `Sec-WebSocket-Accept`, a protocol or an extension not offered): `error`, then `close` 1006 |
| Closing, cancelling | `close(code, reason)`: `code` 1000 or 3000 to 4999, `reason` at most 123 bytes; when the server closes first the runtime answers with its code, and the `close` event carries the code and reason with `wasClean` true; a broken connection, or a server that does not answer the close within 5 seconds, is 1006. A `signal` drops the connection at once, without the closing handshake (`close` 1006, reason `aborted`), while libcurl is still connecting too: its sockets are shut under it (while the name is looked up and there is none yet, at libcurl's next progress callback); an abort while connecting used to wait for the connect to end, up to its 15 seconds (the case fails on the old code). An open WebSocket is held by the runtime (as by a browser), and collected once closed and no longer held by the app |
| Keeping it alive | `keepalive: every_s` (whole seconds, 60–3600; the manifest needs `keepalive` too; without it, or out of range, the constructor throws a `TypeError`): the app's one connection that the system watches while it is frozen ([21](21-push.md) §8.3). The runtime calls `net.keepalive` (§4.7, one at a time) with the URL's host and port, the system dials as the app's uid, keeps a copy and hands the socket to the runtime, which speaks TLS and WebSocket on it; a message that comes while the app is frozen has the system thaw it and reaches `message` whole; heartbeats wait for the `keepalive` event's `beat` (§5). A second one replaces the first (close code 1001, reason `replaced`); when it ends the runtime tells the system `close: true`. Under `kario test` it connects to the test's own server as other WebSockets do. One set of tests on both engines (`jsrt`'s `TestKeepaliveWebSocket`, `TestNodeKeepaliveWebSocket`); the sample is `examples/keepalive-ts` |
| Tests | Under `kario test`, `wss://` and `ws://` to anywhere end at the test's own server (`sdk/ts/node/wstest.mjs`, a pair of sockets in memory, to which the runtime speaks the same handshake and framing as to a real server); the network is not reached: `launch({ websocket: (req) => ({ protocol }) })` decides the handshake (`req` has `url`, `protocols`, `headers`; answering `{ status: 403 }` refuses it, the app getting `error`, then `close` 1006; without it every handshake is accepted without a protocol), and `await app.websocket()` is the server's side of the next connection the app opened: `messages`, `await next()` (the next message), `send(text or bytes)`, `ping()`, `close(code, reason)` (the app answers with its close, `wasClean` true), `drop()` (the connection breaks, 1006), `sendRaw(bytes)` (to test a server that breaks the rules), `await closed` (the code and reason it ended with); `app.websockets` are all of them. `cmd/kario`'s `TestKarioTestNetwork` runs it with a real project: the handshake's URL, protocols and headers, text and binary both ways, a ping, the app closing and the server closing, a refused handshake, a dropped connection (such a connection used to end with 1006 at once; the case fails on the old code) |

The frames servers send are fuzzed by `tools/cfuzz`'s `FuzzWebSocketFrames` ([17](17-app-sandbox.md) §9). Sample: the tutorial's notes (`examples/karioui-notes`, [34](34-app-tutorial.md) §7.1) POSTs its push token to its own server; the selftest case "the tutorial's sample" sends it to a test server on the device's loopback and checks that the server got it. The selftest case 「TypeScript 应用自己的网络在真的沙箱里」 (QEMU only: it needs the real sandbox) has `examples/netcheck`, installed from the development store, read a response as a stream from the same test server (`shell/fetch_headless.go`), abort a request the server holds (the server sees the connection go), send and receive cookies only with `include`, the one with an expiry kept across processes and the session one not, and do a WebSocket echo; all pass on arm64 with kario-jsrt and the image's libcurl (2026-11-26). `Blob`, `File`, `FormData`, `Headers`, `Request`, `Response` (`import { Blob, FormData, Request, Response } from "kario"`, which KarioUI exports too) are subsets of the web's interfaces, the same JavaScript on both engines (`sdk/ts/node/web.js`), and so is the global `ReadableStream` on kario-jsrt (under Node, Node's own, which the classes there use too): kario-jsrt compiles it the first time an app uses one of them or `fetch` (36 KB, about 3.5 ms to compile on the developer machine), so an app that does not pays nothing at start; until then the module exports stand-ins, whose `new`, `instanceof`, subclassing and statics go to the real ones, which then take their place (an import is a live binding), and the global `ReadableStream` is an accessor that does the same. Tested on the developer machine on both engines (`jsrt`'s `TestFetchWeb` and `TestNodeFetchWeb`: each class without the network, stand-ins taken before the first use, a `FormData` read by Go's multipart parser, a `Blob` with its type, a `Request` and options over it, the `Response` fetch gives with the old property style still working; `TestNet` and `TestNodeNet`: `ReadableStream` against Node's, giving the same answers), **not run on QEMU yet**, **not on a real phone**.

## 10. Testing

The Shell has a built-in headless script runner, and the same script runs in a terminal, on the pixel renderer (`--gui`) and in the device boot selftest:

```bash
make build
build/usr/bin/phone-shell --script my-app.script        # your test cases
build/usr/bin/phone-shell --selftest                    # the system's built-in test cases
build/usr/bin/phone-shell --selftest --only '视频' --junit report.xml   # only run cases whose names match ('视频' = video), write a JUnit report
build/usr/bin/phone-shell --selftest --keep-going      # go on after a failed case (the phone starts over); every failure listed at the end
```

Common commands:
- Keys and input: `key <key> [count]` (including `call` for the call key and `end` for the end key), `type <text>`;
- Waiting: `wait <text> [ms]`, `wait-re <regex> [ms]` (for text that keeps changing, such as the playback position; both also accept a toast shown since the last input and already gone), `gone <text>`, `at <screen ID>`;
- Screenshots: `snap <name>`;
- System state: `appstate <app> frozen|running|stopped`, `audio <category>`, `frames <frame count>`;
- Simulating external events: `push <app> <title> | <body> | <data>` (playing the role of your server), `tel ring <number>` (simulated incoming call), `timeshift <seconds>`.

The complete list is at the top of `shell/headless.go`.

## 11. Compatibility test suite (for device vendors)

```bash
make cts     # = phone-shell --cts build/cts-report.json
```

On a developer machine of 16 processors or more `make cts` adds `--parallel`: the script's parts run at once, each with a signed report of its own (`build/cts-report-<part>.json`), which `phone-cts-verify --root-beside` checks together, as for QEMU's boot selftest ([40](40-testing.md) §2); what goes to a certifier is the one report of a run of the whole script (`make cts CTS_PARTS=0`).

- **What runs**: the whole selftest, plus the compatibility test cases. The compatibility test app `com.phone.ctsprobe` (`cts/probe`) is only installed in this mode, and it checks that:
  - capabilities whose permission is not declared are always denied;
  - the interval of background jobs cannot be less than 15 minutes, and jobs can be registered and cancelled;
  - an app with the phone permission can answer and control calls itself;
  - every item of the sandbox self-check passes (the same `sandbox.SelfChecks` as in the Settings app);
  - when the memory limit is exceeded, only the app itself is ended, and the reason is shown;
  - when the app is stuck, the system shows 「没有响应」 (Not responding), and the user can wait for it to recover or close it;
  - after a crash, the system keeps a record that can be viewed in Settings;
  - the app in front can hint the screen's refresh rate (`display.hint` answers the panel's rate now), a hint of two kinds at once is refused; of 16 hints sent at once (without waiting for the answers) no more are granted than a burst plus what the limit refills while they are answered (§4.12): a slow device refills one in the time it answers one, and does not fail for granting them all;
  - without the corresponding permissions, the app cannot install packages, grant itself permissions, change system settings, see other apps' photos in the gallery, answer NFC readers (`nfc`), see and change the card pack (`nfc.state` / `nfc.set` need `system`), read an NFC card or send it commands (`nfc.read` / `nfc.transceive` need `nfc_reader`), or see and switch airplane mode, mobile data and the personal hotspot, send files over Bluetooth, or see, start, stop or undo a move from an old phone (`radio.state` / `radio.set` / `hotspot.state` / `hotspot.set` / `bt.send` / `switch.*` need `system`), or see, import, connect, disconnect or delete a VPN, change its always-on and per-app choices or make its key pair (`vpn.*` need `system`), or schedule, list or cancel scheduled notifications (`notify.*` need `notifications`); `locale.get`, `holidays.get` and `time.offsets`, which need no permission, answer, and an unknown time zone is refused;
  - the app cannot impersonate system UI (a title containing the word for System in any UI language gets the app name prefixed);
  - capability versions (§2.3): `media.list@2` pages what `media.list` gives at once, `media.list@1` is `media.list`, and a version the system lacks (`media.list@99`) is refused as an unknown capability.
- **Provisioning**: before the compatibility test suite starts, it simulates the factory line provisioning a certificate onto the device: a CA representing the certifier (`phone-provision`) issues the device certificate, which is installed into the key service (`csr` / `install_cert`), so the report chains to the certifier's root rather than to the development root the device generated itself.
- **Report**: JSON, containing the device information, the result of each test case, the number of calls, successes and failures for each capability, the capabilities that were never called, and in `skipped` those not called because the cases calling them were skipped (each with that case and why: a phone without a location receiver the script can move, say; they do not fail the report, as the skipped cases do not); `sandbox` says which layers of the sandbox and the app lifecycle the device's kernel lacks: the kernel version, `missing` (protections not in force) and `fallback` (done another way, nothing lost), each with why ([24](24-sku-framework.md) §7.5), and `foreign` when the kernel the run had is not one the device's system ships (a test in a chroot on another system: what is missing is that system's). A device short of protections can still PASS, and the certifier decides; `phone-cts-verify` lists what is missing item by item.
- **Pass criteria**: all test cases pass, and every capability in §4 has been called at least once, each version of a capability counting as one (`media.list` and `media.list@2`, §2.3). If a capability or version is added without a test case for it, the compatibility test suite does not pass.
- **The report is signed**: the report's `attestation` field is a device attestation by the device key service over the report digest (the SHA-256 of the JSON with the signature removed), with a certificate chain leading to the root certificate. If the vendor changes any item in the report, the signature check fails. The certifier checks it like this:

  ```bash
  phone-cts-verify --root root.pub cts-report.json   # signature, certificate chain and results must all pass
  ```

  Before `make cts` starts, it simulates provisioning with a temporary CA (previous item), and `phone-shell --cts` saves that CA's root separately as `<report>.root`, for demonstration only; the device boot selftest does no provisioning, and its root is the one the device generated itself on first boot. In mass production the CA is in the certifier's hands (HSM), and the certifier checks with the root it holds itself, trusting nothing that comes with the report.
- **Certification is done once per model**: the vendor runs the compatibility test suite on a sample unit of the model, enters the company name, unified social credit code and model on the certifier's portal, and submits the signed report. The certifier's backend immediately checks that the signature chains to its root, the result is PASS and the device is not unlocked; after staff approve it, the model is added to the public list of certified models (this service is not open source).
- **Each device only needs provisioning**: in mass production, individual units no longer run the whole compatibility test suite. They run the vendor's own factory test at a factory station and, after passing it, go online to obtain a device certificate. The station reads the device's certificate signing request (the key service's `csr`), has the device produce a device attestation over a random nonce used only for this request (app name `system.provision`, proving that the device holds this key and is not unlocked), and passes it to the certifier's provisioning service; the service checks the station's token and quota and that the model is certified, issues the certificate with the CA, and the station installs it back onto the device (`install_cert`). The CA's private key exists only at the certifier, and stations cannot get it; every issuance is recorded. The open-source side is `ReadCSR`, `AttestFor`, `VerifyPossession`, `(*CA).Certify` and `InstallCerts` in the `keystore` package (`phone-provision` is the local version for when the CA is at hand, used for testing); `keystore.CA`'s Ed25519 key may be one in an HSM (any `crypto.Signer` holding an Ed25519 key), while its SM2 key still has to be the private key itself (PKCS#11 has no standard SM2 mechanism). On real devices, connecting the station to the device over USB and putting the keys into the TEE have to be done together with the hardware (**not implemented**). Staff see the requests at the review desk (the system version, number of test cases, capability coverage, renderer and test device ID from the report; the original report can be downloaded) and certify or reject them with a reason, which is recorded in the audit log; vendors check progress with the request number (`GET /v1/certifications/<number>`); certified models are public (`GET /v1/certified`: vendor, credit code, model, system version, certification time). A backend started without `--cert-root` does not accept requests.
- **Reports of a run in parts**: `phone-shell --cts --parts <part,…>` runs only the cases of those parts of the script (its `#part` lines; the compatibility cases are the part `cts`), and the report carries `parts` (the parts it ran), `all_parts` (all the script's parts) and `part_result` (whether those parts' cases passed), with `result` set to `PART`: a part's report never passes on its own, and a certifier's backend or an older `phone-cts-verify` that checks `result` for PASS refuses it. The parts' reports are checked together: `phone-cts-verify --root root.pub a.json b.json …` (or `--root-beside`: each report's root in `<report>.root`, for the prototype's devices that make their own root) checks each signature on its own, then requires them to be of one version, every part in exactly one of them, every report's cases passed, and every capability called in one of them.
- The device boot selftest also runs in this mode: the script's parts run in several emulators at once ([40](40-testing.md) §1), each emulator's report retrieved over its serial port (`build/selftest/vm<n>/cts-device.json`, with the root public key beside it in `.root`), and at the end `make yocto-selftest` checks them together on the host with `--root-beside`; with one emulator (`SELFTEST_VMS=1`) it is one whole report, checked as before. For the certification plan see 59 (internal document) §2.

## 12. Packaging and release

Signed packages, the installer, delta updates and takedowns are implemented; the store backend is simulated ([07](07-ecosystem-and-store.md) §4.1: developer identity verification, manual review, delta packages, revocation lists, crash report authentication).

**Package format (`phoneapp/1`)**: a tar containing all files of the app directory, plus a `META/signature.json` that:
- lists each file's path, mode (0644 or 0755), size and SHA-256;
- includes the developer certificate: the developer's name and public key, issued by the store's root key;
- is signed as a whole by the developer key (Ed25519).

Packaging and verification both use `pkg`:

```go
dev, _ := pkg.DevDeveloper(keyDir, "我的工作室", store) // developer key + certificate issued by the store ("我的工作室" = "My Studio")
raw, _ := pkg.Build("notes/", dev)                      // notes/ contains manifest.json and the program
p, err := pkg.Open(raw, roots)                          // verification on the device before installing
```

**What the system checks at install time**:

| Check | If it fails |
|------|----------|
| The signature and certificate chain lead to a store root the device trusts; the files and the signature manifest match one to one, with nothing extra and nothing missing | Rejected |
| Only regular files; paths cannot escape the package | Rejected |
| Manifest: `id` is a reverse domain name (not starting with `system.`), `name` and `exec` are present, and `exec` is an executable file in the package root | Rejected |
| The manifest's `nfc`: cards need the `nfc` permission, valid card ids, categories and AIDs (`ui.CheckNFCCards`, which the store backend applies too) | Rejected |
| The manifest's `privacy`: valid kinds and uses; no data sent without `net`; with `net`, the data of every runtime permission listed under `collects` or `local` (`ui.CheckPrivacy`, which the store backend and `kario build` apply too; [33](33-app-guidelines.md) §3) | Rejected |
| A TypeScript app (`"runtime": "js"`): no `exec`, no executable file and no bytecode (`.jsc`) in the package, and `main` is a `.js` file in the package root; machine code only as the modules `native` declares, `lib/<arch>/<name>.so`, libraries of this device's architecture built for the interface's version (§9.3); the store's review applies the same check (`jsrt.Check`, wanting `arm64`) | Rejected |
| No `granted`, no system-only permissions (`system`, `install`), no unknown permissions | Rejected |
| The name must not be the same as that of an app in the system image | Rejected |
| Updates must be signed by the same developer key | Rejected |
| All of the above pass: the system shows a dialog listing the name, version, developer, issuing store and permissions, and says so when the app brings native modules | Not installed if the user cancels |

**After installation**:
- The code is placed in the system directory `packages/<id>`; the app itself can only read and execute it, not modify it;
- The app only runs the programs in its package and cannot borrow programs with the same name from system directories;
- The signature manifest is kept together with the code (`META/signature.json`). On the first launch after every boot, and after developer mode changes, the system re-checks it against the store roots trusted at that time: if files have been modified, unsigned files have been added, or the store is no longer trusted, the app is not allowed to start (`pkg.VerifyDir`);
- Uninstalling deletes the code and data, and clears the runtime grants and usage records, background jobs, alarms, photo grants and all keys in the key service (the app's own keys, its mini-programs' keys, the push key); the push token is invalidated. An app published later by a different developer under the same ID cannot get any of these.

Which stores the device trusts: `share/phone/trust/<store>.pub` in the image; when developer mode is turned on (「设置 › 开发者模式」 (Settings › Developer mode)), additionally `trust/` in the state directory. The prototype's selftest uses packages signed by the "development store" in the state directory (`pkg.DevStore`), which plays the role of the store backend. After developer mode is turned off, packages signed by the development store cannot be installed, and those already installed cannot start. The roots of the official stores come with the product image or are provisioned on the factory line, and developers register in the store backend ([07](07-ecosystem-and-store.md) §4.1).

Without packaging, you can also put the app directory directly into `share/phone/apps/`, which makes it equivalent to an app in the system image. Do this only on development machines.

**Symbol files**: a TypeScript app's package carries a minified `main.js`; `kario package` writes its source map into the symbol file beside the package (`app.phonesym`: a zip of `symbols.json` with the app, the version and the SHA-256 of the package and the module, `main.js.map`, the minified `main.js` itself (a stack's functions get their names in the source back through it), and optionally unstripped native modules), never into the package or onto phones. `kario publish` sends it after the package: `POST /v1/symbols/<app>/<version>`, signed with the developer's key over `phone-symbols/1|<name>|<time>|<app>|<version>|<the symbol file's SHA-256>`. The official store checks that it is that package's (the package's digest, the module's, the libraries' build-ids) and keeps it for the developer and the reviewers only; the crash reports the developer reads on the portal (or through `GET /v1/developer/crashes`) have their stacks mapped back to the TypeScript; crash records at hand are mapped with `kario symbolize -symbols app.phonesym`. The open core (the simulated store) takes no symbol files. Developer machine ✓ ([29](29-app-development.md) §5.6), **not on a real phone**.

## 13. The low-level capabilities WeChat- and Alipay-class apps need: an audit

The owner wants a nostalgic keypad or flip phone that may one day run WeChat and Alipay: as lite clients Tencent and Ant build on Kario's SDK, or through mini-programs. The table goes through the low-level capabilities such clients need: what Kario has now (code, docs), whether the two demos use it — Hongyan (`apps/chat`, WeChat-like, with `phone-chatsrv` as its simulated cloud) and Feiqian (`apps/wallet`, Alipay-like) — and what is missing. Capabilities against product features are in [12](12-super-app-capabilities.md); this is the low level only. Status as in the rest of the docs: **not implemented**, **not on a real phone**, **not verified**; "simulated" means it runs end to end but on a simulated source.

| Capability | What Kario has | Do the demos use it | What is missing |
|------------|----------------|---------------------|-----------------|
| Long-lived connections and push | One system connection (`phone-pushd` and the gateway, TLS / TLCP, end-to-end encrypted, [21](21-push.md)); a frozen app is thawed for 3 seconds (VoIP: 10) or started in the background, then handed the message; data pushes wake an app at most 20 times an hour, the rest queue until it is in front again; a VoIP push not answered by a call report within 10 seconds, 3 times in 24 hours, is demoted to a data push | Hongyan: `push.register`, message and VoIP pushes (sent by `phone-chatsrv`); Feiqian: money-received pushes | The production push service **not implemented** (a simulated gateway); an app's own connection is not kept alive while frozen (as on iOS), so messages come only through the system's push, and Tencent and Ant would have to use Kario's push gateway |
| VoIP and video calls | The system's incoming-call screen, VoIP pushes, the in-call status-bar indicator; `audio.record` and `audio.stream` (shared-memory rings, the app carries the sound itself); `media.call.*` | Hongyan: voice and video calls, incoming calls, back from minimized | The video call's picture is synthetic, with no network transport (simulated); an app gets no camera frames and cannot produce frames of its own (`media.surface.produce` is a design only); hardware codecs, echo cancellation and noise suppression are designs only. `audio.route` needs the `phone` permission, so a VoIP app cannot switch to the speaker. So a third party can make voice calls today (without system echo cancellation), not video calls |
| Voice messages | `audio.record` (microphone permission, status-bar indicator, in front or in a call only); `audio/voice`: Ogg Opus encoding and decoding (Go); playback through `audio.stream` | Hongyan: records, sends and plays them (Opus, about a fiftieth of the PCM) | TypeScript apps have no Opus encoder (it is a Go package; a native module can bring one); Hongyan's voice messages stay on the phone and are not sent to `phone-chatsrv` |
| Photo and video capture, compression | `camera.capture` (the system viewfinder, only the shot is handed over); `media.pick` with `max_side` for a JPEG copy for sending (§13.2); video plays as WebM only | Hongyan: photos through the picker, sending the smaller copy; neither demo uses `camera.capture` | Recording video needs a hardware encoder, **not implemented**; there is no video compression, so no short videos |
| File transfer and share | `file.pick` / `file.save` / `file.open` (only the file the user picks), `share.open`, `media.save`, `intent.invoke` (§4.9, §4.10, §7) | Hongyan: opens received files, saves pictures, receives photos other apps share; asks Feiqian to pay a transfer (`intent.invoke`) | Background upload and download: an app is frozen 10 seconds after leaving the front and has only `job.schedule` (every 15 minutes at most); there is no "finish this transfer in the background", **not implemented** |
| Contacts access | `contacts.list` (runtime permission), `contacts.pick` (the system picker, no permission), `contacts.save` and the rest (confirmed by the system each time) | Neither demo (Hongyan's friends come from `phone-chatsrv`) | The platform has enough; the demos do not show "add friends from the phone's contacts" |
| Notifications | `notify`: banners, the notification centre, opening back into the conversation, quick replies (`input`), call notifications; while locked only the app's name and count show | Hongyan: message notifications with quick reply; Feiqian: money received (the system shows the push's notification part) | Mostly enough; no notification channels, do-not-disturb rules, pictures in notifications or app badge interface |
| Deep links | The `open` event with an argument (at start, from a notification or a push); `intent.invoke` starts another app and gets a result back, the system vouching for the caller | Feiqian: `intent.invoke`'s `pay`, which Hongyan calls | Links in web pages or messages opening an app (URL schemes, App Links) **not implemented**: an H5 checkout cannot bring up the wallet |
| QR scanning from the camera | `scan.qr`: phone-mediad decodes camera frames (gozxing), 4 frames a second at 640×480 grey, until the first code; 2.4 ms a frame with a code on the developer machine, 12–15 ms estimated on a Cortex-A53 (**estimate**); only the result is handed over ([13](13-prototype.md), "QR recognition") | Feiqian: scanning a merchant's code to pay; the mini-program host scanning a table's code | No autofocus, torch or low-light handling: V4L2 only takes frames and controls neither focus, exposure nor light; white-on-black codes and steep version-1 codes are not read; QR only, no barcodes; no reading of pictures in the album; real cameras **not on a real phone** |
| Payment code (dynamic code, brightness, screenshot protection) | `keystore.sign` signs the dynamic code; `image` with `qr:`, `bar:` (Code 128, new), `secure` (masked in screenshots), `bright` (new: full brightness, no dimming while the code is in front) | Feiqian: a signed code every 30 seconds, barcode and QR, on a secure surface, at full brightness | Codes are drawn at a whole number of screen pixels a module (2026-11-26): they used to be scaled to the screen's width by nearest neighbour, ZXing does not read them below about 1.5 pixels a module, and the 18-digit payment barcode came out at 1.48 pixels a module on a 240x320 screen and did not read; now it is 1 pixel a module, 154 pixels wide, and reads (unit tests decode the codes phone-paint draws on four screens); where a code does not fit the screen says so and gives the number; **not verified** with a real till scanner on a real screen; the offline code's seed and algorithm must match the payment company's server, which is theirs |
| System secure confirmation and payment PIN | `auth.confirm`: a dialog the system draws, the PIN going only to the key service, "what you see is what you sign", checked step by step by `keystore.VerifyConfirm` (§4.1) | Feiqian: paying a scanned code, transfers, paying for Hongyan | The payment PIN cannot be changed: there is only the factory default and no way to change it, **not implemented**; it is stored as one salted SHA-256 (the lock PIN uses PBKDF2); a trusted input path (the PIN from the keys straight into a TEE) needs a TEE, **not implemented** |
| Biometrics bound to a hardware key (the SOTER / IFAA model) | `auth.confirm`'s `bio_key`: a match gives a token for one signature with that key only, and the key is voided when the fingerprints change ([31](31-lock-and-biometrics.md) §5); an area sensor on the OK key (under the cap, reading a resting finger with no press) is powered only in the system's fingerprint prompt (new, [31](31-lock-and-biometrics.md) §4.5); the `security` field says `software`, truthfully | Feiqian: fingerprint payments, the payment PIN as the fallback | **The key service is software**: phone-keystored is a system process standing in for a TEE, with no hardware isolation; SOTER and IFAA need a trusted application in a TEE, an attestation key provisioned on the line and the alliances' certification, **not implemented** (why TrustZone alone is not enough: [31](31-lock-and-biometrics.md) §12); real fingerprint sensors **not implemented** |
| Device attestation | `attest.get`: manufacturer root → device certificate → app key certificate, boot state `verified-boot:simulated` / `unlocked`; the trust service checks the model and the provisioning (§4.1, §11) | Feiqian: attests at login, does not pay on an unlocked device | The device key is in a file on the data partition, not in hardware; the boot state is simulated (a real verified boot needs the board's boot chain); whether Chinese payment companies accept Kario's root depends on agreements |
| Secure keyboard for passwords | `input` with `secret: true`: drawn by the system as dots, the input method learns nothing and offers no candidates, no copying, the screen reader does not read it (§3) | Neither demo (no sign-in page; the payment PIN is in the system's confirmation) | The keys skip the input method but pass through the Shell (not trusted input in a TEE); apps cannot bring up the system's PIN pad (only the one in `auth.confirm`) |
| Screen capture blocking | Per node `secure` (images, media streams): masked in screenshots over USB (the only screenshots Kario has now; the panel's renderer never hands out the picture; screen recording and casting are **not implemented** and must mask the same way); `secret` inputs show dots | Feiqian: the payment code | No whole-screen "no screenshots" (Android's FLAG_SECURE): text pages such as bills and chat history can be captured |
| Root and tamper signals | Attestation's `boot` (`unlocked` once unlocked); the app sandbox (own uid, Landlock, seccomp, [17](17-app-sandbox.md)); dm-verity on the system partitions | Feiqian: refuses `unlocked` | Developer mode and USB debugging are not in the attestation; no runtime integrity signal (like Play Integrity's) |
| SMS verification codes | `sms.otp`: waits for the next message with a code, the system says who asks and shows the message, the code goes over only if the user agrees ([32](32-messaging.md) §6.1) | Feiqian: adding a bank card (new) | Carrier one-tap sign-in (number verification) is a design only. Fixed now: the system dialog handing over the code used to take keys injected from a computer; like the permission dialogs, it now takes only the phone's own keys |
| Mini-program runtime | `apps/miniapp`: kario-jsrt (QuickJS) logic and `phone.Ui` views, `Page` / `setData`, `phone.*`, origin labels, the mini-program's own keys and identity (§4.1, [11](11-platform-architecture.md) §10) | The mini-program host (order by scanning and pay); Hongyan and Feiqian carry no mini-programs | WeChat's and Alipay's mini-programs use their own base libraries and `wx.*` / `my.*` interfaces, with back ends (sign-in, payments) at Tencent and Ant; Kario's host cannot run existing mini-program packages |
| Web content (H5) | The `web` node: a web view in its own process, the arrow keys moving between links, the system input method; `phone.call` in the page opens only `share.open`, `clipboard.set`, `location.get` and `auth.confirm` (§3) | Neither demo | No full web interface like a JSSDK (no scanning, paying or picking photos); pages bringing up apps: see deep links |
| Location | `location.get` / `location.watch`, coarse location, background location granted separately, network location (§4.7) | Neither demo | Real GNSS **not on a real phone**; GCJ-02 is the app's to convert |
| NFC (HCE for transit cards) | The manifest's `nfc` AID groups, the `nfc.apdu` event, express transit cards, the default payment app, reading cards ([30](30-nfc.md)) | Feiqian: a transit card (simulated), contactless payment, reading a physical card's balance | The real NCI back end **not implemented**. Chinese transit cards (China T-Union, city cards) are mostly issued into a secure element (eSE, SIM) under TSM agreements between the wallet maker and the issuer, and HCE issuing is rare (**not verified**); for such phones the realistic way is the QR ride code, which needs only what the payment code needs |
| Background job limits | Frozen 10 seconds after leaving the front; exceptions: playing music, in a call; `job.schedule` every 15 minutes at most, wake-ups merged; pushes wake within a budget ([17](17-app-sandbox.md) §5) | Hongyan does not stay resident and lives on pushes; a money-received push wakes a frozen Feiqian | No long task like a foreground service (navigation, big transfers), see above |
| Storage encryption | App data separated by uid (the sandbox); the system partitions have dm-verity only (tamper-evident, not encrypted) | — | The user-data partition is not encrypted (fscrypt / dm-crypt), **not implemented**: a lost phone's storage, taken out, shows the chat history |

### 13.1 Is WeChat or Alipay on Kario realistic

| Path | Realistic? | Who |
|------|------------|-----|
| Tencent or Ant builds a lite client | Technically the most realistic: the core logic (network, storage, protocol) is mostly cross-platform C++ and builds against the C ABI SDK (`sdk/c`); the UI is rewritten in `phone.Ui` ([12](12-super-app-capabilities.md) §7). The precedents are WeChat for watches and Alipay's offline payment code on watches: big vendors have made cut-down clients for small non-Android devices (**not verified** in detail, mostly under NDA) | Tencent or Ant themselves, or a phone maker under licence; it needs scale ([12](12-super-app-capabilities.md) §8) |
| Mini-programs | Existing WeChat and Alipay mini-programs cannot run: they need those base libraries, the `wx.*` / `my.*` interfaces and the back ends (sign-in credentials, payments); Tencent and Ant do license third-party apps to host mini-programs (their mini-program container SDKs, for Android and iOS), and a Kario port needs their consent | Tencent, Ant |
| Web (H5) | Partly: merchants' H5 checkouts and official-account articles display; but bringing up a wallet to pay needs URL schemes (**not implemented**), and web WeChat is closed to most accounts | Kario adds deep links; the payment company decides how an H5 checkout pays on a phone without its wallet |
| Kario's own wallet with banks or UnionPay | Feiqian shows the platform side; a real wallet needs a payment licence, outside this section | — |

Whichever path, these can only come from outside Kario:

| From | What |
|------|------|
| Tencent, Ant | The client itself, push integration (or taking their messages on Kario's push gateway), the mini-program base libraries, the payment and offline codes' algorithms and servers, SOTER / IFAA servers and certification, risk control accepting Kario's attestation |
| A TEE vendor (Qualcomm QTEE, Trustonic Kinibi, Beanpod ISEE, or OP-TEE on the board; why a vendor when every ARM chip has TrustZone: [31](31-lock-and-biometrics.md) §12) | Moving phone-keystored's keys, PIN checks, fingerprint templates and matching into a trusted application; trusted input (the PIN from the keys straight into the TEE); the SOTER / IFAA trusted applications and attestation keys provisioned on the line; the fingerprint sensor's driver in the TEE |
| Chip and module makers | Camera focus, exposure and flash control, hardware codecs (video calls, recording), the NFC controller's NCI driver |

### 13.2 The three gaps filled now, and why these

Chosen as "used daily by such clients, missing in the demos, testable once filled", three at most:

| Gap | Why | What was added | Tests |
|-----|-----|----------------|-------|
