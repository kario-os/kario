# Design gaps and what is not verified

> The **architectural gaps** noted on 2026-11-21 while preparing a OnePlus 6T (A6010, OxygenOS 11.1.2.2) as a real phone (the backup, building Nura, getting ready for the chroot test, [39](39-oneplus-6t.md) §9.1), checked against the documents and code of the time the same day. Only what the design has not solved, or what rests on an unreliable premise, is listed here; the details are in the topic documents, each item linking there.
> Checked again item by item on 2026-11-28 against `d274a1d` (dev): the code, the tests, the selftest table in [13](13-prototype.md) §5, [40](40-testing.md), the topic documents, and the night chains r87 and d100 that ran on this code (QEMU's device and product images, the 6T's builds, plus r87's run of `go test ./shell`, `make selftest`, `make cts` and `make pixel-selftest` on the developer machine). What is done has left §1–§9 for §20 (with the date and the evidence); what is partly done says what is left; §10–§19 record one real-phone run after another and are marked in place with what the phone showed later.
> Status: a list, not a plan. **Not implemented**, **not tried on a phone** and **not verified** are as the topic documents say; **being worked on** marks what someone else is changing right now, which does not count as done.

## 1. Verification on a real phone has only begun

- From 2026-11-21 to 11-23 the chroot kit ran three times on Nura first (§11, §13; the partition backup went through the debug shell of Nura's boot image, [39](39-oneplus-6t.md) §9.1). From 2026-11-24 to 11-27 Kario's own whole-phone image was flashed and booted four times on the same 6T (reports 005–008, [39](39-oneplus-6t.md) §16.9–§16.14), plus a GPU test image 009 ([42](42-gpu-rendering.md) §4): it boots (the initramfs gets round ABL's `root=`, §17), the full selftest passed 193/194 (11-24), 186/195 (11-25, with a China Mobile SIM, mobile data up) and 204/204 (11-26, report 007, 73 more skipped, each saying why; the compatibility run called 132 of the 137 capabilities), and report 008 was checks by hand and `$W perf`, no selftest ([40](40-testing.md) §7); waking at the power key, powering off, the watchdog at a reboot and logind leaving the power key alone have been seen on the phone (§20).
- Most changes made after each run are **not tried on a phone**, waiting for the next run ([39](39-oneplus-6t.md) §14). Not run on the phone yet, or run without success: the touchscreen ([39](39-oneplus-6t.md) §14.17), the A/B layout (§3), the Shell putting the phone to sleep itself and a night's drain ([39](39-oneplus-6t.md) §14.19, **not run**), the GPU on the Adreno (§2), IMS registration and VoLTE (§4), the factory mode ([39](39-oneplus-6t.md) §14.24), the side-by-side comparison with an Android keypad phone ([39](39-oneplus-6t.md) §14.22). The results in [13](13-prototype.md) still come almost all from the developer machine and QEMU.

**What it means**: most "it works" still covers simulated environments only. Calls on the phone have one record (report 008: the first call after boot silent both ways, the later ones with sound, [39](39-oneplus-6t.md) §14.20); for the radio's figures, power and standby current, the real panel's refresh and temperature there is no data yet, and the sensors are not done (§4).

## 2. Rendering and display

- **GPU**: by default phone-paint rasterizes and composes on the CPU. Optional GPU composition exists (`PHONE_PAINT_GPU=1`: GLES 2 composition, presented by page flips of GBM buffers, [37](37-motion.md) §5 item 8), tested on the developer machine's llvmpipe; its GBM and flip part was verified on QEMU with a software GPU (Mesa's softpipe is in the QEMU image, [42](42-gpu-rendering.md) §7). On the Adreno 630 it was tried once: on the GPU test image 009 the GPU did not come up and painting fell back to the CPU (Landlock kept Mesa from finding the device); changed on 2026-11-27, with the GPU firmware in the initramfs too (night chain r87's 6T initramfs manifest gained `linux-firmware-qcom-adreno-a630`), and since then **not tried on a phone** ([42](42-gpu-rendering.md) §4, §5). Rasterizing on the GPU exists too, also optional (`PHONE_PAINT_GPU=raster`, [37](37-motion.md) §5 item 10, §2.5): on llvmpipe every kind of op the GPU paints is byte for byte the CPU's; whether it pays, frame times and power are **not tried on a phone**. There is no data on CPU load and power at 1080×2340 and 60 Hz on the Snapdragon 845 ([37](37-motion.md) §2 has estimates).
- **Exclusive DRM**: phone-paint holds the panel itself (DRM master, [08](08-display-adaptive-refresh.md)), which conflicts with any display manager: the chroot kit's `setup` first stops tinydm, greetd, sddm, lightdm and gdm (`tools/phone-chroot/on-phone.sh`), and Nura has to be installed with the console interface ([24](24-sku-framework.md) §6.2). So no other graphical interface can run on the base system at the same time, and Kario cannot run as a window inside another desktop.
- **The text interface cannot show Chinese on the device's screen**: the Linux console has at most 512 glyphs ([09](09-ui-feasibility-review.md) §3.2), so the device's screen has to go through phone-paint; the text interface is for SSH, the serial console and debugging.
- **CI has no pixel baselines**: the developer machine's pixel baselines are recorded and compared on every run (§20); on CI's Ubuntu phone-paint finds other fonts, `shell/testdata/snapshots/pixel/phone-paint/` has only the developer machine's font set for each form factor, so CI only says "no pixel baselines, not compared"; CI's baselines are to be taken from the `pixel` job's artifacts ([40](40-testing.md) §2, §7, **not verified**). What still moves (progress bars while playing, the camera's picture, video) is listed in `shell/testdata/snapshots/unstable.txt` with the reasons.
- **Coverage** is measured now (§20); CI's manually started `coverage` workflow is **not verified** on GitHub ([40](40-testing.md) §7).
- **No automatic comparison of the two interfaces**: [06](06-gui-architecture.md) §3 says documents are laid out on a character grid, so line breaking, the line-break rules and Mermaid diagrams are the same in the text and the pixel interface; the unit tests cover Mermaid's 9 kinds of diagram ([14](14-tui-route-and-app-framework.md)), and no test compares the text interface with phone-paint cell by cell (`yocto/gui-compare.py` compares phone-paint's CPU and GPU paths, not these two interfaces).

## 3. System updates and the A/B slots

- The 6T has always been flashed with the userdata layout: **no A/B system slots, dm-verity or OTA** ([39](39-oneplus-6t.md) §11), userdata the only root file system, and `system.update` says it is not supported. The whole of [25](25-system-update.md) (RAUC, incremental bundles, resuming, automatic updates) is verified only on QEMU's A/B disk.
- The A/B layout is designed and written ([43](43-phone-partitions.md)): the root file system in `system_a` and `system_b`, read-only through dm-verity, the initramfs mounting the root of the slot ABL picked, RAUC updating a root slot with its boot slot through `rauc-abl`, the data on userdata; the board file has a partition table, and the flash script sizes partitions before writing and never writes the EFS or the firmware's partitions. Scripts and logic unit tests ✓, the images first built on 2026-11-24 and three more times from `phone-fajita-ab.yml` on 2026-11-27 (the module signatures checked each time, the same package list each time, 1268 packages; one of them by the night chain d99, its `build-ab` and its module signature check `modsig-ab` both PASS), and report 008's trial image has an A/B one too, with a signed update bundle ([39](39-oneplus-6t.md) §11); none has booted, **not tried on a phone**; what to check on the phone first is in [39](39-oneplus-6t.md) §15 (how big the partitions are, whether going back to OxygenOS still works).
- `phone-abslot` is tested on disk images (kario-bsp's `tests/abslot-test.py`, plus a model of ABL as read from its source in `tests/rauc-abl-test.py`); on the whole phone with the userdata layout it marked the slot on 2026-11-24 (`phone-qcom-abslot` marked `boot_a` successful, and the tries stopped counting down, [39](39-oneplus-6t.md) §16.9), and ABL counting its tries down after failed boots and marking the slot unbootable has been seen on the phone too ([39](39-oneplus-6t.md) §16.1); falling back to the other slot once the tries are spent, and all this in the A/B layout, are **not tried on a phone** ([39](39-oneplus-6t.md) §14.13, §15).
- The 6T's persistent area (`/var/lib/slots`: a wipe's request, the anti-theft record) is on the same userdata as the data, in the A/B layout too (why: [43](43-phone-partitions.md) §3.4): flashing userdata again or `fastboot -w` removes both ([31](31-lock-and-biometrics.md) §11.5); booting no longer depends on it, and the phone still comes up.

## 4. Telephony: the hard gaps for China

- **VoLTE has not got through on a phone yet** ([39](39-oneplus-6t.md) §11.1, §14.21). Most Chinese carriers need VoLTE for calls (China Unicom and China Telecom have switched 2G and 3G off). The OnePlus 6T's image has 81voltd (opening the IMS bearer for the modem) and `phone-qcom-pdc`, which activates the modem's configuration for the SIM's carrier, and telephonyd takes the IMS bearer for no mobile data and never disconnects it. On the 2026-11-27 image (report 008) 81voltd ran, and `ims-status`, which asks for the IMS registration, answered `InvalidOperation` every time (it had not bound the subscription first; changed in kario-bsp `f228abe`, **not tried on a phone**), so whether IMS registered is not known. When the modem lacks the carrier's configuration it has to be loaded by hand (that writes the modem's persistent storage, deliberately not automated), and carrier compatibility can only be tried carrier by carrier with real cards ([39](39-oneplus-6t.md) §14.6). The status bar's VoLTE mark and the IMS registration state in Settings are done, **not tried on a phone**; a VoLTE switch, Wi-Fi calling and an HD voice mark are **not implemented** ([39](39-oneplus-6t.md) §11).
- **Call audio**: the routing (earpiece, speaker, mute, the UCM boot sequence) is written ([20](20-audio.md) §10). On the phone: report 007's image could neither answer nor place a call (q6voiced exited at boot: the upstream unit is `DynamicUser=yes`, and dbus-daemon cannot look dynamic users up), and on report 008's image the first call after boot was silent both ways while the later ones had sound (`SLIM RX0 MUX` is set in `Voice Call` only); both are changed (q6voiced runs as a user of its own, and the build checks the users of every service started at boot; audiod passes through `Voice Call` first at boot), **not tried on a phone** ([39](39-oneplus-6t.md) §14.20). ModemManager crashed on 007 and 008 (`SEGV`); the two upstream patches applied for it are **never built** and **not tried on a phone** (same section).
- Bluetooth call audio is **not implemented**, and echo cancellation for the speaker is not done (mainline q6voice has no ACDB calibration as on Android, [20](20-audio.md) §10).
- **Headphones**: the 6T has no 3.5 mm jack, mainline USB is device only so USB-C headsets cannot be attached; audiod reads a jack now ([20](20-audio.md) §12.5), which the 6T cannot use ([20](20-audio.md) §10).
- MMS is an **MVP**, run only against a fake MMS centre; a real carrier's is **not tried on a phone** ([32](32-messaging.md) §11).
- **Hanging up during a call**: on a 6T without a keyboard no touch counted during a call, so only the other side could end it (report 008); now, as on Android, the power key hangs up (on by default on the 6T), and while the earpiece plays, touch comes on after a press of a volume key or a one-second hold on the screen, **not tried on a phone**; the 6T has no proximity sensor ([39](39-oneplus-6t.md) §14.23).
- Sensors, the camera, NFC, USB host, Dash fast charging and the vibration motor are not done ([39](39-oneplus-6t.md) §11); the alert slider is written, **not tried on a phone** ([39](39-oneplus-6t.md) §14.18).

## 5. The price of keeping GPLv3 out

The image takes no GPLv3 (the kas file's `INCOMPATIBLE_LICENSE`, [39](39-oneplus-6t.md) §10), so these have to be rewritten or done without:

| The GPLv3 one | Licence | What Kario does |
|------|------|------|
| qbootctl | GPL-3.0 | `phone-abslot`: tested on disk images; marked the slot on the whole phone on 2026-11-24 ([39](39-oneplus-6t.md) §16.9) |
| hexagonrpcd | GPL-3.0+ | Nothing instead: no sensors |
| msm-modem's UIM selection | GPL-3.0+ | `uim-select`: no tests of its own (none in `tests/` of kario-bsp `f228abe`, the commit kario pins); it ran on the whole phone: on 2026-11-24, with no module loadable, it waited its full 60 s (§19), and on 2026-11-25 the SIM card was in use and mobile data up ([39](39-oneplus-6t.md) §16.10) |
| bootmac | GPL-3.0+ | `phone-btaddr`: tested against a socket playing the kernel (kario-bsp's `tests/btaddr-test.py`: it waits for the controller to be set up before setting the address); on the whole phone on 2026-11-25 the old version failed (`failed (17)`), the new one is **not tried on a phone** ([39](39-oneplus-6t.md) §16.10) |
| callaudiod | GPL-3.0+ | phone-audiod's UCM call routing: unit tests; on report 008 the calls after the first one since boot had sound (§4, [39](39-oneplus-6t.md) §14.20) |
| eSpeak NG (the screen reader's voice) | GPL-3.0+ | Nothing instead: the speech engine is **not implemented**, and the screen reader makes no sound on a phone ([20](20-audio.md) §11) |

Each stand-in was written anew from what it has to do, without the original's code. `phone-abslot`, `uim-select`, `phone-btaddr` and audiod's call routing in the table have run on the whole phone; what changed since is **not tried on a phone**.

## 6. Testing and engineering

- **Only the shell package and Settings pass `-race`**: `go test -race ./shell` passes (418 s on 48 cores, 436 s on 4): the time zone is carried explicitly and the process-global `time.Local` is no longer rewritten; what was called Contacts' "disk write of about 600 ms" was the test's Shell building the input-method dictionary on its own loop, with the not-responding check counting the Shell's own hold on the app as the app not answering; both are fixed ([40](40-testing.md) §7). `go test -race ./apps/settings` passes too (2026-11-28): the data races were all in the tests (they read and wrote Settings' state off the app's loop, and one test's app loop had not stopped when the next test started), none in Settings' own code. CI's `race` job runs those of the two packages the `go` job runs; with the shell package alone it ran on GitHub on 2026-11-27 (once each on dev and main) and passed both times, with Settings added it is **not verified** on GitHub ([38](38-contributing.md) §2). Still open: opus-go, which `audio/opusfile` and `audio/voice` use, fails the pointer checks `-race` turns on (checkptr). It is not out of bounds (tests, a stress test and fuzzing ran on guard pages), but its decoder has a real class of bug: it passes the address of a local variable on the goroutine stack down as a `uintptr`, which reads and writes the old stack once the stack moves; with the stack moved at every call, stereo Opus decodes as silence; with a normal build it did not reproduce on the development machine, and on a phone it is **not verified**. The code is upstream and kario carries no copy: **not fixed**, to be reported upstream, the two packages kept out of `-race` ([40](40-testing.md) §7); data races in the tests of `jsrt` too (`net_test.go`, not run again); the SDK's `setZone` still rewriting `time.Local` in app processes (`sdk/sdk.go`); durable writes still on the Shell's loop (saving a contact, say: `contacts.WriteFile` with an fsync; on a phone **not measured**); `ota/delta`'s `TestBigFilePatchMemory` going past its 24 MiB limit under `-race` (**not changed**).
- **The simulated boundary is wide**: the modem, Wi-Fi, Bluetooth, NFC, location, the camera, the fingerprint reader and the update server all have a simulated side ([40](40-testing.md) §3). Real sides seen on the phone: the modem (mobile data up on 2026-11-25, [39](39-oneplus-6t.md) §16.10; calls in §4) and Bluetooth (BlueZ had no adapter that time, `phone-btaddr` in §5); the rest are mostly **not tried on a phone**.
- **A sysfs attribute stopped the Shell**: on the whole phone on 2026-11-25 the kernel answered the Shell's read of the charger's `usb_type` with `EAGAIN`, Go's file object kept waiting for it to become readable, and the Shell's only loop stopped with it; `hal/` now reads and writes device attributes with plain system calls, and the loop has a watchdog, **not tried on a phone** ([39](39-oneplus-6t.md) §16.11).
- **The backup's premise failed on a 6T**: `fajita-flash.sh backup` and `restore-efs` need a TWRP that `fastboot boot` starts on OxygenOS 11, and on that phone TWRP 3.7.0_9 crashed into EDL ([39](39-oneplus-6t.md) §9.1); `test`, `flash`, `restore` and the chroot kit's `push`, for their part, take only a backup in the scripts' own format (`fajita-flash.sh` wants `phone.txt` and `SHA256SUMS`, `push` wants `SHA256SUMS`). The backup made by hand through Nura's debug shell is written up in [39](39-oneplus-6t.md) §9.1; the scripts cannot go that way (**not implemented**).
- **Pairing the first Bluetooth keyboard on the whole phone**: Kario's Settings used to take a keyboard to get to; the touchscreen now works as keys too ([39](39-oneplus-6t.md) §14.17, **not tried on a phone**), so Settings can be reached to pair without a keyboard; Settings › Bluetooth can now also pair a keyboard that has the pairing code typed on it: the system shows the code (2026-11-28; before, Kario did not show it and such a keyboard did not pair), **not tried on a phone**. The 6T itself has only the power and volume keys (the volume keys deliberately do not double as arrows, [24](24-sku-framework.md) §7.4), and its USB is device only; the developer channel takes only a cable the shell itself trusted ([27](27-usb-typec.md) §4), while the USB controller belongs to `phone-bringup` then. The image has no `bluetoothctl` (`bluez5_%.bbappend` drops readline, which is GPLv3; the package list of the 6T image built on 2026-11-28 has `bluez5` and no readline; this is from the recipe and the package list, nobody ran `command -v` on the phone, [39](39-oneplus-6t.md) §14.7). On the whole phone on 2026-11-25 BlueZ had no adapter at all (`phone-btaddr` failed; changed, **not tried on a phone**, [39](39-oneplus-6t.md) §16.10).
- **The build fills in what it lacks (partly gone through in real image builds)**: `make yocto-src` (which `yocto-build` and the others go through) runs `tools/gomodinc.py --ensure`: it regenerates a stale `phone-fw-go-mods.inc` itself and stops with the reason only when it cannot (no network, a Go older than `go.mod` asks for); `go mod tidy` no longer makes it stale. The check runs in every real image build (the build logs of the night chains r87, d100 and d99) and found the list current each time; the "stale, so regenerate it" path has not been gone through in a real build (none of those logs has `writing it again`). `make yocto-doctor` marks what the device image cannot do without (podman or docker, kas-container, rootless podman's subuid/subgid, Go, GCC 14, disk space and more) as MISS; `make doctor`'s exit status still covers the host targets only; the night chains do not run it, and nothing runs it before a build. bitbake's thread counts follow the machine (the smaller of the processors and memory ÷ 2 GiB, `YOCTO_JOBS=` overrides, [13](13-prototype.md)). `yocto-bundle` and `yocto-ota-test` do not go through `yocto-src`, so they do not recheck the module list.
- **Apps stuck at their memory limit**: established on QEMU: the group's file pages (the app's own program) are reclaimed and read back over and over, and the kernel is slow to declare OOM; the Shell now ends such an app by its memory pressure, as Android's lmkd does ([17](17-app-sandbox.md) §5.4). Still missing: the thresholds (half of 2 s) were set on QEMU, while the 6T's kernel has MGLRU on and much faster storage, and its numbers are **not tried on a phone** ([39](39-oneplus-6t.md) §14.12); an app writing files at its limit was not tested (the selftest's data directories are on tmpfs); web process groups are not watched (**not implemented**).
- **Bluetooth pairings lost at a start over**: when the selftest starts over after a failure the state directory is put back, but the pairings BlueZ keeps itself are not in it; on the developer machine the cases using a headset paired earlier fail after a start over ([40](40-testing.md) §2, **not solved**).
- **Flaky unit tests, and some following the clock**: `TestHostileApps/fds` passes or fails by turns; `TestFamilyGrantWithAClockOff`, `TestScreenTimeCountsTheAppOnScreen` and `TestLimitHoldsTheAppBack` follow the wall clock and fail near midnight ([40](40-testing.md) §7, **not solved**).
- **Other packages' tests do not check for programs older than their sources**: `make test` builds the programs it needs first, and a lone `go test ./shell` has its end-to-end tests build theirs; other packages' tests do not notice when the ready-made programs they use are older than the sources ([40](40-testing.md) §6, **not implemented**).
- **kario-jsrt under sanitizers**: ✓ on the developer machine; CI's `jsrt-sanitize` job ran on GitHub on 2026-11-27 (once each on dev and main), and ASan and TSan both failed in `TestNodeFetchResponseHeaders` (the runner's own Node.js 22 treats response headers differently from the developer machine's 24; changed), not a sanitizer's report, so a whole pass on GitHub is **not verified**; clang, MemorySanitizer and runs on arm64 are **not implemented** ([40](40-testing.md) §8).
- **Production-line tests**: the hardware tests and the factory mode have run on the developer machine and QEMU, **not tried on a phone** ([39](39-oneplus-6t.md) §14.24); the radio's figures need instruments, **not implemented**; there is no authentication between a station and the phone (**not implemented**, [40](40-testing.md) §10, [31](31-lock-and-biometrics.md) §13.5).

## 8. Performance and resources

- The first image build wants about 150 GB of disk and some hours (`scripts/doctor.sh`'s hint; longer on machines with fewer than 8 cores or 16 GB of memory).
- There is no data on the CPU load and standby power of phone-paint's software rendering on a real phone ([37](37-motion.md) §2 has estimates; how to measure: [39](39-oneplus-6t.md) §14.3, §14.10).
- **A night's drain**: on report 007 the battery ran flat overnight, because the bring-up image took a wake lock at boot and never let it go; it now holds the lock only while a computer has the bring-up USB configured, **not tried on a phone**; whether an incoming call wakes the sleeping phone (the newly added `phone-qcom-wake`), how often a night wakes it and the standby current are **not run** ([39](39-oneplus-6t.md) §16.12, §14.19).
- **The black screen at boot**: the kernel log scrolling on the panel is changed (**not tried on a phone**); with that change, about 11.5 s after the bootloader's picture show nothing of Kario's (report 007's measurement), mostly because `phone-display` is ordered after telephonyd and the modem's chain; neither moving it nor a logo in the initramfs is done ([39](39-oneplus-6t.md) §16.13).
- The 1 GB memory pressure test and the soak have run only on QEMU and the developer machine (last on 2026-11-27, [40](40-testing.md) §1).

## 9. Security and the ecosystem

- The app sandbox, the capability broker, store signatures and third-party listing are verified mostly on the developer machine and QEMU. On the 6T: Nura's kernel has no Landlock (§11); on Kario's own kernel the "kernel features" case passed on 2026-11-24 (the "kernel features + sandbox" part 3/4; the failed 「沙箱里的 DNS」 (DNS in the sandbox) was the case's fault and is fixed, [39](39-oneplus-6t.md) §16.9); the compatibility report's `sandbox` field and the sandbox self-check's 13/13 were not recorded ([39](39-oneplus-6t.md) §14.12, **not tried on a phone**).
- The web view (WPE WebKit) is in an image of its own (`KASEXTRA=yocto/kas/web.yml`) and last ran on the code of 2026-11-28 ([13](13-prototype.md) §5): `make web-selftest` on the developer machine (WPE WebKit 2.48.3 in a container) passed all 266 cases (before the three fixes in [13](13-prototype.md) §5; after them only the cases they touch reran); on QEMU's web image (WPE WebKit 2.52.6, SKU qemu-t9) the four cases 「网页视图」 (Web view), 「网页表单」 (Web forms), 「浏览器」 (Browser) and 「内存紧张：先结束后台应用的网页」 (Memory pressure: background apps' pages ended first) passed, and so did all 298 cases of the whole `make yocto-selftest` (8 emulators). The low-memory stress test on the web image with a 1 GB SKU (21/21: the browser opened while a video plays, three pages one after another) and the WPE path of `make yocto-bench` ([40](40-testing.md) §1) last ran on the code of 2026-11-27. The night chain neither builds the web image nor runs `make web-selftest`, and the four cases skip in its images: later changes leave the web view **not verified** again until the commands of [13](13-prototype.md) §5 run again. The web view is **not tried on a phone**.
- Trusted payment confirmation, device attestation and fingerprint payment need a TEE, which is **not implemented** ([31](31-lock-and-biometrics.md) §4, R15): phone-keystored stands in, with the device keys and the data salt on the data partition ([31](31-lock-and-biometrics.md) §11.3).
- Anyone can unlock the 6T's bootloader, and its persistent area is on userdata: the anti-theft lock cannot stop a reflash ([31](31-lock-and-biometrics.md) §11.5; a locked bootloader **depends on hardware**). The account server is **not deployed**, so neither the anti-theft lock nor parental remote management has run on a phone against a real server.
- Capability versions and platform level 2 (`media.list@2`, [22](22-developer-api.md) §2.3) are verified on the development machine only: no system of level 2 has been released, and no version has really been removed (removal has been gone through on test tables only); the store's catalogue does not filter by the manifest's `capabilities`, so only the phone's installer refuses; the system's own Music and Gallery apps still use version 1 of `media.list`, not pages (what happens when a library's answer goes past 4 MB is **not verified**); TypeScript apps cannot read the platform level (**not implemented**). The renderer protocol's negotiation at a major change has been gone through with a `phone.frame/0` made up in the tests only ([23](23-renderer-protocol.md) §2).

## 10. What else this real-phone run brought up (that computer's record)

### 12.3 Detached steps reported "gone" by mistake

- A detached step that died halfway (`die`, say the chroot not mounted) wrote no exit code, so status could only say gone. Now it writes one however it ends.
- Status, finding no `/run/kario-chroot/run`, started a new run itself and then looked for the exit code in the new results directory. Now status and log never start one.
- The pid noted was its launcher's `$!`; `setsid` forks once more when handed a process group's leader, and `$!` is then a process that ends at once. Now the step notes its own pid as it starts (one copy in `/run`, one in the results directory), and status also finds it by its command line.
- Under systemd, logind ending the SSH login (with `KillUserProcesses=yes`) kills what is left in the login's scope, `setsid` or not, while phone-shell, already moved into our own cgroup, keeps running: exactly "gone while the test runs". Now under systemd detached steps and `shell-start` go into a scope of their own (`systemd-run --scope`). Whether this was that time's cause is **not established**.
- When status says gone it now prints what the phone shows: the state directory, the `run` file, each pid file and whether its process is there, the results directories, the parent, process group, session and cgroup of the processes concerned, and logind's `KillUserProcesses`; a detached step also notes a hang-up (SIGHUP) or a stop (SIGTERM) it gets (and does not end for it). `kario-phone.sh` prints all that with the last lines of the step's output, ready to paste into the report.

## 13. A black screen and a crash dump after `shell-start` (2026-11-21, **not solved**)

The other side's record: after `shell-start`, Kario's boot animation appeared, then the screen went black and the power key did not light it again; afterwards the phone showed up on USB as `05c6:900e` (Qualcomm's crash dump mode, QUSB_BULK), which is common after a kernel hang and a watchdog reset. This was a hang at kernel level, not the scripts' fault; the cause is **not established**.

The guesses, most suspected first:

1. **Turning the screen off and on.** Compared with the selftest, what `shell-start` adds is the real panel and real hardware: phone-paint drives the panel directly, reads the power key and the touchscreen, turns the screen off on the timeout, sets the backlight, and key presses may vibrate. By default the Shell turns the screen off after 30 s idle: it fades the backlight to 0, then phone-paint turns the display controller's output off (`set_crtc` without a framebuffer) and the panel loses power; the power key sets the mode again and powers the panel up. This path had never run on the 6T then (on the whole phone the power key has turned the screen off and on since 2026-11-24, see the end of this section); the 6T's panel is a DSI command-mode panel (`dsi_samsung_s6e3fc2x01_cmd_display`), and its DSI PLL already failed to lock once at boot (§11). The sequence fits: the picture appeared, then went black, the power key did not light it, and then the crash dump. The report's guess that the backlight, controlled by sde/dsi on its own, was turned off by fbcon and DRM fighting over the display controller is looked into under this one.
2. **phone-paint's mode setting itself** (`drmModeSetCrtc`, dumb buffers) was not verified on the 6T's msm DRM either then (on the whole phone phone-paint has reached the panel this way since 2026-11-24, [39](39-oneplus-6t.md) §16.9, §16.13).
3. **The USB gadget**: unlikely. The image's Shell has whole-phone support (the facts say so) and leaves USB alone while Nura's gadget holds the controller ([24](24-sku-framework.md) §6.2); if SSH still worked after `shell-start` until the hang, this is ruled out.
4. **`chvt 8` and console 1's getty**: they can confuse the keys and the display's state, but are unlikely to hang the kernel.

The steps to isolate it (no `shell-start` again until they have results):

1. Before each step, open another SSH session that streams `dmesg -w` to the computer: if the phone hangs, the last lines are kept.
2. Collect what the crash left: the results directory's `shell.log`, the services' logs under `/var/lib/kario-chroot/state/home/.local/state/phone-sim/run/`, `/sys/fs/pstore`, the previous boot's kernel log (`journalctl -b -1 -k`). What matters most are the last few dozen lines of `shell.log`: what the Shell and phone-paint did around turning the screen off (`screen off`, the backlight).
3. Without Kario, on Nura's console: dim the backlight, set it to 0, bring it back (`/sys/class/backlight/ae94000.dsi.0/brightness`), then turn the display controller's output off and on through DRM's fbdev (write 4, then 0, to `/sys/class/graphics/fb0/blank`: the same part of the same driver phone-paint's screen-off takes), five times if it comes back. A hang or `900e`: the problem is in the kernel's panel power-down and power-up, and Kario has to give this board an option to turn only the backlight off, not the display controller (**not implemented**). All fine: the problem is more likely in Kario, to be narrowed down with the switches below.
4. `shell-start`'s bring-up switches (added now): `--stay-on`, the Shell never turns the screen off (neither the timeout nor the power key turns it off or dims it, the backlight and the display controller stay on, so the phone never sleeps either); `--no-haptics`, no vibration. They hold for that one Shell and are not kept as settings (`kario-phone.sh --stay-on --no-haptics shell-start`, [39](39-oneplus-6t.md) §13.4). Unit tests ✓, **not tried on a phone**.

The report's suggestion to read the memory out of the crash dump first (`05c6:900e` with qdl or edl, which needs this phone's firehose loader) comes after the steps above.

Later: step 3 was done on Nura's console on 2026-11-22, the backlight set to 0 and back, the console blanked and unblanked five times in a row, all fine, so the panel itself powers down and up ([39](39-oneplus-6t.md) §16.5); on the whole phone (2026-11-24) single presses of the power key turned the screen off and on as they should, and the black screen after several quick presses came from places in Kario, fixed, **not tried on a phone** ([39](39-oneplus-6t.md) §16.9). The cause of that hang in the chroot is still **not established**.

## 15. Partitions: split them as Android does?

On the 6T, Android keeps what only this phone has in partitions of their own: `persist` (the fingerprint's and the sensors' calibration), `modemst1` and `modemst2` (the IMEI and the modem's other data), `fsg` and `fsc` (the modem's configuration), and `frp`, `apdp` and others. Kario writes only `dtbo_a/b`, `boot_a/b` and `userdata` (the whole root file system) and **leaves those partitions alone**: flashing Kario loses neither the IMEI nor the calibration; rmtfs still hands `modemst` and `fsg` to the modem, and Kario does not write them ([39](39-oneplus-6t.md) §3.5, §14.1). The report's proposal agreed with the design as it was (the four items below); the whole partition design settled since is [43](43-phone-partitions.md): the first three items stand, the 4th changed, the A/B layout putting the root file system into `system_a` and `system_b` (`vendor` still untouched), and why the persistent area stays on userdata is [43](43-phone-partitions.md) §3.4.

1. Android's `persist`, `modemst1/2`, `fsg` and `fsc` stay as they are; Kario does not write them.
2. Kario's own durable data is in `userdata`'s `/var/lib/phone`, with no `persist` of its own to compete with Android's; the persistent area `/var/lib/slots` is on `userdata` too (§3).
3. Fingerprint templates and sensor calibration, if they are ever taken over, are copied from Android's `persist` into `/var/lib/phone` and used read-only, the original partition unchanged (**not implemented**; neither fingerprint nor sensors are done on the 6T).
4. The A/B slots are for `boot` and `dtbo` only; `userdata` is the only root file system, with no `system_a/b` or `vendor_a/b` as on Android for now. When system updates are to roll back, dm-verity and A/B on `userdata` are what to look at ([39](39-oneplus-6t.md) §11), not Android's whole partition table.

## 16. The second test on a phone: what the whole firmware must bring (2026-11-23, report 003)

That run was in Nura's chroot; these are what the whole firmware (its own kernel and image) has to solve or find out first.

- **logind powering off at the power key and suspending at the cover** (solved, ✓ on QEMU; ✓ on the whole phone on 2026-11-24: `HandlePowerKey` and `HandleLidSwitch` are `ignore`, and the power key does not power the phone off, [39](39-oneplus-6t.md) §16.9; the cover has no magnet, not tested): the image had systemd-logind but did not configure it, so by its defaults a press of the power key powered the phone off and the 6T's Hall sensor (`Hall effect sensor`, the magnetic cover) suspended it when closed, both behind the Shell's back. The image now has a logind drop-in setting every key and the lid to `ignore`; the selftest has a case pressing the real power key, and on QEMU without the drop-in that press powers the emulator off ([28](28-battery.md) §7).
- **The watchdog at a reboot** (changed; ✓ on the whole phone on 2026-11-24: `Watchdog running with a hardware timeout of 30s`, and no extra short boot in `journalctl --list-boots`, [39](39-oneplus-6t.md) §16.9): by default systemd sets `qcom_wdt` to 10 minutes for a reboot, the driver takes 32 seconds at most, and after the `EINVAL` systemd disarms the watchdog. The watchdog is now the board's `[watchdog]`, 30 seconds on the 6T ([24](24-sku-framework.md) §2, [28](28-battery.md) §7). The report put "the extra boot of 2 seconds after a reboot" down to it, but systemd 259 and 261 both disarm the watchdog after the `EINVAL` rather than leave it armed, and the extra boot came after `fastboot reboot` too: its cause is **not found**, and [39](39-oneplus-6t.md) §14.10 has the steps to compare.
- **Power-off** (the code read; ✓ on the whole phone on 2026-11-24: with the cable out it stayed off for over two minutes, and with the cable back in the charger powered it on, as this item guessed, [39](39-oneplus-6t.md) §16.9. Still missing: going into charging while off after a power-off with the cable in; on 2026-11-27 the whole system came up instead, with two `androidboot.mode` on the command line; changed, **not tried on a phone**, [39](39-oneplus-6t.md) §16.14): the report said `pm_power_off` is NULL. The 6T's kernel has PSCI (a `psci` node, `CONFIG_ARM_PSCI_FW`), so `pm_power_off` is PSCI's `SYSTEM_OFF`, and pm8941-pwrkey sets the PMIC's PS_HOLD to shut down first; were it NULL, the kernel would halt, not restart. The USB cable was in that time, so the PMIC powering on again with a charger there is the likelier cause. To try on the 6T with the cable out and in ([39](39-oneplus-6t.md) §14.10).
- **The power key not waking the phone** (the code read; ✓ on the whole phone on 2026-11-24: after `echo mem` a short press woke it in about 10 s, `pm_wakeup_irq` 90, [39](39-oneplus-6t.md) §16.9. Still missing: the Shell putting the phone to sleep itself, and how long from waking to a lit screen, **not run**, [39](39-oneplus-6t.md) §14.19): in the kernel the power key is a wake-up source by default (the driver's `device_init_wakeup`, `enable_irq_wake` at suspend), and its interrupt comes through the same SPMI arbiter interrupt as the RTC alarm, which does wake the phone; the Shell lights the screen at the power key after a wake (`TestPowerKeyAroundAWake`). That run's `event_count` of 0 says nothing: this driver never reports an event to its wake-up source. What was missing is evidence: `/sys/power/pm_wakeup_irq` exists only with `CONFIG_PM_SLEEP_DEBUG`, which Kario's kernels now get through `CONFIG_PM_DEBUG`, so the Shell's log says which interrupt woke the phone. The steps to capture it are in [39](39-oneplus-6t.md) §14.10; a screen that stays dark may also be the display not coming back after the resume (that report's §9.1 item 4), not the wake-up.
- **The speaker too loud in tests** (solved, in the kit, **not tried on a phone**): before `selftest` and `pixel` the kit turns the board's `[audio]` `quiet_controls` down to its `quiet_level` and sets them back after; `--quiet` takes another level or none ([24](24-sku-framework.md) §6.2). The 6T's are the `RX0 Digital` to `RX4 Digital` turned down by hand that time, and whether they are on the speaker's path is **not verified** ([39](39-oneplus-6t.md) §14.5).
- **facts removed the power key's key bitmap** (solved, `tools/phone_chroot_test.py`'s `test_facts_keep_the_key_bitmaps`): in `== input`, `pm8941_pwrkey`'s `key` is `10000000000000`, and the scrub took a run of 14 or more digits for an identity such as an IMEI; the bitmaps' words are now written `0x…`. `facts` also notes the keys' wake-up sources (the devices' `power/wakeup*` and interrupt counts), `pm_wakeup_irq`, how the boot before ended (the watchdog's and power-off's journal lines and pstore's last line) and the sound card's mixer controls.

## 17. The first whole-firmware flash: every boot back in fastboot (2026-11-24, report 004)

The tester flashed the whole firmware built from `0befb13` (userdata layout) on a 6T: `dtbo_a/b` erased, `boot_a/b` and `userdata` written, yet every boot ended back in fastboot, and `fastboot boot` of that boot image too. Kario's kernel with Nura's initramfs came up, with the UFS and a sound userdata in sight. The same day the failed boot's ramoops and the command line ABL hands over were read on the phone, and the cause was found ([39](39-oneplus-6t.md) §1, §8.2).

- **A boot image without an initramfs, relying on ABL not to append its own `root=`** (changed, ✓ on QEMU; ✓ on the whole phone on 2026-11-24: `d4856a3` mounted userdata through phone-initramfs, [39](39-oneplus-6t.md) §16.9): OnePlus's ABL always appends `root=PARTUUID=<Android's system partition>`, a `root=` already on the command line or not; the kernel took the last one, mounted Android's system and ran its init, which rebooted into the bootloader on its error. The userdata layout's boot image now carries phone-initramfs too, which mounts userdata by its partition name and leaves the command line's `root=` alone; `make yocto-userdata-test` simulates ABL's additions on QEMU as they were that time: through the initramfs it comes up, the former way goes for the Android partition. The lesson: a design resting on what closed firmware does (here, how OnePlus's ABL changes the command line) is either checked on the phone first or made not to depend on it; QEMU always used the initramfs, so "the kernel mounts the root itself" had never run anywhere.
- **After repeated failed boots ABL marked the slot unbootable, and `fastboot boot` answered `Load Error` from then on** (changed; when `d4856a3` was flashed on 2026-11-24 the script ran `--set-active=a` first, and the phone came up, [39](39-oneplus-6t.md) §16.9): only `fastboot set_active a` put it right. The flash script's `test`, `flash` and `restore` now make the current slot active every time (both layouts), tested against the simulated phone (`yocto/fajita-flash-test.py`); how to look into it is [39](39-oneplus-6t.md) §8.2 step 3.
- **With `root=` on the command line ABL gives no `androidboot.slot_suffix`**: `phone-abslot` then takes the slot marked active in the GPT for the one booted, and `phone-qcom-abslot` still marks the right one (kario-bsp's `tests/abslot-test.py` tests it with that time's command line; ✓ on the whole phone on 2026-11-24: it marked `boot_a` successful, and the tries stopped counting down, [39](39-oneplus-6t.md) §16.9). So that ABL adds no `skip_initramfs` or `ro init=/init`, the boot image's command line keeps its `root=`.
- **The USB link dropped during a 512M fastboot download** (changed; ✓ on 2026-11-24: `-S 64M` wrote userdata in 8 pieces, [39](39-oneplus-6t.md) §16.2, §16.9): userdata's broke off at 471 MB, and `-S 64M` wrote it. The flash script now sends every image in pieces of `-S 64M` (`--chunk` changes it), [39](39-oneplus-6t.md) §6.
- **A backup without `boot_a`, `dtbo_a`, `dtbo_b` made the script refuse to flash** (changed; flashing `d4856a3` on 2026-11-24 only warned, [39](39-oneplus-6t.md) §16.9): that phone had lost them when Nura was installed, and the tester changed the script. Now the phone's own five partitions must be there, and a missing `boot` or `dtbo` only gets a warning; before writing back, `restore` checks each file it would write, wants `--stock` for any missing or erased one, and writes not a byte otherwise ([39](39-oneplus-6t.md) §9, §9.1, `yocto/fajita-flash-test.py` ✓).

## 18. After the first whole-firmware boot: three problems of the kit and the selftest (2026-11-24, report 005)

The whole firmware of `d4856a3` booted on the 6T, and the full selftest passed 193 of 194 cases. The three below came up in that run and are fixed in this tree (the kernel refusing modules and the VPN (device) case are another matter).

- **`facts` hangs on `/sys/power/wakeup_count`, and `setup` never ends** (fixed, **not tried on a phone**): the kernel makes a read of this attribute wait for as long as a wake-up event is being handled, and a wake lock held is one; on the whole phone's bring-up image `phone-bringup-awake` holds one all the time. `setup` stopped after its wake lock sentence and `facts.txt` was empty (the tester dropped the attribute on the phone to go on). Nura holds no wake lock, so the chroot runs never met it. The kit now waits at most 2 seconds for each attribute, writes `<no answer in 2 s>` and kills the reader (the images' busybox has no `timeout`), and lists the wake-up sources in force; the other attributes and commands `facts` reads were checked and do not wait like this (`tools/phone_chroot_test.py` puts a FIFO in its place; the old script hangs there). The Shell's suspend reads the same attribute in a goroutine outside the event loop, so only that suspend waits ([39](39-oneplus-6t.md) §13.5).
- **After the selftest `phone-display` does not start again, black screen** (fixed; the old behaviour reproduced on QEMU, the new one **not verified**, **not tried on a phone**): the kit stops `phone-display` for the selftest, and `KillMode=process` left the input helper the renderer forks; the kernel had cleared its parent-death signal when it dropped privileges, it only noticed the renderer was gone when a new device appeared, and the two scan-out buffer mappings it inherited at the fork kept the display's DRM master in its hands, so the next renderer could not open the panel (`Permission denied`) and the service gave up after 5 restarts. The report's `Unit process 1004 (renderer)` is that helper (renderer and helper are both named `renderer`), not the selftest's renderer: the selftest runs in the kit's own scope and draws nothing on the panel. The helper is now forked before the graphics card is opened, renderer and helper set the parent-death signal again once their privileges are dropped, and the helper also ends when the renderer's end of its socket closes (`paint/`'s tests; the two that need root were run under `podman unshare`, and all fail on the old code); the two units that run phone-shell have `KillMode=mixed`, which `scripts/yocto-check.py` checks; the kit waits for what a stopped unit leaves to end, and after 10 seconds has systemd end it and says so ([11](11-platform-architecture.md) §14, [23](23-renderer-protocol.md) §5, [39](39-oneplus-6t.md) §13.5).
- **「沙箱里的 DNS」 (DNS in the sandbox) fails on the whole phone** (fixed): the run of only "kernel features + sandbox" had never started Hongyan, and `sandbox-read` gave Hongyan's data directory, not there yet, to its uid: the chown failed; in the full run Hongyan had started before, so it passed. The step now makes the directory as the app's first start does (`TestSandboxReadBeforeTheAppStarted`, failing on the old code; [40](40-testing.md) §6).

## 19. The first whole-phone boot: lockdown refused every kernel module (2026-11-24, report 005 §6.1)

The same 6T, flashed with the whole firmware of `d4856a3`, came up for the first time (the initramfs got round ABL's `root=`, §17), the selftest 193/194. The worst problem: the kernel loaded no module at all (`Lockdown: modprobe: unsigned module loading is restricted`), and with them went the RTC (`phone-clock` waited for `rtc0` in vain, the time went backwards across boots), the battery and the charger, the sound card and the modem (`tqftpserv`, `rmtfs`, `q6voiced` and the SIM session all failed, the Shell reached the panel a minute late); "VPN (device)" failed too, as `nft_ct` could not be loaded.

- **The cause** (found on the build machine, **seen**): the modules were signed, but with the key the kernel had generated for itself in another build directory's build: the shared sstate gave this one the other's packaged modules, while the boot image's kernel was this one's own, trusting only the key generated here. Packaging had not stripped the signatures, and lockdown is meant to be on ([39](39-oneplus-6t.md) §8.3).
- **The change** (made, built, verified on QEMU, and checked in every 6T build of the night chains, r87's and d100's `modsig` (`phone-modsig-check: PASS`) both passing; **not tried on a phone**): modules are signed with the build directory's fixed key (made by `make ota-keys`, never in git), whose checksum is in the task signatures; the image build checks that every module goes with the boot image's kernel (the image of `d4856a3`: all 1094 do not); what the 6T always needs and has no firmware for is built into its kernel (qrtr, the PD mapper, the RTC, the fuel gauge, the charger); QEMU's kernel has module signatures and lockdown too, and its boot selftest runs `module-check.sh` first ([39](39-oneplus-6t.md) §8.3).
- **Two other boot errors**: `regulatory.db` missing (changed: it is in the initramfs now, where cfg80211 reads it while booting; QEMU lacked it the same way); the `-2` of `a630_sqe.fw` at boot is expected, msm loads it when the renderer opens the card, left as it was then ([39](39-oneplus-6t.md) §8.1); since 2026-11-27 the GPU's firmware is in the initramfs too ([42](42-gpu-rendering.md) §5; night chain r87's 6T initramfs manifest has `linux-firmware-qcom-adreno-a630`), and since then **not tried on a phone**.
- The lesson: a kernel and its modules are a pair, but the build system caches them as two products; a constraint between the two (the same key) must either be part of the cache's key or be checked before an image goes out. Both are in place now.
