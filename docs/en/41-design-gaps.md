# Design gaps and what is not verified

> The **architectural gaps** noted on 2026-11-21 while preparing a OnePlus 6T (A6010, OxygenOS 11.1.2.2) as a real phone (the backup, building Nura, getting ready for the chroot test, [39](39-oneplus-6t.md) §9.1), checked against the current documents and code the same day. Only what the design has not solved, or what rests on an unreliable premise, is listed here; the details are in the topic documents, each item linking there.
> Status: a list, not a plan. **Not implemented**, **not tried on a phone** and **not verified** are as the topic documents say; **being worked on** marks what someone else is changing right now, which does not count as done.

## 1. Almost no verification on a real phone

- Testing on real phones **has not started** ([40](40-testing.md) §7); the results in [13](13-prototype.md) all come from the developer machine and QEMU.
- On 2026-11-21 a 6T was prepared on another computer: the partition backup went through the debug shell of Nura's boot image, and `boot_a` holds Nura's boot image ([39](39-oneplus-6t.md) §9.1). The same day the chroot kit (`tools/phone-chroot/`) ran on it for the first time: the selftest stopped at its first failed case (§11), and after `shell-start` the phone hung and went into its crash dump mode (§13, **not established**). Kario's own image (the whole phone) has not run on it yet. What is to be checked on the phone is listed in [39](39-oneplus-6t.md) §14.

**What it means**: every "it works" covers simulated environments only. For what only a real phone shows (call audio, radio, power, the real panel's refresh, sensors, temperature) there is no data yet.

## 2. Rendering and display

- **GPU**: by default phone-paint rasterizes and composes on the CPU. Optional GPU composition exists (`PHONE_PAINT_GPU=1`: GLES 2 composition, presented by page flips of GBM buffers, [37](37-motion.md) §5 item 8), tested on the developer machine's llvmpipe; its GBM and flip part was verified on QEMU with a software GPU (Mesa's softpipe is in the QEMU image, [42](42-gpu-rendering.md) §7). On the Adreno 630 it is **not tried on a phone**. Rasterizing on the GPU exists too, also optional (`PHONE_PAINT_GPU=raster`, [37](37-motion.md) §5 item 10, §2.5): on llvmpipe every kind of op the GPU paints is byte for byte the CPU's; whether it pays, frame times and power are **not tried on a phone**. There is no data on CPU load and power at 1080×2340 and 60 Hz on the Snapdragon 845 ([37](37-motion.md) §2 has estimates).
- **Exclusive DRM**: phone-paint holds the panel itself (DRM master, [08](08-display-adaptive-refresh.md)), which conflicts with any display manager: the chroot kit's `setup` first stops tinydm, greetd, sddm, lightdm and gdm (`tools/phone-chroot/on-phone.sh`), and Nura has to be installed with the console interface ([24](24-sku-framework.md) §6.2). So no other graphical interface can run on the base system at the same time, and Kario cannot run as a window inside another desktop.
- **The text interface cannot show Chinese on the device's screen**: the Linux console has at most 512 glyphs ([09](09-ui-feasibility-review.md) §3.2), so the device's screen has to go through phone-paint; the text interface is for SSH, the serial console and debugging.
- **Pixel baselines not recorded yet**: snapshot comparison exists ([40](40-testing.md) §2): the text renderer's baselines are in git and `make selftest` compares every snapshot; pixel snapshots are compared by a hash of each one's decoded pixels, kept per renderer, form factor and font set, and those baselines are not recorded yet (a whole `make pixel-baselines` on the developer machine, and a set of CI's own), **not verified**. What still moves (progress bars while playing, the camera's picture, video) is listed in `shell/testdata/snapshots/unstable.txt` with the reasons.
- **No coverage measurement** (**not implemented**, [40](40-testing.md) §7).
- **No automatic comparison of the two interfaces**: [06](06-gui-architecture.md) §3 says documents are laid out on a character grid, so line breaking, the line-break rules and Mermaid diagrams are the same in the text and the pixel interface; the unit tests cover Mermaid's 9 kinds of diagram ([14](14-tui-route-and-app-framework.md)), and no test compares the text interface with phone-paint cell by cell.

## 3. System updates and the A/B slots

- The 6T has always been flashed with the userdata layout: **no A/B system slots, dm-verity or OTA** ([39](39-oneplus-6t.md) §11), userdata the only root file system, and `system.update` says it is not supported. The whole of [25](25-system-update.md) (RAUC, incremental bundles, resuming, automatic updates) is verified only on QEMU's A/B disk.
- The A/B layout is designed and written ([43](43-phone-partitions.md)): the root file system in `system_a` and `system_b`, read-only through dm-verity, the initramfs mounting the root of the slot ABL picked, RAUC updating a root slot with its boot slot through `rauc-abl`, the data on userdata; the board file has a partition table, and the flash script sizes partitions before writing and never writes the EFS or the firmware's partitions. Scripts and logic unit tests ✓, the images built once on 2026-11-24 and never booted, **not tried on a phone**; what to check on the phone first is in [39](39-oneplus-6t.md) §15 (how big the partitions are, whether going back to OxygenOS still works).
- `phone-abslot` is tested on disk images only (kario-bsp's `tests/abslot-test.py`, plus a model of ABL as read from its source in `tests/rauc-abl-test.py`); the real GPT attributes, and the bootloader counting down its tries and falling back to the other slot, are **not tried on a phone** ([39](39-oneplus-6t.md) §14.13, §15).
- The 6T's persistent area (`/var/lib/slots`: a wipe's request, the anti-theft record) is on the same userdata as the data, in the A/B layout too (why: [43](43-phone-partitions.md) §3.4): flashing userdata again or `fastboot -w` removes both ([31](31-lock-and-biometrics.md) §11.5); booting no longer depends on it, and the phone still comes up.

## 4. Telephony: the hard gaps for China

- **VoLTE is written, never tried on a phone** ([39](39-oneplus-6t.md) §11.1). Most Chinese carriers need VoLTE for calls (China Unicom and China Telecom have switched 2G and 3G off). The OnePlus 6T's image has 81voltd (opening the IMS bearer for the modem) and `phone-qcom-pdc`, which activates the modem's configuration for the SIM's carrier, and telephonyd takes the IMS bearer for no mobile data and never disconnects it; when the modem lacks the carrier's configuration it has to be loaded by hand (that writes the modem's persistent storage, deliberately not automated), and carrier compatibility can only be tried carrier by carrier with real cards ([39](39-oneplus-6t.md) §14.6); the IMS registration state, a VoLTE switch and Wi-Fi calling are **not implemented**.
- Call audio routing (earpiece, speaker, mute, the UCM boot sequence) is written, **not tried on a phone** ([20](20-audio.md) §10).
- Bluetooth call audio and echo cancellation for the speaker are not done (mainline q6voice has no ACDB calibration as on Android, [20](20-audio.md) §10).
- **Headphones**: the 6T has no 3.5 mm jack, mainline USB is device only so USB-C headsets cannot be attached, and audiod does not know a jack's state anyway.
- MMS is an **MVP**, run only against a fake MMS centre ([32](32-messaging.md) §11).
- Sensors, the camera, NFC, USB host, Dash fast charging and the vibration motor are not done ([39](39-oneplus-6t.md) §11); the alert slider is written, **not tried on a phone** ([39](39-oneplus-6t.md) §14.18).

## 5. The price of keeping GPLv3 out

The image takes no GPLv3 (the kas file's `INCOMPATIBLE_LICENSE`, [39](39-oneplus-6t.md) §10), so these have to be rewritten or done without:

| The GPLv3 one | Licence | What Kario does |
|------|------|------|
| qbootctl | GPL-3.0 | `phone-abslot`: tested on disk images |
| hexagonrpcd | GPL-3.0+ | Nothing instead: no sensors |
| msm-modem's UIM selection | GPL-3.0+ | `uim-select`: no tests of its own |
| bootmac | GPL-3.0+ | `phone-btaddr`: tested against a socket playing the kernel (kario-bsp's `tests/btaddr-test.py`: it waits for the controller to be set up before setting the address, [39](39-oneplus-6t.md) §16.10), **not tried on a phone** |
| callaudiod | GPL-3.0+ | phone-audiod's UCM call routing: unit tests |
| eSpeak NG (the screen reader's voice) | GPL-3.0+ | Nothing instead: the screen reader makes no sound on a phone ([20](20-audio.md) §11) |

Each stand-in was written anew from what it has to do, without the original's code, and none is **tried on a phone**.

## 6. Testing and engineering

- **Only the shell package passes `-race`**: `go test -race ./shell` passes (418 s on 48 cores, 436 s on 4): the time zone is carried explicitly and the process-global `time.Local` is no longer rewritten; what was called Contacts' "disk write of about 600 ms" was the test's Shell building the input-method dictionary on its own loop, with the not-responding check counting the Shell's own hold on the app as the app not answering; both are fixed ([40](40-testing.md) §7). CI's `race` job covers the shell package only, **not verified** on GitHub. Still open: data races in the tests of `apps/settings` and `jsrt`, opus-go failing the pointer checks `-race` turns on, the SDK's `setZone` still rewriting `time.Local` in app processes, durable writes still on the Shell's loop.
- **The simulated boundary is wide**: the modem, Wi-Fi, Bluetooth, NFC, location, the camera, the fingerprint reader and the update server all have a simulated side ([40](40-testing.md) §3), and their real-phone parts are all **not tried on a phone**.
- **The backup's premise failed on a 6T**: `fajita-flash.sh backup` and `restore-efs` need a TWRP that `fastboot boot` starts on OxygenOS 11, and on that phone TWRP 3.7.0_9 crashed into EDL ([39](39-oneplus-6t.md) §9.1); `test`, `flash`, `restore` and the chroot kit's `push`, for their part, take only a backup in the scripts' own format (`fajita-flash.sh` wants `phone.txt` and `SHA256SUMS`, `push` wants `SHA256SUMS`). The backup made by hand through Nura's debug shell is written up in [39](39-oneplus-6t.md) §9.1; the scripts cannot go that way (**not implemented**).
- **On the whole phone the first Bluetooth keyboard cannot be paired through the UI**: Kario's Settings take a keyboard to get to; the 6T itself has only the power and volume keys (the volume keys deliberately do not double as arrows, [24](24-sku-framework.md) §7.4), and its USB is device only; the developer channel takes only a cable the shell itself trusted ([27](27-usb-typec.md) §4), while the USB controller belongs to `phone-bringup` then. Whether the image has `bluetoothctl` is **not checked** ([39](39-oneplus-6t.md) §14.7).
- **The build fills in what it lacks (not verified by a real image build)**: `make yocto-src` (which `yocto-build` and the others go through) regenerates a stale `phone-fw-go-mods.inc` itself and stops with the reason only when it cannot (no network, a Go older than `go.mod` asks for); `go mod tidy` no longer makes it stale. `make yocto-doctor` marks what the device image cannot do without (podman or docker, kas-container, rootless podman's subuid/subgid, Go, GCC 14, disk space and more) as MISS; `make doctor`'s exit status still covers the host targets only. bitbake's thread counts follow the machine (the smaller of the processors and memory ÷ 2 GiB, `YOCTO_JOBS=` overrides, [13](13-prototype.md)). None of this has run in a real image build yet; `yocto-bundle` and `yocto-ota-test` do not recheck the module list, and nothing runs `yocto-doctor` before a build.
- **Apps stuck at their memory limit**: established on QEMU: the group's file pages (the app's own program) are reclaimed and read back over and over, and the kernel is slow to declare OOM; the Shell now ends such an app by its memory pressure, as Android's lmkd does ([17](17-app-sandbox.md) §5.4). Still missing: the thresholds (half of 2 s) were set on QEMU, while the 6T's kernel has MGLRU on and much faster storage, and its numbers are **not tried on a phone** ([39](39-oneplus-6t.md) §14.12); an app writing files at its limit was not tested (the selftest's data directories are on tmpfs); web process groups are not watched (**not implemented**).

- There is no data on the CPU load and standby power of phone-paint's software rendering on a real phone ([37](37-motion.md) §2 has estimates; how to measure: [39](39-oneplus-6t.md) §14.3, §14.10).
- The 1 GB memory pressure test and the soak have run only on QEMU and the developer machine ([40](40-testing.md) §1).

## 9. Security and the ecosystem

- The app sandbox, the capability broker, store signatures and third-party listing are verified only on the developer machine and QEMU; what the sandbox lacks on the 6T's two kernels is what the compatibility report's `sandbox` field will say ([39](39-oneplus-6t.md) §14.12, **not tried on a phone**). The web view (WPE WebKit) is in an image of its own (`KASEXTRA=yocto/kas/web.yml`) and last ran on 2026-11-14: on QEMU's web image the four cases 「网页视图」 (Web view), 「网页表单」 (Web forms), 「浏览器」 (Browser) and 「内存紧张：先结束后台应用的网页」 (Memory pressure: background apps' pages ended first) passed, as did the low-memory stress test on the 1 GB web image, and `make web-selftest` passed on the developer machine. The night chain neither builds the web image nor runs `make web-selftest`: both images of the 2026-11-27 night chain r86 have no web view, and the four cases skip there. On the current code the web view is **not verified** on the developer machine or QEMU, and **not tried on a phone**.
- Trusted payment confirmation, device attestation and fingerprint payment need a TEE, which is **not implemented** ([31](31-lock-and-biometrics.md) §4, R15): phone-keystored stands in, with the device keys and the data salt on the data partition ([31](31-lock-and-biometrics.md) §11.3).
- Anyone can unlock the 6T's bootloader, and its persistent area is on userdata: the anti-theft lock cannot stop a reflash ([31](31-lock-and-biometrics.md) §11.5; a locked bootloader **depends on hardware**). The account server is **not deployed**, so neither the anti-theft lock nor parental remote management has run on a phone against a real server.
- Capability versions and platform level 2 (`media.list@2`, [22](22-developer-api.md) §2.3) are verified on the development machine only: no system of level 2 has been released, and no version has really been removed (removal has been gone through on test tables only); the store's catalogue does not filter by the manifest's `capabilities`, so only the phone's installer refuses; the system's own Music and Gallery apps still use version 1 of `media.list`, not pages (what happens when a library's answer goes past 4 MB is **not verified**); TypeScript apps cannot read the platform level (**not implemented**). The renderer protocol's negotiation at a major change has been gone through with a `phone.frame/0` made up in the tests only ([23](23-renderer-protocol.md) §2).

## 10. What else this real-phone run brought up (that computer's record)

- Nura edge's usr-merge (`usr/sbin -> bin`) clashed with apk-tools 3.0.10, and the `systemd` package failed to unpack; v26.06 (Alpine 3.24, apk 3.0.9) went through. At that time Nura's edge could not be built with pmbootstrap as it was (the record of that one run, **not checked here**).
- `fastboot fetch` is not supported by the 6T's bootloader (`Unable to get max-fetch-size`): there is no shortcut that only reads partitions without writing the phone; a temporary kernel has to be booted ([39](39-oneplus-6t.md) §9.1).
- With the dtbo erased, the bootloader refused TWRP 3.6.2 and LineageOS 22.2's `boot.img` (`Load Error`), whether because of the dtbo was not established. `test` and `flash` erase the dtbo first ([39](39-oneplus-6t.md) §5), so after them a recovery image with an Android kernel may need the stock dtbo written back first: one more reason the backup comes before anything is written to the phone.

## 11. The chroot kit's first run on a real phone (2026-11-21)

The agent on that computer ran `tools/phone-chroot/kario-phone.sh` on a 6T: Nura v26.06 with the console interface (systemd), kernel `7.1.0-rc1-sdm845`, SKU `oneplus-fajita-t9`. Which commit and which image were tested was not recorded that time; the kit now writes both into each run's `kit.txt` ([24](24-sku-framework.md) §6.2). What follows comes from that run's report and results directory, checked against the code; corrections and changes are marked as such.

- **The selftest passed 38 of 39 and stopped at the 39th case.** The selftest stops at its first failure: of the whole script's 227 cases only 39 ran, ending at "Sandbox: every layer in force behaves as expected", and the hundred and eighty-odd after it did not run. The compatibility report exercised only 33 of 134 capabilities (101 `never called`) **mainly because the run did not finish**; the missing modem, Wi-Fi, Bluetooth, NFC, camera and sensors account for only part of the skips (`require-*`). The report concluded from this that the chroot is no gate for the compatibility run; that has to wait for a whole run. The selftest can now go on after a failure (`--keep-going`, [40](40-testing.md) §2), which the kit's `selftest` and `pixel` use; `make selftest`, `make cts` and QEMU still stop at the first failure. Tried on the phone on 2026-11-22, at the end of this section.
- **"Listen on a TCP port" was allowed** (the sandbox self-check 10/11, 3 skipped). The report put it down to the missing Landlock; by the code this item belongs to the "no network" layer (`sandbox/selfcheck_linux.go`): an app without the network permission runs in a network namespace of its own, whose `lo` is down by default, so binding 127.0.0.1 fails; on Nura's kernel the bind succeeded, so `lo` was up in that namespace. Each app has a namespace of its own, so this is no hole between apps, but the sandbox behaves differently on different kernels. The cause was settled by the third run (below): `lo` is down, the bind goes through all the same, and the check was wrong. Landlock blocks TCP listening too (from ABI 4, `sandbox/landlock_linux.go`), and Nura's kernel has no Landlock (below).
- **The Shell did not start on a board without NFC.** phone-nfcd exits normally on a board without an NFC controller ("this board has no NFC controller"), yet `--services spawn` (the Shell starting its own services, in the chroot and on the developer machine) took that for a crash: it restarted it every second and kept waiting for its socket, until the Shell gave up; the other side worked around it with `"nfc": "sim"` in the chroot's `sku.json`. On the whole phone systemd starts phone-nfcd (`Restart=on-failure`), which never had this problem. Now a service that exits with status 0 before its socket appears has nothing to serve on this board: one log line, no restart, no wait; a non-zero exit is still a crash and restarted (`programs/shellcmd`). Without nfcd, apps' `nfc.*` answer "this phone has no NFC" at once (before: after 2 s, with a socket error), and Settings and Cards still say the phone has no NFC ([30](30-nfc.md) §8). Unit tests ✓ (they fail without this change), **not tried on a phone**; the chroot's `sku.json` needs no change any more.
- **Sound**: phone-audiod kept reporting `aplay: audio open error: Invalid argument` (`plughw:0,0`). The facts list no UCM verb: Nura had no `alsaucm`, so `setup` did not set `HiFi` and the card's path was not connected, and `setup` did not say so. Now without `alsaucm` it says phone-audiod cannot play and how to install it (`apk add alsa-utils` on Nura, postmarketOS, Alpine), and the facts say it too. Whether sound plays once it is installed is **not verified**.
- **Camera**: phone-mediad reported `/dev/video7: no streaming video capture`; the chroot has no usable camera (the 6T's camera is not done, [39](39-oneplus-6t.md) §11).
- **ModemManager was not running**: `setup`'s hint was OpenRC's `rc-service modemmanager start`, while Nura v26.06 runs systemd. The hint now follows the base's init system (`systemctl start ModemManager`). That time telephonyd's ModemManager backend had no counterpart.

- **"No response" to the power key after the idle suspend** (2026-11-23, the same 6T). About 40 s after `shell-start` (without `--stay-on`) the screen went off and the phone suspended; on the host the USB gadget **vanished entirely**: not even `18d1:d001` in `lsusb`, the `enx…` interface gone, no ping; the power key did nothing, only a long press restarted the phone.
  - **Two points corrected by reply 004 after report 003**:
    1. This looks more like "the power key **powered the phone off**" than "it would not wake": Kario's image had systemd-logind but never configured it, and its default `HandlePowerKey=poweroff` powers off at the power key, behind the Shell's back; the Hall sensor likewise (suspend when the cover closes). The whole-phone image now has `logind.conf.d/50-phone.conf`, with the power, suspend, hibernate and reboot keys, the lid switch and `IdleAction` all `ignore`, left to the Shell (verified on QEMU: without that configuration a press of the virt machine's power button powers it off at once).
    2. An `event_count` of 0 in `/sys/class/wakeup/wakeupN/event_count` says nothing: pm8941-pwrkey only makes its interrupt a wake-up interrupt and never reports an event to its own wake-up source; `/sys/class/wakeup/wakeupN/power/wakeup` does not exist for this driver at all, the platform device's `/sys/bus/platform/devices/c440000.spmi:pmic@0:pon@800:pwrkey/power/` is the one to read.
  - The power key and the RTC alarm come through the same SPMI arbiter interrupt; the same day the selftest's "suspend" case passed (woken by the RTC's relative alarm), so the power key should in principle wake it too. On the whole phone, capture it as reply 004 §4 step 7 says: `snap` before and after the suspend, `pm_wakeup_irq`, `/proc/interrupts`, dmesg, `journalctl -u phone-display`.

**What the facts show** (not in the report itself):

- Nura's kernel has only the LSMs `capability,bpf`, no Landlock: the sandbox's Landlock layer is not in force on this base. To be looked at again on Kario's own kernel ([39](39-oneplus-6t.md) §14.12).
- At boot `msm_dsi_phy … DSI PLL(0) lock failed`, with a call trace: the panel lights up, but relocking the DSI PLL is not reliable; whether this has to do with §13 is **not established**.
- `a630_sqe.fw` fails to load with error -40 (ELOOP, a symlink loop): the GPU firmware Nura packages is broken, the Adreno 630 does not come up on this base, and GPU composition (§2) cannot be tried in the chroot.
- The clock is at 1970: the Snapdragon's pm8xxx RTC is read-only in the mainline kernel, so without a network the phone starts at 1970, and the results directory was named `19700101-061440`. The kit's `setup` now sets the phone's clock from the build machine's when it is 10 minutes or more behind, and notes it in the run's `clock.txt` (**not tried on a phone**). On the whole phone this was not solved: the RTC cannot be written, so the clock was wrong until the network (NTP) or the modem gave the time; and Kario wrote the RTC's wake alarm as an absolute time, which put the alarm 57 years ahead (it writes `+N` now). The lesson: how the RTC behaves is a board parameter, and the code has to hold on the whole phone and in the chroot alike. Now ([28](28-battery.md) §6): the board configuration's `[rtc]` says whether the RTC can be set, whether the system time is kept as an offset from it, and how its wake alarm is written; the 6T's is read-only and keeps an offset: after the Shell has set the time (by hand, NITZ) and while NTP is synchronised, the offset is kept in the persistent area (`/var/lib/slots/rtc-offset.json`), at boot `phone-clock.service` sets the clock from the RTC plus the offset before the Shell and timesyncd start, and at shutdown it is kept once more; a settable RTC (QEMU's pl031) is written, as hwclock does. NITZ used to set the clock through timedated, but NITZ only comes while automatic time is on, when NTP is on and timedated refuses SetTime, so on the image the network's time never set the clock; it sets it directly now (a unit test, which fails without this change). In the chroot the clock is Nura's: the kit gives every command `PHONE_CLOCK=host`, the Shell also recognises a chroot by itself, and it sets no time, turns no NTP on or off and leaves the RTC alone. Unit tests ✓, **not tried on a phone** (what to check: [39](39-oneplus-6t.md) §14.10). Still missing: without an offset (a new phone, an RTC that lost its power) the clock still waits for the network; the kernel's ways (`allow-set-time` in the device tree, an offset cell in the SDAM) are not used, why in [39](39-oneplus-6t.md) §11.2; the two Snapdragon module boards' RTCs (PM6125) are probably read-only too and have no `[rtc]` yet, to be decided on the boards; in the chroot Settings still says the developer machine's words under "Set time automatically" ("Only the phone itself sets its clock").
- `81voltd.service` runs (an IMS data service over QMI/QRTR): postmarketOS already has a way to IMS, which the VoLTE research (§4, [39](39-oneplus-6t.md) §11.1) should look at.
- The kernel command line in the facts carried the serial number (`androidboot.serialno`): the facts now remove the serial number (on the command line and in the kernel's log) and the modem's IMEI, IMSI, ICCID and number before they are written, and `kario-phone.sh`'s own output shows only the serial's last two characters.

**The second run, the whole script with `--keep-going` (2026-11-22, report 002 §8.19–8.22 there)**: FAIL 104/207, nearly all of them after-effects.

- The first failures came from the base: no Landlock in Nura's kernel (the two sandbox cases), no per-app cgroups at the time (no `setfattr`). The start over after each failure worked, but the next case went on from whatever the failed one had left. "锁屏指纹：设置 › 安全 › 指纹…" (lock-screen fingerprints) failed because the phone has no fingerprint sensor the system can use (the board names none, so phone-keystored has none, and the selftest's `finger` had nothing to touch), after "锁屏 PIN 码" (lock-screen PIN) had set the lock-screen PIN; the case that removes the PIN never got to run, every start over booted locked, and some 90 cases after it were stuck at the PIN screen (`at …: the screen is system/sys.idle`, 「输入 PIN 码」). ### 12.3 Detached steps reported "gone" by mistake

`selftest` and `pixel` run detached on the phone, and `kario-phone.sh` asks every 20 s; sometimes it reported `ended without its exit code (gone)` while the test was still running. This is the scripts' fault, not Kario's at run time. The report does not show which cause it was; what the code showed, and what is changed:

- A detached step that died halfway (`die`, say the chroot not mounted) wrote no exit code, so status could only say gone. Now it writes one however it ends.
- Status, finding no `/run/kario-chroot/run`, started a new run itself and then looked for the exit code in the new results directory. Now status and log never start one.
- The pid noted was its launcher's `$!`; `setsid` forks once more when handed a process group's leader, and `$!` is then a process that ends at once. Now the step notes its own pid as it starts (one copy in `/run`, one in the results directory), and status also finds it by its command line.
- Under systemd, logind ending the SSH login (with `KillUserProcesses=yes`) kills what is left in the login's scope, `setsid` or not, while phone-shell, already moved into our own cgroup, keeps running: exactly "gone while the test runs". Now under systemd detached steps and `shell-start` go into a scope of their own (`systemd-run --scope`). Whether this was that time's cause is **not established**.
- When status says gone it now prints what the phone shows: the state directory, the `run` file, each pid file and whether its process is there, the results directories, the parent, process group, session and cgroup of the processes concerned, and logind's `KillUserProcesses`; a detached step also notes a hang-up (SIGHUP) or a stop (SIGTERM) it gets (and does not end for it). `kario-phone.sh` prints all that with the last lines of the step's output, ready to paste into the report.

## 13. A black screen and a crash dump after `shell-start` (2026-11-21, **not solved**)

The other side's record: after `shell-start`, Kario's boot animation appeared, then the screen went black and the power key did not light it again; afterwards the phone showed up on USB as `05c6:900e` (Qualcomm's crash dump mode, QUSB_BULK), which is common after a kernel hang and a watchdog reset. This was a hang at kernel level, not the scripts' fault; the cause is **not established**.

The guesses, most suspected first:

1. **Turning the screen off and on.** Compared with the selftest, what `shell-start` adds is the real panel and real hardware: phone-paint drives the panel directly, reads the power key and the touchscreen, turns the screen off on the timeout, sets the backlight, and key presses may vibrate. By default the Shell turns the screen off after 30 s idle: it fades the backlight to 0, then phone-paint turns the display controller's output off (`set_crtc` without a framebuffer) and the panel loses power; the power key sets the mode again and powers the panel up. This path has never run on the 6T; the 6T's panel is a DSI command-mode panel (`dsi_samsung_s6e3fc2x01_cmd_display`), and its DSI PLL already failed to lock once at boot (§11). The sequence fits: the picture appeared, then went black, the power key did not light it, and then the crash dump. The report's guess that the backlight, controlled by sde/dsi on its own, was turned off by fbcon and DRM fighting over the display controller is looked into under this one.
2. **phone-paint's mode setting itself** (`drmModeSetCrtc`, dumb buffers) is not verified on the 6T's msm DRM either.
3. **The USB gadget**: unlikely. The image's Shell has whole-phone support (the facts say so) and leaves USB alone while Nura's gadget holds the controller ([24](24-sku-framework.md) §6.2); if SSH still worked after `shell-start` until the hang, this is ruled out.
4. **`chvt 8` and console 1's getty**: they can confuse the keys and the display's state, but are unlikely to hang the kernel.

The steps to isolate it (no `shell-start` again until they have results):

1. Before each step, open another SSH session that streams `dmesg -w` to the computer: if the phone hangs, the last lines are kept.
2. Collect what the crash left: the results directory's `shell.log`, the services' logs under `/var/lib/kario-chroot/state/home/.local/state/phone-sim/run/`, `/sys/fs/pstore`, the previous boot's kernel log (`journalctl -b -1 -k`). What matters most are the last few dozen lines of `shell.log`: what the Shell and phone-paint did around turning the screen off (`screen off`, the backlight).
3. Without Kario, on Nura's console: dim the backlight, set it to 0, bring it back (`/sys/class/backlight/ae94000.dsi.0/brightness`), then turn the display controller's output off and on through DRM's fbdev (write 4, then 0, to `/sys/class/graphics/fb0/blank`: the same part of the same driver phone-paint's screen-off takes), five times if it comes back. A hang or `900e`: the problem is in the kernel's panel power-down and power-up, and Kario has to give this board an option to turn only the backlight off, not the display controller (**not implemented**). All fine: the problem is more likely in Kario, to be narrowed down with the switches below.
4. `shell-start`'s bring-up switches (added now): `--stay-on`, the Shell never turns the screen off (neither the timeout nor the power key turns it off or dims it, the backlight and the display controller stay on, so the phone never sleeps either); `--no-haptics`, no vibration. They hold for that one Shell and are not kept as settings (`kario-phone.sh --stay-on --no-haptics shell-start`, [39](39-oneplus-6t.md) §13.4). Unit tests ✓, **not tried on a phone**.

The report's suggestion to read the memory out of the crash dump first (`05c6:900e` with qdl or edl, which needs this phone's firehose loader) comes after the steps above.

## 15. Partitions: split them as Android does?

On the 6T, Android keeps what only this phone has in partitions of their own: `persist` (the fingerprint's and the sensors' calibration), `modemst1` and `modemst2` (the IMEI and the modem's other data), `fsg` and `fsc` (the modem's configuration), and `frp`, `apdp` and others. Kario writes only `dtbo_a/b`, `boot_a/b` and `userdata` (the whole root file system) and **leaves those partitions alone**: flashing Kario loses neither the IMEI nor the calibration; rmtfs still hands `modemst` and `fsg` to the modem, and Kario does not write them ([39](39-oneplus-6t.md) §3.5, §14.1). The report's proposal agreed with the design as it was (the four items below); the whole partition design settled since is [43](43-phone-partitions.md): the first three items stand, the 4th changed, the A/B layout putting the root file system into `system_a` and `system_b` (`vendor` still untouched), and why the persistent area stays on userdata is [43](43-phone-partitions.md) §3.4.

1. Android's `persist`, `modemst1/2`, `fsg` and `fsc` stay as they are; Kario does not write them.
2. Kario's own durable data is in `userdata`'s `/var/lib/phone`, with no `persist` of its own to compete with Android's; the persistent area `/var/lib/slots` is on `userdata` too (§3).
3. Fingerprint templates and sensor calibration, if they are ever taken over, are copied from Android's `persist` into `/var/lib/phone` and used read-only, the original partition unchanged (**not implemented**; neither fingerprint nor sensors are done on the 6T).
4. The A/B slots are for `boot` and `dtbo` only; `userdata` is the only root file system, with no `system_a/b` or `vendor_a/b` as on Android for now. When system updates are to roll back, dm-verity and A/B on `userdata` are what to look at ([39](39-oneplus-6t.md) §11), not Android's whole partition table.

## 16. The second test on a phone: what the whole firmware must bring (2026-11-23, report 003)

That run was in Nura's chroot; these are what the whole firmware (its own kernel and image) has to solve or find out first.

- **logind powering off at the power key and suspending at the cover** (solved, ✓ on QEMU): the image had systemd-logind but did not configure it, so by its defaults a press of the power key powered the phone off and the 6T's Hall sensor (`Hall effect sensor`, the magnetic cover) suspended it when closed, both behind the Shell's back. The image now has a logind drop-in setting every key and the lid to `ignore`; the selftest has a case pressing the real power key, and on QEMU without the drop-in that press powers the emulator off ([28](28-battery.md) §7).
- **The watchdog at a reboot** (changed, **not tried on a phone**): by default systemd sets `qcom_wdt` to 10 minutes for a reboot, the driver takes 32 seconds at most, and after the `EINVAL` systemd disarms the watchdog. The watchdog is now the board's `[watchdog]`, 30 seconds on the 6T ([24](24-sku-framework.md) §2, [28](28-battery.md) §7). The report put "the extra boot of 2 seconds after a reboot" down to it, but systemd 259 and 261 both disarm the watchdog after the `EINVAL` rather than leave it armed, and the extra boot came after `fastboot reboot` too: its cause is **not found**, and [39](39-oneplus-6t.md) §14.10 has the steps to compare.
- **Power-off** (the code read, **not tried on a phone**): the report said `pm_power_off` is NULL. The 6T's kernel has PSCI (a `psci` node, `CONFIG_ARM_PSCI_FW`), so `pm_power_off` is PSCI's `SYSTEM_OFF`, and pm8941-pwrkey sets the PMIC's PS_HOLD to shut down first; were it NULL, the kernel would halt, not restart. The USB cable was in that time, so the PMIC powering on again with a charger there is the likelier cause. To try on the 6T with the cable out and in ([39](39-oneplus-6t.md) §14.10).
- **The power key not waking the phone** (the code read, **not tried on a phone**): in the kernel the power key is a wake-up source by default (the driver's `device_init_wakeup`, `enable_irq_wake` at suspend), and its interrupt comes through the same SPMI arbiter interrupt as the RTC alarm, which does wake the phone; the Shell lights the screen at the power key after a wake (`TestPowerKeyAroundAWake`). That run's `event_count` of 0 says nothing: this driver never reports an event to its wake-up source. What was missing is evidence: `/sys/power/pm_wakeup_irq` exists only with `CONFIG_PM_SLEEP_DEBUG`, which Kario's kernels now get through `CONFIG_PM_DEBUG`, so the Shell's log says which interrupt woke the phone. The steps to capture it are in [39](39-oneplus-6t.md) §14.10; a screen that stays dark may also be the display not coming back after the resume (that report's §9.1 item 4), not the wake-up.
- **The speaker too loud in tests** (solved, in the kit, **not tried on a phone**): before `selftest` and `pixel` the kit turns the board's `[audio]` `quiet_controls` down to its `quiet_level` and sets them back after; `--quiet` takes another level or none ([24](24-sku-framework.md) §6.2). The 6T's are the `RX0 Digital` to `RX4 Digital` turned down by hand that time, and whether they are on the speaker's path is **not verified** ([39](39-oneplus-6t.md) §14.5).
- **facts removed the power key's key bitmap** (solved): in `== input`, `pm8941_pwrkey`'s `key` is `10000000000000`, and the scrub took a run of 14 or more digits for an identity such as an IMEI; the bitmaps' words are now written `0x…`. `facts` also notes the keys' wake-up sources (the devices' `power/wakeup*` and interrupt counts), `pm_wakeup_irq`, how the boot before ended (the watchdog's and power-off's journal lines and pstore's last line) and the sound card's mixer controls.

## 17. The first whole-firmware flash: every boot back in fastboot (2026-11-24, report 004)

The tester flashed the whole firmware built from `0befb13` (userdata layout) on a 6T: `dtbo_a/b` erased, `boot_a/b` and `userdata` written, yet every boot ended back in fastboot, and `fastboot boot` of that boot image too. Kario's kernel with Nura's initramfs came up, with the UFS and a sound userdata in sight. The same day the failed boot's ramoops and the command line ABL hands over were read on the phone, and the cause was found ([39](39-oneplus-6t.md) §1, §8.2).

- **A boot image without an initramfs, relying on ABL not to append its own `root=`** (changed, ✓ on QEMU, **not tried on a phone**): OnePlus's ABL always appends `root=PARTUUID=<Android's system partition>`, a `root=` already on the command line or not; the kernel took the last one, mounted Android's system and ran its init, which rebooted into the bootloader on its error. The userdata layout's boot image now carries phone-initramfs too, which mounts userdata by its partition name and leaves the command line's `root=` alone; `make yocto-userdata-test` simulates ABL's additions on QEMU as they were that time: through the initramfs it comes up, the former way goes for the Android partition. The lesson: a design resting on what closed firmware does (here, how OnePlus's ABL changes the command line) is either checked on the phone first or made not to depend on it; QEMU always used the initramfs, so "the kernel mounts the root itself" had never run anywhere.
- **After repeated failed boots ABL marked the slot unbootable, and `fastboot boot` answered `Load Error` from then on** (changed, **not tried on a phone**): only `fastboot set_active a` put it right. The flash script's `test`, `flash` and `restore` now make the current slot active every time (both layouts), tested against the simulated phone (`yocto/fajita-flash-test.py`); how to look into it is [39](39-oneplus-6t.md) §8.2 step 3.
- **With `root=` on the command line ABL gives no `androidboot.slot_suffix`**: `phone-abslot` then takes the slot marked active in the GPT for the one booted, and `phone-qcom-abslot` still marks the right one (kario-bsp's `tests/abslot-test.py` tests it with that time's command line, **not tried on a phone**). So that ABL adds no `skip_initramfs` or `ro init=/init`, the boot image's command line keeps its `root=`.
- **The USB link dropped during a 512M fastboot download** (changed): userdata's broke off at 471 MB, and `-S 64M` wrote it. The flash script now sends every image in pieces of `-S 64M` (`--chunk` changes it), [39](39-oneplus-6t.md) §6.
- **A backup without `boot_a`, `dtbo_a`, `dtbo_b` made the script refuse to flash** (changed): that phone had lost them when Nura was installed, and the tester changed the script. Now the phone's own five partitions must be there, and a missing `boot` or `dtbo` only gets a warning; before writing back, `restore` checks each file it would write, wants `--stock` for any missing or erased one, and writes not a byte otherwise ([39](39-oneplus-6t.md) §9, §9.1, `yocto/fajita-flash-test.py` ✓).

## 18. After the first whole-firmware boot: three problems of the kit and the selftest (2026-11-24, report 005)

The whole firmware of `d4856a3` booted on the 6T, and the full selftest passed 193 of 194 cases. The three below came up in that run and are fixed in this tree (the kernel refusing modules and the VPN (device) case are another matter).

- **`facts` hangs on `/sys/power/wakeup_count`, and `setup` never ends** (fixed, **not tried on a phone**): the kernel makes a read of this attribute wait for as long as a wake-up event is being handled, and a wake lock held is one; on the whole phone's bring-up image `phone-bringup-awake` holds one all the time. `setup` stopped after its wake lock sentence and `facts.txt` was empty (the tester dropped the attribute on the phone to go on). Nura holds no wake lock, so the chroot runs never met it. The kit now waits at most 2 seconds for each attribute, writes `<no answer in 2 s>` and kills the reader (the images' busybox has no `timeout`), and lists the wake-up sources in force; the other attributes and commands `facts` reads were checked and do not wait like this (`tools/phone_chroot_test.py` puts a FIFO in its place; the old script hangs there). The Shell's suspend reads the same attribute in a goroutine outside the event loop, so only that suspend waits ([39](39-oneplus-6t.md) §13.5).
- **After the selftest `phone-display` does not start again, black screen** (fixed; the old behaviour reproduced on QEMU, the new one **not verified**, **not tried on a phone**): the kit stops `phone-display` for the selftest, and `KillMode=process` left the input helper the renderer forks; the kernel had cleared its parent-death signal when it dropped privileges, it only noticed the renderer was gone when a new device appeared, and the two scan-out buffer mappings it inherited at the fork kept the display's DRM master in its hands, so the next renderer could not open the panel (`Permission denied`) and the service gave up after 5 restarts. The report's `Unit process 1004 (renderer)` is that helper (renderer and helper are both named `renderer`), not the selftest's renderer: the selftest runs in the kit's own scope and draws nothing on the panel. The helper is now forked before the graphics card is opened, renderer and helper set the parent-death signal again once their privileges are dropped, and the helper also ends when the renderer's end of its socket closes (`paint/`'s tests; the two that need root were run under `podman unshare`, and all fail on the old code); the two units that run phone-shell have `KillMode=mixed`, which `scripts/yocto-check.py` checks; the kit waits for what a stopped unit leaves to end, and after 10 seconds has systemd end it and says so ([11](11-platform-architecture.md) §14, [23](23-renderer-protocol.md) §5, [39](39-oneplus-6t.md) §13.5).
- **「沙箱里的 DNS」 (DNS in the sandbox) fails on the whole phone** (fixed): the run of only "kernel features + sandbox" had never started Hongyan, and `sandbox-read` gave Hongyan's data directory, not there yet, to its uid: the chown failed; in the full run Hongyan had started before, so it passed. The step now makes the directory as the app's first start does (`TestSandboxReadBeforeTheAppStarted`, failing on the old code; [40](40-testing.md) §6).

## 19. The first whole-phone boot: lockdown refused every kernel module (2026-11-24, report 005 §6.1)

The same 6T, flashed with the whole firmware of `d4856a3`, came up for the first time (the initramfs got round ABL's `root=`, §17), the selftest 193/194. The worst problem: the kernel loaded no module at all (`Lockdown: modprobe: unsigned module loading is restricted`), and with them went the RTC (`phone-clock` waited for `rtc0` in vain, the time went backwards across boots), the battery and the charger, the sound card and the modem (`tqftpserv`, `rmtfs`, `q6voiced` and the SIM session all failed, the Shell reached the panel a minute late); "VPN (device)" failed too, as `nft_ct` could not be loaded.

- **The cause** (found on the build machine, **seen**): the modules were signed, but with the key the kernel had generated for itself in another build directory's build: the shared sstate gave this one the other's packaged modules, while the boot image's kernel was this one's own, trusting only the key generated here. Packaging had not stripped the signatures, and lockdown is meant to be on ([39](39-oneplus-6t.md) §8.3).
- **The change** (made, built, verified on QEMU, **not tried on a phone**): modules are signed with the build directory's fixed key (made by `make ota-keys`, never in git), whose checksum is in the task signatures; the image build checks that every module goes with the boot image's kernel (the image of `d4856a3`: all 1094 do not); what the 6T always needs and has no firmware for is built into its kernel (qrtr, the PD mapper, the RTC, the fuel gauge, the charger); QEMU's kernel has module signatures and lockdown too, and its boot selftest runs `module-check.sh` first ([39](39-oneplus-6t.md) §8.3).
- **Two other boot errors**: `regulatory.db` missing (changed: it is in the initramfs now, where cfg80211 reads it while booting; QEMU lacked it the same way); the `-2` of `a630_sqe.fw` at boot is expected, msm loads it when the renderer opens the card, left as it is ([39](39-oneplus-6t.md) §8.1).
- The lesson: a kernel and its modules are a pair, but the build system caches them as two products; a constraint between the two (the same key) must either be part of the cache's key or be checked before an image goes out. Both are in place now.
