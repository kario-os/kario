# SKU framework: one hardware configuration produces one firmware package

> Status: **prototype ✓** (`sku/`, `tools/sku.py`, the `phone-sku` recipe, `make sku`). The three SKUs on the two mainline Snapdragon boards (Snapdragon 662, Snapdragon 460) all build firmware packages, **not yet run on real hardware**; the two QEMU SKUs, T9 keypad and QWERTY keyboard, pass the boot selftest (57 (internal document) verification baseline). The whole-phone board class (the panel and buttons are the phone's own, the keyboard is USB or Bluetooth: OnePlus 6 / 6T, Redmi Note 4X) and the kit that runs our root filesystem in a chroot on Nura (`tools/phone-chroot/`) are prototypes: unit tests and a dry run ✓; the chroot kit first ran on a OnePlus 6T on 2026-11-21 ([41](41-design-gaps.md) §11: the selftest stopped at its first failed case, and the phone hung after `shell-start`, **not established**), the whole phone is **not yet on a real phone** (§6, §7.4). Whether to replace a KaiOS phone from boot or interface with its base is in §7 (a survey, **not tried on a phone**); the key code table of a whole phone's own keypad (`[keymap]`, §7.4) and degrading on old kernels by what a probe finds (§7.5): unit tests ✓, **not tried on a phone**. Where the parts a vendor cannot open (firmware, kernel modules, user-space programs) live, how they get into an image and what they may talk to is in §8 (principles and boundaries; the private BSP layer repositories, the artefact store and more are **not implemented**). The board and SKU files of two open reference phones (QWERTY and T9, QCM6490) are in §9: `check` and `gen` pass, and the overlays merge into the Fairphone 5's mainline device tree ✓; there is no machine and no image, and the hardware is **not implemented**. The third reference phone is a flip (§9.10): the board, outer display, keypad and SKU files ✓, and the framework's new outer display (`outer_display`), lid switch (`[input] lid`) and OK-key fingerprint checks, `sku.json` fields and overlay ✓ (unit tests, the overlay merged into the Fairphone 5's tree); closing and opening the lid, the outer display and rendering to two panels are a design only, **not implemented**. For hardware selection see 61 (internal document); for keypads and displays see 52 (internal document).

## 0. Summary

- Each SKU has one configuration that only says "which board + which display + which keypad + memory tier + region + product layer"; the generator checks that these fit together and expands them into the Yocto configuration, device tree overlays and the runtime device description; `make sku SKU=<name>` builds the image and collects the firmware package, and every SKU in `sku/skus/` is also a target of its own, `make sku-<name>` (`make skus` lists them all). The binaries of the Shell, the services and the apps are identical on all SKUs.
- There is only one key code table (`sku/keys.toml`): the device tree's `linux,keymap` is generated from it, and tests check that phone-paint's evdev table knows every key code in it and that the key code values match the kernel headers.
- SKUs on the same board share the kernel and the root filesystem and differ only in the device tree overlay, `sku.json` and the product layer; later the overlay will be selected at boot by board ID, so that one image can cover a whole board family (**not implemented**).
- The parts a vendor cannot open are in no git repository: one private BSP layer per SoC holds recipes only, the closed files are fetched from an artefact store at build time by address and checksum and go into product images only; a closed user-space part is a separate, sandboxed process that talks only through Linux's standard interfaces or interfaces Kario defines, and the Shell and the system services link no closed library (§8, mostly **not implemented**).

## 2. What the generator checks

`tools/sku.py check` (part of `make test`) expands every SKU:

- QEMU boards only get QEMU displays and keypads, real boards only real ones; the keypad's form factor matches the SKU's form factor (`bar-t9` / `bar-qwerty`); the display resolution (with width and height swapped when mounted landscape) equals the form factor's dimensions; the memory tier is valid.
- Keypad matrix: every position is within the row and column range, every key appears only once, and all keys are in `keys.toml`; the required keys are all present (left and right soft keys, OK, Back, Clear, Call, End, arrow keys; 0–9 / * / # on the T9 keypad; the 26 letters, Space and Shift on the QWERTY keyboard). The Fn layer is only for letter keys in the matrix plus comma and period, each producing a single character, and a keypad with an Fn layer must have an Fn key. `ctrl` is `fn+<key>`, both keys on the matrix, and the matrix has no `ctrl` key (in `keys.toml` `ctrl` is `KEY_LEFTCTRL`).
- The kernel drivers for the display and keypad chips are in the kernel configuration fragment of the kario-qcom machine (when the board's machine is this layer's; another layer's machine, such as the reference phones' `kario-qcm6490`, has its kernel configuration in that layer and is not checked here).
- The notification light (`[leds] notify`), the backlight (`backlight`), the keyboard backlight (`keyboard_backlight`) and the light sensor (`light_sensor`) are valid device class names, and a multicolor light's `notify_color` is 0–255 per channel.
- Whether the board can be woken from suspend (`suspend`): real boards can by default, virtual ones (`virtual = true`, the emulator) cannot, and a board that cannot never suspends ([28](28-battery.md) §3).
- A power key of its own (`power_key = true`, a side key): there the end key is not also the power key; without one it is, the Nokia way ([18](18-nokia-form-factors.md)): held, it opens the power menu, and a press while an alarm rings snoozes it. Kario's T9 and QWERTY product boards (sm6115, sm4250) all say `power_key = true`; only QEMU leaves it out today. How to power off on each kind of phone: "How to power off" in [18](18-nokia-form-factors.md) §5.1.
- The NFC controller (`nfc`): `sim` (the emulator) or `nci:/dev/<node>`; left out, the board has no NFC and phone-nfcd exits ([30](30-nfc.md)).
- The fingerprint sensor (`fingerprint`) is `sim` or `none`: the emulator says `sim`, a real phone leaves it out until its sensor has a driver ([31](31-lock-and-biometrics.md)). A keypad with the sensor on its OK key says `fingerprint = "ok-key"` in the keypad file: an area sensor under the surface of the cap, reading a resting finger with no press; it is short for `fingerprint = { at = "ok-key", sensor = "area", read = "touch" }`, either form will do, and a sensor read by pressing (`read = "press"`), another kind of sensor or another place is refused. `tools/sku.py` requires an OK key in that keypad's matrix and writes `fingerprint_at = "ok-key"` to `sku.json`; the board's `fingerprint` is still the backend. By it phone-keystored powers the sensor only for the system's fingerprint prompts and never for unlocking ([31](31-lock-and-biometrics.md) §4.5); only the flip reference phone's keypad (`t9-fp-v1`, §9.10) says it, and the selftest moves the sensor there on a developer machine with `fingerprint-at ok-key`. On a real board, the board's `[[part]]` must have a part of kind `fingerprint`, and the keypad gives the sensor's size: its sensing area `fingerprint_mm` and the key cap `fingerprint_cap_mm` (width and height in millimetres, the area inside the cap; a keypad without the sensor cannot give them), not written to `sku.json`.
- The outer display (the SKU's `outer_display`, §9.10): other keys in the display file, and a `kind` or `color` not in the table, fail; an outer display names its `drm_driver` (by which the renderer tells the two panels apart) and has no touchscreen; QEMU's board takes only a virtual outer display, a real board only a real one. On a real board the main panel is on DSI and the outer one on SPI (`bus = "spi"`, `spi_max_hz` required, no `lanes`), the outer display's kernel option is in `SPI_PANELS` (only the Sharp memory LCD's `CONFIG_TINYDRM_SHARP_MEMORY` for now), and the board's `[wiring]` has `outer_spi` and what the panel needs (a memory LCD: `outer_vcom`, the PWM of its VCOM signal), all labels in the device tree; a memory LCD's display file gives `vcom_hz` (the VCOM rates its datasheet allows, `[lowest, highest]`), and `outer_vcom`'s period (the PWM's second cell, in ns) must fall in it; a DSI panel cannot give it. A whole phone (`class = "phone"`) has its outer display in the board's `[outer_display]`, not in the SKU; a board that is not a whole phone cannot have an `[outer_display]`.
- The lid switch (`[input] lid`): like the sound switch, an input device's name (at most 79 bytes, printable, no `|`), not one of the buttons and not the sound switch's name; other keys in `[input]` fail on every board. `[wiring] lid_gpio` (a label and its cells) needs `[input] lid`, the name of the overlay's gpio-keys node.
- The location receiver (`gnss`, `location/`): `modemmanager` (the modem's GPS through ModemManager; both Snapdragon boards say this, **not yet tried on a real device**), `nmea:/dev/<node>[@<baud>]` (the kernel GNSS subsystem's `/dev/gnssN` or a serial port, read as NMEA 0183), `fifo:<name>` (a named pipe in the Shell's run directory, which the Shell makes the first time an app asks for the location; QEMU says `fifo:gnss.nmea` and the selftest writes NMEA into it, so the emulator also runs the real parsing path; when running it interactively one can write it oneself, e.g. `cat track.nmea > /run/phone/gnss.nmea`), `sim` (a simulated receiver). Left out, the phone has no receiver and `location.get` returns `this phone has no location receiver`; the developer machine (no SKU id) uses the simulated receiver, and the table `kario run -sku` simulates leaves it out ([22](22-developer-api.md) §4.7).
- The modem's backend (`modem`, §8.8): one of the backends telephonyd is built with (`MODEMS`: `sim`, `modemmanager`, the same as `telephonyd/src/backend.cpp`'s, which `sku_test.py` checks), `sim` when left out; any other value is refused (otherwise telephonyd exits at boot and the phone has no telephony).
- The modem's IMS (`ims`, [39](39-oneplus-6t.md) §11.1): when the modem runs IMS (VoLTE) itself and wants the system to open its IMS bearers, who opens them; only `81voltd` so far (it takes the modem's requests through QMI's IMS data service over QRTR and opens the bearers through ModemManager), and the `IMS` table names the backend it needs, so it needs `modem = "modemmanager"`, and any other value is refused. `gen` writes `PHONE_IMS` into the kas overlay; a board whose Yocto machine is in this layer or a BSP layer given (§8.7.1) needs a machine that installs from `PHONE_IMS` (`oneplus-fajita.conf`: `81voltd` and `phone-qcom-pdc`, which activates the modem's configuration for the SIM), and a machine configuration naming `81voltd` outside `PHONE_IMS` (installing it whatever the SKU) is refused too: the board file is the one source. Left out, the modem needs none (or nobody opens them for it yet), and the image has no 81voltd. Only the OnePlus 6T has it so far (marked in `unverified`).
- The sound card (`[audio]`, [20](20-audio.md) §10): `pcm` (the PCM audiod plays media to, `plughw:<card>,<device>`) is required; `card` (`hw:<n>`), `verb` and `device` are UCM's set-up for media, `call_verb`, `earpiece`, `earpiece_pcm`, `call_speaker`, `call_speaker_pcm` and `call_mic` the call's. What needs what follows phone-audiod's flags (`card` needs `verb`, `call_verb` needs `earpiece`, the call's devices need `call_verb`), and the PCMs must be on `card`'s card. On a board whose Yocto machine is in this layer or a BSP layer given (§8.7.1), the machine's `PHONE_AUDIO_*` must be exactly `[audio]` (one more, one less or one different is refused): the board file is the one source, so the whole-phone image's audiod and the chroot use the same values. Left out, audiod finds the card itself (`--sink auto`). `quiet_controls` (simple mixer controls of `card`'s card) and `quiet_level` (`0%` to `100%`) come together and need `card`: the phone test kit turns those controls down to that level before `selftest` and `pixel` and sets them back to their values after the run (§6.2); they are the kit's alone (`phone.env`), not in `sku.json`, not machine variables.
- The hardware watchdog (`[watchdog]`, [28](28-battery.md) §7): `runtime`, `reboot` and `kexec` are systemd's `RuntimeWatchdogSec`, `RebootWatchdogSec` and `KExecWatchdogSec`, each `off`, `default` (the timeout the hardware has) or a time (`30s`, `2min`, `1h`); `max_timeout` is the longest timeout the board's watchdog driver takes, in seconds: with it, none of the three that is a time (those left out as systemd's defaults: runtime off, reboot 10 min, kexec off) may be longer, as the driver refuses such a timeout with `EINVAL` and systemd then disarms the watchdog. Other keys and other forms are refused. `gen` writes it as a systemd `system.conf` drop-in (`watchdog.conf`), a comment alone for a board without it (systemd's own). The OnePlus 6T and 6: `max_timeout = 32`, `reboot = "30s"` (marked `unverified`).
- The partition table (`[partitions]`, [43](43-phone-partitions.md) §2): `slots` is `abl` (the bootloader keeps the slot in the GPT attributes of `boot_a` and `boot_b`) or `state` (the initramfs keeps it in the state partition), `layout` is `userdata` or `ab` and one these partitions allow, each partition has a name and a role (`boot`, `dtbo`, `root`, `data`, `state`, `vbmeta`, `misc`, `efs`, `firmware`, `android`), no name repeats once the slot suffixes are added, the root is a pair; a partition on the never list (`NEVER`: the names of the partitions holding one phone's own data, the bootloader's state and the firmware, on Qualcomm, Unisoc and MediaTek phones) cannot have a role that is written or erased, and an `efs` one must be on the list; a board with `slots = "state"` (QEMU) has the partitions of the A/B disk and RAUC's slots. For a board with a partition table `gen` writes `PHONE_SLOT_KEEPER`, `PHONE_ROOT_SLOTS` and `PHONE_BOOT_SLOTS` into the kas overlay, and `partitions.conf` for the initramfs; `sku.py partitions <board> [layout]` prints the table the flash script reads; `phone.env` carries `KARIO_PARTITIONS`.
- The real-time clock (`[rtc]`, `hal/rtc`, [28](28-battery.md) §6): `read_only` (it cannot be set, and setting the time does not write it; `false` by default), `offset` (the system time is kept as an offset from this read-only RTC, and the clock set from both at boot; `false` by default, only with `read_only = true`), `alarm` (the wake alarm: `relative` writes `+N`, the default, right on any RTC; `absolute` writes the wake time, never on a read-only RTC); other keys and values that are not booleans are refused. The OnePlus 6T is read-only and keeps an offset (the 6 and the Redmi Note 4X follow it, marked in `unverified`), QEMU's pl031 can be set; a board with `[rtc]` has the whole `rtc` in `sku.json` (the defaults filled in), one without has none (the Shell takes it as settable with `+N` alarms).
- USB host (`[usb]`, `hal/usbhost`, [27](27-usb-typec.md) §2.1): `host` (whether the USB-C port can be a USB host, for keyboards, mice and USB sticks; `false` by default, and the Shell leaves the host side alone), `vbus_ma` (the most the port gives on VBUS as a host, the budget for allowing devices; 500 by default, 100 to 3000), `controller` (only the buses under this USB controller, a device tree node name such as `a600000.usb`; without it every bus but dummy_hcd's, so what the board wires inside to another controller needs no allowing by the user); the other two without `host = true`, and other keys, are refused. QEMU has it (xHCI), the Snapdragon reference board and the flip have it, marked in `unverified`, the OnePlus 6T not yet (its kernel cannot be a host, [39](39-oneplus-6t.md)); a board with `host = true` has `usb` in `sku.json` (the defaults filled in, an empty `controller` left out), which the Shell reads into `SKU.USB` and checks.
- The touchscreen (a display's `touchscreen`, since 2026-11-25): on a virtual display only QEMU's `virtio-multitouch-pci`, which `gen` adds to the kas overlay's `QB_GRAPHICS` (`qemu-480x640` names it, so `qemu-t9` and `qemu-t9-1g` have a touchscreen and the QWERTY `qemu-640x480` has none); on a board whose Yocto machine is in this layer or a BSP layer given (§8.7.1), the touchscreen's driver must be built into that machine's kernel (`TOUCHSCREENS`: `syna,rmi4-i2c` is `CONFIG_RMI4_CORE`, `CONFIG_RMI4_I2C`, `CONFIG_RMI4_F12`, each `=y` in the configuration fragments its kernel recipe lists: built in, it is there from the start and needs no signed module loaded under lockdown); a touchscreen not in the table, a driver made a module or left out are refused; a whole phone whose machine is in neither this layer nor a BSP layer given (the chroot, on Nura's kernel) is not checked. A display with a touchscreen gives `touch` in `sku.json`.
- When kernel sources are available (the copy in the Yocto work directory, or `PHONE_KERNEL_SRC`), it collects labels by following the `#include`s of the board dts and checks that every label the wiring references exists. The regulator on the OnePlus Nord N100 is called `vreg_l9a`, while on the Snapdragon 662 board it is `pm6125_l9a`, so a mistake is reported at generation time. The DSI host's output endpoint is `<panel_dsi>_out` by default (the Snapdragon 662's `mdss_dsi0_out`); SC7280's DSI host is `mdss_dsi` but its endpoint `mdss_dsi0_out`, and such a board says `panel_dsi_out` (the reference phones).
- Wake pins (since 2026-11-26, with kernel sources): every GPIO that is to wake the phone must be one the SoC can be woken by from deep sleep. In deep sleep the SoC's GPIO controller (the TLMM) is powered down, and a pin's interrupt reaches the CPU only through the always-on wake controller (the PDC on SC7280 and SDM845, the MPM on SM6115), which sees only the pins in the pinctrl driver's wake map (`.wakeirq_map`, such as `sc7280_pdc_map` in `drivers/pinctrl/qcom/pinctrl-sc7280.c`). What is checked: on a board that is not a whole phone, the `[wiring]` lines the overlay gives `wakeup-source` (`WAKE_WIRING`: the keypad's interrupt `keypad_irq`, the lid switch's `lid_gpio`); on every board, the keys with `wakeup-source` (or the old `gpio-key,wakeup`) under the gpio-keys nodes `[input]` names in the board's own device tree (`buttons`, `sound_switch`, `lid`, found by the node's `label`). The pin's controller is found by its label (`tlmm`), the controller's driver in `drivers/pinctrl` by its `compatible`, and the wake map by the `.data` the driver gives that compatible; a controller whose driver has no wake map (a PMIC's GPIOs, which wake through the PMIC's own interrupt) is not checked. A pin not in the map is refused, naming the pin, the map and what would not wake the phone (`board qcm6490-ref [wiring] keypad_irq: GPIO 64 of tlmm is not in sc7280_pdc_map (drivers/pinctrl/qcom/pinctrl-sc7280.c), ...: a key press would not wake the phone`). Without kernel sources it is skipped, as the label checks are, and `sku.py check` says so (`no kernel tree (PHONE_KERNEL_SRC): device tree labels, part drivers and wake GPIOs not checked`). The OnePlus 6T is a whole phone with all its wake pins in its own device tree: the power key the board names, `pm8941_pwrkey`, is no gpio-keys (it wakes through the PMIC), the volume keys are on the PMIC's GPIOs and have no `wakeup-source`, and the sound switch (a node only 7.1-rc1 has, GPIO 126, 52 and 24) is no wake source (126 not being in `sdm845_pdc_map` does not matter: gpio-keys reads the switch's position on resume); so the 6T has no pin to check today, and `tools/sku_test.py` shows on a fake tree that they would be checked if they were wake sources. The keypad interrupts of the two SM6115 and SM4250 product boards (GPIO 33 and 35) are in `sm6115_mpm_map`, but mainline's `sm6115.dtsi` (6.18 and 7.1-rc1) has no MPM node and no `wakeup-parent` on its TLMM, so whether a key press wakes them from deep sleep is **not verified**.
- The hardware list (`[[part]]`, §9): each part has a name, a kind (`kind`, one or more of `PART_KINDS`), a bus (`bus`, one of `PART_BUSES`) and a driver (`driver`: one or more files of the kernel source, `drivers/<path>.c` or `sound/<path>.c`, or `"none"`: mainline has no driver); one with a driver has a device tree `compatible`, a `"none"` one has none; a camera, and only a camera, says which way it faces (`facing`: `front`, `back`); other keys are refused. With kernel sources at hand, each driver file must exist and one of them contain the compatible in quotes (the driver's match table). The list is for whoever builds the board and for the docs: it is not in `sku.json` nor in the table `kario run -sku` simulates; `sku.py parts <board>` prints it one part a line (kind, bus, compatible, driver, name).
- Whole-phone boards (`class = "phone"`, §7.4): the SKU names neither display nor keypad (they are the phone's own) and must name its form factor (`device`); the panel less its dark rows (`inset`, as many at the top as at the bottom) must face the same way as the form factor (a landscape form factor says `rotate = 90`, which a panel with dark rows cannot); `scale` is 1–8, and one logical pixel measures 0.15–0.36 mm on the panel (the 2.8-inch 480×640 target at 2× has 0.178 mm; the floor is a 2.4-inch 240×320 panel at 1×, the ceiling twice the target); the physical size has the resolution's aspect ratio within 5% (swapped millimetres would otherwise slip past the previous rule); there is a `compatible`; every entry in `unverified` is one of the board's values; a key code table (`[keymap]`) has codes 1–767, key names from `keys.toml` and every key the form factor needs (§7.4), and a board that is no whole phone cannot have one. For a whole phone whose board names a Yocto machine (`machine`: the OnePlus 6T's `oneplus-fajita`, [39](39-oneplus-6t.md)), `gen` writes `sku.json` and the kas overlay (the machine, the SKU's name; the kernel's own device tree `dtb`, no overlay); a whole phone has no firmware package, and `package` (that is, `make sku-<name>`) fails, pointing to the board's flash script (`flash`). Whole phones without a Yocto machine yet: `gen` and `package` fail at once, pointing to the chroot kit (§6.2); `sku.py files <SKU> <dir>` writes only `sku.json`, the product layer and the kit's `phone.env`; the table `kario run -sku` simulates leaves whole phones out (they are test phones, not something apps are written for).
- `tools/sku_test.py` additionally checks that the form factor table matches `shell/device.go`, that phone-paint knows every key code, and that the key code values match `/usr/include/linux/input-event-codes.h`; and the whole-phone rules (each with an example that breaks it); the touchscreen's rules (QEMU's device, the 6T's driver built in, refused as a module or left out); `[audio]`'s rules, that it equals the 6T machine's `PHONE_AUDIO_*` and a change to either side is refused, and that `sku.json`, `phone.env` and `shell.SKU` carry its values; the rules of `[[part]]` (each with an example that breaks it, the driver files and compatibles checked on a throwaway kernel tree), `panel_dsi_out`, that another layer's machine is not held to the kernel configuration, what the reference phones' three SKUs expand to, and that §9 of this document names every part's and every display's compatible (in both languages); the outer display, lid switch and OK-key fingerprint rules (one wrong example each), QEMU's outer display as a second virtio-gpu; the wake pins' rules (on a fake kernel tree: the candybars' old GPIO 64 and a lid on 64 are refused, the flip and the 6T pass, the 6T's sound switch is refused were it a wake source, the wake map is found by the driver's `.data` and one it cannot tell apart is refused, and the check is skipped without a kernel tree; the lines the overlay gives `wakeup-source` are those `WAKE_WIRING` lists; with the real kernel tree every SKU passes and GPIO 64 is refused). `tools/phone_chroot_test.py` dry-runs the chroot kit: every step prints its plan on the build machine, the dry run changes nothing, and Nura's modem stack is not among what it stops; `setup` sets the sound card up as the board says and `teardown` takes down what `setup` noted; both scripts are shellcheck-clean.

## 5. Not done yet

- Real hardware: the boot method (Qualcomm's ABL needs a boot.img), the flashing package format, and the firmware of the various subsystems (signed firmware for the GPU, baseband and audio DSP has to come from the device maker) are all **not implemented**; the firmware package is currently the kernel, device tree, root filesystem and manifest.
- Selecting the overlay at boot by board ID (one image covering a board family) is **not implemented**.
- UNISOC T610: the mainline kernel has no display, baseband or USB support, so it has to wait for the vendor BSP (61 (internal document) §2.1); no SKU for now.
- The vendor's closed parts: the private BSP layer repositories, the artefact store, `LICENSE_FLAGS` on closed recipes and a sandbox policy for vendor processes are all **not implemented** (§8.6).
- The reference phones (§9): the `kario-qcm6490` machine, the carrier board, its device tree and an image are **not implemented**, and `make sku-ref-…` stops where bitbake finds no such machine; on Kario's side the cameras, headphones, proximity sensor, accelerometer and NFC are **not implemented** (§9.3).
- The flip (§9.10): the renderer reads `lid` (phone-paint reports whether the lid is shut, [23](23-renderer-protocol.md) §2) and does not use `outer` yet; the Shell turns the inner display off and on by the lid and does not count the keypad's keys while it is shut (§9.10.8, unit tests and the developer machine's selftest ✓, **not tried on a phone**), and uses `lid` and `outer` for suspend (the outer display's minute wake, one periodic wake with the lid closed, [28](28-battery.md) §3, unit tests ✓, **not tried on a phone**); "close to end call", "open to answer", the outer display's content and rendering to two panels are **not implemented**, the OK key's USB fingerprint sensor has no backend, and QR scanning has no viewfinder or decoder; the outer display's overlay node and the lid's gpio-keys have only been merged into the Fairphone 5's tree.

### 6.1 The three phones in detail

**OnePlus 6 / 6T** (mainline 6.18.54 sources checked on 2026-11-17):
- Panel: the 6 has a 6.28-inch 1080×2280, the 6T a 6.41-inch 1080×2340, both Samsung DSI command-mode AMOLEDs. In 6.18, `panel-samsung-sofef00` only takes the 6's `samsung,sofef00` (its mode says 68 × 145 mm); no driver in 6.18 takes the `samsung,s6e3fc2x01` the 6T's device tree names (in android-mainline the 6T's tree already says `samsung,s6e3fc2x01-ams641rw`); Nura's kernel drives it. So for a later BSP, only the 6's panel lights up on mainline 6.18; the 6T needs another kernel or a driver. The backlight is registered by the panel driver (DCS brightness 0–1023) under the DSI device's name, `ae94000.dsi.0`; it is the system's only backlight, so `hal/backlight` finds it by itself.
- Keys: power is the PMIC's `pm8941_pwrkey`, volume up and down gpio-keys "Volume keys"; there is also a Hall sensor (SW_LID, for flip covers), which has no keys and which the renderer leaves alone. OnePlus's three-position alert slider is an input device in the mainline device tree (`alert-slider` in `sdm845-oneplus-common.dtsi`, on both the 6 and the 6T): gpio-keys "Alert slider", three GPIOs (126, 52, 24) each reporting EV_ABS `ABS_SND_PROFILE`, top, middle and bottom being `SND_PROFILE_SILENT` (0), `SND_PROFILE_VIBRATE` (1) and `SND_PROFILE_RING` (2); it has no keys. The 6T's board names it in `[input] sound_switch`, and the renderer reads its position, which sets the sound mode (§7.4, [20](20-audio.md) §4.1, **not tried on a phone**; checked on 2026-11-26 in the 7.1-rc1 sources and the dtb built for the 6T).
- Sound: mainline drives the 6's loudspeaker amplifier (MAX98927) but not the 6T's (TFA9894), whose link the device tree deletes: on mainline the 6T has only the earpiece and headphones; whether Nura's kernel adds it is **unverified**.
- Notification light: the 6 has the PMI8998 LPG's RGB LED (the multicolor LED class device `rgb:status`), the 6T none.
- The battery is the bq27411 fuel gauge (the first power supply of type Battery); the vibrator is PMI8998's haptics driver, in Nura's kernel (force feedback on an input device), not in mainline 6.18.
- The sensors (light, proximity) sit behind the SLPI DSP, which Nura reads through hexagonrpcd and libssc, not IIO: `hal/sensor` does not see them, so automatic brightness and turning the screen off at the ear in calls cannot be tested on these two.
- NFC: the chip is the NXP PN553 in the NQ330. When its device tree was first submitted in 2023 the author said it recognised card types but could not read them in full, and withdrew it; sdm845-next's commit message of 2025-11 still says "there isn't upstream driver, just ugly hacks"; in 2026-04 the device tree node went into mainline (`nxp-nci-i2c`). That driver sits on the kernel's NFC subsystem (netlink, the neard path), without a raw NCI node phone-nfcd could open (`nci:/dev/…`), so the boards leave `nfc` out; Nura lists it as unusable too.
- USB: the phone does not power OTG devices, so a keyboard needs a powered adapter (the community says, **unverified**); a Bluetooth keyboard first.

**Redmi Note 4X** (kernel sources checked on 2026-11-12 and 11-17): mainline 6.18 has its device tree, `msm8953-xiaomi-mido.dts`, but its screen there is only the framebuffer the boot loader leaves (simple-framebuffer, 1080×1920), with no DSI panel driver: it displays, but cannot turn the panel off or change the brightness, so screen-off power saving cannot be tested on mainline; the panel drivers (five vendors: BOE ILI9885, EBBG R63350, NT35532, OTM1911, Tianma NT35596) and the PMI8950 backlight are in the msm8953-mainline kernel Nura uses. The notification light is the AW2013's red, green and blue LEDs (`red:indicator` and so on, which the driver blinks by itself), and the only keys are volume up (GPIO) and power and volume down (the PMIC's `pm8941_pwrkey`, `pm8941_resin`). The touchscreen is FocalTech in the mainline device tree (`edt,edt-ft5406`); some phones have a Goodix GT917D. The mainline device tree fixes the USB controller in device mode (no OTG) and has no fuel gauge or vibrator; on the msm8953 kernel, OTG needs g_serial off or the device plugged in before boot (the community says). Mobile data relies on the IPA 2 driver (`CONFIG_QCOM_IPA2_LITE`, merged into Nura's msm8953 kernel in 2024), which nobody has confirmed on the 4X. So this phone mainly tests CPU, memory and rendering times, and calls and SMS.

### 6.2 The phone test kit: the chroot and the whole phone (`tools/phone-chroot/`, prototype, the chroot run on a 6T)

It lives in `tools/`, not `yocto/`: it builds nothing, uses a built image, and runs on the build machine, directing the phone over SSH. It tests a whole phone's SKU two ways, with the same steps and the same results: **the chroot** (the default: the phone runs Nura, and our image's root file system runs in a chroot on its kernel, panel, modem and sound) and **the whole phone** (`--whole`: the phone flashed with Kario, its own kernel and image, [39](39-oneplus-6t.md) §6). Two POSIX sh scripts, shellcheck-clean: `kario-phone.sh` (build machine: `--sku` picks the whole phone's SKU; it pushes the kit, and in the chroot the image, runs the steps on the phone, fetches the results and restores the phone, step by step) and `on-phone.sh` (runs as root on the phone, busybox's sh will do: what each step really does, on either path, `KARIO_TARGET=chroot` or `whole`). What the two paths share is one implementation: the run's results directory, `kit.txt`, the facts and their scrubbing, the detached steps and their polling, `collect`. `--dry-run` prints on the build machine what each step would do here and on the phone, without connecting or changing anything; on the phone, `on-phone.sh --dry-run <step>` prints what it would do given the phone as it is. `--only REGEXP` runs only the cases of `selftest` and `pixel` whose names match (phone-shell's `--only`, reaching the phone as one word whatever it holds). The media cases of `selftest` and `pixel` really play through the speaker: before the run the kit turns the board's `[audio]` `quiet_controls` down to its `quiet_level` (the 6T: `RX0 Digital` to `RX4 Digital` at 15%; whether they reach the speaker is **not verified**, [39](39-oneplus-6t.md) §14.10), notes each control's value in the state directory and sets it back after the run, and `teardown` sets back what a run stopped half-way left; `--quiet 30%` takes another level, `--quiet off` leaves the mixer alone; a board without them gets nothing (unit tests ✓, **not tried on a phone**).

**The image** (the chroot): by default the board's own machine's (the board file's `machine`, `KARIO_MACHINE` in the kit's `phone.env`; for the 6T `phone-image-oneplus-fajita.rootfs…`), the newest under `$WORK`; `--image` names a file, `--machine` another machine. The kit tells what a file holds by its bytes, not its name, and takes three forms: the ext4 (`.ext4`), its zstd (`.ext4.zst`) and the Android sparse form the flash writes (`.ext4.sparse`, unpacked on the way by `tools/phone-chroot/unsparse.py`: the 6T needs one userdata image for both paths); anything else is refused before anything reaches the phone, saying what it takes (a `.wic` is a whole disk, a tar is not loop-mounted), and an image that stops unpacking half-way leaves nothing on the phone. The board's own image is what the flashed phone runs: for the 6T Mesa with freedreno (the GPU path), alsaucm with the sound card's UCM profile (`alsa-ucm-conf-sdm845`), the Qualcomm services and the firmware, tuned for the Snapdragon 845. A generic machine's image (the machines of boards that are not whole phones, `KARIO_GENERIC_MACHINES`: qemuarm64, kario-qcom; ARMv8.0 + CRC, which runs on the A75, A55 and A53) still runs, its binaries being the same, and the kit says what it lacks (on the QEMU image the renderer finds no GPU driver, `msm: driver missing`, and Nura's alsaucm sets the sound card up); another board's image is refused (`--force` goes on). The kit replaces only `sku.json` and the product layer with the SKU's (`tools/sku.py files`). The phone loop-mounts the ext4 rather than unpacking a tar: owners, extended attributes (file capabilities) and device nodes stay as built, the build machine needs no root, and the chroot's root is still a mount point (the app sandbox's pivot_root needs that). Everything on the phone is under `/var/lib/kario-chroot/`: the image, its mount point, our state (`/var/lib/phone` and `/root`, bound into the chroot, so the image itself is hardly written) and each run's results. **Images built before whole-phone support cannot be used**: their Shell takes the USB controller and puts a drop-everything rule on `usb0`, cutting off Nura's USB network (that is, SSH), and it ignores `scale`; the kit refuses an image without it (`--force` goes on regardless, over Wi-Fi). So first `make yocto-build` from this tree.

**What differs in the chroot, and what the kit does about it** (each run's `facts.txt` lists it under `== chroot: what is Nura's and what is the image's`; **not tried on a phone**):

- The image's systemd units do not run: the Shell starts its own services (`--services spawn`), and Nura runs the modem stack (ModemManager, rmtfs, pd-mapper, tqftpserv, q6voiced) and Bluetooth; the image's copies of these are never started, they would compete with Nura's.
- The kernel and its modules are Nura's: it loads the modules it needs itself, from its own `/lib/modules`; the image's are for Kario's kernel and signed with its key, which Nura's kernel would refuse. No code of ours runs `modprobe`.
- The firmware is Nura's: what the kernel loads after `setup` it takes from Nura's `/lib/firmware`, unless `--firmware image`, which points the kernel's firmware path (`/sys/module/firmware_class/parameters/path`) at the image's `/lib/firmware` first (the GPU's `a630_sqe.fw`, which Nura v26.06 fails to load, [41](41-design-gaps.md)); `teardown` puts the path it found back.
- The sound card: its values are the board's `[audio]` in `sku.json`, the ones the flashed phone's audiod has from its unit (`tools/sku.py check` keeps the two equal). The Shell's own audiod sets the card up with the image's alsaucm, as the flashed phone's does (`programs/shellcmd`'s `privateAudio`: the media set-up always; the call set-ups with the SKU's own modem, so in `shell-start` but not in the selftest, whose calls are the simulated baseband's; unit test ✓, which fails with the old code). `setup` does it itself, with Nura's alsaucm, only for an image without alsaucm (the QEMU one); a board without `[audio]` gets no set-up (it used to get card 0's `HiFi`, a guess of the kit's, not the board's).

**The whole phone** (`--whole`, **not tried on a phone**): the phone runs what `yocto/fajita-flash.sh flash` wrote ([39](39-oneplus-6t.md) §6; `test` boots it once from RAM, and Kario comes up only where `flash` wrote userdata before). The kit reaches it over phone-bringup's USB network (`dbg0`, `root@172.16.42.1`, the development image's dropbear with root's empty password: images with `PHONE_BRINGUP = "1"`, the machine's default; [39](39-oneplus-6t.md) §7). That is Nura's address too, so its host keys are kept apart (`~/.ssh/known_hosts.kario-whole`); the image makes a new host key at its first boot, so after each flash `ssh-keygen -R 172.16.42.1 -f ~/.ssh/known_hosts.kario-whole`. `push` sends the kit only, into `/var/lib/kario-test/`; `check` wants Kario built for this SKU (the phone's own `sku.json`); `setup` sets the clock, notes `kit.txt` and the facts and changes nothing else; `selftest`, `pixel` and `bench` stop the Shell on the panel and the audio service for the step (`phone-display.service`, `phone-audiod.socket` and `.service`: the boot selftest, `phone.selftest=1`, runs without them, the selftest's own audiod needing the sound card), run it in a systemd scope delegated to it (`-p Delegate=yes`: the Shell gives each app a group of its own, as under the boot selftest's unit) and start them again after; `teardown` ends the kit's steps and starts what is still stopped, `--purge` also removes `/var/lib/kario-test`. The results are the chroot's, in the same place. What is not possible there yet, and why:

- The developer link (developer mode and a trusted cable: `10.71.0.1`, what `kario device` logs into, [27](27-usb-typec.md) §4) carries `push`, `setup`, `facts` and `collect`, not `selftest`, `pixel` or `bench`: their own Shell takes the USB controller and sets the cable's link up as an untrusted computer's, cutting the session off (stopping `phone-display` ends the trust as well); `on-phone.sh` refuses them over it. An image without phone-bringup has only that link and Wi-Fi.
- The selftest's Wi-Fi and Bluetooth cases are written for the emulator's simulated radios: on the phone they act on its own radios through iwd and BlueZ, which is **not verified** and may drop a Wi-Fi link; the USB cases are skipped (phone-bringup holds the controller). Leave them out with `--only` ([39](39-oneplus-6t.md) §14.1).
- The suspend case cannot pass while `phone-bringup-awake` holds its wake lock (`setup` says so); without the lock the USB link sleeps with the phone, which the polling outlasts.
- `shell-start` and `shell-stop` are the chroot's: the whole phone's Shell is `phone-display.service`, its environment set by a drop-in ([39](39-oneplus-6t.md) §14.1); `mem` measures the running system's processes (Kario's units and the apps' scopes).
- `kit.txt` names the commit the image was built from only for images built with `share/phone/source.txt` (`tools/sku.py gen` writes it); an older image says "not recorded".
- One phone does not hold both paths at once: Nura and Kario each take the whole of userdata, so going from one to the other flashes it again (the chroot's `/var/lib/kario-chroot` goes with Nura); what `collect` fetched stays on the computer.

When `status` finds neither an exit code nor the step running it says `gone` with what the phone shows (the state directory, each pid file and whether its process is there, the results, the processes concerned with their sessions and cgroups, logind's `KillUserProcesses`), and `kario-phone.sh` prints that with the end of the step's output ([41](41-design-gaps.md) §12.3). `on-phone.sh scrub` takes the serial number, the modem's identities and hardware addresses out of any file, as `facts` does. `on-phone.sh partitions` lists the phone's partitions, each one's size in bytes and the role the board file gives it, then what the board file names and the phone does not have (a section of `facts` too; the A/B layout needs it before it goes on a phone, [43](43-phone-partitions.md) §3.2).

**What Nura keeps, and how our services reach it** (the chroot): Nura's D-Bus, ModemManager, rmtfs, pd-mapper and tqftpserv (the modem stack), NetworkManager (SSH over the USB network or Wi-Fi), bluetoothd and sshd keep running. Our telephonyd is ModemManager's client, and the ModemManager on the system bus is Nura's (the board's own image has one too, which does not run here), so Nura's cannot be stopped: with `/run` bound into the chroot our processes are on Nura's system bus (`/run/dbus/system_bus_socket`), and telephonyd calls ModemManager as root. With no systemd in the chroot, the Shell starts its services itself (`--services spawn`): run interactively, the telephonyd it starts takes the image SKU's modem backend (`modemmanager`) and its audiod the board's call set-ups, while the selftest and scripts keep the simulated baseband (they call numbers of the simulated network; `privateModem` and `privateAudio` in `programs/shellcmd`, unit tests ✓). Wi-Fi belongs to Nura's NetworkManager and our iwd does not run, so Settings' Wi-Fi does not work in the chroot; mobile data: telephonyd still connects the bearer through ModemManager with the APN database's APN, but the chroot has no systemd-networkd, so the Shell does not configure the cellular interface's addresses, and Nura's NetworkManager may connect the modem's bearer and configure the interface itself; whether the two get in each other's way is **unverified**; Settings' Bluetooth talks to Nura's bluetoothd (**unverified**). When the Shell finds the USB controller held by another gadget (Nura's USB network, or phone-bringup's on the whole phone), it leaves USB alone: no gadget of its own, no USB firewall (`shell/usb.go`, unit test ✓, which fails without this).

1. Buy the phones: a OnePlus 6T (or 6); a Redmi Note 4X, Qualcomm version (mido, original screen; 3 GB or 4 GB of RAM both do).

3. 4. Enable SSH: add the build machine's key for development boards (`kario-board-test`) to root's `authorized_keys` on the phone, `PermitRootLogin prohibit-password`; or use the default user with `--become doas` (doas without a password).
5. Network: plug the USB cable into the build machine; on Nura's USB network the phone is `172.16.42.1` (the kit's default); then join Wi-Fi with nmcli on Nura: when the keyboard takes the USB port, or USB has to come out to measure standby current, use Wi-Fi with `--phone root@<address>`.

7. Build: the board's own image from this tree (the 6T: `make yocto-build WORK=$HOME/yocto/fajita-work KASFILE=yocto/kas/phone-fajita.yml SKU=oneplus-fajita-t9`, [39](39-oneplus-6t.md) §4), which both the chroot and the whole phone take; the QEMU one (`make yocto-build`) for comparing; for the web view benchmark also `make yocto-web-build`.

## 7. KaiOS phones: replace from boot, or interface with the system base (survey of 2026-11)

With a KaiOS phone in hand there are two paths: **(a) interface with the base**: keep the vendor's boot loader, kernel and vendor partition, replace only Gecko and Gaia with our user space, and reach the hardware through Android's HALs (this is what Ubuntu Touch and Sailfish OS do on Android phones with Halium / libhybris); **(b) replace from boot**: the mainline kernel plus our whole system, the same as on the Snapdragon 662 / 460 (R16). What follows comes from public sources and the local mainline kernel sources (6.18); **not tried on a KaiOS phone**.

**Conclusion: take (b), only on models that already have a mainline port; do not do (a).** By Nura's device list, no KaiOS phone has a maintained mainline port today (reason 4), so we do not work on KaiOS phones for now, and real-phone testing uses the phones of §6 first. Reasons:
1. **(a) does not spare flashing the boot partition either**. Halium has to change the kernel configuration for systemd, rebuild the kernel and flash its own boot image; the boot loader of KaiOS phones is locked and accepts only a boot image signed by the vendor. The ways to write boot (EDL, unlocking, `fastboot oem sudo` on the 2780 Flip) are the same for both paths: both have to take the hardest step, and after it (a) still carries a layer of vendor user space.
2. **The vendor kernels are too old for our system to start on**. The Nokia 8110 4G on KaiOS 2.5 has a 3.10 kernel; the systemd 259 in our image needs 5.4 or later (its README calls this the "minimum baseline"), and Landlock, the cgroup freezer and memfd, which the sandbox, the sound rings and the media surfaces use, are all newer than 3.10 too (§7.5).
3. **There is no ready Halium**. Halium only has versions for Android 7.1 and 9–13, and since 20.04 new Ubuntu Touch ports need 9.0 or later; the base of KaiOS 2.5 is Android 6. libhybris also first needs Android's bionic and init rebuilt with its patches, and KaiOS phones have no LineageOS device tree to build from.
4. **Mainline was ported to these phones, but nobody maintains the ports now**. By Nura's device list ([Devices](https://wiki.nura.eco/wiki/Devices), checked 2026-11-14), the ports of the Nokia 8110 4G, 6300 4G, 8000 4G and 2780 Flip are all "archived", no longer supported; the only KaiOS phone still in a supported category is the 2720 Flip, in "downstream", on the vendor's 3.10.49 kernel with very few features; the generic package `qcom-msm8909` (Snapdragon 210) is in "testing", and whether it boots these Nokias is **unverified**. When they were ported in 2022, keys, Wi-Fi, Bluetooth, charging, the display and the backlight worked, and the modem came up through QRTR and rmtfs; the device trees are still in the community msm8916-mainline kernel, and the 2780 Flip's is in the msm89x7-mainline kernel (§7.2). telephonyd's ModemManager backend and phone-paint's DRM and evdev plug straight into this path, but taking (b) on a KaiOS phone means carrying on these archived ports ourselves.
5. **Security updates**. On (a) the kernel and the HALs stay at the vendor's last release, and our system update ([25](25-system-update.md)) can update only user space; (b) follows mainline and the long-term support releases.

(a) stays only as a fallback: when one kind of hardware never gets a mainline driver, add a vendor backend in the service that manages it (the approach of [11](11-platform-architecture.md) §16), rather than putting the whole system on the vendor base.

Whichever path, KaiOS phones are test phones only: they all have 512 MB of memory, half our smallest memory tier, with no room for the web view (§7.2); their partition tables have no A/B either, so our system update needs the partitions rearranged (§7.3).

### 7.1 How KaiOS is built

KaiOS was forked from Firefox OS (B2G) and has three layers: Gaia is the UI and the apps, written in HTML / JS; Gecko is the web runtime and doubles as the device interface; Gonk is the base: the Linux kernel plus Android's HALs, the vendor's binary libraries and daemons such as rild. There is no ART, so Android apps cannot run; Gecko itself is the "system_server" and calls Android's HALs directly.

| Layer | KaiOS 2.5 | KaiOS 3.x | KaiOS 4.0 |
|----|-----------|-----------|-----------|
| Runtime | Gecko 48 | Gecko 84 | Gecko 123 |
| Android base of Gonk | Android 6.0: vendor libraries and the system in the same system partition | Android 10: vendor libraries in a vendor partition of their own (Treble) | Android 14 |
| Kernel | 3.10 (Nokia 8110 4G) | 4.x (**unverified**) | The GKI kernels Android 14 supports are 5.10–6.1; which one this generation of phones uses is **unverified** |
| Modem | The rild socket, the Firefox OS way (that KaiOS 2.5 kept it as it was is **unverified**) | Gecko's `nsRilWorker` calls `android.hardware.radio@1.1::IRadio` over HIDL | From Android 13 it calls `IRadio` 1.6 instead (in the same file) |
| Display | Firefox OS's `GonkDisplay`: framebuffer or hwcomposer (**unverified**) | `GonkDisplay`: framebuffer (fbdev), DRM, or hwcomposer plus gralloc, chosen per model | Same as left |
| Keys | Since Firefox OS, Gecko has carried a copy of Android's InputReader (**unverified**) | Gecko carries a copy of Android's EventHub, InputReader and InputDispatcher, reading evdev | Same as left |
| First phone | Nokia 8110 4G | Nokia 2760 Flip | TCL Flip 4 (Qualcomm SM4635, 5G) |

So keys are the same on both paths: the vendor kernels report the keypad as evdev too.

Two families had mainline ports, but Nura maintains none of these phones' ports now (only the 2720 Flip has a downstream port on the vendor kernel). MSM8905 / 8909 (the five Nokias and the CAT B35): the community kernel has the phones' device trees, the modem was brought up back in 2022, and EDL is a way to flash them; they are 32-bit Cortex-A7 chips, while our image is arm64 only today (ARMv8.0 tuning, §3), and the seccomp filters of the sandbox and the renderer know only the aarch64 and x86_64 architecture numbers, so an armv7 build comes first (§7.4). The Nokia 2780 Flip with QM215 has 64-bit A53 cores, so our arm64 image runs as it is and fastboot is enough to flash it, but nobody has yet written down which parts of its mainline port work (**unverified**). The screens are 2.4–2.8-inch 240×320, exactly the logical size of the `bar-t9` form factor (480×640 drawn at 2×, `shell/device.go`), so drawn at 1× they get the same layout.

**Memory is the hard limit**: these four Nokias (8110 4G, 6300 4G, 8000 4G, 2780 Flip) all have only 512 MB of memory and 4 GB of storage. Our smallest memory tier is 1 GB (`MEMORY` in `tools/sku.py` accepts only 1g–4g); on QEMU the 23 processes take 234.0 MB, about 190 MB without the simulated cloud services (§4); the web process's memory limit is at least 384 MB, because WPE needs about 250 MB for an ordinary page (`shell/webview.go`). Going by these numbers, a 512 MB phone has no room for the web view and can run only semantic-UI apps (an estimate, **unverified**). So they serve only as test phones, for the modem, keys, display, suspend and current draw; a 512 MB memory tier is needed, with web nodes turned off on it (**not implemented**).

**Why the scale is 4.5**: our layouts are designed for 480×640 at 2×, that is 240 × 320 logical pixels. All three phones are 1080 wide at about 400 ppi: 1080 / 4.5 = 240, so across the screen everything is as on the 9-key bar phone (the same columns, the same line breaks, documents' 32 columns, the main menu's 3 columns), only with more rows down it (484 on the 6T without its dark rows, 427 on the 4X, 320 on the target). A logical pixel is 0.28 mm on these panels and 0.178 mm on the target's 2.8-inch one: body text (11 logical pixels) is 3.1 mm high, about 1.6 times the target's, close to Android's largest font size, readable at arm's length. The three others weighed: 2× in the middle (what the renderer did already) uses 44% of the panel's width, with a logical pixel of 0.126 mm, body text of 1.4 mm and the smallest text of 1.1 mm: too small; 3× (Android's xxhdpi class) gives 360 × 780 logical pixels and text the target's size (0.189 mm), but a different layout across, which cannot show the target's layout; 4× has crisper lines but is 270 wide, again another layout. The generator wants a logical pixel of 0.15–0.36 mm (§2), which 2× on these phones fails. For the cost of drawing the target's pixel count (the renderer's work as on the target), use `--device bar-t9`: 480×640 at 2× in the middle. A developer machine can show the whole phone too: `phone-shell --device bar-t9:1080x2180@4.5` (`DeviceByID` takes `@<scale>`).

**Two decisions**:
- The volume keys do not double as up and down: the power key's short press has to stay screen on / off (standby current depends on it), and up and down without OK and Back operate nothing; in a call the volume keys set the earpiece volume; Bluetooth keyboards drop off after a short idle and reconnect at the next press, so keys would change meaning as the keyboard comes and goes, which makes testing more confusing. Interactive tests use a keyboard; the unattended part (selftest, benchmark, standby) goes over SSH and needs no keys.
- The touchscreen is a second input, only turned into keys (since 2026-11-25; before, it was not read): every gesture is a key that exists already (the focus and OK, a soft key, an arrow, Back), so keyboard navigation is still the only way and its faults still show; on the 6T one can page, open and go back without a Bluetooth keyboard. Typing and PINs still need the keyboard, with the keypad locked touches are ignored but for an incoming call or an alarm, in a call at the ear (with no proximity sensor) but for one ringing in, until a volume key or a finger held for a second wakes them, and a touch does not light the screen ([10](10-keyboard-interaction-model.md) §2.1).

**A whole phone's own keypad (`[keymap]`, unit tests ✓, **not tried on a phone**)**: the mapping above assumes a HID keyboard, with only the power and volume keys on the phone itself. A KaiOS-class phone's keys are a matrix keypad in its device tree, with codes the board chooses (the soft keys reporting `KEY_MENU` and `KEY_BACK`, the green key `KEY_SEND`, the red key `KEY_POWER`, the digits the number row's `KEY_1`…), which phone-paint's table does not know. The board file's `[keymap]` says which key of `keys.toml` each code the kernel reports (in decimal) is, listing every key of the phone's keypad, those whose code is already ours too:

```toml
[keymap]
139 = "soft-left"   # KEY_MENU
158 = "soft-right"  # KEY_BACK
231 = "call"        # KEY_SEND
116 = "end"         # KEY_POWER: the red key is the power key too (no power_key)
352 = "ok"          # KEY_OK
2 = "1"             # KEY_1
```

- `tools/sku.py` checks: only a whole phone may have one (a keypad module's codes come from its matrix); a code is a decimal number 1–767 (`KEY_MAX`); a key name is in `keys.toml`'s `[keys]` (which gained `power`, `KEY_POWER`, for it); every key the form factor needs is in the table (as for keypad modules: the soft keys, OK, back, clear, call, end, the arrows, plus 0–9, `*` and `#` on the 9-key pad, 26 letters, space and Shift on the full keyboard); `unverified` may mark one of its codes (`keymap.139`). With a table, the whole phone's `sku.json` has `keypad = "builtin"` and the `keymap` in code order; `tools/sku_test.py` has a wrong example for each rule.
- The Shell checks it again when it reads `sku.json` (a bad table keeps phone-shell from starting, as an unknown form factor does) and turns it into "the code reported → that key's code here" (the codes of `keys.toml`, `keyCodes` in `shell/sku.go`; `tools/sku_test.py` checks the two agree), which goes to the renderer as `device`'s `keymap` in the handshake ([23](23-renderer-protocol.md) §1); with `--device` choosing another form factor it goes too (the phone's keys do not change with how it draws). Unit tests: `TestBoardKeymap`, `TestKeymapHandshake`.
- phone-paint looks every key up in the table first and reads it as our code from then on: the 9-key pad's long press, the soft keys, the end key that is the power key too all work as with a keypad module (`a_boards_keymap_reads_its_keys_as_ours` in `kms.rs`). Only the codes in the table change, all others are read as they are; a USB or Bluetooth keyboard plugged in goes through the same table, so it lists only the codes of this phone's keypad. An input device with any key of the table counts as a keyboard: a matrix keypad may lack Enter, and before only devices with Enter, a power key or volume keys did (`a_matrix_keypad_is_a_keyboard_by_its_keymap` in `input.rs`).
- phone-gui does not read the table (**not implemented**). No whole-phone board has a `[keymap]` yet: there is no KaiOS phone's board (§7.7); its codes are to be copied from that phone's device tree and confirmed on the phone.

**How the Shell uses the new fields**: `sku.json` has `width`, `height` and `scale` more (`shell.SKU`). `SKUDevice` replaces the form factor's own size and scale with the panel's, documents' columns follow the logical width (`Device.WithScale`); the handshake hands it to the renderer, and phone-paint draws so, in the panel's middle when the panel is bigger (the dark rows). Unit tests: `TestWholePhoneSKU`, `TestWholePhoneHandshake` (the size in the handshake, the main menu's 3 columns, a web page's area at 4.5×), and one more case for `letterbox` in `kms.rs`. Two more changes are for the chroot (§6.2): the Shell leaves alone a USB controller another gadget holds (`TestUSBLeavesAForeignGadgetAlone`), and run interactively, the telephonyd it starts itself takes the SKU's modem backend (`TestPrivateTelephonyFollowsTheSKU`).

**What whole phones still lack** (all **not implemented**):
- audiod switching UCM: a phone's sound card needs its mixer set per use (playback, call, headphones). The OnePlus 6T's whole-phone image has it ([20](20-audio.md) §10, **not tried on a phone**); other phones need their `--ucm-*` in their device configuration; the QEMU image the chroot uses has no alsaucm and passes none of those flags, so there Nura's alsaucm still sets `HiFi` and `Speaker` up first, as the board's `[audio]` says (the audiod the Shell starts itself plays to `[audio]`'s `pcm`), and call audio needs a manual switch to "Voice Call".
- The proximity sensor (screen off at the ear in calls): the OnePlus's sits behind the SLPI, and `hal/sensor` has only the light sensor, read through IIO only.
- Dark rows only as many at the top as at the bottom: a phone with a notch but no rounded corners below loses rows at the bottom for nothing; the renderer would have to take an offset (a protocol field). A panel with dark rows cannot be turned either (a landscape form factor with `rotate`).
- The 512 MB tier (§7.2).
- A Yocto machine and BSP for whole phones (kernel, boot, firmware partitions).

| `MemAvailable` in `/proc/meminfo` | 3.14 or later | The low-memory killer ([17](17-app-sandbox.md) §5.1) | Missing (unless the vendor backported it, **unverified**) | Yes | Estimated as MemFree + Buffers + Cached − Shmem (it used to count as 0: the system was always "low" and ended background apps one after another) |

**Degrading (implemented: unit tests ✓; **not tried** on an old kernel)**: the Shell probes once at start (`sandbox/probe_linux.go`, `shell/cgroup.go`, `shell/kernel.go`) instead of guessing from the kernel version: Landlock is asked its ABI version, seccomp tried with calls that install no filter, cgroups looked at for the files in the delegated group, and `CLONE_INTO_CGROUP` tried for real by starting an sh that does nothing in the Shell's own group. The result goes into the Shell's log (one line in all, one line each for what is missing and what is done another way: `kernel: missing …`, `kernel: fallback …`), the diagnostic dump (`kernel` in `phone-shell --dump`) and the compatibility report (the `sandbox` field: the kernel version, `missing` protections and `fallback`s, each with why; the report's signature covers it, [22](22-developer-api.md) §11). No protection that is not there is claimed: without the memory controller, say, the log's cgroup line names no memory limit. Each item is one of three:

| Handling | Which | Why |
|----------|-------|-----|
| No app starts (as when the Shell runs as root and finds no `phone-sandbox`: the Shell runs, and opening an app says why) | seccomp filters, no_new_privs, the namespaces apps get (mount, pid, ipc, uts, net); only when the Shell runs as root (the device); web processes and the USB sharing helper do not start either | These layers have no stand-in: without them an app can debug other processes, change its view of the file system, gain privileges through a setuid program. System apps are handled the same: they read untrusted input too (the browser, SMS) |
| Runs, and says so (the report's `missing`) | `landlock`, `landlock-tcp`, `landlock-scope`, `cgroups` (no per-app groups), `cgroup-freezer`, `cgroup-memory`, `cgroup-pids`, `cgroup-cpu`, `memfd-seal`; on a developer machine also `uid` (the Shell is not root: apps run as its user, without namespaces) | One layer is short, the others hold (own uid, namespaces, seccomp); the user can use the phone, and certifiers and payment services see what is short and may refuse, as they may on seeing `unlocked` |
| Done another way, nothing lost, only recorded (the report's `fallback`) | `seccomp-tsync`, `seccomp-kill-process`, `clone-into-cgroup`, `cgroup-kill`, `psi`, `psi-trigger`, `pidfd`, `mem-available` | The same protection, the old way; `seccomp-tsync` costs USB file sharing (its helper does not start); `psi` costs an app stuck at its memory limit waiting for the kernel's OOM kill ([17](17-app-sandbox.md) §5.4), `psi-trigger` finding it up to 5 s later with the screen off |

- The compatibility test still decides PASS / FAIL by cases and capabilities: a device short of protections can still PASS, and the certifier decides by the report's `sandbox.missing`; `phone-cts-verify` lists them item by item. An older report without the field verifies as it did; an older `phone-cts-verify` drops the field when reading a new report, the digest no longer matches and it fails: use this version.
- Unlike the earlier proposal, memfd seals are under "says so", not "no app starts": we never stand in with unsealed memory, so without them sound, video, the camera and web pages just do not work, apps never get unsealed shared memory, and refusing apps would gain nothing.
- The device attestation (`attest` called by apps, used by the wallet and payments) does not carry the missing layers yet (**not implemented**): the signed message holds only the boot state (`verified-boot:…` / `unlocked`), one more item takes a new message version, and the relying parties (the wallet compares against `unlocked`) must change with it; only the signed compatibility report carries them now. Settings does not show them either (**not implemented**); the sandbox self-check still marks the checks of a missing layer "skipped".
- The systemd threshold cannot be lowered: either replace init (the Shell's fd store and app scopes depend on systemd and would need rewriting) or take path (b).
- Verification: unit tests on fake cgroupfs trees (4.19, 5.1 (PSI without triggers), 5.4, 5.10, 6.18 and a vendor kernel with the memory controller on v1) and with old kernels' system call errors injected (ENOSYS, EINVAL, EOPNOTSUPP), each fixed behaviour first confirmed to fail before the change (`TestFreezeWithoutFreezer`, `TestStartWithoutCloneInto`, `TestKillWithoutCgroupKill`, `TestMeminfoWithoutMemAvailable`, `TestSeccompWithoutTSync`); the developer machine's own 4.18 kernel has no Landlock, pidfd or `clone3`, and the probes run for real there. QEMU's mainline kernel lacks nothing, which the selftest case "内核特性" (kernel features) checks (QEMU ✓, 2026-11-27 night chain r86). On a real 4.x or 5.x vendor kernel **not tried on a phone**.

### 7.6 The commercial side

- **KaiOS Technologies**: the system is free for handset makers, and the company earns from service fees (FOTA, for example), advertising (KaiAds), the app store and search (public statements from 2018 and 2019; whether this still holds is **unverified**). Neither path uses Gecko, Gaia or KaiStore, so neither needs its license; what (a) uses is the BSP under Gonk, which belongs to the chip maker and the handset maker. What working with it could bring is its experience integrating BSPs on low-end chips and passing carrier certification; its store and advertising compete with our store and push, and the room for cooperation is **unverified**.
- **The vendor binaries** (HALs, rild, the modem's and Wi-Fi's firmware): licensed by the chip maker to the handset maker, with no right for third parties to redistribute them (UBports' porting guide also treats them as "blobs" to be taken from the device). - **The community's ways of flashing** (EDL loaders, unlock packages) are fit only for development and enthusiast builds, not as a product channel. Products go on our own hardware (61 (internal document), R16); the use of KaiOS phones is as cheap test phones, like the Redmi Note 4X in §6.

## 8. Vendor parts that cannot be opened

> Status: principles and boundaries. What exists: the 6T's firmware is downloaded at build time and is not in git; there is no GPLv3 in the images; the licence check of the platform's dependencies; the kernel's lockdown and the image check of module signatures; the sandbox of apps and helpers. **Not implemented**: one private BSP layer repository per SoC, the artefact store for closed files, `LICENSE_FLAGS` on closed recipes, a sandbox policy for vendor processes, an SBOM and the GPL sources handed out with product images (§8.6). How the repositories are reorganized (where SKUs live, how external drivers are built, the BSP contract, several repositories and reproducibility, GPLv3, which repositories there are in the end) is §8.7, decided design, **not implemented**. The baseband splits into the portable core, a Modem backend and SoC glue (§8.8); the MediaTek design is in §8.9 (**not implemented**). What the repositories are called, who can see them, how a vendor's files are reviewed and how the move is carried out is in internal document 60.

Once Kario is on a production phone, the chip maker and the design house will always have parts they give no source for: the firmware of the coprocessors (modem, DSPs, GPU, Wi-Fi), possibly kernel modules, and user-space programs and libraries (VoLTE's IMS, camera tuning, sensor fusion). This section settles where they live, how they get into an image, what they may talk to and how their licences are kept apart.

### 8.1 Principles

- **No closed binary in any git repository** (this one and the internal one alike). Closed files live outside the repositories and are fetched at build time by address and checksum: bitbake checks the `SRC_URI`'s sha256 (a git source is a pinned commit) and stops on a mismatch. Today's examples: the 6T's firmware `firmware-oneplus-sdm845` (`LICENSE = "CLOSED"`) is fetched at build time from sdm845-mainline's public git repository, pinned at commit 3e31a0c3; the 6T kernel's base configuration comes from Nura's pmaports by address and `sha256sum` ([39](39-oneplus-6t.md) §10). The firmware the phone uses comes from that package; Kario does not read the phone's own firmware partitions ([43](43-phone-partitions.md) §1); the backups of the phone's partitions are outside the repository too ([39](39-oneplus-6t.md) §9.1). In production, the files a vendor delivers go into an access-controlled artefact store (**not implemented**). `scripts/binary-check.py` (`make test`, and `make publish` before it pushes) stops programs that would be pushed (ELF, Mach-O, PE: a `.ko` is ELF too) and files larger than 512 KiB; a small firmware file in none of these formats gets past it (**not implemented**).
- **Closed files come in three kinds**, which may go into different images:

| Kind | Example | Images it may go into |
|----|------|-----------|
| With a licence text that allows redistribution | linux-firmware's Adreno 630 and WCN3990 files | Open and product images, with the licence text |
| Obtained from a vendor under contract | A product board's modem and DSP firmware, the vendor's user-space programs (none yet) | Product images only; the files are in the private BSP layer and the artefact store (§8.2), the right to redistribute them is written into the purchase contract |
| No licence granted to us | The 6T's `firmware-oneplus-sdm845`: taken from a community repository | Only images for the owner's own testing, never published or passed on ([39](39-oneplus-6t.md) §10) |

- **Where a vendor grants no right to redistribute**, there is one more way: the firmware stays in the firmware partitions the factory writes, the image carries none of it, and at boot the system mounts that partition read-only and loads from there (the approach of §7.6). Each board's firmware then follows the factory, and a system update cannot replace it; **not implemented**.
- **Open interface, implementation behind it**: a closed part is a thing of its own (firmware in a coprocessor, or a separate process), and Kario talks to it only through Linux's standard interfaces or interfaces Kario defines (§8.4); the Shell, the system services and the renderer never link a closed library.
- **A missing closed part takes away only its own function**: degrading by what the SKU says is there, as today: a board without `nfc` makes phone-nfcd exit; `fingerprint = "none"` means no fingerprint; the 6T has no user space for its sensors (§8.3), so there is no automatic brightness and no screen-off at the ear, and everything else works.
- **The open image carries no part obtained under contract**: this repository alone builds a complete open image. On QEMU nothing is missing; on the mainline boards (kario-qcom) the things that need their subsystem's firmware (modem, GPU, Wi-Fi, DSPs) do not work (§5); the 6T's image carries firmware of the third kind and is for the owner's own testing only.

### 8.2 Three layers

| Layer | Where | What it holds | Status |
|----|------|-------|------|
| The public repository kario | This repository | Interfaces: `hal/`, `svc/`, telephonyd's `Modem` backends, the renderer protocol; the SKU framework (`sku/`, `tools/sku.py`); the Yocto layer `meta-phone`: open recipes, Kario's own glue (`phone-qcom`), kernel configuration fragments (`phone-*.cfg`), `phone-kernel.inc` (lockdown and module signing); recipes that fetch only closed files a third party already publishes (the 6T's firmware, for the owner's own testing) | ✓ |
| One private BSP layer repository per SoC / vendor | Internal (60 (internal document)) | One Yocto layer of recipes only: the machine, the vendor kernel's recipe (its source repository and commit, `require`-ing this repository's `phone-kernel.inc`), one recipe per closed part (its address in the artefact store and sha256, the vendor's licence text and its `LIC_FILES_CHKSUM`); no binaries | **Not implemented** |
| The product configuration | The internal repository's kas files | Choose the BSP layer per SKU and pin its commit; product images are built only there | Product kas files ✓ (QEMU, the 6T trial); choosing a BSP layer **not implemented** |

Board files are in this repository (`sku/boards/`), and a board's `machine` may be a machine of another layer: when `tools/sku.py` finds no file for that machine in this layer or the BSP layers given (`KARIO_BSP_LAYERS`, §8.7.1), it skips the checks that need the machine's file (the touchscreen's driver built into the kernel, `[audio]` equal to `PHONE_AUDIO_*`, §2), as for QEMU's machine. The 6T's Qualcomm parts are such layers now, only public ones (kario-bsp, §8.7.6); a machine this repository's kas files build is not skipped: without its layers `sku.py check` and `gen` fail.

### 8.3 The kernel

- **The kernel and the modules linked into it are GPL-2.0**: every module must come with its source, a requirement written into the purchase contract (**not implemented**: there is no purchase contract yet). We hand out the source of the kernels we ship, as the GPL requires; the 6T's kernel is sdm845-mainline's public tag plus Nura's configuration and this repository's fragments, all public already.
- **The good case: an open driver, with the closed part in the coprocessor's firmware**. On the 6T: the modem (remoteproc, QRTR; the user-space rmtfs and tqftpserv are BSD) and `modem.mbn`; Wi-Fi (ath10k) and `wlanmdsp.mbn`; the GPU (msm, freedreno) and `a630_zap.mbn`; video (venus) and `venus.mbn`; the audio DSP and `adsp.mbn`. The sensors are built the same way: their closed part is in the SLPI's `slpi.mbn` (the firmware package has it), but hexagonrpcd, which talks to it from user space, is GPL-3.0 and not in Kario, so the 6T has no sensors (§6.1, [39](39-oneplus-6t.md) §11): the open half has to pass our licence gates too (§8.5).
- **A binary-only module is only a last resort**. It takes one kernel version (`vermagic` and the symbols' CRCs); to load under lockdown it must be signed with our module key: every `.ko` in the image must be signed with the build's key, or the image check `modules-signed` fails ([39](39-oneplus-6t.md) §8.3, ✓). The key is never given to the vendor: the vendor delivers unsigned modules and we sign them at build time (a recipe that signs a prebuilt `.ko` is **not implemented**; this repository's kernels sign their own modules when the kernel is installed). For every kernel update (long-term-support point releases included) the vendor has to issue the module again, so the kernel's security updates wait for the vendor; a module under a proprietary licence also taints the kernel (`P`) and cannot use the symbols exported to GPL modules only. This is a risk to weigh when choosing the chip (61 (internal document)).
- The module signing key is today each build directory's own development key (`yocto/ota-keys.sh`); a product module key in an HSM (the kernel's `CONFIG_MODULE_SIG_KEY` also takes a `pkcs11:` address) is **not implemented**. What a signature is and how modules from outside are signed: §8.7.2.

### 8.4 Closed user-space parts

Examples: VoLTE's IMS (Qualcomm's is in the modem firmware, [39](39-oneplus-6t.md) §11.1; UNISOC's goes through its own HAL extension, a user-space program), camera tuning (3A, the ISP's parameters), sensor fusion. The rules:

- **A separate process** with its own uid, in a sandbox: namespaces, seccomp, Landlock, only the device nodes it needs, an empty network namespace when it needs no network. What exists: `phone-sandbox`'s app and helper policies ([17](17-app-sandbox.md) §2); the helper policy grants no device and no new sockets, and a policy for vendor processes is **not implemented**; the system services' own systemd units do not have these either (they run as root).
- **It talks to Kario only through these interfaces**: Linux's standard ones (IIO, V4L2 and the media controller, ALSA and UCM, evdev, DRM/KMS, GNSS's `/dev/gnssN`, the power supply class, the LED class: what `hal/` and the services use today); D-Bus protocols with a public specification (as between telephonyd and ModemManager); Unix-socket protocols Kario defines (the system services' `wire` RPC, [11](11-platform-architecture.md) §14). The HALs of a vendor's Android BSP over binder: telephonyd's backend speaks it through the open libgbinder and loads no vendor library (**not implemented**, [11](11-platform-architecture.md) §16); where a vendor library linked against bionic has to be loaded, it goes into a separate, deprivileged HAL host process (§7.4, **not implemented**).
- **The Shell, the system services and the renderer never link nor `dlopen` a closed library**: a closed part that crashes takes only its own function with it, and a hole it brings in stays in its own process. A GPU's user-space driver is a library loaded into the process that draws, so a closed one (Mali's libmali, for example) is not used either: the renderer draws on the CPU (today's default) or through an open Mesa driver ([42](42-gpu-rendering.md)).
- **A precedent**: libcamera runs tuning modules (IPAs, possibly closed) that were not built and signed with it in a separate, isolated process and calls them over IPC (Kario has no libcamera yet, **not implemented**).
- **It gets only what its function needs**: camera tuning, for example, gets frames and statistics and sets the sensor's controls, and reaches neither the apps' data nor keys.
- Today's images contain no closed library or program at all: on the 6T the only closed parts are firmware.

#### 8.7.1 Where SKUs live

- **A SKU file holds hardware facts and feature switches only**: which board, display, keypad, memory tier, region and product layer (§1), and what the board has (`modem`, `gnss`, `nfc`, `fingerprint`, `ims`, `[audio]`, `[partitions]`, ...). A switch's value is one of those `tools/sku.py` knows: one of Kario's interfaces, or an open implementation (`ims = "81voltd"`).
- **What stays out of a SKU**: which vendor recipe implements a switch, artefact addresses and checksums, which BSP layer is used. Those belong to the BSP layer's machine and the product's kas file: the machine turns the switch into its own recipes (as `oneplus-fajita.conf` installs `81voltd phone-qcom-pdc` for `PHONE_IMS = "81voltd"`), and the product's kas file picks the BSP layer and pins its commit (§8.2). Where a closed implementation needs a switch value, `tools/sku.py` gets a value that names no implementation ("the BSP layer provides it by the contract", §8.7.3), never a vendor recipe's name.
- **So a product's SKU is public once the product is announced**: a SKU that switches a closed driver on still says only facts like "has a camera" or "has IMS", nothing of the vendor's. Once a product is announced, its board, display, keypad, product layer and SKU go into this repository's `sku/` and pass `make test`'s `sku.py check` like the existing ones.
- **A product not announced yet** keeps these files in a `sku/` directory of the same shape in the internal repository, all moved into this repository on the day it is announced. `tools/sku.py`'s second search path (done on 2026-11-26, `SKUPathTest` in `tools/sku_test.py`) and what the build flow has to change:
  - **The environment variable `KARIO_SKU_PATH`**: a list of directories separated by `:`, each shaped like `sku/` (`boards/`, `displays/`, `keypads/`, `products/`, `skus/`), searched after this repository's `sku/`; the internal repository's Makefile sets it. `load` and `names` look in all of them, so a SKU and the board, display, keypad and product layer it uses may each be in either (an internal SKU uses this repository's displays and keypads). An id in two of them is an error, so that neither hides the other; so is a directory that does not exist, is given twice, is this repository's `sku/`, or has a `keys.toml`: there is one key code table, in this repository.
  - `sims` writes `cmd/kario/skus.json`, which is in git and public with the SDK: it writes this repository's SKUs only (`names("skus", own=True)`), with `KARIO_SKU_PATH` set too; the test checks the table comes out byte for byte as without it. The Makefile's `make skus` and `sku-<name>` targets read `sku/skus/*.toml` and so list this repository's only.
  - A board whose device tree is not in the kernel source (the product's own tree, which the BSP layer's kernel recipe adds) and whose machine is not this layer's: the label check is skipped and left to that build; for this layer's machines it stays an error.
  - `gen` writes `sku.json` and `sku.yml` into this repository's working tree (`yocto/meta-phone/recipes-phone/phone-sku/files/`, `yocto/kas/generated/`). Both are in `.gitignore` (the test checks with `git check-ignore`), so `make publish` cannot push them; but once release builds take kario from git by commit (§8.7.4), the copy from git does not have these files, so the generated files have to go outside the working tree (into the build directory), and the `phone-sku` recipe and the product's kas file read them there.
  - The checks against a machine file (the touchscreen built into the kernel, `[audio]` equal to `PHONE_AUDIO_*`, IMS installed from `PHONE_IMS`, `phone-abslot` where the bootloader keeps the slot, §2, §8.7.3) look for the machine file in this layer and in BSP layers (done on 2026-11-27): **the environment variable `KARIO_BSP_LAYERS`** is a list of BSP layer directories (separated by `:`, each with a `conf/layer.conf`, none given twice and none meta-phone), and a machine in two places is an error; a BSP layer's kernel recipe takes the configuration fragments beside it and meta-phone's. A machine this repository's kas files build (`machine:` in `yocto/kas/*.yml`, the 6T's for one) that no layer given has makes `sku.py check` and `gen` fail rather than skip quietly; only other boards' machines are skipped when not found (§8.2). `sku.py check` lists the machine files it checked. The Makefile gives it kario-bsp's layers: `make test` and `make sku-check` fetch kario-bsp at the commit `phone-fajita.yml` pins into `build/kario-bsp` (`make bsp-fetch`, `scripts/kario-bsp.py`; they fail when they cannot, or when main no longer has the pinned commit), and `KARIO_BSP=../kario-bsp` takes one's own checkout instead ([38](38-contributing.md) §11). The tests are `BSPLayersTest` in `tools/sku_test.py`.
  - The internal repository's `make biz-check` runs `sku.py check` with both SKU paths and the layers of kario-bsp and of the private BSP repository; this repository's `make test` checks its own SKUs only.
  - Not done yet: the generated files above moved outside the working tree.

#### 8.7.2 External drivers: three kinds of source, and how they are built

All of them get into an image through a BSP layer: the BSP layer's repository holds recipes only (§8.2); sources and files live elsewhere, and the recipes fetch them at fixed versions.

| Source | Where it lives | Recipe |
|------|-------|------|
| A kernel driver with source | The vendor's kernel tree (a private kernel repository), or a module source repository the vendor gives separately | The vendor kernel: `SRC_URI` names the kernel repository, `SRCREV` the full 40-digit commit, and it `require`s this repository's `phone-kernel.inc`. An out-of-tree module: a recipe that does `inherit module`, its `SRC_URI` at a fixed commit of the module's source, built against the image's own kernel, so its version and `vermagic` match by construction |
| A user-space program with source | The vendor's git (which we mirror in a private repository) at a fixed commit | An ordinary recipe (meson, cmake, ...), installed as a separate, sandboxed process (§8.4) |
| Binary only | The artefact store, addressed by sha256 (§8.1) | `SRC_URI` is the artefact store's address, checked by `SRC_URI[sha256sum]`, and there is only a `do_install`; a binary-only `.ko` goes into the kernel's version directory and is signed when installed (below), and the build stops when its `vermagic` does not match the image's kernel |

- Each closed recipe names the vendor's licence and carries its text (`LIC_FILES_CHKSUM`), never `CLOSED`; `LICENSE_FLAGS = "vendor-<vendor>"`, accepted only by the kas file that builds that product (§8.5).
- **Module signing is a signature, not encryption**. At build time the module file's digest is computed with SHA-512 (`CONFIG_MODULE_SIG_SHA512`) and signed with the private key, and the signature (a PKCS#7 / CMS structure) is appended to the end of the `.ko`; the kernel holds only the matching public key (the certificate built into it). At load time the kernel computes the digest again and checks the signature with the public key: a module without a signature, one signed by a key the kernel does not know, or one changed by a single byte after signing fails, and under lockdown (integrity) the kernel refuses to load it ([39](39-oneplus-6t.md) §8.3). The module itself stays as it is: anyone who has the file can read and disassemble it; the signature only proves "someone holding the private key signed this, and it has not changed since", and hides nothing. The signing tool is `scripts/sign-file` in the kernel's source tree, which happens to use OpenSSL's libcrypto (hence the kernel recipe's `openssl-native`). With the private key in an HSM, `CONFIG_MODULE_SIG_KEY` names a `pkcs11:` address and `sign-file` has the HSM sign through OpenSSL, so the private key never leaves the HSM (**not verified** with our kernel and OpenSSL versions).
- This repository's kernels sign their own modules when the kernel is installed (as today). Out-of-tree modules and binary-only `.ko` files: the kernel's `modules_install` signs only with the private key, and whether the kernel build directory OE hands to other recipes has it is **not established**, so a common class in meta-phone signs them after installation with `sign-file` and the same key, and the image check `modules-signed` checks them again. The key is never given to a vendor.

#### 8.7.3 The BSP interface: abstract it, and where

**Abstract it, at the Linux standard interfaces already in use**, plus a few small interfaces of Kario's own where Linux has none; no extra HAL layer. The Shell, the services and the renderer are written against these interfaces, and the BSP layer makes them hold on its board. What a BSP layer has to provide (the "BSP contract"):

| Item | What the BSP layer provides | Checked by |
|----|--------------|-------|
| Machine | `conf/machine/<machine>.conf`: tuning, kernel, device trees, `MACHINE_FEATURES`, image formats; the boot image's parameters for an ABL-like bootloader (`phone-bootimg`) | bitbake's parse; `tools/sku.py check` (given the BSP layer's path, §8.7.1) |
| Kernel | `require phone-kernel.inc`: lockdown, module signing; every line of Kario's configuration fragments (`phone-*.cfg`: Landlock, seccomp, cgroup v2, memfd and namespaces for the sandbox, dm-verity, squashfs and nbd for system updates) | The kernel recipe's configuration check (like `linux-sdm845`'s `do_phone_kconfig`); the image check `modules-signed`; `module-check.sh` after boot and the Shell's kernel probe (§7.5) |
| Linux standard interfaces | Display DRM/KMS, keys evdev, sound ALSA and UCM, sensors IIO, camera V4L2 and the media controller, the power supply, LED and backlight classes, RTC, watchdog, GNSS's `/dev/gnssN`, Wi-Fi (nl80211, for iwd), Bluetooth (HCI, for BlueZ), USB gadget (configfs) and the Type-C class, coprocessors (remoteproc and firmware loading) | The selftest and the compatibility test (`phone-shell --cts`) on the board |
| The board's values | The machine's variables agree with the board file: `PHONE_AUDIO_*` is `[audio]`, IMS installed from `PHONE_IMS`, the touchscreen's driver built in; the partition table and the flash script | `tools/sku.py check` |
| Modem backend | What telephonyd's `Modem` backend needs | The modem's contract is written separately (§8.8; the Android HAL path in [11](11-platform-architecture.md) §16) and not repeated here |
| Carrier configuration | Activating the modem's carrier configuration for the SIM (Qualcomm: `pdc-select`) | As above |
| Voice audio path | The call set-up of the board's `[audio]` (UCM's call verb and devices); a daemon that connects the modem's voice to the sound card during a call (Qualcomm: `q6voiced`) | The call trigger as above; the UCM values by `tools/sku.py check` |
| A/B slot switch | A board whose bootloader keeps the slot (`slots = "abl"` in `[partitions]`): a program that reads and writes the slots (`slots`, `set-active`, `get-state`, `mark-good`, `mark-unbootable`; on Qualcomm `phone-abslot`), RAUC's boot loader backend `/usr/lib/phone/rauc-abl` (`get-primary`, `set-primary`, `get-state`, `set-state`, `get-current`), and the initramfs writing the slot booted into `/var/lib/slots/boot`. A board with `slots = "state"` needs nothing from the BSP | kario-bsp's `tests/abslot-test.py` and `tests/rauc-abl-test.py`; this repository's `tools/slots_test.py` (the `slot-abl` the initramfs reads); `tools/sku.py check`: for a board with `slots = "abl"`, a recipe in its machine's layers `RPROVIDES` `phone-abslot`; the system update tests |
| Licences | Closed recipes name the vendor's licence and carry its text, `LICENSE_FLAGS = "vendor-<vendor>"`; no GPLv3 (§8.7.5) | `scripts/yocto-check.py --layer <layer>` run on the BSP layer (kario-bsp's `make test`); `INCOMPATIBLE_LICENSE` |
| Closed processes | Own uid, sandbox, only the devices needed (§8.4) | Delivery review (internal document 60) |

- **Conformance is what the selftest and the compatibility test say**: the same `selftest.script` and CTS cases run on every board, plus the build-time checks of the table; the CTS report's `sandbox` field says what the kernel lacks (§7.5).
- With `PHONE_SLOT_KEEPER = "abl"`, `phone-initramfs.bb` asks for `phone-abslot`, a name of no vendor's, which Qualcomm's `phone-qcom-abslot` package `RPROVIDES` (done on 2026-11-27; `tools/sku_test.py` checks the initramfs names no vendor and the 6T's layers provide it).

#### 8.7.4 Several repositories and reproducibility

- **Today**: kas manages every upstream layer, each at a full 40-digit commit (`phone-qemuarm64.yml`: bitbake, openembedded-core, meta-rauc, meta-openembedded, meta-yocto; `phone-fajita.yml`: meta-qcom, meta-lts-mixins), so a new build directory gets the same set. kario itself is only a local path in kas (`repos.kario` has no `url`); the product build (the internal repository) also takes kario from the checkout beside it (`KARIO=...`, `/kario` in kas-container). So which commits make up an image is recorded in the image only by `share/phone/source.txt` (kario's commit, and whether it had changes), and a release records the two repositories' commits besides (internal document 60).
- **The plan**:
  1. Release builds take kario by URL and full 40-digit commit (the release tag's), not by local path; day-to-day development keeps the local path. This needs the generated SKU files out of kario's working tree (§8.7.1). BSP layers likewise give full commits (§8.2).
  2. kas lock files: the kas in use is 5.5, and by its source (not run): `kas lock <file>` writes `<name>.lock.yml` beside the first configuration file, which kas then uses by itself, and `kas lock --update` updates it; `kas dump --lock` is the old entry to the same thing. It locks only repositories kas checks out itself that give a branch or tag without a commit, and never a local-path repository (kario). Our upstream layers all give commits already, so a lock file would lock nothing more today: **no lock files**; the commits stay written in the kas files (in one place, so changing one is a line seen in a PR).
  3. **A release records every repository's commit**: `kas dump --resolve-refs --resolve-local` writes out the whole expanded configuration, every repository with its URL and commit, local-path repositories with the commit they have checked out (warning on uncommitted changes); that file goes into the release directory, and can be given to kas as it is to build again. The product image's `source.txt` also lists every repository's commit.
  4. **SBOM**: the SPDX oe-core writes by default (`create-spdx`) goes into the release and is handed out with product images (§8.5). The BSP layer's closed recipes are packages with the vendor's licence name in it; the copy handed out with the image carries no artefact store addresses.
- **Conclusion: no Google `repo`**. It checks many git repositories out at fixed versions from an XML manifest (`repo sync`, with `repo manifest -r` recording a snapshot), designed for AOSP's hundreds of repositories and Gerrit. kas does everything we need: checks layers out by commit, generates bitbake's configuration, builds in a container, refers to configuration across repositories, and expands and records every commit. `repo` would only add a second manifest copying kas's list of repositories (two lists to keep in step) and configures no bitbake; what it adds is checking a few repositories out side by side to edit them, and with two to five repositories `git clone` plus kas's `checkout` and `for-all-repos` is enough.

#### 8.7.5 GPLv3: why it cannot be "managed closed"

- **Shipping it means giving its source**: a GPLv3 program in a product image comes with its "Corresponding Source" (GPLv3 §6: the source plus the scripts that build and install it), the vendor's changes to it included; GPLv3 code linked with closed code into one program makes the whole program GPLv3. So a GPLv3 part cannot be managed as a closed thing; it can only be shipped as open source, with its source tracked.
- **A user product also needs the "Installation Information"**: a phone is what GPLv3 calls a "User Product", and whoever ships it also gives the methods, keys and procedures needed to install and run a modified version on that device (Installation Information, §6), unless nobody can (ourselves included, e.g. code fixed in ROM). Our root file system is checked by dm-verity and signatures and the boot chain is locked ([25](25-system-update.md)): for a modified GPLv3 program to run we would either hand out the signing key (the whole trust chain gone, which payments, end-to-end messages and device attestation rely on) or give a path the user can open (the third row below). An LGPLv3 library is the same: it requires that the user can put in a modified library, and on a user product that again needs Installation Information.
- **What is fine**:
  - GPLv3 tools on the build machine (GCC, binutils, make, bash, bison, ...): they run only at build time and are not in the image, so they put no duty on it.
  - GCC's runtime libraries (libgcc, libstdc++): GPLv3 with the GCC Runtime Library Exception, which lets programs GCC compiled link them under any licence; the image has them (`phone-qemuarm64.yml`'s note).
  - GPLv2 parts (the kernel, 81voltd): their source is given, and there is no Installation Information clause ([39](39-oneplus-6t.md) §10).
- **When a GPLv3 part seems unavoidable**, there are three ways:

| Way | Example | Cost |
|------|------|------|
| Write a permissively licensed replacement | qbootctl → `phone-abslot`, bootmac → `phone-btaddr`, callaudiod → phone-audiod's UCM call routing, msm-modem's UIM selection → `uim-select`: rewritten from what they do, using none of their code ([39](39-oneplus-6t.md) §10) | We write, test and maintain it and follow upstream fixes ourselves; a big part (hexagonrpcd) is a lot of work, and until it exists the function is missing (the 6T has no sensors) |
| Use an old version from when it was GPLv2 | GNU tools from before their move to GPLv3 (what Yocto's meta-gplv2 layer held; whether anyone still maintains it is **not established**) | No security fixes, out of step with newer dependencies: in effect we maintain a fork; only for something very small and very stable |
| Ship it unmodified as a separate program, with its source and a path the user can open | A separate process, not linked with closed code (being in the same image is not linking); its source given with the image; Installation Information: e.g. installing one's own version after unlocking the bootloader (device attestation then reports `unlocked`, and services that require verified boot may refuse), or putting it where dm-verity does not reach and the owner can replace it | The product's kas file needs an `INCOMPATIBLE_LICENSE` exception for it; every release gives its source and goes past legal review; the copy outside verification can also be replaced by an attacker with root, so the sandbox has to hold; whether losing device attestation after unlocking counts as giving the Installation Information is for legal counsel (**not established**) |

  The first is the default; where it cannot be done the function is left out (like the 6T's sensors); the third needs the owner and legal counsel to approve it. A vendor delivery with GPLv3 in it is sent back at review (internal document 60).

#### 8.7.7 When

The move is done in one go in an exclusive window: moving files breaks the merge of every change made to `yocto/` at the same time. The interface changes the move needs (`sku.py`'s second path, the contract's package name, `yocto-check.py` taking a layer path) are merged beforehand as ordinary changes, and the window only moves files, pins commits and runs the full verification (in the window of 2026-11-27, all but the second path were in fact done together with the move). When: **before the first vendor BSP arrives** (the machinery is proven on public code first, and vendor parts never enter meta-phone), **after the current batch of changes is merged and published**. The steps, what to check after each, how long it takes and how to roll back are in internal document 60.

### 8.8 The baseband: portable core, Modem backend and SoC glue

> Status: the parts of the contract written as code ✓: telephonyd's backend table (`telephonyd/src/backend.cpp`), the status contract (`contract_problems`; telephonyd reports on stderr each rule a backend breaks), `tools/sku.py`'s `MODEMS` and `IMS` tables; checked by the unit tests, `make mm-selftest` and `tools/sku_test.py`. There is one implementation, Qualcomm's (the ModemManager backend plus `phone-qcom` and the other glue), **not tried on a phone** ([39](39-oneplus-6t.md) §14.6). MediaTek: §8.9, **not implemented**.

Changing the baseband (say, a Snapdragon for a MediaTek all-in-one SoC) changes two things: one **Modem backend** inside telephonyd and the board's **SoC glue**; the **portable core** stays, and so does the telephonyd protocol the Shell, the apps and phone-smsd see ([04](04-ui-language-telephonyd.md)). The three layers:

| Layer | What it is | Now (Qualcomm) | On another baseband |
|-------|-----------|----------------|---------------------|
| Portable core | telephonyd's `Service` (the RPCs, the call log, the pending queue for phone-smsd, the APN database and APN plan, the three switches and the roaming rule `roaming_allowed`, the emergency numbers, the second-call rule `second_call`); the Shell (the incoming-call screen, the status bar, the SIM PIN screen, airplane mode, the firewall closing `data_ifaces`, networkd files written from `data_ip`, the MMS bearer's policy routing, data usage); phone-smsd; phone-audiod's UCM call routing (following telephonyd's calls, the board's `[audio]`) | One code base | Unchanged |

| SoC glue | The programs and configuration particular to a SoC that run before the modem comes up and beside it, each a process or configuration file of its own, chosen by the Yocto machine and the board file | `phone-qcom` (`uim-select`, `pdc-select`), 81voltd, q6voiced, rmtfs, tqftpserv, qrtr, `alsa-ucm-conf-sdm845` ([39](39-oneplus-6t.md) §10, §11.1) | That SoC's (§8.9) |

**What a backend provides** (the comment above each method of the `Modem` interface is authoritative; these are the essentials):

| Part | What the backend does | Who relies on it |
|------|----------------------|------------------|
| Name | An entry in `backend.cpp`: its name is the board's `modem` value and the `Status.backend` it reports; `tools/sku.py`'s `MODEMS` lists the same names (`sku_test.py` checks both agree) | The board choosing the backend; the Shell only recognises `sim` (the selftest's simulated interface) |
| Status | Every field of `Status`, with a `status` event on each change; `contract_problems` holds: `backend` named; the data link (`data_ip`) present exactly while `data_state` is `connected`, `data_state` `off` while the radio or the switch is (and while there is no modem yet); the data link's and the MMS bearer's interfaces in `data_ifaces`, named so the Shell can write them into networkd files (1–15 letters, digits, `_.-`, not starting with a dot, `valid_iface`); static addressing with an address and a prefix; roaming reported only while registered, `data_state` `roaming` only where the roaming switches refuse the link; signal 0–4 bars, 0 while not registered; PIN tries only while the SIM asks for a PIN or PUK. Addresses may arrive after "connected" (ModemManager does that); the Shell configures the interface once they do | The Shell's status bar, firewall, networkd, data usage |
| Calls | Dial, answer, hang up, hold (resuming the held one swaps two calls), keypad tones; states dialing → alerting / incoming → active / held → ended with the reason it ended; second calls as `second_call` says; emergency numbers dialled with the radio off, with no SIM and with a locked one, the radio powered up first; mute only kept as state (the microphone belongs to the voice path) | The incoming-call screen, the call log, phone-audiod switching UCM with the calls, the glue's voice path |
| SMS, cell broadcasts | Delivery reports asked for, a message's later events under the same id; received ones kept in the modem's storage until `ack_sms` / `ack_cb`; ids computed from the content, stable across restarts | phone-smsd losing nothing |
| USSD, SIM | One USSD session at a time; PIN, PUK and PIN-lock outcomes as `unlock` and `pin` events; reading the SIM's phone book | The Shell's PIN screen, the contacts import |
| Radio and data | `set_radio` (off is airplane mode, refused during an emergency call), `set_data`, `set_data_roaming`; the plan `set_apn` gives: data on the internet APN only, the attach APN handed to the modem; IMS and emergency bearers (the glue's) neither data nor disconnected, their interfaces not in `data_ifaces` | The Shell's switches and firewall; the glue's IMS |
| MMS bearer | Where the plan has an MMS APN of its own, a second bearer, answered once it has addresses; a static IPv4 address (the Shell routes by source address); "over the data link" when the MMS APN is the internet one | phone-smsd's MMS |
| No blocking | Every request to the modem asynchronous, on telephonyd's `Loop`; when the connection to the modem breaks, `Backend::failed` makes telephonyd exit and systemd restarts it | All of telephonyd |
| No closed libraries | The backend speaks public protocols only (D-Bus, AT, MBIM, QMI, binder); a vendor's library only in a process of its own (§8.4) | §8.1 |

The glue's rules: it does not compete with the backend: it connects no data bearer and disconnects nobody else's, and the bearers it opens are recognisable to the backend as IMS or emergency ones (on ModemManager: the APN is one of the plan's IMS or emergency APNs or the generic `ims`, `sos`, or `apn-type` says so); what has to be done before the backend comes up (SIM slot, carrier configuration) is ordered before the backend's daemon in systemd, and its failure costs only that one function; glue that follows calls should follow telephonyd's events (`subscribe`'s `call`), which is backend-neutral, as phone-audiod does; it runs in a process and sandbox of its own (§8.4).

**How a board and SKU choose them**: the board file (`sku/boards/*.toml`) is the one source. `modem` picks the backend (one of `MODEMS`, `sim` when left out; any other value fails `tools/sku.py check`), handed to telephonyd through `sku.json` (`--sku`); `ims` picks the IMS glue (the `IMS` table, which needs its backend), written into the kas overlay as `PHONE_IMS`; `[audio]` is the sound card's and calls' UCM setup; `gnss` picks the location receiver. The other glue follows the Yocto machine: one machine per SoC (later a private BSP layer, §8.2), which installs that SoC's glue packages; one telephonyd program has every backend built in and picks one at run time from `sku.json`.

**How a new backend is checked**:

1. Unit tests (`make telephonyd`): `test_backends` checks the backend table's names and the `Status.backend` each backend reports; `test_contract` walks the simulated baseband through its states (connected, data off, roaming, airplane mode, SIM locked), none of which may break `contract_problems`, and has one breaking example per rule. A new backend adds the states it can produce on the host.
2. Cases over the socket: `mm_test.py` calls telephonyd over its socket and takes its events the way the Shell does; only the "network" side (the mock ModemManager and its control interface) is ModemManager's. A new backend makes a mock of its own transport after it (say, a fake radio service on binder) and runs the same cases; the last case, `backend_contract`, fails if telephonyd reported any status breaking the contract (it is one of the 39 cases of `make mm-selftest`). For a backend through ModemManager (MediaTek through ModemManager, say) telephonyd's side is covered by `make mm-selftest` already; the ModemManager plugin and the modem only on a phone.
3. `make selftest`: the Shell side's call, SMS, APN and roaming cases on the simulated baseband, the same whatever the backend.
4. `tools/sku_test.py`'s `test_modem`: `MODEMS` matches `backend.cpp`'s names, other values are refused.
5. On a phone: telephonyd logs each kind of break once (`the <backend> backend breaks the Modem contract: …`); go through the checklist of [39](39-oneplus-6t.md) §14.6.

### 8.9 MediaTek: three paths (**not implemented**)

> Status: design only, **not implemented**; most of the MediaTek details below come from scattered public material and are **not verified**; there is no MediaTek phone and no vendor material.

In MediaTek's phone SoCs (Dimensity, Helio) the modem and the application processor talk over CCCI (MediaTek's kernel driver, only in vendor kernels): AT and the other channels are character devices, the data interfaces are `ccmniN`; the modem's boot and the file service for its NV data are vendor daemons (of the `ccci_mdinit`, `ccci_fsd` kind, **not verified**). Mainline Linux only has `t7xx` for PCIe modules (the WWAN subsystem, which ModemManager drives over MBIM), not the phone SoCs' CCCI. The largest difference from Snapdragon: Snapdragon's IMS is in the modem's firmware, MediaTek's IMS stack mostly runs in the vendor's user space on the application processor (closed daemons, alongside the RIL on Android, **not verified**).

| Path | How it connects | What the vendor must provide | Fit with Kario's rules |
|------|----------------|------------------------------|------------------------|
| ModemManager over AT (or MBIM) on CCCI | The backend stays `MmModem`, nothing to write; udev tags CCCI's AT port for ModemManager, data goes over `ccmniN`. ModemManager's existing MediaTek plugins are for USB and PCIe modules, so CCCI needs a plugin (open source, upstreamable), and attaching a bearer to `ccmni` needs MediaTek's private AT commands (**not verified**) | A usable vendor kernel (the CCCI driver), AT command documentation (the private commands for data, dual SIM, carrier parameters, IMS), the modem boot and NV services (closed processes) | The best fit: telephonyd and ModemManager are open source, the only closed parts are the firmware and the boot and NV services (processes of their own, sandboxed). No VoLTE: the IMS stack on the AP is out of reach without AT, so no calls on LTE-only carriers |
| Android's radio HAL through libgbinder | A new backend (`android-radio`, say) speaks `IRadio` (AIDL `android.hardware.radio.*`, older HIDL 1.x) and MediaTek's extensions through the open-source libgbinder; the vendor's rild, `mtk-ril` and IMS daemons run in a container holding the vendor's `vendor` partition (the Halium way, with its own servicemanager); this is the path [11](11-platform-architecture.md) §16 plans | The vendor's Android BSP (`vendor` partition, vendor kernel) and the right to redistribute it; the HAL version; documentation of MediaTek's extensions (IMS, dual SIM, carrier configuration) | Fits the rules: telephonyd links libgbinder only, vendor code stays in the container; but the sandbox policy for the container and vendor processes is **not implemented** (§8.6), and §7.5 lists what an old kernel's sandbox lacks. Call audio is set up through the audio HAL (`audio.primary.*`), one more HAL host process (§7.4). The only path to VoLTE |
| MIPC | The private message protocol MediaTek's newer modems give their own RIL, also over CCCI (**not verified**) | The protocol documentation (likely under NDA), or only a library | With documentation: an open-source backend can be written, the lightest of the three; with only a library: it goes into a process of its own speaking a protocol Kario defines, which is the second path's arrangement |

**What the glue is on MediaTek** (all **not verified**): the modem's boot and files: `ccci_mdinit`, `ccci_fsd` and the NV daemons; SIM slot: dual SIM through one RIL instance per card (`IRadio`'s `slot1`, `slot2`), while telephonyd's model has one SIM today; carrier configuration: the modem's carrier parameters (MediaTek calls them SBP), set by the vendor's RIL from the SIM; IMS: the vendor's IMS daemons on the AP and the RIL's IMS extensions; call audio: the audio HAL sets it up over CCCI's speech channel; data interfaces: `ccmniN`, whose name and addresses the RIL returns when it sets up a data call (exactly a `DataLink`).

**Which to take**: VoLTE (many carriers in China and the US have no 2G or 3G left) leaves only the second path: the work is the libgbinder backend, the sandbox for the container and vendor processes, the audio HAL host process, plus the vendor's BSP and contract. Without VoLTE (markets that keep 2G and 3G) and with a vendor willing to give the AT documentation, the first path is cheapest: not a line of telephonyd changes, the work is in a ModemManager plugin. The third depends on whether the purchase contract gives the protocol documentation. Whichever path, Kario's side is: an entry in the backend table with the same name in `MODEMS` (or `modemmanager` still); the board's `modem` and `ims` (the `IMS` table with that glue and the backend it needs); a Yocto machine (or BSP layer) for the SoC installing the glue; a mock of that transport running the socket cases and `backend_contract`; and dual SIM needs telephonyd's model extended first (one SIM today).

### 9.1 New SKUs, not the kario-* ones completed

The three `kario-*` SKUs are the product line (mainline development boards with the Snapdragon 662 and 460, chosen in internal document 61); the reference phones get a board and two SKUs of their own, because:

- The Snapdragon 662 (SM6115) and 460 (SM4250) have **no mobile data and no cameras** on mainline: the IPA driver (`drivers/net/ipa/ipa_main.c`) knows msm8998, sdm845, sc7180, sdx55, sm6350, sm8350, sc7280, sdx65, milos and sm8550, not sm6115, and `sm6115.dtsi` only reserves IPA's memory; camss has no sm6115 in 6.18 nor in 7.1-rc1 (7.1 adds qcm2290); nor is there venus. Completing them cannot give the cameras and the data the reference phones need. **This matters to the product line too: on mainline its two product boards can call and text but have no cellular data, which the owner needs to know.**
- Changing the `kario-*` boards would change product decisions, which is not this task's to do.
- The reference board has no machine of this layer (`kario-qcm6490` is to come with its layer in kario-bsp, §8.7.6), and kept apart from the product boards it leaves their checks and builds untouched.

### 9.5 A 3.5 mm headphone jack yes, FM radio no

**The headphone jack: yes.** A candybar has the room (a jack is about 5 × 12 mm); a wired headset makes calls with no pairing and no charging, and its remote's button answers and hangs up; many hearing and accessibility devices are still wired; mainline's WCD937x has MBHC, which detects the plug and the remote's buttons. The work is on Kario's side: audiod reading the jack's state and switching calls and media to the headphones ([20](20-audio.md) §10 says "headphones: not done" today), **not implemented**; the hardware is there for when it is.

**FM: no.** The headphone cable as the FM antenna is the classic design, but of the FM receiver drivers still in mainline (`drivers/media/radio/`: Si470x, Si476x, TEA5764, TEA5777, TEF6862, SAA7706H and old ISA and USB radios) the only one fit for a phone is the Si4703 (`silabs,si470x`, `radio-si470x-i2c.c`), and it is discontinued (Silicon Labs: last order 2026-06-15, last shipment 2026-12-15), so a new design cannot rely on it; whether the Si476x can still be bought is **not verified**; the common RDA5807 has no mainline driver. The module's WCN6750 has no mainline FM either, and Kario has no radio service or app. So FM is not realistic, and none is fitted.

### 9.7 What a builder has to do

1. Get from Quectel SG560D's hardware design manual, its reference design and the firmware signed with the module's keys (MPSS, ADSP, CDSP, WPSS, IPA): this is the closed firmware of §8, which goes in no git repository but in a private BSP layer (on top of §8.7.6's kario-bsp layer `meta-kario-qcom`).
2. Confirm first that the module's boot loader boots a mainline kernel (whether Quectel's ABL wants a signature, whether it unlocks, the boot.img format): **not verified**, and the biggest risk; if it does not, another module is needed.
3. Draw the carrier board: the panel's DSI (2 lanes); the keypad's TCA8418 and the VCNL4040 (0x60), BMA400 (0x14), DRV2605L (0x5a) and PN7150 (0x28), all on i2c9; both cameras' CSI and CCI; the flash; the I2S amplifier; the headphone jack; USB-C; eight antennas; the SIM holder; the battery; the power key on top and the volume keys on the side.
4. Write the carrier's device tree `qcm6490-<name>.dts`: start from the Fairphone 5's (the same SoC and PMICs), drop its OLED panel, AW88261 amplifiers, PTN36502 and the like, and add a node for each part of §9.3; point the board file's `dtb` at it, and `sku.py check` checks that the wiring's labels are still there. Merged into the Fairphone 5's tree, today's overlay leaves its OLED's `vci-supply` and `dvdd-supply` in `panel@0` (the ST7701 driver does not read them); one's own tree has none.
5. The sound card: `sc8280xp.c` knows boards by compatible, and this board needs one added (a kernel patch, for upstream); until then it can borrow `qcom,qcm6490-idp-sndcard`; then a UCM profile, and only then can the board have `[audio]`.
6. Yocto: add a `meta-kario-qcm6490` layer with the `kario-qcm6490` machine in kario-bsp (a mainline kernel with the sc7280 patches, the firmware recipes, 81voltd installed from `PHONE_IMS`); only with it does `make sku-ref-…` produce a firmware package, and until then it stops where bitbake finds no such machine.
7. Check each value in `unverified` on the board, and delete those confirmed; each item of §9.3 that is **not implemented** on Kario's side is a task of its own.
8. Certification: the module has its own, and the phone still needs radio, SAR and the like; what exactly depends on where it is sold (**not verified**).

### 9.8 What the SKU framework cannot express

This time the framework gained `[[part]]` (the hardware list, its drivers checked against a kernel tree), `sku.py parts`, `panel_dsi_out`, and the kernel configuration checked only for this layer's machines (§2). What it still cannot express, written only in this section and the carrier's device tree:

- a part's address on its bus, its interrupt pin, its supplies (`[[part]]` records the kind of bus only);
- the cameras' CSI lanes, mounting orientation and calibration;
- antennas, the radio, SAR;
- the battery's capacity and charging parameters (in the ADSP's firmware);
- the mechanics: keycaps, case dimensions, a flip's hinge and flex;
- whether Kario's side can use each part (the "Kario" column of §9.3);
- what the outer display shows and when it lights: that is the Shell's policy and the product layer's defaults, not a hardware fact (§8.7.1: the SKU holds only hardware facts and feature switches); the SKU only says what panel the outer display is (§9.10.9);
- which USB port the OK key's fingerprint sensor is on and which GPIO switches its power (written only in the `[[part]]` names; the overlay does not generate them, the carrier's device tree does).

#### 9.10.1 SoC and memory

QCM6490 again, the same module as the two candybars (SG560D-EM):

- Cheaper Qualcomm chips have no mobile data on mainline. 7.1-rc1's IPA knows only milos, msm8998, sc7180, sc7280, sdm845, sdx55, sdx65, sm6350, sm8350 and sm8550; QCM2290 / QRB2210 gained camss in 7.1 but has no IPA, nor does SM6115 (§9.1); msm8953 has no mainline IPA, and msm8916's bam-dmux is too old. A phone that cannot get online cannot run apps like WeChat or Alipay.
- Three phones on one module, one BSP and one kernel: that is where the low cost comes from, not the chip's unit price. Whether SG560D comes with 2 GB, and the prices of other QCM6490 modules (MeiG SRM930, Fibocom SC171), are **not checked**.

4 GB of memory. The owner's rule (2026-11-26): smooth use and long standby first; 2 GB only for basic T9 phones that run only Kario's own apps.

- The flip runs others' apps (the WeChat and Alipay kind). 4 GB holds them and the system, and switching back does not start them anew; 2 GB runs them, but by zram compression and killing processes, so switching is slow and starting apps again costs power too.
- The Fairphone 5's device tree reserves about 492 MiB for firmware (modem 246, removed 81, ADSP 40, boot splash 35, CDSP 30, WPSS 25, WLAN 12 and others): a 2 GB phone leaves Linux about 1.5 GB, a 1 GB one only about 530 MB.
- The system itself takes about 190 MB (234 MB in QEMU, with the simulated cloud); one web page about 250 MB, and the web process's limit is at least 384 MB. An app like WeChat is chat plus a mini-program runtime plus web pages, with the camera's buffers while scanning. Running only Kario's own apps, 2 GB is plenty.
- The cost in standby: the extra 2 GB's self-refresh takes about 1.4–1.8 mW (the IDD6 of Micron's LPDDR4X Z42N datasheet, per 16 Gb die, 25–45 °C), about 0.4–0.5 mA at the battery. The 7-day budget holds it: about 9.2 days with 4 GB, about 9.8 with 2 GB (§9.10.10, **estimates**).

The memory LCD:

- Only it shows all the time at almost no power. An always-visible clock on the OLED takes 50–100 mAh a day, a quarter to a half of the 7-day budget, and burns in; the TFT takes hundreds of mAh a day and can only light for a few seconds, which is no longer "read the time without opening".
- Its price is monochrome, small and unreadable in the dark. The front light is the same panel's front-lit module (Azumo 11655-03) on the LPG's channel 3, lit for about 3 seconds on a key: 30 times a day is about 5 J, about 0.4 mAh. The front-lit module's price and thickness are **not checked**.
- E-paper costs little power too, but refreshes in hundreds of milliseconds to seconds, and mainline has no driver for a panel this small.
- QCM6490 has a single DSI host (`mdss_dsi`, no dsi1), which the inner display takes, so the outer display can only be on SPI; mainline's small SPI panels are one DRM device per panel.
- The datasheet's other points: SPI at most 1.1 MHz (the board uses 1 MHz); VCOM (EXTCOMIN) 57–66 Hz, and the power figures above are measured at 60 Hz, so VCOM follows it at 64.1 Hz (the earlier 1 s was outside the specification); a still picture is rewritten at least every 2 hours.

#### 9.10.4 Lid switch and hinge

- The Hall switch: TI DRV5032 draws µA (the datasheet's figure; which suffix to take is **not checked**); a push-pull variant needs no pull-up. Closed, the magnet comes near and the output goes low, and gpio-keys reports `SW_LID = 1`. The OnePlus 6T's device tree wires one this way (the "Hall Effect Sensor" in `sdm845-oneplus-common.dtsi`). The pin must be in the PDC wake map for opening the lid to wake the phone (`sku.py check` checks it, §2); logind already ignores the lid ([28](28-battery.md)), and the Shell handles it (§9.10.8).
- Over the hinge, the flex carries: the inner display's DSI (2 data pairs and the clock), the outer display's SPI with its enable and VCOM, the camera's CSI (2 pairs and the clock) and CCI, the upper half's sensor I2C, the earpiece, power and ground: about 30–40 lines, 100 Ω differential pairs; the flex has to survive 100,000–200,000 openings (**estimate**). The upper half holds only the inner and outer displays, the camera, its flash, the earpiece and the light and proximity sensor (facing in, by the earpiece); the antennas go in the lower half, away from the hinge's metal.

#### 9.10.5 The OK key's surface is the fingerprint sensor

- Where and how it reads: the OK key in the middle of the navigation cluster, its key cap's surface the sensor. It is a capacitive area sensor (not a swipe sensor), in a coated package, and reads a finger resting on it, without a press; under the cap is still the OK key's dome, and only pressing it down is OK. The cap is 12 × 12 mm with rounded corners, the direction keys around it, the whole cluster about 28 mm (**estimate**).
- As large as it can be: matching works on the minutiae in the sensing area, and the larger the area, the more minutiae and the fewer false rejections. The Goodix sensors in laptop power buttons are only about 4 × 3.25 mm (13 mm²); FPC1025's class is 160×160 pixels at 508 dpi, an 8 × 8 mm sensing area (64 mm²) in a 12 × 12 mm package (also a 14 mm round one), the largest key cap that works. The larger FPC1020 (9.6 × 9.6 mm) comes in a 14 × 14 mm package, which makes the cluster too large.
- The SKU: the keypad file says `fingerprint = "ok-key"`, `fingerprint_mm = [8.0, 8.0]` (the sensing area) and `fingerprint_cap_mm = [12.0, 12.0]` (the key cap), each width and height in millimetres. `sku.py` checks that the area fits the cap, that a real board's keypad gives both, and that a keypad without the sensor gives neither. The size is not in `sku.json`: nothing reads it at run time; it is for whoever builds the board.
- Powered and listening only while a system biometric prompt is open: normally the load switch (GPIO 83) is open, and neither the sensor nor its MCU draws power; keystored powers it for the system's prompt, a finger resting on it is captured and matched, and when the prompt closes the power goes off ([31](31-lock-and-biometrics.md) §4.5). Every press of OK touches it, so it never unlocks the phone, and apps cannot open it. For the few seconds a prompt is open the module draws some tens of mA (**estimate**). Following this decision, the confirmation and enrolment screens say to rest the finger on the OK key, with no need to press ([31](31-lock-and-biometrics.md) §4.5).
- To be honest: mainline Linux has no fingerprint subsystem. The SPI fingerprint sensors common in phones, wired straight to the SoC, need the vendor's matching program in a TEE, which we do not have: they cannot be used.
- So a match-on-chip module: the sensor (SPI) is wired to the module's own MCU, templates are stored and matched in the MCU, and the host only receives "it matched", over USB 2.0 full speed. The driver is user-space libfprint (LGPL), whose match-on-chip drivers are goodixmoc (Goodix), fpcmoc (FPC), elanmoc (Elan), synaptics and egismoc (Egis); it runs in a separate, sandboxed process per §8.4, not linked by the Shell or the system services. keystored needs a "match-on-chip" backend for it (**not implemented**).

Candidates (the sizes are the datasheets'; whether a key-cap-sized USB module libfprint knows can be bought is **not checked**):

#### 9.10.8 Closing and opening the lid (the part that needs no outer display implemented, **not tried on a phone**; the rest a design)

- Opening: wake and light the inner display. On an incoming call with "open to answer" set, answer it. Without a lock-screen PIN, opening releases the keylock; with a PIN, the PIN prompt shows.
- Closing: the inner display goes off at once and the phone locks as on screen-off. An ongoing call ends (setting "close to end call", on by default), but not while a headset, the speaker or Bluetooth is in use. Closing while it rings silences it. Alarms keep ringing (the side key snoozes), media keeps playing.
- While closed, the keypad matrix's keys do not count (the lid presses them); the power key refreshes the outer display, and lights the front light for a few seconds where there is one.
- The lid switch is a wake source; the renderer opens the input device `sku.json`'s `lid` names, reads `SW_LID` and passes it to the Shell ([23](23-renderer-protocol.md)'s `lid`).

Done (2026-11-27; Rust unit tests in `paint/src/lid.rs`, Go unit tests in `shell/lid_test.go`, the developer machine's selftest case 「翻盖的盖子」 (The flip's lid) ✓; **not tried on a phone**):

- Renderer: phone-paint opens the input device named by the handshake's `device`'s `lid` (handed over by the input helper, as the sound switch is), reads it once at start with `EVIOCGSW`, then sends `{"t":"lid","shut":true|false}` at each move; a lid it cannot read, or whose device goes, is reported open. It declares `lid` in `ready`; the Shell takes the lid as open under a renderer that does not (an older one, a headless one, phone-gui). The protocol change is a minor addition to `phone.frame/1`: old and new on either side work together ([23](23-renderer-protocol.md) §2).
- Shell (`shell/lid.go`), acting on changes only:
  - Closing: a ringing call is silenced (the call stays, seen on opening, saying 「铃声已静音」, Ringtone silenced); the inner display goes off, and the lock follows as on screen-off (with a PIN, after the grace period, at once with a grace period of 0; without a PIN no lock, as on screen-off).
  - While closed: the inner display stays dark; a call, an alarm, a notification, the charger or a selftest script cannot light it; keys are dropped (the log has the first and, on opening, the count), except the power key, the volume keys, both volume keys together (the accessibility shortcut), a headset's media keys and keys the computer sends (`kario device key`); keys do not say which device they came from, so a USB or Bluetooth keyboard's keys are dropped too. The power key only silences a ringing call and snoozes a ringing alarm, as with the lid open; nothing else (it lights no inner display, opens no power menu, which nothing could answer there, and no quick card view), until an outer display is drawn for it to refresh (§9.10.9). The volume keys act at once while closed (with the lid open and the screen off the first press only lights the screen).
  - Opening: a lock that fell due while closed comes first, then the inner display lights and the keypad's auto-lock counts from the opening; without a PIN the keylock is released; with a PIN, locked, the PIN prompt opens (not while an overlay such as an incoming call or an alarm is in front, nor during a call).
- Alarms and media unchanged: an alarm rings while closed and the power key snoozes it; the volume keys set the volume as before, and the side keys snoozing an alarm is **not implemented**.

Not done:

- "Close to end call" and "open to answer": there is no call settings page (blocked numbers are in Privacy and security, VoLTE in Mobile network, the dialer has no settings), so they do not fit an existing page; design only. "Not while a headset, the speaker or Bluetooth is in use" also needs the Shell to know where the sound goes: phone-audiod does not read the headset jack (§9.3) and has no Bluetooth audio route, and the Shell does not track the speaker (it only passes the call app's `audio.route` on to phone-audiod).
- The outer display (§9.10.9), the power key refreshing it, the front light.

#### 9.10.9 What the outer display shows and when it lights (design, **not implemented**)

- Always: the time, date, battery and signal.
- When there is one: missed calls and messages (following the lock screen's privacy setting, counts only by default), the weather (from a "glance" source, **not implemented**), who is calling, alarms and timers, charging.
- With the lid open: only the time.
- When it updates: on events; once a minute while closed, only the time's lines, by §9.10.10's short wake; the whole picture rewritten every hour (the datasheet: a still picture is rewritten at least every 2 hours); on the power key, with the front light lit for about 3 seconds. A memory LCD shows all the time; an OLED or LCD outer display lights for 5 seconds and goes off.
- The defaults go in the product layer (profile.d), the setting under Settings › Display › Outer display (**not implemented**). What it shows is the Shell's policy, not the SKU's; the SKU only says what panel the outer display is (`kind`, `color`, size).

What must be true in software (all conditions derived from **estimates**; **not implemented** unless noted):

1. Suspend: suspend 30 seconds after screen-off ([28](28-battery.md) §3 has it). 2. 3. 4. One periodic wake only: with the lid closed, 28 §3's "at most 15 minutes" maintenance wake is relaxed to push's learned heartbeat (at most 28 minutes), and jobs run on that heartbeat's wake. The Shell's side is done ([28](28-battery.md) §3: the RTC set 10 seconds after the heartbeat in case it comes late, 15 minutes when the push connection cannot be counted on; unit tests ✓, **not tried on a phone**); the lid's position comes from the renderer (§9.10.8, phone-paint's Rust unit tests ✓, **not tried on a phone**).
5. The heartbeat interval: steady only when it learns 15 minutes or more on mobile networks; where a carrier's NAT is under 8 minutes, 7 days cannot be reached, and Settings › Battery has to show why.
6. The modem: while the screen is off, indications (signal strength, cell information, network time) are turned off or given thresholds, leaving calls, SMS and data; in standby it camps on LTE (5G SA idle costs about 1 mA more). How ModemManager does this is **not checked**.
7. Wi-Fi: off when not associated (no background scans); associated, in power save, and the host woken only by unicast meant for it (ARP and NS offload, WoWLAN; whether ath11k does it on WCN6750 is **not checked**).
8. The fingerprint module and usb_2 are powered only while a system biometric prompt is open (§9.10.5); the front light lights only for about 3 seconds on a key (§9.10.3).
9. The fallback: if waking the SoC once a minute measures far dearer than estimated, a µA-class small MCU keeps the time and draws the outer display itself, the SoC sending it content only when there is some (the board changes).

#### 9.10.11 How the renderer drives two panels (design, **not implemented**)

- On the phone there are two DRM devices: msm (the inner display) and `sharp_memory_display` (the outer one), in no fixed card order. Today phone-paint's `Display::open()` tries card0, then card1, and takes the first connected connector, so it may open the outer display: it has to choose by driver name (`DRM_IOCTL_VERSION`), the outer display being `sku.json`'s `outer.drm_driver` and the inner display the other one.
- The outer display: a dumb buffer, XRGB8888 (the driver converts to 1 bit), no vblank; damage is passed with `DIRTYFB`, and the driver sends only the changed lines. Drawn in 1 bit: no anti-aliasing, by threshold; Chinese in a bitmap font (Fusion Pixel at 12 px, for example, OFL, its licence to check).
- Protocol: [23](23-renderer-protocol.md) gains an "outer display" target; the Shell lays out the outer display's picture itself, and apps only contribute content through notifications and "glance" data. With the lid closed the inner display is turned off (DPMS off or the CRTC disabled).
- The outer display's DRM device gets fbdev emulation, and fbcon may draw on it: avoid it with `fbcon=map:` or the kernel configuration (**not verified**).
- QEMU: for a SKU with a virtual outer display, `gen` adds a `virtio-gpu-pci` of the outer display's size to `QB_GRAPHICS` (unit test ✓, never run: there is no such QEMU SKU yet), a second DRM device as on the phone; both are `virtio_gpu`, and the renderer takes the second as the outer display by order. The lid is simulated by a uinput device in the guest (as uleds simulates the notification LED), since QMP cannot send `EV_SW`.

#### 9.10.13 What a builder has to do

1. Every step of §9.7 (the module's documents and firmware, booting a mainline kernel, the carrier, the device tree, the sound card, the Yocto machine, certification).
2. Hinge and flex: try an off-the-shelf flip hinge's opening life first, and draw the flex for §9.10.4's line count and impedance.
3. The carrier's device tree: the overlay generates the outer display and the lid (§3), or the tree can have them itself; add usb_2 and its PHY, the fingerprint's load switch (`regulator-fixed`) and `regulator-output`.
4. The BSP layer's kernel configuration needs `CONFIG_TINYDRM_SHARP_MEMORY`, `CONFIG_SPI_QCOM_GENI`, `CONFIG_KEYBOARD_GPIO`, `CONFIG_REGULATOR_USERSPACE_CONSUMER` and `CONFIG_USB_DWC3_QCOM` (this machine is not this layer's, so `sku.py` does not check).
5. Find the fingerprint sensor: a match-on-chip USB module libfprint knows, fitting a 12 mm key cap with a sensing area of about 8 × 8 mm (FPC1025 or a Goodix front-mounted capacitive sensor, with an MCU); failing that, leave it out for now and drop `fingerprint`, `fingerprint_mm` and `fingerprint_cap_mm` from the keypad file.
6. Measure standby (§9.10.10): USB disconnected, lid closed, a power analyser on the battery; watch whether `qcom_stats`' `aosd` and `cxsd` counts rise; check with an oscilloscope that the outer display's EXTCOMIN still runs at 64 Hz in suspend; correct §9.10.10's table with the measured figures.
7. On Kario's side, each is a task of its own: the renderer's two panels (§9.10.11), the Shell's lid (the part needing no outer display done, "close to end call" and "open to answer" not, §9.10.8) and outer display (§9.10.9), the outer display's short wake and the closed lid's maintenance wake (§9.10.10), keystored's match-on-chip backend (§9.10.5), camera QR scanning (§9.10.6).
