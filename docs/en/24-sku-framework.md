# SKU framework: one hardware configuration produces one firmware package

> Status: **prototype ✓** (`sku/`, `tools/sku.py`, the `phone-sku` recipe, `make sku`). The three SKUs on the two mainline Snapdragon boards (Snapdragon 662, Snapdragon 460) all build firmware packages, **not yet run on real hardware**; the two QEMU SKUs, T9 keypad and QWERTY keyboard, pass the boot selftest (57 (internal document) verification baseline). Real-hardware testing on a Phicomm N1 box is planned (§4, **not implemented**). The whole-phone board class (the panel and buttons are the phone's own, the keyboard is USB or Bluetooth: OnePlus 6 / 6T, Redmi Note 4X) and the kit that runs our root filesystem in a chroot on Nura (`tools/phone-chroot/`) are prototypes: unit tests and a dry run ✓, **not yet on a real phone** (§6, §7.4). Whether to replace a KaiOS phone from boot or interface with its base is in §7 (a survey, **not tried on a phone**); the key code table of a whole phone's own keypad (`[keymap]`, §7.4) and degrading on old kernels by what a probe finds (§7.5): unit tests ✓, **not tried on a phone**. For hardware selection see 61 (internal document); for keypads and displays see 52 (internal document).

## 0. Summary

- Each SKU has one configuration that only says "which board + which display + which keypad + memory tier + region + product layer"; the generator checks that these fit together and expands them into the Yocto configuration, device tree overlays and the runtime device description; `make sku SKU=<name>` builds the image and collects the firmware package, and every SKU in `sku/skus/` is also a target of its own, `make sku-<name>` (`make skus` lists them all). The binaries of the Shell, the services and the apps are identical on all SKUs.
- There is only one key code table (`sku/keys.toml`): the device tree's `linux,keymap` is generated from it, and tests check that phone-paint's evdev table knows every key code in it and that the key code values match the kernel headers.
- SKUs on the same board share the kernel and the root filesystem and differ only in the device tree overlay, `sku.json` and the product layer; later the overlay will be selected at boot by board ID, so that one image can cover a whole board family (**not implemented**).

## 1. Files

```
sku/
  keys.toml            key name → Linux key code
  boards/*.toml        boards: Yocto machine, device tree, baseband backend, GPU or not, module wiring (device tree labels), notification light and backlight ([leds], backlight, keyboard_backlight: kernel device class names, hal/), light sensor (light_sensor: an IIO device's name), location receiver (gnss); whole phones (class = "phone", §7.4) also have their own panel ([display]) and keys ([input]), the key code table of their own keypad ([keymap]), the device tree's root compatible, and the values still to confirm on the device (unverified)
  displays/*.toml      displays: panel driver compatible, kernel config, resolution, number of DSI lanes
  keypads/*.toml       keypads: scan chip, address, rows and columns, matrix position → key name, form factor (T9 keypad / QWERTY keyboard), the QWERTY Fn layer ([fn]: key → second character on the keycap), what stands in for a missing Ctrl key (ctrl = "fn+sym")
  products/*.toml      product layer: content merged into the configuration layers (profile.d)
  skus/*.toml          SKUs: one of each of the above, plus memory tier, region, optional rotate (portrait panel mounted landscape)
```

## 2. What the generator checks

`tools/sku.py check` (part of `make test`) expands every SKU:

- QEMU boards only get QEMU displays and keypads, real boards only real ones; the keypad's form factor matches the SKU's form factor (`bar-t9` / `bar-qwerty`); the display resolution (with width and height swapped when mounted landscape) equals the form factor's dimensions; the memory tier is valid.
- Keypad matrix: every position is within the row and column range, every key appears only once, and all keys are in `keys.toml`; the required keys are all present (left and right soft keys, OK, Back, Clear, Call, End, arrow keys; 0–9 / * / # on the T9 keypad; the 26 letters, Space and Shift on the QWERTY keyboard). The Fn layer is only for letter keys in the matrix plus comma and period, each producing a single character, and a keypad with an Fn layer must have an Fn key. `ctrl` is `fn+<key>`, both keys on the matrix, and the matrix has no `ctrl` key (in `keys.toml` `ctrl` is `KEY_LEFTCTRL`).
- The kernel drivers for the display and keypad chips are in the kernel configuration fragment of the kario-qcom machine.
- The notification light (`[leds] notify`), the backlight (`backlight`), the keyboard backlight (`keyboard_backlight`) and the light sensor (`light_sensor`) are valid device class names, and a multicolor light's `notify_color` is 0–255 per channel.
- Whether the board can be woken from suspend (`suspend`): real boards can by default, virtual ones (`virtual = true`, the emulator) cannot, and a board that cannot never suspends ([28](28-battery.md) §3).
- A power key of its own (`power_key = true`, a side key): there the end key is not also the power key; without one it is, the Nokia way ([18](18-nokia-form-factors.md)).
- The NFC controller (`nfc`): `sim` (the emulator) or `nci:/dev/<node>`; left out, the board has no NFC and phone-nfcd exits ([30](30-nfc.md)).
- The fingerprint sensor (`fingerprint`) is `sim` or `none`: the emulator says `sim`, a real phone leaves it out until its sensor has a driver ([31](31-lock-and-biometrics.md)).
- The location receiver (`gnss`, `location/`): `modemmanager` (the modem's GPS through ModemManager; both Snapdragon boards say this, **not yet tried on a real device**), `nmea:/dev/<node>[@<baud>]` (the kernel GNSS subsystem's `/dev/gnssN` or a serial port, read as NMEA 0183), `fifo:<name>` (a named pipe in the Shell's run directory, which the Shell makes the first time an app asks for the location; QEMU says `fifo:gnss.nmea` and the selftest writes NMEA into it, so the emulator also runs the real parsing path; when running it interactively one can write it oneself, e.g. `cat track.nmea > /run/phone/gnss.nmea`), `sim` (a simulated receiver). Left out, the phone has no receiver and `location.get` returns `this phone has no location receiver`; the developer machine (no SKU id) uses the simulated receiver, and the table `kario run -sku` simulates leaves it out ([22](22-developer-api.md) §4.7).
- When kernel sources are available (the copy in the Yocto work directory, or `PHONE_KERNEL_SRC`), it collects labels by following the `#include`s of the board dts and checks that every label the wiring references exists. The regulator on the OnePlus Nord N100 is called `vreg_l9a`, while on the Snapdragon 662 board it is `pm6125_l9a`, so a mistake is reported at generation time.
- Whole-phone boards (`class = "phone"`, §7.4): the SKU names neither display nor keypad (they are the phone's own) and must name its form factor (`device`); the panel less its dark rows (`inset`, as many at the top as at the bottom) must face the same way as the form factor (a landscape form factor says `rotate = 90`, which a panel with dark rows cannot); `scale` is 1–8, and one logical pixel measures 0.15–0.36 mm on the panel (the 2.8-inch 480×640 target at 2× has 0.178 mm; the floor is a 2.4-inch 240×320 panel at 1×, the ceiling twice the target); the physical size has the resolution's aspect ratio within 5% (swapped millimetres would otherwise slip past the previous rule); there is a `compatible`; every entry in `unverified` is one of the board's values; a key code table (`[keymap]`) has codes 1–767, key names from `keys.toml` and every key the form factor needs (§7.4), and a board that is no whole phone cannot have one. For a whole phone whose board names a Yocto machine (`machine`: the OnePlus 6T's `oneplus-fajita`, [39](39-oneplus-6t.md)), `gen` writes `sku.json` and the kas overlay (the machine, the SKU's name; the kernel's own device tree `dtb`, no overlay); a whole phone has no firmware package, and `package` (that is, `make sku-<name>`) fails, pointing to the board's flash script (`flash`). Whole phones without a Yocto machine yet: `gen` and `package` fail at once, pointing to the chroot kit (§6.2); `sku.py files <SKU> <dir>` writes only `sku.json`, the product layer and the kit's `phone.env`; the table `kario run -sku` simulates leaves whole phones out (they are test phones, not something apps are written for).
- `tools/sku_test.py` additionally checks that the form factor table matches `shell/device.go`, that phone-paint knows every key code, and that the key code values match `/usr/include/linux/input-event-codes.h`; and the whole-phone rules (each with an example that breaks it). `tools/phone_chroot_test.py` dry-runs the chroot kit: every step prints its plan on the build machine, the dry run changes nothing, and Nura's modem stack is not among what it stops; both scripts are shellcheck-clean.

## 3. What it generates

| Artifact | Content |
|------|------|
| `yocto/kas/generated/sku.yml` | Machine (`qemuarm64` / `kario-qcom`), `PHONE_SKU`; QEMU's screen size and memory; the device tree file name for real boards. The Makefile appends it after every kas configuration |
| `share/phone/sku.json` (`phone-sku` package) | SKU, board, form factor, display, keypad, memory, `web_gpu`, baseband backend, fingerprint sensor backend (phone-keystored picks by it), location receiver (`gnss`, which the Shell picks by), region, product, plus `fn` (the Fn layer) and `ctrl` (what stands in for Ctrl, [18](18-nokia-form-factors.md) §4.2) on QWERTY keyboards; whole phones also have `width`, `height` (the area drawn: the panel less its dark rows) and `scale`, which the Shell lays pages out for (documents' columns follow the logical width) and hands to the renderer in the handshake (§7.4); a whole phone with a keypad of its own also has `keymap` (code → key name) and `keypad = "builtin"`, which the Shell turns into a code-to-code table for the renderer's handshake (§7.4). When phone-shell is not given `--device`, it picks the form factor from this file and hands the Fn layer to the renderer during the handshake, and phone-paint uses it to produce characters while Fn is held ([23](23-renderer-protocol.md) §2); the memory limit of the web process is set by the memory tier, and whether it uses the GPU by `web_gpu`; when the board has a notification light and a backlight configured there are also `leds` (`notify`: name, colour), `backlight` and `keyboard_backlight`, which the Shell uses for the slow blink, to light the backlight and the keyboard backlight at the brightness set (Settings › Display and brightness) and to dim it before the screen goes off; with a light sensor configured there is also `light_sensor`, which automatic brightness reads; on a machine without a backlight the Shell uses a simulated one, and the Settings page says so ([11](11-platform-architecture.md) §"Then what is hal/") |
| `profile.d/20-product.json` | Product layer (the product name in About phone, etc.), stacked on top of the image's own configuration layers |
| Device tree overlay (real boards) | The display on DSI (compatible, reset pin, power supplies) and the keypad on I2C (interrupt, rows and columns, keymap, wake-up capable); the `phone-sku` recipe compiles it with dtc, and `fdtoverlay` merges it into the board's device tree (the kernel is built with symbols, `-@`), giving `phone-sku-<SKU>.dtb` |
| Firmware package `build/sku/<SKU>/firmware/` | Kernel (with phone-initramfs bundled, which mounts the root filesystem, [25](25-system-update.md)), the merged device tree (real boards), the root filesystem, `sku.json` and a manifest (SHA-256 and size of each file); it first checks that all files are present and only then replaces the old package |

The `kario-qcom` machine: one kernel carries the device trees of both boards; the kernel uses the same source as qemuarm64, with its configuration starting from the arm64 defconfig plus what the platform needs (Landlock, seccomp, namespaces, cgroup, nftables connection marks and the personal hotspot's NAT, and dm-verity / squashfs / nbd for system updates) and the module drivers the SKUs use. Packages keep qemuarm64's instruction set tuning (ARMv8.0 + CRC, which runs on both the A73 and the A53), so the shared cache is reused directly; mass production will switch to A73 + A53 tuning.

The QWERTY SKU mounts the same 2.8-inch portrait display in landscape: when phone-paint finds that the display's mode is exactly the form factor's dimensions with width and height swapped, it draws at the form factor's landscape size and rotates the picture 90° clockwise when putting it on the screen (dirty regions are converted accordingly).

## 4. Real-hardware testing on the Phicomm N1 box (planned, **not implemented**: waiting for network connectivity between the build machine and the box)

**Why this box**:
- The N1 is an Amlogic S905D: quad-core Cortex-A53, 2 GB RAM, 8 GB eMMC, with HDMI, two USB 2.0 ports and gigabit Ethernet.
- The mainline kernel has its device tree (`meson-gxl-s905d-phicomm-n1.dts`); HDMI goes through meson's DRM driver, and for hardware video decoding there is meson's V4L2 driver (in staging; which formats it can decode has to be measured).
- The A53 is exactly the little core of the Snapdragon 460 and 662. Of the devices we have, it is the cheapest real ARM hardware.

**What it cannot test**: baseband, the phone display (MIPI DSI), the matrix keypad (TCA8418), battery and power consumption, and Qualcomm's specific boot method and user space (ABL, QRTR). These have to wait for the Snapdragon devices (R16).

**What to prepare first**:
- Flash Armbian onto the N1: the community commonly uses ophub's amlogic-s9xxx-armbian; pick the s905d image.
- Connect an HDMI monitor, a USB keyboard and an Ethernet cable.
- Add the dedicated public key that the build machine uses to reach development boards (`kario-board-test`) to root's `authorized_keys`.
- A path from the build machine to the box: install Tailscale or ZeroTier on both sides, or use an SSH reverse tunnel through a machine both sides can reach.

**Step one: no BSP, our root filesystem on top of Armbian**. Copy the arm64 root filesystem built by Yocto to the N1: its instruction set tuning is ARMv8.0 + CRC, which runs directly on the A53. chroot into it, hand it the host's `/dev/dri`, `/dev/input` and cgroups, then test:

| # | What to test | How | Compare with |
|---|--------|--------|------|
| 1 | Text selftest | `phone-shell --selftest`: all cases pass; record the time of each case | The boot selftest on QEMU |
| 2 | Pixel selftest on a real screen | phone-paint draws to HDMI (DRM/KMS, no GPU), with the USB keyboard as the keys; run `--gui` once for each of the three form factors, recording frame times and CPU usage. When the display mode is larger than the form factor's dimensions, phone-paint draws at the form factor's size and centers it on the screen (a 480×640 picture in the middle of 1080p), so what you see is what the phone would show (unit tests ✓, **not yet on a real screen**) | `make pixel-selftest` on the dev machine |
| 3 | Memory | PSS of the 23 processes after boot; the memory-pressure case with a real 2 GB of RAM: first end the web pages of background apps, then end background apps | 23 processes totaling 234.0 MB on QEMU, 44.6 MB of it simulated cloud services that a production phone does not run (57 (internal document) verification baseline) |
| 4 | Web view | With the root filesystem of the web view image, run WPE WebKit on the A53: page rendering time, web process memory | The measurements in [15](15-web-vs-semantic-benchmark.md) |
| 5 | Benchmark | Rerun the semantic page vs web page comparison from `yocto/qemu-bench.sh` on real hardware | Same as above |

**Step two: add an N1 SKU and boot our own image from a USB stick**:
- What to add: a new machine (meson, with the kernel enabling meson DRM, eMMC and video decoding), the N1 board in `sku/boards/`, the display "HDMI", the keypad "USB keyboard".
- Boot: through the U-Boot that Armbian uses, boot our kernel and initramfs from the USB stick.
- Then test:
  - A/B updates, dm-verity and rollback on real storage: walk through the `yocto-ota-test` steps by hand on real hardware ([25](25-system-update.md));
  - hardware video decoding: play H.264 through the V4L2 memory-to-memory decoder (R24).

**Where the results go**:
- measured numbers go into the verification baseline;
- problems found go into this section and the corresponding topic documents.

## 5. Not done yet

- Real hardware: the boot method (Qualcomm's ABL needs a boot.img), the flashing package format, and the firmware of the various subsystems (signed firmware for the GPU, baseband and audio DSP has to come from the device maker) are all **not implemented**; the firmware package is currently the kernel, device tree, root filesystem and manifest.
- Selecting the overlay at boot by board ID (one image covering a board family) is **not implemented**.
- UNISOC T610: the mainline kernel has no display, baseband or USB support, so it has to wait for the vendor BSP (61 (internal document) §2.1); no SKU for now.

### 6.1 The three phones in detail

**OnePlus 6 / 6T** (mainline 6.18.54 sources checked on 2026-11-17):
- Panel: the 6 has a 6.28-inch 1080×2280, the 6T a 6.41-inch 1080×2340, both Samsung DSI command-mode AMOLEDs. In 6.18, `panel-samsung-sofef00` only takes the 6's `samsung,sofef00` (its mode says 68 × 145 mm); no driver in 6.18 takes the `samsung,s6e3fc2x01` the 6T's device tree names (in android-mainline the 6T's tree already says `samsung,s6e3fc2x01-ams641rw`); Nura's kernel drives it. So for a later BSP, only the 6's panel lights up on mainline 6.18; the 6T needs another kernel or a driver. The backlight is registered by the panel driver (DCS brightness 0–1023) under the DSI device's name, `ae94000.dsi.0`; it is the system's only backlight, so `hal/backlight` finds it by itself.
- Keys: power is the PMIC's `pm8941_pwrkey`, volume up and down gpio-keys "Volume keys"; there is also a Hall sensor (SW_LID, for flip covers), which has no keys and which the renderer leaves alone. OnePlus's three-position alert slider has only its pin configuration in the mainline device tree, no input device.
- Sound: mainline drives the 6's loudspeaker amplifier (MAX98927) but not the 6T's (TFA9894), whose link the device tree deletes: on mainline the 6T has only the earpiece and headphones; whether Nura's kernel adds it is **unverified**.
- Notification light: the 6 has the PMI8998 LPG's RGB LED (the multicolor LED class device `rgb:status`), the 6T none.
- The battery is the bq27411 fuel gauge (the first power supply of type Battery); the vibrator is PMI8998's haptics driver, in Nura's kernel (force feedback on an input device), not in mainline 6.18.
- The sensors (light, proximity) sit behind the SLPI DSP, which Nura reads through hexagonrpcd and libssc, not IIO: `hal/sensor` does not see them, so automatic brightness and turning the screen off at the ear in calls cannot be tested on these two.
- NFC: the chip is the NXP PN553 in the NQ330. When its device tree was first submitted in 2023 the author said it recognised card types but could not read them in full, and withdrew it; sdm845-next's commit message of 2025-11 still says "there isn't upstream driver, just ugly hacks"; in 2026-04 the device tree node went into mainline (`nxp-nci-i2c`). That driver sits on the kernel's NFC subsystem (netlink, the neard path), without a raw NCI node phone-nfcd could open (`nci:/dev/…`), so the boards leave `nfc` out; Nura lists it as unusable too.
- USB: the phone does not power OTG devices, so a keyboard needs a powered adapter (the community says, **unverified**); a Bluetooth keyboard first.

**Redmi Note 4X** (kernel sources checked on 2026-11-12 and 11-17): mainline 6.18 has its device tree, `msm8953-xiaomi-mido.dts`, but its screen there is only the framebuffer the boot loader leaves (simple-framebuffer, 1080×1920), with no DSI panel driver: it displays, but cannot turn the panel off or change the brightness, so screen-off power saving cannot be tested on mainline; the panel drivers (five vendors: BOE ILI9885, EBBG R63350, NT35532, OTM1911, Tianma NT35596) and the PMI8950 backlight are in the msm8953-mainline kernel Nura uses. The notification light is the AW2013's red, green and blue LEDs (`red:indicator` and so on, which the driver blinks by itself), and the only keys are volume up (GPIO) and power and volume down (the PMIC's `pm8941_pwrkey`, `pm8941_resin`). The touchscreen is FocalTech in the mainline device tree (`edt,edt-ft5406`); some phones have a Goodix GT917D. The mainline device tree fixes the USB controller in device mode (no OTG) and has no fuel gauge or vibrator; on the msm8953 kernel, OTG needs g_serial off or the device plugged in before boot (the community says). Mobile data relies on the IPA 2 driver (`CONFIG_QCOM_IPA2_LITE`, merged into Nura's msm8953 kernel in 2024), which nobody has confirmed on the 4X. So this phone mainly tests CPU, memory and rendering times, and calls and SMS.

### 6.2 The chroot kit (`tools/phone-chroot/`, prototype, **not yet on a real phone**)

It lives in `tools/`, not `yocto/`: it builds nothing, uses a built image, and runs on the build machine, directing the phone over SSH. Two POSIX sh scripts, shellcheck-clean: `kario-phone.sh` (build machine: `--sku` picks the whole phone's SKU; it pushes the image, starts the chroot on the phone, runs the tests, fetches the results and restores the phone, step by step) and `on-phone.sh` (runs as root on the phone, busybox's sh will do: what each step really does). `--dry-run` prints on the build machine what each step would do here and on the phone, without connecting or changing anything; on the phone, `on-phone.sh --dry-run <step>` prints what it would do given the phone as it is.

**The image**: Yocto's `phone-image-<machine>.rootfs.ext4` (or `.ext4.zst`), from qemuarm64 (the default) or kario-qcom: both have the same instruction set tuning (ARMv8.0 + CRC, which runs on the A75, A55 and A53), the binaries are the same on all SKUs, and the kit only replaces `sku.json` and the product layer with the whole phone SKU's (`tools/sku.py files`). The qemuarm64 build already makes ext4 (the A/B disk's slot) and ext4.zst, and kario-qcom's `IMAGE_FSTYPES` has ext4: **no new image type is needed**. The phone loop-mounts the ext4 rather than unpacking a tar: owners, extended attributes (file capabilities) and device nodes stay as built, the build machine needs no root, and the chroot's root is still a mount point (the app sandbox's pivot_root needs that). Everything on the phone is under `/var/lib/kario-chroot/`: the image, its mount point, our state (`/var/lib/phone` and `/root`, bound into the chroot, so the image itself is hardly written) and each run's results. **Images built before this change cannot be used**: their Shell takes the USB controller and puts a drop-everything rule on `usb0`, cutting off Nura's USB network (that is, SSH), and it ignores `scale`; the kit refuses an image without this change (`--force` goes on regardless, over Wi-Fi). So first `make yocto-build` from this tree.

**Steps** (`tools/phone-chroot/kario-phone.sh --sku oneplus-fajita-t9 <step>…`):

| Step | What it does |
|------|--------|
| `push` | First checks that the build machine has this phone's backup (`~/kario-phone-backup/<board>-<serial>`, the serial from the kernel command line's `androidboot.serialno`, its SHA-256 sums matching; refused without one unless `--force`, [39](39-oneplus-6t.md) §3.5); makes the SKU's files and copies them to the phone with `on-phone.sh`; writes the image, unpacked, over SSH (skipped when the phone has the same image, refused while it is mounted, needs some 2 GB) |
| `setup` | Checks the board (the device tree's compatible), aarch64 and loop devices; stops the Nura services that would compete (display managers tinydm, greetd, sddm, lightdm, gdm: only those running, noted down), ends the session's pipewire, pulseaudio, callaudiod, feedbackd, chatty, gnome-calls and mmsdtng; loop-mounts the image, binds `/dev`, `/sys` and `/run` recursively as slaves (unmounting in the chroot never unmounts Nura's), mounts a new `/proc`, tmpfs on `/tmp` and `/var/volatile`; writes the SKU's `sku.json`, the product layer and Nura's `resolv.conf`; on a unified cgroup hierarchy makes `/sys/fs/cgroup/kario` marked `trusted.delegate` (the Shell only takes a delegated group, with a subgroup per app); switches to the unused console 8 (otherwise keys typed for the Shell also reach console 1's login prompt); sets UCM's `HiFi` with Nura's alsaucm; notes the facts (`facts`) |
| `selftest` | The compatibility run in the chroot (`phone-shell --cts`: the selftest plus the CTS cases, push over TLCP, as the image's boot selftest), timeouts times `--timeout-scale` (2); detached on the phone, the build machine asks every 20 seconds, and the link dropping meanwhile does not matter (on a board that can suspend, the selftest's suspend case really suspends the phone once) |
| `pixel` | The selftest drawn four times by phone-paint, headless: the SKU's own panel (1080×2180 at 4.5×) and the three form factors (`--device`), keeping the PNGs and each run's time |
| `bench` | The semantic page vs web page comparison (`bench/bench.py`, the same commands as `yocto/qemu-bench.sh` without the power-off); it needs python3, which only the web view image has (`make yocto-web-build`); the default image skips it and says so |
| `collect` | Fetches all the phone's results into `build/phone/<SKU>/results/` |
| `all` | `push setup selftest pixel bench collect`: the unattended part |
| `shell-start`, `shell-stop` | The Shell on the real panel (`--gui auto`, `PHONE_PAINT_TRACE=1` logs the animations' frame times), keys from the keyboard and the phone's own keys, the Shell's own telephonyd on the SKU's modem backend (ModemManager); with elogind-inhibit, logind's handling of the power key and the Hall sensor is held off; stopping keeps the services' logs |
| `mem` | 60 seconds after `shell-start`, the PSS of each of our processes (rooted in the chroot, in the cgroup, and their descendants) and the total |
| `power-start`, `power-stop` | Notes the battery before and after standby (the fuel gauge's `charge_now`, `energy_now`, the percentage, the suspend count), works out the average current and power, lists the top wake-up sources (with debugfs mounted) |
| `power-sample[=seconds]` | `current_now` every second (the draw with the screen on) |
| `teardown` | Ends all our processes, deletes what a Shell left in Nura's kernel (its nftables table, a USB gadget, networkd files), unmounts everything, deletes the cgroup, switches back to the console it found, starts the services `setup` stopped; `--purge` deletes the image, state and results too. Session programs ended at setup come back at the next login or reboot, the sound card's mixer settings at the next reboot |

**What Nura keeps, and how our services reach it**: Nura's D-Bus, ModemManager, rmtfs, pd-mapper and tqftpserv (the modem stack), NetworkManager (SSH over the USB network or Wi-Fi), bluetoothd and sshd keep running. Our image has no ModemManager (telephonyd is its client; the BSP will bring one), so Nura's cannot be stopped: with `/run` bound into the chroot our processes are on Nura's system bus (`/run/dbus/system_bus_socket`), and telephonyd calls ModemManager as root. With no systemd in the chroot, the Shell starts its services itself (`--services spawn`): run interactively, the telephonyd it starts takes the image SKU's modem backend (`modemmanager`), while the selftest and scripts keep the simulated baseband (they call numbers of the simulated network; `privateModem` in `programs/shellcmd`, unit test ✓). Wi-Fi belongs to Nura's NetworkManager and our iwd does not run, so Settings' Wi-Fi does not work in the chroot; mobile data: telephonyd still connects the bearer through ModemManager with the APN database's APN, but the chroot has no systemd-networkd, so the Shell does not configure the cellular interface's addresses, and Nura's NetworkManager may connect the modem's bearer and configure the interface itself; whether the two get in each other's way is **unverified**; Settings' Bluetooth talks to Nura's bluetoothd (**unverified**). When the Shell finds the USB controller held by another gadget (Nura's USB network), it leaves USB alone: no gadget of its own, no USB firewall (`shell/usb.go`, unit test ✓, which fails without this).

**What the owner does first**:
1. Buy the phones: a OnePlus 6T (or 6); a Redmi Note 4X, Qualcomm version (mido, original screen; 3 GB or 4 GB of RAM both do).
2. Unlock: on the OnePlus, update OxygenOS twice (both slots on the latest), turn on OEM unlocking in the developer options, `fastboot oem unlock`; on the Redmi, apply for Xiaomi's unlock and unlock with Mi Unlock.
3. Back up first, before flashing Nura ([39](39-oneplus-6t.md) §3.5: TWRP runs from RAM and copies the IMEI and the calibration off). Flash Nura: download the v26.06 images from the [install page](https://nura.eco/install/) (the OnePlus 6 and 6T each their own, the 4X Generic MSM8953), or make them with pmbootstrap; pick the "console" interface (no graphical one, so no display manager to stop) and install the SSH server; the OnePlus also needs `fastboot erase dtbo`.
4. Enable SSH: add the build machine's key for development boards (`kario-board-test`) to root's `authorized_keys` on the phone, `PermitRootLogin prohibit-password`; or use the default user with `--become doas` (doas without a password).
5. Network: plug the USB cable into the build machine; on Nura's USB network the phone is `172.16.42.1` (the kit's default); then join Wi-Fi with nmcli on Nura: when the keyboard takes the USB port, or USB has to come out to measure standby current, use Wi-Fi with `--phone root@<address>`.
6. Keyboard: pair a Bluetooth keyboard with bluetoothctl on Nura (phone-paint in the chroot then reads it directly); an OTG keyboard does not work on the OnePlus (the same device tree, USB device only), and OTG on the 4X is **unverified**.
7. Build: `make yocto-build` from this tree; for the web view benchmark also `make yocto-web-build`.

## 7. KaiOS phones: replace from boot, or interface with the system base (survey of 2026-11)

With a KaiOS phone in hand there are two paths: **(a) interface with the base**: keep the vendor's boot loader, kernel and vendor partition, replace only Gecko and Gaia with our user space, and reach the hardware through Android's HALs (this is what Ubuntu Touch and Sailfish OS do on Android phones with Halium / libhybris); **(b) replace from boot**: the mainline kernel plus our whole system, the same as on the Snapdragon 662 / 460 (R16). What follows comes from public sources and the local mainline kernel sources (6.18); **not tried on a KaiOS phone**.

**Conclusion: take (b), only on models that already have a mainline port; do not do (a).** By Nura's device list, no KaiOS phone has a maintained mainline port today (reason 4), so we do not work on KaiOS phones for now, and real-phone testing uses the phones of §6 first. Reasons:
1. **(a) does not spare flashing the boot partition either**. Halium has to change the kernel configuration for systemd, rebuild the kernel and flash its own boot image; the boot loader of KaiOS phones is locked and accepts only a boot image signed by the vendor. The ways to write boot (EDL, unlocking, `fastboot oem sudo` on the 2780 Flip) are the same for both paths: both have to take the hardest step, and after it (a) still carries a layer of vendor user space.
2. **The vendor kernels are too old for our system to start on**. The Nokia 8110 4G on KaiOS 2.5 has a 3.10 kernel; the systemd 259 in our image needs 5.4 or later (its README calls this the "minimum baseline"), and Landlock, the cgroup freezer and memfd, which the sandbox, the sound rings and the media surfaces use, are all newer than 3.10 too (§7.5).
3. **There is no ready Halium**. Halium only has versions for Android 7.1 and 9–13, and since 20.04 new Ubuntu Touch ports need 9.0 or later; the base of KaiOS 2.5 is Android 6. libhybris also first needs Android's bionic and init rebuilt with its patches, and KaiOS phones have no LineageOS device tree to build from.
4. **Mainline was ported to these phones, but nobody maintains the ports now**. By Nura's device list ([Devices](https://wiki.nura.eco/wiki/Devices), checked 2026-11-14), the ports of the Nokia 8110 4G, 6300 4G, 8000 4G and 2780 Flip are all "archived", no longer supported; the only KaiOS phone still in a supported category is the 2720 Flip, in "downstream", on the vendor's 3.10.49 kernel with very few features; the generic package `qcom-msm8909` (Snapdragon 210) is in "testing", and whether it boots these Nokias is **unverified**. When they were ported in 2022, keys, Wi-Fi, Bluetooth, charging, the display and the backlight worked, and the modem came up through QRTR and rmtfs; the device trees are still in the community msm8916-mainline kernel, and the 2780 Flip's is in the msm89x7-mainline kernel (§7.2). telephonyd's ModemManager backend and phone-paint's DRM and evdev plug straight into this path, but taking (b) on a KaiOS phone means carrying on these archived ports ourselves.
5. **Security updates**. On (a) the kernel and the HALs stay at the vendor's last release, and our system update ([25](25-system-update.md)) can update only user space; (b) follows mainline and the long-term support releases.

(a) stays only as a fallback: when one kind of hardware never gets a mainline driver, add a vendor backend in the service that manages it (the approach of [11](11-platform-architecture.md) §16), rather than putting the whole system on the vendor base.

Whichever path, KaiOS phones are test phones only: they all have 512 MB of memory, half our smallest memory tier, with no room for the web view (§7.2); their partition tables have no A/B either, so our system update needs the partitions rearranged (§7.3).

### 7.1 How KaiOS is built

KaiOS was forked from Firefox OS (B2G) and has three layers: Gaia is the UI and the apps, written in HTML / JS; Gecko is the web runtime and doubles as the device interface; Gonk is the base: the Linux kernel plus Android's HALs, the vendor's binary libraries and daemons such as rild. There is no ART, so Android apps cannot run; Gecko itself is the "system_server" and calls Android's HALs directly.

| Layer | KaiOS 2.5 | KaiOS 3.x | KaiOS 4.0 |
|----|-----------|-----------|-----------|
| Runtime | Gecko 48 | Gecko 84 | Gecko 123 |
| Android base of Gonk | Android 6.0: vendor libraries and the system in the same system partition | Android 10: vendor libraries in a vendor partition of their own (Treble) | Android 14 |
| Kernel | 3.10 (Nokia 8110 4G) | 4.x (**unverified**) | The GKI kernels Android 14 supports are 5.10–6.1; which one this generation of phones uses is **unverified** |
| Modem | The rild socket, the Firefox OS way (that KaiOS 2.5 kept it as it was is **unverified**) | Gecko's `nsRilWorker` calls `android.hardware.radio@1.1::IRadio` over HIDL | From Android 13 it calls `IRadio` 1.6 instead (in the same file) |
| Display | Firefox OS's `GonkDisplay`: framebuffer or hwcomposer (**unverified**) | `GonkDisplay`: framebuffer (fbdev), DRM, or hwcomposer plus gralloc, chosen per model | Same as left |
| Keys | Since Firefox OS, Gecko has carried a copy of Android's InputReader (**unverified**) | Gecko carries a copy of Android's EventHub, InputReader and InputDispatcher, reading evdev | Same as left |
| First phone | Nokia 8110 4G | Nokia 2760 Flip | TCL Flip 4 (Qualcomm SM4635, 5G) |

So keys are the same on both paths: the vendor kernels report the keypad as evdev too.

So they serve only as test phones, for the modem, keys, display, suspend and current draw; a 512 MB memory tier is needed, with web nodes turned off on it (**not implemented**).

**Why the scale is 4.5**: our layouts are designed for 480×640 at 2×, that is 240 × 320 logical pixels. All three phones are 1080 wide at about 400 ppi: 1080 / 4.5 = 240, so across the screen everything is as on the 9-key bar phone (the same columns, the same line breaks, documents' 32 columns, the main menu's 3 columns), only with more rows down it (484 on the 6T without its dark rows, 427 on the 4X, 320 on the target). A logical pixel is 0.28 mm on these panels and 0.178 mm on the target's 2.8-inch one: body text (11 logical pixels) is 3.1 mm high, about 1.6 times the target's, close to Android's largest font size, readable at arm's length. The three others weighed: 2× in the middle (what the renderer did already) uses 44% of the panel's width, with a logical pixel of 0.126 mm, body text of 1.4 mm and the smallest text of 1.1 mm: too small; 3× (Android's xxhdpi class) gives 360 × 780 logical pixels and text the target's size (0.189 mm), but a different layout across, which cannot show the target's layout; 4× has crisper lines but is 270 wide, again another layout. The generator wants a logical pixel of 0.15–0.36 mm (§2), which 2× on these phones fails. For the cost of drawing the target's pixel count (the renderer's work as on the target), use `--device bar-t9`: 480×640 at 2× in the middle. A developer machine can show the whole phone too: `phone-shell --device bar-t9:1080x2180@4.5` (`DeviceByID` takes `@<scale>`).

**Two decisions**:
- The volume keys do not double as up and down: the power key's short press has to stay screen on / off (standby current depends on it), and up and down without OK and Back operate nothing; in a call the volume keys set the earpiece volume; Bluetooth keyboards drop off after a short idle and reconnect at the next press, so keys would change meaning as the keyboard comes and goes, which makes testing more confusing. Interactive tests use a keyboard; the unattended part (selftest, benchmark, standby) goes over SSH and needs no keys.
- The touchscreen is there but unused: Kario is a keyboard-first system, and tapping where one looks would hide the keyboard navigation's faults, which is what is being tested; phone-paint takes only keyboards and mice, and a touchscreen is neither, so it does not read it.

**A whole phone's own keypad (`[keymap]`, unit tests ✓, **not tried on a phone**)**: the mapping above assumes a HID keyboard, with only the power and volume keys on the phone itself. A KaiOS-class phone's keys are a matrix keypad in its device tree, with codes the board chooses (the soft keys reporting `KEY_MENU` and `KEY_BACK`, the green key `KEY_SEND`, the red key `KEY_POWER`, the digits the number row's `KEY_1`…), which phone-paint's table does not know. The board file's `[keymap]` says which key of `keys.toml` each code the kernel reports (in decimal) is, listing every key of the phone's keypad, those whose code is already ours too:

```toml
[keymap]
139 = "soft-left"   # KEY_MENU
158 = "soft-right"  # KEY_BACK
231 = "call"        # KEY_SEND
116 = "end"         # KEY_POWER: the red key is the power key too (no power_key)
352 = "ok"          # KEY_OK
2 = "1"             # KEY_1
```

- `tools/sku.py` checks: only a whole phone may have one (a keypad module's codes come from its matrix); a code is a decimal number 1–767 (`KEY_MAX`); a key name is in `keys.toml`'s `[keys]` (which gained `power`, `KEY_POWER`, for it); every key the form factor needs is in the table (as for keypad modules: the soft keys, OK, back, clear, call, end, the arrows, plus 0–9, `*` and `#` on the 9-key pad, 26 letters, space and Shift on the full keyboard); `unverified` may mark one of its codes (`keymap.139`). With a table, the whole phone's `sku.json` has `keypad = "builtin"` and the `keymap` in code order; `tools/sku_test.py` has a wrong example for each rule.
- The Shell checks it again when it reads `sku.json` (a bad table keeps phone-shell from starting, as an unknown form factor does) and turns it into "the code reported → that key's code here" (the codes of `keys.toml`, `keyCodes` in `shell/sku.go`; `tools/sku_test.py` checks the two agree), which goes to the renderer as `device`'s `keymap` in the handshake ([23](23-renderer-protocol.md) §1); with `--device` choosing another form factor it goes too (the phone's keys do not change with how it draws). Unit tests: `TestBoardKeymap`, `TestKeymapHandshake`.
- phone-paint looks every key up in the table first and reads it as our code from then on: the 9-key pad's long press, the soft keys, the end key that is the power key too all work as with a keypad module (`a_boards_keymap_reads_its_keys_as_ours` in `kms.rs`). Only the codes in the table change, all others are read as they are; a USB or Bluetooth keyboard plugged in goes through the same table, so it lists only the codes of this phone's keypad. An input device with any key of the table counts as a keyboard: a matrix keypad may lack Enter, and before only devices with Enter, a power key or volume keys did (`a_matrix_keypad_is_a_keyboard_by_its_keymap` in `input.rs`).
- phone-gui does not read the table (**not implemented**). No whole-phone board has a `[keymap]` yet: there is no KaiOS phone's board (§7.7); its codes are to be copied from that phone's device tree and confirmed on the phone.

**How the Shell uses the new fields**: `sku.json` has `width`, `height` and `scale` more (`shell.SKU`). `SKUDevice` replaces the form factor's own size and scale with the panel's, documents' columns follow the logical width (`Device.WithScale`); the handshake hands it to the renderer, and phone-paint draws so, in the panel's middle when the panel is bigger (the dark rows). Unit tests: `TestWholePhoneSKU`, `TestWholePhoneHandshake` (the size in the handshake, the main menu's 3 columns, a web page's area at 4.5×), and one more case for `letterbox` in `kms.rs`. Two more changes are for the chroot (§6.2): the Shell leaves alone a USB controller another gadget holds (`TestUSBLeavesAForeignGadgetAlone`), and run interactively, the telephonyd it starts itself takes the SKU's modem backend (`TestPrivateTelephonyFollowsTheSKU`).

**What whole phones still lack** (all **not implemented**):
- audiod switching UCM: a phone's sound card needs its mixer set per use (playback, call, headphones). The OnePlus 6T's whole-phone image has it ([20](20-audio.md) §10, **not tried on a phone**); other phones need their `--ucm-*` in their device configuration; the QEMU image the chroot uses has no alsaucm and passes none of those flags, so there Nura's alsaucm still sets `HiFi` first, and call audio needs a manual switch to "Voice Call".
- The proximity sensor (screen off at the ear in calls): the OnePlus's sits behind the SLPI, and `hal/sensor` has only the light sensor, read through IIO only.
- Dark rows only as many at the top as at the bottom: a phone with a notch but no rounded corners below loses rows at the bottom for nothing; the renderer would have to take an offset (a protocol field). A panel with dark rows cannot be turned either (a landscape form factor with `rotate`).
- The 512 MB tier (§7.2).
- A Yocto machine and BSP for whole phones (kernel, boot, firmware partitions).

### 7.5 What the sandbox loses on old kernels

| Mechanism | Kernel requirement | Where we use it | 3.10 (KaiOS 2.5) | 4.x (KaiOS 3.x, version **unverified**) | What the code does without it |
|-----------|--------------------|-----------------|------------------|-----------------------------------------|-------------------------------|
| systemd 259 | 5.4 or later | init, service units, socket activation, the fd store ([11](11-platform-architecture.md) §14) | No | No | Older kernels are not supported |
| Landlock | 5.13 or later; limiting TCP from 6.7, limiting signals and abstract sockets from 6.12 | The file allow-lists of apps, helpers and the renderer ([17](17-app-sandbox.md) §3) | None | None | The launcher adds rules by the kernel's ABI version and leaves the layer out when there is none; the self-check marks the matching items "skipped"; only the selftest step that checks the USB sharing helper requires it. The Shell records `landlock` as missing (also where it is built but not enabled in `lsm=`, which the reason says); before ABI 4 `landlock-tcp` is missing too, before 6 `landlock-scope` |
| seccomp | Filters from 3.5; the `seccomp()` system call and `TSYNC` from 3.17; `SECCOMP_RET_KILL_PROCESS` from 4.14 | Apps, helpers, the renderer ([17](17-app-sandbox.md) §4) | No `seccomp()` (unless the vendor backported it, **unverified**) | Yes; before 4.14 "kill the process" degrades to killing the thread | The launcher calls `seccomp()` with `TSYNC` first; where the kernel lacks the system call (ENOSYS) it installs the filter on its own thread with `prctl(PR_SET_SECCOMP)`: before exec the launcher is locked to that thread, after exec only that one is left, so the app runs under the filter all the same (`TestSeccompWithoutTSync` execs once to check). The USB sharing helper filters all its threads after it started, which takes `TSYNC`, so it does not start. Without filters at all (no `CONFIG_SECCOMP_FILTER`) no app starts |
| cgroup v2 | Unified hierarchy from 4.5; the cpu controller 4.15; PSI 4.20; the freezer 5.2; `CLONE_INTO_CGROUP` 5.7; `cgroup.kill` 5.14 | Per-app memory limits, CPU weights, freezing, the low-memory killer ([17](17-app-sandbox.md) §5) | v1 only | Partly | Probed feature by feature at start. v1 only or the hybrid hierarchy, or no delegated group: no app groups, freezing falls back to SIGSTOP, no per-app memory or process limit or CPU weight. With a group, item by item: without `cgroup.freeze` the app's whole process group gets SIGSTOP; whichever of the memory, pids and cpu controllers is missing, that limit is missing; without `CLONE_INTO_CGROUP` the launcher waits on a pipe until the Shell has moved it into its group; without `cgroup.kill` the Shell sends SIGKILL to the group's processes one by one until it is empty; without `memory.pressure` only available memory counts |
| `MemAvailable` in `/proc/meminfo` | 3.14 or later | The low-memory killer ([17](17-app-sandbox.md) §5.1) | Missing (unless the vendor backported it, **unverified**) | Yes | Estimated as MemFree + Buffers + Cached − Shmem (it used to count as 0: the system was always "low" and ended background apps one after another) |
| memfd and seals | 3.17 or later | audiod's sound rings, the surfaces of mediad and the Shell ([11](11-platform-architecture.md) §14) | None (Android 6 uses ashmem) | Yes | No fallback: neither sound nor media frames can be passed. Nothing stands in with ashmem or tmpfs files: they have no seals, and an app could truncate the shared memory and crash a service with SIGBUS |
| pidfd | 5.3 or later | Go's runtime signalling and waiting for child processes | None | None | Go falls back to pids itself; an app the Shell took over from the previous Shell is not its child, and its pid may be reused after it exits, a small window |
| Namespaces (mount, pid, ipc, uts, net), no_new_privs | 3.8 or later, 3.5 or later | Apps, helpers, web processes ([17](17-app-sandbox.md) §2) | Yes | Yes | Without them no app starts |
| dm-verity | 3.4 or later | Root filesystem verification for system updates ([25](25-system-update.md)) | Yes | Yes | The initramfs sets up verity and checks the signature itself, which works as on QEMU; but boot is flashed by us and the vendor's boot loader does not know our key, so the chain of trust only starts at boot, and that holds for (b) too |

**Degrading (implemented: unit tests ✓; **not tried** on an old kernel)**: the Shell probes once at start (`sandbox/probe_linux.go`, `shell/cgroup.go`, `shell/kernel.go`) instead of guessing from the kernel version: Landlock is asked its ABI version, seccomp tried with calls that install no filter, cgroups looked at for the files in the delegated group, and `CLONE_INTO_CGROUP` tried for real by starting an sh that does nothing in the Shell's own group. The result goes into the Shell's log (one line in all, one line each for what is missing and what is done another way: `kernel: missing …`, `kernel: fallback …`), the diagnostic dump (`kernel` in `phone-shell --dump`) and the compatibility report (the `sandbox` field: the kernel version, `missing` protections and `fallback`s, each with why; the report's signature covers it, [22](22-developer-api.md) §11). No protection that is not there is claimed: without the memory controller, say, the log's cgroup line names no memory limit. Each item is one of three:

| Handling | Which | Why |
|----------|-------|-----|
| No app starts (as when the Shell runs as root and finds no `phone-sandbox`: the Shell runs, and opening an app says why) | seccomp filters, no_new_privs, the namespaces apps get (mount, pid, ipc, uts, net); only when the Shell runs as root (the device); web processes and the USB sharing helper do not start either | These layers have no stand-in: without them an app can debug other processes, change its view of the file system, gain privileges through a setuid program. System apps are handled the same: they read untrusted input too (the browser, SMS) |
| Runs, and says so (the report's `missing`) | `landlock`, `landlock-tcp`, `landlock-scope`, `cgroups` (no per-app groups), `cgroup-freezer`, `cgroup-memory`, `cgroup-pids`, `cgroup-cpu`, `memfd-seal`; on a developer machine also `uid` (the Shell is not root: apps run as its user, without namespaces) | One layer is short, the others hold (own uid, namespaces, seccomp); the user can use the phone, and certifiers and payment services see what is short and may refuse, as they may on seeing `unlocked` |
| Done another way, nothing lost, only recorded (the report's `fallback`) | `seccomp-tsync`, `seccomp-kill-process`, `clone-into-cgroup`, `cgroup-kill`, `psi`, `pidfd`, `mem-available` | The same protection, the old way; `seccomp-tsync` costs USB file sharing (its helper does not start) |

- The compatibility test still decides PASS / FAIL by cases and capabilities: a device short of protections can still PASS, and the certifier decides by the report's `sandbox.missing`; `phone-cts-verify` lists them item by item. An older report without the field verifies as it did; an older `phone-cts-verify` drops the field when reading a new report, the digest no longer matches and it fails: use this version.
- Unlike the earlier proposal, memfd seals are under "says so", not "no app starts": we never stand in with unsealed memory, so without them sound, video, the camera and web pages just do not work, apps never get unsealed shared memory, and refusing apps would gain nothing.
- The device attestation (`attest` called by apps, used by the wallet and payments) does not carry the missing layers yet (**not implemented**): the signed message holds only the boot state (`verified-boot:…` / `unlocked`), one more item takes a new message version, and the relying parties (the wallet compares against `unlocked`) must change with it; only the signed compatibility report carries them now. Settings does not show them either (**not implemented**); the sandbox self-check still marks the checks of a missing layer "skipped".
- The systemd threshold cannot be lowered: either replace init (the Shell's fd store and app scopes depend on systemd and would need rewriting) or take path (b).
- Verification: unit tests on fake cgroupfs trees (4.19, 5.4, 5.10, 6.18 and a vendor kernel with the memory controller on v1) and with old kernels' system call errors injected (ENOSYS, EINVAL, EOPNOTSUPP), each fixed behaviour first confirmed to fail before the change (`TestFreezeWithoutFreezer`, `TestStartWithoutCloneInto`, `TestKillWithoutCgroupKill`, `TestMeminfoWithoutMemAvailable`, `TestSeccompWithoutTSync`); the developer machine's own 4.18 kernel has no Landlock, pidfd or `clone3`, and the probes run for real there. QEMU's mainline kernel lacks nothing, which the selftest case "内核特性" (kernel features) checks (**not verified** on QEMU). On a real 4.x or 5.x vendor kernel **not tried on a phone**.

### 7.6 The commercial side

- **KaiOS Technologies**: the system is free for handset makers, and the company earns from service fees (FOTA, for example), advertising (KaiAds), the app store and search (public statements from 2018 and 2019; whether this still holds is **unverified**). Neither path uses Gecko, Gaia or KaiStore, so neither needs its license; what (a) uses is the BSP under Gonk, which belongs to the chip maker and the handset maker. What working with it could bring is its experience integrating BSPs on low-end chips and passing carrier certification; its store and advertising compete with our store and push, and the room for cooperation is **unverified**.
- **The vendor binaries** (HALs, rild, the modem's and Wi-Fi's firmware): licensed by the chip maker to the handset maker, with no right for third parties to redistribute them (UBports' porting guide also treats them as "blobs" to be taken from the device). Both paths can only use the copy already on the phone, and the image does not carry them: (b) only reads the coprocessors' firmware from the firmware partitions at boot; (a) also loads the vendor's user-space libraries into our processes, with no source to look at when something goes wrong.
- **The community's ways of flashing** (EDL loaders, unlock packages) are fit only for development and enthusiast builds, not as a product channel. Products go on our own hardware (61 (internal document), R16); the use of KaiOS phones is as cheap test phones, like the Redmi Note 4X in §6.
