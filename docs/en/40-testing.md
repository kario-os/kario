# Testing: methods and strategy

> How Kario is tested: the layers, the command for each, which hardware is simulated, how one scenario script runs both on the developer machine and in the emulator, what to run for what change, what to run before publishing, and the rules for writing tests. The commit and CI flow is in [38](38-contributing.md); each round's results are in [13](13-prototype.md) §5 and the internal verification baseline (57 (internal document)).
> Status: the commands and flows written here have been used on the developer machine (RHEL 8, x86-64, 48 cores) and in QEMU (qemuarm64, TCG) (2026-11-19; the runs in parts on QEMU and the developer machine and their times: 2026-11-25); on a real phone (a OnePlus 6T, §7) the same kit ran in the chroot (2026-11-21 to 11-23) and on the whole phone (2026-11-24 to 11-27, [39](39-oneplus-6t.md) §16), and the changes since are **not tried on a phone**.

## 0. Summary

- **One scenario script runs everywhere**: `shell/selftest.script` (208 cases) runs headless on the developer machine (the text UI), through the pixel renderer in three form factors, and at boot in QEMU's two images; the compatibility test (CTS) is that plus capability coverage and a signed report. On a real phone it is the same script (§7).
- **Simulations stand in for hardware, and their limits are written down**: the baseband, ModemManager, Wi-Fi, Bluetooth, NFC, satellite positioning, sensors, fingerprint, camera and the update server all have a simulated side (§3); the real-phone part of each is marked **not tried on a phone**.
- **Every bug fix comes with a test that fails on the old code**, seen failing before the fix; **every capability is called at least once**, or the CTS fails; **every place that parses untrusted input has a fuzz target** (67 targets).
- **Run what the change needs**: CI picks by the change ([38](38-contributing.md) §3); before publishing the whole set runs on the developer machine and in QEMU (§5).
- **Results go into the docs as they are**: ✓ names only the environment it ran in and the date, simulated things say "simulated", what has not run says **not verified**.

## 2. The scenario script

`shell/selftest.script` is a key script: `== title` starts a case, one command per line below it, run by `Runner` in `shell/headless.go`. The commands are of three kinds:

- **Keys and waiting**: `key`, `type`, `long`, `tap` (pixel renderer only), `wait text [ms]`, `wait-re regexp`, `gone text`, `at screen`, `key-if key text ms`. `wait` and `wait-re` also accept a toast shown since the last input (a key, typing, a touch), even one already gone: a toast stays 2.5 s and on a busy machine the runner can look too late, while a person watching the screen saw it; `gone` looks at the screen as it is. `audio category` and `audio paused category` likewise accept a stream phone-audiod reported in that state since the last input or the last `audio` step, even one that has ended: Hongyan's voice message is 1 second long and goes into the ring all at once before the stream is closed, and in the QEMU boot selftest the runner once did not see it at all while the guest stalled, though a person heard it; counting from the last `audio` step too keeps a second `audio call` from passing on the ringback of the dialing. A stream never in that state still fails, and `audio idle` looks at now. Vibration (`vibrated`), the notification light's blinks (`light-blinks`) and emergency alerts (`alerts`) are counted and the screen reader (`spoken`) keeps what it said, so none of them misses a short one; `light`, `backlight` and `keylight` check states that last. After a deep link into an app (a palette command such as 「设置 · 应用权限」) and before the next key, wait for the page it opens (`at g.privacy`), or, for a row of the root and wherever that page may already be on top, for the row to take the focus (`wait ▌ 指纹与密码`): the Shell holds keys behind an action for 0.5 s only (scaled by `--timeout-scale`), on a busy machine the app answers later, and the next key lands on the focus of the page before (main chain r85, 2026-11-27: Settings' root row 「我的设备」). Rows of a group do not use `wait ▌`: when a group on the root has the focus, its subtitle line starts with ▌ too, followed by the name of the group's first row. Before finding an item in the command palette and pressing OK twice (`type /`, `type 湿地`, `key enter`, `key enter`), put the focus where that item cannot be (`key first`, `key last`): with the focus elsewhere the first OK is the Shell's own "Go to" and the second opens it; with the focus already on it the palette's first entry is the item's own action, the first OK opens it and the second lands on the page it opened (main, 2026-11-26: 「视频跳到哪里」 followed the case before with the focus still on 「湿地」, and the second OK paused the video it had just started, at 0:00). A case that checks an app's storage after it is opened again ends it with `appterm` (SIGTERM, with time to finish writing), not `appstop`: storage is written in the background, the number on the screen comes before the one on disk, and SIGKILL loses the write under way ([29](29-app-development.md) §5.4; dev, 2026-11-26: the counter was back at 0 when opened again). Before waiting for a banner, wait for what was sent before it and has no outcome yet to settle (a resent SMS failing again): a newer notification replaces the banner, and one that comes late replaces the one waited for (dev, 2026-11-26: the resend's failure came after 「流量提醒」).
- **Simulating the world**: calls and messages (`tel`, `sms`, `mms`), Wi-Fi access points (`wifi-ap`, `wifi-join`), Bluetooth peers (`bt-peer`, `bt-push`, `bt-oldphone`), card readers (`nfc`), position (`location`), light (`lux`), fingerprints (`finger`), time (`timeshift`), servers (`fetch-server`, `carddav-server`, `parent-server`, `store-publish`) and more, each described at the top of `headless.go`.
- **Checks**: commands that look at the system's state directly, such as `saved`, `sealed`, `perm-state`, `vibrated`, `appstate`, and `snap name` (a snapshot).

`require-*` lines skip a case where the environment lacks something (277 lines: no baseband `require-tel`, no SMS service `require-sms`, BlueZ only `require-bt bluez`, pixel renderer only `require-gui`, ...); a skipped case says SKIP in the report, with why, and is not a failure. A phone lacks some of the simulated hardware the script drives, its board having its own or none, and those cases are skipped there too, not failed: `require-fingerprint` (the simulated fingerprint sensor `finger` touches; a board names a sensor in its SKU's `fingerprint`, the phones none, so phone-keystored has none), `require-gnss sim fifo` (a receiver `location at` moves: the simulated one or the emulator's pipe; the phones' is ModemManager's; also the cases that need the weather app's position), `require-lux` (the simulated light sensor `lux` sets; a board's own is found by itself). The lock-screen cases that only lock the phone unlock it with the PIN, so they run without a fingerprint sensor, and the PIN is still removed at the end. `require-kernel <protection>...` skips where the kernel probe found the protection missing (`shell/kernel.go`, the compatibility report's `sandbox.missing`), and `require-previous` a case that goes on where the one run before it in its part stopped (a message it sent, a call it made, its counts) when that one did not pass (cases skipped in between for the environment or `--only` do not count; a case that only differs in its snapshots ran through). A case never goes on from another part's: when no case of its part ran before it and one was skipped for the environment, it is skipped too, naming that case and why (the background jobs case goes on from the weather case, which needs a location receiver the script can move; on the 6T it went on from the part before and failed at its first step). Other conditions a phone may not meet, each skipped saying why: `require-own-kernel` (the running kernel is one this system ships: `/lib/modules/<release>` is in its root; in the chroot it is Nura's), `require-systemd` (this system's service manager answers `systemctl`; in a root systemd does not run in, `systemctl` prints nothing and exits 0), `require-vpn sim networkd` (either VPN backend; in the chroot there is no systemd-networkd on the bus), `require-wifi-ap` (`wifi-ap` can put an access point up: the simulated Wi-Fi, or a second Wi-Fi device under iwd, the emulator's simulated radios; a phone's own radio is not taken for it), `require-mobile-route` (where the per-app firewall runs, `net-send`'s packets leave by a link that counts as mobile: a mobile data block holds there only, and on Nura they left by its Wi-Fi), `require-bt-peer` (the selftest's Bluetooth peer is a virtual controller, btvirt's, which reaches only virtual ones: skipped where the phone's adapter is a controller of its own or the kernel has no hci_vhci), `require-direct-route` (the device's packets have a route outside the tunnel: with neither Wi-Fi nor mobile data, the VPN cases' `direct` and `blocked` cannot be told from the kernel's network unreachable), `require-sleep` (nobody else holds a wake lock: the bring-up image's `phone-bringup` keeps the kernel from suspending). `require-button power` runs a case only where someone presses the board's own power button when asked (the variable `PHONE_SELFTEST_BUTTONS` names `power`): the `button power` step asks with the request `PHONE-SELFTEST-PRESS: power <n>` on its output (a console file's line, said again until the key goes down; see "What an emulator hands the host over its console" below), reads the kernel's input devices itself until the key has gone down and up (the headless renderer reads no keys), and gives the Shell a short or a long press by the renderer's rules (`button-burst power <presses> <gap ms>` asks for presses in a row and gives each as it comes); in QEMU's boot selftest `yocto/qemu-buttons.py` presses the virt machine's power button from the QEMU monitor (`system_powerdown`, [28](28-battery.md) §7), while the developer machine's runs and the phone kit's do not set it, so the case skips there. The steps are listed at the top of `shell/headless.go`.

**On a kernel without Landlock** (Nura's for the 6T, [41](41-design-gaps.md) §11) "沙箱：独立 uid、命名空间、Landlock" (sandbox: separate uid, namespaces, Landlock) is skipped (`require-kernel landlock`, saying why), not failed: the sandbox does without the layer as designed and says so ([24](24-sku-framework.md) §7.5), the compatibility report's `sandbox.missing` names it for the certifier, the layers still in force are checked by "沙箱：已生效的限制层全部符合预期" (sandbox: every layer in force as expected), which runs everywhere and fails on any ✗, and the DNS case already skips its Landlock half. "内核特性" (kernel features) is the one case that calls a missing protection a failure, on purpose, since Kario's own kernels (QEMU, the whole phone) must lack nothing. On another system's kernel (the chroot on Nura: no `/lib/modules/<release>` of it in the image) it is skipped (`require-own-kernel`), its reason naming what that kernel lacks, and the compatibility report's `sandbox.foreign` says the kernel is not the device's; on a kernel the image ships it still fails, naming what is missing ([39](39-oneplus-6t.md) §14.12).

**When several parts run one after another in one Shell** (the whole script serially, `--parts` in an emulator), each starts from the boot's state as it would alone: on a `#part` line the Runner puts away what the part before left in the Shell and gives the next part its own: the Shell's clock (the offset `timeshift`, the simulated sleep and `clock-at` gave it; the clock the apps read follows it, [22](22-developer-api.md) §2), the simulated battery (`power`), the simulated light (`lux`), the wait before freezing (`freeze-after`), and `screen-auto`, `system-sleep` and `nfc picker`, which the Runner turns off at the start, and the background jobs scheduled in the part (below). A part starting for the first time gets them as at boot (the clock is the machine's), and one the script returns to gets them back as it left them (`shell/partstate.go`); an in-place restart and `--keep-going`'s start over carry them. **What an emulator hands the host over its console** (`yocto/qemu-console.py`; the QEMU boot selftest, the userdata test, the system update tests): what the host keeps and judges by comes over the serial console as console files: the compatibility report and its root (`cts-device.json`, `cts-device.json.root`), the results (`results.txt`: the `PHONE-MODULES:`, `PHONE-CTS:` and `PHONE-SELFTEST-RESULT:` lines and the exit code), the fd store check's (`fdstore.txt`), the PNGs (`<name>.png`, base64, through the journal, `phone-shell --print-png`) and `ota-test`'s `PHONE-OTA:` lines (`ota-test.txt`, a line printed as each is said); so do the button and touch requests a machine says as it runs (below). Each line is written in one write as `PHONE-FILE <name> <n> <its Adler-32> <line>`, and the file ends with `PHONE-FILE-END <name> <lines> <the Adler-32 of them all> [base64]` (`console-file` in the image, in POSIX awk as busybox's is). The kernel prints on the same console past the tty, a whole line at a time (selftest-heartbeat.sh's line through `/dev/kmsg` every 30 s, any message of the kernel's), and that line can land at any byte of a line being written, whose rest comes after it. A line whose sum does not hold is cut at each kernel line's `[<seconds>] ` in it, the rest taken from the line after (past more kernel lines; a cut inside the rest too, three deep), and kept only when the sum then holds, said as `... mended, 1 kernel line taken out of it: ...`. **Going on after a failure** (`phone-shell --selftest --keep-going`, likewise with `--cts` and `--script`): by default a run stops at its first failure. With `--keep-going`, after a failed case the phone starts over as in the cases that restart it (the Shell, its services and apps, in place; the Runner's `KeepGoing`, `shell/headless.go`), and the run goes on at the next case; it still fails, `PHONE-SELFTEST-FAILED:` and the JUnit report listing every failure, and the snapshot comparison's counts and the compatibility run's capability coverage count every case that ran. `make selftest`, `make cts` and QEMU keep stopping at the first failure; the phone kit's `selftest` and `pixel` use it, in the chroot and on the whole phone ([24](24-sku-framework.md) §6.2). The next case starts from the phone's state as the failed case found it, not from what it left behind: as each case starts, the Runner brings a copy of the state and persist directories up to date (`StateCopy`, `shell/keepstate.go`, in the run's directory), and phone-shell puts the copy back once the Shell, its services and its apps have stopped, before the phone starts over. The Shell's clock (as `timeshift` and `clock-at` moved it) also goes back to how that case found it, with what the parts put away (above, "When several parts run one after another in one Shell"); until 2026-11-27 the Shell starting over always had the machine's clock. Only what differs is copied: a file whose size, modification time, mode or owner differ from its copy's, or whose inode changed since shortly before the last copy (a coarse clock's tick, or a writer that sets the time back); files are copied, not linked, since the Shell, the services and the apps rewrite them in place. - A server that has to outlive a Shell restart lives outside the Shell's process: the servers the script starts (`fetch-server`, `keep-server` and the others) are in the Shell's process, and the exec of `shell-restart` ends them, while a real server is out on the network and a connection to it does not drop when the Shell restarts. So a case about a connection surviving the restart uses `keep-server <address> apart`: the same program started again as that server (`shell/keepalive_apart.go`; phone-shell and the test program are only the server when they see `PHONE_KEEP_SERVER`), started like every other child from the process thread with a parent-death signal (§6, "What a test starts ends with the test"), so it dies with phone-shell however that ends, while an in-place restart, which execs from the same thread, keeps it. The runner's control connection to it (a socket pair, a line asked and a line answered) goes on to the next Shell as an app's connection does (`keep_server` in `Resume`: the descriptor stays open across the exec, and the next Shell makes it close-on-exec again as soon as it reads the resume file), and `{keepalive}`, `keep-send` and `keep-got` work as with the one in the process; any other exec (starting over with `--keep-going`, a factory reset's restart) closes that connection, and the server ends with it; `keep-server off` ends it and waits for it to exit. `keep-conns <n>` checks that the server accepted n connections in all and every one is still open (the app did not connect again). The clock `timeshift` moved does not carry over a `shell-restart` (it moves the Shell's own clock), so steps after a restart must not rely on it: 「应用自己的长连接，Shell 重启后」 (an app's own long connection, after a Shell restart) gets its heartbeat past the deadline with `keepalive-due` instead of moving the time on and waiting for a push heartbeat. A restart after a crash (`shell-crash`) does not carry the `apart` server over: the Shell's process ended, and it died with it. To outlive a crash, use `keep-server <address> outside`: started again the same way, without the parent-death signal, and put into a systemd scope of its own (as an app is; it needs app scopes), since systemd ends what is left in the service's group before it restarts the service; its control is a socket in the run directory (`keep-server.sock`, which it listens on), which each Shell connects to once (the path is in `keep_server` in `Resume`); when a control connection ends it waits for the next, and ends, removing the socket, when none comes within a minute (times `--timeout-scale`). `keep-reset` makes the server end every open connection with a reset (the app reads an error); a server without `ws` speaks WebSocket on a connection that opens with `GET`, so a C app's line connection and a TypeScript app's WebSocket can use the same server. The check unit's store has only 4 places (`FileDescriptorStoreMax=4`; the product's `phone-display.service` has 512), so apps' own connections get 1 and two apps contend for it. `fdstore <app> app|keep yes|no` asks systemd whether its store holds the app's (current process's) protocol connection or its own connection (`DumpFileDescriptorStore`, printing `PHONE-FDSTORE-HOLDS`): what the store really holds, not what the Shell believes it put there; `shell-log <text>` waits for a line holding the text in the Shell's own log (`shell.log` in the run directory). `selftest-boot.sh` also checks that the journal has no `Cannot store more fds` from systemd (more put in than the store has places, and systemd quietly closing the rest). `make yocto-selftest ONLY=` runs only the cases of this script whose name matches too (`/tmp/fdstore.only`), and checks nothing when none does.
- A part that is too long is split where its cases do not lean on each other (2026-11-25: `chat` gave `radio`, Wi-Fi, Bluetooth pairing, airplane mode, mobile data, the hotspot, moving from an old phone and the Bluetooth search, with the case that receives a contact card from the paired headset; `apps` gave `carddav`, the three CardDAV cases, the second of which expects the account number `a2` after the first's; `power` gave `calendar`, which does its own `clock-reset` and puts its own holidays in): before splitting, find what each case reads that an earlier one left (contacts, messages, pictures, settings, installed apps, notifications, the battery level, the code in front of the camera, known networks, pairings), and after it each part must pass alone.
- A case opens the app and the screen it works in, from the standby screen: after a failed case the phone starts over (`--keep-going`), and an app reopens where it was only if its process lived (Hongyan in the thread or, started afresh, in its list; Feiqian on its bills or at its home): `wait-re` for either, then `key-if <key> <text> 0` goes on from the one it came to without waiting; the same for a permission a new process asks for again (Hongyan's microphone: `wait-re 录音中|请求使用`, `key-if enter 请求使用 0`). A case that goes on where the one before it stopped, and cannot set that up in a few lines (the message the case before sent, its call, its counts), says `require-previous`.
- Wait for the thing you act on, not for any text: `wait X` passes as soon as X is anywhere on screen (a toast or the status bar count). To move to a row of a list, wait for that row's own text (its subtitle), or use `wait-re`; text found nowhere else on the page (an explanation) only: the VPN page's explanation says "全部流量" itself, so the wait is for the row's "· 全部流量". The command palette lists the rows on the page the moment it opens: a toast comes before the row (the app shows "已导入" first, then fetches the new list), and a palette opened on the toast alone finds no match for the name, and the next keys land in it.
- To wait for a value (a number, a percentage, a duration), wait for its row: `wait-re 预报天数 +4\b`, `wait-re 媒体 +60%`, not `wait 4` or `wait 60%`. The status bar always shows `4G` and the battery (`82%`), the clock shows `10:01` (which holds `0:01`), and another row on the page may hold the same number (the sound page's notification sounds are at 60% from the start): such a wait passes at once, having waited for nothing (2026-11-27 night pass 30: the weather's forecast days). When the last word of a `wait` or `wait-re` is an integer (`+2` too), it is the wait's timeout in milliseconds: `wait = 42` waits 42 ms for "=" (which the calculator's keys show), `wait-re 通讯录 +2` 2 ms for "通讯录". When the text ends in a number, put the timeout after it (`wait = 42 8000`), and end a regexp's number with `\b` (which also keeps 2 from matching 23); `TestScriptWaitTimeouts` finds the waits of under 300 ms in the scripts.
- After a key that changes the screen, `at screen` or `wait` before the next key; never press keys back to back across a screen change.
- Lists may wrap: go to the first or last item with `key first`, `key last`, not `key up 5`.
- Do not hide a race behind a longer wait: when something does not appear, first look for two requests whose answers come in either order, or an old state replacing a new one (examples in §6).
- A compared snapshot must come out the same every run: a toast stays 2.5 seconds, so `gone` it before the snapshot; something that moves by itself (the snake) is snapped paused before its first move, and right after it goes on; numbers that timing decides (screen time sorts the apps by milliseconds) start from a known state (`screen-use clear`); a notification's banner stays 4 seconds and comes when the app posting it wakes: before the snapshot `notified` waits until the notification is in the notification centre, then `gone` until the banner has passed (the calendar's notification about the import after moving from an old phone); a case whose own banner is still up when it ends waits it out with `gone` too, or it lands in the next case's snapshot when that comes quickly (the calendar's system import in the .ics import case: in whole runs it sometimes topped the snapshot of the CalDAV case right after, never when that case ran alone); waiting for an answer means waiting for this one, not an equal one earlier in the conversation (Hongyan's bot answers the shared photo; the case used to find its answer to the photo before, and this answer sometimes came after the case had left, as a banner and a notification in the later standby snapshots); notifications a case leaves are cleared, above all those holding the day's date (the name of the calendar file the move imported), or they end up in later cases' snapshots; a page whose data has not come in says "Loading…", not "none", and the case waits for that to go before the snapshot (the app store's install dialog opens over the store's lists, and before they came in the store used to say "No apps installed yet" and "The catalogue is empty", so the snapshot's edges showed that or the lists, depending on timing; it was masked and its pixels not compared, now it is fixed). Do not cover a real bug like that with `unstable.txt`.

## 4. What runs for what change

CI's rules are the `RULES` table in `scripts/ci-plan.py` ([38](38-contributing.md) §3): docs only run the checks (the checks and the libFuzzer seed replay run every time); a Go package runs it and every package that depends on it; changes that go into `make build` add the selftest, CTS and pixel selftest; when the `jsrt` package runs, its tests run again under the sanitizers (`jsrt-sanitize`, §8); a change to the Node.js runtime (`sdk/ts/node/`, `sdk/ts/embed.go`, `sdk/c/include/kario_native.h`) or to the packages that start it (`jsrt/`, `cmd/kario/`) runs the runtime's tests again on Node 24 (`node-newest`), and every other job that starts Node.js pins 22, the oldest major kario supports: `go`, `race`, `jsrt-sanitize`, `ts`, and outside `platform` `fuzz`, `coverage` and CodeQL's TypeScript analysis ([38](38-contributing.md) §2); telephonyd's ModemManager backend adds `mm-selftest`; `yocto/` runs the recipe checks and two script tests that do not boot; unknown files run everything. The only gate is `pr-ok`. After publishing to main everything runs once by hand (`gh workflow run ci.yml --ref main`); each workflow keeps only its last 3 runs (`scripts/ci-prune.sh`).

Fuzzing in CI: every run has the `libfuzzer-replay` job, which runs each of the seven libFuzzer targets once over the seeds committed in `tools/cfuzz/testdata/libfuzzer/` (`make fuzz-libfuzzer-replay`, `-runs=0`, no mutation; the seeds take under a second, about 2 minutes with the build); a seed that crashes, leaks or times out fails `pr-ok`. The Go targets' seeds and regressions run as plain tests in the `go` job. Fuzzing that mutates blocks nothing: `fuzz-weekly` runs each of the seven libFuzzer targets for 5 minutes every Monday (`-max_total_time`) and uploads failing inputs and the grown corpus as artifacts; the `fuzz` workflow runs any target for any time by hand ([17](17-app-sandbox.md) §9.2). Neither of the two new ones has run on GitHub yet: **not verified**.

What CI does not run (too slow or needs privileges): everything in QEMU, long `make fuzz` runs, soaks; these run on the developer machine as in §5.

## 5. Before publishing

In this order, on the developer machine:

1. The check scripts and `go vet` (seconds each).
2. `make test` (about 6 minutes; `make build` and `make paint` first, §6).
3. `make cts` (about 3 minutes).
4. `make pixel-selftest` (about 3 minutes).
5. QEMU: `make yocto-selftest` of the device image and of the product image (about 6.5 minutes each with nine emulators on the build machine; the two at once share its processors, not measured since the run went parallel).
6. If telephonyd changed: `make mm-selftest`. If system updates changed: `make yocto-ota-test` (product image; about 22 minutes with the device image) and `make yocto-ota-delta` (about 75 minutes, its base saved by `make yocto-ota-base` on the previous release). If the initramfs (`slot-init`, `slot-abl`) or the 6T's boot image changed: `make yocto-userdata-test` (four boots, about 3.5 minutes) and `make yocto-ota-test`.
7. Publish (`make publish`) only when all of it passes; write the results into [13](13-prototype.md) §5 and the internal verification baseline.

**One shared lock**: on the developer machine the selftest, CTS, `go test ./shell` and the pixel selftest all take `/tmp/kario-selftest.lock` (`flock /tmp/kario-selftest.lock make cts`). The parts and form factors of one run at once are fine: each phone-shell has its own temporary state directories and services, the script's servers take free ports, and so does moving from an old phone on the simulated radios (only the interactive `make run` uses the fixed 47800); runs of several people or trees overlapping slow each other's timed waits down and fail now and then, so one runs at a time, and the parts run at once so that each holds the lock for less. Give `go test ./shell` `-timeout 30m`: when the default 10 minutes run out the test is killed (what it started ends with it, §6).

## 6. Rules

- **A regression test fails first**: when fixing a bug, first write a test that reproduces it, run it once on the old code and see it fail (failing the way the bug did), then fix, then see it pass.
- **A case passes on its own too**: what a step needs (an app's data directory, a record) it makes or waits for itself, not relying on what earlier cases left: with `--only` running one case, only the boot comes before it. Example: in 「沙箱里的 DNS」 (DNS in the sandbox), `sandbox-read` works out Hongyan's sandbox and gives Hongyan's data directory to its uid; on the whole phone the run of only "kernel features + sandbox" had never started Hongyan, the directory did not exist yet, and the chown failed (2026-11-24); the step now makes the directory as the app's first start does (`TestSandboxReadBeforeTheAppStarted`). A case that really goes on from the one before says `require-previous` (§2).
- **Never test with a program older than its sources**: the Go tests that run a program built in the tree find it through `tools/prebuilt`. phone-paint (`make paint`): `TestTouchStepsOnPhonePaint` of `shell`; the `build/usr` that `make build` stages: `TestNestedSandbox` of `apps/miniapp` and the manual `TestMeasureHost`; both: `TestPreviewImages`, `TestRunProfile` and `TestRunNativeApp` of `cmd/kario`. When the program is missing or older than its sources the test is skipped, saying which file is newer and what to run: phone-paint older than the newest of `paint/src/*.rs` and `paint/locale/`, `build/usr/bin/kario-system` (which `scripts/stage.sh` installs anew every time) older than the newest of the module's Go files outside the tests, `go.mod`, `go.sum` and `stage.sh`. `make test` runs `make paint` and `make build` first (about 10 seconds when they are built already) and sets `KARIO_PREBUILT_REQUIRED=1`: there those tests fail on a missing or stale program instead of skipping. Why: `make test` did not build the renderer, and in a verification copy `TestTouchStepsOnPhonePaint` ran a phone-paint an older tree had left, failing with "the renderer takes no touch". What is compared is modification times, as make and cargo do: a source whose content changed but whose time is older (copied in with its old time) goes unnoticed. `Cargo.toml` and `Cargo.lock` do not count as phone-paint's sources: cargo does not relink when only they are newer, so counting them would leave the program looking stale even after `make paint`. kario-jsrt (`build/jsrt`), telephonyd and the C SDK's sample app are built first by `make test`'s prerequisites with ninja, which rebuilds by the exact dependencies; under a plain `go test ./shell` the end-to-end tests build all three themselves (the "fresh worktree" rule below), and nothing checks the other packages' programs against their sources (**not implemented**).
- **What a test starts ends with the test**: the end-to-end tests (`e2eStackWith` in `shell/e2e_test.go`) start private system services themselves (not through the Shell, nor phone-shell), and the scenario's parts and the tests that start a Shell each run in a child process of the test binary (`runChild`, `alone`). The services used to be ended only in the test's Cleanup, so they stayed behind, with init as their parent and their working directory in the tree's `shell/`, whenever a child went without running its Cleanups: go test's timeout (a panic on its timer's goroutine), a panic on one of the Shell's goroutines, the child killed (by the parent test's context, by hand, by the caller's timeout), and, once the parent test process was killed, the child writing to its broken output and ending by SIGPIPE. On 2026-11-26 one run on the developer machine left 1525 of them (11–12 services a part, fourteen parts from one run: the parts still running when it was killed; a part that only failed ran its Cleanups and left nothing). Now the services and the child test processes carry a parent-death signal (`Pdeathsig: SIGKILL`) and are started from the thread that never exits (`StartProcess`: Linux sends that signal when the thread that started the child ends, not the process, and `ownThread` and others end threads): however the process that started them ends, the kernel kills them, with no Cleanup needed. Not a process group or a sweep of the run directory: both need someone to kill or sweep in a Cleanup, and the processes stayed behind exactly when no Cleanup ran. The Shell already starts its apps so (apps die with the Shell); on a phone systemd starts the services, and `phone-shell --services spawn` already starts them with that signal; neither changed. A child also writes its run directory to a file its parent names (`KARIO_E2E_RUN_FILE`), and once the child has ended the parent removes its temporary directory and kills whatever still runs from it (`reapChild`): without the Cleanups the hard links of its copy of the programs (about 190 MB) stay in `/tmp`. `TestScenarioPartEnds` starts a part (the boot and one case) and makes it fail, panic on another goroutine (as go test's timeout does), get killed, or have the test process that started it killed, then checks that no process runs a program under its directory, has the directory on its command line or the file's name in its environment; before the change the last three each left 11 services (the last one the child test process as well), the failing one nothing. mediad's ffprobe and ffmpeg did not carry that signal: killed while probing or decoding, mediad left that decoder running with the tests' environment, and under load `TestScenarioPartEnds` sometimes failed on it (2026-11-27, one ffprobe left: on its first start the Shell puts the sample video in the media library, mediad probes it and grabs its poster, and the parts `TestScenarioPartEnds` starts run only 1–2 seconds); its decoders carry it now (`TestDecodersDieWithMediad`; started through `subproc`, see "A service's helpers end with it" below). When the go command itself is killed the test binary runs on to its end and its Cleanups, at the latest to its own `-timeout`, and what it started dies with it. When the test binary itself is killed it runs no `TestMain`, and the directory it staged the programs in, `/tmp/kario-e2e-*` (about 190 MB), used to stay behind, with the hard links of the programs in each part's `t.TempDir()`, so removing the former alone freed nothing (on 2026-11-27 the developer machine's `/tmp` held 228 `TestSelftestScenario*`, the oldest from 11-18). Now the directory is named for its owner (`kario-e2e-<pid>-<start time>-…`: pids are reused, so the start time from `/proc/<pid>/stat` goes with it), and the parts' copies of the programs and their run directories are inside it too (`stack-*`); before staging (`stagedPrefix`), the next run removes such directories whose owner has ended, killing what still runs from them (`removeStaleStaged`). A live owner's (another run going on) stays, and so does one whose name does not say its owner (made by older code, or by Kario Studio's `ide/vscode/scripts/e2e.mjs`). `TestStaleStagedRemoved` covers these: another live process's, this process's, one whose owner has ended, one whose pid was reused, one whose name says no owner, and a program still running from the dead run's directory. With the test binary killed by SIGKILL halfway through the scenario (2026-11-27, developer machine), before the change it left 23 directories, 612 MB together (the one it staged the programs in and 22 `TestSelftestScenario*`), after it one directory of 625 MB, no process in either case; the next run removed it 9 seconds after it started. The input method dictionary's directory (`testDict`, 6.5 MB) is named for its owner the same way (`kario-ime-<pid>-<start time>-…`): a test binary that did not finish its `TestMain` (its timeout, a panic, a signal, or SIGPIPE on its output once the go command was killed) used to leave it behind (about 5,500 in the build machine's `/tmp` on 2026-11-28), and now the next run removes those whose owner has ended before it builds its own, leaving the older `kario-ime-<random>` ones, whose names say no owner (`TestStaleDictRemoved`).
- **`go test ./shell` runs everything in a fresh worktree too**: the scenario needs kario-jsrt (the TypeScript calculator and calendar, two system apps, and the sample app run on it: without it the apps `scripts/stage.sh` installs have no module and do not start), the C SDK's C++ sample app, the native example's library and phone-telephonyd (the `require-tel` cases need it; it runs its own simulated modem), which `make jsrt`, `make capi`, `make native-example` and `make telephonyd` build in `build/`. In a fresh worktree where they were not built yet, `go test ./shell` used to fail 11 parts. Now the end-to-end tests run `make jsrt capi native-example telephonyd` before staging the programs (one at a time in a tree: `flock build/.e2e-make.lock`): the first time in a fresh worktree that adds about 60 seconds (QuickJS's source archive comes from `~/.cache/kario`, else it is downloaded from GitHub) and about 30 seconds more for telephonyd, afterwards ninja has nothing to do, about 1 second (telephonyd runs its unit test each time), and changed sources in `jsrt/`, `sdk/c/` or `telephonyd/` are rebuilt by their dependencies. Not skipping: the calculator and the calendar are in over two hundred lines of the script, skipping would leave about half of the parts unrun in a fresh worktree, and `go test ./shell` without `-v` only says ok, hiding it. `make test` builds them first and sets `KARIO_PREBUILT_REQUIRED=1`, and then the tests run no make: that path is unchanged. The build needs what `make build` needs (cmake, ninja, GCC 14); without it the scenario fails once at staging, with make's output, instead of a dozen parts failing each. telephonyd joined them on 2026-11-27: before, `scripts/stage.sh` installed it only when `build/telephonyd` was there, so the scenario depended on what the tree had built: with it, the 65 `require-tel` cases of the 287 ran, without it they were skipped; those who merge run `make telephonyd` and `make mm-selftest` in the development tree, so its `go test ./shell` and a clean copy's did not run the same cases. The failure reported then, "with `build/telephonyd` the `phone` and `switch` parts fail" (the calculator does not open from `/`; after a phone migration the calendar posts no notification of the import), came from a tree that had telephonyd but no kario-jsrt (the end-to-end tests did not build it yet): only with telephonyd do those parts' telephony cases run, and the calculator and the calendar they use are TypeScript, had no module and did not start. Neither telephonyd nor the Shell is at fault: on today's code the two parts on a prefix with telephonyd but without kario-jsrt fail at the same steps the same way, and with kario-jsrt they pass with telephonyd or without. Always with telephonyd rather than always without: `make test` and CI build it before `go test ./shell` anyway, and always without would leave those 65 cases unrun on the developer machine. After staging, the tests also check that the prefix has phone-telephonyd, kario-jsrt and the C++ sample app (`stagedLacks`); without one, staging fails, naming what to make, also when `KARIO_PREBUILT_REQUIRED` is set and no make runs. The scenario and `TestScenarioPartEnds` build and stage the programs once in a test process (`stagedPrefix`). The whole package (developer machine, the evening of 2026-11-26, load 4–12): in a fresh worktree 173 seconds, all passing (before the change 121 seconds with 11 parts failing); with everything built 124 seconds (before the change 130). With telephonyd (early on 2026-11-27): with `build/telephonyd` there 136 seconds, run again after removing it 144 seconds (building it about 30 seconds of that), both passing, each case with the same outcome in both runs (of the 287, 241 passed and 46 were skipped, all for devices and features the host lacks, none for want of telephonyd).
- **A service's helpers end with it**: on a phone systemd ends a service's whole cgroup, but where no systemd does (`phone-shell --services spawn`, the supervisor in `programs/shellcmd`, the tests) a helper process a service had started outlived it when the service crashed or was killed, with the old state: audiod's `aplay` holding the sound card from the restarted audiod, an `alsaucm` waiting for the card, a compile of the Shell's. The `subproc` package starts such helpers: `subproc.Command` sets the parent-death signal (`SIGKILL`), and `subproc.Start` (and `Output`, `CombinedOutput`) starts them from a thread of its own that stays locked and never exits, so the signal comes when the program ends or execs, not when the thread a goroutine happened to be on ends (Go ends a thread whose goroutine exits locked to it, and a thread an unlocked goroutine forked from can later be such a one: in the Shell `ownThread`, the VPN's and the traffic statistics' code). What has to outlive the Shell's in-place restart (apps, the renderer, the services) still goes through `shell.StartProcess`. Covered now: audiod's `aplay` that plays and the one that reads the card's parameters (`programs/audiod`), and `alsaucm` (`audio/ucm`); mediad's ffprobe and ffmpeg (`programs/mediad`, which had `decoder` for it); the Shell's unsandboxed `kario-jsrt --compile` (`shell/jscache.go`; the sandboxed one had the signal but was started from whatever thread the goroutine was on) and the hostapd of the selftest's enterprise Wi-Fi access point (`shell/radio_hostapd.go`, the same; it runs only in QEMU and on a phone, and **this change was not run there**); the Shell that `kario run` starts (`cmd/kario/run.go`, with SIGTERM, so that it ends cleanly): kario killed by hand, or a test killed while it ran, left the Shell running with its preview's port; the program telephonyd's `run_program` runs (the IMS status, `telephonyd/src/run.cpp`): fork and `PR_SET_PDEATHSIG` instead of `posix_spawn`, which cannot set it, from telephonyd's only thread; the signal ends the program alone, so a guard, a second child in the program's process group waiting for the same death, kills the group (what the program started: the IMS status script's `qmicli`), and each run ends with its group, at the program's exit or the timeout. Covered before and unchanged: what the Shell starts through `StartProcess` (apps, the renderer, the webview, usbhelper, `--services spawn`), audio/hifi's ffmpeg, the charger's renderer, shellcmd's parallel parts, the miniapp runtimes, the end-to-end services. Left on purpose: commands that end on their own (systemctl, ip, networkctl, udhcpc, `rauc info`, the compilers of `kario build`), what runs only on a phone under systemd (`journalctl -f`, the rauc install client, under `KillMode=mixed`), the selftest's helpers under `phone-selftest.service` in QEMU, and `kario`'s interactive children (ssh for the device shell and the debugger, node for the tests and the preview), which end with their pipe or terminal. jsrt and the C SDK start no processes. The tests run on the host, with no audio hardware: a test runs itself again in a child of the test binary, which starts a stand-in for the helper (a script that writes its pid and sleeps) and is killed (`subproc/subproctest`): `TestAplayDiesWithAudiod`, `TestAlsaucmDiesWithAudiod`, `TestCompilerDiesWithTheShell`, `TestRunShellEndsWithKario`, telephonyd's `test_run_program`; for the thread rule, the helper is started from a thread that then ends: `TestAplayOutlivesTheThreadThatStartedIt`, `TestPlayerDecoderOutlivesTheThreadThatStartedIt`; `subproc`'s own `TestChildOutlivesTheThreadThatStartedIt` fails when `Start` starts the child from the calling thread. Each takes under a second, and each of the others failed on the old code (the stand-in outlived its parent, or the helper was killed with the thread), except `TestAplayDiesWithAudiod/playing`: that `aplay` already had the signal. The staging's builds (`e2eBuild`, above): a test process killed while it built left `go build`, `flock … make` and their jobs running in the tree, the lock held. Each command now runs under the test binary run again (`leadSession`) as the leader of a session of its own, with a parent-death signal (SIGTERM): when the test process ends, it sends SIGTERM to every process of its session and SIGKILL to what is left 3 seconds later. A session, not a process group: ninja puts its jobs in groups of their own. A program that left the session (`setsid`: a daemon another tree's build may share) is spared, and another tree's build is in another session. A make ended while it copied QuickJS's archive into the shared `~/.cache/kario` would have left a cut archive there, which fails the build of every tree: the Makefile copies it under a temporary name and renames it. `TestStagingBuildEndsWithTheTest` (under a second) starts two stagers, two trees with a lock each, with a fake `go` and a fake `make` whose job is in a process group of its own, and kills one: nothing of its build remains and the other's goes on; on the old code flock, make and its job outlived it.
- **The Shell's helpers end when it stops**: `Core.Shutdown` used to end only the apps and the media subscriptions. Where a Shell stops and its process goes on (the end-to-end tests, `kario test` on a real Shell, a future restart in place), the helper processes it started stayed until the process ended: the USB sharing helper (phone-usbshared) while the cable was in, and once the test killed it the Shell started another (`usbHelperEnded` did not know the Shell was stopping); a `kario-jsrt --compile` under way; the apps' web processes (phone-webview: what ends one is its app's exit, which waits for the event loop, and `Shutdown` holds the loop); the hostapd of the selftest's enterprise Wi-Fi access point and the simulated device on the hotspot (wpa_supplicant, udhcpc and the like, with its thread and network namespace); a log a computer follows (`journalctl -f`, a stand-in in the tests). The USB helper and the web processes, started from the main thread, also stayed when phone-shell executes itself afresh to restart the phone: the thread that execs is the one that started them, so their parent-death signal does not come (inferred from that signal's rule, not reproduced on its own). Now each one goes into the Shell's table of helpers when it starts (`shell/shutdown.go`), and `Shutdown` ends each the way its own stop does: the USB helper by closing the Shell's end of the socket pair, a compile and a web process by a kill (the web processes after the apps, as each ends after its app), hostapd with SIGTERM (its parent-death signal), the simulated device by ending its thread, a followed log by closing its connection (as the computer going away does); it waits for them within the apps' grace (3 s) and kills those still there then, so they are gone, and reaped, when `Shutdown` returns; none of them starts once the Shell is stopping. phone-shell calls `Shutdown` from its signal goroutine on SIGTERM, with the event loop still running, so the table has a lock of its own and `Shutdown` touches none of their other state: the tidying up (`usbHelperEnded`, `webProcEnded`) still happens on the loop. Not changed: the renderer belongs to whoever starts it (every caller of `StartGUI` calls `Close`, which waits); commands run to their end within a selftest step or a request (ip, udhcpc, networkctl, btmon, `rauc info`, systemctl, sandbox-read, the headless renderer of a screenshot); the rauc install client (the RAUC service does the install, and killing the client would read as a failed install; on a phone systemd looks after it, see the item above); what is no process (the VPN and keepalive simulations and test servers such as `fetch-server` live in the Shell's process, and the emulator's simulated computer is a thread with its network namespace); mediad's decoders (mediad's own; the Shell closes its subscriptions). `TestShutdownEndsHelpers` starts each of these in a child test process of its own (the stand-ins are scripts that write their pid) and checks that the test process has no child left when `Shutdown` returns (by pid, zombies counted): USB network sharing, file transfer and a helper that ignores the socket pair (killed when the grace is up), a compile, a web process, the enterprise access point (also that it got SIGTERM), the device on the hotspot, a followed log (also that the computer's request ended), and `Shutdown` off the event loop (as on SIGTERM, passing under `-race` too); on the old code every subtest fails, and in the three USB ones the Shell started another helper after the test killed one. hostapd and the simulated device only run on the emulator and were tested here with stand-ins only. Both images of the 2026-11-27 night chain r86 carry this change (their `shell/shutdown.go` and `stopEAP` in `radio_hostapd.go` are these), and on the emulator 「企业 Wi-Fi（802.1X）」 (Enterprise Wi-Fi), 「个人热点（模拟器）」 (Personal hotspot, emulator) and 「换机（模拟器，同一 Wi-Fi）」 (Moving from an old phone, emulator, same Wi-Fi) pass: the cases take their simulated devices down themselves; the enterprise access point's hostapd stays up until that virtual machine's cases are done (its memory report still lists it), the Shell's final `Shutdown` sends it SIGTERM as above, and phone-shell then exits normally (exit code 0). The data races were all in the tests; Settings' code is unchanged: its state (`p.s`, `apnState`, `apnDraft`, `acctState` and the like) is read and written on the app's loop only, the goroutines that refresh pages on a timer only `Post`, and the SDK decodes answers and calls back on the loop too (`sdk.GoAs`). The tests touched it off the loop: `TestWellbeingForgotPIN` changed `p.s` and built the page on the test's goroutine while the previous press's action could still be on the loop; `TestAPNEdit`, `TestAPNRefusalToast` and `TestAPNListError` put `apnState` back with `defer`, which runs before `t.Cleanup`, with the app's loop still alive; and one test's app loop had not stopped when the next test started (`TestA11yActions`'s loop reads the accounts' state and `TestAccountsPages` writes it; both APN tests' loops write `apnDraft`). Between a test and its app there is only a socket, and sending and receiving on it is no happens-before edge in Go's memory model, nor to the race detector. Now `fakeShellWith`'s cleanup closes the Shell's end and waits for the app's `Run` to return (an error after 10 seconds), the cleanups that put package state back are registered before `fakeShell` (the cleanup registered last runs first), and `TestWellbeingForgotPIN` changes the state and builds the page on the loop. On the old code `TestAPNEdit`, `TestAPNRefusalToast`, `TestAccountsPages` and `TestWellbeingForgotPIN` fail under `-race`. CI's `race` job now runs Settings too ([38](38-contributing.md) §2), **not verified** on GitHub.
- **opus-go and `-race`** (`audio/opusfile`, `audio/voice`, 2026-11-28): the two packages stay out of `-race`; the problem is in upstream code. opus-go is libopus 1.6.1 translated to Go with ccgo (`github.com/kazzmir/opus-go` v1.7.0, the latest release); kario carries no copy of it (no `replace` in `go.mod`; `vendor/` is what `go mod vendor` writes), so nothing was changed in kario. checkptr stops at two places: the decoder at `opuscc/silk_dec_api.go:149`, where `Opus_silk_Get_Decoder_Size` writes `*(*int32)(unsafe.Pointer(decSizeBytes))` and `decSizeBytes` is the address of the caller's own local variable `silkDecSizeBytes` turned into a `uintptr` (`Opus_opus_decoder_get_size`, `opuscc/common.go:2328`); the encoder at `opusccenc/opusccenc_silk.go:2049`, where `Opus_silk_Get_Encoder_Size` writes to memory from `TLS.Alloc` of opus-go's own small libc (`libcshim`), a `[]byte` on the Go heap. opus-go passes every C pointer as a `uintptr` and turns it back into an `unsafe.Pointer` to use it; checkptr does not allow a pointer made from a `uintptr` that points into the Go heap or a goroutine stack unless it was computed from a pointer in the same expression, so it stops at the first dereference. Whether this is a real memory problem:
  - It is not out of bounds. Under `go test -overlay`, `libcshim` was replaced by a version that gives every block (each `Xmalloc` block, each `TLS.Alloc` frame) its own `mmap` with `PROT_NONE` pages on both sides (the block's end against the page after it, or its start against the page before it; both were run), and the two packages' tests, a stress test (decoders at five sample rates, mono and stereo, fed random packets, lost packets and FEC; the encoder in its three applications, complexity 0/5/10, 6–256 kbit/s, frames of 2.5–60 ms) and `FuzzDecode` fuzzing for 2 minutes (21.63 million inputs) all passed: no guard page touched, no free of a block it did not know, every `TLS.Alloc` frame freed in order. With the shim's memory off the Go heap, checkptr still stops at the decoder's place (the stack variable below).
  - When `TLS.Alloc`'s scratch stack fills its 64 KiB it moves to a bigger one, copying the old; a caller still using the old one then holds a `uintptr` to memory the GC may free. The runs above used 19,440 bytes at most, nowhere near.
  - The real problem: the decoder (`opuscc`) has 141 places (in 42 functions) that turn the address of their own local variable or parameter into a `uintptr` and hand it to another function (`&ac[0]` in `Opus_pitch_downsample`, say); a `uintptr` is no reference, and escape analysis leaves these variables on the goroutine stack. When a Go stack grows it moves as a whole, and pointers are adjusted but `uintptr`s are not: a callee using one after the move writes to the old stack (the caller never sees the result; the old stack has gone back to the runtime and may be another goroutine's by then) and reads from it. The encoder (`opusccenc`) has no such place (it keeps these variables in `TLS.Alloc` frames). opus-go 1.7.0 fixed the same problem for the caller's slices (the comment in `opus/cbuf.go`: packets encoded all zero), not inside the translated code. To reproduce: under `go test -gcflags='github.com/kazzmir/opus-go/...=-d=maymorestack=runtime.mayMoreStackMove' ./audio/opusfile` (the stack moves at every function call in opus-go), `TestStreamsStereoOpus` decodes silence (`decoded 0 Hz, peak 0.00`); with the same flag on kario's own packages only it passes, and so does `audio/voice`'s `TestVoiceCodec` (VoIP mode). Without the flag, with the GC shrinking the decoding goroutine's stack between packets so the next packet's decode grows it again, no sample in 20 rounds differed from a normal decode (`opusfile`'s stereo music; `voice` at 16 kbit/s VoIP and 64 kbit/s music mode): on the development machine (amd64) the window was not hit; on a phone (arm64, other frame sizes) **not verified**. What can hit it: phone-audiod playing Opus music, and Chat decoding a voice message a peer sent (the peer can send music-mode packets).
  - With checkptr off for opus-go only (`-gcflags='github.com/kazzmir/opus-go/...=-d=checkptr=0'`) both packages pass under `-race` (3 runs in a row): no data race found in kario's own code. CI does not run them that way: checkptr reports exactly the real problem above, and turning it off would only hide it.
  - To do (**not done**): report it upstream with the reproduction; until it is fixed the two packages stay out of `-race` (not in `RACE_PKGS`).
- **Production-line testing**: the hardware test and factory mode exist (§10), run on the dev machine and QEMU, **not tried on a phone**; the radio's figures (transmit power, sensitivity) need instruments and come with the whole phone, **not implemented**.
- **Network access and certification tests** (China's network access licence, CCC, SRRC) are done by a qualified phone maker, not in this repository.

## 8. kario-jsrt under the sanitizers

`make jsrt-asan` and `make jsrt-tsan` (developer machine, 2026-11-27 ✓) build kario-jsrt together with QuickJS-ng with AddressSanitizer and UBSan (`-fsanitize=address,undefined`) or with ThreadSanitizer (`-fsanitize=thread`) into `build/jsrt-asan` or `build/jsrt-tsan` (`RelWithDebInfo`, `-fno-omit-frame-pointer`; never over `build/jsrt/kario-jsrt`), then run `go test ./jsrt` against it (`KARIO_JSRT`, `KARIO_JSRT_REQUIRED=1`): every runtime a test of the `jsrt` package starts runs under the sanitizer. The compiler is the first GCC that has the sanitizer's runtime library: on the developer machine gcc-toolset-14 for ASan and gcc-toolset-13 for TSan (14 comes without libtsan); on Ubuntu the system's gcc.

**How the reports reach the test output** (`jsrt/harness_test.go`):

- Only these two targets set `KARIO_JSRT_SANITIZER`, to the report directory `build/jsrt-<sanitizer>/reports` (emptied first each time). Without it the tests pass no sanitizer options at all: `make test` and `go test ./jsrt` are as they were.
- With it, each kario-jsrt a test starts (through a Shell's `launchIn`, run directly by `jsrtCommand`, or by the protocol test) gets a report prefix of its own, `<test name>.<number>`, which `log_path` points at, and its reports go to `<prefix>.<pid>` instead of standard error. The pid alone does not tell them apart: an app as the first process of its pid namespace is 1. Once the process has ended (the Shell's reading loop has reaped it; waited for 10 seconds at most, and not ending in time fails too), the test that started it reads those files, fails if there is one and prints it whole into the test output. The reports of a process started some other way (the test binary's environment set by `TestMain`) go to `unclaimed.<pid>`, which `TestMain` prints after all the tests, failing the run.
- When a test is done with a runtime (the cleanup of `launchIn` and of the protocol test), it closes the connection first and waits for the runtime to leave on its own, 5 seconds at most (`leaveGrace`), before killing it: the teardown and the leak check happen as it exits (below), and a kill would skip both. One that does not leave in time puts a line `did not leave within 5s of its connection closing: killed, without a leak check` in the test output; no current test does. Without `KARIO_JSRT_SANITIZER` the kill follows the close at once, as before.
- Stacks are symbolized in the process: GCC's sanitizer runtime reads the debug information itself (libbacktrace) and starts no symbolizer program. The runtime's seccomp filter, in force once a native module is loaded, denies execve, so an external llvm-symbolizer could not start; clang's runtime needs one, so GCC it is, and the seccomp of normal builds is unchanged. The frames of kario-jsrt and QuickJS-ng carry file and line (`strip_path_prefix` takes the repository's location off), those of libcurl and libc only the library and offset (there is no debug information for them).
- ASan ends the process at its first error, so the test sees the app exit, and the report besides; UBSan and TSan report and go on, so a test that passes still fails on the report (the old `body_cancel` below did).

**The options and why** (`sanitizerOptions`):

- Leak checking is on (ASan's default; the former `detect_leaks=0` is gone), with no suppressions: the current code gets no leak report at all, and nothing is reported in libcurl, OpenSSL or libc either (what they still hold at exit is reachable from their globals, which is not a leak).
- `verify_asan_link_order=0`: the storage tests preload `testdata/slowfs` with `LD_PRELOAD` (it wraps only `fsync` and `rename`), which comes before ASan's runtime, and ASan refuses to start by default.
- `atexit_sleep_ms=0` (TSan): with a thread besides the main one, TSan sleeps a second at exit by default; the SIGTERM tests need the runtime gone within 900 milliseconds.
- `TestNet`'s bound on the peak memory after a flood (96 MB) is not checked under a sanitizer: the shadow memory and the quarantine are resident too, 233 MB under ASan.

**Tearing the runtime down at exit** (`JSRT_TEARDOWN`, `jsrt/src/jsrt.h`): kario-jsrt built with ASan or TSan (GCC defines `__SANITIZE_ADDRESS__` or `__SANITIZE_THREAD__`; another build can ask for it with `-DJSRT_TEARDOWN=1`) lets go of everything it holds as it exits, has LeakSanitizer look (`__lsan_do_leak_check`, which TSan builds do not have), then `_exit`s.

- Why the teardown is what makes leaks findable: LeakSanitizer reports only memory nothing reaches. Once `main` has returned its `jsrt r` is off the stack, and the runtime, the timer table and the app directory all count as "leaks" (the 9 reports of 7 tests when the check was turned on before were all of that kind: the `phoneui_open` handle, the app directory `strdup`'d in `main.c`, QuickJS's arena, the native modules' state, the timer table, the page stack); while what leaves by `_exit` (an app that used native modules or the network, SIGTERM) or is killed by the test is not checked at all. On the other side, a QuickJS object one `JS_FreeValue` short stays on the runtime's object list and is reachable as long as the runtime is; only after `JS_FreeRuntime` is a leaked object unreachable (`RelWithDebInfo` has `-DNDEBUG`, so QuickJS's assertion there that the list is empty is not compiled in), and only then is it reported.
- Every exit goes through `end` in `main.c`: the Shell closed the connection (the main loop ends), the main module failed (exit status 1), a native module or the debugger did not start, SIGTERM. In these builds SIGTERM does not end the process: its handler writes an eventfd, the main loop ends at its next poll, and then, as after a closed connection, the writes are waited for, the runtime torn down and checked, exit status 0.
- The order: the unhandled rejections and the main module's promise; the debugger (detached); what the `kario` module holds, the event handlers, capability calls, timers, page stack, translations and storage (`jsrt_kario_free`); fetch and WebSocket (`jsrt_net_stop`: every request and connection is cancelled, their JS values let go, the fetch and WebSocket threads waited for, and a connection whose thread has finished lets go of its object, which its finalizer frees with the runtime); native modules (`jsrt_native_free`: calls not started yet dropped, those under way waited for, the modules' handlers let go); the storage writer (`jsrt_store_free`: the rest written, the thread joined); `JS_FreeContext`, `JS_FreeRuntime`; last, the C side of the requests and of the network state (`jsrt_net_free`: by then every response body's finalizer has run).
- The thread rules stay (`jsrt_net_drain`'s): no request is freed while its fetch thread can still touch it, no WebSocket connection while its thread is there; a native module's library is not unloaded, its threads may run on, and its state stays. Threads are waited for 200 milliseconds at most (`JSRT_TEARDOWN_WAIT_MS`, from the start of the teardown, shared by the network and native modules); what a thread still there then can reach is kept (reachable, so not a leak).
- Then `_exit`, with no atexit handlers or destructors: OpenSSL's cleanup in atexit and the destructors of native module libraries are not safe under threads still running; LeakSanitizer has looked already.
- Only in sanitizer builds: a normal build frees nothing as it exits and the kernel takes the memory back; tearing down would only slow the exit and wait on threads, and on the device SIGTERM still `_exit(0)`s as soon as the writes are done, so a turn that does not end cannot hold it. What changed in normal builds too is a few error paths that now free what they should (a failed `--compile`, the report of a failed main module, no `PHONE_UI_FD`, the export table of a refused native module below), and the storage writer is created joinable instead of detached (in a normal build it never returns, so that makes no difference).
- The cost: from SIGTERM to the process gone, 10–12 milliseconds in the ASan build, 2–3 before (`TestStorageSIGTERMFirstProcess`'s nothing stored and written, 3 runs each, not holding the lock).

**A change for TSan**: `on_crash` in `native.c` unblocks its signal before `raise`. TSan wraps `sigaction` and runs a handler with every signal blocked, so the SIGABRT raised stayed pending, and the process returned from the handler and exited with 134 instead of being killed by SIGABRT: `TestNativeCrashFirstProcess/abort` failed under TSan before the change and passes after it. In normal builds the handler is installed with `SA_NODEFER` and an empty mask, and the step does nothing.

**What it finds** (developer machine, 2026-11-26 and 27, in scratch copies with a fix reverted or something broken on purpose):

- The old `jsrt_net_drain`: it cleared `posted` for the whole done list at once under the lock, so a fetch thread could put a request on the done list again right away while `settle` freed it, and the next drain wrote to freed memory. `make jsrt-asan` fails: the report of `TestFetchAbortRace` (0.34 seconds) is `heap-use-after-free ... WRITE of size 4`, `#0 jsrt_net_drain jsrt/src/net.c:974`, `#1 loop jsrt/src/main.c:400`, `#2 main jsrt/src/main.c:495`; freed in `req_free net.c:728` ← `settle net.c:958` ← `jsrt_net_drain net.c:985`, allocated in `jsrt_fetch net.c:1246`.
- The old `body_cancel`: it wrote `q->mode` without the lock. `make jsrt-tsan` fails: `TestNet`'s checks all passed, and it failed on the report alone, a `data race`: the main thread writes in `body_cancel jsrt/src/net.c:1073` (through QuickJS's frames back to `jsrt_net_drain net.c:998`, `loop`, `main`), and fetch thread T3 reads in `on_body jsrt/src/net.c:402` holding the lock (called by libcurl's `Curl_client_write`).
- One `free` short (2026-11-27, a scratch copy, `make jsrt-asan` run holding the lock): with the `free(q->buf.s)` of a body read whole (`text()`, `json()`, `arrayBuffer()`) taken out of `settle` (`net.c:966`), `make jsrt-asan` fails (111 seconds): the 5 reports of `TestFetch`, `TestFetchWeb`, `TestFetchAbortRace` and `TestNet` are all `LeakSanitizer: detected memory leaks`, every one allocated at `#0 realloc`, `#1 dstr_put jsrt/src/kario.c:43`, `#2 on_body jsrt/src/net.c:409`, `#3 Curl_client_write (libcurl.so.4+0x1c6d3)`, `TestFetch`'s being `Direct leak of 16779264 byte(s) in 9 object(s)`. The scratch copy has been put back.
- A real leak found once the check was on: when a native module's `kario_native_init` has run and the module is then refused (`TestNativeRefused`), its export table, export names and string values were not let go: `Direct leak of 1120 byte(s)`, `add_export jsrt/src/native.c:585` ← `api_export_number` ← `init` in `testdata/native/probe.c`, and 21 indirect ones. It could not be found before: a process that used native modules left by `_exit`. They are let go now (`native.c`): `make jsrt-asan` failed in `TestNativeRefused` before the change and passes after it.
- Every exit is checked: another scratch copy loses a 4242-byte block at the start of `main`, and each of the 17 processes started by `TestStorageSIGTERMFirstProcess` (the app the first process of its pid namespace, SIGTERM), `TestStorageDurable` (a closed connection, SIGTERM, a failed main module), `TestNet`, `TestNative`, `TestDebugger`, `TestBudget` and `TestNotUnderShell` reports it.
- On the current code both targets pass with the report directory empty; there was no UBSan report.

**CI**: the `jsrt-sanitize` job ([38](38-contributing.md) §2), ASan and TSan on a runner each, at the same time as the `go` job; it runs when the plan runs the `jsrt` package (a change to kario-jsrt's C source, the `jsrt` package's tests, the `sdk/ts/node` and `sdk/c/include` they read, the build files, a run by hand). On every such pull request, not on a schedule:

- It costs little: the tests take only about 15 seconds longer than without a sanitizer (their time goes mostly into waiting, not computing; inferred), and what it adds is mostly the cold build; the two runners go at the same time as the `go` job, which has much more to build and test, so CI as a whole takes no longer.
- It is worth most before the merge: both faults above passed the normal tests, and the ASan one fails within a second every time; run on a schedule, a fault would show only once merged, and the commit that brought it would still have to be found.
- The `platform` workflow runs for pull requests and by hand only, with no schedule trigger; with one, the plan would run all of CI ("a schedule event runs everything").

It ran on GitHub on 2026-11-27 (once each on dev and main), and ASan and TSan both failed: what failed is three cases of `TestNodeFetchResponseHeaders` (the job ran on the runner's own Node.js 22, whose fetch took response headers named with a non-token and joined a folded line, all of which the developer machine's Node.js 24 refuses; the Node runtime now refuses such names itself, and the test expects the fold's result by Node's version), not a sanitizer's report; a whole pass on GitHub is **not verified**. The job sets `vm.mmap_rnd_bits` to 28 first: with the kernel's address randomization any wider, the sanitizers' shadow memory may not fit.

**Not there yet**: clang (it needs an external symbolizer), MemorySanitizer (the whole chain of dependencies would need instrumenting, and libcurl is not), runs on arm64 (only the x86-64 developer machine so far): **not implemented**. What leak checking does not see: TSan builds (they have no LeakSanitizer); a process ended by a signal (the native module crash tests); what a thread that did not finish within the teardown's 200 milliseconds holds; a native module's own memory (its library stays loaded); the tests that run Node.js (not kario-jsrt). In a sanitizer build SIGTERM waits for the main loop to come back to its poll, so a turn that does not end, a debugger stopped at a breakpoint or a blocking synchronous native call keeps the process from leaving (normal builds are not affected).

- **The same contacts**: `compare.py vcf --zhangsan <number> --lisi <number>` writes a card file of 202 people (Zhang San, Li Si and 200 common names, many sharing a surname, so that searching is a test), which every phone imports; Zhang San's number is the sender phone's, so the call and the SMS really go through. - **The same message traffic**: the second account sends both phones the same message at a fixed interval from the sender phone (`traffic.sh`, by default one every 15 minutes, 96 in 24 hours); Kario's Hongyan receives it through the demo server on the cloud host (§9.7), Android's WeChat through WeChat's own servers.
- **The same brightness**: automatic brightness off, the middle of the screen equally bright (a light meter or app against a white page, within 10%), each setting noted.
- **The same start**: each round begins with a reboot and 10 minutes idle after it (`android-half.sh idle` waits the 10 minutes before the memory; `kario-half.sh mem-idle` asks whether it rebooted and idled first); automatic updates off on both; Bluetooth on only for the tasks that need the keyboard; location off.
- **How the Android phones are set up**: after a factory reset only WeChat and Alipay are added, both logged in with their notifications on, battery optimisation left as it is (as an ordinary user leaves it, no allow list for WeChat); the vendor's own apps stay, and `facts` notes which app plays each role.
- **One person, the same runs**: each task 5 times on each phone (`--reps`), after 3 practice runs on each; the phones in turn (Kario, Android, Kario...), so that practice evens out; the median is reported.
- **Each phone's quickest way**: each phone is done with its own fewest keys (found first), not by copying the other's path; the table says how many keys were pressed, not how many should be.

### 9.6 Hardware for the same smoothness: Kario's ladder

Kario on the 6T is brought down to the J36's class: only the 4 little cores (A55 1.77 GHz, the J36's are A53 2.0 GHz), 3 GB of memory left, then 2 GB; each rung runs `tasks.play` (`kario-half.sh perf`) and the seven tasks again, each a column of the table (`--side kario-3g`, `--side kario-2g`). Compared are `play.*`, `frames.*`, `start.*` and `task.*.s` against the J36's column: no worse than the J36 on that rung, and the answer to "how much hardware" is "no more than an Android keypad phone sold now"; still fine a rung lower, and it is less. The memory rows are not read on the ladder (the memory held counts as used).

At run time (try this first; after a reboot and idle, in the USB console, **not verified**):

```
for c in 4 5 6 7; do echo 0 > /sys/devices/system/cpu/cpu$c/online; done
keep=3072                                           # MB left to the system: 3072 on this rung, 2048 on the next
total=$(awk '/MemTotal/ {print int($2 / 1024)}' /proc/meminfo)
mkdir -p /run/hold && mount -t tmpfs -o size=$((total - keep))m hold /run/hold
dd if=/dev/zero of=/run/hold/fill bs=1M count=$((total - keep))
```

Kario has no swap, so the pages in tmpfs cannot be reclaimed and that memory is as good as taken away; afterwards `umount /run/hold`, and a reboot brings the big cores back. Where the big cores cannot go offline (a kernel without CPU hotplug), change the boot parameters: repack the boot image with `unpack_bootimg` and `mkbootimg` as [39](39-oneplus-6t.md) §8.2 does, with Kario's own kernel and ramdisk and `maxcpus=4 mem=3G` (or `mem=2G`) after its command line, and `fastboot boot` it (in memory only, nothing written to the phone; whether the part `mem=` cuts off holds memory the modem reserves is **not checked**, and if it does not boot, use the run-time way only). The same limits can be put on the second 6T's LineageOS (`adb root`, Rooted debugging in the developer options); it has zram, so holding memory takes random data (`/dev/urandom`), **not verified**.

### 9.7 Standby for 24 hours

Two rounds of 24 hours, the two phones side by side at once: first Kario's 6T and the J36, then Kario's 6T and LineageOS's 6T (WeChat account A moved over to it: a WeChat account is logged in on one phone at a time). Kario's Hongyan talks by default to the demo server and push gateway on the phone itself (`127.0.0.1`), so its messages would not cross the radio, which is unfair to Android. So the two move to a cloud host, which the phone reaches over mobile data as WeChat reaches its servers. The cloud host's public IPv4 must be on its own interface (the certificate the gateway signs itself at its first start names only the address it listens on and `localhost`; a cloud host whose public address comes in by NAT will not do):

```

./phone-chatsrv --listen $H:8791 --gateway https://$H:8790 --gateway-cert ~/pushgw-tls/cert.pem &
```

Copy the cloud host's `~/pushgw-tls/cert.pem` to the phone's `/var/lib/kario-test/cloud-pushgw.pem`, then in the phone's USB console (a drop-in's `EnvironmentFile=` comes after the product layer's `services.env` and overrides it):

```
for u in phone-pushd phone-display; do mkdir -p /etc/systemd/system/$u.service.d; printf '[Service]\nEnvironmentFile=/etc/kario-compare.env\n' > /etc/systemd/system/$u.service.d/compare.conf; done

```

Open Hongyan once (it logs in to the server on the cloud host with its new push token), send one with `traffic.sh --chat http://$H:8791 --count 1`, and a notification should show on the phone. The demo server has no authentication (it is a demo): anyone who knows the address can send, so it runs for the two test days only and stops after, with no real data on it; afterwards delete the two drop-ins and `/etc/kario-compare.env`, `systemctl daemon-reload`, and restart the two services. The push heartbeat is learnt (from 30 seconds, doubled once a connection outlives 3 of them, at most 28 minutes, [21](21-push.md) §2), and WeChat has its own: both phones are first connected on this network for 3 hours, then rebooted and left idle 10 minutes before the start (the interval learnt survives the reboot).

> 2026-11-27. The threat model was written first ([31](31-lock-and-biometrics.md) §13) and this follows it. There now are: the test program `phone-factory-test` (package `factory`, `programs/factorytest`), factory mode (the gate at boot, the Shell's factory screen, the USB link without trust) and the interface the station uses (§10.5, [22](22-developer-api.md) §11). What ran is in §10.6: the Go tests on the dev machine, the factory cases of `make selftest`, phone-paint's pixel cases in four form factors, and `make yocto-factory-test` on QEMU. All of it is **not tried on a phone**: the steps on the OnePlus 6T are in [39](39-oneplus-6t.md) §14.24, for the tester Reasonix to try.

### 10.1 What it checks

The SKU decides: the SKU in `sku.json` (made by `tools/sku.py`) and its `factory` section: each key the operator presses (`keys`, by `keys.toml`'s names), the chip of the phone's own keypad and the codes its input device reports (`keypad`; a whole phone's Bluetooth or USB keyboard is not the phone's own and has none), the board's button devices (`buttons`), the kinds of its parts (`parts`, a camera as `camera-<facing>`), the main panel's pixels (`panel`), and what the SKU's `[factory]` gives: `optional` (checks whose failure does not fail the unit; `camera.*` names a kind) and `storage_gb`. Each check is automatic or done by a person (interactive), required or optional; a check of hardware the SKU does not have is skipped with the reason, which is not a failure.

| Check | Kind | When | What it checks |
|-------|------|------|----------------|
| `input.keypad` | auto | the phone's own keypad | an input device reports all the keypad's codes (for a USB keyboard 1, A and Enter) |
| `input.buttons` | auto | buttons given | each button's input device is there (power, volume) |
| `input.sound-switch` | auto | a sound switch | that device reports `ABS_SND_PROFILE` or `SW_MUTE_DEVICE` |
| `input.lid` | auto | a lid | that device reports `SW_LID` |
| `input.touch` | auto | a touchscreen | a direct (`INPUT_PROP_DIRECT`) input device reporting positions |
| `display.mode` | auto | the panel's pixels given | a connected DRM connector's preferred mode is the panel's pixels |
| `audio.card` | auto | a sound card | the SKU's card (or the first) is in sysfs |
| `audio.ucm` | auto | the board names UCM verbs | the verbs `alsaucm` lists include the board's (music's and the call's) |
| `vibrator` | auto | a vibration motor | `leds/vibrator`, or a force-feedback (`FF_RUMBLE`, `FF_PERIODIC`) input device |
| `sensor.light`, `sensor.proximity`, `sensor.accelerometer`, `sensor.gyroscope`, `sensor.magnetometer` | auto | that sensor | an IIO device with that kind of channel, which reads |
| `battery` | auto | a fuel gauge or charger | the battery is there, its voltage and capacity read; with USB in it is charging or full |
| `rtc` | auto | always | read twice a second apart, the clock runs |
| `storage` | auto | `storage_gb` given | the internal disks hold at least that together |
| `memory` | auto | the memory size given | the device tree's memory nodes add up to at least the SKU's (without nodes `MemTotal`, up to an eighth short) |
| `wifi` | auto | Wi-Fi | an ieee80211 phy |
| `bluetooth` | auto | Bluetooth | an hci device |
| `modem` | auto | a modem | telephonyd's `status` has an IMEI (waiting up to 90 seconds for ModemManager); the test sends no AT commands, and the report has no IMEI |
| `sim` | auto | a modem | a SIM in the tray (ready, wanting a PIN or PUK, or locked all count) |

### 10.2 The test program

```
phone-factory-test [--auto] [--out FILE] [--sku FILE]      on the phone: the report on stdout and in FILE (default /run/phone/factory/report.json)
phone-factory-test --unit ADDR [--auto] [--wait DUR] [--device ID] [--out FILE]
                                                           test the unit at ADDR (one phone on USB: 10.71.0.1:7171; the station gives $UNIT)
phone-factory-test --unit ADDR --provision CA_DIR          provision it with a CA at hand (the station's flow locally, for tests)
phone-factory-test --gate                                  phone-factory-gate.service: factory mode's gate
phone-factory-test --serve [--listen ADDR]                 phone-factory.service: the test program in factory mode
phone-factory-test --fake DIR ...                          on a dev machine: a phone made up in DIR with all the SKU's hardware
```

- Exit codes: 0 every required check passed; 1 one did not (failed, or an interactive one not done); 2 the test could not run (arguments, SKU, no connection); 3 not in factory mode (the keystore is provisioned, or does not answer).
- `--auto` runs only the automatic checks. Without it the interactive results come from the factory screen (§10.3): `--wait` is how long to wait for the operator, and what is not done by then does not pass.
- On the phone, when the test program serves in factory mode (`/run/phone/factory.sock`), `phone-factory-test` on the command line asks it, with the result the station gets; otherwise it runs the checks itself, asking the keystore first too: provisioned, it exits 3.
- `--device` (by default the environment's `DEVICE_ID`, which the station sets for its test command): a report with another device id exits 2, so one unit's results are not recorded for another ([31](31-lock-and-biometrics.md) §13.4, property 6).
- The report's device id is the keystore's; the report has no IMEI and no user data.

### 10.3 Factory mode

With `kario.factory=1` on the kernel command line and the keystore not provisioned, the boot is in factory mode (why that is safe: [31](31-lock-and-biometrics.md) §13):

1. `phone-factory-gate.service` (started only with `kario.factory=1` on the command line, ordered before the Shell, messages and push) runs `phone-factory-test --gate`: it asks keystored whether it is provisioned; if not it writes the mark `/run/phone/factory/on`; if so it exits 3 and clears the mark, and the boot is a normal one, the log saying why.
2. With the mark, `phone-factory.service` starts the test program (`--serve`), which asks the keystore again as it starts; `phone-smsd` and `phone-pushd` do not start (`ConditionPathExists=!/run/phone/factory/on`).
3. The Shell sees the mark at boot, asks the gate again itself and enters factory mode: its state directory moves to `/run/phone/factory/state` (in memory), it starts no apps and no setup, and shows only the factory screen; the status bar's middle always says 「■ 工厂模式」 (■ Factory mode), and every screen's title starts with 「工厂测试」 (Factory test).
4. The factory screen's home lists the SKU's interactive checks, then 「自动检查」 (Automatic checks) and 「清除并重启」 (Erase and restart). OK opens, ↑↓ move; on a check's screen OK records a pass and Back a failure (on the 6T, with only power and volume keys: power opens, volume up passes, volume down fails and moves). Once a check is recorded the selection moves to the next one. The results go to the test program (`/v1/result`), which is what the station's full test gets.
5. The display check's full-panel colours are drawn by the renderer: the frame has a `pattern` member ([23](23-renderer-protocol.md) §4), which phone-paint and phone-gui both draw over the whole panel without the status bar, the grid's lines on the same panel pixels; the next key, or 30 seconds, bring back the marked screen. On a renderer without `pattern` the check is skipped with the reason. Both renderers draw the touch check's squares, but phone-gui reads no touchscreen ([23](23-renderer-protocol.md) §10), so with it no square can be touched and the check fails after 20 seconds or on Back.
6. Plugged into the station: once USB is configured the link has its address and DHCP, the firewall lets only UDP 67 and TCP 7171 through, and there is no 「信任这台电脑吗」 (trust this computer) prompt ([27](27-usb-typec.md) §3.4).
7. Leaving: once the station has provisioned it, the screen says it has its certificate and powers off after 10 seconds (OK at once); or 「清除并重启」 on the home erases the data partition as a factory reset does (the device keys and the factory's certificates stay). There is no way back to the normal system; factory mode's things are all on `/run`, so after a power cut the boot is a normal one with nothing of it left.

### 10.4 The report

The report is JSON whose `schema` is `kario.factory-report/1` (fields added later keep the name; it changes only when a meaning does):

| Field | What it is |
|-------|-----------|
| `schema` | `kario.factory-report/1` |
| `device_id` | the keystore's device id (absent when the keystore does not answer) |
| `sku`, `board` | the SKU's and the board's ids |
| `mode` | `auto` or `full` |
| `started` | when it started (RFC 3339) |
| `duration_ms` | how many milliseconds it took |
| `passed` | every required check passed |
| `refused` | not in factory mode: why (then there are no checks, exit 3) |
| `checks` | an object per check, in §10.1's order |

Each check: `id` (§10.1's name), `kind` (`auto` or `interactive`), `required`, `result` (`pass`, `fail`, `skip`; an interactive one not done yet is `skip` with the reason `not done on the factory screen`), `value` (what was measured: device names, a mode, a voltage, a capacity…), `reason` (why it failed or was skipped) and `duration_ms`.

The test program's HTTP API (`factory/server.go`) has on the USB link's `10.71.0.1:7171` only the station's five requests; the factory screen's four are only on the test program's socket (`/run/phone/factory.sock`, 0600):

| Request | Who | What |
|---------|-----|------|
| `GET /v1/unit` | station | `kario.factory-unit/1`: `device_id`, `sku`, `board`, `provisioned` |
| `POST /v1/test` | station | `{"mode": "auto"\|"full", "wait_s": N}`: runs the test and answers the report; not in factory mode, 403 and a report with `refused` |
| `GET /v1/keystore/csr` | station | the keystore's `csr` |
| `POST /v1/keystore/attest` | station | `{"nonce": "…"}`: a device attestation of the nonce as the app `system.provision` |
| `POST /v1/keystore/install_cert` | station | `{"cert", "cert_sm2", "root"}`: installs the certificates; everything asked after is 403 |
| `GET /v1/plan` | factory screen | the SKU, the plan, the results so far |
| `POST /v1/result` | factory screen | an interactive check's result |
| `POST /v1/microphone` | factory screen | record and measure (`{"loopback": true}`: with the tone playing) |
| `GET /v1/report` | factory screen | the last report |

The station's requests other than `/v1/unit` ask the keystore first whether it is provisioned, and are 403 if it is; `/v1/unit` answers `provisioned` as it is (503 when the keystore does not answer).

### 10.5 The station

The station's (kario-internal) flow is in [22](22-developer-api.md) §11: it takes several phones, each plugged into a USB port of its own (a `usb:IFACE` target), and tests them in parallel: it waits for the test program to answer, reads the `csr`, runs the test and provisions the units that passed; one that failed gets no certificate, and its result goes to the provisioning service too, which can require a passed test per model. The test is the full test by default (`POST /v1/test` with `full`, waiting for the operator to finish the checks a person does on each unit's factory screen), only the automatic checks (`auto`) when unattended, or the vendor's own command instead: it gets `DEVICE_ID` (the unit's device id) and `UNIT` (the unit's test program's address), must exit 0, and the factory report on its stdout is the unit's:

```
phone-factory-test --unit "$UNIT" --wait 10m
```

The exit code is as in §10.2. All the station does through the test program goes through package `factory`'s client: `*factory.Unit`'s `Info` and `Test` and `factory.Keystore` (`CSR`, `Attest`, `InstallCerts`), with `factory.KeystoreSock` for a keystore over a socket. `factory.Dial` never goes through a proxy, also with `HTTP_PROXY` set on the station machine. `factory.Provision` is the same flow with a CA at hand (for tests).

The station does not tell the phones apart by address: each is `10.71.0.1` on its own link, and the station's own address on the links is often the same too. For each `usb:IFACE` it opens a Unix socket only it can read and write, every connection through which is bound to that interface with `SO_BINDTODEVICE` before it connects to `10.71.0.1:7171`, and `UNIT` is that socket (`unix:…`). The station machine needs Linux 5.7 or later (or `CAP_NET_RAW`), a DHCP client on each USB interface, `rp_filter=2` on those interfaces and a fixed interface name for each port (why: [22](22-developer-api.md) §11). On a dev machine with one phone attached, `phone-factory-test --unit 10.71.0.1:7171` still tests it directly.

The station testing several units at once has run on the dev machine against the real test program and over real kernel links in network namespaces; **not tried on a phone**, nor on real USB hardware (interface names fixed per port, DHCP on each link, real cables). There is no authentication between the station and the phone: **not implemented**, see [31](31-lock-and-biometrics.md) §13.5.

### 10.6 How to run it and what ran

- Go tests: `go test ./factory ./programs/factorytest` (SKU to plan, the report's format and this section's fields, exit codes, the gate refusing a provisioned keystore, each automatic check passing and failing against a made-up sysfs and made-up services, the microphone's loopback, the station's API, `factory.Dial` not using `HTTP_PROXY`); `go test ./shell -run Factory` (the factory screen's keys, display, touch, microphone, the 6T's buttons only, cameras skipped, factory mode's screen, the USB link, powering off once provisioned).
- `make selftest`'s 「工厂模式」 (factory mode) cases (`#part factory`): the Shell starts the test program in its own process over a made-up unit (`factory on`): keys, display, speaker, vibration, the front camera, the automatic checks (the exit code going from 0 to 1 with the sound card taken away), the USB link, and exit 3 once provisioned; the touchscreen case needs a pixel renderer.
- Pixel cases: `phone-shell --selftest --gui phone-paint --device <form factor> --only '工厂模式|工站灌装'`, for bar-t9, bar-qwerty, communicator and the flip (`--sku shell/testdata/sku-lid.json`).
- phone-gui: `cd gui && cargo test --release --locked` (`tests/pattern.rs`: it declares `pattern`, a solid colour fills the whole panel and leaves nothing once taken away, a grid's lines fall on the same whole pixels as phone-paint's); the pixel cases as above with `--gui gui/target/release/phone-gui`.
- QEMU: `make yocto-factory-test` (after `make yocto-build`) boots twice with `kario.factory=1`; the results are below.
- OnePlus 6T: **not tried on a phone**; the steps are in [39](39-oneplus-6t.md) §14.24.
