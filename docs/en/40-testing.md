# Testing: methods and strategy

> How Kario is tested: the layers, the command for each, which hardware is simulated, how one scenario script runs both on the developer machine and in the emulator, what to run for what change, what to run before publishing, and the rules for writing tests. The commit and CI flow is in [38](38-contributing.md); each round's results are in [13](13-prototype.md) §5 and the internal verification baseline (57 (internal document)).
> Status: the commands and flows written here have been used on the developer machine (RHEL 8, x86-64, 48 cores) and in QEMU (qemuarm64, TCG) (2026-11-19; the runs in parts on QEMU and the developer machine and their times: 2026-11-25); **not tried on a phone**: testing on a real phone (§7) has not started.

## 0. Summary

- **One scenario script runs everywhere**: `shell/selftest.script` (208 cases) runs headless on the developer machine (the text UI), through the pixel renderer in three form factors, and at boot in QEMU's two images; the compatibility test (CTS) is that plus capability coverage and a signed report. On a real phone it will be the same script (§7).
- **Simulations stand in for hardware, and their limits are written down**: the baseband, ModemManager, Wi-Fi, Bluetooth, NFC, satellite positioning, sensors, fingerprint, camera and the update server all have a simulated side (§3); the real-phone part of each is marked **not tried on a phone**.
- **Every bug fix comes with a test that fails on the old code**, seen failing before the fix; **every capability is called at least once**, or the CTS fails; **every place that parses untrusted input has a fuzz target** (67 targets).
- **Run what the change needs**: CI picks by the change ([38](38-contributing.md) §3); before publishing the whole set runs on the developer machine and in QEMU (§5).
- **Results go into the docs as they are**: ✓ names only the environment it ran in and the date, simulated things say "simulated", what has not run says **not verified**.

## 2. The scenario script

`shell/selftest.script` is a key script: `== title` starts a case, one command per line below it, run by `Runner` in `shell/headless.go`. The commands are of three kinds:

- **Keys and waiting**: `key`, `type`, `long`, `tap` (pixel renderer only), `wait text [ms]`, `wait-re regexp`, `gone text`, `at screen`, `key-if key text ms`. `wait` and `wait-re` also accept a toast shown since the last input (a key, typing, a touch), even one already gone: a toast stays 2.5 s and on a busy machine the runner can look too late, while a person watching the screen saw it; `gone` looks at the screen as it is.
- **Simulating the world**: calls and messages (`tel`, `sms`, `mms`), Wi-Fi access points (`wifi-ap`, `wifi-join`), Bluetooth peers (`bt-peer`, `bt-push`, `bt-oldphone`), card readers (`nfc`), position (`location`), light (`lux`), fingerprints (`finger`), time (`timeshift`), servers (`fetch-server`, `carddav-server`, `parent-server`, `store-publish`) and more, each described at the top of `headless.go`.
- **Checks**: commands that look at the system's state directly, such as `saved`, `sealed`, `perm-state`, `vibrated`, `appstate`, and `snap name` (a snapshot).

`require-*` lines skip a case where the environment lacks something (277 lines: no baseband `require-tel`, no SMS service `require-sms`, BlueZ only `require-bt bluez`, pixel renderer only `require-gui`, ...); a skipped case says SKIP in the report, with why, and is not a failure. A phone lacks some of the simulated hardware the script drives, its board having its own or none, and those cases are skipped there too, not failed: `require-fingerprint` (the simulated fingerprint sensor `finger` touches; a board names a sensor in its SKU's `fingerprint`, the phones none, so phone-keystored has none), `require-gnss sim fifo` (a receiver `location at` moves: the simulated one or the emulator's pipe; the phones' is ModemManager's; also the cases that need the weather app's position), `require-lux` (the simulated light sensor `lux` sets; a board's own is found by itself). The lock-screen cases that only lock the phone unlock it with the PIN, so they run without a fingerprint sensor, and the PIN is still removed at the end. `require-kernel <protection>...` skips where the kernel probe found the protection missing (`shell/kernel.go`, the compatibility report's `sandbox.missing`), and `require-previous` a case that goes on where the one run before it in its part stopped (a message it sent, a call it made, its counts) when that one did not pass (cases skipped in between for the environment or `--only` do not count; a case that only differs in its snapshots ran through). A case never goes on from another part's: when no case of its part ran before it and one was skipped for the environment, it is skipped too, naming that case and why (the background jobs case goes on from the weather case, which needs a location receiver the script can move; on the 6T it went on from the part before and failed at its first step). Other conditions a phone may not meet, each skipped saying why: `require-own-kernel` (the running kernel is one this system ships: `/lib/modules/<release>` is in its root; in the chroot it is Nura's), `require-systemd` (this system's service manager answers `systemctl`; in a root systemd does not run in, `systemctl` prints nothing and exits 0), `require-vpn sim networkd` (either VPN backend; in the chroot there is no systemd-networkd on the bus), `require-wifi-ap` (`wifi-ap` can put an access point up: the simulated Wi-Fi, or a second Wi-Fi device under iwd, the emulator's simulated radios; a phone's own radio is not taken for it), `require-mobile-route` (where the per-app firewall runs, `net-send`'s packets leave by a link that counts as mobile: a mobile data block holds there only, and on Nura they left by its Wi-Fi), `require-bt-peer` (the selftest's Bluetooth peer is a virtual controller, btvirt's, which reaches only virtual ones: skipped where the phone's adapter is a controller of its own or the kernel has no hci_vhci), `require-direct-route` (the device's packets have a route outside the tunnel: with neither Wi-Fi nor mobile data, the VPN cases' `direct` and `blocked` cannot be told from the kernel's network unreachable), `require-sleep` (nobody else holds a wake lock: the bring-up image's `phone-bringup` keeps the kernel from suspending). `require-button power` runs a case only where someone presses the board's own power button when asked (the variable `PHONE_SELFTEST_BUTTONS` names `power`): the `button power` step asks with `PHONE-SELFTEST-PRESS: power <n>` on its output, reads the kernel's input devices itself until the key has gone down and up (the headless renderer reads no keys), and gives the Shell a short or a long press by the renderer's rules (`button-burst power <presses> <gap ms>` asks for presses in a row and gives each as it comes); in QEMU's boot selftest `yocto/qemu-buttons.py` presses the virt machine's power button from the QEMU monitor (`system_powerdown`, [28](28-battery.md) §7), while the developer machine's runs and the phone kit's do not set it, so the case skips there. The steps are listed at the top of `shell/headless.go`.

**On a kernel without Landlock** (Nura's for the 6T, [41](41-design-gaps.md) §11) "沙箱：独立 uid、命名空间、Landlock" (sandbox: separate uid, namespaces, Landlock) is skipped (`require-kernel landlock`, saying why), not failed: the sandbox does without the layer as designed and says so ([24](24-sku-framework.md) §7.5), the compatibility report's `sandbox.missing` names it for the certifier, the layers still in force are checked by "沙箱：已生效的限制层全部符合预期" (sandbox: every layer in force as expected), which runs everywhere and fails on any ✗, and the DNS case already skips its Landlock half. "内核特性" (kernel features) is the one case that calls a missing protection a failure, on purpose, since Kario's own kernels (QEMU, the whole phone) must lack nothing. On another system's kernel (the chroot on Nura: no `/lib/modules/<release>` of it in the image) it is skipped (`require-own-kernel`), its reason naming what that kernel lacks, and the compatibility report's `sandbox.foreign` says the kernel is not the device's; on a kernel the image ships it still fails, naming what is missing ([39](39-oneplus-6t.md) §14.12).

**What a failure prints**: the failing line and why, the whole screen's text at that moment, each app process's state (frozen or not, what it waits on), the last few dozen lines of the Shell's log; in QEMU also the Bluetooth and iwd journals and the snapshots' PNGs (base64 on the serial console). Before the result line, `PHONE-SELFTEST-FAILED:` names each failed case with its reason.

**Going on after a failure** (`phone-shell --selftest --keep-going`, likewise with `--cts` and `--script`): by default a run stops at its first failure. With `--keep-going`, after a failed case the phone starts over as in the cases that restart it (the Shell, its services and apps, in place; the Runner's `KeepGoing`, `shell/headless.go`), and the run goes on at the next case; it still fails, `PHONE-SELFTEST-FAILED:` and the JUnit report listing every failure, and the snapshot comparison's counts and the compatibility run's capability coverage count every case that ran. `make selftest`, `make cts` and QEMU keep stopping at the first failure; the phone kit's `selftest` and `pixel` use it, in the chroot and on the whole phone ([24](24-sku-framework.md) §6.2). The next case starts from the phone's state as the failed case found it, not from what it left behind: as each case starts, the Runner brings a copy of the state and persist directories up to date (`StateCopy`, `shell/keepstate.go`, in the run's directory), and phone-shell puts the copy back once the Shell, its services and its apps have stopped, before the phone starts over. Only what differs is copied: a file whose size, modification time, mode or owner differ from its copy's, or whose inode changed since shortly before the last copy (a coarse clock's tick, or a writer that sets the time back); files are copied, not linked, since the Shell, the services and the apps rewrite them in place. The cost is printed at the end (`PHONE-SELFTEST-KEPT:`, counted across the start overs): on the developer machine the whole script (227 cases, 16.5 minutes) took 6.5 ms a case on average, 2.9 ms the median, 195 ms at most (the largest copy, the 12 MB of the music import, took 13 ms), 41 MB copied in all, about 1.5 seconds of the run, for a state of at most 134 files in 102 directories, 16.5 MB (the copy takes as much again). Not put back: what is not on the phone's disk, namely the simulated servers' state (the store backend, the push gateway; the Hongyan server starts empty anyway), the clock moved by `timeshift`, the screen and the apps' processes (an app opens at its first screen after the start over, and asks again for a permission granted only to its last process: a case opens its own app and screen, rules below), and the simulated radios' devices and pairings (BlueZ keeps its own; on the developer machine a case using the headset paired earlier fails after a start over, "通讯录：蓝牙收名片" for one, **not solved**). A phone with a lock-screen PIN starts locked, as a phone does, so the lock-screen cases begin with `unlock 2468` (types the PIN on the lock screen only when locked). A case that fails while undoing what earlier cases set (the PIN-removal case) leaves that to the cases after it. Unit tests ✓ (`shell/keepstate_test.go`; `shell/keepgoing_test.go`: a case sets a lock-screen PIN and fails, and the next starts without it; one fails with a PIN an earlier case set, and the next starts locked and unlocks it; without putting the state back the next case starts locked and fails, as on the phone); on the developer machine, the lock-screen cases with a failure put into "锁屏通知" (lock-screen notifications) and phone-keystored without a fingerprint sensor: only that case fails (before this change: ten of the twelve cases after the one setting the PIN, which was never removed). **Not tried on a phone**.

**Snapshot comparison** (`shell/snapcmp.go`; `make selftest`, `make pixel-selftest`): the snapshot `snap name` keeps is compared with its baseline in `shell/testdata/snapshots/`, and one that differs fails its case (a line `SNAPSHOT-DIFF:` in the report, and the counts in `PHONE-SNAPSHOTS:` at the end); `make cts`, `go test ./shell` and QEMU do not compare.

- **What changes is held still**: while a snapshot to compare is drawn, the clock of the status bar and the idle screen stands at 2030-01-09 09:41 (in the time zone in force), the battery is the simulated 82% (or what the script set with `power`), the signal three bars, the live network speed 0, transitions and the boot animation at a fixed frame. The boot snapshot at the top of the script (`sleep` and `snap 00-boot`) shows that frame of the boot animation even when it comes after the 1.5-second animation is over (a busy machine, all the parts starting at once); not once the script took another step before it or reached its first case. Only while the selftest draws a snapshot: the product's display does not change. The letters and digits of the times left in the frames and the text (`9:41`, `01-09 09:41`), loopback ports, device IDs (`PH-…`) and hotspot names (`Kario-…`) become 0 before comparing. In a run that compares snapshots the apps get a fixed seed for what they draw at random (`PHONE_TEST_SEED`: the snake's food falls on the same cell every time), and phone-mediad runs with `--test-stills`, so every photo the simulated camera takes is the same picture (its viewfinder stays live). Before each key the selftest gives the pixel renderer the screen as it is, as a person sees it before pressing: where a list scrolls follows the frames the renderer laid out, and when the selftest sent at most one frame every 100 ms, quick keys acted on screens the renderer never had, so the same snapshot came out scrolled a row further in one run than in another.
- **Text**: one per form factor, `text/<form-factor>/<name>.txt`, about 110 KB for all of them; when one differs, the differences line by line go to `build/snapshots/diff/<name>.diff`.
- **Pixels**: about 120 PNGs a form factor, about 31 MB for the three, and as much again with every change to the UI: not for git. The baseline is a SHA-256 of each one's decoded pixels (its first 128 bits), in a file for each renderer, form factor and set of fonts (`pixel/<renderer>/<form-factor>[-<fonts>].json`). phone-paint draws with the fonts it finds on the system, and other fonts draw otherwise, so the file's name carries a hash of the font files it would use; a machine whose fonts have no baselines is told "no pixel baselines … not compared", which does not fail. For one that differs, when the machine kept the baseline's PNG (`build/pixel-baseline/<form-factor>/`, left by `make pixel-baselines`, in CI in a cache), `build/pixel/<form-factor>/diff/<name>.png` shows three panels: the baseline, this run, and the pixels that differ in red. Each run writes its hashes to `build/pixel/<form-factor>/snapshots.json`.
- **What still changes**: `unstable.txt`, a rule a line: `name skip` (not compared), `skip-text`, `skip-pixel`, or `name mask regexp` (what matches, or its first group if it has one, becomes `#` before comparing); a name may have `*`. The weather, the calendar's month and day (they follow the real date) and the native module comparison (it shows times) are not compared at all; the standby screen's weather line (charging, Spanish, and the standby screen behind the USB trust and quick card dialogs, which only the pixel renderer draws), the Spanish date, the parent's pairing code, the wallet's order number (numbered by the time of the order, and beside the confirmation on the wide screen: the trusted confirmation and the two fingerprint payments), the tutorial sample's push token (base64url, with `-` and `_`, cut short by the text renderer), and on About the computer's kernel version and the time the Shell has run have only the changing part masked; behind the SIM PIN dialog (`47-sim-pin`, pixels only) the subtitle of the phone's recent dialled calls is masked whole: the contacts case hangs up as soon as its call connects, telephonyd logs the duration in whole seconds, so it is 0 (no duration shown) or 1 s as the second turned (a busy machine failed it twice in a row); the video and the song are taken while they play, so their bars are masked and their pixels not compared, and the simulated camera is a live picture (in the video call's corner and the camera's viewfinder), its pixels not compared; the photo taken is one fixed picture and is compared. `TestUnstableNamesSnapshots` checks that each rule names a snapshot of the script.
- **Updating the baselines**: after a change to the UI, `make selftest-baselines` and `make pixel-baselines` (`UPDATE=1`), and a look at the `git diff` before committing; the baselines are always recorded by the whole script in one Shell, serially (the same as with the parts at once, §2); a whole run also deletes the baselines of snapshots no longer in the script.

**Rules for writing cases** (each learned the hard way):

- A case leaves the phone as it found it: delete the pictures, contacts, settings, pairings, networks joined, apps installed, notifications ("全部清除" in the notification center), files put into an app's directory (`app-file-drop`) and apps' standby lines (`widget <app> off`) it added; later cases count things, and in the serial run other parts' snapshots show them (§2: their snapshots then differ between the parts at once and the whole script serially). What the phone cannot take away, only an ended process loses (Hongyan's chats), the part that needs it sets up at its start (afresh). Not only what shows: "企业 Wi-Fi" (enterprise Wi-Fi) ended connected to `Kario-Corp`, and on the emulator iwd's other radio then joined that known network every 5 seconds, got no address and dropped it, the Wi-Fi page's list rebuilt each time, the always-on VPN after it reconnecting each time; one VPN case went from 28 to 87 seconds (2026-11-25). It now ends with `wifi-forget Kario-Corp`. That radio could also join before the case's own connect: the test network has one static address, so wlan0, coming second, failed on the address conflict, the Shell deleted the file and both radios dropped (main's r82 and r83, on a busy machine); so the test network's iwd file turns autoconnect off (`AutoConnect=false`, for this test access point only).
- Put a new case under the `#part` it belongs to; never rely on state another part left (in parallel it is not there: `go test ./shell`, the developer machine's `make selftest`, `make pixel-selftest` and `make cts` and QEMU's boot selftest all run the parts in parallel). Simulated state counts too: the two fingerprint payment cases of the `keys` part scanned the shop's code a `chat` case had held up to QEMU's camera (vivid), and failed once the parts ran apart (2026-11-25); now they hold it up themselves. On the developer machine the synthetic camera has that code on its table from the start, which is why it was not seen before.
- Several selftests run at once on one machine (the form factors, the parts): a server the script starts takes a free port, not a fixed one (`fetch-server 127.0.0.1:0`, its address typed by `fill {fetch}`; the fixed 47123 could not be bound by the second of two runs at once, `TestFetchServerOfTwoSelftestsAtOnce`).
- A part that is too long is split where its cases do not lean on each other (2026-11-25: `chat` gave `radio`, Wi-Fi, Bluetooth pairing, airplane mode, mobile data, the hotspot, moving from an old phone and the Bluetooth search, with the case that receives a contact card from the paired headset; `apps` gave `carddav`, the three CardDAV cases, the second of which expects the account number `a2` after the first's; `power` gave `calendar`, which does its own `clock-reset` and puts its own holidays in): before splitting, find what each case reads that an earlier one left (contacts, messages, pictures, settings, installed apps, notifications, the battery level, the code in front of the camera, known networks, pairings), and after it each part must pass alone.
- A case opens the app and the screen it works in, from the standby screen: after a failed case the phone starts over (`--keep-going`), and an app reopens where it was only if its process lived (Hongyan in the thread or, started afresh, in its list; Feiqian on its bills or at its home): `wait-re` for either, then `key-if <key> <text> 0` goes on from the one it came to without waiting; the same for a permission a new process asks for again (Hongyan's microphone: `wait-re 录音中|请求使用`, `key-if enter 请求使用 0`). A case that goes on where the one before it stopped, and cannot set that up in a few lines (the message the case before sent, its call, its counts), says `require-previous`.
- Wait for the thing you act on, not for any text: `wait X` passes as soon as X is anywhere on screen (a toast or the status bar count). To move to a row of a list, wait for that row's own text (its subtitle), or use `wait-re`; text found nowhere else on the page (an explanation) only: the VPN page's explanation says "全部流量" itself, so the wait is for the row's "· 全部流量". The command palette lists the rows on the page the moment it opens: a toast comes before the row (the app shows "已导入" first, then fetches the new list), and a palette opened on the toast alone finds no match for the name, and the next keys land in it.
- After a key that changes the screen, `at screen` or `wait` before the next key; never press keys back to back across a screen change.
- Lists may wrap: go to the first or last item with `key first`, `key last`, not `key up 5`.
- Do not hide a race behind a longer wait: when something does not appear, first look for two requests whose answers come in either order, or an old state replacing a new one (examples in §6).
- A compared snapshot must come out the same every run: a toast stays 2.5 seconds, so `gone` it before the snapshot; something that moves by itself (the snake) is snapped paused before its first move, and right after it goes on; numbers that timing decides (screen time sorts the apps by milliseconds) start from a known state (`screen-use clear`); a notification's banner stays 4 seconds and comes when the app posting it wakes: before the snapshot `notified` waits until the notification is in the notification centre, then `gone` until the banner has passed (the calendar's notification about the import after moving from an old phone); a case whose own banner is still up when it ends waits it out with `gone` too, or it lands in the next case's snapshot when that comes quickly (the calendar's system import in the .ics import case: in whole runs it sometimes topped the snapshot of the CalDAV case right after, never when that case ran alone); waiting for an answer means waiting for this one, not an equal one earlier in the conversation (Hongyan's bot answers the shared photo; the case used to find its answer to the photo before, and this answer sometimes came after the case had left, as a banner and a notification in the later standby snapshots); notifications a case leaves are cleared, above all those holding the day's date (the name of the calendar file the move imported), or they end up in later cases' snapshots; a page whose data has not come in says "Loading…", not "none", and the case waits for that to go before the snapshot (the app store's install dialog opens over the store's lists, and before they came in the store used to say "No apps installed yet" and "The catalogue is empty", so the snapshot's edges showed that or the lists, depending on timing; it was masked and its pixels not compared, now it is fixed). Do not cover a real bug like that with `unstable.txt`.

## 4. What runs for what change

CI's rules are the `RULES` table in `scripts/ci-plan.py` ([38](38-contributing.md) §3): docs only run the checks; a Go package runs it and every package that depends on it; changes that go into `make build` add the selftest, CTS and pixel selftest; telephonyd's ModemManager backend adds `mm-selftest`; `yocto/` runs the recipe checks and two script tests that do not boot; unknown files run everything. The only gate is `pr-ok`. After publishing to main everything runs once by hand (`gh workflow run ci.yml --ref main`); each workflow keeps only its last 3 runs (`scripts/ci-prune.sh`).

What CI does not run (too slow or needs privileges): everything in QEMU, long `make fuzz` runs, soaks; these run on the developer machine as in §5.

## 5. Before publishing

In this order, on the developer machine:

1. The check scripts and `go vet` (seconds each).
2. `make test` (about 6 minutes; `make build` and `make paint` first, §6).
3. `make cts` (about 3 minutes).
4. `make pixel-selftest` (about 3 minutes).
5. QEMU: `make yocto-selftest` of the device image and of the product image (about 6.5 minutes each with nine emulators on the build machine; the two at once share its processors, not measured since the run went parallel).
6. If telephonyd changed: `make mm-selftest`. If system updates changed: `make yocto-ota-test` (product image; about 22 minutes with the device image) and `make yocto-ota-delta` (about 75 minutes, its base saved by `make yocto-ota-base` on the previous release). If the initramfs (`slot-init`, `slot-abl`) or the 6T's boot image changed: `make yocto-userdata-test` (four boots, about 3.5 minutes) and `make yocto-ota-test`.
7. Publish (`make publish`) only when all of it passes; write the results into [13](13-prototype.md) §5 and the internal verification baseline.

**One shared lock**: on the developer machine the selftest, CTS, `go test ./shell` and the pixel selftest all take `/tmp/kario-selftest.lock` (`flock /tmp/kario-selftest.lock make cts`). The parts and form factors of one run at once are fine: each phone-shell has its own temporary state directories and services, the script's servers take free ports, and so does moving from an old phone on the simulated radios (only the interactive `make run` uses the fixed 47800); runs of several people or trees overlapping slow each other's timed waits down and fail now and then, so one runs at a time, and the parts run at once so that each holds the lock for less. Give `go test ./shell` `-timeout 30m`: when the default 10 minutes run out the test is killed (what it started ends with it, §6).

## 6. Rules

- **A regression test fails first**: when fixing a bug, first write a test that reproduces it, run it once on the old code and see it fail (failing the way the bug did), then fix, then see it pass.
- **A case passes on its own too**: what a step needs (an app's data directory, a record) it makes or waits for itself, not relying on what earlier cases left: with `--only` running one case, only the boot comes before it. Example: in 「沙箱里的 DNS」 (DNS in the sandbox), `sandbox-read` works out Hongyan's sandbox and gives Hongyan's data directory to its uid; on the whole phone the run of only "kernel features + sandbox" had never started Hongyan, the directory did not exist yet, and the chown failed (2026-11-24); the step now makes the directory as the app's first start does (`TestSandboxReadBeforeTheAppStarted`). A case that really goes on from the one before says `require-previous` (§2).
- **Never test with a program older than its sources**: the Go tests that run a program built in the tree find it through `tools/prebuilt`. phone-paint (`make paint`): `TestTouchStepsOnPhonePaint` of `shell`; the `build/usr` that `make build` stages: `TestNestedSandbox` of `apps/miniapp` and the manual `TestMeasureHost`; both: `TestPreviewImages`, `TestRunProfile` and `TestRunNativeApp` of `cmd/kario`. When the program is missing or older than its sources the test is skipped, saying which file is newer and what to run: phone-paint older than the newest of `paint/src/*.rs` and `paint/locale/`, `build/usr/bin/kario-system` (which `scripts/stage.sh` installs anew every time) older than the newest of the module's Go files outside the tests, `go.mod`, `go.sum` and `stage.sh`. `make test` runs `make paint` and `make build` first (about 10 seconds when they are built already) and sets `KARIO_PREBUILT_REQUIRED=1`: there those tests fail on a missing or stale program instead of skipping. Why: `make test` did not build the renderer, and in a verification copy `TestTouchStepsOnPhonePaint` ran a phone-paint an older tree had left, failing with "the renderer takes no touch". What is compared is modification times, as make and cargo do: a source whose content changed but whose time is older (copied in with its old time) goes unnoticed. `Cargo.toml` and `Cargo.lock` do not count as phone-paint's sources: cargo does not relink when only they are newer, so counting them would leave the program looking stale even after `make paint`. kario-jsrt (`build/jsrt`), telephonyd and the C SDK's sample app are built first by `make test`'s prerequisites with ninja, which rebuilds by the exact dependencies; under a plain `go test ./shell` the end-to-end tests build kario-jsrt and the sample app themselves (the "fresh worktree" rule below), and nothing checks telephonyd or the other packages' programs against their sources (**not implemented**).
- **What a test starts ends with the test**: the end-to-end tests (`e2eStackWith` in `shell/e2e_test.go`) start private system services themselves (not through the Shell, nor phone-shell), and the scenario's parts and the tests that start a Shell each run in a child process of the test binary (`runChild`, `alone`). The services used to be ended only in the test's Cleanup, so they stayed behind, with init as their parent and their working directory in the tree's `shell/`, whenever a child went without running its Cleanups: go test's timeout (a panic on its timer's goroutine), a panic on one of the Shell's goroutines, the child killed (by the parent test's context, by hand, by the caller's timeout), and, once the parent test process was killed, the child writing to its broken output and ending by SIGPIPE. On 2026-11-26 one run on the developer machine left 1525 of them (11–12 services a part, fourteen parts from one run: the parts still running when it was killed; a part that only failed ran its Cleanups and left nothing). Now the services and the child test processes carry a parent-death signal (`Pdeathsig: SIGKILL`) and are started from the thread that never exits (`StartProcess`: Linux sends that signal when the thread that started the child ends, not the process, and `ownThread` and others end threads): however the process that started them ends, the kernel kills them, with no Cleanup needed. Not a process group or a sweep of the run directory: both need someone to kill or sweep in a Cleanup, and the processes stayed behind exactly when no Cleanup ran. The Shell already starts its apps so (apps die with the Shell); on a phone systemd starts the services, and `phone-shell --services spawn` already starts them with that signal; neither changed. A child also writes its run directory to a file its parent names (`KARIO_E2E_RUN_FILE`), and once the child has ended the parent removes its temporary directory and kills whatever still runs from it (`reapChild`): without the Cleanups the hard links of its copy of the programs (about 190 MB) stay in `/tmp`. `TestScenarioPartEnds` starts a part (the boot and one case) and makes it fail, panic on another goroutine (as go test's timeout does), get killed, or have the test process that started it killed, then checks that no process runs a program under its directory, has the directory on its command line or the file's name in its environment; before the change the last three each left 11 services (the last one the child test process as well), the failing one nothing. When the go command itself is killed the test binary runs on to its end and its Cleanups, at the latest to its own `-timeout`, and what it started dies with it.
- **`go test ./shell` runs everything in a fresh worktree too**: the scenario needs kario-jsrt (the TypeScript calculator and calendar, two system apps, and the sample app run on it: without it the apps `scripts/stage.sh` installs have no module and do not start), the C SDK's C++ sample app and the native example's library, which `make jsrt`, `make capi` and `make native-example` build in `build/`. In a fresh worktree where they were not built yet, `go test ./shell` used to fail 11 parts. Now the end-to-end tests run `make jsrt capi native-example` before staging the programs (one at a time in a tree: `flock build/.e2e-make.lock`): the first time in a fresh worktree that adds about 60 seconds (QuickJS's source archive comes from `~/.cache/kario`, else it is downloaded from GitHub), afterwards ninja has nothing to do, about 0.6 seconds, and changed sources in `jsrt/` or `sdk/c/` are rebuilt by their dependencies. Not skipping: the calculator and the calendar are in over two hundred lines of the script, skipping would leave about half of the parts unrun in a fresh worktree, and `go test ./shell` without `-v` only says ok, hiding it. `make test` builds them first and sets `KARIO_PREBUILT_REQUIRED=1`, and then the tests run no make: that path is unchanged. The build needs what `make build` needs (cmake, ninja, GCC 14); without it the scenario fails once at staging, with make's output, instead of a dozen parts failing each. telephonyd (`make telephonyd`) is not among them: when it is not built the `require-tel` cases skip, as before. The scenario and `TestScenarioPartEnds` build and stage the programs once in a test process (`stagedPrefix`). The whole package (developer machine, the evening of 2026-11-26, load 4–12): in a fresh worktree 173 seconds, all passing (before the change 121 seconds with 11 parts failing); with everything built 124 seconds (before the change 130).
- **The renderer's tests with the debug checks on**: `make test` and CI run phone-paint's tests with `cargo test --profile checked`: `checked` is release with `debug-assertions` and `overflow-checks` on (for the dependencies too, `paint/Cargo.toml`), which the shipped renderer and the release build every selftest uses never check. It takes about as long as `--release` (developer machine, 2026-11-26: the 138 tests 14.8 seconds against 17.0, a cold build about 45 seconds each). tiny-skia's own debug assertions are on there too, so `a_rect_between_two_columns_paints_both` does not compare with tiny-skia's plain fill there (that is the very rect it asserts on), only checks that our way of painting it does not trip it. The pixel selftest drew the 9-key form factor once with a `checked` phone-paint (all 244 cases passed, the 137 pixel snapshots the same as the baselines, no renderer panic); it is not wired into `make pixel-selftest`: the watchdog restarts a renderer that crashes, so seeing one would need its standard error collected as well.
- **Every capability covered**: a new capability needs a case that calls it; `make cts` saying "never called" fails it (example: the account's "Use mobile data" switch passed only once a case pressed it). A case that may be skipped on a phone names what it calls with `covers <capability>...` (first in the case, before its requirements): a capability nothing else called is then counted skipped with that case and its reason (the report's `skipped`, `PHONE-CTS-SKIPPED:`), not never called, the way the case itself does not fail the run. On the 6T, location.watch, location.stop, settings.apps, settings.app.set and widget.set were called only by cases that need a location receiver the script can move.
- **Untrusted input is fuzzed**: the network, files, Bluetooth, NFC, SMS, update bundles, messages from apps. What fuzzing finds stays as a minimal input in a regression case (`testdata/fuzz/`).
- **An intermittent failure is a real bug until shown otherwise**: first rerun once on its own to tell intermittent from always, then find the root cause. Examples:
  - Bluetooth turned on in Settings and the search pressed at once: the Shell handed both changes to BlueZ concurrently, and an old state that came back late wiped the devices found. The fix made the changes run in order and Settings drop out-of-date refreshes, instead of waiting longer.
  - The command palette's "Go to" lists only the rows on the page when it opens, and on real iwd the network's row arrives late. The case now waits for that row before pressing `/`.
  - "Ask a parent for time" failed only after 22:38 in the evening: the calendar reminder case before it set the phone's clock 1 hour 22 minutes ahead (`timeshift 4900`) and nothing set it back (`timeshift` adds up, only `clock-reset` returns it to zero), so near midnight the phone was already in tomorrow and the parent's server, going by its own time, refused the request. A case that agrees the time with a server starts with `clock-reset` (as the calendar's month view does). With the clock set back, "Factory reset" failed next: binding a Kario account signed in by an earlier case had failed, the time of the next try was reckoned on the clock set ahead and stayed after that account signed out, so with the clock 1 hour 22 minutes back the account signed in next waited that much longer to be bound. The fix is that signing out forgets the retry (`shell/antitheft.go`), so the next account is bound at once.
  - Cards opened 0.44 seconds after switching back to Simplified Chinese still named the cards in Spanish (about once in a hundred whole runs): the Shell handed nfcd the new language's policy only with its housekeeping (every 0.5 seconds with the screen on), and Cards does not ask again while open. The fix is that `nfc.state` first waits for nfcd to have the policy as it is now (`nfcFresh` in `shell/nfc.go`), not a longer wait in the case.
- **Intermittent failures on a busy machine**: QEMU emulates in software (TCG), and many emulators at once are slower than one (the boot selftest's eight: its longest part 446 to 519 seconds by the load, 435 serially, 2026-11-25); judge an intermittent failure by rerunning when the machine is quiet, or with fewer emulators (`SELFTEST_VMS=`). In the four runs in eleven parts the video case ("视频：…") failed once (playback stayed at 0:00; load about 11) and passed the other three times; why is **not investigated** (2026-11-25). The "Error parsing Opus packet header." of phone-mediad's ffmpeg in that log does not point to the cause: ffmpeg 8.0 printed it whenever it reached the end of a WebM file, after good playback too; the layer now carries the upstream fix ([20](20-audio.md) §9.1). CI's machines have few cores and the Shell package's ten parallel parts starve the timed tests of other packages, so `make test` and CI run the Shell package last and on its own. Of a timeout, find which step ran out: `TestHostileApps/noread` failed once in ten on a busy developer machine, in 5.04 seconds; the step it checks (the Shell ending an app that does not read) takes 10–40 ms from the queue filling to the app reaped (at load 70 too), and its 5-second wait running out would make the subtest at least 5.33 seconds, so what ran out was the 5 seconds for the fake app to say hello. The fake app is a new process of the test binary itself (about 50 MB), whose start on a busy machine can take seconds (inferred, not reproduced); the bound on the start is now 30 seconds (`fakeAppHello` in `shell/hostile_test.go`), and an app that never starts still fails. `TestInstallProxy` (no more of a download once the proxy stops) failed once at a load of about 50: the 1 MiB bundle was all in the loopback's socket buffers before the stop, and with `go test -cpu 1` it failed 299 runs in 300 (on the code before the change too); now the test's server holds back what follows the first eighth of a whole download until the request has been up 10 seconds, a stopped proxy ends the request before that, and one that does not stop still fails (2026-11-26). `TestDevLink` failed once in `make test` (「已停止与电脑共享」): the test set a trusted computer directly with the simulated cable unplugged, and the Shell's first routine USB check, about half a second after it starts, saw the cable gone and ended the sharing; only a slow run has that check come after the trust. Now the test plugs the simulated cable in with the trust (`TestDevLinkDebug`, `TestDevLinkAttach` and `TestUSBFirewallFollowsDeveloperMode` too; `devOpen` and `TestUSBFirewallDrains` already did); with a check inserted after the trust it failed the same way before the change and passes after it (2026-11-26).
- **Results go into the docs**: status lines name the environment and the date (developer machine, QEMU, real phone), what has not run says **not verified**, simulated things say "simulated"; figures from assessments say "estimate".
