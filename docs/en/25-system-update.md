# System updates (OTA): A/B system slots and dm-verity

> Status: **prototype ✓** (QEMU): A/B slots, RAUC, update bundle signing, dm-verity on the system slots with a signed root hash, 「系统更新」 (System update) in Settings, delta (adaptive) updates, staged rollout and pausing, the health check (the Shell, the renderer and an app all come up), and automatic rollback on boot failure and on verification failure; `make yocto-ota-test` verifies all of this on QEMU (the verification baseline of 57 (internal document)). Per-version incremental packages (the way Android's A/B updates work: block operations plus binary diffs, §5): unit tests ✓ on the host, and generating and applying them on the slot images of two real version pairs, checked byte for byte ✓; installed through Settings on the emulator ✓ (`make yocto-ota-delta`, §5.5), not run on a real device. The boot method on real devices, secure boot for the boot chain and baseband firmware updates come with R16.

## 0. Summary

- **Two sets of system partitions (A/B slots)**: an update is written into the slot that is not running; the phone keeps working normally while it is being written, and a power loss only voids this one update; once installation finishes, a reboot goes into the new slot.
- **RAUC** writes the slots: the update bundle is a RAUC bundle in verity format, signed with our update key (development keys are generated by `yocto/ota-keys.sh` and kept out of the repository; in production the signing happens in an HSM), and the image trusts only the CA in its own keyring; the bundle states which device models it applies to, and other models refuse to install it. When installing from a URL it writes while downloading (streaming), without storing the whole bundle first; for this, the update server (and any CDN in between) must support HTTP Range requests. If it does not, RAUC fails with an error instead of falling back to downloading the whole bundle.
- **System slots are read-only and verified block by block (dm-verity)**: a slot holds ext4 plus its hash tree; the slot's "descriptor" (block count, hash tree location, salt, root hash) is signed with the update key and kept in the state partition. At boot the initramfs first verifies the descriptor's signature with its built-in CA certificate, then mounts the system read-only through dm-verity; from then on every block that is read is checked against the root hash, and a block with even one modified byte reads as an I/O error. Neither modifying the system partition offline nor substituting a self-computed root hash gets through.
- **Delta updates**: the update bundle carries a hash for every 4 KiB block of the slot image (RAUC's `block-hash-index` adaptive mode); during a streaming installation, blocks already present in either slot are copied straight from the local disk and only the remaining blocks are downloaded. There is no need to build a separate diff bundle for each pair of old and new versions: one bundle is a delta update for every old version. But Go programs, relinked every time, change almost entirely, so a round of development downloads about half the bundle; a release therefore also makes an **incremental package** for each of the last few versions (§5): block operations (copy from the phone's slot, binary diff, write new data, write zeros) that rebuild the slot on the phone, where the hash tree is recomputed and the slot may boot only if the root hash matches the signed descriptor; `latest.json` lists them by the version they start from, and the phone takes the one for its own version, otherwise the full bundle (adaptive). On the host, the incremental payload for the round from `c6b9001` to `be494c0` (where the adaptive install actually downloaded 65.3 MB on the emulator) is 6.7 MB.
- **No downgrade**: release images write `min-bundle-version=<own version>` into RAUC's `system.conf`, and update bundles older than that (the version is in the signed manifest) are always refused, whatever the update server offers; 「设置 › 系统更新」 (Settings › System update) likewise only offers versions newer than the current one (`已是最新版本` (Already up to date)). So to withdraw a bad version, you have to publish again with a higher version number. Development builds have no version number and skip this check.
- **Signature on `latest.json`** (when the product layer provides a public key, `PHONE_UPDATE_KEY`, [11](11-platform-architecture.md) §15): the update server signs it fresh each time with an online key, and the response headers carry `X-Offer-Issued` (the issue time) and `X-Offer-Signature` (Ed25519, over `kario-offer/1`, the issue time and the exact bytes of `latest.json`). The device rejects responses that are unsigned, have a wrong signature, were issued more than 7 days ago, or are older than the last one it accepted. This way, someone impersonating or intercepting the update server can neither change the rollout percentage nor use an old `latest.json` to keep a phone on an old version forever. The signing is done by the update server (closed source, D11; the formats of the signature and of install reports are in the `ota` package, shared by phone and server); the staged rollout tool edits the file as usual and does not have to deal with signing.
- **System data comes from the update server too**: the holiday calendar `holidays.json` (each region's public holidays and the weekend days that are make-up workdays, `ota.Holidays`; door cards chosen by the time of use need it, [30](30-nfc.md) §4) sits next to `latest.json` and is signed the same way, except that the signature is over `kario-data/1`, the file's name, the issue time and the exact bytes (`ota.DataMessage`), so a signature cannot be moved to another file. With an update server the phone fetches it once a day (an hour later after a failure) and likewise refuses it unsigned, wrongly signed, signed more than 7 days ago or older than the one it has; it is kept in `<state dir>/shell/holidays.json`. The update server serves the file only when it reads as a calendar. The platform ships no calendar: the dates are the government's (in China the yearly notice of the General Office of the State Council) and must be checked before they go onto the update server; real calendar data is **not implemented**, and the selftest uses a test calendar ([30](30-nfc.md) §7).
- **Staged rollout**: `rollout` in `latest.json` is the percentage (%) of devices this version has been rolled out to, and `paused` pauses the rollout. On its first check each device draws a random bucket from 0–9999 and stores it in the data partition shared by both systems; the bucket decides whether its turn has come. The server does not know which device is in which batch. When it is not yet the device's turn, Settings states the reason and does not offer installation.
- **Telling the server how the installation went**: after the phone installs an update, it records which slot and which version it installed; once the new slot is marked good, or the phone has gone back to the old slot, the Shell sends `POST /report` to the update server (version, `good` or `rollback`, bucket); if it is not delivered, it is sent again at the next boot. The update server's staged rollout tool runs periodically: it raises `rollout` step by step over time (by default 1% → 10% → 50% → 100%, one day per step), and sets a version to `paused` if it has enough reports (20 by default) and the share of rollbacks exceeds a threshold (5% by default), or if there are enough day reports and the share of phones with app crashes exceeds a threshold (10% by default); once paused, the rollout has to be released by hand.
- **Reporting again one day later**: one full day after the new slot is marked good, the Shell sends another install report (`kind: "day"`) with the number of app crashes during that day (the number of crash log entries recorded since the new slot was marked good); if the phone was switched off in between, the report is sent at the next boot. A version that installs fine but keeps crashing when it runs is stopped this way too.
- **Signing install reports**: the key service performs a device attestation for each install report (`attest`, with the app name recorded as `system.ota-report` and the nonce being the SHA-256 of the version, result, bucket, kind and crash count (`kario-report/2`); app IDs starting with `system.` cannot be installed, so no other app can impersonate it), and the attestation is sent along with the report. When the update server is configured with the certification body's root (`--device-root`), it accepts only reports signed under that root and answers 403 to everything else: forged "successes" cannot dilute the rollback rate. For the same phone and the same version, only the first install verdict and the first day report count (the server stores a hash of version, kind and device ID; device IDs never appear in `reports.jsonl`); unlocked phones (whose attested boot state is `unlocked` and which may be running a self-built system) are still accepted, but marked `unlocked` and not counted for the staged rollout. Without `--device-root` the server accepts unsigned reports as before. On phones without a provisioned device certificate, the attestation root is one the phone generated itself at first boot, a different one on every phone, so the server cannot check them uniformly: this can only be turned on on the real server after factory provisioning ([22](22-developer-api.md) §11). The open-source side has `ota.VerifyReport` and the command-line tool `phone-ota-verify`, so anyone can verify reports.
- **The new slot has to "prove its health"**: after the new slot boots, it is marked good only when the system services are running, the Shell has come up with the renderer, and an app (Settings) can launch and speak the protocol; until it is marked good, every boot uses up one chance, and once all three are used up the phone goes back to the last good slot. If the new slot already fails verification at boot (wrong descriptor signature, data not matching the root hash), this boot goes straight back to the good slot and the new slot gets no more chances.
- The whole selection is done by a very small initramfs (busybox, veritysetup, openssl and one script, about 16 MB unpacked) after the kernel starts and before the system starts, without depending on any particular bootloader; it also mounts the state partition and the data partition. Disks without A/B partitions (the single root filesystem image used for development) go through the same initramfs, which boots read-write from the `root=` on the kernel command line, without dm-verity.
- In 「设置 › 系统更新」 the user sees the current version and the running slot, and can check for updates, install and reboot; bundles with an untrusted signature or not meant for this device are refused, with the reason stated.

## 1. Partitions

| Partition (GPT name) | Content |
|------|------|
| `state` | The slots' boot state and the signed descriptors of both slots (16 MB); the initramfs mounts it at `/var/lib/slots` |
| `rootfs_a`, `rootfs_b` | Two systems (1 GB each, leaving headroom for larger future versions), identical at the factory; read-only |
| `data` | Writable data of the system and the user, shared by both systems; the initramfs mounts it over all of `/var/lib` (app data is in `/var/lib/phone`); if it cannot be mounted, `/var/lib` is read-only and the log says so |

`/var/lib/slots/boot` is four lines of text: `slot` (the slot to boot next), `good` (the slot last marked good), `tries` (how many boot chances the new slot has left), `booted` (the running slot). It is only parsed by format and never executed: a slot can only be a or b, a count can only be digits, and a corrupted file is treated as "boot A". `rootfs_<slot>.verity` and `.verity.sig` are the slot's descriptor and its signature (CMS).

The mounting is done in the initramfs rather than in systemd mount units: a mount unit first waits for its device to appear, and on disks without these two partitions it would wait 90 seconds for nothing. The system's fstab has no line for `/`, so systemd does not try to remount the read-only root read-write. `/dev/console`, `/dev/kmsg` and the mount points in the initramfs are created in advance from the image's device table (`phone-initramfs-devices.txt`), because the kernel has to open the console before it runs `/init`.

## 2. The course of one update

1. 「检查更新」 (Check for updates) in Settings: the Shell reads `latest.json` from the update server (version, release notes, size, bundle URL; optionally `rollout` and `paused`), and verifies the signature first when a public key is configured. When the rollout is paused, the bucket is outside `rollout`, or the version is not newer than the current one, the version is not offered, and Settings shows the reason (`held` in `system.update`).
2. 「安装」 (Install): the Shell runs `rauc install <URL>`. RAUC first verifies the signature and the device model, then marks the other slot as not bootable and writes the slot image (ext4 plus hash tree, written as is; going by block hash, blocks already present in either slot are copied locally and the rest are downloaded through HTTP Range requests); a hook in the bundle puts the slot's signed descriptor into the state partition; finally the slot is set as the next boot (`slot` changes to the new slot, `tries=3`). When `latest.json` has an incremental package starting from the phone's version, the URL is that package's: the slot is written by the install hook in the package instead (§5.3), and every other step is the same; if it fails to install, the full bundle is installed next.
3. Reboot: the initramfs sees `slot ≠ good` with chances left and uses one up (`tries=2`); it verifies the descriptor's signature, opens the slot with veritysetup, mounts it read-only and boots from the new slot. If any step fails, this boot starts from the `good` slot instead, which also stays the slot for the next boot.
4. Once the system is up, `phone-ota-good` runs the health check (`ota-healthy`): telephonyd is running; when the display service is running (always on the phone; on the emulator it needs `phone.gui=1`), it also waits for the Shell to write `/run/phone/healthy` (at most 120 seconds). After the renderer handshake succeeds, the Shell launches the Settings app in the background, writes this file once the app speaks the protocol (Shell version, renderer, app, startup time), and then ends the app. If the check passes, `rauc status mark-good` runs: `good` changes to the new slot, `tries=0`. When the renderer cannot come up, the Shell keeps exiting and restarting, and the file never appears.
5. If the new slot is never marked good (it fails to boot, keeps crashing, or fails the health check), the initramfs goes back to the `good` slot after the three chances are used up.

At build time, `phone-verity.bbclass` adds an image type `ext4.verity`: ext4 with 4 KiB blocks (dm-verity verifies in 4 KiB units), followed by the hash tree computed by veritysetup (without a verity superblock; all parameters are in the signed descriptor), with the descriptor signed with the update key as CMS; the factory disk (`phone-ab.wks.in`) writes this image into both slots, and the state partition comes with both slots' descriptors preloaded. RAUC uses a custom boot backend (`rauc-boot`) to read and write the same state: `get-primary`, `set-primary`, `get-state`, `set-state`, `get-current`.

## 3. Verification

- `tools/slots_test.py` (part of `make test`): runs the RAUC backend and the initramfs selection logic in a temporary directory — healthy after an update, never healthy after an update (rollback after three tries), the good slot marked bad, a slot that fails verification rejected on the spot, a corrupted state file.
- `make yocto-ota-test`: the update bundle is served by a small HTTP server with Range support (`yocto/ota-www.py`, which records how many bytes each request sent), and the A/B disk image is booted on QEMU 11 times in a row, doing one step and shutting down each time — on A, first check for updates against two servers, one with the staged rollout at 0% and one with the rollout paused, and Settings offers installation for neither and states the reason; then refuse a bundle signed with an untrusted key; then install the bundle to B through 「设置 › 系统更新」 (Settings › System update); B comes up with the display service (Shell, renderer, Settings app) and is marked good; install from B to A; A boots three times in a row on an emulator without a display device (`novga`), where the renderer cannot come up and the health check fails; the seventh boot goes back to B; install to A again, and after shutdown corrupt A's filesystem on disk, so that at the next boot A fails verification and the phone goes straight back to B; install A once more, and after shutdown replace A's descriptor in the state partition with one that has a different root hash (keeping the old signature), so that at the next boot the signature is wrong and the phone goes straight back to B. The test checks the slot of every boot, the two non-offers, the four refusals, the four installations, that each installation downloaded less than a quarter of the bundle, B's health record, that B reported `good` to the server after it was marked good and that the report was signed (after the first boot the phone prints its attestation root; `ota-www.py` stores the reports exactly as received, and at the end `phone-ota-verify` checks each one against that root, and the test fails if any one is wrong), that the system always runs read-only through dm-verity, and the reason each of the two tamperings was detected. A refusal must be due to the signature (RAUC's error message mentions the signature or the certificate); any other reason, such as a failed download, counts as a failure. When the closed-source product repository runs the same test, it substitutes the official update server and staged rollout tool (`OTA_SERVER`, `OTA_ROLLOUT`): the server verifies and deduplicates on the spot (the two later reports from the same phone for the same version are accepted but not counted again), and the rollout percentage adjusts according to the reports.
- In the test every installation uses the same image, so the slots already contain the vast majority of the blocks, and the download size is the lower bound for adaptive mode: about 4.2 MB each time, 3% of the 130.7 MB update bundle (almost all of it the block hash index itself: one 32-byte hash per 4 KiB).
- **Across versions** (`make yocto-ota-base` saves the A/B disk, the slot image and the file list of one build; after changes and a rebuild, `make yocto-ota-delta` boots from it and installs the new update bundle; it now installs twice, on two copies of the base disk, once with an incremental package made against the base and once adaptively with the full bundle, and compares the downloads, §5.5): from `5da8671` to `88dc389`, with one round of development in between (the protocol gained fields for notification actions, the SDK gained callbacks, and the store, notifications, music and cloud services all changed), the actual download was 55.5 MB, 38% of the 142.4 MB update bundle; the new slot came up healthy and the install report was delivered. Of the 490.6 MB new slot image, 23065 4 KiB blocks were in neither of the phone's slots (90.1 MB; what gets downloaded is the compressed form); 38 files changed, 145.6 MB, almost all of them Go programs: changing packages that every program links (`ui`, `sdk`) means every program has to be relinked, and a change in one place of a Go program shifts all the code after it, so practically the whole program changes (phone-shell 22.8 MB, the mini-program host 16.9 MB, phone-cts-verify 14.3 MB, …). For a patch release that changes only one program, the download is roughly that program's compressed size plus the 4.4 MB index.
- To go smaller there are three routes: build the system programs as one multicall program (like busybox, dispatching by the name it was invoked under), which the system services already do (the next items), but that saves image size, not each round's delta; ship per-file binary diffs (Android's approach; RAUC does not support it itself, so the incremental package's install hook does it now, §5); or download by content-defined chunks (RAUC's casync bundles), **not implemented**.
- **Estimate for a multicall program** (2026-11, compiled only, not run on a device): the 27 Go programs in the product image were turned into libraries as they are, plus one entry point that dispatches by invocation name, and built the same way as the recipes, as arm64 static PIE with symbols stripped:

  | Approach | Uncompressed | gzip -9 (approximates the update bundle) | Pages each process has to relocate at startup |
  |------|------|------|------|
  | Now: 27 programs, each linked separately | 162 MB | 58 MB | Small apps 0.3 MB, Shell 2.0 MB (14.6 MB in total for the 27) |
  | All combined into one (PIE) | 31 MB | 11 MB | 2.5 MB for every process |
  | Only the 8 system services combined (Shell, pushd, keystored, imed, audiod, mediad, sandbox, cts-verify; apps unchanged) | 62 MB → 23 MB | 23 MB → 8 MB | 2.0 MB per service process |
  | Any of these as non-PIE | Same as above | Same as above | 0 |

  Combining only the services is almost free: the Shell already contains most of the other services' code, the image shrinks by 39 MB, and the delta for a round of development drops by about 15 MB (55.5 MB → about 40 MB); the cost is that small services such as pushd and imed each relocate about 1.5 MB more, part of which is offset by shared runtime code pages; this has to be measured on the device. Combining everything into one could bring the delta down to about 10–15 MB, but two things have to be decided first: under PIE, each of the 19 Go processes gets about 2 MB more private pages (about 37 MB more in total), while non-PIE has no such overhead (and can share code pages as well), at the cost that the program's own addresses are no longer randomized (heap, stack and mmap are still randomized, and Go is memory-safe); and the system apps would be merged into the system program too and stop being separate packages (they are updated together with the system anyway; apps installed from the store are not affected).
- **The system services are combined into one program, `kario-system`** (R45, following k3s and busybox): the code of the Shell, pushd, keystored, imed, audiod, mediad, the sandbox launcher and `phone-cts-verify` is each a package under `programs/` (`Main()`), and `cmd/kario-system` dispatches by invocation name; in the image, `bin/phone-shell` and the others are links pointing to it, and so is `lib/phone/bin/phone-sandbox`, so neither the systemd units nor the path used to launch apps changed. The development `cmd/phone-*` programs are still there, three lines each, and can still be built separately. It is still PIE (program addresses randomized); apps are still one program each, since they are packages that are installed and signature-checked individually. Two points need care: when the Shell re-executes itself, it uses the link it was started through (the process name stays `phone-shell` and does not become `kario-system`); the sandbox launcher's package-level `init`, which locks the thread, only runs when it is started under the name `phone-sandbox`, so it does not take effect in the other services.
- **Measured on the device** (2026-11, qemuarm64): the Go programs in the product image went from 27 programs, 156.2 MB, to 20 programs, 116.4 MB (`kario-system` is 23.7 MB; the 8 programs it replaced were 62 MB together), and the update bundle from 139.1 MB to 125.7 MB; each installation downloads 4.1 MB instead of 4.4 MB. Memory was not saved (PSS in the public image's selftest, one full selftest before and one after the merge): the Shell 28.2 → 18.4 MB, imed 11.2 → 14.4, audiod 10.0 → 11.8, pushd 9.0 → 11.0, keystored 4.7 → 8.5; these five together 63.1 → 64.1 MB. The code pages mapped from the program file went down by 14.4 MB because they are shared, and the private pages went up by 15.4 MB, more than the estimated 1.5 MB per service: besides the PIE relocations, every process also runs the initialization of every package linked in (`GODEBUG=inittrace=1`: keystored allocates 0.14 MB during initialization when built on its own and 1.5 MB inside the combined program, mostly the package-level data of libraries such as goja, goldmark and bubbletea). mediad's heap varies with the video being played (14.2–23.4 MB across three selftests), so it is left out.
- **One round across versions, measured after the merge**: from `c6b9001` (after the merge) to `be494c0`, a round that added tombstones, the canvas node, Wi-Fi and Bluetooth (iwd and BlueZ in the image, wireless and Bluetooth in the kernel), USSD, and the store's staged rollout and automatic updates, and changed both `ui` and `sdk`. The download was 65.3 MB, 50% of the 130.7 MB update bundle; the new slot came up healthy and the report was delivered. Of the 457.1 MB new slot image, 30270 blocks were not on the phone (118.2 MB, uncompressed); 112 files changed or were added, 123.4 MB: 19 relinked Go programs, 107.0 MB (`kario-system` 23.8 MB, the mini-program host 16.9 MB, each app), the new snake game 2.5 MB, iwd and BlueZ 3.7 MB, other new libraries 7.3 MB, kernel modules 0.4 MB. So the merge did not make a round's delta smaller: the apps are not in `kario-system`, a change to `ui` or `sdk` relinks every one of them, and each changes almost entirely; the earlier estimate of "about 40 MB a round" was wrong. What would really save is per-file binary diffs, or content-defined chunks (RAUC supports casync: chunk boundaries follow the content, so the chunks after shifted code are still recognized). The former exists now (§5): for the same pair of versions, the incremental payload made on the host is 6.7 MB, about a tenth of what this install actually downloaded (this pair was not installed on the emulator; the pair that was is in §5.5); the latter is **not implemented**.

- Host selftest case 「系统更新」 (System update): on a machine without A/B partitions, Settings explains that online updates are not possible.

## 4. Not done yet

- **Boot chain**: dm-verity protects against modifications to the system partition; the kernel and the initramfs (which contains the CA certificate) themselves have to be verified by the bootloader (secure boot), otherwise replacing them gets around it. On QEMU the kernel is passed in from outside; on real devices this is done together with R16 / R15.
- A bad block found at runtime currently only returns an I/O error; whether to change this to rebooting into the other slot (dm-verity's `restart_on_corruption`) will be decided once real devices have a boot chain.
- Booting on real devices: Qualcomm ABL has its own A/B slot mechanism (boot_a / boot_b), and Unisoc uses U-Boot; each needs a RAUC backend, or the initramfs approach chained after them, **not implemented** (comes with R16).
- Baseband firmware is updated along with the vendor partitions (comes with R16).
- Signals such as battery do not yet take part in pausing, **not implemented**. The update test on the device only covers `good` reports (the boots that rolled back did not start the display service, so the Shell was not there); the report a day later is only in the host test (`TestDayReport`).
- Incremental packages (§5): installed on the emulator, with a rollback, B to A, a power cut and a damaged package falling back to the full bundle (§5.5); an install downloads about 17% more than the package itself, because RAUC's streaming install has no cache and some blocks are read twice (§5.5), **not improved**. Settings shows the size of the incremental package chosen (`size` of `available.delta`, with the full bundle's in brackets; when the server gives no size it says only "Incremental", not the full bundle's size) ✓ (unit test). The applier is now in the system image as well (`/usr/bin/phone-ota-delta`): the hook asks it `can-apply`, uses it when it applies the payload, and a streaming install then does not download the bundle's copy; the release tool leaves the applier out of the packages for earlier releases known to have a suitable one (§5.3, §5.4): a package without the applier installed on the emulator with the image's ✓. The pre-rename 0.6.0 and 0.7.0 have no update path (another machine string, §5.4).

## 5. Per-version incremental packages

> Status: host ✓ (unit tests of every part; generated, applied and checked byte for byte on the slot images of two real version pairs); installed through Settings on the emulator ✓ (`make yocto-ota-delta`: RAUC runs the install hook, and the hook refuses a package made for another version; a rollback when the new slot is not healthy, B to A, a power cut while it writes, and a damaged package falling back to the full bundle, §5.5); not run on a real device.

Adaptive mode looks blocks up one by one, and after a Go program is relinked almost every block of it has changed, so a round of development downloads about half the update bundle (§3). Android's A/B updates (`update_engine` payloads, made by `delta_generator`) make one payload per pair of old and new versions: block operations, where unchanged blocks are copied from the phone's old slot and changed files are sent as binary diffs. This follows that model; the code is in `ota/delta` (payload format, generation, application), `ota/delta/bsdiff`, `ota/delta/xz`, `ota/delta/ext4`, `ota/verity` and the command `phone-ota-delta`, all using only the Go standard library and code of our own, with no new dependencies.

### 5.1 Payload format

A payload is a header (`KDLT`, the format version, the manifest length), a JSON manifest and the operations' data, one piece after another in the order of the operations, so it can be written while it is being downloaded, read once from start to end. The manifest states the source image (version, size in bytes, SHA-256, its verity root hash), the target image (size in bytes, SHA-256) and the target's verity descriptor (block count, hash tree location, salt, root hash). The image is the part of the slot that dm-verity covers (the ext4); the hash tree is not in the payload but recomputed on the phone. Each operation states which blocks it reads and which it writes (extents of 4 KiB blocks, each list taken in order as one stream), and the SHA-256 of its data, of the source data it reads and of the result it writes:

| Operation | What it does |
|------|------|
| `REPLACE` | Writes the data the operation carries: xz-compressed or stored |
| `SOURCE_COPY` | Copies blocks from the source slot, wherever they are (not necessarily in the same position) |
| `SOURCE_BSDIFF` | Makes the new blocks from blocks of the source slot plus a binary diff |
| `ZERO` | Writes zeros |

- Compression is xz (LZMA2): the standard library has neither zstd nor xz, so the decompressor is our own (`ota/delta/xz`, the xz file format plus LZMA2, tested against the xz program's output; decoding a Go program on the host runs at about seven tenths of the xz program's speed); compression calls the xz program on the build host (`-9e`, with a dictionary sized to the data). No Go module is added.
- The binary diff is our own bsdiff (`ota/delta/bsdiff`): Colin Percival's published method (the idea under the BSD licence; the code and the patch format are ours), a suffix array of the old data (the SA-IS algorithm), exact matches stretched in both directions as long as at least half the bytes agree, stored as byte-wise differences (when code has only moved or its addresses changed these are almost all zeros and compress to very little), and what matches nothing stored as is; a patch is three streams, control, diff and extra, each xz-compressed.
- The manifest is checked as a whole before it is used: known operations, every extent inside its image, every target block written by exactly one operation, the data packed in order, every hash present.

### 5.2 Generation

`phone-ota-delta generate --source <old> --target <new slot image> --out rootfs.kdelta [--report report.json]`, run on the build host. The old one can be a slot image (with `<file>.desc` as its descriptor) or the A/B disk of a release (`.wic` or `.wic.gz`: it takes `rootfs_a` and reads the descriptor from the state partition). The ext4 is parsed by our own code (`ota/delta/ext4`: superblock, group descriptors, inodes, extent trees and old-style block maps, directories), which yields the blocks that hold each file's data.

1. Each target block: an all-zero block is written as zeros; a block that exists anywhere in the source slot is copied from there (first trying the block after the one copied last, then the same position, then a lookup by hash); the rest are new.
2. Files with new blocks: binary-diffed against the file at the same path in the source slot (failing that, the only file with the same name; for a newly added program, the program in the same directory closest in size), and the patch is used (one `SOURCE_BSDIFF` for the whole file) if it is smaller than writing just this file's new blocks; otherwise the new blocks are written.
3. The new blocks of small files are compressed together with the file system's metadata (inode tables, directories, bitmaps, …) into `REPLACE` operations of at most 4 MiB each.
4. Before writing the payload out, the generator applies it in memory to the source image: the result must be exactly the target image, and the hash tree must come to the signed root hash. The report compares the payload with the whole image and with an estimate of the adaptive install (the block hash index plus the 128 KiB in-bundle blocks that contain a block not in the source slot, gzip-compressed as mksquashfs does), and shows how each changed file is sent and at what size.

### 5.3 Installation

An incremental package is a RAUC bundle (verity format), signed with the same update key as the full bundle and stating the same device model and version (so `min-bundle-version` still refuses downgrades). The slot's image is the payload `rootfs.kdelta`, marked `hooks=install`: once RAUC has verified the signature and marked the other slot as not bootable, it does not write the slot itself but runs the bundle's hook `delta-hook`; the bundle also carries the target's signed descriptor and `phone-ota-delta` built for the machine. Why an install hook rather than having the Shell apply the payload: signature, device model, no downgrade, slot marking and streaming download are all RAUC's existing steps, and if the hook fails RAUC does not set the slot as the next boot; the Shell just installs another URL. There are two appliers: one in the system image (`/usr/bin/phone-ota-delta`, a program of its own that links only the update code and so seldom changes within a version), and one in the bundle (from the same build as the payload, so its format always matches, for old systems whose image has no applier yet or one that does not read this format). The hook asks the system's applier, `phone-ota-delta can-apply <payload>`: it reads the format number in the payload's header itself (the 4 bytes after `KDLT`), and when it applies that format it prints the number and exits 0, so the hook uses the system's, and a streaming install never reads, nor downloads, the bundle's copy (about 1.2 MB compressed); when it does not (exit 3, or an older applier without the command) the hook uses the bundle's; with none in the bundle either it fails, RAUC does not mark the slot and the Shell installs the full bundle next. The system's applier is under dm-verity, as trustworthy as the bundle's copy. The hook does not read the format itself: the phone's busybox is built without `CONFIG_DESKTOP`, so its `od` knows no `-A -t -j -N`; the earlier hook read it with `od`, got an empty format on the emulator, never used the system's applier, and every package without the applier failed to install (falling back to the full bundle each time, §5.5); the host test used GNU `od` and did not notice. The hook's test now gives it only commands busybox has too (`sed`, `mv`, `sync`, `tee`, `tail`, `rm`, `cp`, `grep`). The applier's output is also kept in `/run/phone-ota-delta.log`: which applier ran, how long it took and its memory peak, or where it stopped.

The hook reads the running slot from the state partition, first deletes the old descriptor of the slot about to be written (a half-written slot has no descriptor it could be opened with), and runs the applier:

1. Everything is checked before writing: the manifest is valid; the verity descriptor in the manifest is identical to the signed descriptor in the bundle; the source image is the running slot (the root hash in the manifest is compared with this slot's descriptor in the state partition; without a root hash, the whole slot is read and its SHA-256 computed). If not, it reports "the payload is for another system version" and writes nothing.
2. Operation by operation: read its data and check the SHA-256; read the source blocks through the running slot's dm-verity device (`/dev/mapper/root_a`), so the kernel has verified every block, and check the source data's SHA-256; compute the result, check its SHA-256, and write it into the other slot.
3. Once everything is written: sync, drop the page cache, and read the whole image back from the device: its SHA-256 must be the target image's, and the root hash of the recomputed hash tree must be the one in the signed descriptor; then the hash tree is written after the image.

If any step fails, the applier exits with a failure, the hook fails, RAUC does not mark the slot, the slot has no descriptor either, and the initramfs will not use it. Only when all is right does the hook put the signed descriptor into the state partition (as the full bundle's `verity-hook` does), and RAUC then sets the slot as the next boot; at the next boot the initramfs verifies the descriptor's signature and opens the slot through dm-verity as usual. The payload is read only once from start to end: in a streaming install RAUC downloads through HTTP Range only the parts of the bundle that are read, that is, the payload (and the applier, when the bundle's is used). The download is about 17% larger than the bundle itself: RAUC's streaming install (NBD → dm-verity → squashfs) has no download cache, so blocks read twice are downloaded twice (measured in §5.5).

### 5.4 Release and selection

`latest.json` (signed as a whole, as before) gains an entry `deltas`, each item an incremental package and the version it starts from:

```json
{"version": "0.8.0", "size": 130652032, "url": "phone-bundle-0.8.0.raucb", "rollout": 10,
 "deltas": [{"from": "0.7.0", "from_root_hash": "c02eb5fb3706f7eb78f84a8da06a82fbaf6d6b4eb8bac681ea546fd2a0f93579", "size": 7900000, "url": "phone-delta-0.7.0-0.8.0.raucb"}]}
```

The phone (`shell/update.go`) picks an incremental package when it offers this version: one with `from_root_hash` is used only when the running slot's root hash (from its descriptor in the state partition) is exactly that (it is that very image); one without it, by release version (`from` equals the phone's version). The one picked goes into `available.delta` of `system.update`; installing tries it first and, if it fails to install, installs the full bundle next. Without a suitable incremental package the full bundle is installed (adaptive).

The release tool (kario-internal's `tools/release.py`) makes an incremental package for each of the `--deltas` (default 3) newest releases in `dist/` that kept their A/B disk: through `make yocto-bundle OTA_DELTA_FROM="<version>=<disk>…"` it goes into the build container, where `yocto/qemu-ota-delta.sh bundle` generates the payload for each version and the `phone-bundle-delta` recipe bundles and signs it; the result goes into `dist/v<version>/phone-delta-<old>-<new>.raucb` and into `latest.json`. The update server `kario-otasrv` needs no change for incremental packages (it serves every `*.raucb`).

Each release's `MANIFEST.json` records which payload formats its image's applier reads (`ota_delta_formats`: the release tool builds `phone-ota-delta` and asks `formats` when kario is at exactly the commit the image was built from, without local changes; when it cannot ask, nothing is recorded). For an earlier release with formats on record, `OTA_DELTA_FROM` names it `<version>@<format,…>=<disk>`; after generating the payload `qemu-ota-delta.sh bundle` reads its format number and, when it is among them, leaves the applier out of the bundle (the `phone-bundle-delta` recipe adds the applier only when `PHONE_DELTA_DIR` has one), and records whose applier will apply it (`<label>.raucb.applier`: `system` or `bundle`); the others carry it as before, and `--bundle-applier` puts it into every package. A release without that record (0.7.1, whose image has no applier either) still gets packages carrying it; 0.6.0 and 0.7.0 have another machine string and get no packages (below).

**The machine string (RAUC's `compatible`) must not change after a release.** RAUC installs only bundles whose `compatible` is exactly the one in the system's `system.conf`, full bundles and incremental ones alike. The rename (J1J → Kario) changed it from `j1j-qemuarm64` to `kario-qemuarm64`, so phones on 0.6.0 or 0.7.0 cannot install any later release: on the emulator, 0.7.0 installing 0.7.1's full bundle gets `Compatible mismatch: Expected 'j1j-qemuarm64' but bundle manifest has 'kario-qemuarm64'` from RAUC (§5.5). Those two were trial releases that never reached phones, so there is no migration (how one would go: a full bundle written with the old machine string for those phones, after which the new system has the new one; but 0.7.0's Shell reads only `latest.json`'s `url`, so old and new phones would need separate addresses). The release tool (`tools/release.py`) reads each bundle's machine string from the signature at its end and records it in `MANIFEST.json` as `compatible`: earlier releases with another one get no incremental package (it would not install); when the release just before already differs, it stops without releasing unless `--compatible-change` says to go ahead knowing those phones get no update again.

**Why the download is larger than the package** (the test server logs where each request starts, and `ota-delta.py ranges` splits them by the bundle's structure): the `0a4ff0b` → round 5 package is 6.6 MiB; one install made 95 requests for 7.7 MiB; every byte of the package was downloaded, 1.1 MiB of it (17%) twice: 0.7 MiB of the 5.4 MiB payload, 0.4 MiB of the rest of the squashfs image (applier, hook, descriptor, metadata), and the whole dm-verity hash tree a second time. RAUC's streaming install is a squashfs on dm-verity on an NBD device, with no download cache, so blocks read twice are downloaded twice (which reader reads them again is **not looked into**). This is a proportional cost, not one that doubles with the package; for a tiny package a fixed few tens of KB look large (an 18 KB package downloaded 51 KB).
