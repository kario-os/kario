> Status: **prototype ✓** (QEMU): A/B slots, RAUC, update bundle signing, dm-verity on the system slots with a signed root hash, 「系统更新」 (System update) in Settings, delta (adaptive) updates, staged rollout and pausing, the health check (the Shell, the renderer and an app all come up), and automatic rollback on boot failure and on verification failure; `make yocto-ota-test` verifies all of this on QEMU (the verification baseline of 57 (internal document)). Per-version incremental packages (the way Android's A/B updates work: block operations plus binary diffs, §5): unit tests ✓ on the host, and generating and applying them on the slot images of two real version pairs, checked byte for byte ✓; installed through Settings on the emulator ✓ (`make yocto-ota-delta`, §5.5), not run on a real device. Resuming an incremental install after a power cut or a lost network (§5.6): unit tests on the host ✓, and a power cut run on QEMU on 2026-11-15: the power went at 226 MiB of A written, the next install resumed at operation 49 of 86, skipped 3.6 MB of payload and downloaded 4.13 MB (the whole incremental package is 4.2 MB); a lost network run on QEMU on 2026-11-19: with the network gone for 90 s, the Shell installed again, resuming at the checkpoint, and the whole download went from 1.76 times the package down to 1.15 times (the checkpoint is now recorded where the network went, §5.5, §5.6); automatic updates in the background (§6): host selftest ✓ (a simulated A/B phone), the same case passes inside the QEMU image too, automatic updates with real RAUC on the A/B disk run on QEMU on 2026-11-25 ✓ (§3), not run on a real device; stopping half way when the conditions go away and going on once they hold (§6): host unit tests and selftest ✓, an incremental package stopped at a checkpoint by the stop file, the half-written slot not booting, and the next install resuming at the checkpoint ✓ on QEMU (2026-11-19), a full bundle stopped through the Shell's proxy **not on QEMU**, not on a real device. Payload format 2 (§5.1): a big file's patch is cut into pieces that each make 4 MiB of new data, applied as they download, one piece in memory at a time, and a resumed install can stop in the middle of a patch (host unit tests ✓); a patch's old file is read from the source slot through a few windows as the patch needs it, never held whole (patching a 32 MiB program, the applier's peak memory went from about 91 MiB to about 16 MiB, host ✓, §5.1; on QEMU, with the patch of the 35.3 MB `kario-system`: 92.7–93.7 MB with the old applier, 16.6–19.4 MB with the new, 2026-11-25, §5.5); the applier reads the payload straight from the dm-verity device of the bundle RAUC mounted (compressed blocks decompressed by itself), each block once, no longer through squashfs and the page cache, and udev no longer probes RAUC's network block device (§5.5, host ✓; on QEMU on 2026-11-19: installing an incremental package whole once more, what is downloaded twice went from 29.8% of the package to 1.0%); metered networks (§6.1): host unit tests and selftest ✓, the question to the DHCP server **not tried on a phone**; an automatic update's download keeps to the Wi-Fi it began on, and stops at once when the user marks the network metered (§6, host ✓). ## 0. Summary

- **Two sets of system partitions (A/B slots)**: an update is written into the slot that is not running; the phone keeps working normally while it is being written, and a power loss only voids this one update; once installation finishes, a reboot goes into the new slot.
- **RAUC** writes the slots: the update bundle is a RAUC bundle in verity format, signed with our update key (development keys are generated by `yocto/ota-keys.sh` and kept out of the repository; in production the signing happens in an HSM), and the image trusts only the CA in its own keyring; the bundle states which device models it applies to, and other models refuse to install it. When installing from a URL it writes while downloading (streaming), without storing the whole bundle first; for this, the update server (and any CDN in between) must support HTTP Range requests. If it does not, RAUC fails with an error instead of falling back to downloading the whole bundle.
- **System slots are read-only and verified block by block (dm-verity)**: a slot holds ext4 plus its hash tree; the slot's "descriptor" (block count, hash tree location, salt, root hash) is signed with the update key and kept in the state partition. At boot the initramfs first verifies the descriptor's signature with its built-in CA certificate, then mounts the system read-only through dm-verity; from then on every block that is read is checked against the root hash, and a block with even one modified byte reads as an I/O error. Neither modifying the system partition offline nor substituting a self-computed root hash gets through.
- **Delta updates**: the update bundle carries a hash for every 4 KiB block of the slot image (RAUC's `block-hash-index` adaptive mode); during a streaming installation, blocks already present in either slot are copied straight from the local disk and only the remaining blocks are downloaded. There is no need to build a separate diff bundle for each pair of old and new versions: one bundle is a delta update for every old version. But Go programs, relinked every time, change almost entirely, so a round of development downloads about half the bundle; a release therefore also makes an **incremental package** for each of the last few versions (§5): block operations (copy from the phone's slot, binary diff, write new data, write zeros) that rebuild the slot on the phone, where the hash tree is recomputed and the slot may boot only if the root hash matches the signed descriptor; `latest.json` lists them by the version they start from, and the phone takes the one for its own version, otherwise the full bundle (adaptive). On the host, the incremental payload for the round from `c6b9001` to `be494c0` (where the adaptive install actually downloaded 65.3 MB on the emulator) is 6.7 MB. In payload format 2 a big file's patch comes in pieces (each makes 4 MiB of the new file), each with its own SHA-256, checked and applied as it downloads, one in memory at a time; nor is the old file read into memory whole: the patch reads it from the running slot through a few windows as it needs it (§5.1).
- **Resuming an install**: when the power or the network goes in the middle of an incremental install, the next install of the same package goes on from the checkpoint the applier recorded, neither reading nor downloading the part of the payload already done; the whole slot is still checked at the end, so a wrong checkpoint can only make that install fail (§5.6); a checkpoint may also fall in the middle of a patch in pieces (format 2); when the payload stops arriving (the network gone) or the install is told to stop, the applier records one more where it stopped instead of relying on the one of a few seconds earlier. A download that stops is tried again by the Shell after a while, up to three times.
- **Automatic updates**: once switched on in 「设置 › 系统更新」 (Settings › System update) (off in the open-source image; a product can turn it on by default in its configuration), the Shell checks once a day and downloads and installs in the background at a low priority, only on Wi-Fi that is not metered (§6.1), with the battery at least half full or charging, and not in a call; when the conditions go away while it installs (a call coming in, the charger unplugged with the battery under half, a metered network or no Wi-Fi), it stops, and once they hold again it goes on (an incremental package from its checkpoint, a full bundle taking the blocks already written from the slot), the half-written slot never booting meanwhile; the download keeps to the Wi-Fi it began on and ends when the phone leaves it, never going on over mobile data (§6); then a notification offers 「现在重启」 (Restart now) or 「今晚」 (Tonight); with tonight, the phone restarts at night with the screen off, no call and no alarm due soon (§6).
- **Metered networks**: a Wi-Fi network can be metered (a phone's hotspot): detected automatically (the network's DHCP server sends Android's `ANDROID_METERED`, or its addresses are in a phone hotspot's range), or chosen per network in 「设置 › Wi-Fi」 (Settings › Wi-Fi), yes or no, automatic by default; mobile data always counts as metered. System updates, the store's automatic updates and apps' background jobs that ask for an unmetered network wait while on a metered one, and stop when the phone moves to one half-way; what the user starts downloads as usual (§6.1).
- **No downgrade**: release images write `min-bundle-version=<own version>` into RAUC's `system.conf`, and update bundles older than that (the version is in the signed manifest) are always refused, whatever the update server offers; 「设置 › 系统更新」 (Settings › System update) likewise only offers versions newer than the current one (`已是最新版本` (Already up to date)). So to withdraw a bad version, you have to publish again with a higher version number. Development builds have no version number and skip this check.
- **Signature on `latest.json`** (when the product layer provides a public key, `PHONE_UPDATE_KEY`, [11](11-platform-architecture.md) §15): the update server signs it fresh each time with an online key, and the response headers carry `X-Offer-Issued` (the issue time), `X-Offer-Signature` (Ed25519, over `kario-offer/1`, the issue time and the exact bytes of `latest.json`) and `X-Offer-Key` (the ID of the key that signed; `ota.SignHeaders`, `ota.VerifyHeaders`). The `PHONE_UPDATE_KEY` file holds one public key a line: normally one, while the key is rotated the one that signs and the next one; the phone picks the one the key ID names, and without a key ID (an old server) tries each. The update server's key can be rotated; the steps, and what happens to phones that did not keep up, are in [11](11-platform-architecture.md) §15.1. The device rejects responses that are unsigned, have a wrong signature, name a key not in the file, were issued more than 7 days ago, or are older than the last one it accepted. This way, someone impersonating or intercepting the update server can neither change the rollout percentage nor use an old `latest.json` to keep a phone on an old version forever. The signing is done by the update server (closed source, D11; the formats of the signature and of install reports are in the `ota` package, shared by phone and server); the staged rollout tool edits the file as usual and does not have to deal with signing.
- **System data comes from the update server too**: the holiday calendar `holidays.json` (each region's public holidays and the weekend days that are make-up workdays, `ota.Holidays`; door cards chosen by the time of use need it, [30](30-nfc.md) §4, and the calendar marks days off and workdays by it, apps reading it with `holidays.get`, [22](22-developer-api.md) §4.4) sits next to `latest.json` and is signed the same way, except that the signature is over `kario-data/1`, the file's name, the issue time and the exact bytes (`ota.DataMessage`), so a signature cannot be moved to another file. With an update server the phone fetches it once a day (an hour later after a failure) and likewise refuses it unsigned, wrongly signed, signed more than 7 days ago or older than the one it has; it is kept in `<state dir>/shell/holidays.json`. The update server serves the file only when it reads as a calendar. The platform ships no calendar: the dates are the government's (in China the yearly notice of the General Office of the State Council) and must be checked before they go onto the update server; real calendar data is **not implemented**, and the selftest uses a test calendar ([30](30-nfc.md) §7).
- **Staged rollout**: `rollout` in `latest.json` is the percentage (%) of devices this version has been rolled out to, and `paused` pauses the rollout. On its first check each device draws a random bucket from 0–9999 and stores it in the data partition shared by both systems; the bucket decides whether its turn has come. The server does not know which device is in which batch. When it is not yet the device's turn, Settings states the reason and does not offer installation.
- **Telling the server how the installation went**: after the phone installs an update, it records which slot and which version it installed; once the new slot is marked good, or the phone has gone back to the old slot, the Shell sends `POST /report` to the update server (version, `good` or `rollback`, bucket); if it is not delivered, it is sent again at the next boot. The update server's staged rollout tool runs periodically: it raises `rollout` step by step over time (by default 1% → 10% → 50% → 100%, one day per step), and sets a version to `paused` if it has enough reports (20 by default) and the share of rollbacks exceeds a threshold (5% by default), or if there are enough day reports and the share of phones with app crashes exceeds a threshold (10% by default); once paused, the rollout has to be released by hand.
- **Reporting again one day later**: one full day after the new slot is marked good, the Shell sends another install report (`kind: "day"`) with the number of app crashes during that day (the number of crash log entries recorded since the new slot was marked good); if the phone was switched off in between, the report is sent at the next boot. A version that installs fine but keeps crashing when it runs is stopped this way too.
- **Signing install reports**: the key service performs a device attestation for each install report (`attest`, with the app name recorded as `system.ota-report` and the nonce being the SHA-256 of the version, result, bucket, kind and crash count (`kario-report/2`); app IDs starting with `system.` cannot be installed, so no other app can impersonate it), and the attestation is sent along with the report. When the update server is configured with the certification body's root (`--device-root`), it accepts only reports signed under that root and answers 403 to everything else: forged "successes" cannot dilute the rollback rate. For the same phone and the same version, only the first install verdict and the first day report count (the server stores a hash of version, kind and device ID; device IDs never appear in `reports.jsonl`); unlocked phones (whose attested boot state is `unlocked` and which may be running a self-built system) are still accepted, but marked `unlocked` and not counted for the staged rollout. Without `--device-root` the server accepts unsigned reports as before. On phones without a provisioned device certificate, the attestation root is one the phone generated itself at first boot, a different one on every phone, so the server cannot check them uniformly: this can only be turned on on the real server after factory provisioning ([22](22-developer-api.md) §11). The open-source side has `ota.VerifyReport` and the command-line tool `phone-ota-verify`, so anyone can verify reports.
- **The new slot has to "prove its health"**: after the new slot boots, it is marked good only when the system services are running, the Shell has come up with the renderer, and an app (Settings) can launch and speak the protocol; until it is marked good, every boot uses up one chance, and once all three are used up the phone goes back to the last good slot. If the new slot already fails verification at boot (wrong descriptor signature, data not matching the root hash), this boot goes straight back to the good slot and the new slot gets no more chances.
- The whole selection is done by a very small initramfs (busybox, veritysetup, openssl and one script, about 16 MB unpacked) after the kernel starts and before the system starts, without depending on any particular bootloader; it also mounts the state partition and the data partition. Disks without A/B partitions (the single root filesystem image used for development) go through the same initramfs, which boots read-write from the `root=` on the kernel command line, without dm-verity.
- In 「设置 › 系统更新」 the user sees the current version and the running slot, and can check for updates, install and reboot; bundles with an untrusted signature or not meant for this device are refused, with the reason stated.

## 1. Partitions

| Partition (GPT name) | Content |
|------|------|
| `state` | The slots' boot state and the signed descriptors of both slots (16 MB); the initramfs mounts it at `/var/lib/slots`; a factory reset's request and the anti-theft lock's record are kept here too, out of the erase's reach ([31](31-lock-and-biometrics.md) §11) |
| `rootfs_a`, `rootfs_b` | Two systems (1 GB each, leaving headroom for larger future versions), identical at the factory; read-only |
| `data` | Writable data of the system and the user, shared by both systems; the initramfs mounts it over all of `/var/lib` (app data is in `/var/lib/phone`); if it cannot be mounted, `/var/lib` is read-only and the log says so; for a factory reset the initramfs makes it anew first, copying back only the device's identity ([31](31-lock-and-biometrics.md) §11.1) |

`/var/lib/slots/boot` is four lines of text: `slot` (the slot to boot next), `good` (the slot last marked good), `tries` (how many boot chances the new slot has left), `booted` (the running slot). It is only parsed by format and never executed: a slot can only be a or b, a count can only be digits, and a corrupted file is treated as "boot A". `rootfs_<slot>.verity` and `.verity.sig` are the slot's descriptor and its signature (CMS).

The mounting is done in the initramfs rather than in systemd mount units: a mount unit first waits for its device to appear, and on disks without these two partitions it would wait 90 seconds for nothing. The system's fstab has no line for `/`, so systemd does not try to remount the read-only root read-write. `/dev/console`, `/dev/kmsg` and the mount points in the initramfs are created in advance from the image's device table (`phone-initramfs-devices.txt`), because the kernel has to open the console before it runs `/init`.

## 2. The course of one update

1. 「检查更新」 (Check for updates) in Settings: the Shell reads `latest.json` from the update server (version, release notes, size, bundle URL; optionally `rollout` and `paused`), and verifies the signature first when a public key is configured. When the rollout is paused, the bucket is outside `rollout`, or the version is not newer than the current one, the version is not offered, and Settings shows the reason (`held` in `system.update`).
2. 「安装」 (Install): the Shell runs `rauc install <URL>`. RAUC first verifies the signature and the device model, then marks the other slot as not bootable and writes the slot image (ext4 plus hash tree, written as is; going by block hash, blocks already present in either slot are copied locally and the rest are downloaded through HTTP Range requests); a hook in the bundle puts the slot's signed descriptor into the state partition; finally the slot is set as the next boot (`slot` changes to the new slot, `tries=3`). When `latest.json` has an incremental package starting from the phone's version, the URL is that package's: the slot is written by the install hook in the package instead (§5.3), and every other step is the same; if it fails to install, the full bundle is installed next. A download that stopped (RAUC reports a download, connection or timeout error, or the incremental package's applier says the payload stopped arriving) is no failure to install: the Shell installs the same package again after 30 seconds, 2 minutes and 8 minutes, an incremental one going on from its checkpoint (§5.6), and only when all three fail does the install fail. While it installs, Settings shows the progress: the percentage RAUC prints, for an incremental package the applier's operations done; while a retry waits, which attempt and at what time.
3. Reboot: the initramfs sees `slot ≠ good` with chances left and uses one up (`tries=2`); it verifies the descriptor's signature, opens the slot with veritysetup, mounts it read-only and boots from the new slot. If any step fails, this boot starts from the `good` slot instead, which also stays the slot for the next boot.
4. Once the system is up, `phone-ota-good` runs the health check (`ota-healthy`): telephonyd is running; when the display service is running (always on the phone; on the emulator it needs `phone.gui=1`), it also waits for the Shell to write `/run/phone/healthy` (at most 120 seconds). After the renderer handshake succeeds, the Shell launches the Settings app in the background, writes this file once the app speaks the protocol (Shell version, renderer, app, startup time), and then ends the app. If the check passes, `rauc status mark-good` runs: `good` changes to the new slot, `tries=0`. When the renderer cannot come up, the Shell keeps exiting and restarting, and the file never appears.
5. If the new slot is never marked good (it fails to boot, keeps crashing, or fails the health check), the initramfs goes back to the `good` slot after the three chances are used up.

At build time, `phone-verity.bbclass` adds an image type `ext4.verity`: ext4 with 4 KiB blocks (dm-verity verifies in 4 KiB units), followed by the hash tree computed by veritysetup (without a verity superblock; all parameters are in the signed descriptor), with the descriptor signed with the update key as CMS; the factory disk (`phone-ab.wks.in`) writes this image into both slots, and the state partition comes with both slots' descriptors preloaded. RAUC uses a custom boot backend (`rauc-boot`) to read and write the same state: `get-primary`, `set-primary`, `get-state`, `set-state`, `get-current`.

## 3. Verification

- `tools/slots_test.py` (part of `make test`): runs the RAUC backend and the initramfs selection logic in a temporary directory — healthy after an update, never healthy after an update (rollback after three tries), the good slot marked bad, a slot that fails verification rejected on the spot, a corrupted state file.
- `make yocto-ota-test`: the update bundle is served by a small HTTP server with Range support (`yocto/ota-www.py`, which records how many bytes each request sent), and the A/B disk image is booted on QEMU 13 times in a row, doing one step and shutting down each time — on A, first check for updates against two servers, one with the staged rollout at 0% and one with the rollout paused, and Settings offers installation for neither and states the reason; then refuse a bundle signed with an untrusted key; then install the bundle to B through 「设置 › 系统更新」 (Settings › System update); B comes up with the display service (Shell, renderer, Settings app) and is marked good; install from B to A; A boots three times in a row on an emulator without a display device (`novga`), where the renderer cannot come up and the health check fails; the seventh boot goes back to B (with the display service, the Shell reporting `rollback` to the server, ✓ on 2026-11-25); install to A again, and after shutdown corrupt A's filesystem on disk, so that at the next boot A fails verification and the phone goes straight back to B; install A once more, and after shutdown replace A's descriptor in the state partition with one that has a different root hash (keeping the old signature), so that at the next boot the signature is wrong and the phone goes straight back to B; the last two boots are automatic updates with the real RAUC (`ota-auto.script`): B joins the simulated Wi-Fi (iwd's access point on the second simulated radio), the user marks it metered in 「设置 › Wi-Fi」 (Settings › Wi-Fi), and with automatic updates on the Shell says it does not install on a metered network; marked not metered and an hour later (`timeshift`), it installs into A in the background and posts 「系统更新已安装」 (System update installed), and at the next boot A is healthy (these two steps run on QEMU on 2026-11-25 ✓: the Shell first says `not now: on a metered network (Kario-Test)`, and once the network is marked not metered it installs into A in the background through its proxy, downloading 3106716 bytes of the 147912600-byte bundle; A comes up healthy and reports `good`). The test checks the slot of every boot, the two non-offers, the four refusals, the five installations (one of them automatic), that each installation downloaded less than a quarter of the bundle, that the automatic update first waited on the metered network, B's health record, A's health record at the end, that B reported `good` to the server after it was marked good and that the report was signed (after the first boot the phone prints its attestation root; `ota-www.py` stores the reports exactly as received, and at the end `phone-ota-verify` checks each one against that root, and the test fails if any one is wrong), that the system always runs read-only through dm-verity, and the reason each of the two tamperings was detected. A refusal must be due to the signature (RAUC's error message mentions the signature or the certificate); any other reason, such as a failed download, counts as a failure. When the closed-source product repository runs the same test, it substitutes the official update server and staged rollout tool (`OTA_SERVER`, `OTA_ROLLOUT`): the server verifies and deduplicates on the spot (the two later reports from the same phone for the same version are accepted but not counted again), and the rollout percentage adjusts according to the reports.
- In the test every installation uses the same image, so the slots already contain the vast majority of the blocks, and the download size is the lower bound for adaptive mode: about 4.2 MB each time, 3% of the 130.7 MB update bundle (almost all of it the block hash index itself: one 32-byte hash per 4 KiB).
- **Across versions** (`make yocto-ota-base` saves the A/B disk, the slot image and the file list of one build; after changes and a rebuild, `make yocto-ota-delta` boots from it and installs the new update bundle; it now installs twice, on two copies of the base disk, once with an incremental package made against the base and once adaptively with the full bundle, and compares the downloads, §5.5): from `5da8671` to `88dc389`, with one round of development in between (the protocol gained fields for notification actions, the SDK gained callbacks, and the store, notifications, music and cloud services all changed), the actual download was 55.5 MB, 38% of the 142.4 MB update bundle; the new slot came up healthy and the install report was delivered. Of the 490.6 MB new slot image, 23065 4 KiB blocks were in neither of the phone's slots (90.1 MB; what gets downloaded is the compressed form); 38 files changed, 145.6 MB, almost all of them Go programs: changing packages that every program links (`ui`, `sdk`) means every program has to be relinked, and a change in one place of a Go program shifts all the code after it, so practically the whole program changes (phone-shell 22.8 MB, the mini-program host 16.9 MB, phone-cts-verify 14.3 MB, …). For a patch release that changes only one program, the download is roughly that program's compressed size plus the 4.4 MB index.
- To go smaller there are three routes: build the system programs as one multicall program (like busybox, dispatching by the name it was invoked under), which the system services already do (the next items), but that saves image size, not each round's delta; ship per-file binary diffs (Android's approach; RAUC does not support it itself, so the incremental package's install hook does it now, §5); or download by content-defined chunks (RAUC's casync bundles), **not implemented**.
- **Estimate for a multicall program** (2026-11, compiled only, not run on a device): the 27 Go programs in the product image were turned into libraries as they are, plus one entry point that dispatches by invocation name, and built the same way as the recipes, as arm64 static PIE with symbols stripped:

  | Approach | Uncompressed | gzip -9 (approximates the update bundle) | Pages each process has to relocate at startup |
  |------|------|------|------|
  | Now: 27 programs, each linked separately | 162 MB | 58 MB | Small apps 0.3 MB, Shell 2.0 MB (14.6 MB in total for the 27) |
  | All combined into one (PIE) | 31 MB | 11 MB | 2.5 MB for every process |
  | Only the 8 system services combined (Shell, pushd, keystored, imed, audiod, mediad, sandbox, cts-verify; apps unchanged) | 62 MB → 23 MB | 23 MB → 8 MB | 2.0 MB per service process |
  | Any of these as non-PIE | Same as above | Same as above | 0 |

  Combining only the services is almost free: the Shell already contains most of the other services' code, the image shrinks by 39 MB, and the delta for a round of development drops by about 15 MB (55.5 MB → about 40 MB); the cost is that small services such as pushd and imed each relocate about 1.5 MB more, part of which is offset by shared runtime code pages; this has to be measured on the device. Combining everything into one could bring the delta down to about 10–15 MB, but two things have to be decided first: under PIE, each of the 19 Go processes gets about 2 MB more private pages (about 37 MB more in total), while non-PIE has no such overhead (and can share code pages as well), at the cost that the program's own addresses are no longer randomized (heap, stack and mmap are still randomized, and Go is memory-safe); and the system apps would be merged into the system program too and stop being separate packages (they are updated together with the system anyway; apps installed from the store are not affected).
- **The system services are combined into one program, `kario-system`** (R45, following k3s and busybox): the code of the Shell, pushd, keystored, imed, audiod, mediad, the sandbox launcher and `phone-cts-verify` is each a package under `programs/` (`Main()`), and `cmd/kario-system` dispatches by invocation name; in the image, `bin/phone-shell` and the others are links pointing to it, and so is `lib/phone/bin/phone-sandbox`, so neither the systemd units nor the path used to launch apps changed. The development `cmd/phone-*` programs are still there, three lines each, and can still be built separately. It is still PIE (program addresses randomized); apps are still one program each, since they are packages that are installed and signature-checked individually. Two points need care: when the Shell re-executes itself, it uses the link it was started through (the process name stays `phone-shell` and does not become `kario-system`); the sandbox launcher's package-level `init`, which locks the thread, only runs when it is started under the name `phone-sandbox`, so it does not take effect in the other services.
- **Measured on the device** (2026-11, qemuarm64): the Go programs in the product image went from 27 programs, 156.2 MB, to 20 programs, 116.4 MB (`kario-system` is 23.7 MB; the 8 programs it replaced were 62 MB together), and the update bundle from 139.1 MB to 125.7 MB; each installation downloads 4.1 MB instead of 4.4 MB. Memory was not saved (PSS in the public image's selftest, one full selftest before and one after the merge): the Shell 28.2 → 18.4 MB, imed 11.2 → 14.4, audiod 10.0 → 11.8, pushd 9.0 → 11.0, keystored 4.7 → 8.5; these five together 63.1 → 64.1 MB. ## 5. Per-version incremental packages

> Status: host ✓ (unit tests of every part; generated, applied and checked byte for byte on the slot images of two real version pairs); installed through Settings on the emulator ✓ (`make yocto-ota-delta`: RAUC runs the install hook, and the hook refuses a package made for another version; a rollback when the new slot is not healthy, B to A, a power cut while it writes, and a damaged package falling back to the full bundle, §5.5); not run on a real device.

Adaptive mode looks blocks up one by one, and after a Go program is relinked almost every block of it has changed, so a round of development downloads about half the update bundle (§3). Android's A/B updates (`update_engine` payloads, made by `delta_generator`) make one payload per pair of old and new versions: block operations, where unchanged blocks are copied from the phone's old slot and changed files are sent as binary diffs. This follows that model; the code is in `ota/delta` (payload format, generation, application), `ota/delta/bsdiff`, `ota/delta/xz`, `ota/delta/ext4`, `ota/verity` and the command `phone-ota-delta`, all using only the Go standard library and code of our own, with no new dependencies.

### 5.1 Payload format

A payload is a header (`KDLT`, the format number, the manifest length), a JSON manifest and the operations' data, one piece after another in the order of the operations, so it can be written while it is being downloaded, read once from start to end. The manifest states the source image (version, size in bytes, SHA-256, its verity root hash), the target image (size in bytes, SHA-256) and the target's verity descriptor (block count, hash tree location, salt, root hash). The image is the part of the slot that dm-verity covers (the ext4); the hash tree is not in the payload but recomputed on the phone. Each operation states which blocks it reads and which it writes (extents of 4 KiB blocks, each list taken in order as one stream), and the SHA-256 of its data, of the source data it reads and of the result it writes:

| Operation | What it does |
|------|------|
| `REPLACE` | Writes the data the operation carries: xz-compressed or stored |
| `SOURCE_COPY` | Copies blocks from the source slot, wherever they are (not necessarily in the same position) |
| `SOURCE_BSDIFF` | Makes the new blocks from blocks of the source slot plus a binary diff; in format 2 a big file's patch comes in pieces (below) |
| `ZERO` | Writes zeros |

- Compression is xz (LZMA2): the standard library has neither zstd nor xz, so the decompressor is our own (`ota/delta/xz`, the xz file format plus LZMA2, tested against the xz program's output; decoding a Go program on the host runs at about seven tenths of the xz program's speed); compression calls the xz program on the build host (`-9e`, with a dictionary sized to the data). No Go module is added.
- The binary diff is our own bsdiff (`ota/delta/bsdiff`): Colin Percival's published method (the idea under the BSD licence; the code and the patch format are ours), a suffix array of the old data (the SA-IS algorithm), exact matches stretched in both directions as long as at least half the bytes agree, stored as byte-wise differences (when code has only moved or its addresses changed these are almost all zeros and compress to very little), and what matches nothing stored as is; a patch is three streams, control, diff and extra, each xz-compressed.
- **Patches in pieces** (format 2, `Pieces` in `ota/delta/bsdiff`): for a file bigger than a piece (4 MiB by default), the patch is cut at every 4 MiB of the new file; each piece says where in the old file it starts and carries its own control, diff and extra streams (each xz-compressed), needing none of the others; the operation in the manifest states the bytes each piece makes (`piece`, a multiple of 4 KiB, at most 16 MiB) and each piece's length and SHA-256 (`pieces`). The applier reads one piece at a time, checks its SHA-256 before applying it and writes it to the target, holding the decompressed streams of one piece in memory (before, all of the decompressed patch, about as big as the new file); a checkpoint may come between two pieces (§5.6). A file one piece holds still gets a whole patch. The format number is 2: the applier reads 1 and 2, the generator writes 2 by default, and `--format 1` for appliers that read only 1 (§5.4). On the host, a patch applied in pieces and one applied whole make the same bytes; the payload of the fixed synthetic system (`TestPayloadSize`: a 5.9 MB program and two apps relinked, a new app, some of 900 small files changed, added and removed) is 309328 bytes in format 1 and 310465 in format 2 (0.37% more: each piece's streams are compressed on their own, and the manifest holds each piece's hash), and the test wants at most 330000 bytes.
- **The old file is not read into memory whole** (`bsdiff.Patcher`, `ApplyAt`): the applier first reads the operation's source blocks once in order and checks their SHA-256, then, applying the patch, reads the old data from the source slot where the patch needs it, through a few windows (4, each at most 256 KiB): reading on from the end of a window reads 256 KiB ahead, a step elsewhere (code that moved) reads only what it needs (at least 4 KiB), so it does not push out the window the next step comes back to. What it reads is the running slot's dm-verity device, every block verified by the kernel as before, and the result has its own hash. One piece's decompressed streams and the windows are reused from piece to piece rather than allocated for each. The payload format does not change: formats 1 and 2 as before, and a whole patch reads its old file the same way (only its three streams are still decompressed whole). Measured on the host (`TestBigFilePatchMemory`: a 32 MiB program in each of two slots, the new one as a relink of the old, the patch in 8 pieces; the applier runs in a process of its own and its own VmHWM is read): the peak memory was 90–91 MiB (the 32 MiB old file whole in memory, plus each piece's streams) and is now about 16 MiB (15.8–16.3 MiB over several runs), not growing with the file; 64.1 MiB of the source slot read (an image of 48.4 MiB, the program read once for its hash and once for the patch); the result is the target byte for byte. With dense changes (1500 edits in 2 MiB: bytes changed, stretches inserted, removed and moved) the old file is read about 1.5 times over, with large stretches moved about 1.07 times (`TestStreamedOldData`).
- The manifest is checked as a whole before it is used: known operations, every extent inside its image, every target block written by exactly one operation, the data packed in order, every hash present, the pieces covering their destination and their lengths adding up to the operation's data. Limits: a manifest of at most 64 MiB (the generator does not write a larger one), an image of at most 2²⁴ blocks (64 GiB), an operation of at most 65536 blocks (256 MiB) and 1 GiB of data, a piece of at most four times the piece size plus 2 MiB (all three streams stored, the worst case), so a payload holds at most 2⁵⁴ bytes of data after its manifest.

### 5.2 Generation

`phone-ota-delta generate --source <old> --target <new slot image> --out rootfs.kdelta [--report report.json]`, run on the build host. The old one can be a slot image (with `<file>.desc` as its descriptor) or the A/B disk of a release (`.wic` or `.wic.gz`: it takes `rootfs_a` and reads the descriptor from the state partition). The ext4 is parsed by our own code (`ota/delta/ext4`: superblock, group descriptors, inodes, extent trees and old-style block maps, directories), which yields the blocks that hold each file's data.

1. Each target block: an all-zero block is written as zeros; a block that exists anywhere in the source slot is copied from there (first trying the block after the one copied last, then the same position, then a lookup by hash); the rest are new.
2. Files with new blocks: binary-diffed against the file at the same path in the source slot (failing that, the only file with the same name; for a newly added program, the program in the same directory closest in size), and the patch is used (one `SOURCE_BSDIFF` for the whole file) if it is smaller than writing just this file's new blocks; otherwise the new blocks are written.
3. The new blocks of small files are compressed together with the file system's metadata (inode tables, directories, bitmaps, …) into `REPLACE` operations of at most 4 MiB each.
4. Before writing the payload out, the generator applies it in memory to the source image: the result must be exactly the target image, and the hash tree must come to the signed root hash. The report compares the payload with the whole image and with an estimate of the adaptive install (the block hash index plus the 128 KiB in-bundle blocks that contain a block not in the source slot, gzip-compressed as mksquashfs does), and shows how each changed file is sent and at what size.

### 5.3 Installation

An incremental package is a RAUC bundle (verity format), signed with the same update key as the full bundle and stating the same device model and version (so `min-bundle-version` still refuses downgrades). The slot's image is the payload `rootfs.kdelta`, marked `hooks=install`: once RAUC has verified the signature and marked the other slot as not bootable, it does not write the slot itself but runs the bundle's hook `delta-hook`; the bundle also carries the target's signed descriptor and `phone-ota-delta` built for the machine, and, where dm-verity's read-ahead would reach into the image, a padding file nothing reads (`zz-verity-pad`, at most 252 KiB, §5.5). Why an install hook rather than having the Shell apply the payload: signature, device model, no downgrade, slot marking and streaming download are all RAUC's existing steps, and if the hook fails RAUC does not set the slot as the next boot; the Shell just installs another URL. There are two appliers: one in the system image (`/usr/bin/phone-ota-delta`, a program of its own that links only the update code and so seldom changes within a version), and one in the bundle (from the same build as the payload, so its format always matches, for old systems whose image has no applier yet or one that does not read this format). The hook asks the system's applier, `phone-ota-delta can-apply <payload>`: it reads the format number in the payload's header itself (the 4 bytes after `KDLT`; in a mounted bundle from the bundle's device, not through the mounted file, §5.5), and when it applies that format it prints the number and exits 0, so the hook uses the system's, and a streaming install never reads, nor downloads, the bundle's copy (about 1.2 MB compressed); when it does not (exit 3, or an older applier without the command) the hook uses the bundle's; with none in the bundle either it fails, RAUC does not mark the slot and the Shell installs the full bundle next. The system's applier is under dm-verity, as trustworthy as the bundle's copy. The hook does not read the format itself: the phone's busybox is built without `CONFIG_DESKTOP`, so its `od` knows no `-A -t -j -N`; the earlier hook read it with `od`, got an empty format on the emulator, never used the system's applier, and every package without the applier failed to install (falling back to the full bundle each time, §5.5); the host test used GNU `od` and did not notice. The hook's test now gives it only commands busybox has too (`sed`, `mv`, `sync`, `tee`, `tail`, `rm`, `cp`, `grep`). The applier's output is also kept in `/run/phone-ota-delta.log`: which applier ran, how long it took and its memory peak, or where it stopped; and its progress (the operations done) and the checkpoint it resumed from (§5.6), which Settings reads to show the progress. The hook gives the applier `--checkpoint <state partition>/rootfs_<slot>.progress`; an older applier in an image does not know that option, so the hook first asks `phone-ota-delta can-resume` and, without an answer, leaves it out and installs from the start as before; when the answer lists `stop`, it also gives `--stop /run/phone-ota-delta.stop`: once that file appears, the applier stops before the next operation or piece, records a checkpoint and exits with a failure (the Shell creates it to stop an automatic install, §6). The full bundle's hook (`verity-hook`) too now removes the slot's old descriptor (with the checkpoint) before RAUC writes the slot, so a slot whose install failed or was stopped half way has no descriptor it could be opened with either.

The hook reads the running slot from the state partition, first deletes the old descriptor of the slot about to be written (a half-written slot has no descriptor it could be opened with), and runs the applier:

1. Everything is checked before writing: the manifest is valid; the verity descriptor in the manifest is identical to the signed descriptor in the bundle; the source image is the running slot (the root hash in the manifest is compared with this slot's descriptor in the state partition; without a root hash, the whole slot is read and its SHA-256 computed). If not, it reports "the payload is for another system version" and writes nothing.
2. Operation by operation: read its data and check the SHA-256; read the source blocks through the running slot's dm-verity device (`/dev/mapper/root_a`), so the kernel has verified every block, and check the source data's SHA-256 (read once in order and not kept in memory; a copy or a patch reads it from the device again as it uses it, §5.1); compute the result, check its SHA-256, and write it into the other slot.
3. Once everything is written: sync, drop the page cache, and read the whole image back from the device: its SHA-256 must be the target image's, and the root hash of the recomputed hash tree must be the one in the signed descriptor; then the hash tree is written after the image.

If any step fails, the applier exits with a failure, the hook fails, RAUC does not mark the slot, the slot has no descriptor either, and the initramfs will not use it. Only when all is right does the hook put the signed descriptor into the state partition (as the full bundle's `verity-hook` does), and RAUC then sets the slot as the next boot; at the next boot the initramfs verifies the descriptor's signature and opens the slot through dm-verity as usual. The payload is read only once from start to end: in a streaming install RAUC downloads through HTTP Range only the parts of the bundle that are read, that is, the payload (and the applier, when the bundle's is used). With the payload read through squashfs the download was about 17% larger than the bundle itself: RAUC's streaming install (NBD → dm-verity → squashfs) has no download cache, so blocks read twice are downloaded twice (measured in §5.5); so the applier now reads the payload straight from the bundle's device instead of through squashfs (§5.5, "Reading straight from the bundle's device").

### 5.4 Release and selection

`latest.json` (signed as a whole, as before) gains an entry `deltas`, each item an incremental package and the version it starts from:

```json
{"version": "0.8.0", "size": 130652032, "url": "phone-bundle-0.8.0.raucb", "rollout": 10,
 "deltas": [{"from": "0.7.0", "from_root_hash": "c02eb5fb3706f7eb78f84a8da06a82fbaf6d6b4eb8bac681ea546fd2a0f93579", "size": 7900000, "url": "phone-delta-0.7.0-0.8.0.raucb"}]}
```

The phone (`shell/update.go`) picks an incremental package when it offers this version: one with `from_root_hash` is used only when the running slot's root hash (from its descriptor in the state partition) is exactly that (it is that very image); one without it, by release version (`from` equals the phone's version). The one picked goes into `available.delta` of `system.update`; installing tries it first and, if it fails to install, installs the full bundle next. Without a suitable incremental package the full bundle is installed (adaptive).

The release tool (kario-internal's `tools/release.py`) makes an incremental package for each of the `--deltas` (default 3) newest releases in `dist/` that kept their A/B disk: through `make yocto-bundle OTA_DELTA_FROM="<version>=<disk>…"` it goes into the build container, where `yocto/qemu-ota-delta.sh bundle` generates the payload for each version and the `phone-bundle-delta` recipe bundles and signs it; the result goes into `dist/v<version>/phone-delta-<old>-<new>.raucb` and into `latest.json`. The update server `kario-otasrv` needs no change for incremental packages (it serves every `*.raucb`).

Releases are built from a commit (`SRC=git`, kario at the tag without local changes): before bitbake, `make yocto-src` checks that phone-fw's Go module list is from that commit's go.mod and go.sum; if it is not, it writes the list again when the working tree's two files are the commit's, and otherwise stops and says so, rather than building with a stale list until it fails halfway ([13](13-prototype.md) §5.1).

Each release's `MANIFEST.json` records which payload formats its image's applier reads (`ota_delta_formats`: the release tool builds `phone-ota-delta` and asks `formats` when kario is at exactly the commit the image was built from, without local changes; when it cannot ask, nothing is recorded). For an earlier release with formats on record, `OTA_DELTA_FROM` names it `<version>@<format,…>=<disk>`; after generating the payload `qemu-ota-delta.sh bundle` reads its format number and, when it is among them, leaves the applier out of the bundle (the `phone-bundle-delta` recipe adds the applier only when `PHONE_DELTA_DIR` has one), and records whose applier will apply it (`<label>.raucb.applier`: `system` or `bundle`); the others carry it as before, and `--bundle-applier` puts it into every package. The payload is generated in the newest format the source system's applier reads (2 when it reads 2, else 1, without pieces), so that the bundle can leave the applier out; when what it reads is not known, format 2, with the applier. A release without that record (0.7.1, whose image has no applier either) still gets packages carrying it; 0.6.0 and 0.7.0 have another machine string and get no packages (below).

**The machine string (RAUC's `compatible`) must not change after a release.** RAUC installs only bundles whose `compatible` is exactly the one in the system's `system.conf`, full bundles and incremental ones alike. The rename (J1J → Kario) changed it from `j1j-qemuarm64` to `kario-qemuarm64`, so phones on 0.6.0 or 0.7.0 cannot install any later release: on the emulator, 0.7.0 installing 0.7.1's full bundle gets `Compatible mismatch: Expected 'j1j-qemuarm64' but bundle manifest has 'kario-qemuarm64'` from RAUC (§5.5). Those two were trial releases that never reached phones, so there is no migration (how one would go: a full bundle written with the old machine string for those phones, after which the new system has the new one; but 0.7.0's Shell reads only `latest.json`'s `url`, so old and new phones would need separate addresses). The release tool (`tools/release.py`) reads each bundle's machine string from the signature at its end and records it in `MANIFEST.json` as `compatible`: earlier releases with another one get no incremental package (it would not install); when the release just before already differs, it stops without releasing unless `--compatible-change` says to go ahead knowing those phones get no update again.

**Why the download is larger than the package** (the test server logs where each request starts, and `ota-delta.py ranges` splits them by the bundle's structure): the `0a4ff0b` → round 5 package is 6.6 MiB; one install made 95 requests for 7.7 MiB; every byte of the package was downloaded, 1.1 MiB of it (17%) twice: 0.7 MiB of the 5.4 MiB payload, 0.4 MiB of the rest of the squashfs image (applier, hook, descriptor, metadata), and the whole dm-verity hash tree a second time. RAUC's streaming install is a squashfs on dm-verity on an NBD device, with no download cache, so blocks read twice are downloaded twice (who reads them the second time: the next paragraph). This is a proportional cost, not one that doubles with the package; for a tiny package a fixed few tens of KB look large (an 18 KB package downloaded 51 KB).

**Who reads them the second time** (2026-11-19, the base `8000e19` and the published `f6cea8e`; the test server logs where each request starts and how long it is, matched against the bundle's structure: in c3, 1785860 bytes of the 5990264-byte package were downloaded twice; n1 downloaded 10522410 bytes in all):

- udev's blkid: as soon as RAUC connects the network block device, udev probes it with blkid for file systems and RAID signatures, by `60-persistent-storage.rules` (whose device names include `nbd*`), reading through the page cache the start of the bundle, the offsets at powers of two (64K, 128K, 256K … 4M) and near its end, at least 64 KiB each, about 1.26 MB an install; the applier reading the payload through dm-verity (not through the NBD device's page cache) downloads them again. The image now has a rule (`59-rauc-nbd.rules`, installed by the RAUC bbappend) that sets `UDEV_DISABLE_PERSISTENT_STORAGE_RULES_FLAG` for `nbd*`, and udev no longer probes it; nothing on the phone uses its links. The rule is in the running system, so it helps only phones that run this version already; installs from an earlier system (i1, i2, f1 below) are still probed.
- The kernel's read-ahead: the hook's `can-apply` read the payload's header through the mounted file; the kernel read the whole first block (compressed, about 108 KB) and left a read-ahead mark on a page; the applier then read the first block through the file (compressed blocks all went through the file then), hit the mark, and the kernel read the three blocks after it (about 393 KB) into the page cache (`FADV_RANDOM` on the file does not stop such asynchronous read-ahead), while the applier read those three blocks from the device. Now no byte of the payload is read through the mounted file (but a tail in a fragment block, which this package does not have): the applier reads compressed blocks from the device too and decompresses them itself (gzip as it reads, xz a block at a time), and `can-apply` reads the header from the bundle's device too, decompressing only as far as the format number (gzip decompresses 32 KiB at a time: one to a few device blocks).
- The compressed blocks themselves: mksquashfs keeps a block compressed when gzip takes as much as a byte off it, and although the payload's data is xz-compressed already, 7 of its 46 blocks lost a few dozen bytes that way; read through the kernel, the device block each shares with the stored blocks on either side was downloaded twice.
- The squashfs tables: parsing the superblock and the tables, the applier read the same device block again for each small read (O_DIRECT has no cache), 6 times an install; now it keeps the block it read last.
- And in the lost network (n1): the checkpoint lay about 0.7 MB behind where the applier had read (the periodic one, §5.6), the applier reads 1 MiB at a time from the device and what had come of the read the network cut was lost; the retry went through all of the above again.
- What is left: dm-verity's read-ahead of the hash tree. It reads the leaf level's hash blocks ahead in clusters of `dm_verity_prefetch_cluster` (256 KiB by default), aligned on the device's absolute block numbers, so the cluster reaches back from the start of the hash tree into the squashfs image: this package's hash tree starts at byte 6000640 (block 1465), its leaves in blocks 1466–1477, the cluster aligns to block 1408 and reads exactly those 256 KiB, 5767168–6029312, followed by the leaves' other 24 KiB; the first 233 KB are the image's tail, about 230 KB of them the payload's last blocks, kept in dm-bufio (not the page cache), and the applier downloads them again when it reads the payload's tail, most of what c3 downloads twice after the changes (below). It comes each time the package is mounted, at most 63 blocks (252 KiB), not growing with the package (and not with a tree of one level: the kernel reads ahead only the levels below the top, and an image of up to 128 blocks has one). The first fix, a 256 KiB file after the payload in a package whose payload is at least 1 MiB, gave the cluster that file instead: the payload's tail was downloaded once, but the blocks the cluster read were downloaded all the same, so the download stayed as it was, and the package grew by 256 KiB; a package whose payload is under 1 MiB had no such file, and its tail was still downloaded twice (2026-11-25, below). Now the image ends where the cluster stays in the tree (`phone-verity-pad.py`, which `phone-bundle-delta.bb` runs after `rauc bundle`, whatever the payload's size): the leaves start u blocks after the tree's start (u being the blocks of the levels above them, 1 for an image under 64 MiB), and when the image's block count is a multiple of 64 or one of the u counts before it, the leaves' first cluster starts no earlier than the tree; for any other count the script writes a `zz-verity-pad` (bytes that do not compress, then zeros to a whole squashfs block: mksquashfs stores it as data blocks, the last one compressed, and not in a fragment, where the small files the hook reads are; the same bytes in every build) that grows the image to the middle of the next run of such counts, and runs `rauc bundle` again (once, as a rule: the file's size in the image is known to within a few hundred bytes, and there are 4 KiB to spare either way; short of it, it corrects the file by the difference and runs again, at most 4 times, and the build fails if it still does not come out). Nothing reads the file and none of the image is read ahead: each time the package is mounted, up to 63 blocks less are downloaded (and a resumed install mounts it again); the package grows by 0–252 KiB, 126 KiB on average over the 64 places in a cluster where an image can end, less than the 256 KiB of before. Making `dm_verity.prefetch_cluster` smaller would do too, but it is a setting of the whole system, the system slot's hash reads would change with it, and it would only help phones that already run that kernel; not done. Host test (`yocto/verity-pad-test.py`: packages made as RAUC 1.15 makes them, mksquashfs with RAUC's options, the hash tree right after the image, a signature; a streamed install's requests to the network block device worked out as the kernel's dm-verity makes them, the mount reading the superblock and tables, the applier each of the payload's blocks once from the device): a 1.0 MB payload like that of 2026-11-25 has an image of 246 blocks, of which the read-ahead takes the last 54, 53 of them the payload's tail; padded by 40 KiB to 256 blocks, the read-ahead takes none of the image and the install downloads 216 KiB less; with the image ending on every fourth block of a cluster, 16 places, unpadded all 16 had payload blocks downloaded twice, padded none, the package growing by less than 63 blocks; a 5.4 MB payload with the old 256 KiB file has 40 blocks (the file's) read ahead and downloads as much as unpadded, now 39 blocks less, with a package 160 KiB smaller; an image of up to 128 blocks gets no padding and no second build; `do_bundle` run again takes out the last run's padding before measuring; a build that never takes the padding fails. **Reading straight from the bundle's device** (`ota/delta/squashfs`, `--direct` of `phone-ota-delta apply`, on by default): what was downloaded twice was thought to be blocks read through squashfs (squashfs reads a whole 128 KiB block each time, aligned to device blocks; where the read-ahead windows and squashfs's blocks do not line up, the same block is read a second time, and with no cache underneath it is downloaded a second time); measured, most of it was what the paragraph above lists. Having opened the payload, the applier checks whether its file system is squashfs (`fstatfs`) and, if it is, finds the device it is mounted from through `/sys/dev/block/<major:minor>` (RAUC's dm-verity device, on NBD in a streaming install), parses squashfs's superblock, inode table and directory table itself (metadata gzip- or xz-compressed), and finds every data block of the payload's file (whose inode number and size must be the opened file's), and reads them from the device with `O_DIRECT`, aligned to 4 KiB, in order, no device block twice and never past the end of the payload's run of blocks: stored blocks as they are, compressed blocks (the first, which holds the manifest, and blocks gzip happened to take a few bytes off) decompressed by itself, blocks of zeros (sparse) as zeros; only a tail in a fragment block and a block that does not decompress here are read through the mounted file (`POSIX_FADV_RANDOM`, no read-ahead). It is still the dm-verity device that is read, every block checked by the kernel; the payload's integrity still rests on the SHA-256 of every operation and piece in the manifest. When any step does not work out (not squashfs, an unknown compression, the file not matching), it reads the file as before, and the log says why. What a resumed install skips is not read from the device. Host test (bundles made by mksquashfs with RAUC's options; gzip, xz, 64 KiB and 1 MiB blocks, no fragments, always fragments, sparse blocks): what is read is the file byte for byte, no device block is read twice, and only a tail in a fragment block comes through the file; reading the header alone (`can-apply`) reads only the first few device blocks of a gzip bundle; no more than a squashfs block is read before a skip; when the device stops answering (the network gone) the stream says so and does not turn to the file (which would download it again through the kernel); a compressed block that does not decompress from its start is read through the file, one that fails half way is an error (the bytes handed over cannot be taken back, and the payload's hashes stop it too). ### 5.6 Resuming an install

> Status: host ✓ (`ota/delta`'s unit tests: an install with the power cut every few writes or syncs, writes not yet synced partly lost at the cut, and each install after it comes out byte for byte the target; resuming after a lost network; checkpoints that do not match are ignored; `cmd/phone-ota-delta`'s hook test: with only those busybox commands, the next install after a lost network resumes); resuming after a power cut on the emulator ✓ (2026-11-15, §5.5, item 2); resuming after a lost network on the emulator ✓ (2026-11-19, n1 in §5.5: on the first run the retry came while the network was still gone, the Shell did not take that for a stopped download and installed the full bundle; rerun after the fix, it resumed at the checkpoint and installed), downloading 1.76 times the package at first, and 1.15 times after the changes, among them the checkpoint where the install stopped (below); a checkpoint at the operation (or piece) where the network went: host ✓ (`TestNetworkLossCheckpointsWhereItStopped`); resuming after being told to stop (the stop file, §6): host ✓ (`TestStopAndResume`, the hook's test), on the emulator ✓ (2026-11-19, s1 in §5.5); not run on a real device.

When Android's update_engine is interrupted halfway through, the next run goes on from the step it recorded; this does the same. Every 32 MiB written or every 5 seconds, once an operation is done, the applier (`phone-ota-delta apply --checkpoint`; the hook gives it `rootfs_<slot>.progress` next to the slot descriptors in the state partition) first syncs the target slot (fsync) and then records a checkpoint: which payload (the SHA-256 of its header and manifest, and the manifest holds every operation's hashes), the source image (its root hash, or its SHA-256 when there is none), the target's root hash, the target partition's size in bytes, the index of the next operation and where its data starts in the payload; the last line is the SHA-256 of the lines before it. It is written to a temporary file, fsynced and renamed, and then the directory is fsynced, so a power cut leaves either the old one or the new one.

The next install of the same package (the same payload, the same source image, the same slot written, a partition of the same size) skips the operations before the checkpoint without reading their data: the payload is a file in the mounted bundle, the applier seeks forward in it, and a streaming RAUC install then does not download that part. When anything does not match (another payload, another source version, another partition size, a damaged or incomplete checkpoint, a data position past the 2⁵⁴ bytes a payload can hold counting as damaged), the checkpoint is removed first and the install starts from the beginning, since the blocks it vouches for are about to be overwritten.

Why skipping is safe:

- A checkpoint is written only after the target is synced, so every operation before it is on the disk. When the power goes between writing data and the next checkpoint, those operations run again next time: each reads only the source slot (the running one, through dm-verity) and its own data, never the target slot, and writes the same blocks, so running it again gives the same result.
- The blocks skipped are still read back and checked at the end with all the others: the SHA-256 of the whole image and the root hash of the recomputed hash tree must be the signed descriptor's. Even a wrong checkpoint can only make that install fail, never make a bad slot bootable; when the check fails the checkpoint is removed and the Shell installs the full bundle next.
- When something else writes the slot, its checkpoint no longer holds: the full bundle's hook (`verity-hook`'s `slot-pre-install`) removes it before RAUC writes the slot.

When the checkpoint goes: when the install completes, when the read-back check fails, and on errors such as data or source blocks not matching their hashes; it stays only when the payload stops arriving (the network gone, the bundle gone) and when the install is told to stop (the stop file of `--stop`, §6), and then the applier first records one more where it stopped: the target slot is still there, and once synced, the operations written whole before it stopped (for a patch in pieces, the pieces written whole) make the checkpoint, so the next install does not download again the data since the last periodic checkpoint (which can lie up to 32 MiB of slot data or 5 seconds behind; on QEMU, when the network went, it lay about 0.7 MB of payload behind, §5.5). The applier writes `the payload stopped arriving` or `stopped on request` in its log, from which the Shell knows it was the network, or its own stop, and installs the same incremental package again after a while (§2, §6) instead of turning to the full bundle at once.

The full bundle (adaptive) needs nothing of its own: RAUC looks blocks up by hash in both slots anyway, so the blocks a previous, interrupted install already wrote into the target slot are not downloaded again (not tested on its own).

**Checkpoints within a patch in pieces** (format 2): when an operation is in pieces, a checkpoint may also be recorded after each piece (still every 32 MiB or every 5 seconds), with one more item, `next_piece` (checkpoint format 2; one of the old format does not read, is removed, and the install starts from the beginning). The resumed install skips the data before that piece; the part of the operation already written is not read from the payload again but read back from the target slot to compute the operation's result hash (synced before the checkpoint); every piece after is checked before it is applied as always, and at the end the operation's result hash and the whole slot are checked as always. When a piece's data does not arrive (the network gone) the checkpoint stays as before. On the host (`TestResumeMidPiece`, patches in 64 KiB pieces), with the power cut at every fourth of 121 writes and syncs, 18 of the 31 installs after a cut resumed in the middle of an operation, all coming out byte for byte the target and reading less of the payload by the part skipped; a damaged piece is refused before it is applied (`TestDamagedPieceRejected`), its blocks are not written and the checkpoint goes.

Measured (host, `TestResumeAfterPowerCut`, `TestResumeAfterNetworkLoss`): a small 24 MB image with 7 operations, an install of 93 writes and syncs, the power cut at every third of them; 20 of the 31 installs after a cut resumed from a checkpoint, and all came out byte for byte the target; in half of them the payload was a file to seek in, and what was read was the payload less the part skipped (the lost network case: 5382 of the 11445 bytes of the payload read), in the other half a stream, where the part skipped is read and thrown away.

## 6. Automatic updates

> Status: host selftest ✓ (a simulated A/B phone: the Shell checks, installs, notifies and restarts as usual, while RAUC, the slots, the network and the restart are simulated); unit tests ✓ (stopping at once when the user marks the network metered: `TestAutoInstallStopsOnMeteredWifi`, which fails on the old code; the download keeping to the address it began from: `TestInstallProxyKeepsItsNetwork`); the same case (a simulated A/B phone) passes inside the QEMU image too; automatic updates with real RAUC on the A/B disk run on QEMU on 2026-11-25 ✓ (§3), not run on a real device.

Android checks for updates in the background and downloads and installs them only on an unmetered network, with enough battery or charging, then asks the user to restart (or restarts at night); this does the same, in the Shell (`shell/updateauto.go`):

- **The switch**: 「切换自动更新」 (Switch automatic updates) in the options of 「设置 › 系统更新」 (Settings › System update) (`auto_system_update` of `settings.set`, [22](22-developer-api.md)). Off in the open-source image: a system someone built should not install updates by itself without their knowing; a product writes `"auto_system_update": true` in the `settings` of its configuration layer to have it on by default.
- **Once a day**: on the Shell's own timer, as the holiday calendar is fetched (the store's 「充电时自动更新」 (automatic updates while charging) uses an app's background job, `job.schedule`; a system update involves no app). After a failed check, or with the conditions not met, it looks again an hour later; with no new version, once installed, or after a failure for good, it checks again the next day.
- **The conditions**: on Wi-Fi that is not metered (§6.1; mobile data always counts as metered), the battery at least 50% or charging, not in a call.
- **Low priority**: RAUC installs within `rauc.service`, and `rauc install` only asks it to, so the priority is set in the service's drop-in (`phone-priority.conf`: Nice=10, CPUWeight=20, I/O best-effort at its lowest level, IOWeight=20), and an incremental package's applier, a child of its hook, runs the same way. An install the user starts runs at this priority too, since the phone stays in use while it installs. The I/O class is not idle: with steady foreground I/O (a video being recorded) idle could keep the install waiting forever; IOWeight takes effect only with BFQ or io.cost, and which I/O scheduler the device uses is **not verified**. ota-test prints these properties of rauc.service after each install, and `make yocto-ota-delta` checks them (passed on QEMU on 2026-11-15).
- **Once installed**: a notification 「系统更新已安装」 (System update installed) with 「现在重启」 (Restart now) or 「今晚」 (Tonight). With tonight, the phone restarts between 2:00 and 5:00 at night with the screen off, no call and no alarm due within an hour, the next night if that one did not work out; without a choice it does not restart, and Settings still has 「重启」 (Restart). After the restart the new slot's health check and three tries apply as always (§2).
- **A download that stops** (installs the user started and automatic ones alike): tried again after 30 seconds, 2 minutes and 8 minutes, an incremental package resuming (§5.6); before an automatic install's retry the conditions are checked again, and if they are not met it waits for the next check.
- **When the conditions go away half way** (automatic updates only; what the user started installs to the end as usual): while it installs, the Shell keeps watching the conditions: a call coming in, or the charger unplugged with the battery under half, stops it at once; the network is looked at every 30 seconds, and a metered network, or no Wi-Fi, stops it too. RAUC can neither pause nor cancel, so "stopping" is making this install fail on purpose, keeping what was written: for an incremental package the Shell creates the stop file (`/run/phone-ota-delta.stop`, the hook's `--stop` to the applier, §5.3), and the applier stops before the next operation or piece, records a checkpoint and exits; the hook fails and RAUC does not set the slot to boot next. A full bundle's download goes through a proxy of the Shell's on the loopback (`shell/updateproxy.go`: an automatic install has RAUC fetch the bundle from `http://127.0.0.1:<port>/<random>/<bundle name>`, and the proxy fetches it from the update server, ranges as they are), and stopping is the proxy closing every connection and refusing every request after: RAUC takes it for the network gone, and fails and cleans up as it does then; an applier that has not stopped within 30 seconds (an older one in an image, which does not know `--stop`) has its download cut the same way. RAUC's streaming child (the `rauc` with `RAUC_NBD_SERVER`) is not stopped directly: RAUC writes a disconnect request to its socket when it cleans up, and its main process does not ignore SIGPIPE, so stopping the child could take RAUC down too, the bundle left mounted. The update is then "paused": the state in `system.update` goes back to `idle` with `paused` (why it waits; Settings shows words like "The automatic update is paused during the call; it goes on afterwards"), the version stays offered, and the user can install it at once (what the user starts is not stopped); the Shell looks at the conditions every minute and, once they hold, installs the same package again: an incremental one resumes at its checkpoint, the full bundle's adaptive install takes the blocks already written from the slot and does not download them again.
- **Leaving the Wi-Fi, or it becoming metered**: an automatic install downloads through the proxy, and the proxy's connections to the update server all leave from the local address of its first one, that is, the Wi-Fi the conditions held on when it began (Android too ties the download to one network: the update client passes `NETWORK_ID` in the headers of `applyPayload`, and update_engine downloads over that network only). When the Wi-Fi goes, its address goes with it and no further connection can be made: RAUC fails as when the network goes away, the Shell tries again as after a lost network, and before the retry finds the phone not on Wi-Fi and pauses; the download does not go on over mobile data until the Shell next looks at the network (up to 30 seconds later). When the user changes whether a network counts as metered in 「设置 › Wi-Fi」 (Settings › Wi-Fi), or joins or forgets a network, the Shell looks at the network again at once, not 30 seconds later.
- **A half-written slot never boots**: before writing, RAUC marks the target slot bad through the boot backend (`rauc-boot set-state <slot> bad`; the slot to boot next, `slot`, stays on the good one), and calls `set-primary` only once every slot installed; both hooks remove the slot's descriptor before it is written, and the initramfs does not open a slot without one. A new system still on trial (not yet marked good) gets no automatic updates: the other slot, the one to write, is then the good slot to fall back to, `good` still points at it when RAUC marks it bad, and half written there would be no system to fall back to.
- **Not done**: that an automatic update's download does not turn to mobile data when the Wi-Fi goes is tested on the host only (a unit test: with the proxy's address gone, not a byte is fetched); how soon the kernel of a phone drops the Wi-Fi's address once it disconnects, and how long the connections left over take to fail, is **not tried**; what the user installs by hand still downloads straight from the update server, not through the proxy, whatever the network, and is never stopped (the user's decision; Android, updating by hand on mobile data, only asks first).

The selftest's simulation (`shell/update_headless.go`, the `ota` command): the A/B slots' boot state, a stand-in for `rauc install` (it downloads the bundle piece by piece with range requests, prints its progress the way RAUC does, and sets the other slot for the next start), the restart, the network the phone is on (`ota net wifi|mobile` once it is said, else the phone's own network, metered or not as in §6.1), and an update server on the machine (signing `latest.json` with a key of its own and offering 9.0.0); `ota cut` makes a download stop halfway. An automatic install downloads through the Shell's proxy, as on a phone, and stopping it cuts that: the third case sets the battery to 30%, not charging, half way through the install; the Shell stops it, Settings says 「自动更新已暂停：电量低，充电时继续」 (The automatic update is paused: the battery is low; it goes on once the phone charges), and a minute after the charger is plugged in it installs to the end; the fourth case marks the network the phone is on as metered in 「设置 › Wi-Fi」 (Settings › Wi-Fi) half way through the install, the Shell stops it at once (within 3 seconds, not 30 seconds later at its next look at the network), and a minute after it is marked not metered it installs to the end. The machine's own slots and RAUC are left alone, and `ota off` puts everything back. The real RAUC and slots are tested on the emulator (§3, §5.5).

### 6.1 Metered networks

> Status: host unit tests ✓ (`metered`, and `shell`'s `TestMeteredDetection`, `TestAutoUpdateMetered`, `TestMeterProbeAskedAgain`, `TestUnmeteredJob`, `TestUnmeteredJobStops`; `apps/store`'s `TestAutoFetchStops`); host selftest 「Wi-Fi 计费网络」 (Metered Wi-Fi) ✓ (a simulated phone hotspot whose DHCP sends `ANDROID_METERED`) and 「后台任务遇到计费网络」 (A background job meets a metered network) ✓ (the simulated Wi-Fi; the same case on QEMU's iwd **has not run yet**); the selftest of the store's background updates now joins Wi-Fi first ✓; the QEMU step for automatic updates with the real RAUC (§3: iwd's access point, nothing installed while the user marks it metered, installed once not metered) ran on 2026-11-25 ✓; asking the DHCP server **not tried on a phone**.

Android tells metered Wi-Fi networks from unmetered ones: automatically by the hint in DHCP (an Android hotspot sends `ANDROID_METERED`), or as the user chooses for each network; mobile data always counts as metered. System updates (GMS), the app store's automatic updates and background jobs that ask for an unmetered network (`JobScheduler`'s `NETWORK_TYPE_UNMETERED`) wait while on a metered one. This does the same (package `metered`, `shell/metered.go`):

- **Automatic detection**: iwd is the phone's DHCP client and does not pass on the vendor-specific information (option 43), so once the phone is on a network the Shell asks again itself: it broadcasts a DHCPREQUEST on a packet socket (RFC 2131's renewal: with the address the phone has, without a requested address or a server identifier, with the client identifier iwd uses, the hardware type and MAC, asking for option 43), and a DHCPACK whose option 43 has `ANDROID_METERED` means metered; the server just renews the lease, and iwd ignores an answer to another's transaction. It waits 1.5 seconds; without an answer the network counts as not metered for now and is asked again 5 minutes later (before, it counted so until the address changed: one lost packet, and a phone's hotspot counted as unmetered for good, an automatic update downloading on it). Addresses in 172.20.10.0/28 (an iPhone's personal hotspot) or 192.168.43.0/24 (older Android phones' and Kario's own hotspot) count as metered too, without asking. An answer is kept for the network and the address, and asked again on a new address. It needs root (a packet socket); a developer machine does not ask.
- **The user's choice**: networks saved or connected have 「按流量计费：自动检测 / 是 / 否」 (Metered: automatic / yes / no) in 「设置 › Wi-Fi」 (Settings › Wi-Fi) (switched with `m`), kept in the Shell's settings (`wifi_metered`, by network name), before automatic detection; forgetting the network removes it. The connected network says whether it counts as metered and why: 「按流量计费：手机热点」 (Metered: a phone's hotspot, as DHCP says), 「按流量计费：像是手机热点」 (Metered: looks like a hotspot, by its addresses), 「按流量计费（你的设置）」 (Metered (your choice)), 「不按流量计费（你的设置）」 (Not metered (your choice)).
- **Who waits**: automatic system updates in the background (§6, with the reason "on a metered network (<network>)"); apps' background jobs registered with `unmetered: true` ([22](22-developer-api.md) §4.7), which run only on Wi-Fi that is not metered, the Shell going by the network it looked at within the last 30 seconds (an older look starts another, off the loop); the store's automatic updates while charging are such a job; while it runs the Shell looks at the network every 2 seconds and stops it once the phone leaves unmetered Wi-Fi (`job.stop`, the run's wake ending 5 seconds later), running it again as soon as the phone is back; the store, told so, ends its background downloads and downloads again on that run ([22](22-developer-api.md) §4.7). What the user starts downloads as usual: installing a system update in Settings, a download in the store, whatever the network.
- An app's `wifi.state` has `metered_choice`, `metered` (for the connected network, the verdict) and `metered_hint` (`dhcp` or `hotspot`) on each network, and `wifi.set` with `{ssid, metered}` (`auto`, `metered`, `unmetered`) changes the choice (system apps only, [22](22-developer-api.md) §4.5).

### 7.1 Design notes: Virtual A/B, puffdiff and zucchini, FEC

This round added a few small, clear things after update_engine: patches in pieces applied as they download (update_engine too uses an operation's data as it reads it, and an operation's data is bounded); resuming in the middle of a big operation (update_engine records the hash state of the payload read so far; here every piece has its own hash, so the piece number is enough, and the part of the operation already done is read back from the target slot and hashed again, with no hash state to keep); downloading each block of the payload once (update_engine downloads its payload itself; Kario's payload is in a RAUC bundle, which the applier reads from the bundle's device); metered networks (not update_engine's business but the update client's, by whether the network is metered; here the Shell's, §6.1); patching without reading the old file into memory whole (update_engine's bspatch also reads the source partition by extents, §5.1); an automatic update's download tied to the network it began on (update_engine's `NETWORK_ID`, §6). These three are not done, with why and at what cost:

- **Virtual A/B** (Android 11 on): one copy of each partition, the update written into a snapshot (dm-snapshot's COW, compressible from Android 12 on) and merged in the background once the new system is up. It saves a slot's space (1 GB here), at the cost of no further update until the merge is done, the merge going on after a power cut, and the snapshot put together at boot (Android does it in first-stage init); Kario's slots are signed as dm-verity descriptors, and snapshots would change the initramfs's whole slot choice and rollback. On a phone with tens of GB of storage that 1 GB is not worth the complexity, so it is not done now; on a phone with little storage it is a large piece of it (an eighth of 8 GB), worth doing later: decided on 2026-11-26 and tied to the storage of the low-end T9 SKUs ([43](43-phone-partitions.md) §7.3), **not implemented**.
- **puffdiff, zucchini**: puffdiff inflates deflate-compressed files (APKs, zips) before diffing them; Kario's system slot has hardly any big deflate files (the system apps are Go programs, and apps from the store are not in the system slot), so it would not help. zucchini knows the relative jumps in executables and diffs shifted code smaller; on ARM64 it comes close to turning `BL`'s relative addresses into absolute ones first (what xz's BCJ filters do) and then running bsdiff. bsdiff's patches of relinked Go programs are already about 4–9% of the program (§5.5: about 1 MB for the 23.8 MB `kario-system`, 2.6 MB for the 28.3 MB one); how much more could be saved has to be measured on real arm64 Go programs first, **not implemented** (it would take a reversible transform on both sides, the generator and the applier, and one more operation in the payload format).
- **FEC**: Android computes dm-verity's error correction codes on the device (Reed-Solomon, about 0.8% of the partition), and a damaged block is corrected when read, an error only when it cannot be. It guards against bit flips of the storage, not tampering (the root hash does that), at the cost of one more pass and about 8 MB more written after an install. A damaged block reads as an I/O error in Kario now (§4), and a phone's storage (UFS, eMMC) has its own ECC; to be decided once real devices give numbers on damaged blocks, **not implemented**. The codes could go after the hash tree with two more items in the descriptor, leaving today's slots as they are.

## 8. A/B slots on a phone

> Status: the OnePlus 6T's A/B layout ([43](43-phone-partitions.md)) is written: RAUC's backend `rauc-abl`, `phone-abslot`'s new commands, the initramfs mounting the root by ABL's slot, the update bundles carrying the boot slot; unit tests and tests on GPT disk images ✓ ([43](43-phone-partitions.md) §6), the images built once on 2026-11-24 and never booted, **not tried on a phone**; the steps on the phone are in [39](39-oneplus-6t.md) §15.

The sections above describe the emulator's disk: the initramfs picks the slot itself and keeps its state in the state partition. A phone's bootloader has A/B slots of its own; Kario comes after it, and the rest stays as it is:

| | The emulator's disk | OnePlus 6T (A/B layout) |
|------|------|------|
| Who picks the slot | The initramfs, from `boot` in the state partition (§1) | ABL, from the GPT attributes of `boot_a` and `boot_b` |
| Root slots | `rootfs_a`, `rootfs_b` | `system_a`, `system_b` (the names the board file gives) |
| The slot's descriptor | In the state partition, written by the hook after an install | In the boot image's initramfs (`/etc/phone/rootfs.verity`); copied into `/var/lib/slots` at boot for the shell and the incremental bundles' hook |
| What an update writes | The root slot | The root slot and its boot slot (RAUC's parent and child slots): the kernel loads only modules signed by the same build |
| RAUC's backend | `rauc-boot` (the state partition) | `rauc-abl`: `phone-abslot` changes the GPT attributes, and the slots' state goes into `/var/lib/slots/boot` in the same format |
| A new slot's chances | 3 | ABL's 7 |
| A new slot failing verification | The initramfs goes back to the good slot right away | The initramfs reboots, ABL spends a try and turns to the other slot once they are spent |
| Persistent area | The state partition | `/var/lib/slots` on userdata ([43](43-phone-partitions.md) §3.4) |
| Data | The `data` partition | `userdata`, an ext4 the initramfs makes at the first boot |

The shell's system update page, the incremental bundles (whose applier reads the running slot's dm-verity device `root_<slot>`), automatic updates, staged rollouts and reports need no change: the `/var/lib/slots/boot` and `rootfs_<slot>.verity` they read are on the phone too. The boot image in an incremental bundle is whole (RAUC writes it as it is), its size **not measured**.
