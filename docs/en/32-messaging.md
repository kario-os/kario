# Messaging: phone-smsd, the hand-off with telephonyd, blocking, emergency alerts

## 0. Summary

- **SMS storage moves out of telephonyd into phone-smsd.** telephonyd only does the radio side: sending, receiving, delivery reports, cell broadcasts; smsd owns everything once a message is stored. This is Android's layering: the RIL / telephony framework receives messages, reassembles long ones and acknowledges them to the network, then hands them to TelephonyProvider (`mmssms.db`) to store.
- **Not one is lost.** Every message telephonyd receives (and every cell broadcast, every outgoing message's outcome) first goes into its own queue of unacknowledged events (on disk); once smsd has stored it and synced it to disk it acknowledges it with `sms.ack`, and only then does telephonyd let go of it; with ModemManager the copy in the modem's storage is deleted only then too. After a restart of either side, what was not acknowledged is handed over again, and smsd recognises what it already stored (§3).
- **No database.** smsd's store is an append-only log over a snapshot: each change is one line, synced; at 256 lines they are compacted into a new snapshot; a last line a crash cut short is dropped when read. Files 0600, directory 0700 (§4).
- **Only the default SMS app deletes and blocks.** As Android lets only the default SMS app write the SMS store, `sms.delete`, `sms.block` and `sms.blocked` are only for the default SMS app; that is a role (Android's `ROLE_SMS`): the system's Messages by default, which the user can give to another app with the `sms` permission in Settings › Apps › Default apps (the system asks first). Other apps with the `sms` permission can only read and send, and each message they send needs the user's confirmation (§8).
- **Emergency alerts come over everything.** Cell broadcasts are graded by channel (national, extreme, severe, AMBER, test), raise a system screen even over the lock screen, sound in audiod's own `alert` category (silent mode or not) and vibrate; the national level cannot be switched off, the others can in Settings. An alert with an area (circles, polygons) is held back only when the phone knows it is outside; one that does not know where it is shows it (§7).
- **MMS goes over the data connection.** A multimedia message is announced by a WAP push in an 8-bit SMS; smsd stores the notification, acknowledges the SMS, then fetches the m-retrieve.conf from the MMSC over the MMS access point; the shell puts the pictures in the album; outgoing ones go to the MMSC as m-send.req (§11).
- **One block list for calls and messages.** smsd keeps it (numbers, prefixes, hidden numbers, numbers not in the contacts); the shell holds a copy and declines a blocked call without ringing, logged as "blocked" (§6).
- **Numbers compare as E.164.** "138 0013 8000", "+86 138-0013-8000" and "0086 13800138000" are one number in China, "612 34 56 78" and "+34 612345678" one in Spain; foreign numbers are shown the way their country writes them (§13).

## 2. Architecture

```
 network ──► modem ──► telephonyd (C++, the radio side)
                          │ unacknowledged queue (telephony.json's pending, on disk;
                          │ with ModemManager: the copy in the modem's storage)
                          │ events sms / cb (with a key)   ▲ sms.ack {keys}
                          ▼                               │
                        phone-smsd (Go, the storage side)─┘
                          │ log + snapshot (state/smsd/)
                          │ events message / changed / alert; unnotified + notified
                          ▼
                        shell: notifications (copy code), flash dialog, emergency-alert screen,
                          │    MMS pictures into the album, blocked calls, broker (sms.*, block.*)
                          │
                          ▼
                        Messages (the default SMS app), other apps with the sms permission
```

smsd is telephonyd's second client (the other is the shell); apps reach smsd only through the broker. MMS bypasses telephonyd: smsd talks HTTP to the MMSC over the MMS access point (§11).

## 3. The hand-off: not one message lost

1. telephonyd receives a message, makes the event `{"event":"sms","key":…,"sms":{…}}`, puts it into the unacknowledged queue, writes it to disk (a temporary file, `fsync`, then a rename) and broadcasts it. With ModemManager the id is computed from the number, the SMSC timestamp and the text (FNV-1a), so the same message reported again after ModemManager restarts keeps its id and is queued once.
2. smsd subscribes to telephonyd and, each time it connects, first asks for `sms.pending`: what came while smsd was down and what it had no time to acknowledge.
3. smsd sends `sms.ack` only once it has stored the message (the log synced to disk). The ids it stored are kept in a list of the last 2000; one handed over again is acknowledged, not stored again.
4. telephonyd deletes it from the queue only on the acknowledgement; with ModemManager this is also when it calls `Messaging.Delete` on the copy in the modem's storage (a SIM has a few dozen slots, and a full one takes no new messages).
5. Outgoing messages' outcomes (`sent`, `delivered`, `failed`) and cell broadcasts go through the same acknowledgement; `sending` is smsd's own record and is not queued.
6. The messages telephonyd used to keep itself (`sms` in `telephony.json`) are taken by smsd each time it connects, with `sms.legacy`, stored, and then telephonyd is told to delete them with `sms.legacy_drop`; a crash half way is harmless: the next try skips the ids it has.

| Who restarts | Outcome |
|--------------|---------|
| smsd crashes, a message arrives meanwhile | It stays in telephonyd's queue; when smsd is back it gets it from `sms.pending`, stores and acknowledges it (selftest §10) |
| smsd crashes after storing, before acknowledging | telephonyd hands it over again; smsd recognises the id and only acknowledges |
| telephonyd restarts (simulated baseband) | The queue is read back from `telephony.json`; smsd gets it from `sms.pending` when it reconnects (selftest §10: the test hook `sim.sms` with `held` only queues the message, without an event, as if telephonyd died right after storing it; then telephonyd is killed) |
| telephonyd restarts (ModemManager) | What was not acknowledged is still in the modem's storage, listed again, with the same ids |
| The shell is not there (or not yet reconnected) | smsd stores as usual; new messages and alerts not shown yet stay on smsd's "unnotified" list, which the shell takes with `unnotified` as soon as it subscribes and confirms with `notified` once shown |
| An SMS app reads its conversations while smsd restarts (or starts before smsd at boot) | That call fails; the system's Messages does not take it for no messages: it keeps the list and the conversation it read last, and says "Messages are not available right now. They will show again by themselves." when it has read nothing yet (§9); as soon as the shell is subscribed to smsd it sends the running default SMS app and the system's Messages the `sms` event, and they read again (`TestSMSAppsHearSmsdBack`; selftest §10) |

## 4. The store

- Directory `<state>/smsd/` (0700): `snapshot.json` (0600) and `log` (0600, one change a line, with its sequence number). Reading takes the snapshot, then replays the newer lines of the log by sequence number; an unfinished last line is cut off.
- Compaction: at 256 lines in the log a new snapshot is written (temporary file, `fsync`, rename, directory sync), then the log is emptied; a crash between the two is harmless: the replay skips by sequence number what the snapshot already holds.
- Limits: 10000 messages (the oldest go), 500 alerts, 2000 received ids remembered, 200 unnotified, 256 multimedia messages waiting for their delivery reports, 500 drafts.
- Drafts: one per conversation (`sms.draft {peer, text}`, the default SMS app only; an empty `text` drops it, at most 5000 characters), stored as one change; `sms.threads` gives `draft` and `draft_at`, a conversation with a draft alone is listed too (count 0), ordered by the later of `draft_at` and its last message; the change that sends to the conversation (a new message or a scheduled one) drops the draft as well. Drafts go by the conversation's key, so they are found after a region change too.
- MMS parts: `<state>/smsd/parts/<message id>.<index>` (0600), written before the change that names them; once the shell put a picture in the album, smsd deletes its copy (`part.media`). An outgoing message's PDU waits in `outbox/` until the MMSC took it (sending again uses it). Files no message needs are removed at start.
- Conversations go by the normalised number (§13): a number whose country is known as E.164 (`+8613800138000`), a short code (10086, 95588) as its digits, a sender with letters (a company's name) case-insensitively; a group's conversation is its members' numbers, sorted, joined by commas. The region numbers written nationally are read in comes from the shell (`region`); when it changes every conversation is normalised again, and so are the ones stored before (Chinese numbers without `+86`) when read.
- Search runs in memory: the text (case-insensitive) and the number; contact names are matched by the Messages app itself (smsd does not know the contacts).
- Import (moving from an old phone, [36](36-device-switch.md) §7; the messages read over Bluetooth from the old phone's MAP too, §8): `import`, which only the Shell calls, takes `{messages: [{peer, dir, text, at, read}]}` (at most 500 at a time, `at` in Unix seconds) and stores them as one change: each goes in by its time (before the first message later than it, the others keeping their order), received ones read or unread as given, sent ones read and `sent`, all marked `imported`; received ones have their verification codes found as usual, a blocked sender's go to the blocked folder; none goes on the unnotified list, nothing is notified, one `changed` is sent. Messages without a number or text, with a direction other than `in` / `out` or an `at` not above 0, and those it has (same conversation, direction, time and text) are not stored. Restoring a backup (§4.1) goes through it too: a multimedia message (`kind: "mms"`) keeps its subject, text (at most 5000 characters) and a group's members, and a sent one with `state: "failed"` stays not sent. It returns `{ids}`, each message's new id by place (starting with `i`), empty for one not stored. `delete_imported` with `{ids}` deletes the imported ones among them (an import undone) and returns `{deleted}`.

### 4.1 Backup and restore (the XML of Android's "SMS Backup & Restore")

Most people moving from Android have a backup made by this app (SyncTech): a root `<smses>` with an `<sms>` element per SMS and an `<mms>` element per multimedia message (with the `<part>` elements of its `<parts>` and the `<addr>` elements of its `<addrs>`), everything in attributes. Kario reads and writes this format (package `smsbackup`); the file is in Files, and the user decides where it goes.

- Backup (`sms.backup`, the default SMS app only): the shell asks smsd for every message (the blocked folder too) and writes them by time, leaving out scheduled ones and those going out. An SMS gets `address`, `date` (milliseconds), `type` (1 received, 2 sent, 5 not sent), `body`, `read`, `readable_date` and `contact_name`; a multimedia message `msg_box`, `m_type` (132 received, 128 sent), `address` (the numbers joined by `~`), `sub`, one `text/plain` `part` and its `addr` elements (137 the sender, 151 the recipients; Android's `insert-address-token` for this phone's number when it is unknown). Pictures are not written (they are in the album). Line breaks are written as `&#10;`. The system first says how many messages and the file name (`sms-YYYYMMDDhhmmss.xml`, which the Android app recognises too) and saves it into Files once the user agrees; the file is not given to the app.
- Restore (`sms.restore`, the default SMS app only): the system lists the `.xml` files of Files and the user picks one; the shell reads it off its loop (it may be large), says how many messages it holds and, once agreed, hands them to smsd's `import` (§4) 500 at a time: those it has (same conversation, direction, time and text) are left out, so restoring one's own backup adds nothing; nothing is notified, received messages have their codes found and are sorted by the block list as usual. Read are received, sent and failed SMS, and the subject, the text parts and a group's members (the recipients without this phone's number) of received and sent multimedia messages; drafts, the outbox, multimedia messages with pictures alone and dates before 2000 do not count and are counted in `skipped`. smsd keeps at most 10000 messages, so restoring more drops the oldest as usual.
- Reading: a backup is untrusted input, read by a small scanner of our own rather than `encoding/xml`: a picture's base64 (`data`, megabytes perhaps) is read past without being held; the app writes emoji as two numeric references (a UTF-16 surrogate pair, like `&#55357;&#56832;`), which come out as one character; control characters are dropped instead of failing the file. At most 20000 bytes of an attribute value are kept (the rest is read past), at most 5000 characters of text, 200 of a subject, 64 bytes of a number, 20000 messages and 32 MB of text in all; a file cut short keeps what was read. It has a fuzz target (`smsbackup`: `FuzzParse`, [17](17-app-sandbox.md) §9).

## 5. Sending and delivery reports

- `sms.send` first stores the message as `sending`, then hands it to telephonyd (with smsd's id, which its later events carry); without telephonyd it is recorded as `failed` at once.
- Delivery reports: the simulated network reports `delivered` 0.5 s after sending (numbers ending in 999 fail, numbers ending in 998 are sent but never get a report); ModemManager is asked for a report when the message is created (`delivery-report-request`), and on its `DeliveryState` telephonyd reports `delivered` or `failed` by its class, nothing while the network still retries; at most 64 messages wait for a report, the oldest giving way.
- States only move forward (`sending` < `sent` < `delivered` / `failed`): late or repeated reports do not take one back; sending again (the default SMS app only, `sms.send {id}`) takes it from `failed` back to `sending`.
- A message still `sending` after 3 minutes (telephonyd went away meanwhile; ModemManager gives up after 2) is recorded as `failed` by smsd.
- The part counter (`ui.SMSSegments`, shared by the Messages app and smsd): the GSM 7-bit alphabet takes 160 characters a part, 153 when split; any character outside it (Chinese, emoji) means UCS-2, 70 / 67; smsd does not send more than 10 parts.
- A message with pictures, a subject or several recipients (commas or semicolons between them, at most 20) goes as a multimedia message (§11); Android's group messages are MMS by default too.

### 5.1 Scheduled sending

- `sms.send` with `at` (Unix seconds) schedules the message, for the default SMS app only; a time already past (by more than a minute) or more than a year ahead is refused. smsd stores it as an outgoing message with `state: "scheduled"`, `due` the moment it goes and `zone` the phone's time zone when it was picked (for display only); a multimedia message too (its PDU goes into `outbox/` first). It is in the log and the snapshot, so it survives restarts.
- When due: smsd's timer wakes at the next one's time and at least every 30 seconds, comparing with the wall clock (a clock set by hand sends by the new time); a due message goes the way of one sent again (`sending` → `sent` …), its time becomes the moment it went, and it moves to the end of its conversation. One that came due while the phone was off or smsd was not running goes as soon as smsd runs.
- Time zones: it is the moment that is scheduled, not a time on the clock face. Messages turns the date and time the user picked in the phone's current zone into Unix seconds; a phone that moves to another zone afterwards still sends it at that moment. The conversation shows it on the current zone's clock and, when the zone differs from the one it was picked in, that zone's time too ("Scheduled · 2026-11-19 20:00 (09:00 Asia/Shanghai)"); the page says so. A wall time a daylight-saving change skips is normalised by Go's `time.Date`.
- Cancelling is deleting (`sms.delete`); in the conversation a scheduled message has "Send now" (`sms.send {id}`) and "Cancel sending". The selftest makes smsd send the scheduled ones at once with `schedule.sim` (taken only with the simulated baseband). `scheduled`, read-only, answers how many scheduled messages still wait (`{scheduled}`): the selftest asks as each case begins and as it ends, and a case that leaves one behind fails ([40](40-testing.md) §2); an older smsd does not know it, and then nothing is checked.

## 6. Blocking and verification codes

- One block list for calls and messages (Android's BlockedNumberProvider), kept by smsd: numbers as their E.164 form (§13); prefixes ending in `*` (`1065*`: every number starting 1065), compared with a number's E.164 form, its national number (with and without the trunk prefix 0) and its digits as written; two switches: block hidden numbers (calls without a number: empty, or a word the network puts there such as unknown, private, anonymous), and block numbers not in the contacts (short codes and senders with a name too; the shell hands smsd the contacts' numbers, and until it did this switch blocks no message). Calls from emergency numbers are never blocked.
- Words (`block.set {word, on}`, the list's `words`) block messages only: a received SMS, an MMS notification's subject, a downloaded MMS's text, a flash message, and received messages imported or restored go to "Blocked" when their text or subject holds one of them, whoever sent them (an MMS found to hold one only once downloaded is moved there too, unnotified). Both sides are compared with letters and digits alone, lower-cased, full-width as ASCII (`ui.WordKey`), so spaces or marks between the characters (a word spelt out with spaces and asterisks) do not hide it; a word of marks alone is refused. At most 200 words of at most 40 characters; words that compare alike are one. Settings › Blocked numbers and Messages' Blocked page both add and remove them.
- A blocked number's messages go straight to the "Blocked" folder, marked read, with no notification and not on the unnotified list; an MMS notification goes there too and is not downloaded (the user can download it from "Blocked"). Messages after unblocking are as usual; the earlier ones stay in "Blocked".
- Calls: the shell holds a copy of the list (fetched again whenever smsd says it changed) and checks each incoming call first; a blocked one does not ring, raises no call screen and no missed-call notification, and is hung up (`hangup` with `blocked`); telephonyd logs it as `blocked`, which Phone shows as "Blocked".
- Who changes it: the default SMS app, the system's Phone and Settings (`block.list`, `block.set`); the older `sms.block` and `sms.blocked` stay with the default SMS app. Where: Messages' Blocked page and a conversation's "Block number"; Phone's call log menu "Block number" / "Unblock number"; Settings › Privacy and security › Blocked numbers (numbers, prefixes, the two switches).
- Verification codes: 4–8 digits (or two runs split by one space or dash, as `123 456`) near a word that announces a code, the one nearest the word winning, at most 40 characters away. Amounts (a currency sign before, 元 or decimals after), years, times (a colon), quantities and numbers longer than 8 digits are not codes. The words and marks are Chinese, English and Spanish data in `programs/smsd/otp.json`, not in the code.
- A detected code is stored with the message (`code`): the notification offers "Copy code" (the shell copies it itself, Messages need not start), and in the conversation `c` on that message copies it too; the clipboard stays as before: only the user pastes, in an input field. An app that needs a code uses `sms.otp` (§6.1).

### 6.1 Handing a verification code to an app (`sms.otp`)

An app signing the user in does not read messages: it calls `sms.otp {seconds?}` (default 120 seconds, at most 300) to start waiting, then has its server send the code. When the next message with a code arrives (smsd's `code`; only one that came after the call counts, none in "Blocked"), the shell raises a system dialog: "“App” asks for the verification code of this message: sender: text; give it the code 123456?"; with the user's "Give", the app gets `{code, from}` and nothing of any other message; with Cancel `cancelled`, without a code in time an error. A new call by the same app replaces its last (which answers `cancelled`); with several apps waiting, the foreground one goes first, else the one waiting longest. Behind a lock-screen PIN no dialog shows (a code never shows on a locked screen) and the wait goes on. An app that quits loses its wait. Like Android's SMS User Consent API: no permission, the user's yes is the consent. Sample: `examples/smslite`'s "Wait for a verification code".

## 7. Emergency alerts (cell broadcast)

| Channel (3GPP TS 23.041) | Level | Can be switched off |
|--------------------------|-------|---------------------|
| 4370, 4383 | National (`presidential`) | No |
| 4371–4372, 4384–4385; ETWS 4352–4354, 4356 | Extreme (`extreme`) | Yes, on by default |
| 4373–4378, 4386–4391, 4396–4397 | Severe (`severe`) | Yes, on by default |
| 4379, 4392 | AMBER (`amber`) | Yes, on by default |
| Others (monthly tests, exercises, operator messages, ETWS tests and so on) | Test (`test`) | Yes, off by default |

- telephonyd: the simulated network sends one with the test hook `sim.cb {channel, serial, text}`; ModemManager 1.24 (the Yocto layer's meta-openembedded wrynose has `modemmanager_1.24.2`) has `org.freedesktop.ModemManager1.Modem.CellBroadcast`: telephonyd sets the channels 4352–4359 and 4370–4400 (`SetChannels`), takes `Added` and the `Cbm` objects (`State`, `Text`, `Channel`, `MessageCode`, `Update`) and calls `Delete` once smsd acknowledged. The ModemManager side is tested against the mock ModemManager (the `cell_broadcast` case), **not verified on hardware**; modems differ in their cell broadcast support.
- smsd deduplicates: the same channel and serial number (message code + update number) within 24 hours is one alert; a new serial number (an update) is a new one. Every alert is stored, whether its level is on or not.
- The shell: when the level is on it raises the system screen `alertOverlay`: on top even over the lock screen (it stays when the lock closes dialogs), the end key does not close it, only OK or Back; the screen lights up; audiod's new `alert` category (highest priority, volume 1, sounds in silent mode too) plays the 853 Hz + 960 Hz attention signal (2 s, half a second, half a second, looping until closed); three vibrations. With the level off it is only recorded.
- Settings › Emergency alerts: one line per level, the national level reading "Always shown"; the `settings.set` keys `alert_extreme`, `alert_severe`, `alert_amber`, `alert_test`.
- Messages › Emergency alerts: the alerts received (level, text, time, channel).

### 7.1 Alert areas (geofencing)

A WEA 3.0 alert (ATIS-0700041) may carry warning area coordinates (WAC): circles (a centre and a radius) or polygons, and the longest the phone should wait for a position. telephonyd hands smsd the WAC as it came (hex; the simulated network: `sim.cb`'s `wac`; ModemManager 1.24's `Cbm` objects carry none, **not implemented**). smsd reads it as Android does (the length in two octets, little-endian, then shapes: 4 bits of type, 10 bits of length, 2 spare; a coordinate is 22 bits of latitude and 22 of longitude, a radius 20 bits in 1/64 km; `ui.ParseWAC`); one it cannot read counts as no area; every alert is stored all the same.

The rule (the shell's `alertWhere`):

| Case | Shown |
|------|-------|
| The alert has no area | Yes (by its level's switch) |
| It has one, the last fix is at most 30 minutes old and the position (with its accuracy: within the accuracy radius of the edge counts as inside) is in one of the shapes | Yes |
| It has one, the last fix is at most 30 minutes old and outside every shape | No, only recorded (the log, `AlertsOutside`) |
| It has one, and there is no fix, the last one is older than 30 minutes, or location is switched off | Yes (better shown outside than missed inside) |

The shell does not turn the location receiver on for an alert; it uses the position the apps' last fix left; the longest wait is read but not used, **not implemented**.

|------------|----------------|
| `sms.send` | `sms` permission; for a store app that is not the default SMS app the system states every message's recipient and text (and how many pictures) and sends it only once the user confirms; only the default SMS app may send again with `{id}` and schedule with `at`; `media` may only name photos the app can see |

The default SMS app is the `sms` role (`smsrole.go`): Settings › Apps › Default apps lists the system's Messages and the other apps that declare the `sms` permission; picking a store app, the system asks first ("it can then read, send, delete and block messages without asking"), picking Messages it does not; `settings.set`'s key `sms_app` (the text is the app ID). The app holding the role deletes messages, keeps the block list, sends without a confirmation per message, posts the notifications of new messages and may see the pictures of received multimedia messages (`media.grant`); the system's Messages then only reads and sends (deleting is refused). If the holder is uninstalled, the role goes back to Messages; an app installed later under the same ID has to be chosen (and agreed to) again. Sample: `examples/smslite` (the smallest store SMS app, which the selftest uses).

Arguments and results are in [22](22-developer-api.md) §4.2; apps without the `sms` permission are refused all of them (the compatibility probe checks each).

## 9. The Messages app

- Conversation list: the contact's name or the number (a group: all its members), the last message ("Me:" for sent ones, "Not sent:" for failed ones, an MMS's subject and text, "Picture" for one with only a picture), the time, the unread count; "Draft:" when it has a draft, "Scheduled:" when its last message is a scheduled one; each conversation's menu has "Delete conversation" (confirmed first; its draft goes too) and "Block number" (confirmed first). The right soft key writes a new message; the page menu: Search (`s`), Blocked (`k`), Emergency alerts (`e`), Back up to Files (`f`), Restore from Files (`r`).
- Conversation: both sides' bubbles, sent ones marked "Sending…", "Sent", "Delivered", "Not sent"; an MMS's pictures follow its bubble (image nodes `media:<id>`), a part the album does not take shows its name, type and size; one not downloaded reads "Multimedia message, downloading…" / "not downloaded" (with Download) / "expired at the operator"; in a group, a received message says who sent it; a kept flash message is marked "Flash"; a contact card in an MMS reads "Contact card: name", and OK adds it to Contacts; scheduled messages come last, reading "Scheduled · time". On a message: Resend (when it was not sent), Send now and Cancel sending (`x`, a scheduled one), Copy code (`c`), Copy text (`y`), Delete (`d`, confirmed first); the page menu: Attach a picture (`p`, the system's photo picker, at most 5), Send later (`t`), Call, Delete conversation, Block / Unblock, and Save number when the number is not in the contacts. The input starts with the conversation's draft; what was typed and not sent becomes the draft when the user leaves the conversation or the app goes to the background. Under the input, the part counter ("68 left · 1 SMS"), or "Multimedia message" with a picture attached or in a group. Contacts' "Send message" opens the conversation with that number through `message.compose`; leaving the conversation goes back to Contacts.
- New message: recipients (several numbers separated by commas make a group MMS), text, part counter, Send; shared text comes filled in; the page menu: Choose a contact (`c`, the system's contact picker; the number chosen joins the recipients), Send later (`t`). Left unsent with recipients and text, it becomes that conversation's draft.
- Send later: a date and a time (the system's date and time fields, an hour ahead to start with), a line saying which zone's clock that is and that it goes at that moment even if the phone is in another zone by then; the right soft key "Schedule".
- Search: text (an MMS's subject too), numbers and contact names, as you type.
- Blocked: the blocked numbers and prefixes (OK unblocks), the conversations from blocked numbers, and how the two switches stand; the page menu: "Block a number" (`a`, a number or a prefix ending in `*`), "Block a word" (`w`), "Block hidden numbers" (`h`), "Block numbers not in Contacts" (`u`) (the same list as Settings'); the blocked words are listed under the numbers, OK unblocks.
- Emergency alerts: the record and each alert's details.
- What smsd does not answer (while it restarts, or before it is up at boot) is not taken for nothing there: the conversation list and the open conversation keep what was read last, and with nothing read yet say "Messages are not available right now. They will show again by themselves." instead of "No messages"; Search, Blocked and Emergency alerts say the same instead of "Found (0)" or "None". Once smsd is back the shell sends the `sms` event (§3) and the pages that are open read again; nothing polls.

## 11. Multimedia messages (MMS)

> **MVP, not tried on a phone**: sending and receiving work against a fake MMSC (`mms.FakeMMSC`, in unit tests, the selftest and the simulated baseband); a real operator's MMSC, MMS access point and data bearer have not been tried.

```
operator ──WAP push (8-bit SMS, port 2948)──► telephonyd ──sms {data}──► smsd
                                                             │ stores the "MMS notification" (to download), acknowledges the SMS
                                                             │ GET content-location ──► MMSC (through the MMS proxy)
                                                             │ ◄── m-retrieve.conf
                                                             │ keeps the text and parts, tells the shell; POST m-notifyresp.ind
                                                             ▼
                                        shell: pictures into the album (part / part.media), notification, conversation
out: Messages sms.send {media} ─► the shell reads the photos ─► smsd: scaling, m-send.req ──POST──► MMSC ◄── m-send.conf
delivery report: MMSC ──WAP push m-delivery.ind──► smsd marks "Delivered" by the Message-ID
```

- **Receiving**: telephonyd hands over an 8-bit message's user data as it came (hex; the simulated network: `sim.sms`'s `data`; ModemManager: the SMS's `Data` property, **not verified**). smsd reads the WSP push (also with a user data header still in front); a push of `application/vnd.wap.mms-message` (or for the MMS user agent's application ID) carries an MMS PDU: an m-notification.ind is stored as a multimedia message to download (from the notification's From, not the operator's gateway that sent the push), and the SMS acknowledged once stored; an m-delivery.ind is a delivery report. `application/vnd.wap.sic` (a service indication) is stored as an ordinary message: its text and link, which the system never opens by itself. Other data messages go (no app listens on data ports).
- **Downloading**: in the background, each when it is due (`mmsLoop`: at once for a new notification, otherwise every 30 seconds); a `GET` of the notification's location, at most 2 MB, no redirects followed, 2 minutes at most; the parts in their SMIL order: the text parts make the text (character sets: UTF-8, GBK, GB18030, Big5, UCS-2 / UTF-16 and others), the others become part files; then an m-notifyresp.ind (Retrieved) is `POST`ed to the MMSC. A failure is tried again after 30 seconds, 2 minutes and 10 minutes; after the fourth the message reads "not downloaded" and is notified, and Messages' Download fetches it again (`sms.download`); one past the notification's expiry reads "expired".
- **Who can make the phone fetch**: anyone can send a notification (a forged WAP push). Through the operator's MMS proxy, the operator's network decides what is reachable; without a proxy (only the selftest's fake MMSC) only locations on the MMSC's own host are fetched: one SMS must not make the phone connect anywhere it says.
- **Parts and the album**: parts are kept by smsd first (§4); on the "downloaded" event the shell puts PNG, JPEG and GIF (the first frame, as PNG) pictures into the album (named "MMS from …"), tells smsd their `media:<id>`, and smsd deletes its copy; parts the album does not take (audio, video, vCard) stay with smsd, and Messages shows their name, type and size; a vCard (`text/vcard`, `text/x-vcard` or `.vcf`) reads "Contact card: name", and "Add to Contacts" has the system read its contacts, say how many are new and add them once the user agrees (`sms.vcard`, the way of a vCard imported from Files). Deleting the message leaves the album's picture. Messages in the blocked folder do not go to the album.
- **Groups**: a received message's To and Cc plus its sender, without this phone's number (telephonyd's status `own`; without it, a single recipient is this phone), more than one left makes a group: `members` are those numbers, the conversation their normalised numbers sorted and joined; replying in a group sends to everyone. Outgoing: more than one recipient makes a group.
- **Sending**: the shell reads the photos the app gives (only ones it can see, `media:<id>`) and hands them to smsd; smsd makes each picture fit (the longer side 1280, JPEG quality stepping down, the whole message at most 300 KB), writes the m-send.req (SMIL, pictures, UTF-8 text, multipart/related, a delivery report asked for), stores it in `outbox/` and `POST`s it to the MMSC; an OK m-send.conf marks it "Sent" and keeps its Message-ID (the last 256), anything else "Not sent", and sending again uses the stored PDU.
- **The MMS access point** (`apn.go`): telephonyd's `apn.mms` first: the APN of type mms its APN database (with the user's changes) has for the SIM, answered as the database writes an APN (smsd reads only `apn`, `mmsc`, `mms_proxy` and `mms_port`, `svc.MMSAPN`); without it, or without an `mmsc`, the published settings of the SIM's operator: China Mobile `http://mmsc.monternet.com`, proxy `10.0.0.172:80` (cmwap); China Unicom `http://mmsc.myuni.com.cn`, `10.0.0.172:80` (3gwap); China Telecom `http://mmsc.vnet.mobi`, `10.0.0.200:80` (ctwap)—by MCC 460 and the MNC (when telephonyd's status has `sim_mnc`), else by the operator's name. The simulated baseband ignores what the simulated SIM's APNs say: it uses the selftest's fake MMSC when given one (`mms.sim`, taken only while telephonyd runs the simulated baseband), else one smsd starts on a loopback port of its own process (`mms.FakeMMSC`), which takes what is sent and, 0.5 s later, as the simulated network does for SMS, sends a delivery report's WAP push for each recipient through telephonyd's `sim.sms` (from `1065800000`). Where the operator keeps MMS on an access point of its own (China Mobile's cmwap beside the internet's cmnet), MMS needs a second PDP context: before each fetch, send and m-notifyresp.ind smsd asks telephonyd's `mms.connect`, telephonyd connects a second bearer on the MMS access point (held three minutes from each call) and answers with its interface and addresses; the Shell gives that interface its address and a routing table of its own, and a policy rule hands only what leaves from that address to that table ([04](04-ui-language-telephonyd.md), Shell side); smsd waits for the address on the interface (ten seconds at most), and its connections and DNS queries (to the bearer's DNS servers) leave from that address, so they reach the proxy over the MMS bearer while the phone's other traffic is unaffected; transfers at the same time share one, and the last to finish lets it go with `mms.disconnect`. Where the MMS access point is the internet one, telephonyd answers `shared` and smsd reaches the proxy over whatever route the phone has, as it does with the simulated modem, the selftest's fake MMSC, a telephonyd without the method or no telephonyd. With mobile data off, roaming where a switch says no, or a bearer that does not connect, the transfer fails and is tried again on the download's schedule. Unit tests (a fake telephonyd, the connection leaving from 127.0.0.2) and the bearer on the simulated ModemManager ✓, **not tried on a phone**: whether the second bearer connects on a live network (ModemManager bringing up several bearers over Qualcomm's QRTR) and whether the MMSC takes requests from it are to be checked on the 6T ([39](39-oneplus-6t.md) §14.6).
- Everything parsed is untrusted input: WSP pushes, MMS PDUs (headers, multipart bodies, at most 64 parts, 64 recipients, 256 headers), SMIL (at most 64 KB), service indications (WBXML); each has a fuzz target ([17](17-app-sandbox.md) §9).

## 12. Flash messages (class 0)

- telephonyd reports a message's class (the simulated network: `sim.sms`'s `class`; ModemManager: the SMS's `Class` property, **not verified**).
- smsd does not store a class 0 message: it holds it in memory (at most 20) and hands it to the shell (the `flash` event; `unnotified`'s `flash` while the shell is not subscribed); the shell raises a system dialog (over the lock screen too, which does not close it; the screen lights up, one vibration) titled "Flash message from …": OK keeps it, Back closes it. telephonyd is told to let it go only once the shell showed it (`notified`): a flash message that arrives while the shell is away or smsd crashes is not lost, it shows again.
- Keeping it (`flash.save`) stores it in the inbox, read, marked `flash`; Messages marks it "Flash". Closed, it is gone.
- A blocked sender's class 0 message goes to "Blocked" like any other.

## 13. Number normalisation (E.164)

- Package `phonenum`: compact libphonenumber-style metadata (`phonenum/metadata.json`, written by us from ITU-T E.164, E.212 and the national numbering plans): each region's country code, mobile country codes (MCC), international prefixes (00, 011, 0011, 810 …), national (trunk) prefixes (0, 1, 8, Mexico's 01 / 044 / 045 …), national number lengths and a few display patterns. It covers the regions of the offered languages (mainland China, Hong Kong, Macao, Taiwan, 21 Spanish-speaking countries and territories) and the US, Canada, the UK, Ireland, the main European countries, Russia, Kazakhstan, Turkey, Japan, Korea, South-East Asia, India, Australia and New Zealand, the Gulf, South Africa, Egypt and Nigeria: 62 in all; other countries' numbers are read by their country code alone (ITU's country codes are prefix-free).
- Reading: a number with `+` or the region's international prefix by its country code; a national one in the region, its national prefix dropped (China's `010 1234 5678` → `+861012345678`), valid when its length is one the country uses; a national prefix written after the country code by mistake (`+44 (0)20 …`, `+44 020 …`) dropped; Mexico's old mobile `1` and Argentina's national mobile `15` (the international `9`) rewritten by rule.
- Comparing (`phonenum.Key`, `ui.NumberKey`): valid numbers as E.164; a short code of the region's country (10086, 911) as its digits, so `10086` and `+8610086` are one; another country's invalid number with its country code; senders with letters case-insensitively. Conversations, the contacts (the shell's index) and the block list use it.
- The region: the shell's (Settings › Region, by default the SIM's country, [11](11-platform-architecture.md)); the shell makes it its own process's default, tells smsd (`region`), and app processes get it in `PHONE_REGION`. When it changes, the contacts' index and smsd's conversations and block list are normalised again.
- Display (`phonenum.Display`, `ui.NumberText`): a number written with a country code (as networks send senders) is shown the region's way: its own numbers in the national form (`+8613800138000` → `138 0013 8000`, `+12015550123` in the US → `(201) 555-0123`), foreign ones grouped after the country code (`+34 612 34 56 78`); numbers written nationally, short codes and names as written.
