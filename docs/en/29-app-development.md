# App development: a TypeScript framework and the system middleware

> Status: **P1–P4 are done on the developer machine, P5 on the developer machine** (§5.1–§5.3): the engine and runtime, the declarative framework KarioUI, the runtime under Node, the `kario` command line (`new`, `build`, `run`, `test`, `package`, `publish`, `device`), the calculator rewritten in KarioUI (it replaced the Go one), the Kario Studio extension, the interface and review guidelines ([33](33-app-guidelines.md)), a tutorial ([34](34-app-tutorial.md)); unit tests and the selftest pass on the developer machine, and the whole selftest passes on QEMU (case counts in "Current verification baseline" in 57 (internal document); the TypeScript calculator, the KarioUI sample, native modules, mini-programs and developing against the device among them); **not on a real phone**. Privacy labels ([33](33-app-guidelines.md) §3) are done, and `kario publish` has been run against the official store backend on the developer machine. Native modules (P5, §5.3) are done on the developer machine: the C interface, loading and refusing in kario-jsrt, packaging and review, loading under Node, a sample and measurements; measured on QEMU as well (§5.3), **not on a real phone**. Developing against a phone (`kario device`: installing, logs, reloading and restarting over a trusted cable, §3), precompiling store TypeScript apps to bytecode on the device (§5.1) and a selftest step timing TypeScript against Go apps (§5.1) are done on the developer machine, unit tests and selftest passing, and pass on QEMU too (the case over real SSH, bytecode on the device, start times, §5.1); **not on a real phone**. The guidelines have do and don't screenshots (made by a script), the tutorial covers push and background jobs, and the developer documentation can be read on the developer portal (not open source; §4); moving mini-programs onto the same engine is done on the developer machine (§5.4), and the mini-program selftest cases pass on QEMU. Debugging on the device (breakpoints (with conditions and hit counts), logpoints, function breakpoints, stepping, the call stack, variables, evaluating in a frame, `debugger` statements, pausing on uncaught exceptions, attaching to a running app without restarting it, over the developer link and from Kario Studio, §5.5) and symbol files (`kario package` writes the source map into a file of its own, never into the package, and the store symbolizes crash reports with it for the developer, §5.6) are done on the developer machine, unit tests passing; **not on a real phone**. In 2026-11 the main language for apps was changed to TypeScript, replacing the earlier Swift plan. How to write apps today: [34](34-app-tutorial.md) and [22](22-developer-api.md); this document is the route and how far it has come.

## 0. Conclusion

- **The middleware already exists; it now becomes the only way in.** The Shell's broker, the system services (audio, media, keys, push, telephony, input method) and the phone.Ui protocol together are the Kario runtime: apps do not get the devices, the system draws their UI, and every capability is requested through it (permissions, purposes, sandbox, audit, [17](17-app-sandbox.md)). A TypeScript app sees only the `kario.*` interfaces: no file system, network sockets or processes. That is stricter than Android's Java layer, which still has a way around it in JNI.
- **The main language for apps is TypeScript**, with the declarative framework KarioUI on top, written the way SwiftUI and HarmonyOS's ArkUI are (the UI updates itself when the state changes). On the device the QuickJS-ng engine (MIT, a few hundred KB) runs precompiled bytecode; on the developer machine the same code runs in Node.js, and VS Code's built-in JS debugger sets breakpoints in it directly.
- **The tools are just one VS Code / Cursor extension** plus a `kario` command line (written in Go, with esbuild built in to compile TypeScript, so packaging does not need Node installed).
- **TypeScript is the recommended way, not the only one**: big apps such as WeChat and Alipay need not be rewritten in TypeScript. WeChat on Android is already Java / Kotlin UI on top of a lot of C++ (the Mars network library, the WCDB database, audio and video codecs, the mini-program engine). Kario gives them two ways: TypeScript for the UI with the performance-critical parts as **native modules** (a C interface, like HarmonyOS's NAPI or React Native's TurboModules, P5: done on the developer machine, **not on a real phone**, §5.3); or the whole app in C / C++ / Rust / Go, speaking the phone.Ui protocol directly (possible today, `sdk/c`, the hello-cpp sample). Both run in the same process sandbox and reach capabilities only through the middleware; native code only means one more review step.
- Go stays for the system services and the existing system apps, Rust / C++ for the renderer and whatever needs speed; mini-programs run on the same engine too (§5.4).
- Learning from Apple means learning its way of "one company setting the whole tool chain, the guidelines and the review standard", not its language.

## 2. Why TypeScript

- **The most people**: TS / JS developers are the largest group in China, and people who have written WeChat mini-programs are ready-made (our mini-programs are TS already); HarmonyOS's ArkTS has shown this route works on phones.
- **The tools are there**: TypeScript's completion, navigation and diagnostics come with VS Code, given the type definitions (`@kario/sdk`); so does the debugger. One extension installs every tool, with no 1 GB Swift tool chain to install as well.
- **Security is easier to argue**: two layers of sandbox. The engine has only `kario.*` (no `fs`, `net`, `child_process`), and outside the process it is still today's sandbox (namespaces, seccomp, Landlock, the per-app firewall). An app that is TypeScript only brings no native code, so review looks only at the JS and the manifest; an app with native modules (P5, §5.3) is reviewed as a native app, every version of it, in the same sandbox.
- **It fits the protocol**: KarioUI does no layout of its own — the UI is semantic nodes the system draws — so it is simpler than both SwiftUI and ArkUI: view functions evaluate to a node tree, which is compared with the previous one, and only the changes are sent (the protocol already has `Update`, the renderer incremental frames).
- The engines for the device that were compared:

| Engine | Size | Memory per app | Start | Debugging | Licence |
|------|------|----------------|------|------|------|
| QuickJS-ng | about 1 MB | from 1–2 MB | fast (precompiled bytecode) | on the device: Kario's debugger patch to the engine (breakpoints, stepping, stack, variables, §5.5); on the developer machine debug in Node instead | MIT |
| Hermes | about 3 MB | a few MB | very fast (bytecode, used by React Native) | Chrome DevTools protocol | MIT |
| V8 | over 10 MB | over 10 MB per instance | fast (JIT) | complete | BSD |
| goja (the mini-programs' engine before, replaced) | built into the Go program | follows the Go program | parses the source | none | MIT |

  QuickJS-ng first: the smallest, easy to bring into Yocto, and a 2 GB phone can hold dozens of apps with it; switch to Hermes if measurements show it is too slow. V8 is too heavy.

A KarioUI app looks like this (the system's calculator, `apps/calc/src/main.ts`, with the key tables left out; [34](34-app-tutorial.md) goes step by step):

```ts
import { Text, Tile, act, app, page, state, tr } from "@kario/ui";
import { empty, press, type Calc } from "./calc";

const calc = state<Calc>(empty, { save: "calc" });
const key = (k: string) => calc.set(press(calc.value, k));

const Main = page("calc", () => ({
  title: tr("Calculator"),
  columns: 4,
  layout: "bottom",
  focus: "k:=",
  body: [
    Text(calc.value.expr || "0", { style: "display" }),
    status(),
    KEYS.map((k) => Tile(k, { id: "k:" + k, onOk: act("press", k, () => key(k)) })),
  ],
  actions: [act("clear", tr("Clear"), () => key("C"), { key: "C" })],
}));

app(Main);
```

- The runtime itself: `kario-jsrt` is 1.2 MB stripped (x86-64, `-O3`, the engine linked in statically), one copy shared by every TypeScript app; each Go app carries its own runtime (notes' program is 2.5 MB). A TypeScript app's Pss is small because libc's and `kario-jsrt`'s code pages are shared between processes, while a static Go program uses its own alone.
- Optimised for size (`-Os`, `CMAKE_BUILD_TYPE=MinSizeRel`): `kario-jsrt` is 0.68 MB, hello-ts starts as fast (2.2 ms / 1.7 ms) with 0.9 MB Pss; only a large bundle's source parses more slowly (294 KB: 52 ms, bytecode 7.0 ms). Which one the device gets waits for numbers from a real phone (QEMU is TCG emulation, its timings say nothing about a phone); the Yocto recipes use their default compiler flags for now.
- In the real Shell (the memory report at the end of the selftest, with the sandbox, development build): `kario-jsrt` running hello-ts 1.3 MB PSS (0.3 MB private dirty), `phone-app-calc` 4.5 MB.
- A small app's source parses in under 1 ms; bytecode pays off from bundles of a few hundred KB: 294 KB go from 42 ms to 6.7 ms, with half the memory (no parser structures left behind). Bytecode is 1.5–1.9 times the size of the source and does not resist a hostile writer, so packages may not carry it: the system image's is compiled at build time (on the developer machine with `build/jsrt/kario-jsrt`; in Yocto with the build host's `kario-jsrt-native`: the same QuickJS writes the same bytecode for x86-64 and arm64, and the runtime checks the engine version before it uses any. Yocto used to have no such runtime, so the image's calculator and hello-ts ran their source, which the start-time step on the emulator showed) and a store app's by the system on the device after installation ("Store apps' bytecode" above); neither is the developer's.

### 5.3 P5: native modules

Done on the developer machine; the unit tests and the selftest pass. The selftest and the measurement on QEMU (the completion criterion) are done (the table below); **not on a real phone**. TypeScript for the interface and the logic; the slow parts (codecs, image processing, cryptography, databases, an app's own network protocol) written in C, C++ or Rust as shared libraries, signed with the package, which the JS calls in the same process. How to write one: [22](22-developer-api.md) §9.3. Four things came later (the table's last four rows): wrappers for C++ and Rust, sealing executable memory once the modules are loaded, symbolized native stacks, and one package carrying several architectures with the store thinning it per device; these four are tested on the developer machine (x86_64); on QEMU only sealing has run, with the "native modules" case (the filter goes on on arm64, the runtime does not run the app if it cannot, and the module works; the sealed calls are not tested one by one on arm64), the other three are **not run** on QEMU, and none is **on a real phone**.

| Aspect | How (what differs from the earlier design comes after the table) |
|------|------|
| Interface | `sdk/c/include/kario_native.h`, versioned (1.0): the library exports `kario_native_abi` and `kario_native_init` (`KARIO_NATIVE_MODULE`); the runtime hands `init` a table of functions (`kario_api`, starting with its own size, later minor versions only appending), through which the module registers its names, reads its arguments and sets its results. A module links nothing of the runtime and never touches a QuickJS object or a `JSValue`: QuickJS-ng's C interface changes between versions (0.18's `JS_NewArrayBuffer` takes a realloc callback and a maximum length, no longer QuickJS's original signature), `JSValue`'s layout follows the engine's build options, and a signed package has to keep working after a system update brings a new engine; it is also why the same `.so` loads in Node (Developer machine, below), and a move to Hermes would need no rebuilt modules. The price: one call through the table per argument, values only numbers, booleans, strings, bytes and JSON, and native code never calls into JavaScript |
| The JS side | `import { blur } from "native:imgproc"`: an ordinary ES module whose names are the module's, plus every module's own `on(event, handler)`; `kario build` leaves `native:*` to the runtime; to fall back, catch the error of `await import("native:…")`; the developer writes the types with `declare module` |
| Threads | A plain function runs synchronously on the engine's thread; a `KARIO_ASYNC` one on one of `kario-jsrt`'s worker threads (at most 4 per app, started as needed, more calls wait), its result coming back through an eventfd that the message loop polls with the protocol's socket, the Promise settled on the engine's thread; the module's own threads can only `emit` (copied, at most 1024 queued, through the same eventfd) to the module's `on` handlers. Processes and threads are still the cgroup's 128, CPU still the cgroup's |
| Memory | A synchronous call lends the C code JavaScript's memory itself (changed in place, nothing copied); an asynchronous call gets a copy (JavaScript runs on meanwhile); the result's bytes are allocated by the runtime and become the `ArrayBuffer` without another copy. Modules are never unloaded |
| Package and manifest | The manifest's `"native": ["imgproc"]`, the library at `lib/<arch>/imgproc.so`, the architectures `arm64` and `x86_64`, mode 0644; `jsrt.Check` (the same for the installer, the store and `kario build`) checks the names, the places and the ELF (class, byte order, machine, shared library, both entry points, the interface's version), and refuses any other file under `lib/`, ELF anywhere else in the package, and a library that asks for an executable stack (Sealing executable memory, below); the installer wants its own architecture, the store `arm64`, and so does `kario package` (`-arch arm64,x86_64` says which go in, each of them required); a package may carry several architectures, and the store sends each device its own only (Thinning, below) |
| Loading and refusing | `kario-jsrt` (`jsrt/src/native.c`): a valid name, declared in the manifest, inside the package after `realpath` (no symbolic links, no file outside it), a regular file, an ELF of this machine without an executable stack; then `dlopen` (`RTLD_NOW`), the interface's version, `init`; each refusal comes with a sentence saying why (unit tests cover each, with the same messages under Node). The modules the manifest declares all load before the app's code runs, in the manifest's order (`init` runs then); one that does not load has its reason kept, and importing it throws that sentence (a static import still keeps the app from starting, `import()` can still catch it); under Node a module still loads at its import |
| Sandbox and review | The same process, the same sandbox, capabilities only through `kario.*` as before: native code can do no more than an app written with `sdk/c` today (hello-cpp). Every version of an app with `native` goes to the human review, as a native app (33 §2.2); the install dialog says it brings native code and names the modules, so do the store's Details page and the catalogue (`native`); an update that brings new native modules is not installed in the background |
| Developer machine | Both ways work: `kario run` (Node by default) and `kario test` load the same `.so` through `kario-native.node` (`sdk/ts/node/native.c`, Node-API; Node-API is a stable C interface of the node program, its functions are declared there and no Node headers are needed; `kario` compiles it with this machine's C compiler, cached by the sources' digest; it also reads the app's socket for Node, without which a reply's files do not arrive, so `kario run` and `kario test` always build it when the machine has a C compiler), and the TypeScript still stops at breakpoints in VS Code; `kario run -engine jsrt` runs on kario-jsrt, as on the device, with gdb attached for the C code. The trade-off: under Node the TypeScript can be debugged, but V8's JIT makes it much faster (table below), so performance and crash lines are measured on kario-jsrt; under Node a crash in native code leaves no stack (V8 keeps SIGSEGV for itself), executable memory is not sealed (V8 makes machine code all along), and there is no sandbox |
| Building | `kario build` compiles no C: developers build with their own tools (`cc` here, a cross compiler or the SDK Yocto exports for phones) into the project's `native/<arch>/` (`-native DIR` for another place); `kario build` notes a missing `arm64` |
| Device | The `phone-fw` recipe compiles the sample's module with the target's `${CC}`, and `scripts/stage.sh` puts the sample with `lib/arm64/imgproc.so` into `share/phone/examples/imgproc` (a package source, like examples/notes); the selftest case "native modules" signs it with the development store, installs it from the store, compares the two, and prints the numbers of the app's log as a `PHONE-APP-LOG` line; `phone-capi` installs `kario_native.h`, and `sdk/c`'s CMake now puts `kario_native.hpp` into the `-dev` package too (no image rebuilt since, **not on a real phone**) |

| Sealing executable memory | Once the modules are loaded and before the app's code runs, `kario-jsrt` installs a seccomp filter on every thread (`SECCOMP_FILTER_FLAG_TSYNC`; it stacks on the filter of the Shell's sandbox, `sandbox/`, and each minds its own): `mmap`, `mprotect` and `pkey_mprotect` with `PROT_EXEC`, `shmat` with `SHM_EXEC`, `remap_file_pages`, `personality` with `READ_IMPLIES_EXEC`, `execve` and `execveat` (a memfd or a downloaded file would be code from outside the package) all return `EPERM`, and the app runs on; on x86_64 every x32 system call is refused. glibc's `dlopen` fails too once sealed, hence all modules load first, with the libraries they link. | Crashes and stacks | When an app with native modules gets a fatal signal (SIGSEGV, SIGBUS, SIGILL, SIGFPE, SIGABRT), the handler, on an alternate signal stack (one for the engine's thread and one for each worker), writes to the log: the module and the function (or "a thread of its own"), the signal and the address, a line for each frame (the library it is in, the offset into the library's file, the build-id; at most 48 frames) and a closing line; then the app dies of that signal as before. | Thinning | A package may carry `lib/arm64/` and `lib/x86_64/`. Unit tests in `pkg` (`TestThin`) and `appstore` (`TestThinnedDownload`); no selftest case has a package with both architectures, **not run** on QEMU |

What differs from the earlier design: the JS side is the ES module `native:imgproc` instead of `native("imgproc")` (checked statically, tree-shaken, easy to type); the library is `lib/<arch>/<name>.so` instead of `native/<arch>/lib<name>.so`, the architecture called `arm64` rather than `aarch64` (as Apple and Android name it); the module gets a table of functions instead of calling symbols the runtime exports (`kario-jsrt` is linked with `-Wl,--gc-sections` and exports none, and the same library has to go into Node too); booleans, `emit` and `on` (results from a module's own threads back in JS) were added; loading under Node is done now, not "later"; in kario-jsrt modules no longer load at their first `import` but all as the app starts, so executable memory can be sealed afterwards (sealed, `dlopen` no longer works).

### 5.4 P4: mini-programs on kario-jsrt

Done on the developer machine (unit tests and the 5 selftest cases of mini-programs pass); on QEMU the 5 mini-program cases pass too, with no "running it in the host's sandbox only" fallback in the log; the Landlock layer and the 64 MB limit per runtime were not looked at one by one on QEMU; **not on a real phone**. Mini-programs used to run on goja (a JS engine written in Go) inside the host's process; now they run on the engine of TypeScript apps, kario-jsrt (QuickJS-ng 0.18), and the three built-in mini-programs and the signed sample did not change a line.

Not done yet:
- A mini-program starts from source every time (`--no-bytecode`): QuickJS's bytecode does not resist a hostile writer, so only the system compiles it (§5.2), and the host does not compile mini-programs; they are small and parse in under 1 ms, **not implemented** and not needed for now.
- QuickJS-ng's InternalErrors (out of memory) cannot be caught in JavaScript; the host recognises them on the runtime's stderr and says so. kario-jsrt's own behaviour here (the same for TypeScript apps) is unchanged. A failed storage write no longer throws (it is written in the background, said only in the log, and `flush()` rejects); `setStorage` throws only past the quota.
- On SIGTERM (the Shell stopping it at shutdown or a language change) the host stops its programs first and waits for the storage writes under way (at most 5 s; the Shell gives each app 3 s, `stopGrace`) before it exits (`TestTerminatedHostLetsRuntimesSave`). When the host is killed with SIGKILL, its runtimes are killed with it (`Pdeathsig`), losing a write still under way, the file keeping its last whole version.
- A closed mini-program stays 5 minutes, at most 3 of them in 32 MB together (the row "Kept after closing" above): setting these by how short the system is of memory is **not implemented** (the system gives apps no memory pressure event; when the host itself is ended in the background, the runtimes it keeps end with it).
- goja stays in the repository: the Shell draws Mermaid diagrams with it (`shell/mermaid.go`), so the dependency cannot go.

### 5.5 Debugging on the device

Done on the developer machine, unit tests passing (end of this section); **not on a real phone**; **not run** on QEMU (no selftest case: it needs a debugger on the computer's side). QuickJS-ng 0.18 has no debugger protocol; what the engine has ready is an interrupt callback (`JS_SetInterruptHandler`, called about once every ten thousand jumps or calls: no breakpoints or steps with that), a table from pc to line and column (`pc2line`, recording only the positions of calls, property accesses, operators and throws) and the chain of stack frames (`JSStackFrame`, internal, not exported); `debugger` statements are skipped. The quickjs-debugger line (koush/quickjs) calls a check before every instruction in the interpreter loop, caches breakpoints by function, speaks its own protocol over TCP and has a VS Code extension turn it into DAP; this follows the same idea with a smaller patch, costs an app that is not being debugged not one more instruction, and goes over the developer link that is there already.

| Part | How |
|------|-----|
| The engine patch | `yocto/meta-phone/recipes-phone/quickjs/files/kario-debugger.patch` (MIT, as QuickJS-ng; `make jsrt` and Yocto's quickjs recipe apply the same file): bytecode frames entered once `JS_SetDebugHandler` has set a handler switch to a second dispatch table that runs every instruction through the handler (without one, the table is the usual one); a new opcode `OP_debugger`; a thrown exception calls the handler once before the stack unwinds, saying whether a try on the stack catches it (its own frame by the catch offsets on its stack, the frames below by the try ranges in their bytecode, up to an async function, whose exception rejects its promise); functions that read and write frames: their count, positions, line tables, arguments and locals, closure variables, setting a variable; code compiled while a handler is set records every statement's position (otherwise only variable reads', calls', properties', operators' and throws'), and so does code compiled without one once `JS_SetDebugPositions` is on (an app a debugger may attach to later). **Not implemented**:
- The end-to-end test in the editor (§5.2's "Kario Studio" above) debugs on a fake phone (`cmd/kario`'s `TestE2EPhone`: the real `kario dap`, `phone-dev` and kario-jsrt, a fake Shell); debugging against a real Shell on the developer machine or the emulator, a selftest case on QEMU and a real phone are **not done**. A breakpoint in the middle of an expression of several lines (a line inside an object or array literal) may report the stop on the next line (the line event goes by the first instruction with a position on that line; not changed here).
- Attaching works only with a process this Shell started: an app a restarted Shell took over has no socket to attach through, and attach restarts it under the debugger (back on its pages through the tombstone).
- Locals are the whole function's (at run time QuickJS does not know which block scope is in force where it stands): a block's variables still show after the block, those not initialized yet do not, and of two with the same name the inner one shows.
- Closure variables are only the outer variables this function uses (QuickJS captures only those), so other variables of the module's top level are not visible from other functions; `this` is there only when the function uses it.
- Whether an exception is "uncaught": any not caught by a try in an async function counts (it rejects a promise, and whether someone `catch`es it later is not predicted), one native code catches does not; Node judges more finely.
- A getter is read when the user opens it ("(...)", calling the app's code with the object as `this`, as under Node; a class's getters on the prototype are listed on the object); the entries of Maps, Sets and arrays come in the pages the editor asks for (`indexedVariables`, past 500 entries too), the other properties apart. A Proxy's traps and `Symbol`-keyed properties are not listed.
- Function breakpoints go by the name only: a dotted name by its last part (any function of that name), stopping as the function is entered, at the function's first line; hit counts start again when a file's breakpoints are set again; a logpoint's `{}` pair by braces, with no escapes.
- Data breakpoints, restarting a frame and stepping into a native module's C code (gdb for C code, §5.3) are not there.
- Conditions, a logpoint's expressions, evaluations and a variable's new value are written in TypeScript: `kario dap` strips the types first with esbuild (`as`, `<T>`, `!`, `satisfies`), then gives a variable esbuild renamed in the bundle (a suffix added for a clash of names, such as `count2`) its new name (esbuild's `Define`, which replaces only names the expression does not declare itself), and a frame's variables show the source's names too (the new name stays when the source's is taken). The renames come from the source map's `names` and the built `main.js`, by source file: a name renamed two ways in one file is left as it is; a function breakpoint's condition is in no known file, so only its types are stripped. What esbuild cannot read goes to the phone as it is, which says what is wrong.

### 5.6 Symbol files and crash reports at the store

Done on the developer machine, unit tests and the portal's browser test passing (end of this section); **not on a real phone**. The `main.js` running on phones is minified, and the stacks in crash reports are its lines and columns; now `kario package` writes the source map into a file of its own, and the store maps the stacks back to the TypeScript for the developer once it has it.

| Step | How |
|------|-----|
| `kario package` | The module's source map (external, no link left in `main.js`, `sources` relative to the project's directory: `src/main.ts`, `kario-sdk:@kario/ui`) goes into the symbol file beside the package, `<package name>.phonesym` (`-symbols` puts it elsewhere, `-` writes none), never into the package; packaging a directory built by `kario build -sourcemap` takes its map out into the symbol file too. A symbol file (`jsrt.SymbolFile`) is a zip: `symbols.json` (the app, the version, the package's SHA-256, the module and its SHA-256), `main.js.map`, `main.js` itself (minified, as in the package, its digest checked when read; a stack's functions get their names in the source through it, "`kario symbolize`" below), and optionally `lib/<arch>/<name>.so` (unstripped libraries given with `-native-symbols DIR`, whose build-ids must be those in the package) |
| `kario publish` | Once the package is with the review, the symbol file follows (the `.phonesym` beside it, or `-symbols`): `POST /v1/symbols/<app>/<version>`, signed with the developer's key (`-key`) over `phone-symbols/1\|<name>\|<time>\|<app>\|<version>\|<the symbol file's SHA-256>` (`pkg.SymbolsMsg`). Another package's symbol file is refused before anything is sent; a store that takes no symbol files (the open core, the simulated store) is reported as such; when the store refuses it, the error says the package went in and the symbol file did not |
| `kario symbolize` | `-map main.js.map` or `-symbols app.phonesym`: the JavaScript stacks of `main.js` in a log, a crash record or the store's list map back to the TypeScript; a symbol file's libraries symbolize native backtraces too. Function names go back to the source's as well (`jsrt.SourceMap.SymbolizeStackNamed`): for a frame minified as `a`, the nearest declaration of `a` before its position (`function a`, `class a`, `let`/`const`/`var a =`) and the name the source map keeps there (esbuild keeps `names` for every identifier it renamed when minifying); minifying, esbuild never gives an inner scope a name of the scopes around it, so no other declaration of `a` lies between a function's start and a position in its body. It needs the module itself: the symbol file carries it (one written before has none, and only positions are mapped), and with `-map` the `main.js` beside the map is used (as `kario build -sourcemap` lays them out). Method and property names are not minified in the first place and stay; an anonymous function stays `<anonymous>`; a function assigned to an existing variable (`a = function…`) is not found |
| The store backend (not open source) | `kario-storesrv` in kario-internal: checks the signature, that the version is one this developer submitted (published, the previous one of a staged rollout, or under review) and that the symbol file is that package's (the package's digest, the module's, the libraries' build-ids), and keeps it in the store's data directory, readable by the developer and the staff only; the developer reads the crash reports symbolized through `GET /v1/developer/crashes` (signed as for reading crash reports), the staff through `/v1/admin/crashes`, and a reviewer can download the symbol file; the portal's crash reports show the mapped stacks, and a symbol file can be chosen with a package to submit |

Checked by: `TestSourceMap`, `TestSymbolFile` and `TestFunctionNames` in `jsrt` (a stack the real kario-jsrt throws from a module esbuild minified: a function declared and an arrow function in a `const` get their names back, a method keeps its own, an anonymous one stays anonymous, columns counted in UTF-16 with Chinese on the line); `TestPackageSymbols` in `cmd/kario` (no `.map` in the package, the symbol file matching the package and the module and carrying it; the package's minified `main.js` run by the real kario-jsrt throws, and the stack it writes lands on the throwing line of `src/main.ts` through the symbol file, the function named `explode`, not its minified name), `TestPublishSymbols` (the signature, another package's symbol file, the wrong key), `TestPublishToStore` (the open core takes no symbol files); the accessors `appstore` gives a store backend (`Crashes`, `Submitted`, `Authenticate`); the store backend's and the portal's tests are in the internal repository.

**Not implemented**: `kario package` does not strip libraries for the developer (for phones to get libraries without debug information the developer strips them and gives the unstripped ones to `-native-symbols`); symbol files are not cleaned up with a takedown; the crash reports devices send carry only the log's last 20 lines, so older frames are missing. The store backend (not open source) symbolizes with `jsrt.SymbolFile.Symbolize`, so symbol files written now, which carry the module, give the names there too; **not verified** on the store backend.

## 6. Risks

- **Differences between the two engines**: Node (V8) on the developer machine, QuickJS-ng on the device. Only standard ECMAScript and `kario.*` are allowed, the type definitions have no Node or browser interfaces, and under Node too `main.js` can import only `kario`; the runtime cases of `jsrt` run on both engines (`jsrt/node_test.go`), and the calculator passes the selftest on both. Globals such as `process` can still be reached under Node, and Node is no sandbox: running on the developer machine does not mean running on the device; the selftest on kario-jsrt decides.
- **Performance**: QuickJS is an interpreter and computes much more slowly than V8. The system draws the UI and apps only manage state, which is usually enough; heavy work (image decoding, cryptography, media) goes to the system services, an app's own hot loops to native modules (§5.3: blurring an image in C is about 47 times faster than on QuickJS on the developer machine). Switch to Hermes if measurements say otherwise.
- **Ecosystem**: most npm packages rely on Node or browser interfaces and cannot be used as they are; pure-logic libraries can be bundled in.
- **People**: the type definitions are generated from `ui/caps.go`, so the interface changes in one place and both sides follow. The Go SDK is not deprecated; system apps can move over gradually.
