# Lock screen and biometrics: the lock-screen PIN, fingerprint unlock, fingerprint payments

> Status: **prototype ✓ (developer machine)**. The lock-screen PIN, locking when the screen goes off, emergency calls and hidden notification contents on the lock screen, enrolling a fingerprint and unlocking with it, disabling after failures in a row, fingerprint payments and the payment key voided when a new finger is enrolled pass in 9 selftest cases on the developer machine (run with both the text and the pixel renderer); `keystore` and `hal/fingerprint` unit tests ✓. The fingerprint sensor is **simulated**; real sensors are **not implemented** (they depend on the hardware and the vendor's TEE, see §4.1); templates, matching and tokens in the TEE are **not implemented** (R15): phone-keystored stands in for it. QEMU selftest ✓ (the 9 lock-screen cases), not on a real phone. The factory reset and the anti-theft lock (§11) were implemented on 2026-11-21: unit tests ✓, 2 developer-machine selftest cases ✓; the wipe at boot on a device: host tests of its script, and its QEMU case ✓ (2026-11-27 night chain r86; it empties a temporary tree, a test over several boots is **not implemented**), **not tried on a phone**.

## 0. Conclusions

- Without a lock-screen PIN everything is as before: the keypad lock is Nokia's, the left soft key then `*` undoes it, no secret involved.
- Once a PIN (4 to 16 digits) is set in 「设置 › 安全」 (Settings › Security), the keypad lock becomes a secure lock, as on Android and iOS: the phone locks when the screen goes off (a grace period can be set) and starts locked; the lock screen hides the app that was in front, and notifications show only the app's name and a count (their contents can be allowed in Settings); only the PIN or an enrolled fingerprint undoes it.
- What works locked: dialling emergency numbers, answering a call, stopping an alarm; NFC door cards and the express transit card work with the screen off and the phone locked without a key, and a double press of the power key opens the quick card view ([30](30-nfc.md) §5). Other features can add their own lock-screen shortcuts (§2.3).
- The PIN is typed only on system screens and checked by phone-keystored, which keeps a salted, slow hash (PBKDF2 over an HMAC with a key derived from the device key); the PIN itself is never written to disk or logs, and the Shell does not keep it. 5 wrong in a row cost a 30-second wait, more cost longer, and a restart does not reset the count.
- Fingerprints go through `hal/fingerprint`: the developer machine and QEMU have a simulated sensor, which the selftest touches with `finger <name>`. Templates and matching are in phone-keystored (the TEE's stand-in); a match yields only an authentication token (after Android's HardwareAuthToken), which the Shell passes on.
- Minor mode's parental PIN ([19](19-core-apps.md) §1.2) is in phone-keystored too, kept and counted apart from the lock-screen PIN, checked the same way with the same waits after wrong tries; when it is forgotten, a phone with a parent's account linked resets it once the parent confirms on their page, one without needs reflashing (§10).
- The factory reset is in 「设置 › 更多设置」 (Settings › More settings): it takes the lock-screen PIN (the parental PIN in minor mode) and the system's own last confirmation, and the phone restarts and erases its data before the services start; the system and its updates, and the phone's identity from the factory (device keys and certificates), stay. A phone with a Kario account signed in has an anti-theft lock (as Android's FRP): erased other than by its owner with the PIN (a forgotten PIN on the lock screen, a flashed data partition), it needs a code from that account before it can be used (§11).
- Fingerprint payments: `auth.confirm` gains `bio_key`; a biometric-bound key signs only after a fingerprint match and is voided when a finger is enrolled or removed (iOS's biometryCurrentSet, Android's setInvalidatedByBiometricEnrollment). The system's confirmation dialog says 「触碰指纹传感器确认，或输入支付密码」 ("touch the fingerprint sensor to confirm, or enter the payment PIN"), the signature still covers the text shown, and the server still checks it with `keystore.VerifyConfirm`.

## 2. The lock screen

### 2.1 When it locks

`c.keylock` is the one lock state and `c.locked()` its predicate; the PIN only decides how it is undone (`c.secureLocked()`).

| Situation | No PIN | With a PIN |
|------|-------------|-------------|
| Left soft key then `*` on the idle screen | Keypad lock | Secure lock |
| Automatic keypad lock (Settings › Keypad lock) | Keypad lock | Secure lock |
| The screen goes off | No lock (as before) | Locks once the grace period is over (immediately by default): "immediately" locks in the same housekeeping round that turns the screen off; a grace period is counted by the housekeeping, every 5 seconds while the screen is off, and checked once more before a key wakes the screen |
| Start, Shell restart | No lock | Locked; the Shell locks by the state it remembered, then follows phone-keystored. It locks even when that state (`shell/lock.json`) is damaged, removed or rewritten without the PIN: while phone-keystored's `keystore/lock.json` or its copy is there (they are only while a PIN is set), the Shell starts as if a PIN were set (`keystore.LockPINSet`), without waiting for phone-keystored's answer ([11](11-platform-architecture.md) §17). When phone-keystored's own record and its copy are both damaged the phone stays locked too, and no PIN unlocks it (§3). Unit tests ✓, **not tried on a phone** |

When a secure lock engages, the Shell closes the menus and dialogs on the screen (a call, an alarm and the SIM PIN screen stay), hides the app in front and the system pages above the idle screen, and leaves only the idle screen; unlocking gives them back as they were.

### 2.2 What works locked

| Key or event | Secure lock |
|------------|--------|
| Digit keys, OK, the left soft key | Bring up the PIN screen (a digit counts as the first one) |
| Call key | If what was typed on the PIN screen is an emergency number (112, 110, 119, 120, 122, 911, 999), it is dialled at once, no unlocking; the digits are never shown, so a PIN starting like an emergency number gives nothing away. The call key on the lock screen also brings this screen up |
| Fingerprint | An enrolled finger unlocks (with the screen off, the touch lights it first); an unknown one shows 「未能识别指纹」 ("fingerprint not recognized") |
| Incoming call | The system's answering screen as always; once answered only the call screen is usable: menus, the task switcher and Back cannot leave it; after hanging up the lock screen is back. When the screen goes off and the phone locks during a call, the call screen in front stays rather than being hidden, and lighting the screen shows it (as on Android and iOS), again with only the call screen usable; its right soft key 「最小化」 (Minimize) does nothing while locked. When the call goes on but the lock screen is back (the call was put in the background before the lock, or the call screen was replaced by another app), the lock screen says 「通话键 回到通话」 (Call key: back to the call), and the call key brings the call screen back without unlocking; the same for cellular and VoIP calls (unit tests `TestLockReturnsToCall`, `TestLockDuringACall`, the developer-machine selftest 「锁屏：通话中息屏上锁……」, **not run on a real phone**; a call in front and in the background: [19](19-core-apps.md) §5) |
| Alarm | Rings and stops as always |
| Notifications | The idle screen shows only the app's name and a count, like 「飞钱：1 条通知」 ("Feiqian: 1 notification"); a banner shows only the app's name; with 「锁定时显示通知内容」 (notification contents when locked) on in Settings they show as usual |
| End key | Back to the lock screen (after an emergency call); on boards without a power key, two presses on the lock screen after a pause: the quick card view ([18](18-nokia-form-factors.md) §5.1) |
| Power key | Screen off, screen on (screen off locks by the rules of §2.1); two presses open the quick card view over the lock screen without unlocking, the chosen card presented for 60 seconds, a payment card needing unlocking first ([30](30-nfc.md) §5); held, the power menu |

### 2.3 Lock-screen shortcuts (for other features)

The lock screen can offer system features that work without unlocking (such as a torch). They are listed in `lockShortcuts` in `shell/lock.go`, one line per feature, which can sit in an `init` of the feature's own file. None is registered now: NFC's old → shortcut is gone, as cards work without a key and the power key opens the quick card view ([30](30-nfc.md) §5).

```go
lockShortcuts = append(lockShortcuts, lockShortcut{Key: KeyF2, Label: "Torch", Run: (*Core).torch})
```

Rules: when `Run` is called the phone is still locked, so it may only raise a system overlay; everything else stays behind the lock. `Label` is English and is translated where the lock screen's hint shows it. Keys the lock screen keeps for itself: the digits, OK, the left soft key, `*`, the call key, the end key and Back (the power key does not pass through the lock screen); free are the right soft key and the arrows.

## 3. The PIN

| Step | How |
|------|------|
| Set, change, remove | Settings › Security; the PIN is typed on the system's own screen (the Settings app calls `settings.set lock_pin` and the reply waits for the user to finish), and the Settings app never sees it; changing asks for the current PIN first and the new one twice; removing asks for the current PIN and removes the fingerprints too |
| Storage | phone-keystored's `keystore/lock.json`: a random salt, PBKDF2-SHA256 (100,000 rounds) over an HMAC with a key derived from the device key (the file is no use on another device; the derivation takes the data area's random salt too, a new one after a factory reset, §11.3; in production the TEE's hardware key); plus the "secure user ID", made when the PIN is set and carried by tokens |
| A damaged file | Written with a copy `lock.json.bak` (`statefile.WriteKeep`, both written whole, [11](11-platform-architecture.md) §17); when `lock.json` is damaged or gone it is read from the copy, the PIN works as usual, and it is written again from the copy. An older phone without a copy starts as before and gains one at the next write. Both damaged: phone-keystored starts all the same (saying so in its log), takes a PIN to be set and no PIN to be right (`lock_damaged`), refuses to set, change or remove the PIN, and writes neither file; fingerprints cannot unlock either (after a restart the PIN comes first). The lock screen says 「锁屏 PIN 码的记录坏了：什么 PIN 码都解不开这台手机。」 (The lock-screen PIN's record is damaged: no PIN unlocks this phone.) and offers §11.2's "# erases this phone" at once, without 5 wrong PINs first: anyone can enter 5 wrong PINs first, so this opens nothing more; the erase takes the record with the data, and the anti-theft lock holds. There is no other way: a way to replace it without the PIN would be a way around the lock screen. Before, a damaged file kept phone-keystored from starting: the lock screen could not be unlocked, and whatever takes keys (payment confirmations, push, device attestation) did not work either. Unit tests ✓, **not tried on a phone** |
| No plaintext | The PIN is in the Shell's memory only while half typed on a system screen, and dropped once sent; never written to disk or logs |
| Wrong attempts | 1–4 in a row: the screen says how many more are free; 5–9: a 30-second wait after each; 10–14: 1 minute; 15–19: 5 minutes; 20–29: 30 minutes; 30–39: 1 hour; then 1 day. The count is in `lock.json`; after a restart the current wait starts over (a restart never shortens it) |
| The payment PIN | The lock-screen PIN and the payment PIN of the trusted confirmation are two things (like Alipay's payment password and the phone's lock-screen passcode); merging them is a later choice, **not implemented** |

## 4. Fingerprints

### 4.1 The HAL and sensors

`hal/fingerprint` defines `Sensor`: `Capture` waits for a touch and reads its features, `Enroll` starts an enrolment (`Add` takes touch after touch and reports progress, then gives the template), `Match` compares features with a template. The package is used only inside phone-keystored: readings and templates never leave that process.

| Backend | Status |
|------|------|
| Simulated (`Sim`, developer machine and QEMU) | ✓: each name is a different finger, each touch a slightly different reading; an enrolment takes 5 touches and another finger does not count; the selftest command `finger <name>` goes through the Shell to phone-keystored (`fp.sim_touch`, a test hook like the simulated baseband's `sim.ring`) |
| A phone's SPI sensor (FPC, Goodix) | **Not implemented**, depends on the hardware: there is no mainline driver; the vendor drives it from a trusted application in the TEE, which also enrols and matches, so a backend is a client of that trusted application and needs the vendor's TEE. The test phone, a Redmi Note 4X, has an FPC sensor with no mainline driver |
| A USB sensor (one libfprint supports) | **Not implemented**; libfprint is LGPL, so it could only run as a separate process, the backend talking to it across processes, never linked into the platform |
| Phones without a usable sensor | The board configuration leaves out `fingerprint` ([24](24-sku-framework.md)), so phone-keystored has no sensor; Settings says 「没有指纹传感器」 (no fingerprint sensor) |

phone-keystored picks its backend from the board configuration (`fingerprint` in `sku.json`): the emulator's board says `sim`, a real phone's board leaves it out until its sensor has a driver, so it has no fingerprints; the developer machine, with no `sku.json`, uses the simulated backend; `--fingerprint` overrides it. On a phone the sensor's interrupt should be a wakeup source, so a touch wakes it from suspend (**not implemented**); on the developer machine the `finger` command lights the screen first.

### 4.2 Templates and matching (keystored standing in for the TEE)

| Step | How |
|------|------|
| Enrolling | First the PIN on the system screen: phone-keystored issues a challenge, a correct PIN yields a token for that challenge, and enrolling takes that token for 10 minutes (Android's way); then the system's enrolment screen lights its progress step by step, and a finger already enrolled is refused |
| Storage | `keystore/fingerprints.json`: names and templates, the templates encrypted (AES-GCM) with a key derived from the device key; plus the "fingerprint set ID", new at each finger added or removed |
| Matching | Only inside phone-keystored; a match yields a token, never the template or the reading |
| Rename, delete | Settings › Security › Fingerprints (the PIN first to get in); deleting takes that token too |

### 4.3 Authentication tokens

After Android's HardwareAuthToken: the PIN check and the fingerprint matcher each make one, and operations that need the user (enrolling a finger, signing with a biometric-bound key) take it. The MAC key is made at random at each start of phone-keystored, so only it can make and check tokens and none survives a restart; the Shell only passes them on.

```
version(1) | challenge(8) | secure user ID(8) | authenticator ID(8) | type(4: 1 PIN, 2 fingerprint) | time(8: ms since start) | HMAC-SHA256(32)
```

### 4.4 Rules

| Rule | How |
|------|------|
| At most 5 fingerprints | A sixth cannot be enrolled |
| 5 unrecognized in a row | Fingerprints are disabled and the lock screen asks for the PIN; a correct PIN brings them back (unlocking and payments share the count) |
| After a restart | The first unlock needs the PIN (phone-keystored refuses fingerprints until it has seen the PIN since it started) |
| 48 hours without the PIN | The same |
| Removing the PIN | All fingerprints go, and the biometric-bound keys are voided with them |
| What they are used for | Settings › Security › Fingerprints: 「解锁手机」 (unlocking the phone, on by default) and 「支付」 (payments, off by default) |

### 4.5 The sensor powered only when a fingerprint is wanted; a sensor on the OK key

phone-keystored powers the sensor: only while something waits (an enrolment, `fp.auth`), and for 1.5 seconds after the wait ends (so retries in a row do not power it up again and again; a sensor on the OK key does not linger, see the table below); `fp.cancel` powers it down at once. An unpowered sensor reads nothing, and that touch is lost, not kept for later (`Sensor.SetPower`, which the simulated sensor follows). `lock.status`'s `powered` says whether it is powered now, and the selftest command `fingerprint-power on|off` waits for it.

A keypad phone may put the sensor on the OK key in the middle of the navigation cluster: an area sensor under the surface of the key cap, as large as the cap allows, which reads a finger resting on it with no press. The SKU keypad says `fingerprint = "ok-key"`, short for `fingerprint = { at = "ok-key", sensor = "area", read = "touch" }` ([24](24-sku-framework.md)); `tools/sku.py` takes only these two forms, refusing a sensor read by pressing (`read = "press"`, which would make OK a fingerprint key), another kind of sensor, another place, and missing or extra keys, and it requires an OK key in the keypad's matrix; either form becomes `fingerprint_at = "ok-key"` in `sku.json`. OK is pressed hundreds of times a day and every press touches the sensor, so:

| Rule | How |
|------|-----|
| Read only for the system's fingerprint prompts | The Shell starts a wait only while the system's confirmation (`auth.confirm` with a `bio_key`) or the enrolment screen is open, so only then is the sensor powered; touching or pressing OK on the idle screen, the lock screen or in an app reads nothing. It is powered down as soon as the wait ends, with no 1.5-second linger: otherwise the press of OK after a payment would be read, and kept as the answer to the next prompt (`TestOKKeySensorOffOutsideThePrompt`, which fails on the old code) |
| Powered once the prompt has been up 500 ms | The same rule as the system dialogs' keys (`overlayArmDelay`, [11](11-platform-architecture.md) §16.1): the press of OK that opened the prompt is not an answer, nor is the finger still resting on OK then; the Shell sends `fp.auth` only once the prompt has been up for 500 ms. A real driver must also take only a finger that lands after power-up (a requirement in `hal/fingerprint`, §9) |
| Not for unlocking | The lock screen does not wait for a finger, and its hint no longer mentions the sensor; a finger resting on OK does nothing, and only pressing OK brings up the PIN pad; Settings has no 「解锁手机」 (unlock the phone) switch and says the sensor is under the OK key's cap, reads a resting finger without a press and is powered only when the system asks for a fingerprint; phone-keystored also refuses a match that is not for a key (`ErrPromptOnly`), so a Shell bug cannot unlock either |
| How to confirm | The prompt says 「把录入过的手指放在 OK 键上确认（不用按下），或输入支付密码」 (rest an enrolled finger on the OK key to confirm, no need to press it, or enter the payment PIN); the enrolment screen says to rest the same finger on the OK key, lifting it between touches, with no need to press |
| Who decides | phone-keystored reads `sku.json`'s `fingerprint_at` and tells the Shell in `lock.status`'s `place`; the selftest's `fingerprint-at ok-key|own` (`fp.sim_place`, on the simulated sensor only) moves it on a developer machine |

**Press or touch: which counts.** A finger resting on OK is read, and a finger pressing OK is on the cap too, so the two often come together:

- In the prompt's first 500 ms neither counts: the sensor is off and OK is not taken (the table above).
- After that, a finger read and matched is the answer: it signs and closes the prompt. OK is still a key, given to the prompt, which neither reads a finger, nor confirms, nor cancels with it; with some payment PIN digits typed it says 「请输入完整的 6 位支付密码」 (enter all 6 digits of the payment PIN), with none it does nothing. So OK alone never pays.
- When both happen, the finger read counts and the press of OK that came with it is the system's: while the prompt is open the prompt takes it (the point above), and once the finger has closed the prompt one press of OK within 500 ms is dropped (`okAfterFinger`), so it does not land on the page under the prompt (a payment's result page, or 「添加指纹」, add a fingerprint, in Settings after an enrolment).
- Why: only the reading proves who is there; OK carries no identity, anyone's press is the same, so letting it confirm would drop the fingerprint step. In the prompt OK means "confirm", the same intent as resting the finger, so a press need not cancel the authentication as on Android's side-key sensors: Android's power key means "screen off", the opposite, so a power press during BiometricPrompt fails the side sensor's authentication (`BIOMETRIC_ERROR_POWER_PRESSED`, [commit eac8784](https://github.com/aosp-mirror/platform_frameworks_base/commit/eac8784630f6c2db499983bc3b200ef440180db8)), and a press shortly after a success counts as a cancel (`config_sidefpsBpPowerPressWindow`, [commit ae84de6](https://github.com/aosp-mirror/platform_frameworks_base/commit/ae84de69b07e8b1dd062bf4fd267e26c90a9912d)). Android also consumes the power key's single press while BiometricPrompt is up ([`SideFpsEventHandler.shouldConsumeSinglePress`](https://android.googlesource.com/platform/frameworks/base/+/master/services/core/java/com/android/server/policy/SideFpsEventHandler.java)); Kario dropping the press that came with the finger is the same move.

The unit test `TestOKKeyReadsATouchNotAPress` (`shell`, with phone-keystored over its socket, a real key store and the simulated sensor) walks through these rules; it fails on the old code (where a touch on the lock screen pressed OK and brought up the PIN pad). All of this runs on the simulated sensor only: a driver for a real sensor on the OK key is **not implemented** and **not tried on a phone**, and that the rules above hold whichever of OK's key code and the touch reaches the Shell first is **not verified** (§9).

**The security level, honestly.** `lock.status`, key proofs (`KeyProof`) and device attestations (`Attestation`) carry `security`: `software` (now: the phone-keystored process stands in for a TEE, [22](22-developer-api.md) §4.1) or `tee` (in production, given by the trusted application in the TEE). With `software` the prompt adds a line, 「这台手机没有安全硬件（TEE）：密钥由系统的密钥服务保管，指纹也由它比对」 (this phone has no secure hardware: the system's key service keeps the key and matches the finger), and Feiqian's result and security pages say where the key is kept. The field is **not signed**: in software the key that signs and the process that reports the level are the same, so a signature would prove nothing; for a server to trust it, a TEE's attestation key has to sign it (as SOTER and IFAA do, §9).

## 5. Fingerprint payments

1. The app calls `auth.confirm{key, bio_key, prompt, payload}` (Feiqian: `key: "pay"`, `bio_key: "pay-bio"`). If the user turned on fingerprints for payments and has one enrolled, the system's confirmation dialog says 「触碰指纹传感器确认，或输入支付密码」 and waits for both a finger and the payment PIN.
2. A fingerprint match: phone-keystored first checks that the `bio_key` key exists and is bound to the current set of fingers, then waits for the touch; a match yields a token valid for one signature with this very key (within 30 seconds); the Shell hands the token to `confirm_bio`, and the key signs "the text shown + the payload". The proof has `key_alias` `pay-bio` and `bio: true`.
3. The payment PIN: signs with `key` as before; afterwards phone-keystored makes the `bio_key` key (if missing or voided), bound to the current set of fingers. So a biometric-bound key is made **only after the payment PIN confirmed**: someone who learnt the lock-screen PIN and enrolled their own finger voids the old key and still cannot pay.
4. After a finger is enrolled or removed: the dialog explains 「开通指纹支付后指纹有变动，请用支付密码确认，指纹支付随之重新开通」 ("the fingerprints changed since fingerprint payment was set up: confirm with the payment PIN to set it up again") and takes only the payment PIN; once confirmed the new key is made and the next payment can use a finger again. The first use goes the same way (「先用支付密码确认一次，之后就能用指纹支付」, "confirm with the payment PIN once to start paying with a fingerprint").
5. The server (the simulated merchant inside Feiqian) checks as before with `keystore.VerifyConfirm`, step by step: manufacturer root → device certificate → app key certificate → signature → content. A biometric-bound key's certificate says it is fingerprint-bound (`keystore.AppKeyCertMsgBio`), and `VerifyConfirm` picks the certificate form by the proof's `bio`, so the server knows a fingerprint confirmed it; Feiqian accepts both `pay` and `pay-bio`.

| Key | Confirmed by | What its certificate says |
|------|----------|-----------|
| `key` (such as `pay`) | The payment PIN | `user_auth` |
| `bio_key` (such as `pay-bio`) | A fingerprint, within 30 seconds of the match, once | Fingerprint-bound; voided once the set of fingers changes |

Mini-program hosts still pass only `key` and are not affected.

## 6. Settings › Security

| Item | How |
|----|------|
| Lock-screen PIN | Set, change, remove, all typed on the system screen (`settings.set` `lock_pin`: 1 set or change, 0 remove) |
| Lock after the screen goes off | Immediately, 5 s, 30 s, 1 min, 5 min (`lock_grace`, seconds) |
| Notification contents when locked | A switch (`lock_show_content`) |
| Fingerprints | The PIN on the system screen first (`fingerprint_auth`); the list of fingerprints, rename (`fingerprint_rename`, the ID as the value and the name as `text`), delete (`fingerprint_delete`); add (`fingerprint_enroll`, the system's enrolment screen); the two switches 「解锁手机」 and 「支付」 (`fingerprint_unlock`, `fingerprint_pay`) |

`settings.get` has `security`: whether a PIN is set, the grace period and its choices, whether notification contents show, the sensor, the fingerprints (IDs and names only), the maximum, the two switches, and why fingerprints cannot be used for now (`restart`, `timeout`, `lockout`). The Settings app's code is `apps/settings/security.go`; the Shell's side is `shell/lock.go`, `shell/lockpad.go` and `shell/biometric.go`.

## 7. Interfaces

phone-keystored's methods (only the Shell calls them; `keystore/methods.go`):

| Method | What it does |
|------|--------|
| `lock.status` | The PIN, any wait, the sensor, the fingerprints, why the PIN is needed; `damaged`: the PIN's record and its copy are both damaged (§3) |
| `lock.set_pin` / `lock.clear_pin` / `lock.verify` | Set or change, remove, check the PIN; checking takes a challenge and a correct PIN yields a token; with the record damaged each answers `lock_damaged` |

### 11.2 A forgotten lock-screen PIN

Kario has no recovery as Android has ([27](27-usb-typec.md) §4.1); flashing goes through the board's tools. So the way out of a forgotten lock-screen PIN is on the lock screen, after iOS's "Erase iPhone" on its lockout screen (iOS 15.2 on): after 5 wrong PINs in a row (the first wait of 30 seconds), the PIN screen gains a line 「忘了 PIN 码？按 # 清除这台手机和上面的一切」 (Forgot the PIN? # erases this phone and everything on it); # brings the system's own confirmation 「不用 PIN 码清除这台手机？」 (Erase this phone without its PIN?), which says the Kario account signed in will be asked for afterwards. In minor mode the parental PIN comes first (else a child could wipe minor mode away with a few wrong PINs). Such an erase lacks the owner's lock-screen PIN, and the anti-theft lock holds.

| Ways to erase without the lock-screen PIN | State |
|------|------|
| 「忘了 PIN 码」 (Forgot the PIN) on the lock screen | ✓ (above); the anti-theft lock holds |
| phone-keystored's record of the PIN damaged with its copy (§3) | The lock screen says the record is damaged and offers "# erases" without 5 wrong PINs first, the rest as above; unit tests ✓, **not tried on a phone** |
| A wipe screen entered with keys at boot (Android recovery's Wipe data) | **Not implemented**: it needs reading keys and drawing in the initramfs; when done it counts as an untrusted erase, as the lock screen's does |
| Erasing after too many wrong PINs (iOS's "Erase data" option) | **Not implemented**; now the waits grow, to a day at most (§3) |
| A flashing tool rewriting the data partition (fastboot, Qualcomm EDL) | The erase cannot be stopped; with the state partition not rewritten the anti-theft lock holds (§11.4: the data area lacks the record's token) |

### 11.3 Keys: the factory identity stays, the data area's keys change

phone-keystored's device keys (Ed25519 and SM2) are what the device certificate vouches for: on the factory line the certifier's CA certifies the two public keys ([11](11-platform-architecture.md) §7, [22](22-developer-api.md) §11), and registering with the push gateway, the update server's reports and payments' trusted confirmations rely on that chain to know "this is a genuine, certified phone". New device keys would void the certificate, and only the factory station can issue another: the owner has no way to. So a factory reset **keeps** the device keys, the device certificates and the roots (`keystore/device.key`, `device-sm2.key`, `factory/`); the device ID stays, and `wipe.Keep` lists them. Android does the same: the attestation keys provisioned in Keymaster at the factory survive a factory reset; the keys of the user's data go.

Gone: every app key (`keystore/apps/`, mini-programs' too), the push keys, the payment PIN (back to the default), the lock-screen and parental PINs, the fingerprint templates, the secrets the system sealed; the device-unlock state goes too (the components the owner built and swapped in live in the data area and go with it, and device attestation reports a normal boot again).

Deleting the files is not enough: keys derived from the same device key (the PINs' peppers, the templates' key, the sealed secrets' key) would stay the same, and data copied off before the erase (a sealed app password, say) would still open on this phone. So the derivation also takes a random salt of the data area (`keystore/data.salt`, `keystore.DataSaltPath`): written when a new key store is made, deleted with the data area by the erase, and written anew as the erase's last step; what was sealed before the erase no longer opens and the PINs' hashes no longer match (`TestDataSaltAfterAReset`). Phones from before this version have no salt and derive as before (`TestStoreWithoutADataSalt`) until their first factory reset. In production the salt belongs in the TEE's secure storage, destroyed by the erase (**depends on hardware**); now it is on the data partition, where deleting is not erasing (§11.1).

### 11.4 The anti-theft lock

After Android's FRP (Factory Reset Protection) and the iPhone's Activation Lock: a phone with a Kario account signed in, erased other than by its owner with the PIN, needs that account before it can be used again. The code is in `shell/antitheft.go`, the protocol is package `antitheft` (kario-antitheft/1).

| Step | How |
|------|------|
| When it comes on | With a Kario account signed in in 「设置 › 账号」 (Settings › Accounts) (the product's `PHONE_ACCOUNT_SERVER`): the Shell binds the phone on the account server (`POST /v1/antitheft/bind`: the account's e-mail address and app password (signed in with a code, the one the server made for this phone; signing out ends the binding before it revokes that password, [19](19-core-apps.md) §1.1, "Signing in with a code"), and the device's attestation over the server's one-time challenge), and the server records that this phone (by its device key) is the account's; then the Shell writes the record in the persistent area (`/var/lib/slots/antitheft.json`: the account's ID, its address masked as `l***i@example.com`, the device ID, a random token) and the same token in the data area (`<state dir>/shell/antitheft.json`, written first). Failing, it tries again after a minute, doubling, at most 6 hours; signing out ends the wait, so the account signed in next is bound at once. A 401 to the binding itself (the server refuses the password: the phone signed out on the account's page before it was bound, say) is not tried again: the account's sign-in counts as refused (「登录被拒绝」, Sign-in refused, in Settings, the syncs stop too, [19](19-core-apps.md) §1.1 "Errors and backoff") until the user presses 「立即同步」 (Sync now) or signs in again; a 401 to another request, the challenge say, does not count. A 409 to the binding (the server has this phone bound to another account still: a previous owner's binding never ended, or one this phone left when it signed out of another account; the answer does not say which account) is not tried again either, and the log has the device ID; Settings › Accounts' list says the account's anti-theft lock is not on, that this phone is still locked to another Kario account and that its previous owner must remove it under 「防盗锁」 (Anti-theft lock) on that account's page (with the device ID), with a row 「重试开启防盗锁」 (Try the anti-theft lock again) below: pressed, it binds again at once, and a 409 again says the previous owner has not removed it yet; a check of 「已在账号的网页上移除？」 (Removed it on the account's page?) finding the binding this phone left gone, or signing in again, binds at once too ([19](19-core-apps.md) §1.1, "The anti-theft lock's binding answered 409" under "Signing in with a code"). The factory reset page shows it |
| When it goes off | Signing out of the Kario account (with a lock-screen PIN set, that first: else whoever holds the phone unlocked could sign out, then erase it from the lock screen); a factory reset from Settings with the PIN without 「保留防盗锁」 (Keep the anti-theft lock); the server's release while locked. Each deletes the record and tells the server the binding ended (as best it can). Before signing out, when the binding could not end the confirmation says so beforehand: with no network now (the Shell looks at the network when it changes, and at most every 30 seconds while Settings' accounts pages are open), or the server refusing the account's password (a 401 to the sync, the calendar or the binding), the confirmation says the anti-theft lock stays on at the account and to remove the phone under 「防盗锁」 (Anti-theft lock) on the account's page afterwards, in place of the line on revoking the phone's sign-in; when it can end it the confirmation is as it was. When signing out could not end it (the phone was signed out on the account's page already, so the unbinding gets a 401; or no server), the server keeps the binding and the phone could not be bound to another account later (409), so Settings says in the sign-out's result that the anti-theft lock is still on at the account, and the accounts' list keeps a note saying to remove the phone under 「防盗锁」 (Anti-theft lock) on the account's page (with the account's e-mail address and the device ID) until the phone, asking `status` with its device attestation, learns it is no longer bound (at most once a minute while the list is open, and at once on 「已在账号的网页上移除？」, Removed it on the account's page?), or the phone is bound again ([19](19-core-apps.md) §1.1, "Signing out" under "Signing in with a code") |
| When it locks | At start (`startTheft`): a record in the persistent area that says it is locked (an erase from the lock screen, the owner kept the lock), or whose token the data area lacks (the data area was replaced: flashing, an erase the Shell did not ask for). So an erase from the lock screen locks as flashing the data partition does. The record and the data area's token each have a copy kept (`.bak`, [11](11-platform-architecture.md) §17): a write cut short is read from the copy and does not lock the owner's phone; with the record and its copy both damaged it still locks (the account unknown, shown as "?"). Unit tests ✓, **not tried on a phone** |
| While locked | The system's own screen over everything: 「这台手机是在没有机主 PIN 码的情况下清除的。它原来登录着 Kario 账号 l***i@example.com」 (This phone was erased without its owner's PIN. It was signed in to the Kario account l***i@example.com); the left soft key has the server send a 6-digit code to that address, typed and then OK; OK without a code asks the server whether the owner removed the phone on the account's page; the call key dials emergency numbers only (the lock screen's path, no case of its own), and during a call the end key hangs up. No other key does anything, injected keys neither |
| Release | The server, having checked the code (10 minutes, 5 tries) or found that the owner removed the phone, signs a release `{device ID, account, the phone's nonce for this attempt, issued, expires}` with the account server's signing key over `kario-antitheft-release/1\n` and the JSON (`antitheft.Release`). The release carries the ID of the key that signed it (`key`, the rotation of [11](11-platform-architecture.md) §15.1). The phone takes it only when the signature matches the product's public key (`PHONE_FAMILY_KEY`: the same key signs minor mode's policies, each under its own prefix), the device ID is its own, the account is the record's and the nonce the one it made for this attempt (`antitheft.Verify`; the phone's clock is not asked: after an erase it cannot be trusted, and a nonce used once is enough against replay). Then the record goes, and the phone is as new |

The protocol (package `antitheft`; each request takes a one-time challenge first; the device attestation's app is `system.antitheft`, over `antitheft.Nonce(purpose, account, challenge, the phone's nonce)`):

| Request | Credentials | Answer |
|------|------|------|
| `POST /v1/antitheft/challenge` | — | `{challenge, expires_in}` (5 minutes, once) |
| `POST /v1/antitheft/bind` | Basic: the e-mail address, an app password; the device attestation | `{account, email}`; bound to another account: 409 (its `error` only says that account's owner removes it first, not which account) |
| `POST /v1/antitheft/unbind` | The same | 204 |
| `POST /v1/antitheft/status` | The device attestation (the account's ID, the phone's nonce); a locked phone, and one that signed out leaving the binding | `{bound, email}`; with `release` when the owner removed it; no such account: 404 |
| `POST /v1/antitheft/code` | The same | 202 `{email}`; 5 an hour per phone and 10 per account, then 429 |
| `POST /v1/antitheft/release` | The same, with the code | The signed release; a wrong code 401 |
| `GET /v1/antitheft/devices`, `DELETE /v1/antitheft/devices/{device ID}` | The account page's session (removing takes a sign-in with a code within 10 minutes, else 403 with `reauth`) | The phones bound; removing one, which gets a release when it asks next |

The server's side (kario-internal's `kario-accountsrv`) is in internal documents 63 §9 and 64 §3.2.

Threat model:

| Threat | What stops it |
|------|--------|
| A stolen locked phone, erased from the lock screen | It is locked after the erase and needs the code sent to the account's address; the server's binding and the phone's record are both still there |
| A stolen unlocked phone | Erasing from Settings takes the lock-screen PIN, so does signing out of the Kario account; a phone without a lock-screen PIN is not protected (Android's FRP too works only with a screen lock set) |
| Flashing the data partition | The record on the state partition stays and the data area lacks its token, so it locks. The prototype's device keys are on the data partition, so the device ID changes: a code still releases it (the release names the device ID now and the record's account), but the factory certificate is gone too (production's device keys are in the TEE, **depends on hardware**) |
| Flashing the state partition too, or editing the record | Not stopped: without a record nothing locks. It takes a locked bootloader refusing to flash, and in production the record in RPMB or the TEE's secure storage (**depends on hardware**); the server keeps the binding, but asking it at boot whether the phone is still bound is **not implemented** |
| Binding someone else's phone to one's own account, asking a release for another's phone | Every request carries a device attestation by that phone's device key over the purpose, the account and a one-time challenge; the server keeps bindings by the device's public key, so another key claiming the same device ID finds nothing of the phone; the phone takes only a release with its own nonce for this attempt. In production the server has the certifier's root (`--device-root`) and takes only provisioned phones; the trial's phones are not provisioned and prove only that they hold the key |
| A man in the middle (a TLS-terminating reverse proxy included) forging a release | A release carries the account server's signature, and the phone trusts only the public key in the product image |
| Replaying an old release | A release names the phone's nonce for this attempt, and only that one is taken |
| Flooding with codes, guessing codes | 5 an hour per phone and 10 per account; each code holds 10 minutes and 5 tries, for this phone only; codes go only to the account's address |
| A stolen account mailbox | It can release the account's phones and remove them on the page; a stronger sign-in (a phone number, two-step) is **not implemented** |
| The account page left signed in on someone else's computer | Removing a phone takes a session signed in with a code within 10 minutes, so an old session cannot remove a stolen phone (signing in again takes a code from the account's mailbox); signing a phone out on the page leaves the anti-theft lock alone |
| The account server's signing key leaking | It can sign a release for any phone; changing the key means a new public key with a system update, a procedure **not implemented**; a key apart from minor mode's is **not implemented** (one key now, under separate prefixes) |
| Deleting the account | The phones bound to it count as removed by the owner and are released when they next ask, never locked for good |

## 12. Why a TEE vendor is still needed: TrustZone is a CPU mode, not software

> Researched on 2026-11-26. What has a link is what the source says; **inference** marks what follows from the sources without them saying it; **not verified** marks what needs the module vendor's or Qualcomm's documents.

Every ARM application processor has TrustZone, so why do §4.1 and §9 say fingerprints, PIN checks, SOTER and IFAA need "the vendor's TEE"? Because TrustZone is only hardware: a CPU state plus one bit on the bus. What software runs in the secure world, and who may put software there, the chip maker and the device maker decide with the secure boot keys; code Kario writes cannot get in.

### 12.1 TrustZone: a CPU state and a bit on the bus

| Layer | What it is |
|----|--------|
| CPU | The processor has a Secure and a Non-secure state. EL3 (the level the secure monitor runs at) is always Secure; below EL3 the state is set by the `SCR_EL3.NS` bit, which only EL3 can change. Each state has its own physical address space ([Arm: Security states](https://support.arm.com/documentation/102418/0102/TrustZone-in-the-processor/Security-States)) |
| Bus and peripherals | Every access carries its security attribute on the bus (AXI's `AxPROT[1]`), and filters such as the TZASC in front of memory let it through or refuse it, so a range of memory or a peripheral (say the fingerprint sensor's SPI) is given to the secure world only ([Arm: Completers, peripherals, and memories](https://support.arm.com/documentation/102418/0102/System-architecture/Completers--peripherals--and-memories)) |
| Software | TrustZone brings no software: the EL3 monitor, the TEE operating system in the secure world and the trusted applications (TAs) on it must be written, signed and loaded by the boot chain. The chain starts in the chip's ROM, and whoever's keys may sign these images decides what is in the secure world (the next two sections) |

### 12.2 The TEE operating systems that run there

| TEE OS | Whose | Notes |
|--------------|------|------|
| QTEE (formerly QSEE) | Qualcomm | On Qualcomm chips, the QCM6490 included; Linux talks to it through `smcinvoke` (the kernel's `qcomtee` driver, the user-space [libqcomtee](https://github.com/quic/quic-teec), [kernel docs](https://docs.kernel.org/tee/qtee.html)). Xiaomi's Qualcomm phones use it ([Check Point](https://research.checkpoint.com/2022/researching-xiaomis-tee/)) |
| Kinibi | Trustonic | Used on Samsung Exynos among others ([Project Zero](https://projectzero.google/2017/07/trust-issues-exploiting-trustzone-tees.html)); system TAs must be signed by the chip maker, the device maker or Trustonic ([Kinibi 510A Security Target](http://www.commoncriteriaportal.org/files/epfiles/Trustonic-Kinibi-510A-ST-1.2.pdf)) |
| ISEE (Beanpod) | Beanpod Technology | A Chinese TEE that MediaTek works with ([MediaTek press release](https://www.mediatek.com/zh-cn/press-room/doujia_tee), [Beanpod white paper](https://www.beanpodtech.com/en/whitepapers/isee-tee-security-foundation/)); Xiaomi's MediaTek phones use it or Mitee ([Check Point](https://research.checkpoint.com/2022/researching-xiaomis-tee/)) |
| OP-TEE | Open source (TrustedFirmware.org) | TAs are signed with your own key: the build's `default_ta.pem` is public, and a product replaces it with its own and signs offline or in an HSM ([OP-TEE docs](https://optee.readthedocs.io/en/latest/building/trusted_applications.html)) |

### 12.3 Who signs the trusted applications

- Qualcomm's secure boot: Qualcomm's root is in the chip's ROM, the hash of the device maker's root public key is blown into fuses (OTP) at the factory, and every later image is loaded only once its signature checks; the QTEE image may be signed by both Qualcomm and the device maker, and which images must be signed by both is "pre-configured by Qualcomm Technologies on a product-line basis" ([Qualcomm: Secure Boot and Image Authentication](https://www.qualcomm.com/content/dam/qcomm-martech/dm-assets/documents/secure-boot-and-image-authentication-version_final.pdf)).
- QTEE loads only TAs this chain accepts: Qualcomm's public [qtee-tas](https://github.com/qualcomm/qtee-tas) are signed with test keys, per chip (qcm6490 among them), and changing them breaks the signature; on a device with secure boot on, the device maker must re-sign TAs with its own certificate through sectools and blow its root certificate's hash into the fuses, a Qualcomm engineer says in [meta-qcom #1454](https://github.com/qualcomm-linux/meta-qcom/issues/1454), adding that the security profiles were not public yet. Qualcomm's Linux docs also have the device maker sign `tz.mbn` with sectools and blow the fuses with kodiak's fuse-blower ([Sign and flash images](https://docs.qualcomm.com/doc/80-70020-11/topic/sign-and-flash-images.html)).
- So "putting a fingerprint TA in the TEE" takes a key that can sign TAs in this phone's chain (the device maker's, whose hash is in the fuses), and an SDK and documents to write the TA. Fuses cannot be changed once blown: if the module Kario gets already has the module vendor's root blown, only the module vendor can sign (**inference** from the two sources above).
- Device makers like Xiaomi can put TAs they signed themselves into QSEE and Beanpod's TEE ([Check Point](https://research.checkpoint.com/2022/researching-xiaomis-tee/)); they are the device makers and hold that key.

### 12.4 What SOTER and IFAA need

| | SOTER (Tencent, WeChat Pay) | IFAA (the alliance Alipay leads) |
|---|---|---|
| Code in the TEE | Tencent gives no TEE code; the chip or device maker implements SOTER's TA in the TEE, with all three levels of keys (ATTK, ASK, AuthKey) in the TEE; Xiaomi wrote its own soter TA ([Check Point](https://research.checkpoint.com/2022/researching-xiaomis-tee/)) | The IFAA TA, which talks to the fingerprint TA inside the TEE, with its key in RPMB ([patent CN107133794A](https://patents.google.com/patent/CN107133794A/zh)) |
| Production line | Before shipping, the device's root key ATTK is generated in the TEE and the device maker hands its public key to Tencent's server; the app's ASK and each scene's AuthKey derive from it ([SOTER wiki](https://github.com/Tencent/soter/wiki/%E5%8E%9F%E7%90%86)); it is written by a command on the line and kept in RPMB ([Tencent Cloud article](https://cloud.tencent.com/developer/article/1005987)) | Keys injected on the line ([Tencent Cloud article](https://cloud.tencent.com/developer/article/1043697)); one per model ([Tencent Cloud article](https://cloud.tencent.com/developer/article/1043485)) |
| Certification | The device maker passes Tencent's and WeChat Pay's acceptance ([Tencent Cloud article](https://cloud.tencent.cn/developer/article/1030885)) | Tested at 泰尔实验室 (CTTL, the CAICT's test lab) first, then by Alipay ([Tencent Cloud article](https://cloud.tencent.com/developer/article/1043485)); levels 1–4 ([blog](https://chujian521.github.io/blog/2024/12/07/IFAA%E6%8C%87%E7%BA%B9%E6%94%AF%E4%BB%98%E5%8D%8F%E8%AE%AE%E5%88%86%E6%9E%90/)) |

Both need a TA in the TEE (so that signing key), keys injected on the line (a station and RPMB), and the device's certification (which the device maker applies for). Kario as software can do none of these; the `security` field of §4.5 can be signed so that a server trusts it only inside this chain. Most of the SOTER and IFAA steps above come from third-party articles, not Tencent's or Alipay's official documents (**not verified**; the official integration documents have to be asked for as a device maker).

### 12.5 Can the QCM6490 run OP-TEE instead

| Does a production QCM6490 fused with a device maker's root accept a BL2 signed only by the device maker | **Not verified**. ### 12.6 What Kario needs from a module vendor

| Need | Why |
|------|--------|
| Who owns the secure boot keys, and who signs | Whoever's root is in the fuses is the only one who can sign TZ, TAs and the images after (§12.3); either the module ships unfused and Kario's device maker blows its own, or the module vendor signs for us |
| A signed TZ/QTEE image, or a signature for an OP-TEE swap | §12.5; plus how each later version is signed and by whom (a system update has to carry TZ updates, [25](25-system-update.md)) |
| The right to sign TAs for QTEE, or a TA SDK and documents | Fingerprint matching, PIN checks and the token key go into the TEE (R15); whether Qualcomm's TA SDK is given to a module vendor's customers is **not verified** |

| SOTER's ATTK and IFAA's keys injected on the line, and certification | §12.4; talking to Tencent and Alipay takes a device maker's standing |
| Trusted UI | The PIN reaching the TEE through a trusted input path (R15 in §9); whether the keypad and the screen work in the secure world depends on the chip and the module (**not verified**) |

## 13. Factory mode: the threat model

> Written on 2026-11-27 before the implementation, which follows it. Factory mode is the one boot on the line in which the phone's hardware is tested and its device certificate provisioned; the test itself (what it checks, how to run it) is in [40](40-testing.md) §10, the station's flow in [22](22-developer-api.md) §11, USB in [27](27-usb-typec.md) §3.4. What is implemented is at the start of [40](40-testing.md) §10; all of it is **not tried on a phone**.

### 13.1 What it is

When the bootloader has put `kario.factory=1` on the kernel command line and the keystore has no device certificate yet ([22](22-developer-api.md) §11), the phone does only the line's work for that boot: the Shell shows only the factory test's screens, and the test program `phone-factory-test --serve` answers the station over the USB network: it runs the automatic checks, hands over the report and forwards the three provisioning requests (`csr`, `attest`, `install_cert`).

### 13.2 What is protected

- The device's identity: the device key in the keystore, and the device certificate the factory signs. Relying parties (payment servers, the compatibility report's verifier) trust only the certifier's root ([22](22-developer-api.md) §11).
- The user's data on a phone that has been used: a developer's phone, a repaired phone, a lost or stolen phone.
- USB trust ([27](27-usb-typec.md) §3): a computer that is not trusted reaches nothing on the phone.
- What the lock-screen PIN (§3), the parental PIN (§10) and the anti-theft lock (§11.4) guard.

### 13.3 Attackers

| | Who | What they want |
|---|-----|----------------|
| T1 | Someone holding a sold (provisioned) phone, perhaps found or stolen | To get round the lock screen or the anti-theft lock through factory mode, read the data, use USB without trust |
| T2 | Someone holding a phone that is not provisioned: a unit on the line, a developer's phone (the OnePlus 6T) | To read its data; to provision it under their own CA; to make attestations with it |
| T3 | The computer at the other end of the USB cable (a public charging point, a hostile computer) | To get into the phone without trust |
| T4 | Software on the phone: an app, a service gone wrong | To put the phone into factory mode, or to use factory mode's interfaces |
| T5 | A station that makes a mistake | To record one phone's result against another |

### 13.4 The properties and how they hold

1. **Only while the keystore is not provisioned** (against T1). The gate is `provisioned` in keystored's answer to `csr` (`Store.Provisioned`: whether the device certificate from the factory is there). The certificate is under the keystore's `factory/`, which a factory reset keeps (`wipe.Keep`), so no wipe takes a provisioned phone back to factory mode. Everything that acts on factory mode asks again itself, when it acts: `phone-factory-gate.service` at boot (before the Shell, SMS and push), the Shell before it starts in factory mode, the test program when it starts serving, and every request of the station (`install_cert` too: keystored itself does not refuse a second provisioning). No answer (keystored silent for 30 s) counts as provisioned: refused. A refused boot is a normal boot, with the reason in the log.
2. **Getting in takes someone at the phone** (against T1, T3, T4). Only `kario.factory=1` on the kernel command line counts, and only the bootloader writes the command line. Why this and not a key combination at boot:
   - The bootloader gives the command line. An unlocked bootloader (a developer's 6T) needs `fastboot boot` of a boot image with the command line changed: the phone has to be in fastboot first (off, then volume up and power held), on the cable; the image is only in memory and lasts for that one boot. A locked bootloader starts only images signed with the product's key, the command line inside the signature: only the line's image carries it. QEMU gets it from `-append`.
   - A key combination needs Kario to read the keys early in the boot (neither systemd's generators nor the initramfs do), and differs from board to board; the 6T has three keys and the bootloader has taken their combinations (fastboot, recovery); anyone holding the phone can press it, and it gets pressed by mistake; only the gate of property 1 would be left, where the command line has to get past the bootloader first.
   - Software on the phone cannot write the next boot's command line: apps are in their sandbox and cannot touch partitions; what can write the boot partition is root already, and factory mode gives it nothing more (the gate still holds).
3. **The screen always shows factory mode** (against a phone in factory mode handed to someone as a normal phone). Every screen's title starts with "Factory test", and the status bar's middle says "Factory mode". The exception is the display check's full-screen colours and grid: the operator starts them with a key, and the next key or 30 s brings back a marked screen.
4. **No path to the user's data** (against T2, T3). In factory mode the Shell starts no app, signs in to no account, does not sync or register for push; its state directory is in `/run` (memory): nothing of the user's can it read, nothing it writes stays. `phone-smsd` and `phone-pushd` do not start for that boot: SMS and pushes the test SIM gets do not land in the data area. Over USB only the test program's one port (TCP 7171) and DHCP are open: no file sharing, no MTP, no SSH even in developer mode. The test program reads only sysfs and device nodes, and asks the services only for the state of the hardware (telephonyd's `status`, audiod, mediad), never for what they store.
5. **USB without trust only in factory mode** (against T3). In factory mode, as soon as a computer configures the phone, the link gets its address and DHCP (as after trust), and the firewall (`netfw.Link`) lets through only UDP 67 and TCP 7171. In every other state the trust flow of [27](27-usb-typec.md) §3 stays as it is: in the code it is one test before `askTrust`, and only a factory-mode boot takes the other branch. The factory link has no authentication and no encryption: on the line, the other end of the cable is the station. What a computer gets in factory mode is the report and the three requests below.
6. **The three provisioning requests are bounded** (against T2, T5). `attest` is always for the app `system.provision` with the station's nonce: it proves only that the phone holds this device key and cannot stand for any app's attestation. `install_cert` is forwarded only while the phone is not provisioned, and keystored still checks that the certificate is this phone's. Someone holding a phone that is not provisioned can provision it under their own CA: its attestations then chain to that CA's root, which relying parties do not trust, and factory mode is gone for good (property 1). That is a denial of service which needs someone at the phone; accepted. The station requires the device ID in the report to be the one in `csr` (`DEVICE_ID`) and stops otherwise (T5).
7. **Two ways out, and never a normal boot into a factory-mode state**. Provisioned: the screen says so and the phone powers off 10 s later (OK at once); the next boot is a normal boot, and factory mode is never available again (property 1). Erased: "Erase and restart" leaves a request as a factory reset does (§11.1) and restarts; the next boot empties the data area first (the device keys and the factory's files stay). Factory mode has no menu back to the normal system. Everything of it is in `/run`: the Shell's state, the test program's report, the link's networkd file, the gate's mark `/run/phone/factory/on`; a power cut or a forced restart (the power key held) ends it the same way: the normal boot after it finds nothing of factory mode, USB needs trust again, and apps and accounts are as they were.
8. **The report is no secret and holds none of the user's data**: the device ID, the SKU and the hardware values measured; not the IMEI.

### 13.5 Not covered, and the risks left

- An unlocked bootloader: whoever holds the phone can boot anything anyway; factory mode gives them nothing more, and the gate still holds.
- The factory USB link has no authentication: with a phone that is not provisioned in factory mode, anyone at the other end of the cable can read the report and provision it (property 6).
- Someone holding a phone that is not provisioned can "Erase and restart" it: the phone is in their hands already.
- A key combination at boot, and authentication between station and phone: not done ([40](40-testing.md) §10).
- A station testing several phones at once (the station (kario-internal), [22](22-developer-api.md) §11): every phone is `10.71.0.1`, so the station does not go by address; each connection is bound to that phone's USB interface (`SO_BINDTODEVICE`). If binding fails, or `rp_filter` drops the answers, the unit cannot be reached; it is never another unit that answers. The report's device ID must be the `csr`'s (property 6), and the certificates go to the phone that gave the `csr`. What is left: with interface names that do not match the ports (not fixed), the phone the operator sets aside by the station's line may be another one; a phone that got its certificates powers off by itself, which shows.
- All of the above is **not tried on a phone**.
