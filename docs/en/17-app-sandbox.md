# Limiting app behavior: sandbox, permissions, background

> Status: **prototype ✓**. The launcher `phone-sandbox`, the capability broker and background freezing are all implemented. On the device (QEMU, kernel 6.18) the sandbox self-check gives 13/13 as expected (§7). For remaining work see 57 (internal document) R47 (§8) and R55 (§9).

## 0. Summary

Android and iOS follow the same idea: by default an app can do nothing, and everything it is able to do has to go through the system. They differ in how this is implemented:

- **Android**: one uid per app, plus SELinux mandatory access control, seccomp system-call filtering, runtime permissions and background execution limits.
- **iOS**: sandbox profiles (Seatbelt), entitlements (privileges spelled out in the signature), code signing plus review; apps are suspended after they leave the foreground.

This platform confines apps inside seven layers. The **only channel** through which an app deals with the system is the connection (fd 3) that the Shell hands it at launch; everything else is denied at the kernel level.

| Layer | What it does | Counterpart |
|----|--------|------|
| 1. Channel | One process per app, which only gets fd 3; every capability goes through the Shell's broker, which checks the manifest permissions and runtime grants before forwarding | iOS XPC + entitlement; Android Binder + permissions |
| 2. Separate uid | One uid per app (starting at 10000), which owns only its own data directory; the sockets and key files of system services belong to root with mode 0600 | Android app uid |
| 3. Namespaces | Separate PID space (cannot see other processes), private `/proc`, IPC/UTS isolation; apps without the `net` permission live in an empty network namespace (not even local loopback) | Android process isolation; iOS without a network entitlement |
| 4. Landlock | File allowlist: system code read-only, read/write only in its own data directory; **cannot execute files it wrote itself** (W^X); cannot listen on TCP ports; cannot send signals to processes outside the sandbox or connect to abstract unix sockets outside the sandbox | iOS Seatbelt; the app domain of Android SELinux; Android 10 and later forbid executing from the data directory |
| 5. seccomp | Blocks debugging other processes, mounting, kernel modules, eBPF, perf, kernel keyrings, io_uring, creating new namespaces and so on, returning EPERM | Android app seccomp filter |
| 6. Resource limits | Core dumps disabled; 1024 file descriptors, 256 processes. On the device each app also has its own cgroup v2 group: 192 MB of memory, no swap, 128 processes; CPU weight 400 in the foreground, 50 in the background; Go programs additionally get a `GOMEMLIMIT` soft limit (144 MB). When the memory limit is exceeded, the kernel kills only that one app; when an app is stuck at its limit, the Shell ends it by its memory pressure (§5.4); either way the system shows 「超出内存上限」 (Memory limit exceeded). When system memory is tight, the Shell ends background apps first (§5.1) | Android memcg and lmkd; iOS jetsam |
| 7. Background freezing | Frozen about 10 seconds after leaving the foreground and resumed on returning to the foreground; apps that declare the VoIP background mode and hold the permission are exempt. On the device this uses the cgroup freezer, which stops the whole process tree together; on a dev machine without cgroup delegation, or on a kernel without the freezer (before 5.2), it falls back to SIGSTOP (to the app's whole process group) | iOS background suspension; Android cached apps freezer (also the cgroup v2 freezer) |

Beyond these seven layers there are four more:

- **Kernel layer**: every Kario kernel forces lockdown (integrity): it loads only modules signed with the build directory's key, and not even root can write `/dev/mem` or writable debugfs files or kexec an unsigned kernel; apps are kept from loading modules by seccomp anyway (§4), this layer is about the system's own processes ([39](39-oneplus-6t.md) §8.3).

- **UI layer** (already in place): apps can only submit semantic nodes and cannot draw system dialogs; they cannot read raw key presses (the input method belongs to the system, [16](16-input-method.md)), cannot read the screen and cannot read other apps; secure screens are masked in screenshots and screen recordings.
- **Distribution layer**: app packages are signed, and the permissions in the manifest play the role of entitlements; at install time the signature is verified and the system shows a confirmation dialog; before the first launch after boot the files are checked again, and modified ones are not allowed to run; packages signed by the development store can only be installed and run in developer mode; uninstalling also deletes the app's keys ([22](22-developer-api.md) §12).
- **Protocol layer**: each message an app sends is at most 4 MB, a page has at most 1000 nodes, and the page stack is at most 32 deep; at most 5 notifications per minute get a banner and an alert sound; when a foreground app is stuck, the system shows 「没有响应」 (Not responding) after 5 seconds (§5.2).

**Per-app data usage and Wi-Fi only** (package `netfw`, needs root on the device): each app has its own uid, and the Shell builds a table `inet phone` in nftables that matches outbound traffic by the socket's uid and inbound traffic by the connection mark (the outbound rule sets the connection mark to the uid, so reply packets can be attributed). There is one named counter per app, per network type and per direction; packets a Wi-Fi-only app sends from a non-Wi-Fi interface are dropped and the app gets EPERM, so it fails immediately instead of waiting for a timeout; an app whose mobile data is blocked (background data off while it is not on the screen, or its own data limit used up, [19](19-core-apps.md) §1.3) gets the same rule, changed as soon as the block changes. The rules are replaced as a whole in one transaction, and the counters live outside the rules, so changing the rules or restarting the Shell does not reset them. Every 30 seconds, when the 「流量」 (Data usage) page is opened, when an app is uninstalled and at normal shutdown, the Shell atomically reads and resets the counters (`Harvest`) and adds them, per day and per app, into the data usage record (`data-usage.json`, [19](19-core-apps.md) §1.3, with the data plan); a Shell crash loses nothing (the counts are still in the kernel), and only a power loss drops the portion since the last read. A kernel without named counters (nf_tables stateful objects, Linux 4.10) cannot have the table: there is no per-app data usage and no Wi-Fi only, background data and the apps' own limits are the Shell's policy alone (the app is told, its jobs wait for Wi-Fi, its connections are not stopped), and the data usage page has the totals by network alone (the interfaces' counters). A few conventions: loopback (traffic between local services) is not counted; interfaces whose names start with `wl` count as Wi-Fi and all others as mobile networks, and an unrecognized interface is treated as a metered network; it uses a pure-Go netlink library (`google/nftables`), so the image does not need the `nft` command-line tool (which would pull in GPLv3 readline). The kernel needs conntrack and `nft_ct`: the image installs the `nft_ct` module package, and the kernel loads it automatically (together with conntrack) the first time a rule uses the connection mark. While the personal hotspot ([22](22-developer-api.md) §4.5) is on, the same table has two more chains: `share-nat-hotspot` (nat, postrouting) masquerades what the hotspot's subnet sends out of the default route's interface as the phone's address; `share-fwd-hotspot` (forward) lets through only the hotspot's packets to the default route's interface and the replies coming back, so the devices on the hotspot reach no other interface through the phone; what it lets through is still dropped by the mobile data cut (a drop in any chain counts). When the hotspot goes off both chains go. Masquerading needs `nft_masq`, `nft_chain_nat` and `nf_nat`: the image installs these module packages, and the kernel loads them the first time the rules are added (✓ on the emulator, the selftest 个人热点（模拟器）). On a dev machine the Shell is not root, so this feature is not available, and Settings says so accurately.

**The VPN and the per-app firewall**: while a VPN ([11](11-platform-architecture.md) §16) is connected, apps' packets leave by the tunnel's interface `kario-vpn`, and the firewall still tells them apart by the app's uid and counts them; the tunnel's own encapsulated UDP packets come from the kernel's WireGuard, under no app's uid, so no per-app rule holds them up. The tunnel counts as the network under it: every 5 seconds the Shell asks which interface the tunnel's own packets (carrying its firewall mark) leave by; if it starts with `wl`, `kario-vpn` counts as Wi-Fi too, otherwise as mobile, so a “Wi-Fi only” app may use the tunnel while it rides Wi-Fi and cannot send while it rides the mobile network, and Settings › Data usage counts by the network underneath. With mobile data off the firewall closes the cellular interface, and a tunnel over it goes down with it. When the always-on VPN has 「屏蔽未使用 VPN 的连接」 (Block connections without VPN) on, the same table gets an output chain `vpn-lock` (`netfw.Lock`, ahead of the per-app rules, and it only adds drops): there whether the tunnel is up or down, it drops every packet but loopback, the tunnel's interface `kario-vpn`, packets carrying the tunnel's firewall mark (the tunnel's own, and the apps per-app routing keeps out), UDP to the VPN's servers, DHCP (68 to 67, 546 to 547), IPv6 router solicitation and neighbour discovery, and the interfaces that lead only to devices nearby (the USB cable's, and the hotspot's while it is on); an app gets EPERM at once. For a server given by name it also lets uid 0 ask DNS servers (the Shell resolves the name itself with the upstream DNS servers; systemd-resolved's and the apps' queries stay blocked). Per-app VPN (`netfw.Apps`): an output chain of the route type, `vpn-apps`, gives packets the tunnel's firewall mark by their socket's uid (in 「只有选中的应用」 (only the chosen apps) mode those of the apps not chosen and of the system, in 「除选中的应用外的全部」 (all but the chosen apps) mode those of the chosen apps; an app's web views go with it), and the kernel routes them again: a packet with the mark does not look up the tunnel's table. A socket picked the tunnel's source address when it connected, by the route without the mark, so such a packet leaving by another interface is masqueraded as that interface's address by the nat chain `vpn-apps-nat`, and the replies find their way back (this relies on loose reverse path filtering, systemd's default `rp_filter=2` in the image). Not covered: when the tunnel moves to another network, the rules follow within 5 seconds; apps without the network permission are in an empty network namespace, where the VPN does not reach them; without the block, while the tunnel is down or coming up apps' traffic goes over the network underneath; what the phone forwards for the hotspot's devices goes past the VPN, and the block does not hold it; a full tunnel takes over only the address families in AllowedIPs (with only 0.0.0.0/0, IPv6 bypasses it, as with wg-quick); the block's and per-app VPN's emulator cases ✓ (2026-11-27 night chain r86), **not tried on a phone**.

## 2. Launch flow

```
Shell (root)
  │ clone(NEWNS | NEWPID | NEWIPC | NEWUTS [| NEWNET, when there is no net permission])
  ▼
phone-sandbox (in the new namespaces, still root at this point)
  │ 1. mount a private /proc (sees only itself)
  │ 2. rlimit: core 0, fd 1024, processes 256
  │ 3. setgroups([]) → setresgid / setresuid(app uid): drop all privileges
  │ 4. create TMPDIR (tmp/ under the data directory; there is no shared /tmp)
  │ 5. no_new_privs: no later exec can gain privileges again
  │ 6. Landlock ruleset → restrict_self
  │ 7. seccomp filter (all threads; with prctl on this thread where the kernel has no seccomp())
  │ 8. execve(app); the environment variable PHONE_SANDBOX lists the layers actually in effect
  ▼
App process: only the fd 3 path is left
```

- Once applied, the restrictions cannot be revoked, and the app inherits them across exec. This is the same approach as Android's minijail and Chrome's sandbox.
- On a dev machine the Shell is not root and can only apply the layers that need no privileges: rlimit, seccomp, and Landlock when the kernel supports it (this dev machine runs kernel 4.18, which has no Landlock). The 「沙箱自检」 (Sandbox self-check) in Settings marks the checks that do not apply as 「跳过」 (Skipped).
- If the Shell runs as root but cannot find `phone-sandbox`, it **refuses to launch the app** instead of falling back to an unrestricted state.
- **System helpers** (for now only file sharing with a computer, `phone-usbshared`, [27](27-usb-typec.md) §3.2) go through the same launcher with `helper` in the policy: namespaces and uid as above, but no data directory and no device let through, and Landlock lets them read and run their own program only. Once the helper holds its inherited fds it adds a seccomp layer of its own (`sandbox.DescriptorsOnly`, layer name `fd-only`): exec, new sockets (socket, socketpair, bind, connect, listen) and file operations by path return EPERM. That layer needs neither root nor Landlock, so the development machine has it too: there the layers in force are "rlimit · seccomp · fd-only". A Shell running as root that cannot find the launcher refuses to start the helper as well.

## 3. Landlock rules

| Path | Access |
|------|------|
| `/usr` `/lib` `/lib64` `/bin` `/sbin`, the app's install directory | Read, execute |
| `/etc` `/proc` | Read |
| With the `net` permission: the directory `/etc/resolv.conf` finally links into (on the image systemd-resolved's `/run/systemd/resolve`) | Read. The whole directory, because resolved replaces the file as the network changes; without this rule an app cannot read the resolver's configuration, asks `127.0.0.1:53`, where nothing answers, and resolves no name at all (Go apps and web processes alike). The selftest case "DNS in the sandbox" checks on the device that Chat, which has `net`, can read it and Settings, which has not, cannot |
| Vendor root public key (a single file) | Read |
| Its own data directory (including `tmp/`) | Read/write, create and delete files; **no execute** |
| `/dev/null` `/dev/zero` `/dev/urandom` `/dev/random` | Read/write |
| Everything else | Denied |
| TCP | Cannot listen; without the `net` permission cannot connect either |
| Scope | Cannot send signals to processes outside the sandbox, cannot connect to abstract unix sockets outside the sandbox |

The newer the kernel's Landlock ABI version, the more it can control. The launcher enables the rules that match the version and degrades automatically on older kernels.

## 4. seccomp blocking

System calls that return EPERM:
- Debugging and reading/writing other processes: `ptrace`, `process_vm_readv/writev`, `pidfd_getfd`.
- Changing the file system view: `mount`, `umount2`, `pivot_root`, `chroot`, and the new mount API (`fsopen` and so on).
- Creating new namespaces: `unshare`, `setns`, `clone` with namespace flags. `clone3` returns ENOSYS so that libc falls back to `clone`, whose flags can be checked.
- Kernel modules and kernel replacement: `init_module`, `finit_module`, `delete_module`, `kexec_*`, `reboot`.
- Interfaces with a large kernel attack surface: `bpf`, `perf_event_open`, `userfaultfd`, keyring calls such as `keyctl`, `io_uring_*`.
- System state: `swapon/off`, `acct`, `quotactl`, changing the system time (`settimeofday` and so on), `syslog`, `open_by_handle_at`.

On an architecture mismatch (for example a 32-bit call executed on AArch64) the process is killed outright.

## 5. Background freezing

- When an app leaves the foreground, it first receives a `lifecycle: background` message and has 10 seconds to save its state (this is when the SDK calls `OnSave` and hands the system what it needs to rebuild its pages, §5.3); after that it is paused with SIGSTOP. Before it returns to the foreground it is resumed with SIGCONT.
- Exceptions:
  - Apps that declare `"background": ["voip"]` in the manifest and hold the `voip` permission (a chat app has to receive incoming calls);
  - Apps that are in a call;
  - Apps that declare `"background": ["audio"]` and are currently playing (music). Once playback is paused or finished, they are frozen as usual.
- While an app is frozen, the messages the Shell sends it queue up in the connection buffer and are handled after it resumes; the Shell itself never blocks because of this.
- Push ([21](21-push.md)):
  - Messages that carry only a title and body are displayed by the system and do not wake the app;
  - Messages that carry data resume a frozen app for 3 seconds, or launch it in the background if its process is not running, at most 20 times per app per hour;
  - VoIP pushes are not limited.
- An app's own long connection ([21](21-push.md) §8): an app with the `keepalive` permission (the store reviews every version) is frozen all the same, but its one connection stays: the kernel keeps the TCP connection, and when data comes the system thaws it for 3 seconds (at most 20 times an hour); its heartbeats do not run on its own timers: the system thaws it for 2 seconds to send one in a wake that comes anyway (a push heartbeat, a push, background jobs), and wakes for it alone only when none came by the deadline, at most 6 times an hour; Settings › Battery lists these wakes per app.
- Scheduled background tasks ([22](22-developer-api.md) §4.7): an app registers "refresh every N minutes (at least 15)"; when the time comes, the system resumes it or launches it in the background under the same rules as push, sends a `job` event, and counts it against the same budget of 20 per hour. The weather app uses this to refresh every hour.
- With push available, Hongyan does not declare the `voip` background mode; it is frozen like any other app after leaving the foreground, and both messages and incoming calls rely on push ([21](21-push.md) §4). The `voip` background mode is still kept for apps that really need it, but using it is not recommended.
- cgroup, two approaches:
  - **App scopes** (used by the display service, `PHONE_APP_SCOPES=1`): each app gets a systemd transient scope `phone-apps.slice/app-<id>-<pid>.scope`, and the limits are handed to systemd as properties of the scope (`MemoryMax`, `TasksMax`, `CPUWeight`). After launching the app, the Shell calls `StartTransientUnit` over D-Bus to move it there; until then the sandbox launcher waits on a pipe, so the app's code never runs in the Shell's group. The Shell's own service group contains no apps, so after a crash systemd can restart the Shell, and the apps stay in their own scopes waiting for it to take them over ([11](11-platform-architecture.md) §14).
  - **Delegated subtree** (used by the boot selftest service): systemd hands the service's group to the Shell with `Delegate=yes` (the Shell confirms this by checking the `trusted.delegate` mark set by systemd; root has write access to every group, so checking write access proves nothing). The Shell first moves itself and the other processes of the service into a child group `shell`, then creates an `app.<id>` group for each app, and app processes are started directly in their own group (`CLONE_INTO_CGROUP`); where the kernel lacks it (before 5.7) the launcher first waits on a pipe until the Shell has moved it into the group, as with app scopes, so no app code runs in the Shell's group.
  - Freezing writes `cgroup.freeze`, which stops child processes too, and a SIGCONT sent by some other process cannot undo it.
  - On old kernels the Shell probes item by item at start (the freezer, `cgroup.kill`, `CLONE_INTO_CGROUP`, the memory, pids and cpu controllers, PSI and its triggers), does what is missing the old way or goes without, and says so ([24](24-sku-framework.md) §7.5).
  - Groups in the delegated subtree also get `memory.oom.group=1` (from 4.19): the kernel's OOM kill ends all the processes of the group at once, not only the biggest one (say, a helper process the app started), which would leave half an app behind with the Shell none the wiser. An app scope's files belong to systemd and the Shell does not write them; there systemd's `OOMPolicy` decides (**not verified**). No `memory.high` is set (§5.4).
  - After an app exits, the Shell reads `memory.events` (and whether it ended the app itself for being stuck at its limit, §5.4) to tell whether the exit was caused by exceeding the memory limit, then kills the processes left in the group (`cgroup.kill`; before 5.14, which lacks it, SIGKILL to each process in the group until it is empty), waits until they are really gone (`cgroup.kill` does not wait) and deletes the group; on the next start, a group left from before is killed and deleted first and a new one made. The page cache a dead process tree leaves stays charged to its old group, and a kept group counts it against the new processes: in the low-memory stress test, the browser's web process after a revival from its tombstone was over WebKit's limit the moment it started, and the next one hung on its page. Web process groups are handled the same way.
  - The code is in `shell/cgroup.go` and `scopes.go`.

### 5.1 When memory is tight: low-memory cleanup

- System memory is checked once per second. It counts as tight when the available memory in `/proc/meminfo` (kernels before 3.14 have no `MemAvailable`: estimated as MemFree + Buffers + Cached − Shmem) is below 10% of the total, or when the memory pressure (PSI: the app group's `memory.pressure`, or `/proc/pressure/memory` when there is no cgroup) has `some avg10` above 20%.
- **End background apps' web pages first**: one app's web process can use several hundred MB (up to the per-model limit, 512 MB on a 2 GB model), so under memory pressure the Shell first ends the web process of one background app while the app itself stays alive; system apps (the browser) count too. When the user returns to that page, it reloads in a new process, the same way a browser discards background tabs. The choice follows the same order as for apps below, and within one category the web process using the most memory (the web cgroup's `memory.current`) is ended first. The web pages of the foreground app and of apps doing work in the background are left alone.
- When there are no background web pages left to end, background apps are ended one at a time (asked to end first, so that the storage write under way finishes, and killed only if still there after 1 second, §5.5), with a 2-second wait before re-evaluating. By category: first apps that have never been in the foreground (launched in the background by push or background tasks), then apps used a while ago, and last the two most recently used; within one category the app using the most memory goes first (the cgroup's `memory.current`, or resident memory when there is no cgroup), which frees the most at once.
- The foreground app, apps in a call, apps playing in the background and system apps are never chosen. An app ended this way does not count as a crash; it leaves a tombstone, and the next time it is opened it returns to its earlier pages (§5.3).
- The code is in `shell/lowmem.go`; the selftest uses `mem-low` to simulate memory pressure, and the web view case checks that the web pages of the browser and of Hongyan are ended first, that the apps are still there, and that the page reloads after going back to it (`pages-ended`).

### 5.2 Hangs and crashes

- **Not responding**: after the user does something in the foreground app, the system sends `ping`, and the SDK answers `pong` in the same loop that handles actions. If no answer arrives within 5 seconds, the system shows the dialog 「没有响应」 (Not responding): 「等待」 (Wait) gives the app another 5 seconds, 「关闭应用」 (Close app) ends it; if the app recovers, the dialog disappears by itself. An app waiting for the system to answer one of its capability requests (for example while a grant dialog is still open) does not count as not responding; nor while the Shell rests from it for the loop time it took (reading its next message later, the limits in [22](22-developer-api.md) §8.1); nor for the time the Shell's own loop stood still (waiting for the disk, the process not given the CPU), when the app's `pong` may have been waiting behind it; background and frozen apps are not checked (`shell/anr.go`).
- **Crash log**: when an app exits on its own with a non-zero exit code, the system records the time, version, reason and the last 20 lines of its log, keeping at most 50 entries (`shell/crash.go`). Apps ended by the system (low-memory cleanup, exceeding the memory limit (the kernel's OOM kill, or the Shell ending an app stuck at its limit, §5.4), the user choosing close in 「没有响应」, uninstall) do not count as crashes.
- **Crash loop**: an app that crashes 3 times within 10 minutes is temporarily not launched in the background by the system; push and background task data are held until the user opens it.

### 5.3 Tombstones: a background app that was ended comes back as it was

- When the low-memory cleanup ends a background app (§5.1), the system keeps its tombstone: the last state the app handed to the system (when the app leaves the foreground the SDK calls `OnSave`, and the state comes up in a `state` message, at most 64 KB of JSON, [22](22-developer-api.md) §3) and its page stack at that moment. The app stays in 「切换应用」 (Switch app).
- When the user returns to it (from 「切换应用」, the main menu or a notification alike; also when a push or a scheduled task launches it in the background first), the system immediately shows its earlier pages and at the same time starts a new process, whose `start` message carries that state (the SDK's `Restore`), and the app rebuilds its pages from it. When a rebuilt page has the same screen ID as before, the system puts back the half-typed text in its input fields and the focus exactly as they were, so the app does not have to save them itself. Until the new pages arrive, the old pages are only displayed (their actions belong to the process that has already ended): keys pressed meanwhile are kept (up to 32) and handed to the app once its new pages are all there, and Back returns to idle as usual; the same goes for keys pressed during a cold start before the first page appears. Keys always go only to the foreground (focused) app: the kept keys are its own, only its new process is not ready yet; once it is no longer in front (the user went back to idle or switched to another app) they are dropped, never handed to anyone else. Android's InputDispatcher does the same: while the focused window is not ready for input, key events wait in its queue for it (and an app that keeps them waiting too long is reported as not responding) instead of being dropped or given to another window.
- A tombstone is kept for one day only; none is kept when the user ends the app in 「切换应用」, when the app is updated or uninstalled, or when the app exits or crashes on its own.
- When an app the system has just ended (for whatever reason) is opened again before its exit has come in, the system starts the new process on top as soon as the old one is gone, instead of putting the dying one on screen and falling back to the home screen when it exits (`shell/relaunch_test.go`).
- This is the same approach as iOS (snapshot plus state restoration); on Android the system keeps the Activity stack, and each page is rebuilt from its saved Bundle.
- Selftest: Hongyan opens the conversation with 张三 (Zhang San), writes 「明天见」 ("See you tomorrow") in the input field without sending it, and goes back to idle; `lowmem-kill` ends it the way the low-memory cleanup does; going back from 「切换应用」, it is still in this conversation, the draft is still there, and pressing OK sends it. The code is in `shell/tomb.go`.

### 5.4 Stuck at the memory limit: ended by memory pressure

- **The problem** (found on QEMU, 2026-11-23): when an app's group reaches its `memory.max`, the kernel first reclaims what of the group it can. Without swap, all it can reclaim are the file pages charged to the group, that is the app's own program and libraries; they are read straight back in, every round of reclaim frees a little, and so the kernel does not declare OOM. The compatibility case 「应用超出内存上限」 (app over its memory limit), run alone in 10 boots, thrashed like that for 15–58 s in 5 of them and took 4.1–4.5 s in the other 5: while it thrashed, the group held 190 MB of anonymous pages and 0 MB of file pages, read back 10,000–27,000 pages a second (median about 17,000: its roughly 4 MB of program read back a dozen times or more a second), `max` in `memory.events` rose by about 700 a second, and all its tasks were waiting on memory (PSI `full`) mostly 55–70% of the time, until the kernel's OOM killer finally ended it. On a phone that is an app frozen for tens of seconds instead of ended at once.
- **What the Shell does** (after Android's lmkd, per app): it watches each app group's `memory.pressure` and `memory.events`. When, over the last 2 s, all the group's tasks waited on memory at least half of the time and its usage was at the limit all along (`max` went up between every two samples), the Shell ends the app just as the kernel's OOM kill would: only that app, with 「超出内存上限」, not counted as a crash (§5.2). An app at its limit for 2 s that is not stuck enough to be ended gets an `at its memory limit` line in the Shell's log every 10 s, with how much of those 2 s it waited on memory (for setting the thresholds and checking them on a phone). Where the kernel has PSI triggers (from 5.2), the Shell sets a trigger of "500 ms of `full` in 1 s" on the group's `memory.pressure` and waits on all the apps' triggers with one epoll; its housekeeping (every half second with the screen on, every 5 s with it off) samples too, and is all there is without triggers. The kernel's own OOM kill stays as it was: when it comes promptly (in the 5 runs that did not thrash, less than a second at the limit) the Shell does not step in.
- **Why half the time and 2 s**: on QEMU a thrashing group, over every 2 s, had a `full` median of 60–63%, a 5th percentile of 56–60% and a lowest of 49%; a group whose page cache filled its limit while it read files had at most 19% over 2 s (31% over half a second). The whole 2 s count, without requiring each half second in it to be over half: with that requirement an app thrashing at its limit for 24 s was never ended by the Shell, because now and then a half second below half made it count from the start again. lmkd's "critical" level defaults to 700 ms of `full` in 1 s, which the thrashing groups on QEMU rarely reached.
- **Results on QEMU** (2026-11-23, with the fixed image): 「应用超出内存上限」 alone, 20 boots in a row, passed all 20 times in 4.0–9.9 s: the Shell ended the app in 10 (all its tasks waiting on memory 50–68% of those 2 s), the kernel's OOM kill came first in the other 10 (9 in 4.0–5.1 s; one at 9.9 s, whose 2 s had only 42%, under half). Before the fix the same 10 runs took 15–58 s in 5 of them. The whole compatibility run (10 cases) passed 3 times in a row, this case taking 2.6–7.0 s there; 「应用读大量文件」 alone passed 5 times, its 2 s at the limit with only 3–5% waiting on memory in the log, and the Shell did not end it.
- **No false kills of apps reading files**: reading files also reclaims at the limit, but clean page cache is reclaimed cheaply and what was read is not read back. The compatibility case 「应用读大量文件，页缓存占满内存上限时照常运行」 (an app reading many files keeps running while its page cache fills its memory limit): the probe reads 400 MB from `/usr` with only its own small heap, then again holding another 96 MB (dropping each file's cached pages first, so that what it reads in is charged to its group); the case requires that the group really reached its limit (`mem-event … max 1`) and the app is still running. Writing files (dirty pages have to be written back before they can be reclaimed) was not tested: the selftest's data directories are on tmpfs, where what is written is memory that cannot be reclaimed (**not verified**).
- **No `memory.high`**: above it the kernel slows the app's allocations down (reclaim, then a sleep of up to 2 s each time), trading "ended at once" for "slowly stuck", which is exactly what this avoids; Go apps' `GOMEMLIMIT` already makes their garbage collector work harder before the hard limit.
- **When the kernel lacks it**: without PSI (before 4.20, or booted with `psi=0`) there is only the kernel's OOM kill; with PSI but no triggers (before 5.2) there is only the housekeeping; both are reported among the kernel features (`psi`, `psi-trigger`, [24](24-sku-framework.md) §7.5). QEMU's kernel and the Nura configuration the 6T uses both have `CONFIG_PSI` on and `CONFIG_PSI_DEFAULT_DISABLED` off; Kario's kernel fragment `phone-power.cfg` requires it too (checked at build time by `do_phone_kconfig`).
- Web process groups are not watched (**not implemented**): a page stuck at its limit leaves the app itself working.
- App scopes (the display service) are watched the same way, the triggers set on the scopes' groups; the selftest on QEMU uses the delegated subtree, so on scopes it is **not verified**.
- The code is in `shell/memstall.go`; unit tests in `shell/memstall_test.go` (the decision; on fake group files, the stuck app is ended, told to be over its limit, with no crash record, while the one reading files runs on). On the OnePlus 6T **not tried on a phone**; what to confirm there is in [39](39-oneplus-6t.md) §14.12.

### 5.5 Ending an app: asked first, killed only after a grace

- **The problem**: a runtime's storage is written by a thread of its own in the background (kario-jsrt's `jsrt/src/store.c`, the Node engine's `sdk/ts/node/kario.mjs`); a save returns to the app at once and is on disk when `flush()` resolves (the `storage` row of [22](22-developer-api.md)). The Shell used to end apps with SIGKILL every time, so the write under way was lost, the file keeping its last whole version, after the app had already told the user it was saved.
- **What the Shell does** (`shell/endapp.go`): it first shuts down the sending side of its end of the connection (`shutdown(SHUT_WR)`; a copy in systemd's fd store as well), and the app, reading the end of its connection, exits by itself: kario-jsrt and Node once the write under way is done, the Go SDK's `Run` once the messages it has read are handled, the mini-program host once its runtimes have saved ([29](29-app-development.md)). What the app still sends is read (the state it hands over, say); the Shell sends it nothing more, and pushes, background jobs and notification actions that come meanwhile are kept for its next process, which the system starts in the background once the old one has exited. A frozen app is thawed first (a frozen process does not read the end of its connection), it is not frozen again during the grace, and the "not responding" dialog no longer comes up for it. Only if it is still there when the grace is up is it killed with SIGKILL, what it left running ending with it as usual (§5). The wait does not hold up the Shell's loop: a timer posts the kill to the loop when the time comes.
- **Why not SIGTERM to ask**: a Go app that does not handle SIGTERM dies at once, losing as much as with SIGKILL; and on the device an app is process 1 of its pid namespace, to which the kernel delivers no default-action signal: kario-jsrt used to send itself SIGTERM again with the default action once its write was done, so the process did not end and every TypeScript app took the whole grace (checked on the developer machine with `unshare -U -r -p -f`). Now it handles SIGTERM from its start and exits with status 0 once its writes are done; nor can its own `abort()` end it by the signal, so it exits with 128 + 6, which the Shell still records as a crash (`TestStorageSIGTERMFirstProcess`, `TestNativeCrashFirstProcess`, `TestShutdownTypeScriptAppAsFirstProcess`, failing on the old code). At shutdown the Shell still sends SIGTERM and waits at most 3 s (`stopGrace`).
- **The grace on each path**:

| Path | Grace | Why |
|------|-------|-----|
| Low-memory cleanup (`shell/lowmem.go`; the selftest's `lowmem-kill`) | 1 s (`shortGrace`) | Memory is short, so it must be quick; the cleanup waits 2 s (`lowMemSettled`) before it picks the next one anyway; an app with nothing to write exits as soon as it reads the end; 1 s is enough for slow flash to sync a 1 MB store |
| The user closes it in "Not responding", or stops it from the background battery notice | 1 s | The app's loop may never read the end (stuck, spinning), while its storage thread finishes the write regardless; the stuck page and the spinning CPU do not stay longer |
| App update, uninstall (`shell/install.go`) | 3 s (`endGrace`, as at shutdown) | Memory is not short and nobody waits for it; on an update the new version is in place at once, opening the app after the old process has exited starts the new version, which reads what the old one finished writing; on an uninstall the files and the data are deleted at once as before, and nothing written later can land in the deleted directory |
| "Stop running" in Switch apps, the restart for a language change, network permission changed from "denied" to allowed, minor mode hiding the app, the developer's reload / restart, the system update's health check ending the Settings it started in the background, a frozen app's queue filling up | 3 s | As above |
| A protocol or limit violation (`shell/guard.go`), a store takedown, stuck at its memory limit (§5.4), network permission changed to "denied" | None: SIGKILL at once | A grace would keep running what has to stop: a violating app would go on violating, a taken-down (possibly malicious) one would keep running, a stuck one would stay stuck (it could not write anyway), and the network just taken away would stay usable for a few seconds |

- Not among them: an app that closed its connection itself but whose process stays is killed after 5 s (`connGoneGrace`); when the Shell itself is killed its apps die with it (`Pdeathsig`), which cannot wait; the selftest's `appkill` kills at once, as the kernel's OOM killer does; web processes (§5.1) are not apps and are still ended at once. The mini-program host gives each of its runtimes 5 s; when the host itself is ended, the grace the Shell gives it is what counts.
- Tests: `shell/endapp_test.go` runs `jsrt/testdata/storage` under the real kario-jsrt, with `jsrt/testdata/slowfs` preloaded so that each fsync takes 0.4–1.5 s longer: it saves a and waits for its write, saves b, and right after its acknowledgement triggers the low-memory cleanup, ends the frozen app, updates, uninstalls, gives the network back; each time the app exits by itself (it is not killed), the loop keeps turning meanwhile, and the file holds b (the uninstalled one leaves nothing behind). The code from before fails the same cases: the apps are killed with SIGKILL and the file still holds a. Also: a push for an app being ended goes to the process started in the background after it; network permission changed to "denied" kills at once. `shell/endapp_grace_test.go`: on a fake cgroup group a frozen app is thawed (`cgroup.freeze`) before it is asked, one that stays is killed with SIGKILL only once the grace is up, and `endApp` itself returns at once. On the developer machine freezing is SIGSTOP; the cgroup freezer was tested on a fake group only, on a real group **not verified**; on the OnePlus 6T **not tried on a phone**.
- Selftest: in 「KarioUI 计算器」 (KarioUI calculator) the calculator, once frozen in the background, is ended with `lowmem-kill`, and `ended-itself` checks that it exited by itself and was not killed once its grace was up; `ended-itself` is checked as well after the 「应用商店」 (App store) case uninstalls the notes app and after the 「TypeScript 应用」 (TypeScript app) case's `lowmem-kill`. On QEMU (the real sandbox, pid namespace and cgroup freezer) ✓ on both images (2026-11-27 night chain r86).

The Settings app plays an app that wants to do harm and tries each item in turn:

| Check | Expected | Layer relied on |
|------|------|----------|
| Read the device private key | Denied | Separate uid |
| Read another app's data | Denied | Separate uid |
| Connect directly to the key service | Denied | Separate uid |
| Execute code it wrote itself | Denied | Landlock |
| Write the shared temporary directories /tmp, /var/tmp | Denied | Landlock |
| See other processes | Denied | Namespaces |
| Access the network | Denied | Empty network namespace |
| Listen on a TCP port | Denied (Landlock: the bind refused) or Denied (No network: it binds, but nothing can connect) | Landlock (from ABI 4) / empty network namespace |
| Dangerous system calls (such as keyctl) | Denied | seccomp |
| Write its own data directory | Allowed | — |
| Read the vendor root public key | Allowed | — |
| Open the display device /dev/dri | Denied | Separate uid |
| Read the keyboard device /dev/input | Denied | Separate uid |

This checklist (`sandbox/selfcheck_linux.go`) is also used by the compatibility test suite (CTS): if a vendor weakens the sandbox, the CTS fails. The top of the page shows the layers actually in effect. Checks that depend on a layer not in effect are marked 「跳过」 (Skipped) and are not counted in the result.

"Listen on a TCP port" looks at the layer that really keeps the app's port to itself, and says which: where the kernel has Landlock's network rules (from ABI 4), binding the port is refused (EACCES), shown as 「拒绝（Landlock）」 (Denied (Landlock)); a bind that goes through then fails the check, even though the namespace would leave it unreachable, so on kernels with Landlock's network rules (QEMU, Kario's own) the strongest result is still demanded. Without those rules (Nura's kernel, the developer machine) binding needs no interface up and goes through in the app's own network namespace; what keeps everyone else out is the namespace, whose `lo` is down, so not even a connection to its own port gets through (ENETUNREACH), shown as 「拒绝（无网络）」 (Denied (No network)). Before, the item only did `net.Listen` and was always "Allowed" on a kernel without Landlock ([41](41-design-gaps.md) §11). The compatibility probe logs which layer it was (`sandbox: … stopped by the … layer`). A unit test runs the item in a new network namespace (`sandbox/selfcheck_test.go`, failing before the change).

## 9. Untrusted input and fuzzing

Besides apps, the system reads a lot that others wrote: the computer at the other end of the USB cable, Bluetooth peers, NFC readers and cards in the field, SMS from anyone, files from the store and the update server (the part read before the signature is checked), music copied in. The code that reads them is written as if the input were hostile: sizes are bounded first, loops have iteration caps, recursion has a depth cap, and a failure is an error, not a crash, a hang or all the memory. Parsing runs in a sandboxed process where it can (`phone-usbshared` for USB sharing, the system services); what the Shell reads itself (the music library scan, installing packages, OBEX, the pages apps send) has to hold all the more, because when it falls over the whole UI goes. Third-party decoders (go-mp3, oggvorbis) panic on damaged files; we `recover` at the boundary where we call them and treat it as a damaged file, so phone-audiod does not exit.

Each of these parsers has Go native fuzz targets (`go test -fuzz`): no panic, no hang (an asynchronous part that has not ended after 10 seconds fails), input sizes bounded first, and the invariants that are cheap to check (decode, encode, decode gives the same; what parses has bounded output; oversized input is refused; the library only gets names inside its folders, and so on). The seed corpora come from real messages (the data of existing tests, the files in `audio/testdata`, sessions built by protocol in code); failing inputs stay as regressions in each package's `testdata/fuzz/<target>/`, and `make test` runs the seeds and these regressions every time. The C and C++ parsers (libphoneui's line reader, telephonyd's JSON and request handling, kario-jsrt's WebSocket frames and handshake answers, fetch's response headers, TextDecoder's UTF-8 decoding) are built with the address and undefined behaviour sanitizers (ASan, UBSan) into small programs that Go fuzz targets feed through a socket or a pipe (`tools/cfuzz`); the same harnesses are also built with clang as libFuzzer targets, which mutate in process by the code's coverage (`make fuzz-libfuzzer`).

The system services' RPC and the Shell's app messages are handled with state, and their targets run with it. The services' targets (`FuzzRPC` in `programs/<service>`) all go through `wire/rpcfuzz`: the service's real handler sits on wire's server loop (`wire.ServeConn`, the path it takes when the service runs), with state of the test's own (a store in a temporary directory, simulated hardware); the input is lines, a line starting with `{` written as it is, any other one's first byte picking the method and the rest the params. Every line gets exactly one answer (a result, or an error with a message); the requests that wait (a scan, a card reader, a finger) all answer within 10 seconds once what they wait on is cancelled; results encode; an input allocates at most 16 MB plus 4 MB a line; no goroutine is left after it. telephonyd's target (`telephonyd/test/rpc_lines.cpp`) runs the real server and the simulated modem in process, moves the simulated clock on, and wants every line answered within 120 simulated seconds. The Shell's target (`shell`: `FuzzAppMsg`) starts a new Shell for each input and adopts a fake app process: its manifest declares every permission, the runtime ones granted up front (`granted`), and stand-ins that answer every call with an error at once hold the services' sockets; the lines are written as the app's messages, requests going through every check of the broker (the busy limits, the manifest, consent) to the capability, with the input's arguments. No panic; every request answered exactly once, within 20 seconds (the test says no for the user to every dialog that shows, pressing Esc; the three capabilities that wait by design, for an SMS code, a location fix, an NFC tag, are not timed); the Shell's event loop comes round within 5 seconds; an input allocates at most 256 MB plus 16 MB a line. The few capabilities that must not run on a shared machine are stopped before they are written (judged by the same decoding the Shell reads messages with): `switch.start` (listens on a TCP port), `net.keepalive` (connects to any host the arguments name), `account.add` (CardDAV discovery against the server in the arguments), and `settings.set` of the language or region (they hold for the whole test process and restart the app); the system bus points at an address that does not exist (the host's iwd and BlueZ are not touched), `hal.SysRoot` is a temporary directory, and the target is skipped when run as root.

### 9.2 How to run

`make test` runs every target's seeds and regressions (the seven C and C++ targets are skipped when the sanitizer builds are not there). `make fuzz` runs each target in turn, each for `FUZZTIME` (30 seconds by default) with `FUZZPAR` processes (8), after building the C/C++ sanitizer programs into `FUZZBIN` (`/tmp/fuzz/bin`). `make fuzz-libfuzzer` builds the seven harnesses with clang (`LF_CC`, `LF_CXX`; clang 19 at least: libstdc++ 14 declares the `std::expected` telephonyd's JSON uses only from clang 19 on) as libFuzzer targets (with `-DKARIO_LIBFUZZER`, `-fsanitize=fuzzer,address,undefined`) and runs each for `FUZZTIME` (seconds, minutes or hours), from the seeds in `tools/cfuzz/testdata/libfuzzer/<target>/` and the corpus grown in `FUZZCORPUS` (`/tmp/fuzz/corpus`); a failing input is written into `FUZZOUT` (`/tmp/fuzz/out`); a leak is a failure in the WebSocket frames and handshake answers, fetch's response headers, TextDecoder and telephonyd's request handling (not in libphoneui or telephonyd's JSON reading), as on the Go side. The harness of fetch's response headers is built with `FETCH_MAX_HEAD` at 8 KB: libFuzzer's inputs are at most 64 KB and the lines kept are never longer than those received, so the 64 KB limit is out of its reach. `make fuzz-list` lists both kinds of target (`ONLY` applies):

```
make fuzz                                   # 84 targets, 30 seconds each
make fuzz ONLY='usbshare|obex' FUZZTIME=10m # only the matching ones, 10 minutes each
make fuzz ONLY='FuzzRPC|FuzzAppMsg' FUZZTIME=2m FUZZPAR=4 # the system services' RPC and the Shell's app messages
make fuzz-libfuzzer FUZZTIME=10m            # the seven libFuzzer targets, 10 minutes each
go test ./usbshare/mtp -run '^$' -fuzz '^FuzzResponder$' -fuzztime 5m
```

`./shell:FuzzAppMsg` starts a Shell for every input and almost every input reaches new code and takes time to minimize (under one input a second for 4 processes together); on a shared machine it runs with fewer processes (`FUZZPAR=4`) and, like the Shell's other tests, under the test lock.

On GitHub: Actions › fuzz › Run workflow, or `gh workflow run fuzz -f targets='usbshare|obex' -f minutes=30`. `targets` is a regular expression on `make fuzz-list`'s names (empty for all), `minutes` the minutes per target (10 by default, at most 300). Each target runs in a job of its own: a Go target's corpus is in Go's build cache (`$(go env GOCACHE)/fuzz/<package>/<target>`), a libFuzzer target's in `FUZZCORPUS`; it goes into the Actions cache by target, and the next run carries on from the newest. A failing input (Go writes it into the package's `testdata/fuzz/<target>/`, to be committed as a regression once fixed; libFuzzer's is the raw bytes, reproduced with `/tmp/fuzz/bin/lf-<target> <file>`) is uploaded as the artifact `crashers-<target>` and fails the run. Like `platform`, it ends by keeping only the newest 3 runs of each workflow. On the development machine every `make fuzz` and `make fuzz-libfuzzer` target has run (2026-11-18, 5 to 10 seconds each); the workflow passes actionlint and was run once by hand on GitHub on 2026-11-19 (`targets` `libfuzzer|cfuzz`, a minute each), passed. On 2026-11-27 the harness of telephonyd's request handling turned out not to link on dev (`ims.cpp` missing), failing `make fuzz-harnesses` and `make fuzz-libfuzzer` as a whole; it is in `TELEPHONYD_RPC_SRC` now.

### 9.4 Not covered

- kario-jsrt (C, the TypeScript runtime on QuickJS) and native modules: the WebSocket frames and handshake answers servers send, fetch's response headers and TextDecoder have targets (§9.1); fetch's responses are libcurl's to read, and the part of `on_head` that works with libcurl (which response's headers count: not a 1xx's nor a redirect's that is followed; trailers dropped) has only the cases of `TestFetch*`; an audio stream's shared ring (`map_ring`) has no target; the files of capability replies are read as regular files only, with size limits ([22](22-developer-api.md) §9.2); QuickJS's, goja's and libcurl's own robustness is upstream's.
- Where fetch's response headers still differ between the engines ([22](22-developer-api.md) §9.4): Node's parser takes 16 KB of them at most, kario-jsrt 64 KB (Node's `--max-http-header-size` lifts it, which needs the arguments `kario run` starts Node with and the few places the tests start it changed: not done); a response with bare LF line ends goes on kario-jsrt (libcurl takes it) and is refused under Node; bytes outside ASCII read as UTF-8 on kario-jsrt and as Latin-1 under Node; the refusals other than a NUL's are worded differently; a request header named `__proto__` is never sent by Node's own fetch (however the runtime hands it over), while kario-jsrt sends it.
- What the Shell's app messages (`FuzzAppMsg`) do not reach: `switch.start`, `net.keepalive`, `account.add` and `settings.set` of the language or region, stopped before they are written; with stand-ins answering errors for the services, what a capability does after a service's normal answer (CardDAV discovery once `account.add` has sealed, a signed package being installed); with every dialog refused, what follows the user's yes; the host's radios (iwd, BlueZ), the paths only root takes (the clock, networkd's VPN, cgroups); the screen (`Frame` is never called, no web view starts); with one app per input, `intent.invoke` and `share.open` find no other app.
- What the system services' RPC targets do not reach: nfcd's `sim.tap` (the simulated reader polls in real time, every 0.6 s) is answered with an error; mediad's `player.*` comes without the video the Shell passes along, and its frames socket has only the length limit's regression; audiod plays only files in the fuzz directory (the Shell names only the apps' and the user's files); keystored does PBKDF2 for every input, two hundred or so a second; pushd talks to a gateway of the test's; the Shell's developer link (devlink) has no target; telephonyd also converts doubles straight to integers reading its state file and ModemManager, and §9.3 changed only the requests' side.
- telephonyd's two limits: the user's `apns.json` is not counted when read back (only telephonyd writes it); once the list is full Settings shows telephonyd's English words, untranslated like the other `apn.set` errors; tones are at most 32 a request and go to the modem without a rate limit.
- What runs only on the computer's side or reads only local data: `usbshare/mtp`'s usbfs descriptor parsing, the MTP Initiator, the input method dictionaries, the system's own catalogs.
- The standard library's and third parties' decoders themselves (PNG, JPEG, goldmark, goja, go-mp3, oggvorbis, opus-go): only tested through our call paths. The video still mediad hands back is, like a camera photo, limited to 8 MB and has its header (format, sides up to 4096) checked before it is decoded (`readPhoto`, `TestReadPhotoBounds`): mediad is a sandboxed service, and even a compromised one cannot make the Shell allocate an image that claims billions of pixels.
- telephonyd's reading of the modem (AT commands, ModemManager), mediad's video, the web view (WPE), the renderer protocol the two Rust renderers read: not done (Rust would need cargo-fuzz, and no dependency is added).
- C/C++ coverage: Go's fuzzing does not see the branches in C code, so `tools/cfuzz`'s seven targets mutate blind; their libFuzzer builds follow coverage (§9.2), but a libFuzzer crash has to be turned into Go's regression format (`go test fuzz v1`) by hand to get into `make test`.
