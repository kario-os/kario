# USB-C: charging, keyboards and mice, connecting to a computer

> Status: **prototype ✓ (QEMU)**. Plugging keyboards and mice in and out, and connecting to a computer (trust → password → copy files → unplug to stop), pass end to end on the emulator (dummy_hcd makes one virtual machine both the phone and the computer); since file sharing moved into a sandboxed process of its own (§3.2) it has passed on the emulator too (2026-11-14); recognizing PD fast charging has unit tests and is **not tried on real hardware** (that waits for a Snapdragon board, R16). File transfer over MTP (§3.3) has unit tests and passes the development machine's selftest and the emulator's (over dummy_hcd, with our own initiator and libmtp's tools); with real Windows, macOS and Linux computers it is **not verified on hardware**. The developer link's tools for the system (§4, §4.1: files to and from the phone, screenshots, keys and typing, the system's log, port forwarding, restarts, sideloading a system update, bug reports) pass their unit tests and selftest cases on the developer machine; the emulator cases over real SSH (pushing and pulling files, keys, the system's log, port forwarding) QEMU ✓ (2026-11-27 night chain r86), and they are **not on a real phone**; a non-root developer account is **not implemented** (§4.2). The hardware layer on the phone is in [11](11-platform-architecture.md) §"Then what is hal/".

## 0. Conclusions

- One USB-C port does three things: charging (the Type-C port controller's kernel driver does the PD negotiation; we only read the result), keyboards and mice (the phone is the USB host), and a computer (the phone is a USB device and shares files with it through a USB network link).
- Connecting to a computer follows the iPhone: a computer plugged in only charges the phone, and gets anything **only after the user taps "Trust" on the phone**; every connection has its own password, unplugging ends it, and the trust is not kept.
- No drivers to install: to the computer the phone is a CDC-NCM network adapter, which macOS, Linux and Windows 11 drive with their own drivers; on the computer a browser, or "connect a network drive" (WebDAV), opens it, with no computer-side software of ours. Settings › USB can change it to file transfer over MTP (§3.3), with which the computer's file manager shows the phone as a device.

## 1. Charging: USB PD

| Part | How |
|------|------|
| Negotiation | The kernel driver of the Type-C port controller (on the Snapdragon 662, the PMIC's Type-C block) negotiates voltage and current with the charger (PD, PPS); the phone's software takes no part |
| Reading the result | `hal/power` reads the power supply class (`/sys/class/power_supply`): in the USB supply's `usb_type` the bracketed entry is the current type; `[PD]` and `[PD_PPS]` are PD fast charging, `[DCP]` and the like a dedicated charger; older drivers report the type `USB_PD` directly |
| Telling the user | Plugging in a charger lights the screen with "Fast charging" or "Charging" ([28](28-battery.md)); the status bar still shows ⚡ and the level |
| What the phone draws | Connected to a computer, the phone as a USB device asks it for 500 mA (USB 2's limit, `MaxPower` in `hal/usbgadget`); the current a charger gives is negotiated separately by the port controller and has nothing to do with this |

To confirm on real hardware (**not implemented**): how far the mainline kernel's Type-C / PD driver for the Snapdragon 662 (PMI632) goes; the charging curve and thermal protection are the charger driver's.

## 2. Keyboards and mice: USB HID

- The kernel's USB HID driver turns keyboards and mice into evdev devices (kernel configuration `phone-usb.cfg`). A keyboard follows the same key path as the phone's own keypad, renderer → Shell ([11](11-platform-architecture.md)); a full keyboard's letters type directly.
- **Ones plugged in after start work too**: the renderer cannot open `/dev/input` once it has dropped its privileges, so the input helper forked before that opens new devices and hands it their descriptors ([23](23-renderer-protocol.md) §5). When one is plugged in or out the renderer sends an `input` message and the Shell logs it.
- **Mouse**: this is a keys-first system, and a mouse is keys first: the wheel moves the focus up and down (a horizontal wheel left and right), the right button is Back, the middle one Options. Moving the mouse brings up a pointer; pointing at an item and clicking moves the focus there and chooses it (as OK); a click on the soft-key bar is that soft key; typing hides the pointer, and with no pointer the left button is OK. The renderer turns the pointer position into a node (`tap`, [23](23-renderer-protocol.md) §3), and the Shell accepts only nodes of the frame it sent itself.

### 2.1 The phone as host: roles, allowing, power, while locked

> Status: unit tests ✓ on the developer machine (`hal/usbhost`, `shell`, `tools/sku_test.py`, phone-paint); the emulator case "USB keyboard and mouse plugged into the phone" is written but **has not run yet** (**not verified** on QEMU); **not tried on a phone**: the OnePlus 6T's kernel cannot be a host yet ([39](39-oneplus-6t.md)), and a dock's data role swap (DR_Swap) has not been tried against a real port controller. Mounting a USB stick once allowed is **not implemented**.

- **The board says whether it can be a host**: the SKU's `[usb]` ([24](24-sku-framework.md)): `host`, `vbus_ma` (the most the port gives on VBUS as a host, 500 by default), `controller` (only the buses under this controller; what the board wires inside to another controller, such as the flip's fingerprint sensor, needs no allowing by the user). On a board without `host = true` the Shell leaves the host side alone (`shell/usbhost.go`).
- **Held first, allowed after a look** (as USBGuard does, with the kernel's USB authorization): at start the Shell writes 0 into those buses' root hubs' `authorized_default`, so the kernel enumerates a device plugged in but binds no driver, and it draws one unit load (100 mA). dummy_hcd's bus (the side that plays the computer on the emulator, §3) is not held. With the housekeeping, every second, the Shell reads `/sys/bus/usb/devices`, parses the device descriptor and every configuration's interfaces from `descriptors`, which can be read for a device not allowed yet (the union of all configurations: a device can become something else by switching configuration, `hal/usbhost`), and decides one by one:
  - Keyboards, mice, other HID devices, hubs: within the budget, `authorized` is written and the device allowed; the kernel binds usbhid and the renderer's input helper opens it (above).
  - Storage (interface class 0x08): not yet. With the phone unlocked the Shell asks "Allow the USB storage “…”?" (a trust dialog, which refuses injected keys as trusting a computer does); while locked it says "Unlock the phone to use the USB storage" and asks after the unlock. Allowed, it is let in, and a toast says the phone cannot open USB storage yet; not allowed, it stays out until plugged in again.
  - A composite device that says it is storage and a keyboard (the usual shape of a BadUSB stick): asked about as storage, the question adding that it also says it is a keyboard or a mouse and, allowed, can type and click on the phone; until then its keyboard interface does nothing either.
  - One unplugged is forgotten, and a question about it taken down.
- **VBUS budget**: the devices allowed add up by their descriptors' bMaxPower (2 mA a unit on USB 2, 8 mA on USB 3), those behind a self-powered hub not counted (the self-powered bit in the hub's configuration descriptor, in every configuration); one past `vbus_ma` is not allowed, with "“…” needs N mA; the phone gives M mA. Plug it into a powered hub.", and is tried again once another goes and frees current. When the other end powers the phone (the phone's power role is sink, as with a powered dock), VBUS is not the phone's and there is no budget.
- **Hubs**: allowed, and the devices behind one are decided one by one as above; behind a bus-powered hub they count against the phone's budget.
- **Roles**: whether the port is host or device is the port controller's decision (the Type-C class `/sys/class/typec`, the `usb_role` class): with a device on the other end (a keyboard, a stick, an OTG cable) it is host and gives VBUS, with a computer it is device (§3); the Shell reads it into the log (`usb-c: host (source)`) and normally changes nothing. The exception is a powered dock or hub: it powers the phone, so the port starts as device by its power role; when the other end speaks PD, the port can swap data roles, and no host has reset the bus within 3 seconds (the device controller's state is not default, addressed, configured or suspended), the Shell writes `host` into the port's `data_role` once (DR_Swap), only once a plug, and leaves it if the other end says no. A computer resets the bus when plugged in, so it is never swapped away.
- **A keyboard plugged in while locked enters only the PIN** (as on Android): the renderer numbers each input device, the `input` message carries the number and the bus, and every key its device's number ([23](23-renderer-protocol.md) §3, `paint/src/kms.rs`). A USB or Bluetooth input device that appears while the phone is locked (also one plugged in when the renderer starts: a reboot is no way around it) is noted (`shell/inputlock.go`): on the PIN pad it has only digits, Backspace, Enter and Esc, without the pad only digits and Enter (with a PIN) or the unlocking Tab and `*` (keypad lock); not the call key (emergency calls), not `#` (erasing the phone after wrong PINs), not the power key, not the lock screen's shortcuts. A key dropped is logged by its name only, not what it typed; at the first one a toast says once what is held back: "This keyboard was plugged in while the phone was locked: it only enters the PIN until you unlock", for a mouse "This mouse was plugged in while the phone was locked: it works once you unlock", for anything else (a touchscreen), or when what is held back is of several kinds (one keyboard is often several input devices, a stick can be a keyboard and a mouse), "This input device was plugged in while the phone was locked: it is limited until you unlock"; that one toast counts for everything held back at the time, not one toast each. Guessing the PIN still waits phone-keystored's delays. After the user unlocks, the hold goes, and the next lock does not bring it back. The phone's own keypad and a keyboard plugged in before the lock are not affected; keys injected over the developer link have their own gate (§4). While locked the Shell ignores a mouse's click on a node (`tap`), so a mouse has only keys, its left button (OK) and wheel, and those come under this rule too.
- **A touchscreen plugged in while locked touches nothing**: the renderer gives every touch its touchscreen's number (`touch`'s `dev`, [23](23-renderer-protocol.md) §3) and follows each touchscreen's finger on its own. The Shell drops the touches (coming down, moving, lifting) of a USB or Bluetooth touchscreen that appeared while the phone was locked until the unlock: not even the PIN pad's soft key bar, a tap around it (Back) or a call ringing in. Each touch is logged in one line without its position, and the toast is as above. Its finger coming down and lifting during a touch on the phone's own touchscreen does not break that touch. The phone's own touchscreen (the OnePlus 6T's RMI4 and QEMU's virtio multitouch are on neither USB nor Bluetooth) is never held back, and every touch from a renderer that numbers none counts as the phone's own. Unlike a keyboard it cannot even enter the PIN: the phone is unlocked with its own keys or touchscreen.

## 3. Connecting to a computer: trust first, as on an iPhone

| Step | On the phone | On the computer |
|------|--------|--------|
| Boot | The phone is always a USB network adapter (CDC-NCM in configfs, `hal/usbgadget`), with MAC addresses derived from its serial number so the computer sees the same device every time; but the phone's side has **no address** | — |
| Plug in | The device controller's state becomes `configured` (the computer configured it; a charger does not), the screen lights up and asks "Trust this computer?" | The system sees a USB network adapter, gets no address and can reach nothing |
| Trust | The link gets `10.71.0.1/24` and a DHCP server (a systemd-networkd runtime configuration, gone after a reboot), file sharing starts, and a notification shows the address and an 8-digit one-time password | DHCP gives it an address; a browser opens `http://10.71.0.1`, or it connects to that as a network drive (WebDAV), with the password |
| Copy files | Four folders, `Photos`, `Videos`, `Music` and `Files` (always named in English), all readable and writable; what is added is saved through the system's own libraries (photos, the music library, files) and shows up in Photos, Music and "Files" as if saved on the phone (§3.1) | Download, upload; folders can be made in Music and whole folders copied |
| Unplug | Sharing stops, the address and DHCP are removed, the trust is forgotten, and "Stopped sharing with the computer" shows | The connection is gone |

- The password is compared in constant time; 10 wrong ones lock that connection, and sharing has to start again from the phone.
- A USB bus reset is not unplugging (Windows resets after an error; libmtp resets a phone it takes for Android when it lets go, which it does when DeviceInfo names `android.com`): the device passes through default and addressed back to configured, and sharing and the trust stay, and so does the question "Trust this computer?" while it is being asked (a computer often resets the phone right after it first configures it, as the emulator does: the question used to go and come back, and a confirmation pressed meanwhile was lost); only when it is not configured again within 15 seconds does it count as unplugged.
- **Asked on every plug** (report 008, 2026-11-27, **not tried on a phone**): in report 008 "Trust this computer?" showed only once, was gone after a press of the power key, and plugging in again never asked again. The Shell used to keep the dialog it was asking with when the dialog went without an answer, and never asked again. And the Shell reads the controller's state every second (every 5 seconds with the screen off): a cable pulled and plugged in again between two reads leaves the controller saying `configured` throughout, and the Shell took the cable for never moved: no question, and a trusted computer swapped for another still trusted. Now the charger's word counts: a charger (`online`) saying the cable is out makes `configured` an unplug too (the rule of the bring-up wake lock `phone-bringup-awake`), and a charger coming or going has the controller read again at once, not a second later; a board with no charger that can say (QEMU, a battery's status alone) still goes by the controller. So a cable pulled and plugged in again is a new computer, asked again, never the one trusted before. However the question's dialog goes (an answer, the lock, another screen closing it), the Shell forgets it is asking, and the next plug asks; a question the lock-screen PIN closed unanswered is no refusal, and it is asked again once the phone is unlocked if the computer is still there. Unit tests `TestUSBReplugBetweenReadsAsksAgain`, `TestUSBTrustEndsWithTheCableBetweenReads`, `TestUSBQuestionGoesWithItsOverlay`, `TestUSBQuestionClosedByTheLockAskedAfterUnlock` (all failing without this change), `TestUSBWithoutAChargersWord`.
- The firewall gives the USB link a chain of its own (`netfw.Link`, ahead of the per-app rules): before trust nothing gets in; once trusted only DHCP and file sharing (port 80) are let through, plus the debug shell (port 22) in developer mode; turning developer mode on or off with the cable in changes the chain at once, not at the next unplugging: off, 22 takes no new connection right away, and the connections already open drain before it closes to them (next item). So other services on the phone cannot be reached over the cable even when they listen on every interface. The selftest on the device checks that 80 is open and 22 closed, 22 open once developer mode is on, and closed again when it goes off with the cable in (no new connection gets in; unit test ✓, QEMU ✓).
- When developer mode goes off, the SSH connections already open drain; the phone does not reset them. The Shell ends the developer link's requests within a second, and the session's end, the computer's acknowledgements of the phone's data and the computer closing a forwarded channel all have to get through. Before, 22 closed to them at once as well: with data still moving on the session (a forwarded connection, a followed log) the phone's unacknowledged data could not go out, the session's end never reached the computer, and the computer's ssh only exited when TCP gave up (some 15 minutes). Now the chain has, for 22, a rule that lets in only the connections already open (`netfw.Link`'s `Drain`: packets of connections conntrack has seen both ways, `ct state established,related`; a new SYN is still dropped), with a counter; the Shell reads it every half second (`LinkDrained`) and drops the rule once nothing came in for 3 seconds, or after 30 seconds at most, closing 22 to them too. The times are `shell/usbfw.go`'s constants `usbDrainIdle` and `usbDrainMax`; `drainLimits` looks at `usbState`'s `drainIdle` and `drainMax` first (for a setting to fill in later). Matching a connection's state takes conntrack and `nft_ct`, which the per-app rules need anyway to set and read connection marks (the image has `nft_ct`); the Shell's kernel probe (`shell/kernel.go`) does not look at netfilter, and a kernel that refuses the rule gets 22 closed at once (the old way, with a line in the log); a connection made before conntrack began to track it is taken up at the next packet the phone sends (`nf_conntrack_tcp_loose`), and the computer's packets get in from then on. Limits: an SSH session does not end while a connection it forwards is open (dbclient and OpenSSH both wait for the forwarded channels to close), so if the computer keeps sending through one, it is cut after 30 seconds all the same and the computer's ssh still waits for TCP to give up; the interactive shell of `kario device shell` does not go through `phone-dev`, the Shell does not end it, 22 closes to it after 3 quiet seconds, and the shell on the phone stays while the computer's end hangs (**not handled**). Also, where the kernel cannot build the per-app table (no named counters, before Linux 4.10, [17](17-app-sandbox.md) §1) the Shell has no firewall to use and builds no chain for the cable either, so once the computer is trusted 22 is reachable whatever developer mode says (**not handled**, **not tried on a phone**).
- File sharing listens only on the USB link's address and cannot be reached over Wi-Fi; untrusted, the link has not even an IPv6 link-local address, so no service on the phone can be reached over the cable. A runtime systemd-networkd file the Shell writes at boot does this: networkd leaves the link alone before the trust and after unplugging, even where a `.network` matches every interface (QEMU's `ip=dhcp` on the kernel command line makes systemd-network-generator write one); on the emulator the computer's end is kept from networkd the same way, for the selftest to bring up in a network namespace of its own.
- Not trusting it: charging only.
- The sharing server (`usbshare/`) runs in a sandboxed process of its own, `phone-usbshared`; files are still read and written through the Shell's photo, music and file libraries, so the files' index and permission rules stay as they are (§3.2).
- With file transfer (MTP) chosen in Settings › USB, the phone is enumerated again as an MTP device once trusted, and shows up as a phone in Windows Explorer; the rules are the same as here, only without a password (§3.3). Apple does not use MTP, and Windows needs the "Apple Devices" app.

### 3.1 Folders

The computer sees a few folders split the way people copy things, always named in English, `Photos`, `Videos`, `Music` and `Files`, whatever the phone's language (as Android's `DCIM` and `Music` are: scripts and sync tools on the computer find folders by name, and a name that changed would lose them); the same on the web page, mounted as a network drive (WebDAV) and in the URLs (the lowercase `photos` and so on also work). The rest of the web page's text follows the phone's language.

| Folder | Holds | What the computer may add | Largest file | Once added |
|--------|--------|------------|--------------|------------|
| Photos | The photos of the system's photo library | JPEG, PNG | 8 MB (sides up to 4096) | In the library as if taken by the camera, with its thumbnail |
| Videos | The videos of the system's photo library | WebM (VP8 / VP9) | 4 GB | In the library; mediad reads its size, length and poster frame |
| Music | The music library (`media/music`), **folders kept**: an album's folder copied in is still a folder | Music files (FLAC, WAV, AIFF, ALAC, APE, WavPack, MP3, Ogg, DSF, DFF), cue sheets, SACD images (`.iso`), and what albums often come with: cover pictures, lyrics (`.lrc`), rip logs, playlists | 9 GB (a dual-layer SACD image) | In the library the next time Music opens (or comes back); a cue sheet becomes its tracks and its image is not listed on its own ([20](20-audio.md) §9) |
| Files | The user's files (documents, attachments) | Any file | 16 MB | In "Files", as if saved on the phone |

- A name already taken becomes "name (2)": nothing on the phone is overwritten, and the computer cannot delete or change files on the phone.
- In Music, folders can be made (WebDAV's `MKCOL`) and the web page can upload a whole folder, at most 8 levels deep; names may not start with a dot or contain control characters or `..`. Large files are written as they arrive into a temporary file in the same folder and renamed when complete, outside the Shell's event loop.
- There are no folders of their own for recordings or downloads: the phone has no system library holding them yet (recordings are in each app's data directory; the browser's downloads go into "Files").

### 3.2 The sharing service in a sandboxed process of its own

Everything a computer sends (HTTP, WebDAV, a browser's multipart uploads) is parsed by `phone-usbshared`, a process of its own the Shell starts once the user trusts the computer, the way Android runs MTP in the MediaProvider process and not in system_server: any computer plugged in can reach this code, and a bug in it, exploited, gets a process that can touch nothing rather than the Shell, which holds everything. Code: `programs/usbshared` (the helper), `usbshare/remote.go` (the protocol, both ends), `shell/usbhelper.go` (launch, restarts, selftest).

| Aspect | Shell | phone-usbshared |
|------|-------|-----------------|
| Network | Makes the listening socket (port 80 on the link's address needs a privilege) and keeps it while sharing is on; while the helper restarts, the computer's connections wait in its queue | Inherits only that listening socket (fd 3) and accepts on it; on the device it is in an empty network namespace; it cannot make a socket of its own, nor bind, connect or listen |
| Files | The photo library, the music library and the file library (`usbLibrary` in `shell/usb.go`); what is added is saved through the system's libraries as before | Cannot open a single path: for a download the Shell opens the file and hands over a read-only fd with `SCM_RIGHTS`; for an upload the Shell gives it the write end of a pipe, and the library stores from the read end as the bytes arrive |
| Talking to the other side | One end of a socket pair (`usbshare.Helper`); each of the helper's requests is untrusted input | The other end (fd 4, `usbshare.Remote`): list the folders, list files, make a folder, open, thumbnail, save, log; the only thing the Shell asks it is the selftest's probe |
| Identity | root | On the device: its own uid (`system/usbshared` in `uids.json`), fresh mount, pid, ipc and uts namespaces and an empty net namespace, no capabilities, no_new_privs |
| Resources | Makes the helper a group, `app.system.usbshared`, under the cgroup delegated to it (a systemd scope with app scopes on) and starts it right inside (`CLONE_INTO_CGROUP`); once the helper has exited it reads `memory.events` to log whether it went over its memory, then ends and removes the group; on a machine without cgroup delegation (a developer machine) the helper stays in the Shell's group, as apps do | A group of its own: 64 MB of memory, no swap, 64 processes and threads, Go's soft limit `GOMEMLIMIT=48MiB`; files stream through pipes and the helper itself needs a few MB. Over the limit the kernel ends the helper alone, and the Shell restarts it as usual (counting toward the 3) |
| Kernel layers | — | Started through `phone-sandbox` (the `helper` policy): Landlock lets it read and run its own program and nothing else (plus the system's library directories when a development build is dynamically linked), and forbids TCP bind and connect; seccomp is the apps' filter; once it holds its fds it adds a layer of its own (`sandbox.DescriptorsOnly`, layer name `fd-only`): exec, new sockets and every file operation by path (open, create, remove, rename, link, change mode / owner / times / extended attributes, inotify) return EPERM, with neither root nor Landlock needed |

What the Shell checks in the helper's requests:

- Folders: only the four it lists itself (by ID).
- Names: valid UTF-8, no control characters, no element empty, `.` or `..`; `/` (and Windows' `\`) separates folders only in Music; the music library checks again itself (no leading dot, at most 8 levels), then opens itself as an `os.Root`: no name resolves outside it, not through a link in it leading out either. Making a folder or uploading with a name that fails gets "Not a name the phone takes for a file or folder".
- Sizes: each folder's limit is counted again on the Shell's side. When an upload's pipe reaches its end, the library keeps the file only if the helper says the copy is complete and its byte count is what came through the pipe; otherwise it is dropped. The computer still sees 413 over the limit.
- Only regular files opened read-only are handed over.
- Thumbnails only of the folders the library says keep them (Photos, Videos), the name checked as for the rest; what is handed over is a JPEG the Shell made itself (§3.3), and the helper decodes no picture.
- File descriptors the helper sends are always closed; at most 256 requests are handled at once and 32 uploads; at most 100 log lines a second, each at most 512 bytes, with control characters turned into spaces. The helper's log lines ("copied to the computer", "the computer added") still go into the Shell's log; the count of added files is the Shell's own, kept when a save succeeds.

Lifetime: it starts after the trust; it ends when the cable is pulled (the Shell closes its end of the socket pair, and kills it if still there a second later); when the Shell stops (`Core.Shutdown`: systemd stopping phone-shell, before phone-shell executes itself afresh to restart the phone, a test ending a Shell) it is ended the same way and waited for within the apps' grace (3 s), killed if still there then: it is gone when `Shutdown` returns, and is not started again; when the Shell's process itself goes, it ends with it (parent-death signal, and the socket pair breaks). If it crashes while sharing is on the Shell restarts it, at most 3 times in one sharing, after which sharing stops ("Stopped sharing with the computer"). The wrong-password count lives in the helper and starts from zero after a restart, which is why restarts are bounded. The language follows the Shell's: the Shell tells it the current one every time it lists the folders.

On the development machine the Shell is not root, so there is no separate uid and no namespaces, and the development machine's kernel (4.18) has no Landlock: rlimits, seccomp and `fd-only` apply. The selftest checks that the helper gets EPERM opening by path, creating a file, making IPv4 and Unix sockets, exec and ptrace. On the device (QEMU, root) it also requires a separate uid, no capabilities, namespaces and Landlock; that part, and the cases over the real USB link, passed on the emulator (2026-11-14).

| Environment | Result |
|------|------|
| Unit tests (`usbshare`, `sandbox`, `programs/usbshared`) | ✓ (§5) |
| Development machine selftest (not root, kernel 4.18) | ✓: the existing USB cases ("USB 连接电脑……" and "音乐：电脑经 USB……"; the firewall case needs netfw and is skipped on the development machine) pass without a step changed, and the new case "USB 文件共享在单独的沙箱进程里……" passes |

### 3.3 File transfer (MTP)

In Settings › USB the user chooses what a trusted computer gets: network sharing (the default) or file transfer (MTP). MTP (the Media Transfer Protocol, built on PTP's container format) is how Android phones connect to computers: Windows Explorer and Linux file managers (gvfs, KDE, through libmtp) show the phone as a device of its own; macOS has none built in and needs Android File Transfer or OpenMTP. Code: `usbshare/mtp` (the protocol, the phone's end and the computer's), `hal/usbgadget/ffs.go` (the FunctionFS function), `shell/usbmtp.go` (switching, selftest), `programs/usbshared/mtp.go` (the helper), `apps/settings/usb.go` (the settings page).

Network sharing stays the default, for the reasons of §0: nothing to install on the computer (macOS, Linux and Windows 11 have the NCM driver and a browser), a password for each connection shown only on the phone, and the debug shell (SSH) in developer mode goes only over it; MTP needs third-party software on a Mac and has no password. What MTP gives is drag and drop in Windows Explorer, and Windows versions before 11, which have no NCM driver.

| Step | On the phone | On the computer |
|------|--------|--------|
| Plug in | As in §3: first a USB network adapter without an address, and the screen asks "Trust this computer?". With a lock-screen PIN and the phone locked, it does not ask yet: it says to unlock, and asks once unlocked. MTP has no password, so the trust is the only gate (Android too offers MTP storage only unlocked) | A network adapter that gets no address |
| Trust | The Shell (root) makes the FunctionFS function `ffs.mtp` in configfs, mounts it, writes its descriptors and strings to ep0 and opens its three endpoints; then it puts it in the configuration in place of the network function and binds the controller again (product `0x0105`, the Microsoft OS descriptor on), starts the sandboxed helper and notifies "File transfer on" | The network adapter goes and an MTP device "Kario phone" comes, with four storages: Photos, Videos, Music, Files |
| Copy files | The helper uses, through `usbshare.Remote`, the same library as network sharing: a download is a read-only fd the Shell opened, an upload goes into a pipe, and the Shell checks as before (§3.2) | Drag in, drag out; folders can be made in Music |
| Unplug | Sharing stops, the configuration gets the network function back, the trust is forgotten | The device is gone |

- The rules are §3.1's: each folder is a storage, always named in English; the computer reads everything and adds files, a name already taken becomes "name (2)" (and ObjectInfoChanged tells the computer the new name); folders can be made only in Music. The phone's files are read-only to the computer (ProtectionStatus read-only): deleting, renaming and moving get Object_WriteProtected. A file the computer announced with SendObjectInfo and has not sent yet may be renamed or deleted: it is not on the phone. A folder the library offers read-only (not `Writable`, which the web page shows without its upload form) is a read-only storage (AccessCapability read-only): files, folders and copies into it get Store_Read_Only; today all four folders are writable.
- What a folder would not take is refused before the bytes come: a file other than JPEG or PNG into Photos (Invalid_ObjectFormatCode), one over the folder's limit (Object_Too_Large), one larger than the free space (Store_Full); data longer or shorter than announced gets Incomplete_Transfer, and the Shell keeps no file cut short. A file of 4 GB or more is announced as 0xFFFFFFFF, as the specification says, and its data runs to the end of the transfer.
- SendObjectPropList (what Windows and libmtp use in place of SendObjectInfo when the device offers it): the format and the size are parameters, the size an exact 64-bit number (above 4 GB too; the data container's length is still written 0xFFFFFFFF); the name is the ObjectFileName property, or Name without it; the few properties we list must have their types (otherwise Invalid_ObjectProp_Format, the response's fourth parameter saying which one), and other properties (an artist, a duration) are left alone, the file has its own. The checks after that are SendObjectInfo's code, in the same order with the same codes (storage, read-only, parent, name, format, limit, free space), and SendObject follows as before. libmtp puts into the list only the properties that may be set, so ObjectFileName's property description now says settable: only a file announced and not sent yet can be renamed, renaming a file on the phone still gets Object_WriteProtected, and ProtectionStatus is still read-only.
- Thumbnails (GetThumb): only the folders the library (the Shell) says keep thumbnails have them, Photos and Videos; when the library keeps none, DeviceInfo does not list GetThumb and it gets Operation_Not_Supported. What is sent is the gallery's own thumbnail (240×240, cropped from the centre) as JPEG: a photo's is the one made when it came into the gallery, made again from the photo if lost; a video's is the still mediad read, and until then it gets No_Thumbnail_Present, after that it has one. ObjectInfo gives ThumbFormat (JPEG), ThumbCompressedSize, ThumbPixWidth and ThumbPixHeight, all 0 for an object without a thumbnail. Only the Shell decodes pictures (its own thumbnails, or photos in its gallery, as the gallery does to show them); the helper only passes the bytes on, checking that they start as a JPEG, are at most 1 MB and at most 1024 pixels a side; an object's thumbnail size is kept until the file changes, and the last thumbnail's bytes for the GetThumb that follows a GetObjectInfo.
- Playlists (object references): what a computer makes is an abstract playlist (format 0xBA05, Windows Media Player's and libmtp's "name.pla", references with no content). The phone stores it as an M3U8 file `name.m3u8` in the same folder (`#EXTM3U` first, one track a line, its path relative to the playlist's folder, with `./` before a line that would not read back as that track). Why: the music library already takes the `.m3u` and `.m3u8` files computers copy over, and as a file it is still there after the cable, a restart of the helper, on another computer and over network sharing, and other players read it; references kept only in the helper's memory would be gone at a restart, and the music app would never see them. In order: SendObjectPropList or SendObjectInfo announces a playlist (only in a folder that takes `.m3u8`: Music, Files; Photos and Videos get Invalid_ObjectFormatCode), the SendObject after it (libmtp sends 0 or 1 byte) is taken and dropped, and SetObjectReferences with the tracks writes the file, from then on a plain M3U file (ObjectInfoChanged tells the computer its new name and format). Tracks must be files in the same storage (an object that does not exist, a folder, one in another storage or one not sent yet gets Invalid_ObjectReference); once on the phone a playlist cannot be changed (Object_WriteProtected, as for renaming and overwriting); one given no tracks before the session ends is not kept; at most 16 wait for their tracks at once. GetObjectReferences: an M3U, M3U8 or PLS file on the phone (made by a computer or copied over) gives the handles of the tracks it names, in order: read in the helper, the first 1 MB, leaving out URLs, absolute paths, paths out of the storage and files that do not exist, read as Latin-1 when not UTF-8, `\` taken as `/`; any other object gives an empty list. The music app has no playlists yet (a list is the play queue, [20](20-audio.md) §9.8): a playlist the computer makes is in the music library's folder, but the app does not show it, **not implemented**.
- Operations: GetDeviceInfo, OpenSession, CloseSession, GetStorageIDs, GetStorageInfo, GetNumObjects, GetObjectHandles, GetObjectInfo, GetObject, GetThumb (when the library keeps thumbnails), GetPartialObject and Android's GetPartialObject64 (libmtp and gvfs read in pieces), SendObjectInfo, SendObjectPropList, SendObject, DeleteObject, MoveObject, CopyObject (a copy on the phone into a folder that takes it), GetObjectPropsSupported, GetObjectPropDesc, GetObjectPropValue, GetObjectPropList (Windows reads by property list, taken as Android takes it: depth 0 one object, depth 1 a folder and its contents), SetObjectPropValue, GetObjectReferences, SetObjectReferences, GetDevicePropDesc and GetDevicePropValue (the device's name). DeviceInfo's formats include abstract playlists (libmtp makes no playlist without). Events: ObjectAdded, ObjectRemoved (the folders the computer looked at are listed again every 5 seconds, so a photo taken or a file deleted on the phone reaches it), ObjectInfoChanged, StorageInfoChanged. Class requests on the control endpoint: Cancel, Device Reset, Get Device Status.
- How the computer knows it is MTP: the interface is of the still image class 6/1/1 (PTP) and named "MTP" (which libmtp looks at); Windows reads the Microsoft OS descriptor (the string at 0xEE, then with the vendor request it names the extended compatible ID "MTP"), and the kernel's configfs answers both for the function; DeviceInfo's vendor extension is `microsoft.com: 1.0`.
- Sandbox: still `phone-usbshared`, started through `phone-sandbox` the same way and adding `fd-only` the same way; fd 3 is ep0, fd 4 the Shell, fds 5, 6 and 7 the bulk-in, bulk-out and interrupt endpoints, and the helper opens no path. The Shell keeps these files open (FunctionFS takes the function away when ep0 is last closed): a helper that crashes is started again with the same files, and the computer, its session gone, opens another (Windows does).
- The developer machine has no USB device controller: a simulated cable (`mtp.NewSim`) carries USB's packets on pipes (512 bytes a packet, a short or zero-length packet ending a transfer), and the selftest plays the computer. The FunctionFS layer is unit-tested without root: SOCK_SEQPACKET socket pairs stand in for the function's files (each read or write one record, as each is one FunctionFS request; a write of nothing a zero-length packet), and `OpenMTP` writes its descriptors into plain files standing in for the mount point. The bulk-out endpoint is always read in whole packets, what a read cannot hold kept for the next one: FunctionFS rounds a request up to whole packets, and older kernels fail it with EOVERFLOW when more data comes than the read holds. On the emulator the computer is dummy_hcd's host side: the selftest uses its own Go initiator over usbfs (`/dev/bus/usb`), then libmtp's own tools (mtp-detect, mtp-files, mtp-getfile; libmtp is what the Linux file managers gvfs and KIO use) to detect the device, list files and copy one. libmtp-bin goes into the emulator's image only, not a phone's; libmtp and libusb are LGPL-2.1, the image's licence rule (`INCOMPATIBLE_LICENSE`) bars only GPLv3, LGPLv3 and AGPLv3, and `scripts/license-check.py` checks only Go modules and Rust crates, not the image's packages.
- Kernel: `phone-usb.cfg` turns on `CONFIG_USB_CONFIGFS_F_FS`, and the emulator's `phone-usb-sim.cfg` `CONFIG_USB_DUMMY_HCD`. The build stops when the kernel configuration lacks them (`do_phone_usb_kconfig` in the kernel recipe; Yocto's own configuration check only warns); the selftest's MTP case starts with `usb-mtp kernel`, before `require-usb` so that it is never skipped, which checks the running kernel: `CONFIG_USB_CONFIGFS_F_FS` in its configuration (`/proc/config.gz`; the functionfs file system registers only with the first FunctionFS function, so it cannot be looked for) where there is a device controller, and on the emulator (QEMU's virt board) also dummy_hcd's controller, without which every USB case would be skipped unseen.

### 3.4 Factory mode: the station is not asked about (**not tried on a phone**)

The boot on the line before a phone gets its device certificate is in factory mode (`kario.factory=1` on the kernel command line, only while the keystore is not provisioned; the threat model is in [31](31-lock-and-biometrics.md) §13, the test in [40](40-testing.md) §10). In that boot, once a computer configures the phone (`configured`), the Shell does not ask 「信任这台电脑吗？」 (trust this computer?) and gives the link the same `10.71.0.1/24` and DHCP as after trust, but the firewall's chain for it (`netfw.Link`) lets through only UDP 67 (DHCP) and TCP 7171 (the test program `phone-factory-test --serve`, over which the station runs the test and provisions the phone, [22](22-developer-api.md) §11): no file sharing, no MTP, and no port 22 even in developer mode. The factory screen's home gains a line 「USB：已连上工站」 (USB: the station's link is up); pulling the cable takes away the address, DHCP and the chain.

Every other state (a normal boot, a provisioned phone booted with `kario.factory=1`, the boot after a power cut) goes through the trust flow above as ever: in the code it is one test before `askTrust` in `checkUSB` (`c.factory != nil`), and factory mode exists only when the Shell passed the gate at boot (the mark `/run/phone/factory/on` there and the keystore asked again itself). Factory mode's link has no authentication and no encryption: the station is at the other end of the cable.

## 4. For comparison: how an iPhone connects to a computer for debugging

| Stage | iPhone | Kario |
|------|--------|-------|
| Trust | Plugged in, the phone asks "Trust This Computer?" and wants the passcode; the two exchange a pairing record (made by lockdownd; the computer keeps it in `/var/db/lockdown`, on Windows in `Apple\Lockdown`), after which it does not ask again; "Settings › General › Transfer or Reset › Reset Location & Privacy" clears them | Asks every time the cable goes in and keeps no pairing record; unplugging ends it |
| Link | Always usbmux: many TCP-like connections multiplexed on one USB interface (usbmuxd on the computer); since iOS 17 there is also a USB-NCM network adapter, and developer services go over an IPv6 tunnel on it | A USB-NCM network adapter with ordinary TCP/IP |
| Finding services | lockdownd (port 62078) starts services by name; since iOS 17 it is RemoteXPC / RSD (remote service discovery), which lists the services once the tunnel (CoreDevice) is up | Only file sharing (port 80); in developer mode also the debug shell, over which the developer's requests reach the Shell through `phone-dev` (below) |
| Files | AFC (Apple File Conduit) serves the Finder's file sharing, limited to the sandboxes of apps that declare file sharing; photos go over PTP | A browser / WebDAV, with four folders: photos, videos, music, files (§3.1) |
| Debugging | First "Settings › Privacy & Security › Developer Mode" has to be turned on (a restart and one more confirmation, since iOS 16); Xcode mounts a personalized developer disk image (DDI, signed per device since iOS 17), then reaches debugserver, instruments and other services through the tunnel; after pairing it can also debug over Wi-Fi | In developer mode (turned on in Settings, [07](07-ecosystem-and-store.md)) a trusted cable reaches the debug shell (SSH, dropbear in development images); `kario device` on the computer installs apps, streams their logs, reloads and restarts them over it (below); outside developer mode the cable reaches only file sharing, with ports filtered by link (`netfw.Link`) |
| Computer-side software | Built into macOS; Windows needs "Apple Devices" or iTunes; the open-source libimobiledevice / pymobiledevice3 implement the same protocols | None needed: a browser, a file manager, `ssh` |

So the answer to "how does an iPhone connect to a debug interface" is that it has no separate debug port; it is this one cable. Trust it first (pairing), turn on Developer Mode, and Xcode finds the developer services lockdownd / RSD lists over usbmux (since iOS 17, a tunnel on the USB network adapter). We copied the two rules, "trust first" and "debugging only in developer mode", and replaced the link with a standard USB network adapter, which removes usbmux and the dedicated computer-side software.

**The developer link (`kario device`)**: the developer services Xcode reaches through its tunnel are, here, one command over SSH. On the computer `kario device install|logs|reload|restart|uninstall|shell`, and for the system `push|pull|screenshot|key|type|syslog|forward|reverse|reboot|update|bugreport` (`cmd/kario/device.go`; compared with Android's adb and fastboot in §4.1), runs `ssh root@10.71.0.1 phone-dev …` (the development image's dropbear; `-ssh` and `-to` name another ssh and address); `phone-dev` on the phone (`programs/devcmd`, one of `kario-system`'s names) only hands the request, with the SSH session's `SSH_CONNECTION`, to `dev.sock` in the Shell's run directory (package `devctl` is the protocol between them), and the Shell decides (`shell/devlink.go`):

| Rule | How |
|------|-----|
| Developer mode only | Checked for every request (and every second while a log is followed); off, the request is refused: "developer mode is off on the phone" |
| Only over the trusted cable | The computer has to be trusted, with network sharing (file transfer over MTP has no network); on a device the SSH session's local address has to be the cable's `10.71.0.1` (SSH that came in over Wi-Fi does not count; dropbear gets its connections from systemd's dual-stack socket, so `SSH_CONNECTION` says `::ffff:10.71.0.1`, and the parsed IPv4 address is what is compared: the first real SSH run on the emulator failed on a string comparison); unplugging or the trust ending stops a followed log too |
| The Shell's own user only | The socket is 0600, and the peer's uid is checked with `SO_PEERCRED` (root on the device; every app has a uid of its own) |
| Installed apps only | Logs, reload, restart and uninstall take apps installed from a store (this link included); system apps are always refused |
| Installing goes through the installer | The package has to be signed by a store the phone trusts (the development store in developer mode) and passes the same `checkPackage` and `unpack`, only without the confirmation dialog (developer mode and trusting this computer are the user's own taps); the phone shows "Installed “…” from the computer". A project directory is signed by `kario device` with a development store first, and that store's root sent with `trust` (there is one development store: once it is the computer's, installed apps another development store signed fail verification before their next start) |
| Files go to two places only | `push` and `pull` carry the file in the SSH session command's standard input and output (no scp or sftp server on the phone), its size said first, so one byte short is a failure; the Shell lets them touch only the developer directory (`/var/lib/phone/dev`, like Android's `/data/local/tmp`) and the data of apps installed in developer mode (`APP-ID:PATH`, like `run-as`), the path resolved through `os.Root`, so neither `..` nor a link leads out; a push goes to a temporary file renamed once complete, so one cut short leaves nothing; a file written into an app's data belongs to the app's uid; one file at a time |
| Injected keys are told apart | The keys of `key` and `type` are marked as the computer's and pressed one at a time through the Shell's event loop (waiting out a system dialog's first moment, as for the person's keys); the status bar says "● Keys from the computer" until 3 s after the last one. The system dialogs that grant a permission, confirm trustedly (payment), take or set a PIN (the lock screen, the SIM), enrol a fingerprint, unlock the device, trust a computer, pair over Bluetooth, set the default SMS app, let an app text or call, hand an app photos or the camera, share, or pick a card in the quick card view (which pays), and the keypad lock, take none of them (only cancelling; not the arrows either: the computer cannot move the choice onto "Allow" for the person); the phone says to use its own keys and the computer gets an error. Android likewise keeps injected input off its secure windows. The factory reset's PIN screen and last confirmation, and the anti-theft lock's screen, take none either ([31](31-lock-and-biometrics.md) §11) |
| Screenshots mask secure screens | The panel's renderer hands its picture to no other process ([23](23-renderer-protocol.md) §5), so the Shell starts a headless instance of the same renderer (on a device as nobody, without network; the PNG read back through `os.Root`) and has it draw the panel's frame as a PNG, as the selftest's `snap` does. While a PIN is being entered, a trusted confirmation or a Bluetooth pairing code is up, or the page has secure content (a payment code, the switch's QR code and hotspot password), the frame keeps only the status bar, the title and the soft keys and has one `secure` picture in place of its content, which every renderer masks in snapshots; no shared memory goes over either, and the computer is told "masked: …". Without a pixel renderer (the developer machine's text screen) it is refused |
| Port forwarding follows the gate | `forward` and `reverse` are the computer's SSH session's own port forwarding (`ssh -L`, `-R`), ending on the phone's loopback; the forwarded connections all ride port 22, which the cable's firewall (`netfw.Link`) lets through in developer mode only (when it goes off, the connections open drain before it closes, §3), and the Shell checks that too; the loopback is accepted before the per-app rules (an app without the network permission is in an empty network namespace, with no loopback of the phone's, and cannot reach a reverse forward); reverse forwards use ports from 1024 up. `phone-dev forward` stays in the session, the Shell checks the gate every second and ends the request when it closes; the session's command ending ends SSH, and the forwarding with it; stopping `kario device` on the computer does the same |
| System updates are verified as usual | `update` receives the `.raucb` onto the data partition and takes Settings' own update path: RAUC verifies its signature against the image's keyring and that it is for this machine, and refuses an unsigned or wrongly signed one, the computer seeing RAUC's own words; it goes into the other slot, which starts on trial at the next restart and is left for the old slot if it does not come up healthy; with the version `rauc info` reads, it is remembered for the update server's report as usual ([25](25-system-update.md)); the progress goes back to the computer line by line; the bundle is deleted once installed |
| Restarts | `reboot` goes through systemd (`systemctl reboot --reboot-argument=bootloader\|recovery`); an update waiting is restarted into as Settings would; a developer machine is not restarted |
| Bug reports have no private data | `bugreport` is a zip: versions, `sku.json`, the apps, the crash records (without the app's log tail), the Shell's and the renderer's logs, systemd's journal (on a developer machine, the services' logs), `dmesg`, RAUC's status; message and chat contents, contacts, photos and files, keys of any kind, Wi-Fi passphrases, account tokens, the apps' data and the apps' own logs stay out, as README.txt in the zip says |

Verification: `devctl`, `phone-dev` and the Shell's side have unit tests on the developer machine (`shell`'s `TestDevLink`: refused with developer mode off, with no trusted computer, with file transfer, and on a device for a session that did not come over the cable; once trusted, install, logs, a followed log ending when the cable goes, restart, reload, uninstall; system apps refused; `TestDevLinkRefusesBeforeThePackage`: for an install the package goes only after the Shell has agreed, so a refusal arrives before it is sent and an 8 MB package never breaks the pipe halfway (checked first to fail so with the old "package straight after the request", as the selftest on the developer machine sometimes did); `cmd/kario`'s `TestDevice`: a fake ssh and a fake phone); the developer machine's selftest case "Developer mode: the computer over a trusted cable…" ✓ (`phone-dev` run directly, no SSH). The emulator case over real SSH (the computer's end in a network namespace of its own, with dropbear's `dbclient`), "Developer mode on the emulator: …", passes on QEMU (2026-11-15; the first run failed on comparing the address as a string, see "Only over the trusted cable" above); OpenSSH on a real computer against a real phone **not on a real phone**.

The tools for the system: `devctl`'s `TestCheck`, `TestCallBinary`, `TestCallBodyAndProgress`, `TestCallForward`; `shell`'s `TestDevToolsGate` (every tool meets the same gate), `TestDevInjectedKeys` (trust dialogs and the keypad lock refuse injected keys, cancelling works, the person's own keys answer, the status bar), `TestDevTypedText`, `TestDevPushPull` (the developer directory and the data of an app installed in developer mode; elsewhere, `..`, system apps and store apps refused; a push cut short leaves no file), `TestDevSyslog` (on the developer machine the services' logs and the Shell's, never an app's, `-u`, `-n`; journalctl's arguments on a device; a followed log stops when developer mode goes off), `TestDevForward` (refused when the firewall does not let 22 through, ends when developer mode goes off or the computer goes), `TestDevReboot`, `TestDevUpdate` (progress, the slot, an unsigned bundle refused by RAUC, no bundle left on the phone), `TestDevScreenshot` (a fake renderer: the screenshot's frame has neither a pairing code nor a payment's prompt, the dialog replaced by a secure picture), `TestDevBugreport` (an app's log and a crash record's log tail stay out); `cmd/kario`'s `TestDeviceTools` and `TestRemoteWord` (quoting in the remote command line). The emulator case over real SSH (pushing and pulling files, keys, systemd's journal, and port forwarding with `dev-forward`: `dbclient -L` in the computer's network namespace, the bytes really going through port 22 to an echo service on the phone's loopback and back, the session ending at once when developer mode goes off) runs on QEMU only and passes there (2026-11-20, see [13](13-prototype.md)). Data still moving on the session when developer mode goes off (§3's drain): `netfw`'s `TestLinkRules` (the drain's rule takes only connections already open and counts them; without a port draining no rule asks conntrack), `shell`'s `TestUSBDrainDone` (over after 3 quiet seconds, or at 30) and `TestUSBFirewallDrains` (off, 22 takes no new connection while the open ones still get in; not closed while they are busy, closed once they are quiet or at the limit; developer mode on again or the cable out ends the drain; a kernel that refuses the rule gets the port closed at once; first confirmed to fail without the drain); `dev-forward` now turns developer mode off while a forwarded connection still carries bytes both ways, QEMU ✓ (2026-11-21: a new SSH connection refused, 53 more echoes back through the open session after that, dbclient exiting as soon as the computer closed the forwarded connection, saying why, and 22 closing to the open connection 3.7 s later); the same step fails on an image lacking only the drain: dbclient still running 83 s after developer mode went off, not one echo back after it, 336 bytes unacknowledged on the phone, though the Shell had ended the request long before. **Not on a real phone**.

### 4.1 For comparison with Android: does Kario need adb and fastboot

adb yes, and `kario device` is it (table below); fastboot's part Kario does not do: Kario implements no boot loader, and flashing and unlocking the boot loader use the board's own: on the OnePlus 6T the fastboot built into ABL (which `yocto/fajita-flash.sh` flashes through, [39](39-oneplus-6t.md)), and factory flashing goes through the ODM's tools (Qualcomm's EDL, the 9008 download mode; Unisoc's download tool). Most of what Android's recovery does is replaced by the A/B slots with RAUC's rollback ([25](25-system-update.md)).

- QEMU (qemuarm64): no boot loader reads the reason (QEMU loads the kernel itself); a plain restart.
- The developer machine: no restart, "not a phone".

Still missing (**not implemented**): debugging over Wi-Fi (`adb tcpip`, `adb pair`: the cable only); directories and many files in one `push` or `pull`, `adb sync`; screen recording (`screenrecord`); the system services' state through `kario device` as `dumpsys` gives it (the phone has `phone-shell --dump`); a wipe screen at boot (recovery's wipe data, [31](31-lock-and-biometrics.md) §11.2); a non-root developer account (§4.2). The OnePlus 6T has no RAUC A/B system slots (the root file system is the whole userdata), so `update` refuses there and the system is flashed with `fajita-flash.sh` from fastboot; `reboot recovery` has no recovery to go to. The screenshot's headless renderer lacks the Landlock and seccomp of the panel's renderer (it is only nobody, without network).

### 4.2 Root, or an ordinary account for the developer

Today: there is one image (no separate user build as on Android), always with dropbear, letting root in with an empty password (kas's `allow-empty-password empty-root-password allow-root-login`), so in developer mode a trusted cable is a root shell, and `kario device` logs in as root. On Android's user builds adbd runs as the `shell` user and `adb root` is refused; only userdebug and eng builds have root.

Assessment: none of §4's tools needs root: `phone-dev` only reaches the Shell's socket, and what may be touched is the Shell's decision. So an ordinary account needs only to log in, run `phone-dev` and reach `dev.sock`. Still, it is no small change: the image needs the user; dropbear has to refuse root and empty passwords and take keys instead, which means handing the computer's public key to the phone when it is trusted and asking the user to check its fingerprint, as Android does (a new trust step and its screen); the existing QEMU cases over SSH all log in as root and would change with it; all of it needs images built and checked on the emulator. So it is **not implemented** this time; the design:

| Part | How |
|------|------|
| Account | `dev`, its uid fixed by the image (say 2000, like Android's `shell`), the developer directory as home, in no privileged group |
| Login | dropbear with `-w` (no root) and `-s` (no passwords), `dev` by key only; when a computer is trusted in developer mode, the phone shows the fingerprint of its public key for the user to confirm, and the Shell writes it into `dev`'s `authorized_keys`, forgotten at unplugging (or remembered as on Android, revocable in Settings) |
| Socket | `dev.sock` becomes 0660 with group `dev`; the Shell takes its own uid and `dev`'s through `SO_PEERCRED` |
| Tools | All through the Shell, unchanged; `kario device shell` is `dev`'s shell: it can read `/proc` and run `phone-dev`, and reaches no one else's data |
| Root | Only on an unlocked device (Settings › Device unlock, by which the app keys are erased), like Android's userdebug |

## 6. Not done

- MTP has not been tried with real Windows, macOS (Android File Transfer, OpenMTP) or Linux (gvfs, KIO) computers, **not verified on hardware**; Windows' property-list reading and uploads follow the specification and what Android does, and the tests' initiator is our own; on the emulator libmtp's tools join it (✓), while Windows' MTP driver (WPD) and the macOS programs have no stand-in.
- Cancelling an MTP transfer half-way stops only between two chunks (when the computer stops taking or sending, the read or write stuck on FunctionFS cannot be stopped) and has not been tried with Windows, **not verified**; the helper starts before the computer has finished enumerating and takes the packet size of high speed (512 bytes), so full-speed computers are **not verified**. A change on the phone reaches the computer as an event up to 5 seconds later.
- Thumbnails, SendObjectPropList and playlists follow the specification and libmtp's source and were tested only against our own initiator, **not verified**: whether Windows Explorer shows thumbnails through GetThumb or the representative sample properties (RepresentativeSampleData, which we do not have, **not implemented**), and whether it and macOS's Image Capture trust the thumbnail size in ObjectInfo; which properties Windows Media Player sends when it syncs a playlist, and what it makes of a `.pla` of 0 bytes; libmtp's playlist listing (Rhythmbox and others) looks only for objects of the abstract playlist format, and what the phone stores is an M3U file, so they will probably not list it as a playlist; the phone refuses libmtp's changes to an existing playlist (files on the phone are not changed), and how libmtp tells the user. libmtp now uploads with SendObjectPropList, and the emulator's libmtp case only reads, so that path is **not verified** either.
- PD drivers on real hardware, and switching the port's data role (whether the phone is host or device is the port controller's decision; `CONFIG_TYPEC` and `USB_ROLE_SWITCH` are on); a dock's DR_Swap (§2.1) is **not tried on a phone**.
- The phone as host (§2.1): the OnePlus 6T's kernel and device tree cannot be a host yet ([39](39-oneplus-6t.md)), so it is **not tried on a phone** on any phone; mounting an allowed stick and opening it in Files is **not implemented**; USB-C headphones (the audio class), network adapters and other classes are allowed as plain devices with nothing special done; a touchscreen plugged in while locked (§2.1) has unit tests only: none of QEMU's USB devices is a touchscreen (`usb-tablet` is an absolute mouse without `INPUT_PROP_DIRECT`), so no selftest case covers it; on a board whose own touchscreen is on USB (none now) it would count as plugged in while locked after a reboot with a PIN, and the phone would be unlocked with its keys.
