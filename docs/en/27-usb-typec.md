# USB-C: charging, keyboards and mice, connecting to a computer

> Status: **prototype ✓ (QEMU)**. Plugging keyboards and mice in and out, and connecting to a computer (trust → password → copy files → unplug to stop), pass end to end on the emulator (dummy_hcd makes one virtual machine both the phone and the computer); since file sharing moved into a sandboxed process of its own (§3.2) it has passed on the emulator too (2026-11-14); recognizing PD fast charging has unit tests and is **not tried on real hardware** (that waits for a Snapdragon board, R16). File transfer over MTP (§3.3) has unit tests and passes the development machine's selftest and the emulator's (over dummy_hcd, with our own initiator and libmtp's tools); with real Windows, macOS and Linux computers it is **not verified on hardware**. The hardware layer on the phone is in [11](11-platform-architecture.md) §"Then what is hal/".

## 0. Conclusions

- One USB-C port does three things: charging (the Type-C port controller's kernel driver does the PD negotiation; we only read the result), keyboards and mice (the phone is the USB host), and a computer (the phone is a USB device and shares files with it through a USB network link).
- Connecting to a computer follows the iPhone: a computer plugged in only charges the phone, and gets anything **only after the user taps "Trust" on the phone**; every connection has its own password, unplugging ends it, and the trust is not kept.
- No drivers to install: to the computer the phone is a CDC-NCM network adapter, which macOS, Linux and Windows 11 drive with their own drivers; on the computer a browser, or "connect a network drive" (WebDAV), opens it, with no computer-side software of ours. Settings › USB can change it to file transfer over MTP (§3.3), with which the computer's file manager shows the phone as a device.

## 1. Charging: USB PD

| Part | How |
|------|------|
| Negotiation | The kernel driver of the Type-C port controller (on the Snapdragon 662, the PMIC's Type-C block) negotiates voltage and current with the charger (PD, PPS); the phone's software takes no part |
| Reading the result | `hal/power` reads the power supply class (`/sys/class/power_supply`): in the USB supply's `usb_type` the bracketed entry is the current type; `[PD]` and `[PD_PPS]` are PD fast charging, `[DCP]` and the like a dedicated charger; older drivers report the type `USB_PD` directly |
| Telling the user | Plugging in a charger lights the screen with "Fast charging" or "Charging" ([28](28-battery.md)); the status bar still shows ⚡ and the level |
| What the phone draws | Connected to a computer, the phone as a USB device asks it for 500 mA (USB 2's limit, `MaxPower` in `hal/usbgadget`); the current a charger gives is negotiated separately by the port controller and has nothing to do with this |

To confirm on real hardware (**not implemented**): how far the mainline kernel's Type-C / PD driver for the Snapdragon 662 (PMI632) goes; the charging curve and thermal protection are the charger driver's.

## 2. Keyboards and mice: USB HID

- The kernel's USB HID driver turns keyboards and mice into evdev devices (kernel configuration `phone-usb.cfg`). A keyboard follows the same key path as the phone's own keypad, renderer → Shell ([11](11-platform-architecture.md)); a full keyboard's letters type directly.
- **Ones plugged in after start work too**: the renderer cannot open `/dev/input` once it has dropped its privileges, so the input helper forked before that opens new devices and hands it their descriptors ([23](23-renderer-protocol.md) §5). When one is plugged in or out the renderer sends an `input` message and the Shell logs it.
- **Mouse**: this is a keys-first system, and a mouse is keys first: the wheel moves the focus up and down (a horizontal wheel left and right), the right button is Back, the middle one Options. Moving the mouse brings up a pointer; pointing at an item and clicking moves the focus there and chooses it (as OK); a click on the soft-key bar is that soft key; typing hides the pointer, and with no pointer the left button is OK. The renderer turns the pointer position into a node (`tap`, [23](23-renderer-protocol.md) §3), and the Shell accepts only nodes of the frame it sent itself.

## 3. Connecting to a computer: trust first, as on an iPhone

| Step | On the phone | On the computer |
|------|--------|--------|
| Boot | The phone is always a USB network adapter (CDC-NCM in configfs, `hal/usbgadget`), with MAC addresses derived from its serial number so the computer sees the same device every time; but the phone's side has **no address** | — |
| Plug in | The device controller's state becomes `configured` (the computer configured it; a charger does not), the screen lights up and asks "Trust this computer?" | The system sees a USB network adapter, gets no address and can reach nothing |
| Trust | The link gets `10.71.0.1/24` and a DHCP server (a systemd-networkd runtime configuration, gone after a reboot), file sharing starts, and a notification shows the address and an 8-digit one-time password | DHCP gives it an address; a browser opens `http://10.71.0.1`, or it connects to that as a network drive (WebDAV), with the password |
| Copy files | Four folders, `Photos`, `Videos`, `Music` and `Files` (always named in English), all readable and writable; what is added is saved through the system's own libraries (photos, the music library, files) and shows up in Photos, Music and "Files" as if saved on the phone (§3.1) | Download, upload; folders can be made in Music and whole folders copied |
| Unplug | Sharing stops, the address and DHCP are removed, the trust is forgotten, and "Stopped sharing with the computer" shows | The connection is gone |

- The password is compared in constant time; 10 wrong ones lock that connection, and sharing has to start again from the phone.
- A USB bus reset is not unplugging (Windows resets after an error; libmtp resets a phone it takes for Android when it lets go, which it does when DeviceInfo names `android.com`): the device passes through default and addressed back to configured, and sharing and the trust stay; only when it is not configured again within 15 seconds does it count as unplugged.
- The firewall gives the USB link a chain of its own (`netfw.Link`, ahead of the per-app rules): before trust nothing gets in; once trusted only DHCP and file sharing (port 80) are let through, plus the debug shell (port 22) in developer mode. So other services on the phone cannot be reached over the cable even when they listen on every interface. The selftest on the device checks that 80 is open and 22 closed, and 22 open once developer mode is on.
- File sharing listens only on the USB link's address and cannot be reached over Wi-Fi; untrusted, the link has not even an IPv6 link-local address, so no service on the phone can be reached over the cable. A runtime systemd-networkd file the Shell writes at boot does this: networkd leaves the link alone before the trust and after unplugging, even where a `.network` matches every interface (QEMU's `ip=dhcp` on the kernel command line makes systemd-network-generator write one); on the emulator the computer's end is kept from networkd the same way, for the selftest to bring up in a network namespace of its own.
- Not trusting it: charging only.
- The sharing server (`usbshare/`) runs in a sandboxed process of its own, `phone-usbshared`; files are still read and written through the Shell's photo, music and file libraries, so the files' index and permission rules stay as they are (§3.2).
- With file transfer (MTP) chosen in Settings › USB, the phone is enumerated again as an MTP device once trusted, and shows up as a phone in Windows Explorer; the rules are the same as here, only without a password (§3.3). Apple does not use MTP, and Windows needs the "Apple Devices" app.

### 3.1 Folders

The computer sees a few folders split the way people copy things, always named in English, `Photos`, `Videos`, `Music` and `Files`, whatever the phone's language (as Android's `DCIM` and `Music` are: scripts and sync tools on the computer find folders by name, and a name that changed would lose them); the same on the web page, mounted as a network drive (WebDAV) and in the URLs (the lowercase `photos` and so on also work). The rest of the web page's text follows the phone's language.

| Folder | Holds | What the computer may add | Largest file | Once added |
|--------|--------|------------|--------------|------------|
| Photos | The photos of the system's photo library | JPEG, PNG | 8 MB (sides up to 4096) | In the library as if taken by the camera, with its thumbnail |
| Videos | The videos of the system's photo library | WebM (VP8 / VP9) | 4 GB | In the library; mediad reads its size, length and poster frame |
| Music | The music library (`media/music`), **folders kept**: an album's folder copied in is still a folder | Music files (FLAC, WAV, AIFF, ALAC, APE, WavPack, MP3, Ogg, DSF, DFF), cue sheets, SACD images (`.iso`), and what albums often come with: cover pictures, lyrics (`.lrc`), rip logs, playlists | 9 GB (a dual-layer SACD image) | In the library the next time Music opens (or comes back); a cue sheet becomes its tracks and its image is not listed on its own ([20](20-audio.md) §9) |
| Files | The user's files (documents, attachments) | Any file | 16 MB | In "Files", as if saved on the phone |

- A name already taken becomes "name (2)": nothing on the phone is overwritten, and the computer cannot delete or change files on the phone.
- In Music, folders can be made (WebDAV's `MKCOL`) and the web page can upload a whole folder, at most 8 levels deep; names may not start with a dot or contain control characters or `..`. Large files are written as they arrive into a temporary file in the same folder and renamed when complete, outside the Shell's event loop.
- There are no folders of their own for recordings or downloads: the phone has no system library holding them yet (recordings are in each app's data directory; the browser's downloads go into "Files").

### 3.2 The sharing service in a sandboxed process of its own

Everything a computer sends (HTTP, WebDAV, a browser's multipart uploads) is parsed by `phone-usbshared`, a process of its own the Shell starts once the user trusts the computer, the way Android runs MTP in the MediaProvider process and not in system_server: any computer plugged in can reach this code, and a bug in it, exploited, gets a process that can touch nothing rather than the Shell, which holds everything. Code: `programs/usbshared` (the helper), `usbshare/remote.go` (the protocol, both ends), `shell/usbhelper.go` (launch, restarts, selftest).

| Aspect | Shell | phone-usbshared |
|------|-------|-----------------|
| Network | Makes the listening socket (port 80 on the link's address needs a privilege) and keeps it while sharing is on; while the helper restarts, the computer's connections wait in its queue | Inherits only that listening socket (fd 3) and accepts on it; on the device it is in an empty network namespace; it cannot make a socket of its own, nor bind, connect or listen |
| Files | The photo library, the music library and the file library (`usbLibrary` in `shell/usb.go`); what is added is saved through the system's libraries as before | Cannot open a single path: for a download the Shell opens the file and hands over a read-only fd with `SCM_RIGHTS`; for an upload the Shell gives it the write end of a pipe, and the library stores from the read end as the bytes arrive |
| Talking to the other side | One end of a socket pair (`usbshare.Helper`); each of the helper's requests is untrusted input | The other end (fd 4, `usbshare.Remote`): list the folders, list files, make a folder, open, save, log; the only thing the Shell asks it is the selftest's probe |
| Identity | root | On the device: its own uid (`system/usbshared` in `uids.json`), fresh mount, pid, ipc and uts namespaces and an empty net namespace, no capabilities, no_new_privs |
| Resources | Makes the helper a group, `app.system.usbshared`, under the cgroup delegated to it (a systemd scope with app scopes on) and starts it right inside (`CLONE_INTO_CGROUP`); once the helper has exited it reads `memory.events` to log whether it went over its memory, then ends and removes the group; on a machine without cgroup delegation (a developer machine) the helper stays in the Shell's group, as apps do | A group of its own: 64 MB of memory, no swap, 64 processes and threads, Go's soft limit `GOMEMLIMIT=48MiB`; files stream through pipes and the helper itself needs a few MB. Over the limit the kernel ends the helper alone, and the Shell restarts it as usual (counting toward the 3) |
| Kernel layers | — | Started through `phone-sandbox` (the `helper` policy): Landlock lets it read and run its own program and nothing else (plus the system's library directories when a development build is dynamically linked), and forbids TCP bind and connect; seccomp is the apps' filter; once it holds its fds it adds a layer of its own (`sandbox.DescriptorsOnly`, layer name `fd-only`): exec, new sockets and every file operation by path (open, create, remove, rename, link, change mode / owner / times / extended attributes, inotify) return EPERM, with neither root nor Landlock needed |

What the Shell checks in the helper's requests:

- Folders: only the four it lists itself (by ID).
- Names: valid UTF-8, no control characters, no element empty, `.` or `..`; `/` (and Windows' `\`) separates folders only in Music; the music library checks again itself (no leading dot, at most 8 levels). Making a folder or uploading with a name that fails gets "Not a name the phone takes for a file or folder".
- Sizes: each folder's limit is counted again on the Shell's side. When an upload's pipe reaches its end, the library keeps the file only if the helper says the copy is complete and its byte count is what came through the pipe; otherwise it is dropped. The computer still sees 413 over the limit.
- Only regular files opened read-only are handed over.
- File descriptors the helper sends are always closed; at most 256 requests are handled at once and 32 uploads; at most 100 log lines a second, each at most 512 bytes, with control characters turned into spaces. The helper's log lines ("copied to the computer", "the computer added") still go into the Shell's log; the count of added files is the Shell's own, kept when a save succeeds.

Lifetime: it starts after the trust; it ends when the cable is pulled or the Shell exits (parent-death signal, and the socket pair breaks), and is killed if still there a second later; if it crashes while sharing is on the Shell restarts it, at most 3 times in one sharing, after which sharing stops ("Stopped sharing with the computer"). The wrong-password count lives in the helper and starts from zero after a restart, which is why restarts are bounded. The language follows the Shell's: the Shell tells it the current one every time it lists the folders.

On the development machine the Shell is not root, so there is no separate uid and no namespaces, and the development machine's kernel (4.18) has no Landlock: rlimits, seccomp and `fd-only` apply. The selftest checks that the helper gets EPERM opening by path, creating a file, making IPv4 and Unix sockets, exec and ptrace. On the device (QEMU, root) it also requires a separate uid, no capabilities, namespaces and Landlock; that part, and the cases over the real USB link, passed on the emulator (2026-11-14).

| Environment | Result |
|------|------|
| Unit tests (`usbshare`, `sandbox`, `programs/usbshared`) | ✓ (§5) |
| Development machine selftest (not root, kernel 4.18) | ✓: the existing USB cases ("USB 连接电脑……" and "音乐：电脑经 USB……"; the firewall case needs netfw and is skipped on the development machine) pass without a step changed, and the new case "USB 文件共享在单独的沙箱进程里……" passes |
| Emulator (QEMU, root, dummy_hcd) | ✓: the USB cases above all pass, the helper in a cgroup of its own with its memory and process limits |

### 3.3 File transfer (MTP)

In Settings › USB the user chooses what a trusted computer gets: network sharing (the default) or file transfer (MTP). MTP (the Media Transfer Protocol, built on PTP's container format) is how Android phones connect to computers: Windows Explorer and Linux file managers (gvfs, KDE, through libmtp) show the phone as a device of its own; macOS has none built in and needs Android File Transfer or OpenMTP. Code: `usbshare/mtp` (the protocol, the phone's end and the computer's), `hal/usbgadget/ffs.go` (the FunctionFS function), `shell/usbmtp.go` (switching, selftest), `programs/usbshared/mtp.go` (the helper), `apps/settings/usb.go` (the settings page).

Network sharing stays the default, for the reasons of §0: nothing to install on the computer (macOS, Linux and Windows 11 have the NCM driver and a browser), a password for each connection shown only on the phone, and the debug shell (SSH) in developer mode goes only over it; MTP needs third-party software on a Mac and has no password. What MTP gives is drag and drop in Windows Explorer, and Windows versions before 11, which have no NCM driver.

| Step | On the phone | On the computer |
|------|--------|--------|
| Plug in | As in §3: first a USB network adapter without an address, and the screen asks "Trust this computer?". With a lock-screen PIN and the phone locked, it does not ask yet: it says to unlock, and asks once unlocked. MTP has no password, so the trust is the only gate (Android too offers MTP storage only unlocked) | A network adapter that gets no address |
| Trust | The Shell (root) makes the FunctionFS function `ffs.mtp` in configfs, mounts it, writes its descriptors and strings to ep0 and opens its three endpoints; then it puts it in the configuration in place of the network function and binds the controller again (product `0x0105`, the Microsoft OS descriptor on), starts the sandboxed helper and notifies "File transfer on" | The network adapter goes and an MTP device "Kario phone" comes, with four storages: Photos, Videos, Music, Files |
| Copy files | The helper uses, through `usbshare.Remote`, the same library as network sharing: a download is a read-only fd the Shell opened, an upload goes into a pipe, and the Shell checks as before (§3.2) | Drag in, drag out; folders can be made in Music |
| Unplug | Sharing stops, the configuration gets the network function back, the trust is forgotten | The device is gone |

- The rules are §3.1's: each folder is a storage, always named in English; the computer reads everything and adds files, a name already taken becomes "name (2)" (and ObjectInfoChanged tells the computer the new name); folders can be made only in Music. The phone's files are read-only to the computer (ProtectionStatus read-only): deleting, renaming and moving get Object_WriteProtected. A file the computer announced with SendObjectInfo and has not sent yet may be renamed or deleted: it is not on the phone. A folder the library offers read-only (not `Writable`, which the web page shows without its upload form) is a read-only storage (AccessCapability read-only): files, folders and copies into it get Store_Read_Only; today all four folders are writable.
- What a folder would not take is refused before the bytes come: a file other than JPEG or PNG into Photos (Invalid_ObjectFormatCode), one over the folder's limit (Object_Too_Large), one larger than the free space (Store_Full); data longer or shorter than announced gets Incomplete_Transfer, and the Shell keeps no file cut short. A file of 4 GB or more is announced as 0xFFFFFFFF, as the specification says, and its data runs to the end of the transfer.
- Operations: GetDeviceInfo, OpenSession, CloseSession, GetStorageIDs, GetStorageInfo, GetNumObjects, GetObjectHandles, GetObjectInfo, GetObject, GetPartialObject and Android's GetPartialObject64 (libmtp and gvfs read in pieces), SendObjectInfo, SendObject, DeleteObject, MoveObject, CopyObject (a copy on the phone into a folder that takes it), GetObjectPropsSupported, GetObjectPropDesc, GetObjectPropValue, GetObjectPropList (Windows reads by property list, taken as Android takes it: depth 0 one object, depth 1 a folder and its contents), SetObjectPropValue, GetDevicePropDesc and GetDevicePropValue (the device's name). Events: ObjectAdded, ObjectRemoved (the folders the computer looked at are listed again every 5 seconds, so a photo taken or a file deleted on the phone reaches it), ObjectInfoChanged, StorageInfoChanged. Class requests on the control endpoint: Cancel, Device Reset, Get Device Status.
- How the computer knows it is MTP: the interface is of the still image class 6/1/1 (PTP) and named "MTP" (which libmtp looks at); Windows reads the Microsoft OS descriptor (the string at 0xEE, then with the vendor request it names the extended compatible ID "MTP"), and the kernel's configfs answers both for the function; DeviceInfo's vendor extension is `microsoft.com: 1.0`.
- Sandbox: still `phone-usbshared`, started through `phone-sandbox` the same way and adding `fd-only` the same way; fd 3 is ep0, fd 4 the Shell, fds 5, 6 and 7 the bulk-in, bulk-out and interrupt endpoints, and the helper opens no path. The Shell keeps these files open (FunctionFS takes the function away when ep0 is last closed): a helper that crashes is started again with the same files, and the computer, its session gone, opens another (Windows does).
- The developer machine has no USB device controller: a simulated cable (`mtp.NewSim`) carries USB's packets on pipes (512 bytes a packet, a short or zero-length packet ending a transfer), and the selftest plays the computer. The FunctionFS layer is unit-tested without root: SOCK_SEQPACKET socket pairs stand in for the function's files (each read or write one record, as each is one FunctionFS request; a write of nothing a zero-length packet), and `OpenMTP` writes its descriptors into plain files standing in for the mount point. The bulk-out endpoint is always read in whole packets, what a read cannot hold kept for the next one: FunctionFS rounds a request up to whole packets, and older kernels fail it with EOVERFLOW when more data comes than the read holds. On the emulator the computer is dummy_hcd's host side: the selftest uses its own Go initiator over usbfs (`/dev/bus/usb`), then libmtp's own tools (mtp-detect, mtp-files, mtp-getfile; libmtp is what the Linux file managers gvfs and KIO use) to detect the device, list files and copy one. libmtp-bin goes into the emulator's image only, not a phone's; libmtp and libusb are LGPL-2.1, the image's licence rule (`INCOMPATIBLE_LICENSE`) bars only GPLv3, LGPLv3 and AGPLv3, and `scripts/license-check.py` checks only Go modules and Rust crates, not the image's packages.
- Kernel: `phone-usb.cfg` turns on `CONFIG_USB_CONFIGFS_F_FS`, and the emulator's `phone-usb-sim.cfg` `CONFIG_USB_DUMMY_HCD`. The build stops when the kernel configuration lacks them (`do_phone_usb_kconfig` in the kernel recipe; Yocto's own configuration check only warns); the selftest's MTP case starts with `usb-mtp kernel`, before `require-usb` so that it is never skipped, which checks the running kernel: `CONFIG_USB_CONFIGFS_F_FS` in its configuration (`/proc/config.gz`; the functionfs file system registers only with the first FunctionFS function, so it cannot be looked for) where there is a device controller, and on the emulator (QEMU's virt board) also dummy_hcd's controller, without which every USB case would be skipped unseen.

|------|------|
| Unit tests (`usbshare/mtp`, `hal/usbgadget`, `programs/usbshared`, `shell`) | ✓ (§5) |
| Development machine selftest (simulated cable, the real sandboxed helper) | ✓ |

## 4. For comparison: how an iPhone connects to a computer for debugging

| Stage | iPhone | Kario |
|------|--------|-------|
| Trust | Plugged in, the phone asks "Trust This Computer?" and wants the passcode; the two exchange a pairing record (made by lockdownd; the computer keeps it in `/var/db/lockdown`, on Windows in `Apple\Lockdown`), after which it does not ask again; "Settings › General › Transfer or Reset › Reset Location & Privacy" clears them | Asks every time the cable goes in and keeps no pairing record; unplugging ends it |
| Link | Always usbmux: many TCP-like connections multiplexed on one USB interface (usbmuxd on the computer); since iOS 17 there is also a USB-NCM network adapter, and developer services go over an IPv6 tunnel on it | A USB-NCM network adapter with ordinary TCP/IP |
| Finding services | lockdownd (port 62078) starts services by name; since iOS 17 it is RemoteXPC / RSD (remote service discovery), which lists the services once the tunnel (CoreDevice) is up | Only file sharing (port 80); in developer mode also the debug shell |
| Files | AFC (Apple File Conduit) serves the Finder's file sharing, limited to the sandboxes of apps that declare file sharing; photos go over PTP | A browser / WebDAV, with four folders: photos, videos, music, files (§3.1) |
| Debugging | First "Settings › Privacy & Security › Developer Mode" has to be turned on (a restart and one more confirmation, since iOS 16); Xcode mounts a personalized developer disk image (DDI, signed per device since iOS 17), then reaches debugserver, instruments and other services through the tunnel; after pairing it can also debug over Wi-Fi | In developer mode (turned on in Settings, [07](07-ecosystem-and-store.md)) a trusted cable reaches the debug shell (SSH, dropbear in development images); outside developer mode the cable reaches only file sharing, with ports filtered by link (`netfw.Link`) |
| Computer-side software | Built into macOS; Windows needs "Apple Devices" or iTunes; the open-source libimobiledevice / pymobiledevice3 implement the same protocols | None needed: a browser, a file manager, `ssh` |

So the answer to "how does an iPhone connect to a debug interface" is that it has no separate debug port; it is this one cable. Trust it first (pairing), turn on Developer Mode, and Xcode finds the developer services lockdownd / RSD lists over usbmux (since iOS 17, a tunnel on the USB network adapter). We copied the two rules, "trust first" and "debugging only in developer mode", and replaced the link with a standard USB network adapter, which removes usbmux and the dedicated computer-side software.

## 6. Not done

- MTP has not been tried with real Windows, macOS (Android File Transfer, OpenMTP) or Linux (gvfs, KIO) computers, **not verified on hardware**; Windows' property-list reading and uploads follow the specification and what Android does, and the tests' initiator is our own; on the emulator libmtp's tools join it (✓), while Windows' MTP driver (WPD) and the macOS programs have no stand-in.
- Cancelling an MTP transfer half-way stops only between two chunks (when the computer stops taking or sending, the read or write stuck on FunctionFS cannot be stopped) and has not been tried with Windows, **not verified**; the helper starts before the computer has finished enumerating and takes the packet size of high speed (512 bytes), so full-speed computers are **not verified**. Thumbnails (GetThumb), SendObjectPropList and object references (playlists) are **not implemented**; a change on the phone reaches the computer as an event up to 5 seconds later.
- PD drivers on real hardware, and switching the port's data role (whether the phone is host or device is the port controller's decision; `CONFIG_TYPEC` and `USB_ROLE_SWITCH` are on).
