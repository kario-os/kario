# OnePlus 6T (fajita): Kario's first real phone

> Kario on the OnePlus 6T (Snapdragon 845, codename fajita): what to buy, how to prepare the phone, how to build the image, trying it with `fastboot boot` before flashing it, debugging without a serial port, what to check first after boot, how to return to Android, and what is not done yet. The device support follows what Nura (postmarketOS until it was renamed in 2026-09) does: the kernel, its configuration, the firmware and the sound configuration are the same ones Nura uses, see §12.
> Status: the boot image and the userdata image built on the developer machine (2026-11-18, RHEL 8, x86-64, kas-container; §4, SKU `oneplus-fajita-t9`, the image's `sku.json` holding this phone's screen at 4.5 times). Checked: the header as `unpack_bootimg` reads it (version 0, page size 4096, the offsets, the command line); the kernel in the boot image is byte for byte `Image.gz` followed by the 6T's device tree (`dtc` reads "OnePlus 6T", the S6E3FC2X01 panel); all 134 options of Kario's configuration fragments are in the final kernel configuration; the root file system has every service that should be enabled enabled and every firmware file the device tree names; `e2fsck` finds no problem; the sparse image restores to the ext4; `phone-abslot` tested on disk images (kario-bsp's `tests/abslot-test.py`), `fajita-flash.sh` run against a fake fastboot. On 2026-11-21 a 6T was prepared on another computer (§9.1: partition backups, TWRP not working on OxygenOS 11, Nura's boot image in `boot_a`); Kario has run on it since 2026-11-22: first in the chroot on Nura, then on 2026-11-24 the first whole-firmware flash (which did not boot; the cause is known: OnePlus's ABL always appends a `root=` of its own), recorded in §16. Apart from what §9.1 and §16 record, everything this document says about behaviour on the phone is **not tried on a phone** (未上真机); what is still to be checked on the phone is listed in §14.Kario has not run on it yet: apart from what §9.1 records, everything this document says about behaviour on the phone is **not tried on a phone** (未上真机); what is still to be checked on the phone is listed in §14. On 2026-11-24 the whole firmware was flashed on it for the first time (the image of `0befb13`): the flash succeeded, and every boot ended back in fastboot. ## 1. Overview

| Item | How |
|----|------|
| Boot | The phone's own bootloader (ABL) loads an Android boot image directly (header version 0, page size 4096, kernel offset 0x8000, ramdisk 0x01000000, tags 0x100, as in Nura's deviceinfo), written to `boot_a` and `boot_b` |
| Kernel | sdm845-mainline's `sdm845-7.1-rc1-r0` (the tag Nura's linux-postmarketos-qcom-sdm845 builds), Nura's configuration plus Kario's configuration fragments; `Image.gz` with `sdm845-oneplus-fajita.dtb` appended; lockdown (integrity) forced, loading only modules signed with the build directory's key (§8.3) |
| Root file system | The whole `userdata` partition is one ext4 (4 KiB blocks, not partitioned further), which the boot image's phone-initramfs finds by its partition name and mounts read-write, whatever `root=` the command line names; it grows to the whole partition at the first boot. This is the default userdata layout; for the A/B layout (the root file system in `system_a` and `system_b`, the data on userdata) see [43](43-phone-partitions.md) and §15, **not tried on a phone** |
| A/B slots | After boot `phone-qcom-abslot` marks the slot it booted from as "successful" in the GPT attributes, so the bootloader does not count down its tries and fall back to the other slot (in the A/B layout it is marked after the health check instead, [43](43-phone-partitions.md) §3.5) |
| Debugging | A serial console and SSH over the USB cable (§7); the previous boot's kernel log kept in ramoops |
| Names | Yocto machine `oneplus-fajita` (kario-bsp's `meta-kario-sdm845/conf/machine/oneplus-fajita.conf`), kas file `yocto/kas/phone-fajita.yml`, SKU `oneplus-fajita-t9` (board `sku/boards/oneplus-fajita.toml`, [24](24-sku-framework.md)) |

Why an initramfs (changed 2026-11-24): the boot image used to carry an empty cpio, and the kernel mounted the root itself through `root=PARTLABEL=userdata`. That relied on Qualcomm's ABL source (the copy SHIFT6mq publishes, also a Snapdragon 845): when the boot image's own command line has `root=`, ABL appends neither the system partition as `root=` nor `skip_initramfs`, `ro init=/init` and the slot suffix. OnePlus's ABL behaves otherwise, as found on that 6T on 2026-11-24 (how, in §8.2):

- ABL **always** appends `root=PARTUUID=<Android's system partition>` among its `androidboot.*` words, whether or not the boot image's own command line has a `root=`; the kernel takes the last `root=`.
- With a `root=` in the boot image's command line, ABL adds neither `skip_initramfs rootwait ro init=/init` nor `androidboot.slot_suffix=_a`; without one (Nura's command line) it adds them all.
- The failed boot's console (ramoops, read after a warm reboot): the kernel mounted Android's system partition, could not execute `/etc/init` and ran `/bin/init` (Android's init), which could not mount selinuxfs in its first stage and rebooted into the bootloader after `InitFatalReboot: signal 6`: back in fastboot 17 s after power-on.
- Once failed boots had spent slot a's tries, ABL marked it unbootable (`slot-unbootable:a: yes`, `slot-retry-count:a: 0`) and from then on refused `fastboot boot` of any image with `Load Error`, until `fastboot set_active a` (tries back to 7).

Kario's kernel, device tree, UFS and root file system are fine: Kario's kernel with Nura's initramfs came up and saw the UFS (`sda1`…`sda17`) and a sound userdata (`sda17`, `PARTLABEL=userdata`). The failure of busybox's `mount PARTLABEL=userdata` that time says nothing about the kernel: busybox's `mount` does not take `PARTLABEL=`, the kernel's root mounting does (on QEMU, with nothing appended, the kernel mounts by it, §8.2).

Now the userdata layout's boot image carries phone-initramfs too (the same one QEMU and the A/B layout use, [43](43-phone-partitions.md)) and no longer depends on what ABL does with the command line: it learns the userdata layout from `/etc/phone/layout` in the ramdisk, looks the partition up by name in sysfs after the board's partition table (`partitions.conf`, whose data partition is `userdata`; no udev; the UFS's units come up one after the other, so it waits up to 30 s), mounts the ext4 read-write without fsck, and `switch_root`s to `/sbin/init`; the command line's `root=`, `init=`, `ro` and `skip_initramfs` are never used. It writes the whole `/proc/cmdline` (ABL's additions included) and what it did into the kernel log (lines starting `phone-initramfs:`), which the next boot finds in pstore and `bringup-log` (§8.2). When the partition is missing, holds no ext4 (Android's or Nura's data) or has no `/sbin/init`, it says why and reboots after 10 s (a warm reboot, so pstore keeps this boot's log); it never formats userdata. The boot image's own command line keeps `root=PARTLABEL=userdata`, which nothing reads: with it, ABL adds no `skip_initramfs`, `ro init=/init` or `androidboot.slot_suffix` (its own `root=` it adds all the same). Without a slot suffix, `phone-abslot` takes the slot marked active in the GPT for the one this boot started from: ABL boots the active slot, and `fajita-flash.sh`'s `flash` and `test` make the current slot active first, so `phone-qcom-abslot` still marks the right slot (kario-bsp's `tests/abslot-test.py` tests it with the command line ABL gave that time). `rootfstype`, `rootwait` and `rw` were for a kernel mounting the root itself and are gone. The root file system keeps its `/` line in fstab, so that systemd grows the ext4 to the whole partition at the first boot; the `/init` link is still there too, but it is for a kernel mounting the root itself, and on the 6T such a kernel always mounts the Android partition ABL names: it is of no use any more. UFS, GPT and ext4 are built into the kernel: the initramfs needs no module. Shown on QEMU (`make yocto-userdata-test`: the 6T's partition names on a SCSI disk with 4096-byte sectors, the command line ending with ABL's additions simulated as they were that time, §8.2), **not tried on a phone**.

Why not U-Boot with systemd-boot: Nura now installs systemd-boot for sdm845 as well, for those who also flash U-Boot (UEFI); with the stock bootloader Nura flashes the same Android boot image. U-Boot in between is one more thing to flash and debug; the first real phone starts with the fewest.

Two kinds of test, one after the other, **both after the backup of §3.5** (before anything is written to the phone for the first time), with the same kit (`tools/phone-chroot/kario-phone.sh --sku oneplus-fajita-t9`, [24](24-sku-framework.md) §6.2), the same steps and the same results; §13 is the procedure for both:

1. chroot: the phone runs Nura, and the root file system of this phone's own image (the one §6 flashes) runs on its kernel: the apps, the shell, the selftest, the compatibility run, the pixel selftest, memory and power, on Nura's kernel, panel, modem and sound.
2. The whole phone (`--whole`): the phone boots our own image (§5 to try it, §6 to flash it), and the kernel, firmware, boot and A/B slots are ours; the same selftest, compatibility run, pixel selftest, facts and results, over its USB console's network (§7).

Back to OxygenOS: §9; in the worst case (no fastboot) the MSM download tool of §3.4, after which the backup of §3.5 writes the IMEI and the calibration back.

## 2. What to buy

- A OnePlus 6T; the China model A6010 is fine (the same hardware as the international one, only shipped with HydrogenOS). 8 GB or 6 GB of memory both work. The screen should be good: a broken or replaced screen may not be the original panel.
- Keyboard: a **Bluetooth keyboard**. A USB-C OTG keyboard does not work today: in the mainline device tree the 6T's USB is device only (`dr_mode = "peripheral"`) and the phone supplies no VBUS; host mode would lose the USB console of §7. The Shell's side can be a host already (allowing, the VBUS budget, a keyboard plugged in while locked entering only the PIN, [27](27-usb-typec.md) §2.1); the 6T still lacks (**not implemented**; the kernel and board files change in another repository): dwc3 with `dr_mode = "otg"` and `usb-role-switch`, PMI8998's Type-C port driver (mainline's `qcom_pmic_typec`, `CONFIG_TYPEC_QCOM_PMIC`; whether it knows PMI8998 in the kernel version in use has to be checked, **not verified**) with a `usb-c-connector` in the device tree (`data-role` and `power-role` both `dual`, its endpoint to dwc3), PMI8998's VBUS regulator (`CONFIG_REGULATOR_QCOM_USB_VBUS`, its compatible to be checked too) as its `vbus-supply`, and in the kernel also `CONFIG_USB_DWC3_DUAL_ROLE`, `CONFIG_USB_XHCI_PLATFORM`, `CONFIG_USB_HID`, `CONFIG_HID_GENERIC` (and `CONFIG_USB_STORAGE` for sticks); then the board file gets `[usb] host = true`, `vbus_ma = 500`, noted in `unverified`. What plugging a keyboard in does while §7's USB console holds the device controller (the console drops while the port is host and has to come back after) has to be seen on the phone (**not tried on a phone**).
- A USB-C cable that carries data, and a Linux computer with `fastboot` and `adb` (android-tools), and a TWRP image for the 6T for the backup of §3.5 (on one 6T with OxygenOS 11 TWRP did not come up, and Nura's boot image did the job instead, see §9.1).
- A SIM card. Most Chinese carriers need VoLTE for calls (China Unicom and China Telecom have switched 2G and 3G off); VoLTE is written, **not tried on a phone** (§11.1, the steps to try it in §14.6); try SMS and data first. Trying calls takes a second phone at the other end.

## 3. Preparing the phone

### 3.1 The system: OxygenOS 11.1.2.2

Nura and the community say to update to the 6T's last OxygenOS (11.1.2.2) first: the mainline kernel uses the firmware in the phone's partitions (modem, DSPs and so on), and this version is the one tested most.

The China model ships with HydrogenOS. The A6010 hardware is the same, so OxygenOS can be flashed on it:

1. Unlock as in §3.3, or flash the international OxygenOS straight away with the MSM download tool of §3.4 (the community's international MSM packages for fajita are OxygenOS 9 or 10).
2. In OxygenOS, install the full 11.1.2.2 package under Settings › System › System updates › Local upgrade (downloaded from OnePlus or a community mirror).

These steps are the community's; Kario has not tried them (**not tried on a phone**).

### 3.2 The same firmware in both slots

The 6T has A/B slots, and the other slot may hold older firmware. Kario's boot image goes to both slots (§6), and when the bootloader falls back to the other slot it uses that slot's modem and other firmware, so both slots must match. Two ways:

- Install the same full 11.1.2.2 package twice through Local upgrade (each install goes to the slot not in use).
- Or, following LineageOS's install guide for fajita, `adb sideload` its copy-partitions package in its recovery, which copies slot a's partitions to slot b.

### 3.3 Unlocking the bootloader

1. Settings › About phone, tap "Build number" seven times to get the developer options; in them turn on "OEM unlocking" and "USB debugging".
2. `adb reboot bootloader` (or hold Volume up + Power with the phone off) to get into fastboot.
3. `fastboot oem unlock`, then choose the confirmation with the volume keys and press Power. **This erases all data on the phone.**
4. Reboot into the system, go through the setup wizard, then back to fastboot: `fastboot getvar unlocked` should say `yes` (or `fastboot oem device-info` shows `Device unlocked: true`).

### 3.4 When it is bricked: the MSM download tool

When a 6T is truly bricked (no fastboot), Qualcomm's EDL mode and OnePlus's MSM download tool (Windows, the community's fajita packages) restore it: with the phone off, hold Volume up and Volume down while plugging in the USB cable, the phone enters EDL (9008), and the tool writes every partition back to the factory state, relocking the bootloader too. Kario writes only `dtbo`, `boot` and `userdata` (§6; the A/B layout `system` too, §15), so it is seldom needed; but it is the last way back, so find the package for your model before you start. It wipes or replaces `persist` (the fingerprint's and the sensors' calibration) and the partitions holding the IMEI, and the factory package's are not this phone's: after using it, write them back from the backup of §3.5 with `fajita-flash.sh restore-efs`. **Do not use it before the backup of §3.5 is made**: until then the phone's copy of those partitions is the only one. How to leave EDL without flashing anything: §9.1.

### 3.5 Backup: the partitions only this phone has

After unlocking and before anything is written to the phone for the first time (installing Nura counts), copy these to the computer: `persist` (the fingerprint's and the sensors' calibration; another phone's does not work), `modemst1`, `modemst2`, `fsg`, `fsc` (the IMEI and the modem's configuration: without them there is no IMEI and no calls), `boot` and `dtbo` of both slots (to go back to OxygenOS), and each LUN's GPT.

```
yocto/fajita-flash.sh backup twrp-fajita.img
```

`twrp-fajita.img` is a TWRP for the 6T that `fastboot boot` starts on OxygenOS 11 (twrp.me's fajita page, or the community's build on XDA). The script starts it with `fastboot boot`, so it runs from RAM and nothing is written to the phone; it copies each partition with `dd` through TWRP's adb and checks each against the phone's SHA-256; it writes `SHA256SUMS` and `phone.txt` (the serial number, the time, whether `boot` is OxygenOS's); and it ends in fastboot mode. The default place is `~/kario-phone-backup/oneplus-fajita-<serial>/`, outside the repository; **copy it to another disk or a cloud drive too**: it is this phone's only copy of its IMEI and calibration. With a backup already there the script does nothing, so a phone changed later never replaces it.

`test`, `flash` and `restore` first check this backup (the same serial number, the phone's own five partitions all there, each file's SHA-256) and refuse, writing nothing to the phone, when it does not check out; a missing `boot` or `dtbo` (the phone had lost them by then, §9.1) only gets a warning, and going back to OxygenOS then needs `--stock` (§9).

Tested against a simulated phone (`yocto/fajita-flash-test.py`, in `make test` and CI), **not tried on a phone**.

On one 6T (OxygenOS 11.1.2.2) this step could not be done: TWRP 3.7.0_9 crashed into EDL after `fastboot boot`, and the bootloader refused other images. That phone's backup was made with `dd` in the debug shell of Nura's boot image instead, see §9.1; the script cannot go that way yet (**not implemented**).

## 4. Building

```
make yocto-doctor WORK=$HOME/yocto/fajita-work
make yocto-build WORK=$HOME/yocto/fajita-work KASFILE=yocto/kas/phone-fajita.yml SKU=oneplus-fajita-t9
```

- First `make yocto-doctor`: anything the build cannot do without (podman or docker, kas-container, subordinate uids and gids for rootless podman, a Go no older than go.mod's, GCC 14, cargo, openssl, the disk) that is missing is marked MISS, and it exits 1; see [13](13-prototype.md) §5.1. After go.mod or go.sum changed, `make yocto-build` first writes the Go module list again (which needs the network).

- The SKU `oneplus-fajita-t9` is this phone as a 9-key bar phone ([24](24-sku-framework.md) §7.4): it generates `phone-sku`'s `sku.json` (the shell draws for the 1080×2340 screen at 4.5 times, 80 rows left dark at the top and the bottom for the notch and the rounded corners) and the kas overlay (machine `oneplus-fajita`; a whole phone uses the kernel's own device tree, no overlay). A whole phone has no firmware package from `make sku`: the build's images are flashed as they are (§5, §6).
- The kas file keeps `phone-qemuarm64.yml`'s distribution and packages, drops the A/B system slots, dm-verity and the wic disk (none in the userdata layout; the A/B layout: the last item of this list), adds meta-qcom. The upstream layers' commits are pinned in `phone-qemuarm64.yml`, the same as the QEMU images' (later wrynose makes udev depend on iproute2-devlink, which ends up needing bash, GPL-3.0). The parallelism (`BB_NUMBER_THREADS`, `PARALLEL_MAKE`) is no longer fixed at 16 but follows this machine's processors and memory (`make yocto-doctor` prints it, `YOCTO_JOBS=` changes it, [13](13-prototype.md) §5.1); the single-threaded ncurses and zstd and the zstd without pzstd added on an 8-core, 15 GB machine were not taken, for the reasons given there.
- `PHONE_BRINGUP = "0"` (local.conf or a kas overlay) builds the image without the debugging aids of §7.
- The GPU test image: add `KASEXTRA=yocto/kas/paint-gpu.yml`, and phone-paint composes on the GPU from boot ([42](42-gpu-rendering.md) §3; where that does not start or fails later it draws on the CPU as always); the rest is this SKU's image (only `sku.json`'s `"paint_gpu": "compose"` more), the same SKU; check it on the phone as in §8.1.
- The screen shows no kernel or systemd output and no cursor while the phone boots (since 2026-11-26, report 007, §16.13): from the bootloader's picture straight to the Shell's boot animation. To see the boot log, add `KASEXTRA=yocto/kas/boot-log.yml` (it sets `PHONE_BOOT_LOG = "1"`, which adds `console=tty0` to the command line); it is independent of `PHONE_BRINGUP`. The serial console (`console=ttyMSM0`), pstore and the journal keep the full log in both kinds of image.
- The kernel module signing key: `make yocto-build` runs `make ota-keys` first, which makes `kernel-modules.pem` in `$WORK/ota-keys/` where there is none (never in git, beside the update keys); the kernel trusts only it, and the image build checks every module (§8.3).
- The A/B layout ([43](43-phone-partitions.md), built once on 2026-11-24, **never booted**): `KASFILE=yocto/kas/phone-fajita-ab.yml` (it includes `phone-fajita.yml`, sets `PHONE_LAYOUT = "ab"` and adds RAUC, dm-verity and the update keys), the same SKU.

The results are in `$WORK/build/tmp/deploy/images/oneplus-fajita/`:

| File | Written to | Size (the 2026-11-24 build) |
|------|--------|------|
| `boot-oneplus-fajita.img` | `boot_a`, `boot_b`: the kernel followed by the device tree, phone-initramfs | 23 101 440 B (22.0 MiB) |
| `phone-image-oneplus-fajita.rootfs.ext4.sparse` | `userdata` (a run of zeros travels as 4 bytes) | 494 244 860 B (471 MiB) |
| `phone-image-oneplus-fajita.rootfs.ext4` | The same file system, raw | 756 830 208 B (722 MiB) |
| `phone-image-oneplus-fajita.rootfs.abboot` (A/B layout) | `boot_a`, `boot_b`: the kernel, the device tree, phone-initramfs, the root's signed verity descriptor | 23 101 440 B (22.0 MiB) |
| `phone-image-oneplus-fajita.rootfs.ext4.verity.sparse` (A/B layout) | `system_a`, `system_b`: ext4 plus the dm-verity hash tree | 502 748 180 B (766 509 056 B unpacked) |

AOSP's mkbootimg makes the boot image (`mkbootimg-native`); `yocto/meta-phone/files/phone-img2simg.py` makes the sparse image: blocks of zeros, or of one word repeated, become fill chunks, never "don't care", so the partition's old data cannot show through where the file system expects zeros. Checking the boot image: `unpack_bootimg --boot_img boot-oneplus-fajita.img` (the same AOSP tools, in the build under `tmp/sysroots-components/x86_64/mkbootimg-native/usr/bin/`) should list header version 0, page size 4096, the offsets above and the command line. The 2026-11-24 build (in the build machine's `bt-work`) reads: a kernel of 15 885 968 B (exactly `Image.gz` followed by `sdm845-oneplus-fajita.dtb`, byte for byte), a ramdisk of 7 204 986 B: 1024 bytes of a cpio holding only `etc/phone/layout` (`layout=userdata`), then byte for byte `phone-initramfs-oneplus-fajita.cpio.gz` (7 203 962 B, about 18 MB unpacked: busybox, `/init` being `slot-init`, the board's `partitions.conf`, and the veritysetup, openssl and mke2fs the A/B layout needs); the command line `root=PARTLABEL=userdata console=ttyMSM0,115200 phone.gui=1 console=tty0` (since 2026-11-26 the default is `… phone.gui=1 vt.global_cursor_default=0`, with `console=tty0` only when `PHONE_BOOT_LOG = "1"`, the item above); the former one's (`0befb13`) ramdisk was an empty cpio of 512 bytes. How big `boot_a` and `boot_b` are is not in the documents yet (§15.1): that 6T's `boot_a` has held Nura's boot image (its own build of the same kernel version with a 14 MB initramfs), which is bigger than this; `flash` reads `partition-size` before writing, as before. `fajita-flash.sh`'s `test` and `flash` refuse a boot image whose ramdisk has no initramfs or names no layout (§5).

## 5. Trying it first: fastboot boot

```
yocto/fajita-flash.sh -n test     # only print the fastboot commands it would run
yocto/fajita-flash.sh test
```

It needs the backup of §3.5 first. `test` erases `dtbo_a` and `dtbo_b`, then boots the boot image once with `fastboot boot`: neither `boot` nor `userdata` is written, and after a reboot the bootloader starts from its own `boot` partition again. The dtbo has to go: otherwise ABL applies Android's device tree overlays to the mainline device tree and the phone stays in fastboot (sdm845-mainline's install notes). With the dtbo erased, OxygenOS does not start either until the dtbo is back (§9).

At this point userdata still holds Android's or Nura's data, not Kario's root file system: a boot image built with `KASEXTRA=yocto/kas/boot-log.yml` (§4) shows the kernel's output on the screen (`console=tty0`) and the initramfs's lines (`phone-initramfs: … no ext4 on /dev/sda17` or `has no /sbin/init`); the default image writes none of this on the screen, the bootloader's picture stays until the display driver takes over (about 6 s) and the screen is dark after that, so use the boot-log image for this step. After 10 s it reboots, and the phone starts the system in its `boot` partition (OxygenOS, with its dtbo erased, does not start, §9). Check that the screen lights up, the kernel runs and the initramfs finds userdata, then flash. The script first checks that `fastboot getvar product` says `sdm845` and refuses anything else; the bootloader reports the SoC, and a OnePlus 6 says `sdm845` too, so before writing it also asks you to confirm it is a 6T (`-y` skips the question). `test` and `flash` refuse a boot image without the initramfs (builds before 2026-11-24) or whose ramdisk does not name the userdata layout. Before `fastboot boot`, `test` makes the current slot active (`fastboot --set-active`, which changes only the slot's attributes in the GPT): once ABL has marked a slot that kept failing unbootable it refuses even `fastboot boot` (`Load Error`, §8.2), and making it active clears that mark and gives it 7 tries again; it also clears the slot's "successful" mark, which the system in `boot` sets again at its next start (Kario's `phone-qcom-abslot`, OxygenOS's own).

## 6. Flashing

```
yocto/fajita-flash.sh flash
```

It needs the backup of §3.5 first. `boot` and `userdata` must come from the same build directory: Kario's kernel forces lockdown (integrity) and loads only modules signed with that build directory's key (§8.3); the image build has already checked that the modules in userdata and the kernel in the boot image belong together.

In order: erase `dtbo_a` and `dtbo_b`; write Kario's boot image to both `boot_a` and `boot_b` (should the bootloader fall back to the other slot, it is still Kario: a 6T user saw a slot never marked "successful" fall back to OxygenOS on a cold boot); write userdata's sparse image; make the current slot active (in both layouts: ABL clears an unbootable mark and gives it 7 tries, and `phone-qcom-abslot` marks it successful once Kario is up, §1); reboot. Every image goes with `fastboot -S 64M`, in downloads of at most 64 MiB (`--chunk` sets another size, e.g. `--chunk 16M`): on the 6T of 2026-11-24 the former `-S 512M` (the bootloader takes at most 512 MiB at a time) lost the USB link 471 MB into the first piece (`Write to device failed in SendBuffer()`), while `-S 64M` wrote it in 8 pieces in 22.5 s. A smaller piece costs one more round trip, tens of milliseconds; smaller than 64M works too, 64M is what worked on that phone. `-s` picks the phone, `-d` another image directory, `-n` only prints.

The partitions written and erased come from the board file (`[partitions]` in `sku/boards/oneplus-fajita.toml`, [43](43-phone-partitions.md) §2). Before writing, the script reads the size of each partition it writes or erases with `fastboot getvar partition-size:<name>`, and writes nothing when one is missing or an image does not fit; a dry run (`-n`) first lists each partition to be written, the file and its size, then the fastboot commands. `persist`, `modemst*`, `fsg`, `fsc`, the modem's and the boot chain's partitions are never written in any path, whatever the board file says. After flashing it notes the layout in the backup directory (`kario.txt`). `--layout ab` flashes the A/B layout: check §15 first.

At the first boot the initramfs finds userdata by its name and mounts it read-write (§1), systemd grows the ext4 to the whole of userdata (`x-systemd.growfs`), `phone-qcom-abslot` marks the slot, and then Kario's UI comes up.

## 7. The debugging console

There is no serial port (the 6T's debug UART is only on test points on the board), so debugging goes over the USB cable. With `PHONE_BRINGUP = "1"` (the machine's default) the image has `phone-bringup`:

- Early in boot it binds a USB device (`kario-bringup`, 1d6b:0104) with two functions: a CDC-ACM serial port (`ttyGS0` on the phone, root logged in automatically) and a CDC-NCM network interface (`dbg0` on the phone, address 172.16.42.1, handing the computer 172.16.42.11–20). It takes the USB controller first, so the shell's own USB sharing does not work meanwhile; it is not called `usb0`, so the firewall the shell sets on its USB link leaves it alone.
- While a computer has the USB device configured (plugged into a computer that took it), the wake lock `phone-bringup` keeps the phone out of suspend, so the USB console does not drop; unplugged, or on a charger alone, it is released and the phone sleeps as usual (`phone-bringup-awake`, changed 2026-11-26, **not tried on a phone**; before, it was taken at boot and never released, and the battery was empty after a night, §16.12). `/usr/libexec/phone-bringup/awake check` says whether it should be held now, and why.
- The boot log on the screen is not part of this: `PHONE_BOOT_LOG` controls it (§4), and a bring-up image does not write the log on the screen by default either.
- Kernel logs: the device tree has a ramoops region (`ramoops@ac300000` in `sdm845-oneplus-common.dtsi`, 4 MiB: console 256 KiB, crash records of 256 KiB each, ftrace 256 KiB, pmsg 2 MiB, with 16 bytes of ECC; read in `sdm845-7.1-rc1-r0` on 2026-11-24), and the kernel has `CONFIG_PSTORE_RAM` and `CONFIG_PSTORE_CONSOLE`, so the previous boot's console and crash logs survive a warm reboot (**not verified** on the 6T); systemd-pstore moves them to `/var/lib/systemd/pstore` at every boot; the journal is kept on userdata too. The initramfs's lines (`phone-initramfs:`, §1) are in there as well.

```
picocom /dev/ttyACM0                 # serial: ttyACM0 appears on the computer (screen /dev/ttyACM0 works too)
ssh root@172.16.42.1                 # network: DHCP on the computer's new interface; otherwise ip addr add 172.16.42.2/24 dev <interface>
journalctl -b -1                     # the previous boot's log
bringup-log                          # the previous kernel log pstore kept (-a: all of it)
phone-abslot status                  # the state of both slots
systemctl stop phone-bringup-awake   # release the wake lock even on a computer, to try suspend
```

Under lockdown (integrity) unsigned modules do not load; of debugfs only the read-only files can be read (such as `wakeup_sources`), not the writable ones or those with an ioctl or mmap: using those takes a kernel built without `phone-lockdown.cfg` (§8.3).

root has no password, so whoever has the cable is root: this is a development image, for debugging only. An image with `PHONE_BRINGUP = "0"` has none of this (dropbear and the empty password are `phone-qemuarm64.yml`'s settings, in every development image).

It takes Nura v26.06's boot image for the 6T (`~/kario-images/nura-boot.img`) and AOSP's `unpack_bootimg` and `mkbootimg` (the build's `mkbootimg-native`, §4):

  --base 0 --pagesize 4096 --kernel_offset 0x8000 --ramdisk_offset 0x01000000 \
  --second_offset 0x00f00000 --tags_offset 0x100 -o ~/kario-images/test-kb.img
```

1. Watch what happens; note the seconds from power-on to the failure and the text on the screen (take a photo):
   - The kernel's text and a few `phone-initramfs:` lines on the screen, a reboot after some ten seconds, again and again: the initramfs did not find or mount userdata, and its last lines say why (pstore has them too). Hold volume up as it reboots to get into fastboot (with the slot never marked "successful", ABL also stops in fastboot once it has counted its tries).
   - Back in fastboot within some ten seconds: that is what happened on 2026-11-24 (17 s), the kernel mounting its root itself took the Android partition ABL named and ran Android's init (§1). An image with the initramfs should not do that any more: read pstore (step 2).
   - The kernel's text stops at `Waiting for root device`: that is the old image without the initramfs (`fajita-flash.sh` now refuses it).
   - systemd came up but not Kario's UI: past mounting the root; connect the USB console as §7 says.
2. The failed boot's kernel log and ABL's command line: **do not cut the power** (ramoops lives in RAM and survives only a warm reboot); back in fastboot, right away `fastboot boot ~/kario-images/test-kb.img`, and in its debug shell (`telnet 172.16.42.1 23`):

   ```

### 8.3 Kernel modules: under lockdown only signed ones load

Every Kario kernel forces lockdown (integrity, `phone-lockdown.cfg`; the 6T's base configuration, Nura's, always had it, but Kario's fragments did not pin it): the kernel loads only modules that are signed with a key whose certificate it carries. Modules are signed at installation (stripped of debug information first: packaging leaves signed modules alone) with the build directory's key, `$WORK/ota-keys/kernel-modules.pem`: `yocto/ota-keys.sh` makes it (`make ota-keys`, which `make yocto-build` runs first), never in git; `phone-kernel.inc` puts it at `certs/kario-modules.pem` (`CONFIG_MODULE_SIG_KEY`), and its certificate is the one built into the kernel.

On 2026-11-24 the first whole-phone boot (the image of `d4856a3`, [41](41-design-gaps.md) §18) loaded no module at all, each attempt `Lockdown: modprobe: unsigned module loading is restricted`: no RTC, battery, charger or sound card; `qrtr` is a module, so `tqftpserv` said `socket(AF_QIPCRTR): Address family not supported`, and so is the modem's remoteproc, so `rmtfs` said `Failed to get rprocfd`; `uim-select` asked for qrtr every two seconds for its whole 60 seconds, and the Shell, ordered after it, reached the panel a minute late; the "VPN (device)" case's `netlink receive: no such file or directory` was the same: the Shell's per-app firewall needs `nft_ct`, and when it cannot be loaded nf_tables answers `ENOENT` (WireGuard was built in all along). The cause (read from the build machine's files, **seen**): all 1094 modules were signed, but with the key the kernel generated for itself in bt-work's build (serial `53:01:12:ad…`), while the kernel flashed was fajita-work's, carrying only the one it had generated (`5b:c1:aa:4a…`). The two build directories share their sstate: fajita-work's module packages (`do_package_write_rpm`) came from what bt-work had left there, while its boot image was made with the kernel fajita-work had compiled; the key a kernel generates differs in every build and is in no task's signature, so the sstate could not tell them apart. The kernel reports "unsigned", "key not there" and "unknown algorithm" with the same sentence, which made it look unsigned. Packaging did not strip the signatures (OE does not strip signed modules).

Now (built, verified on QEMU, on the whole phone **not tried on a phone**):

- The key stays in the build directory, and its checksum is in the kernel tasks' signatures: another key means another kernel and other modules in the sstate, never paired wrongly again. The cost: build directories have different keys, so kernels (QEMU's too) are no longer shared between build directories through the sstate; each build directory compiles its own.
- The image build checks (`phone-modsig.bbclass`, `files/phone-modsig-check.py`): every `.ko` in the root file system is in the directory of the boot image's kernel's release, signed, with the build directory's key, and verifies, and that kernel carries the key's certificate; otherwise `do_image_qa` fails (`modules-signed`). The image of `d4856a3` does not pass: all 1094 modules are `signed by a key the kernel does not have`. `yocto/modsig-test.py` tests it (`make test`, CI); `scripts/yocto-check.py` also stops a configuration that leaves the signing key to the kernel.
- Built into the kernel (`phone-fajita.cfg`): what the 6T always has, needs from the start of user space and has no firmware for. The IPC router `qrtr`, its channel to the DSPs `qrtr-smd` and the PD mapper the DSPs ask when they start (rmtfs, tqftpserv and the modem's QMI clients open qrtr sockets as soon as they start; as a module each socket asks for it to be loaded); the PMIC's RTC `rtc-pm8xxx` (the kernel sets the clock from it before user space, `hctosys` is 1, phone-clock does not wait); the fuel gauge bq27411 (`bq27xxx_battery` and its I2C part), the PMI8998 charger (`qcom_smbx`) and the ADC it reads (`qcom-spmi-rradc`), so the battery is there when the Shell starts.
- Still modules (signed): what loads firmware from the root file system, the modem and the DSPs (remoteproc), IPA, Wi-Fi (ath10k), video (venus), the sound card: built in they would ask for their firmware once, from the initramfs, before the root file system is mounted. Also what is loaded when used: `nft_ct`, NAT (the Shell's firewall and the hotspot; nf_tables loads them itself). WireGuard was built in already (`phone-vpn.cfg`).
- To check (whole phone): `cat /sys/kernel/security/lockdown` shows `[integrity]`; `/usr/libexec/phone/module-check.sh` loads a module (by default `nft_masq`) and what it needs afresh, the kernel verified its signature (no `E` taint), a copy of it with one byte after the signature (where the kernel no longer finds it) is refused (`Operation not permitted`), it prints `PHONE-MODULES: PASS` and leaves the module as it was; `modinfo -F signer nft_masq` says `Kario kernel modules (development)`. QEMU's boot selftest runs it first every time (`make yocto-selftest`).
- QEMU's kernel (linux-yocto 6.18) had neither module signatures nor lockdown, not even securityfs (so the lockdown level could not be read, and `module-check.sh` failed on its first run for that); `phone-lockdown.cfg` goes into every Kario kernel, and QEMU's boot selftest now runs under lockdown too (2026-11-25: `PHONE-MODULES: PASS`, the whole selftest passing).

## 9. Returning to Android

Kario writes only `dtbo_a/b`, `boot_a/b` and `userdata`; `system`, `vendor` and the firmware partitions are still OxygenOS's (the A/B layout wrote `system_a/b` too, [43](43-phone-partitions.md) §3.1). The ways back, lightest first:

- `yocto/fajita-flash.sh restore`: writes both slots' `boot` and `dtbo` back from the backup of §3.5, makes the current slot active (after Kario failed to come up ABL may have marked it unbootable, and then OxygenOS would not start either), clears userdata with `fastboot -w` and reboots into OxygenOS (its first start after the wipe takes a few minutes). When the backup was taken after Nura or Kario was installed (`stock-boot=no` in `phone.txt`), or lacks `boot` or `dtbo` (the phone had lost them by then, §9.1: the script says "restore will want --stock" when it checks the backup), take `boot.img` and `dtbo.img` from the full OxygenOS 11.1.2.2 package instead (it holds a `payload.bin`; a tool such as payload-dumper unpacks it) and name their directory with `--stock`. Before writing anything the script checks the four files it would write back: each `boot` an Android boot image that is neither Kario's nor Nura's, each `dtbo` starting with the mark of Android's device tree overlay table (`d7b7ab1e`, which a copy of an erased partition lacks); with one missing or wrong it stops and asks for `--stock`, writing not a byte. `--stock`'s two files are checked the same way. After the A/B layout (`layout=ab` in the backup directory's `kario.txt`) `--stock` is a must, and the directory needs the same package's `system.img` too: the script writes it into `system_a` and `system_b` (sizes checked first).
- No IMEI, or no fingerprint can be enrolled (the MSM tool or something else touched those partitions): `yocto/fajita-flash.sh restore-efs twrp-fajita.img` writes the backup's `persist`, `modemst1`, `modemst2`, `fsg` and `fsc` back through TWRP, reading each back to check it. Where TWRP does not come up, write them back from Nura's debug shell instead, see §9.1.
- No fastboot: the MSM download tool (§3.4), unlocking again (§3.3: the MSM tool locks the bootloader), then `restore-efs` (or §9.1).

Not to do: **do not lock the bootloader again** (`fastboot oem lock` / `flashing lock`) while the phone is not on its factory system: that bricks it for good; do not `fastboot erase` or flash `modem`, `persist`, `modemst*`, `fsg` or `fsc` (the script touches only `dtbo`, `boot` and `userdata`, and `system` too in the A/B layout; those partitions are on the script's never list, and `restore-efs` writes back only a backup that checks out).

`restore` and `restore-efs` are tested against a simulated phone (`yocto/fajita-flash-test.py`), **not tried on a phone**.

### 9.1 What happened on one 6T (2026-11-21)

A China model 6T (A6010, OxygenOS 11.1.2.2, `ONEPLUS A6010_41_210805`) went through the preparation and the backup on another computer. Numbers that belong to that phone alone, its serial number and IMEI, stay out of the documents; below they are written `<serial>`. Where it differed from what is said above:

- **TWRP did not work**: TWRP 3.7.0_9 starts with `fastboot boot`, but crashed after coming up on OxygenOS 11, the first time straight into EDL (`05c6:900e` on USB, QUSB_BULK); the bootloader refused TWRP 3.6.2 and LineageOS 22.2's `boot.img` (`Failed to load/authenticate boot image: Load Error`; `dtbo_a` and `dtbo_b` were erased by then, and whether that is the cause was not established). So on this phone `backup TWRP.img` of §3.5 and `restore-efs TWRP.img` of §9 **cannot be used**; other TWRP versions were not tried.
- **`fastboot fetch` is not supported** (`Unable to get max-fetch-size`): reading a partition takes booting another kernel.
- **Nura's boot image worked**: `fastboot boot` of the `boot.img` Nura v26.06 has for the 6T (mainline kernel `7.1.0-rc1-sdm845`, header version 0) runs from RAM and ended in the debug shell of postmarketOS's initramfs: the phone at `172.16.42.1` on a USB network interface, the computer given `172.16.42.2/24`, telnet on port 23, root, no password. In that shell `dd` read the partitions and `nc` carried them to the computer, which made the backup; the same way writes them back. With Nura installed on userdata the same boot image starts Nura itself, whose SSH does as well (**not tried**).
- That initramfs has no `/dev/block/by-name/`: the partitions are the kernel's numbered `sdX`, on this phone `persist`=`/dev/sda2`, `modemst1`=`/dev/sdf2`, `modemst2`=`/dev/sdf3`, `fsg`=`/dev/sdf4`, `fsc`=`/dev/sdf5`, `boot_a`=`/dev/sde11`, `boot_b`=`/dev/sde39`, `dtbo_a`=`/dev/sde18`, `dtbo_b`=`/dev/sde46`. The numbers may change with the kernel: check `grep PARTNAME /sys/class/block/<name>/uevent` before every read or write. Each LUN's (`sda`…`sdf`) GPT is its first 6 sectors of 4096 bytes (`dd bs=4096 count=6`, what the script copies).
- **The phone now**: `boot_a` holds Nura's boot image; `boot_b` is still OxygenOS's own (backed up as `boot_b.img`); `dtbo_a` and `dtbo_b` are erased (installing Nura erases them) and **the stock dtbo was not backed up**: going back to OxygenOS takes it from the `payload.bin` of the full OxygenOS 11.1.2.2 package.
- **Where the backup is**: in `~/kario-phone-backup/oneplus-fajita-<serial>/` on that computer, outside the repository, each partition's SHA-256 checked against the phone's. A phone's backup, its firmware and its keys **never go into the repository** (no `device/` directory or the like in it either); copy the backup to another disk or a cloud drive too.

For the scripts to take a backup made by hand (`test`, `flash`, `restore` and the chroot kit's `push` check it first, §3.5): the file names are the script's; what must be there is the phone's own five, `persist.img`, `modemst1.img`, `modemst2.img`, `fsg.img`, `fsc.img`; `boot_a.img`, `boot_b.img`, `dtbo_a.img`, `dtbo_b.img` only where they are still the stock ones (`boot_b.img` on this phone), and for those missing the script only says so (`the backup has no boot_a.img … restore will want --stock`) and flashes all the same; `gpt-sda.bin`…`gpt-sdf.bin` for the GPTs; `phone.txt` has a line `serial=<serial>` (what `fastboot getvar serialno` says), and since this phone's `boot_a` is no longer the stock one, `stock-boot=no`; last, in that directory, `sha256sum *.img *.bin > SHA256SUMS`. A `dtbo_a.img` and `dtbo_b.img` copied after the erase hold the erased contents: leave them out (`restore` tells them anyway: without the overlay table's mark it refuses); `stock-boot=no` makes `restore` insist on `--stock`. On 2026-11-24 the tester made such a backup, and the check and the dry run before `flash` passed (with the script as they had changed it; the script now does what this paragraph says, `yocto/fajita-flash-test.py` ✓).

Backing up one partition from the debug shell (the computer listens first, then the phone sends; the two `sha256sum` must match):

```
nc -l -p 9999 > persist.img                       # on the computer (OpenBSD's nc: nc -l 9999)
grep PARTNAME /sys/class/block/sda2/uevent        # on the phone: PARTNAME=persist
dd if=/dev/sda2 bs=4096 | nc 172.16.42.2 9999     # on the phone
sha256sum /dev/sda2                               # on the phone; on the computer sha256sum persist.img
```

**Back to OxygenOS (this phone)**: take `boot.img` and `dtbo.img` out of the `payload.bin` of the full OxygenOS 11.1.2.2 package (with a tool such as payload-dumper) into a directory outside the repository. With the backup made so that the scripts take it, `yocto/fajita-flash.sh restore --stock <that directory>` writes the two files to both slots, runs `fastboot -w` and reboots. When the scripts refuse the backup, do the same by hand (`boot_b.img` is OxygenOS's own boot and can stand in for the package's `boot.img`):

```
fastboot flash boot_a boot.img && fastboot flash boot_b boot.img
fastboot flash dtbo_a dtbo.img && fastboot flash dtbo_b dtbo.img
fastboot -w
fastboot reboot
```

**Writing the EFS back (IMEI, the fingerprint's and the sensors' calibration) without TWRP**: only when those partitions really were lost (no IMEI, no fingerprint can be enrolled, §9). Write them from Nura's debug shell, not from a running Kario or Nura: there rmtfs holds `modemst1`, `modemst2`, `fsg` and `fsc` open, reading and writing them for the modem.

```
fastboot boot ~/kario-images/nura-boot.img   # Nura v26.06's boot image for the 6T, run from RAM
telnet 172.16.42.1 23                        # once the USB interface is up and the computer has 172.16.42.2/24
```

Write each backup to the partition of its name, **only** these five: `persist`, `modemst1`, `modemst2`, `fsg`, `fsc`. First carry it to the phone's `/tmp` (on the computer `nc -l -p 9999 < persist.img`, on the phone `nc 172.16.42.2 9999 > /tmp/persist.img`), check `sha256sum /tmp/persist.img` against the backup's `SHA256SUMS` and the target partition's `PARTNAME`, `dd if=/tmp/persist.img of=/dev/sda2 bs=4096`, read it back with `sha256sum /dev/sda2` to check it, and `sync`.

**Leaving EDL**: with the phone at `05c6:900e`, Sahara, Firehose and USB resets from the computer did nothing; **unplug the USB cable and hold the power key for 40 seconds** (failing that, power + volume up for 20 seconds), and the phone resets. Before the backup is made, do not get out with the MSM download tool (§3.4): it rewrites `persist`, `modemst*` and `fsg`, whose only copy is then the phone's.

This section is that computer's record, its commands checked against this repository's scripts. Going back to OxygenOS and writing the EFS back have **not been done** on this phone yet.

### 11.1 VoLTE (81voltd, the carrier configuration and telephonyd's part done, **not tried on a phone**)

Most Chinese carriers need VoLTE for calls (§2), which makes it the biggest gap in using the 6T as a phone. What follows comes from reading sources and public discussions on 2026-11-18, all **not tried on a phone**. On the Snapdragon 845 the IMS stack (SIP, RTP, voice codecs) runs in the modem firmware; what Linux has to do is pick the right carrier configuration for the modem and connect the IMS data network for it:

| Part | What it does | State |
|------|--------|------|
| Carrier configuration (MBN) | The modem turns IMS and VoLTE on, with their parameters, per carrier. The files are in the `modem` partition (vfat) under `image/modem_pr/mcfg/configs/mcfg_sw/…`; on Android the vendor's service picks one by SIM card and loads it into the modem over QMI PDC | Kario's firmware package, like Nura's, does not install `modem_pr`; whether the modem reads one itself through tqftpserv, and which, is **unknown**. The configurations the modem holds already (loaded by Android, kept in the modem's persistent storage) are activated by `phone-qcom-pdc` for the SIM's carrier; loading a file into the modem is done by hand only (below), **not tried on a phone** |
| IMS data (QMI service 770) | The modem asks the application processor to open a data connection for IMS (the APN is usually `ims`) | Nura uses 81voltd: on the request it opens a bearer through ModemManager's `CreateBearer` (APN, IP family, 3GPP profile id). Kario's image has it too (for SKUs whose board has `ims`, below), built, **not tried on a phone** |
| ModemManager | Open a second bearer besides the internet one (multiplexed rmnet), with a profile id | The image has 1.24.2, which has `profile-id` and multiplexing; a second bearer over QRTR is **not verified** |
| telephonyd | Not take the IMS bearer for mobile data, nor disconnect it | Done on 2026-11-25, tested against the simulated ModemManager, **not tried on a phone**, see below |
| Call audio | VoLTE calls also use the DSP's voice path, so q6voiced and audiod's UCM set-ups apply as they are | Whether an IMS call is an ordinary Call object in ModemManager is **unknown** |

**81voltd**: version 1.2.0 of gitlab.nura.eco/modem/81voltd, packaged in Alpine community; Nura's `soc-qcom-modem` depends on it. The licence is **GPL-2.0-or-later** (LICENSE holds the GPLv2 text, and every source file is marked `GPL-2.0-or-later`), not GPL-3.0, so it may go into the image. It is about two thousand lines of C depending on libqmi (`qmi-glib`), ModemManager's `mm-glib` and libqrtr, built with meson; all three are in Yocto (meta-oe, meta-qcom), and a recipe would be about twenty lines. The problems it states itself: stopping it does not disconnect the bearers it opened; ModemManager's errors are not passed on to the modem. The pmaports merge request that added it calls it a stopgap, to be merged into ModemManager in the long run. From its source (`qvd-modem.c`, `qvd-server.c`): it knows ModemManager's QRTR modem by its port `qrtr0` and queues the modem's requests until that modem shows up; `CreateBearer` gets only the APN, the IP family and the profile id (when the modem gives one), no `apn-type`; when someone else disconnects the bearer (airplane mode, a radio restart) it tells the modem the connection is down, and the modem asks again.

**Where it clashed with telephonyd** (changed on 2026-11-25, see [04](04-ui-language-telephonyd.md) "Bearers other programs bring up"; tested against the simulated ModemManager, **not tried on a phone**):

- telephonyd took any connected bearer for "mobile data connected": once the IMS bearer was up it no longer opened a bearer for the internet. Now it tells bearers apart by their `BearerType`, `apn-type` and APN: 81voltd 1.2.0's `CreateBearer` gives only the APN, the IP family and the profile id, no `apn-type` (its source was read), and telephonyd recognises it by the SIM's IMS APNs and the well-known `ims` and `sos`, not as data.
- Turning the data switch off called `Simple.Disconnect("/")`, which disconnects **every** bearer, the IMS one included. Now only telephonyd's own data bearer is disconnected (by its path); airplane mode still has `Modem.Enable(false)` take every bearer down (the radio goes off anyway).
- `status`'s `data_ifaces` no longer include the IMS bearer's interface, and the shell's firewall does not close it with mobile data off.
- Also note: the first time telephonyd sets the modem's LTE attach APN ([04](04-ui-language-telephonyd.md) "The LTE initial attach APN"), ModemManager takes the radio down and up again; the IMS bearer drops once with it and 81voltd has to bring it up again.

**81voltd in the image** (2026-11-25, built, **not tried on a phone**): the recipe kario-bsp's `meta-kario-qcom/recipes-bsp/81voltd/81voltd_1.2.0.bb` takes the tag `v1.2.0` of gitlab.nura.eco/modem/81voltd, its commit pinned to 7c0cd944 (`SRCREV`); the licence checksums cover `LICENSE` and `main.c`'s SPDX line; built with meson, with the `qmi_imsd.c` generated in the repository (no qmic). What it needs, glib, ModemManager 1.24.2's `libmm-glib`, libqmi 1.38 (QRTR on) and meta-qcom's libqrtr, is in the 6T's image already. Upstream's unit says `After=ModemManager.target` (no such target, so no ordering) and it installs an OpenRC script; neither is used, Kario's `81voltd.service` stands in: ordered after ModemManager, `phone-qcom-uim` and `phone-qcom-pdc`, restarted 5 s after a failure, with `G_MESSAGES_DEBUG=all` (it logs what the modem asked and which bearer it opened as GLib info messages, which are dropped otherwise). Only SKUs whose board has `ims = "81voltd"` get it ([24](24-sku-framework.md) §2: `tools/sku.py` writes it into the kas overlay as `PHONE_IMS`, from which the machine `oneplus-fajita` installs `81voltd` and `phone-qcom-pdc`), so far `oneplus-fajita-t9` alone; the OnePlus 6's board has no Yocto machine yet and leaves it out. Stopping or restarting 81voltd leaves the bearers it opened connected, and when the modem asks again it opens another: airplane mode on and off clears the old ones (`Modem.Enable(false)` disconnects every bearer).

**Carrier configuration: `phone-qcom-pdc`** (2026-11-25, tested against a simulated qmicli, **not tried on a phone**): on Android the vendor's service activates the modem's software configuration (MCFG) for the SIM's carrier, which holds the IMS and VoLTE parameters. Kario's `pdc-select` (recipe `phone-qcom`, the oneshot unit `phone-qcom-pdc.service` at boot, after `phone-qcom-uim` and before ModemManager, as activating restarts the modem; not run when `phone-qcom-uim` fails, without a SIM):

1. `qmicli --nas-get-home-network` reads the SIM's home network (MCC, MNC; every 2 s, at most 10 times while the SIM is not ready, then it does nothing) and looks the carrier up in `/usr/share/phone-qcom/pdc-carriers`: China Mobile (460 00, 02, 04, 07, 08, 13), China Unicom (01, 06, 09), China Telecom (03, 05, 11), China Broadnet (15), each with the words configuration names call it by (`cmcc`; `cu`, `unicom`; `ct`, `telecom`; `cbn`). A carrier not in the table: nothing done.
2. A carrier dealt with before (`/var/lib/phone-qcom/pdc-<MCC>-<MNC>` exists): nothing done. One choice per carrier, and a configuration changed by hand afterwards stays.
3. `qmicli --pdc-list-configs=software` lists the modem's configurations (each one's name and status goes into the journal); of those whose name has one of the carrier's words and that are no lab or test build (`lab`, `test`, `cta`, `ptcrb` in the name), one for VoLTE (`volte`, `hvolte`) comes first, then a commercial one (`commercial`), then one for phones sold unlocked (`openmkt`), and among equals the newest version. None: nothing done, nothing recorded.
4. The one picked is Active or Pending already: recorded as `kept`, left as it is. Otherwise it is recorded as `activated` first (an activation that does not take is not tried again at every boot, each time restarting the modem), `qmicli --pdc-activate-config=software,<ID>` (no answer within 60 s and it carries on: the modem may be restarting), then it waits until the list shows it Active (Pending is not enough: the old modem is still running then; at most a minute, and if it stays Pending it says it applies at the modem's next start), and runs `uim-select` again (after the restart the SIM's session has to be opened again).

It never calls `--pdc-load-config` (which writes a file into the modem's flash), `--pdc-deactivate-config` or `--pdc-delete-config`, and leaves platform configurations alone. `pdc-select --dry-run` only says what it would do; to turn it off: `systemctl disable --now phone-qcom-pdc`; to have it choose again: remove `/var/lib/phone-qcom/pdc-*`. The slowest run (the first boot with a carrier's SIM, activating) holds ModemManager back two or three minutes; usually it takes the few seconds of one SIM read. The words follow the names of the three Chinese carriers' configurations seen on Quectel's modules (`Volte_OpenMkt-Commercial-CMCC`, `OpenMkt-Commercial-CU`, `OpenMkt-Commercial-CT`) and Qualcomm's MCFG directories (`China/CT/Commercial/hVoLTE_OpenMkt`); which ones the 6T's modem holds and what they are called (a 6T running LineageOS listed 25, `TGL_Comb_Attach-Lab-CMCC` among them, so at least China Mobile's lab build) is to be seen on the phone (§14.6). Tests: kario-bsp's `tests/pdc-select-test.py` (`make test`, CI; the fake qmicli answers as libqmi 1.38's does).

**Loading a configuration file into the modem is done by hand only**: when the modem lacks the carrier's configuration, `mcfg_sw.mbn` has to be copied out of the `modem` partition's `image/modem_pr/mcfg/configs/mcfg_sw/generic/china/…` and loaded with `qmicli --pdc-load-config`. That writes the modem's persistent storage (EFS), and a modem with a wrong one loaded has misbehaved; only the tester does it, after the backup of §3.5, following §14.6. Kario never loads one by itself.

**Calls, SMS and emergency calls over IMS** (from ModemManager 1.24.2's and libqmi 1.38's sources, **not tried on a phone**):

- Calls: ModemManager dials through QMI Voice's `Dial Call` with the number alone and no call type, so the modem decides between CS and IMS by its configuration; `All Call Status` reports every call, whatever its domain. A VoLTE call is an ordinary Call object in ModemManager: telephonyd, q6voiced (which opens the voice path by the Call's state) and phone-audiod's UCM call set-up need no change, and the audio still goes through the DSP's voice path (IMS media is in the modem and the DSP); DTMF (`Call.SendDtmf`) is sent by the modem too. The reports of the 6T making VoLTE calls on Nura with 81voltd went the same way.
- The IMS registration state: ModemManager 1.24 has no interface for it. telephonyd asks the modem through phone-qcom-ims's `ims-status` (QMI's IMSA service) and logs the state; when an outgoing call on 4G or 5G ends before it rings with IMS not registered, the screen says "Call failed: VoLTE is not registered" (§14.21, tested against the simulated ModemManager and qmicli, **not tried on a phone**). The state last read is `status`'s `ims`: while registered on 4G or 5G with IMS registered, the status bar writes 「VoLTE」 left of the network type, and the last row of Settings › Mobile network says the registration (§14.21, **not tried on a phone**); an HD voice mark is **not implemented**. For tests the modem can also be asked directly, binding first (§14.21 step 2); without the binding IMSA only answers `InvalidOperation` (008).
- SMS: ModemManager sends and receives through QMI WMS without saying whether over IMS; with no CS domain (a Telecom SIM on 4G alone) whether SMS goes over IMS is up to the modem and the network, **not tried on a phone**.
- Emergency calls: the modem asks for the emergency data connection (APN usually `sos`) through the IMS data service as well, and 81voltd opens it; how the three Chinese carriers route emergency calls on 4G is **not tried on a phone**, and real emergency numbers are not dialled to find out (§14.1).
- A VoLTE switch in Settings (Android's "Enhanced 4G LTE mode"), Wi-Fi calling, video calls, moving a call to 2G or 3G (SRVCC): **not implemented**. China Unicom and China Telecom have switched 2G and 3G off, so with VoLTE off there are no calls at all: no switch for now.

**How to try it once the phone is here** (in order, each step can be undone):

1. Make the backup of §3.5 first: a wrong PDC configuration makes the modem misbehave (one of Nura's developers ran into that), and the backup of `modemst1/2` and `fsg` is the way back.
2. In OxygenOS, check that the SIM card does VoLTE on Android; copy `image/modem_pr` out of the `modem` partition and look for the Chinese carriers' directories (`…/generic/china/…`).
3. On Nura (test one, §13.4) install 81voltd: `qmicli -d qrtr://0 --pdc-list-configs=software` lists the configurations in the modem and which one is active; if needed load the matching `mcfg_sw.mbn` with `--pdc-load-config` and activate it with `--pdc-activate-config`, then place a VoLTE call. What the community reports: on Nura the 6T and the Pixel 3a make VoLTE calls with 81voltd, with some carriers (Telstra in Australia) failing; someone switching configurations with qmicli on a 6T running LineageOS got a German card working with "Volte_OEM_Lab".
4. Kario's part is done (the 81voltd recipe, `phone-qcom-pdc` activating the modem's configuration by the SIM's MCC/MNC, telephonyd recognising the IMS bearer): on the whole phone follow "VoLTE" at the end of §14.6 step by step, checking that the properties of the bearer 81voltd opens, as `mmcli -b` shows them, are what telephonyd recognises.

**Effort**: the 81voltd recipe, telephonyd telling the bearers apart and activating the configuration the modem holds for the SIM are done; loading a configuration file into the modem (`--pdc-load-config`) is deliberately not automated; hardest to estimate is carrier compatibility, which can only be tried carrier by carrier with real cards.

- How emergency calls and SMS over IMS go.

### 11.2 The read-only RTC: what the kernel could do instead (research, the kernel not changed)

The 6T's RTC is the PM8998's (`rtc@6000` in `pm8998.dtsi`, `qcom,pm8941-rtc`, the `rtc-pm8xxx` driver). Read on 2026-11-23 in the sources of `linux-sdm845`'s tag (`sdm845-7.1-rc1-r0`) and Nura's configuration (the very file the recipe downloads and checks):

- The driver sets the time one of three ways: with `allow-set-time` in the device tree it changes the RTC's counter; with an nvmem cell named `offset` (`nvmem-cells`, `nvmem-cell-names = "offset"`, usually 4 bytes in the PMIC's SDAM) it leaves the counter alone, writes the offset to that cell and adds it when reading the time (a drift under 30 seconds waits until shutdown, to spare the flash); with `qcom,uefi-rtc-info` it keeps the offset in a UEFI variable (Snapdragon Windows laptops, sharing it with Windows). With none of them `set_time` returns `-ENODEV`. The 6T's device tree (`pm8998.dtsi`, `sdm845-oneplus-common.dtsi`) has none of the three, and `rtc@6000` has no label either.
- Nura's configuration: `CONFIG_RTC_DRV_PM8XXX=m` (a module), `CONFIG_RTC_HCTOSYS=y`, `CONFIG_RTC_SYSTOHC=y` (both `rtc0`), `CONFIG_NVMEM_SPMI_SDAM=m`. When the RTC registers (once udev has loaded the module) the kernel sets the clock from its count once, so `phone-clock` waits for that ([28](28-battery.md) §6); while NTP is synchronised it writes the RTC every 11 minutes, which fails on a read-only RTC and does no harm.

**`allow-set-time`**: a device tree patch (the node has no label, so it goes by its path) makes the RTC settable, and the kernel's `hctosys`, hwclock and timedated are all right then. Not used:
- On Qualcomm phones the modem's and TrustZone's time services take the PMIC's RTC as a monotonic time base; Android does not write it, and Qualcomm's time-services daemon keeps the offset in `/data` (Android kernels' qpnp-rtc driver writes the RTC only where the device tree says `qcom,qpnp-rtc-write = <1>`). That, and whether the time the modem works out from the counter goes wrong once Linux changes it, are **not verified** (no public account found).
- The access rights to the PMIC's peripherals are what TrustZone configures in the SPMI arbiter: whether the HLOS may write the RTC's write registers has **not been tried** on the 6T.

**An nvmem cell** (what mainline does on the sc8280xp reference board, the CRD: `rtc-offset@bc` in the PMK8280's SDAM 6; in this tag the Lenovo X13s uses `qcom,uefi-rtc-info` instead): it needs an SDAM that Linux may write and nothing else uses. The PM8998's device tree has no SDAM node (none in this tag's `pm8998.dtsi`; whether SDAM is only in newer PMICs is **not verified**), which bytes are free only Qualcomm's firmware documents know, and a wrong cell would overwrite what the bootloader or the modem keeps there. Not done.

**A UEFI variable**: the 6T boots through Android's ABL, without UEFI runtime services: not possible.

**Decision**: Kario's own 6T kernel (`linux-sdm845`, §10) does not make the RTC settable (no device tree patch, no offset cell), the RTC stays read-only, and the offset is kept in user space (the board's `[rtc] read_only = true`, `offset = true`, [28](28-battery.md) §6): the same way on every board, relying on no spare firmware bytes and leaving the modem's time base alone. Once a board's kernel gives a settable RTC (`allow-set-time` or an offset cell in its device tree), its board file says `read_only = false` without `offset`. One smaller change was made on 2026-11-24: `CONFIG_RTC_DRV_PM8XXX=y` in `phone-fajita.cfg` (its dependencies `MFD_SPMI_PMIC` and `RTC_CLASS` are `y` in Nura's configuration) registers the RTC before user space starts, the kernel sets the clock from it, and `phone-clock` waits for no module (§8.3; `linux-sdm845`'s configuration check confirms it is in the final configuration, **not tried on a phone**).

### 14.20 Calls that cannot be answered or placed: q6voiced, the order of the services and one call's logs (**not tried on a phone**)

On image 007 (main) the incoming-call screen showed, but the call could not be answered, and outgoing calls failed. In the logs q6voiced exits at boot (`Connection error: Did not receive a reply`), and systemd gives up after five restarts. Without q6voiced the call's sound path in the DSP (the q6voice PCM) never opens, so even a call the modem connects is silent on both sides. The cause (reproduced on QEMU, see below): the upstream unit has `DynamicUser=yes`, and only `Requires=dbus.service`, with no `After=`. Kario's system bus is dbus-daemon, and systemd starts it with `SYSTEMD_NSS_DYNAMIC_BYPASS=1` (so that the bus and nss-systemd never wait for each other), so dbus-daemon cannot look up any dynamic user. On authentication it looks up the connecting user's groups; when that fails it refuses the connection and closes it, and libdbus reports `Did not receive a reply`, including on restarts after the bus is up. nss-systemd is not missing: the image's `nsswitch.conf` has `passwd: compat systemd`, and both root and `messagebus` resolve the dynamic user; only the bus process cannot. The earlier postmarketOS images used dbus-broker, which takes the peer's groups from the socket and looks up no user, and q6voiced ran there.

Now q6voiced runs as its own system user, `q6voiced`, in the `audio` group. It is ordered after the bus and ModemManager, and `q6voiced-wait` starts it once ModemManager is on the bus; the journal gets a line for what it waits for, each time that changes. On failure it is restarted with growing delays (2 s up to 60 s) and never given up. ModemManager, rmtfs, tqftpserv and phone-telephonyd never give up either.

Failed answers and dials are no longer silent. telephonyd logs `phone-telephonyd: call cN failed: <reason>`, and the screen shows "Call failed: <reason>" (the Shell says it when the call screen is not in front). The Phone app shows "Answering…" for a call that has been answered but not connected yet.

On QEMU (the qemuarm64 image with test units, started at boot through the kernel's `systemd.wants=`): a `DynamicUser=yes` service, with or without `Group=audio`, gets `Did not receive a reply` from the system bus, while the static user `messagebus` connects; dbus-daemon's environment has `SYSTEMD_NSS_DYNAMIC_BYPASS=1`. With the q6voiced program of the 6T image (`-cpu max`), the upstream unit is given up after five restarts with the same error as on 007, and with Kario's drop-in (the `q6voiced` user) it keeps running, with no restart, waiting for ModemManager. Later images cannot bring such a service back: at build time `phone-svcusers.bbclass` checks every service that starts at boot (through `.wants`, `.requires`, D-Bus activation, and the sockets, timers and path units that start one). `do_image_qa` fails (`service-users`) for a `DynamicUser=` service while the system bus is dbus-daemon (unless a static user has its name: systemd then runs it as that user), and for a `User=` or `Group=` missing from the image's `/etc/passwd` or `/etc/group` (`files/phone-svcusers-check.py`, tested by `yocto/svcusers-test.py` in `make test` and CI). On the three 6T root file systems built from the code before the fix it reports q6voiced alone, and the QEMU and other images' root file systems pass.

On image 008 q6voiced kept running, but the first call after boot was silent on both sides; later calls, and calls after a restart of q6voiced, had sound (report 008). The first call's log has `Unable to set hw params for PLAYBACK: Invalid argument` and `Failed to open rx`. The cause (worked out from the kernel, the UCM profile and q6voiced's code, **not checked on a phone**): when q6voiced opens the voice PCM (`hw:0,6`), the DSP sends the sound to the SLIMbus port of the earpiece, and which of the codec's channels that port uses is set by `SLIM RX0 MUX`. In the 6T's UCM profile only `Voice Call` sets it to `AIF1_PB`; `HiFi` does not, and no disable sequence sets it back. After boot the card had only been in `HiFi`, the channel was empty, the DSP refused, and alsa-lib reported `Invalid argument`. q6voiced opens the PCM once each time ModemManager says a call turned dialing, ringing at the other end or connected, and on failure closes it and does not try again (an incoming call gets only the attempt at connecting). It follows ModemManager, while audiod follows telephonyd (which follows ModemManager), so q6voiced is always a step ahead of audiod's move to `Voice Call`. Once audiod had moved to `Voice Call` during the first call the channel stayed set, which is why later calls and a restarted q6voiced could open the PCM. Now audiod's first start after boot sets up `HiFi` by way of `Voice Call` ([20](20-audio.md) §10), so the channel is set before the first call; unit tests ✓ (failing on the old code), **not tried on a phone**. That q6voiced does not try again after a failure is unchanged (an upstream program, packaged in kario-bsp; a retry would be a patch there): if its open fails for another reason later, that call is still silent, with the same two lines in the log.

What each service waits for at boot, and what happens when the service it depends on is late or missing:

| Service | Order | When the other side is late or missing |
|---|---|---|
| rmtfs | none (`ConditionPathExists=/dev/qcom_rmtfs_mem1`) | The modem boots from the file systems it serves. After an exit it is restarted every second, now without ever giving up, more slowly over time (up to 30 s). If the device node is not there yet at boot, rmtfs does not start and the modem does not boot (the node was there on 007) |
| tqftpserv | none | As rmtfs. On 007 it ran the whole time; the missing `.dig` files of `mcfg_hw` and `mcfg_sw` are the modem asking, not errors |
| phone-qcom-uim | after rmtfs and tqftpserv, before ModemManager | Asks the modem every 2 s, 30 times. If the modem is later than that, it fails and the SIM's session stays closed (ModemManager cannot read the SIM), with no retry on that boot: `systemctl restart phone-qcom-uim ModemManager` |
| phone-qcom-pdc (dev only) | requires uim, after it, before ModemManager | Does not run when uim failed |
| ModemManager | after uim (and pdc) | `mmcli -L` is empty until the modem shows up on QRTR; ModemManager waits for it itself. When the modem does not answer it exits 1 with the reason on one line (kario-bsp's `tests/ims-status-test.py`, with a simulated qmicli).
- On 008 it exited 1 every time: `QMI protocol error (70): 'InvalidOperation'`. IMSA answers only a client bound to a subscription: it has to send Bind first (in libqmi since 1.36, `qmicli --imsa-bind=<value>`; the libqmi commit that added it says that without it every IMSA request gets InvalidOperation), and the script above (the one in kario-bsp `b5ab9d3`) did not. qmicli sends one kind of request per run, and over QRTR a client lives with its process's socket, so it goes, binding and all, when the process exits; so the two qmicli runs have to go through qmi-proxy (`-p`): the first with `--client-no-release-cid --imsa-bind=0` binds the client and keeps it, the second with `--client-cid=<it> --imsa-get-ims-registration-status` asks, and releases it on exit. ModemManager talks to the modem through qmi-proxy too (libqmi 1.38 uses it for a QRTR device opened with the proxy flag), so while ModemManager runs the proxy keeps the device open and the kept client and its binding last between the two runs; with ModemManager away the second run gets InvalidOperation all the same, and telephonyd asks again later. The `ims-status` changed this way, with its test (the simulated qmicli refuses unbound requests as the 6T did, and the old script fails it), is in kario-bsp `f228abe`, which kario pins: **not tried on a phone**. That the value 0 is the first SIM's subscription is assumed (libqmi only says it is a 32-bit value): **not verified**.

## 16. What the phone showed (2026-11-22 to 11-25)

The Chinese-market 6T of §9.1 went through more rounds on another computer, following §13 and §14: the chroot on Nura first (§13.4, 2026-11-22 and 11-23), then on 2026-11-24 the first whole-firmware flash (§13.5), on 2026-11-25 the second (§16.10). This records, by topic, what was actually seen on the phone: when, what, whether it was **seen** or **inferred**, and what Kario does now. Numbers that belong to this phone alone, such as its serial number, are left out. Where this disagrees with the rest of this document, this wins; the other places name their source.

### 16.1 The bootloader (ABL) and booting

- **ABL always appends a root= of its own** (2026-11-24, seen): in the run of `androidboot.*` at the end of the command line ABL hands the kernel there is always a `root=PARTUUID=<GUID>` naming Android's system partition, even when the boot image's own command line has a `root=`; the kernel takes the last `root=`. When the image's line has a `root=`, ABL leaves out `skip_initramfs rootwait ro init=/init` and `androidboot.slot_suffix=_a`; without one (Nura's line) it adds them all. Qualcomm's public ABL source (§12, SHIFT6mq) adds no `root=` either when the image has one; OnePlus's ABL does.
- **What that did** (2026-11-24, seen, read from ramoops): on every boot of the whole-firmware image of `0befb13` (an empty ramdisk, `root=PARTLABEL=userdata`, the kernel mounting the root itself: "Why no initramfs" at the top of this document) the kernel mounted Android's system partition and ran `/system/bin/init`, which found no selinuxfs in its first stage, ended in `InitFatalReboot: signal 6` and rebooted: back in fastboot after some 17 s. The kernel, the device tree, the UFS drivers and the root file system written to userdata were all fine: Kario's kernel with Nura's initramfs came up, saw `sda1`…`sda17`, and userdata (`sda17` on this phone) was a sound ext4.
- **What Kario does about it**: the userdata layout boots through phone-initramfs too (since 2026-11-24): it learns the layout from the boot image's ramdisk, finds userdata by the board's partition name in sysfs, mounts it read-write and ignores every `root=`, writing the whole command line and its decision to the kernel log (pstore keeps it); the image's command line keeps `root=PARTLABEL=userdata` only so that ABL adds no `skip_initramfs`, `ro init=/init` or slot suffix (the top of this document, [43](43-phone-partitions.md)). Shown on QEMU with ABL's additions simulated as seen (`make yocto-userdata-test`); on 2026-11-24 the 6T's first whole-firmware boot came up this way (§16.9).
- **A slot's tries run out** (2026-11-24, seen): on each failed boot ABL counts the slot's tries down, and at 0 marks it unbootable (`fastboot getvar slot-unbootable:a` says `yes`, `slot-retry-count:a` `0`); from then on `fastboot boot` of any image says `Load Error`, even one that booted before. `fastboot set_active a` brings it back (tries back at 7). So on a `Load Error`, look at those two `getvar`s first. Once Kario has booted it must mark the slot successful, or every boot takes a try: `phone-abslot mark-good` in `phone-qcom-abslot.service`, which takes the slot marked active when the command line has no `androidboot.slot_suffix`. `fajita-flash.sh`'s `test`, `flash` and `restore` now `fastboot --set-active=<current slot>` every time (both layouts); with no slot suffix `phone-abslot` takes the GPT's active slot, tested with that time's command line (kario-bsp's `tests/abslot-test.py`), and `phone-qcom-abslot.service` waits for udev's `by-partlabel/boot_a` (it marked the slot on the whole phone on 2026-11-24, §16.9).
- **Reading the failed boot's kernel log** (2026-11-24, works): the 6T's device tree has `ramoops@ac300000`, Kario's kernel has `CONFIG_PSTORE_RAM` and console records, and `CONFIG_PANIC_TIMEOUT=0` (it does not restart itself after a panic). After the failure, a **warm** restart (no power cut), `fastboot boot` an image that does come up (next item), `mount -t pstore pstore /sys/fs/pstore`, read `console-ramoops-0`. That time it held 55562 bytes; ECC reported 5 corrected bytes and 434 bad blocks, so some of it was garbled, but the lines that mattered were readable.
- **A boot image for diagnosis** (2026-11-24): Kario's kernel (the boot image's, with its device tree) and Nura's initramfs, packed again as an Android boot image of header version 0 (the offsets and page size of `PHONE_BOOTIMG_*` in `oneplus-fajita.conf`), `fastboot boot`ed into RAM only: it comes up in postmarketOS's initramfs debug shell (reached as in §9.1), running Kario's kernel. With another command line in it (Kario's own, say), `cat /proc/cmdline` shows what ABL added. That shell is not process 1, so `switch_root` does not work there.
- **busybox's `mount` does not take `PARTLABEL=`**: in that shell `mount PARTLABEL=userdata /mnt` says `No such file or directory` while `mount /dev/sda17 /mnt` works. That says nothing about the kernel, whose root mounting does take `PARTLABEL=`.
- `androidboot.bootcount=1919247457`: ABL passes this large number every time; why is unknown, and it has no visible effect.

### 16.2 Flashing and fastboot

- **Big images go in chunks** (2026-11-24, seen): `fastboot flash userdata` (a sparse image of some 470 MB) lost the USB connection at 471 MB (`Write to device failed in SendBuffer()`); with `fastboot -S 64M` it went through (8 chunks, 22.5 s). fastboot's USB sometimes drops by itself after a few seconds (`usb 1-1: USB disconnect`): plug in again and retry. `fajita-flash.sh` now sends every image with `fastboot -S 64M` (`--chunk` changes it), tested against a simulated phone that drops downloads over 100M.
- **A backup without `boot_a` and `dtbo`** (2026-11-24): installing Nura had overwritten this phone's `boot_a` and erased its `dtbo` before the backup was taken (§9.1), so `fajita-flash.sh` refused to flash when checking the backup; the five EFS partitions and the six GPT headers were all there. Done: the phone's own five partitions must be there, a missing `boot` or `dtbo` only gets a warning; before writing back `restore` checks each file (an Android boot image, the DTBO mark `d7b7ab1e`), wants `--stock` for any missing or erased one, and otherwise writes not a byte (`yocto/fajita-flash-test.py`).
- **No power-off in fastboot** (2026-11-23, seen): `fastboot oem poweroff`, `oem shutdown` and `oem help` all say `unknown command`, under both `18d1:d001` and `18d1:d00d`; `getvar all` has only the charging settings (`off-mode-charge:1`, `charger-screen-enabled:1`). The only way to power it off is to hold the power key for 15–20 s.
- **Two kinds of `Load Error`**: after the dtbo was erased, the `boot.img` of TWRP 3.6.2 and of LineageOS 22.2 were refused (§9.1); the one of 2026-11-24 was an unbootable slot (§16.1). Check `getvar slot-unbootable:a` first (§8.2); the script now runs `set_active` first, so the second kind should not come up.
- After a restart `lsusb` may show `18d1:d001` while `fastboot devices` is empty: it is about to reset once more (§16.3). Wait 60–90 s before doing anything, and do not take it for a broken flash.

### 16.3 Restart, power-off and the watchdog

- **One extra boot after a restart** (2026-11-23, seen, cause unknown): after `reboot` or `fastboot reboot` the phone came up, reset about 2 s later, and only came up properly the third time (`journalctl --list-boots` lists a boot that lived 2 s). When Nura shut down, systemd logged `Using hardware watchdog /dev/watchdog0: 'qcom_wdt'` and `Failed to set watchdog hardware timeout to 10min: Invalid argument`: sdm845's `qcom_wdt` takes at most some 32 s (a count of at most 0xFFFFF on a 32764 Hz clock), not systemd's default 10 min, and on that EINVAL systemd disarms the watchdog. The extra boot also follows `fastboot reboot`, when Linux is not running, so the watchdog is not all of it. Kario's board `[watchdog]` sets the watchdog to 30 s for a restart (**not tried on a phone**; the comparison to make is in §14.10).
- **Powered off, on again 2 s later** (2026-11-23, seen; the cause is inferred): on Nura `systemctl poweroff` got to `Reached target System Power Off`, and 2 s later the phone was up again. The tester took it that the kernel had no way to power off (`pm_power_off` empty); the kernel says otherwise: sdm845 has PSCI 1.0 and `ARM_PSCI_FW=y`, so power-off goes through PSCI's `SYSTEM_OFF`, and a kernel without a way would halt, not restart. The USB cable was in and ABL has `off-mode-charge:1`, so more likely the PMIC saw the charger and powered the phone on again (§14.10 tries it with the cable out and in).
- On those occasions `pstore` was empty and `ramoops` held only `error in header` (old data in the PMIC): no crash.

### 16.4 Suspend and wake-up

- **The RTC counts from 1970 and is read-only** (2026-11-22, seen): `hwclock -w` says `ioctl(RTC_SET_TIME) failed: No such device`; at boot `rtc-pm8xxx … setting system clock to 1970-01-01…`, and the system time is right only once the network sets it, 56.9 years apart. Seconds written to `wakealarm` are by the RTC's own clock; `+N` means N seconds from now. Kario used to write the system time, so the alarm went 57 years ahead and a suspended phone never woke; it now writes `+N` (`hal/pm`, [11](11-platform-architecture.md)). On 2026-11-22 `echo +30 > wakealarm` woke the phone, and on 2026-11-23 the selftest's suspend case passed. How the time is kept: the board's `[rtc]` ([28](28-battery.md) §6).
- **The USB is gone while it sleeps** (seen): the USB controller is no wake-up source in s2idle (the only ones are the power key, the charger, the hall sensor, remoteproc, IPA, the RTC and alarmtimer); the computer's `lsusb` loses the phone and the USB network goes, until it wakes. So the phone must not sleep while tests run over USB: the whole-firmware bring-up image holds the `phone-bringup-awake` wake lock while a computer has the USB console configured (§13.5; images before 2026-11-26 took it at boot and never let go, and the battery was empty after a night, §16.12).
- **Suspend could not be stopped on Nura** (2026-11-22, seen): 3 s after the last SSH session ended came `PM: suspend entry (s2idle)`. `systemctl mask sleep.target …` does not stop it (`systemd-suspend.service` is static); with the service itself masked, `autosleep` off and logind's `IdleAction=ignore` it still slept; Nura's `sleep-inhibitor` held no lock with 3 SSH sessions open; `systemd-inhibit --mode=block` made `systemctl suspend` fail, and the phone still slept. In the end it was the selftest's own suspend case that really suspended the phone, which then could not wake because of the RTC above; with the RTC fixed none of this needs stopping.
- **The power key did not wake it in the chroot** (2026-11-23, seen; cause not found): some 40 s after `shell-start` the screen went off and the phone suspended; the power key did nothing, and only holding it (a restart) helped; the RTC did wake it the same day. logind was held off by the kit's `systemd-inhibit --what=handle-power-key` then, and the Shell was asleep too. `/sys/class/wakeup/wakeupN/event_count` at 0 and no `power/wakeup` there say nothing: pm8941-pwrkey never reports events to its wake-up source, and its attributes are in `/sys/bus/platform/devices/c440000.spmi:pmic@0:pon@800:pwrkey/power/`. On the whole phone, capture it as §14.10 says.
- **logind in Kario's image** (found 2026-11-23, seen on QEMU): unconfigured, it powered the phone off on the power key and would suspend it when a magnetic cover closes, past the Shell; the image now has `logind.conf.d/50-phone.conf`, which leaves them to the Shell ([28](28-battery.md) §7).

### 16.5 The display

- At boot `msm_dsi_phy: DSI PLL(0) lock failed, status=0x00000000` (on 2026-11-22 and 11-23 both).
- **The display did not come back after a suspend** (2026-11-22, seen): a dark screen the power key did not light, the system alive; `bl_power` 4, `fb0/blank` 4, and in dmesg `PM: suspend exit`, the DSI error above and a `dpu_encoder_phys_cmd_ctl_start_irq` timeout. By hand, `echo 0 > /sys/class/graphics/fb0/blank`, `echo 0` into the backlight's `bl_power`, writing `brightness` back and `chvt 1` each brought it back. The backlight to 0 and back, and the console blanked and unblanked, 5 times each, were fine: the panel's own power-off and power-on work. What Kario's Shell does on this path, and whether it is fixed: §16.12.
- **Screen states that disagree** (2026-11-23, `off true, panel on true`): partly a Shell bug (a restarted Shell finding the backlight off took the screen for on and never let the panel go off; fixed), the rest maybe the display chain above.
- `page flip: Invalid argument` (seen 2026-11-21): on 2026-11-23, 15 s of drm debugging did not show it again ([42](42-gpu-rendering.md) §4.3).
- **The GPU's firmware**: Nura v26.06 failed to load `a630_sqe.fw` with -40 (ELOOP, a symlink loop), `msm_dpu: failed to load a630_sqe.fw`; Kario's image brings the a630 firmware itself (§8.1).

### 16.6 Sound

The tester set `RX0 Digital`…`RX4 Digital` to 15% (`RX0 Digital` 19/124, -65 dB); whether those gains reach the speaker amplifier (a TFA9894 on QUAT_MI2S) is **not confirmed**. The kit turns them down before `selftest` and `pixel` and back afterwards (the board `[audio]`'s `quiet_controls`, §14.5).

### 16.7 Nura (the chroot's host)

- Nura v26.06 console, kernel `7.1.0-rc1-sdm845`, systemd; on the USB network the phone is `172.16.42.1`, user `user` with `sudo` without a password.
- Its LSMs are `capability,bpf` only, with no Landlock built; Wi-Fi is NetworkManager's, with no systemd-networkd; the modem's stack (ModemManager, rmtfs, pd-mapper, tqftpserv, q6voiced) is Nura's. So in the chroot the kernel features, VPN, factory reset and mobile-route cases are skipped, saying why ([40](40-testing.md)).
- In a new network namespace `lo` is DOWN; `bind` still works there and connecting to oneself fails. The sandbox's self-check used to look at `bind` alone and said "allowed" on any kernel without Landlock's network rules (fixed, [17](17-app-sandbox.md)).
- Nura's postmarketOS initramfs finds its root by partition itself and ignores `root=`, so ABL's `root=` (§16.1) never touches it.
- Camera and video: `/dev/video7: no streaming video capture`, `qcom-venus aa00000.video-codec: non legacy binding`; the 6T's camera is not done (§11).
- One selftest with the CTS (`--keep-going`) took some 18 minutes in the chroot (2026-11-23, 1107 s).

### 16.9 The first whole-firmware boot (2026-11-24, `d4856a3`)

Flashed as §13.5 says (the backup check only warned about the missing `boot_a` and `dtbo`; userdata in 8 chunks of `-S 64M`; `--set-active=a`), the whole-firmware image of `d4856a3` (reply 005) **came up the first time**:

- **The root** (seen): `phone-initramfs: … not used from the command line: root=PARTLABEL=userdata root=PARTUUID=92049492-…`, `the root file system: /dev/sda17, the partition userdata (found after 0 s)`, `starting /sbin/init`. ABL still appends its `root=` (§16.1); the initramfs ignores it.
- **The slot** (seen): `phone-qcom-abslot` marked `boot_a` successful, and after several restarts and one power-off the tries had not been counted down.
- **Selftest** (seen): a full run 193/194 (the chroot round: 183/194), CTS capabilities 132/137 (the 5 not called are skipped with the location cases that need a simulated receiver); kernel features and sandbox 3/4, the four media cases 4/4. Failed: "VPN (device)" (`netlink receive: no such file or directory`) and "DNS in the sandbox" (`chown …/state/apps/com.phone.chat: no such file or directory`: only in the short "kernel features + sandbox" run, where 鸿雁 had never started and had no data directory yet; it passed in the full run. - **Power-key wake-up** (seen, §14.10): `echo mem > /sys/power/state`, a short press once the USB had gone, up again in some 10 s (timed to USB and SSH coming back, not to a lit screen, §16.12); `pm_wakeup_irq` went from `No data available` to 90, `suspend_stats/success` 0 → 1, `pm8941_pwrkey`'s interrupts 16 → 17, and dmesg has `PM: Triggering wakeup from IRQ 90`. Its failing in the chroot (§16.4) was logind's and the kit's doing, not the kernel's.
- **Power-off** (seen): with the cable out `systemctl poweroff` stayed off for over two minutes; with the cable back in, the charger powered the phone on (`androidboot.mode=charger` on the command line), as `off-mode-charge:1` says (§16.3's inference holds). Kario now recognises the parameter and boots charger mode instead of the whole system ([28](28-battery.md) §10, 2026-11-26, **not tried on a phone**). pstore was empty, so the kernel's last line could not be seen.
- **Restart and the watchdog** (seen): `Watchdog running with a hardware timeout of 30s` (systemd and systemd-shutdown both), no `Failed to set`, and **no** extra short boot in `journalctl --list-boots`; `watchdog0: watchdog did not stop!` is the intended safety net.
- **The power key is the Shell's** (seen): logind's `HandlePowerKey` and `HandleLidSwitch` are both `ignore`; a short press turns the screen off, another on, a ~600 ms hold opens the power menu, and the phone does not power off. The cover: no magnet, **not tried**.
- **A black screen after quick power presses** (seen, by the user on the phone): single presses turned the screen off and on correctly; after a few quick presses the screen went black and keys did nothing; a later press flashed garbage and the screen came back. No logs: that image kept the Shell's screen and panel lines only in `/run/phone/shell.log`. **Cause** (inferred, **not verified on the phone**): four problems in Kario itself: every press went straight to the renderer, which queued panel changes one after another (with a panel taking 2 s per change, 6 presses kept it changing for about 10 s); a failed "panel on" was never retried, so the Shell believed the screen was lit; the backlight came on before the panel was powered (likely the garbled flash); and late page-flip events around the panel changes were counted for the next frame, which went into the buffer still on screen. **Fixed** (2026-11-25, **not tried on a phone**): one panel change at a time, ending as the last press left it, the backlight waits for the panel, a failure is retried once, and every press and panel change goes to the journal; the next round captures per §14.10 "pressing the power key again and again".
- **The kernel's lockdown kept out every module** (seen, the most serious): `Lockdown: modprobe: unsigned module loading is restricted`, `/sys/kernel/security/lockdown` at `[integrity]` and not lowerable; `rtc-pm8xxx` and `bq27xxx_battery` are modules, so `/sys/class/rtc/` and `/sys/class/power_supply/` were empty, `phone-clock` said `no rtc0 after 15s`, the time went back 3 s across a restart, and the clock step (§14.10) could not be done. The lockdown itself comes from Nura's defconfig (`CONFIG_LOCK_DOWN_KERNEL_FORCE_INTEGRITY=y`). **Fixed**: lockdown stays; each build directory has a fixed module signing key (`$WORK/ota-keys/kernel-modules.pem`, outside git) whose checksum is in the task hashes; the RTC, fuel gauge, charger, qrtr and PD mapper are built in; the image build checks every module's signature, and QEMU's boot loads a module and requires a copy changed by one byte to be refused ([17](17-app-sandbox.md); **not tried on a phone**).
- **The kit hung reading `/sys/power/wakeup_count`** (seen): while a wake lock is held (the whole firmware's bring-up image always holds `phone-bringup-awake`) the kernel keeps that read waiting, so `setup`'s facts stopped and `facts.txt` was empty; Nura holds no wake lock, so the chroot rounds never met it. - **The panel did not come back after the selftest** (seen): after the kit stopped `phone-display`, the "renderer" left (1004) was the panel renderer's child that opens the input devices for it: dropping privileges (setuid) had cleared its parent-death signal, and it was forked after the scan-out buffers were mapped, so it kept the DRM master; the new renderer got `/dev/dri/card0: Permission denied`, gave up after five restarts, `bl_power` 4. Fixed: the child is forked before the display device is opened, both set the parent-death signal again after dropping privileges and the child exits when the renderer's end closes; `phone-display` now has `KillMode=mixed` (`yocto-check` refuses `process` for a unit running phone-shell); the kit waits for a stopped unit's group to empty and names and kills what is left after 10 s (**not tried on a phone**).

### 16.11 The second whole-firmware run (2026-11-25, `86fae7a`, report 006): charging, the Shell stopping, holding the power key

These three things from the same report; the phone had a SIM card in and held the bring-up wake lock (it never suspended, `suspend_stats`' `success=0`).

- **At full, pulling the charger out and plugging it in did not light the screen** (seen): the charger's driver saw it (sampled on the phone every 0.5 s: `pmi8998-charger`'s `online` 1→0→1, its `status` following as `Full`, `Discharging`, `Not charging`), while the bq27411 fuel gauge said `Full` throughout; `bl_power` stayed 4, no message, no `screen on (charger)` in the log. **Cause** (found by reading the code, reproduced by unit tests): `hal/power` counted a battery whose `status` was `Charging` or `Full` as on external power, and the bq27411 keeps saying `Full` at 100% once the charger is gone, so to the Shell the phone was plugged in all along and plugging it in again was no plug. Writing to the renderer cannot stop the Shell like this: a thread of the renderer always reads its input into an unbounded queue, also while its main thread is stuck.

### 16.12 An empty battery after a night (report 007, 2026-11-26): the bring-up wake lock and the whole sleep path

On the whole-phone image of `48026c7` the user left the screen off for a night; in the morning the battery was empty.

- **Cause** (found in the image's unit and the Shell's code; matches the report's logs): the bring-up `phone-bringup-awake` was a oneshot that did `echo phone-bringup > /sys/power/wake_lock` at boot (the boot log's `Bring-up: keep the phone out of suspend …`), with no timeout and released by nobody, so the kernel never suspended; the Shell does not try to sleep while someone else holds a wake lock (§16.10's change) and kept the reason in memory only. The report's Shell log has the boot's `sleep: mem after 30s with the screen off` and not one `sleep:` line after it. With the screen off, the CPU, Wi-Fi and the modem ran all night.
- **Change** (2026-11-26, **not tried on a phone**):
  - `phone-bringup-awake` is now a small script that keeps running (`/usr/libexec/phone-bringup/awake`) and holds the lock only while a computer has the bring-up USB device configured: the controller `kario-bringup/UDC` is bound to has `configured` in `/sys/class/udc/<udc>/state`; `suspended` (the computer suspended the link) counts too while the cable still powers the phone. Unplugged, on a charger alone (`powered`, `default`: no computer configured it), or with the USB power supply's `online` at 0 (a controller without VBUS sensing may stay `configured` after the unplugging), it lets go. On battery it never holds it.
  - The lock has a 6 second timeout and is renewed every 2 seconds: if the script dies (even by `kill -9`) the lock expires by itself; `systemctl stop` releases it (`ExecStopPost`).
  - It reads those two attributes every 2 seconds rather than using udev: a UDC's `state` changes only with `sysfs_notify`, no uevent (the kernel's `usb_gadget_set_state`), which udev never sees; a read is two sysfs attributes and does not touch the USB itself, so every 2 seconds costs too little to measure (**inferred**); while the phone is suspended the script is frozen with every other process, never waking it, and catches up within 2 seconds of a wake. From a computer configuring the device to the lock being held is 2 seconds at most: the Shell sleeps only after the screen has been off 30 seconds, and if it goes to sleep in just those 2 seconds the phone sleeps once, as without a lock, and holds it when the computer configures it again after the wake (**inferred**).
  - One line per change: `phone-bringup-awake: holding the wake lock phone-bringup: a computer has configured kario-bringup on a600000.usb`, or `… not holding the wake lock phone-bringup, the phone may sleep: …`; `awake check` prints whether it should be held now and why, and `$W facts`'s `== sleep` has that line too.
  - The kit goes over USB as before: on the cable the lock is held, and `wakeup_count`, unreadable then, gets the 2 second wait and `<no answer in 2 s>` of §13.5; the suspend case is skipped as before and runs after `systemctl stop phone-bringup-awake`.
  - The Shell logs `sleep: awake (…)` each time what keeps it awake changes (leaving out what passes by itself within seconds: the screen on or just off, just woken, something due), so a night's log says why it did not sleep; report 007's night would have said `sleep: awake (wake lock phone-bringup)`.
  - Tests: `yocto/bringup-awake-test.py` (a fake sysfs: the UDC's state, the charger's `online`, `wake_lock`, `wake_unlock`; the old unit fails it), `shell`'s `TestForeignWakeLockKeepsThePhoneUp` (the old code does not log the line and fails). `bitbake phone-bringup phone-qcom` built in the fajita build directory; the packages hold the new script, the unit and the udev rule with the modem's name filled in.
- **When the Shell goes to sleep** (`shell/sleep.go`, [28](28-battery.md) §5): at each housekeeping (every 5 seconds with the screen off) it checks: the screen off 30 seconds or more, awake 10 seconds or more since a wake; no call or ringing, no sound playing, no update installing, no contacts syncing, no trusted computer on the Shell's own USB (in the bring-up image the controller is bring-up's, so this one does not apply), no NFC reader, no app woken by a push or a job still running; the next thing (an alarm, a scheduled notification, a job's deadline, the maintenance wake every 15 minutes at the latest) 13 seconds or more away; no wake lock held by anyone else. Then it reads `wakeup_count`, checks again, writes the count back, sets the RTC alarm 3 seconds before the next thing and writes `/sys/power/state`. When the count cannot be written back or the kernel gives up on the way (`EBUSY`) it logs `sleep: suspend aborted by a wake-up event`, from 2026-11-26 with the wake-up sources that reported an event in brackets. The Shell writes `/sys/power/state` itself, so logind does not know of the suspend and ModemManager does not turn the modem off before it (**inferred**), which is what lets a call wake it.
- **The 6T's wake-up sources** (read in the `sdm845-7.1-rc1` kernel source and device tree, **inferred**; check them as in §14.19):

| Wake-up source | How it wakes | By default |
|---|---|---|
| The power key `pm8941_pwrkey` | a wake interrupt (`enable_irq_wake`); when only the release was seen, the driver reports the press as well | on (seen waking it on 2026-11-24, §16.9) |
| The volume keys and the Hall sensor (`gpio-keys`) | `wakeup-source` in the device tree | on; whether opening the cover lights the screen is **not tried on a phone** |
| The charger's cable interrupt `usb-plugin` | a wake interrupt (`devm_pm_set_wake_irq`) | on |
| The RTC alarm (`rtc-pm8xxx`), `alarmtimer` | a wake interrupt | on (seen waking it on 2026-11-22, §16.4) |
| IPA (mobile data packets) | a wake interrupt | on |
| The modem: the GLINK `IPCRTR` channel QRTR uses (calls, SMS, QMI indications) | GLINK makes every channel `device_set_wakeup_capable` without enabling it | **off**: asleep, a call or an SMS waits for the next RTC wake (15 minutes at the latest); from 2026-11-26 a udev rule enables the modem's one (below) |
| ADSP, CDSP (`qcom_q6v5_pas`, not the modem) | `device_init_wakeup` | on |
| The USB controller, the touchscreen, Wi-Fi | no wake-up source (§16.4) | — |

  - The modem's channel is `/sys/bus/rpmsg/devices/4080000.remoteproc:glink-edge.IPCRTR.-1.-1/power/wakeup`; the new package `phone-qcom-wake` (`60-phone-qcom-wake.rules`, which the 6T's machine file brings in) writes `enabled` when the channel appears. Once the channel can wake the phone, GLINK reports a wake-up event when a message from the modem arrives (read in `qcom_glink_native.c`, **inferred**); once awake the Shell lights the screen for the call or the new SMS. The price: each of the modem's QMI indications (signal, registration) wakes the phone too; how often in a night is to be measured (§14.19 item 2).
  - At a wake the Shell logs `sleep: woke after …s (irq N; wake-up sources …)`: besides `pm_wakeup_irq`, from 2026-11-26 it names the wake-up sources whose `wakeup_count` rose while it was suspended (`/sys/class/wakeup/wakeup*/`), which tells the alarm, the modem's channel and the charger apart (`hal/pm`'s `TestWokenByNamesTheWakeUpSources`, which the old code fails; **not tried on a phone**).
- **The display did not come back after a suspend** (§16.5, 2026-11-22): that was on Nura, before Kario's whole firmware; how the panel was turned off and on was not recorded (**inferred**: the kernel did it itself at suspend and resume, and the DSI did not come up at the resume); one more mode set by hand (`fb0/blank=0`) brought it back. Kario's Shell always turns the panel off before it sleeps (the screen has been off 30 seconds by then), and when the screen comes on after a wake the renderer does a full mode set (`phone-paint`'s `power(on)`), which is the step done by hand that time; on 2026-11-24 the first whole-phone image lit its screen after a power-key wake (§16.9), seen that once only. One way it can still go wrong: the panel powers on, but no page flip completes within 500 ms (the renderer's `but no page flip completed in 500 ms after the panel came on`, what a command-mode DSI panel that did not come up looks like). Before, the Shell only logged that and lit the backlight over a black panel; from 2026-11-26 it turns the panel off and on once more (once only, the backlight waiting for the second time; logged `panel: on …; turning it off and on again`; `TestPanelOnWithAWarningOffAndOnAgain`, which the old code fails; **not tried on a phone**).
- **About 10 seconds from the power key to a lit screen** (§16.9): that time ran from the press to USB and SSH coming back, not to the lit screen, and the phone had gone to sleep by `echo mem` in the console, not by the Shell. USB coming back means: the controller powered up again, the computer enumerating it again (a second or two), the computer's DHCP again (NetworkManager often takes several seconds), SSH reconnecting. The screen means: the kernel resuming each device (UFS, DSI, the GPU …; `pm_print_times` writes how long each took), the renderer reading the power key (the log's `power key: from the renderer`), the Shell turning the panel on (`panel: on in N ms`; the panel took 188 ms when a charger lit the screen in report 007), then the backlight. Only one thing in the kernel's resume looks like it could make 10 seconds: DRM's wait for `flip_done` times out after exactly 10 seconds (`flip_done timed out`, the display chain problem of §16.5). So measure first (§14.19 item 4), and change nothing before that. What can be shorter: a static address on the computer's USB network interface (`172.16.42.2/24`, §7) saves the DHCP, for testing only; a slow device in the kernel shows in `pm_print_times`; if it is `flip_done`'s 10 seconds, the display chain did not come up, and that is what to fix, not the wait.

### 16.13 The kernel log on the screen during boot (2026-11-26, report 007)

- **What was seen** (seen, report 007's photos and `fajita-boot-1.log`): after the bootloader's picture and until the Shell showed, the screen scrolled the kernel's and systemd's output, with a blinking cursor in the top left. A user's phone should not do that.
- **Cause**: `console=tty0` on the command line (§4), and the kernel's fbcon taking over any frame buffer at once: at 0.214 s the simplefb the bootloader left (`Console: switching to colour frame buffer device 135x146`), at 5.99 s msm's `msmdrmfb`; everything the kernel and systemd wrote to tty0 after that was painted on the panel.
- **Change** (**not tried on a phone**):
  - The default command line no longer has `console=tty0`; it has `vt.global_cursor_default=0` (no cursor) instead. The machine file has `PHONE_BOOT_LOG ??= "0"`; `KASEXTRA=yocto/kas/boot-log.yml` sets it to 1, and the command line has the old `console=tty0` (§4). The boot image and the A/B layout's `abboot` share the switch. The serial `console=ttyMSM0`, pstore and the journal are unchanged and `quiet` is not added: not a line of the log is lost, it is only not painted on the screen.
  - The kernel gets `CONFIG_FRAMEBUFFER_CONSOLE_DEFERRED_TAKEOVER=y` (`phone-console.cfg`, every kernel using `phone-kernel.inc`): without `console=tty0`, tty1 is still a VT and systemd's vconsole-setup writes escape sequences to it, and without this option fbcon takes over all the same and paints the screen black; with it, fbcon waits until there is text to draw, and as nothing writes text to tty1 (getty@tty1 and phone-display exclude each other, the renderer uses DRM directly) it never takes over. A kernel configuration with fbcon but without the option fails the build (`do_phone_console_kconfig`).
  - Built on 2026-11-26 (`linux-sdm845`, `phone-fw`, `phone-qcom`, not flashed): the kernel's `.config` has `CONFIG_FRAMEBUFFER_CONSOLE_DEFERRED_TAKEOVER=y`, and `boot-oneplus-fajita.img`'s command line reads `root=PARTLABEL=userdata console=ttyMSM0,115200 phone.gui=1 vt.global_cursor_default=0`; `yocto/boot-console-test.py` checks both layouts' command lines with `PHONE_BOOT_LOG` off and on, on the build machine.
  - Other machines: QEMU's command line is put together by runqemu from `SERIAL_CONSOLES` (`console=ttyAMA0 console=hvc0`) and never had `console=tty0`; the `kario-qcom` machine file writes no command line. Their kernel (linux-yocto, which uses `phone-kernel.inc` too) gets `DEFERRED_TAKEOVER` as well, so on virtio-gpu there is no longer fbcon's empty console and cursor before the renderer starts either.
- **Measurement** (`fajita-boot-1.log`, kernel time): simplefb 0.21 s; msm takes the display over at 5.75 s (`switching to colour dummy device`); the initramfs switches to `/sbin/init` at 7.12 s; `Reached target Basic System` at about 11 s (that line has only whole seconds); `phone-display` starts only at 15.7 s (`Startup finished … = 15.659s`); `PHONE-GUI-READY` at about 17.3 s (the GPU firmware loads at 17.21 s, the first frame comes after it). With the change the bootloader's picture stays until 5.75 s, and **from 5.75 s to the first frame, about 11.5 s, the screen shows nothing of Kario's**; whether the panel is black, frozen on its last picture or garbage during that time depends on whether the panel driver resets the panel when it probes, and only the phone can show it (§14.2 "the boot screen").
- **Most of the 11.5 dark seconds are userspace ordering**: `phone-display.service` is ordered after `phone-telephonyd.service`, and telephonyd waits for the baseband chain (`phone-qcom-uim` finishes only at 15:35:16, and telephonyd and the Shell start in the same second). From basic.target to the Shell is 5 s.
- **Whether to draw a static logo from phone-initramfs**: not now. It could cover 6.75 s (the initramfs starting) to the first frame, about 10.5 s; but:
  - the initramfs has only busybox, so it needs another small statically linked program. That program cannot be a DRM master that keeps the card open (when it exits, its frame buffer is removed, the CRTC turns off and the screen is dark again; to stay, it would have to live across `switch_root` until the renderer takes over, as plymouth does); the way that works is to write the picture into `msmdrmfb` and make the kernel's fbdev do one modeset with `FBIOPUT_VSCREENINFO`, leaving the picture on fbdev's frame buffer until the renderer's first modeset replaces it.
  - That modeset is the one fbcon used to do at 5.99 s; the 6T's command-mode panel has reported its DSI PLL failing to lock at boot (`DSI PLL(0) lock failed`, §16.5, §16.9), and one more moment of turning the panel on is one more risk; in boot-log mode it would also fight fbcon for the screen.
  - The logo would have to line up with the first frame of the Shell's boot animation, or the screen jumps at 17 s.
  - Moving the ordering is worth more first: with `phone-display` not waiting for telephonyd (the Shell has to cope with telephonyd arriving late or restarting anyway), the boot animation could show about 5 s earlier, leaving about 5 s of dark screen, and then a logo can be judged again. Neither is done; they are recorded here.

### 16.14 Powered off with the cable in, the whole system came up (2026-11-27, report 008)

- **What was seen** (seen, report 008's journal): with the cable in, Power off was tapped in the power menu: about 4 seconds after the menu opened and the power key was released, the last boot went through `systemd-reboot.service` (`Reached target System Reboot`), not a power-off, and the whole system came up (the Shell and the screen), not charger mode. The power menu was opened again and this time `systemd-poweroff.service` ran; the charger powered the phone on with two modes on the command line, `androidboot.mode=charger` first and `androidboot.mode=normal` after it, the generator took the last one, the whole system came up again, and the charger's screen never showed. What the user saw: "powering off takes very long" and "no charging screen".
- **The command line**: on the charger's boot ABL writes `androidboot.mode=charger` as before (§16.9 saw it alone), this time followed by an `androidboot.mode=normal`; why there is sometimes one more is **not known** (ABL's source is not at hand). **Changed**: the generator boots charger mode whenever the command line has `androidboot.mode=charger`, whatever other `androidboot.mode=` come before or after it; `systemd.unit=` still wins ([28](28-battery.md) §10; `yocto/charger-generator-test.py` has report 008's kind of command line, on which the old generator fails; **not tried on a phone**).
- **A power-off turned into a reboot**: nothing in Kario turns a power-off into a reboot (the Power off entry only calls `systemctl poweroff`); the Shell's `power: …` line was only written to `/run`, so which entry was chosen cannot be seen. The inference (**not verified**) is that the finger landed on Restart, right under Power off: on the 6T a row of the menu is about 5 mm high. **Changed**: Power off or Restart tapped on the screen is asked again, and the line goes to the journal ([28](28-battery.md) §7, §10). The next round takes the evidence by step 8 of §14.10 "charger mode"; if it then logs `power: poweroff` and the last boot still went through `systemd-reboot`, it was no mistaken tap, and the power-off path itself is next to look at.
- None of these changes are in the OnePlus 6T's board files (`recipes-bsp`, the fajita machine and kernel files and `phone-fajita*.yml` are untouched): the generator is phone-fw's, the confirmation on a tap the Shell's.
