# telephonyd · UI

## telephonyd

> Status: **prototype ✓** (`telephonyd`, C++23). Two backends: a simulated modem (dev machine, QEMU) and ModemManager (tested against a mock ModemManager, **not yet run against a real baseband**, tracked with R16). Implementation: [19](19-core-apps.md) §2.

An in-house telephony daemon in **C++23**, responsible for calls, sending and receiving SMS (stored by phone-smsd, [32](32-messaging.md)) and network status.

```
App ──phone.Ui req (tel.* / sms.*)──► Shell broker ─────────────JSON lines─────────────► phone-telephonyd ──► Modem interface
                                            ▲                                                    │   ├─ SimModem (dev machine, QEMU)
System incoming-call screen · status-bar signal · SMS notifications ◄── event subscription ──────┘   └─ MmModem ──D-Bus──► ModemManager
```

Shell side (`shell/telephony.go`, `broker_phone.go`):
- Keeps one subscription connection open and reconnects automatically after telephonyd restarts; without telephonyd the status bar shows 「无服务」 (No service) and everything else works as usual.
- A SIM incoming call is always taken over full screen by the system, no matter what is in the foreground; once answered it is handed to the Phone app; missed calls go to the notification center.
- SMS do not come through this subscription: phone-smsd takes them from telephonyd and stores them, the Shell subscribes to smsd, received messages are notified under the name of the 「短信」 (Messages) app, and the app also receives `sms` events while it is running (`shell/messaging.go`, [32](32-messaging.md)).
- When an app without the `phone` permission requests to dial, the system first shows a dialog asking the user to confirm; the call screen always belongs to the Phone app.
- For messages that could not be sent, the Messages app marks them 「未发出」 (Not sent) and they can be resent; the system also posts a notification under the Messages app's name.
- When the SIM requires a PIN (or a PUK plus a new PIN), the system draws a screen of the same kind as the payment confirmation to ask for the code; the digits go only through the Shell to telephonyd and the SIM, and apps never get them; a wrong entry shows how many attempts remain, and the Back key lets you enter it later (it reappears when the SIM state changes or someone dials); the status bar and the idle screen show 「SIM 已锁」 (SIM locked) and 「无 SIM 卡」 (No SIM card).
- Airplane mode, mobile data, data roaming and national roaming are the Shell's to decide (`shell/airplane.go`, [11](11-platform-architecture.md) §16): each time the Shell connects to telephonyd it brings telephonyd's switches in line with the system settings; while mobile data is on but a roaming switch keeps the link down (`data_state` `roaming`), the firewall closes `data_ifaces` as for mobile data off, and a notification in Settings' name, 「漫游时没有移动数据」 (No mobile data while roaming), says which network the phone is on and which switch to turn on; opening it shows Settings › Mobile network, and it goes when the roaming ends, the switch goes on or mobile data goes off; in airplane mode the Shell itself refuses a non-emergency number (「飞行模式已打开，关闭后才能打电话」, Airplane mode is on; turn it off to call). Settings' APN pages use the `apn.list` and `apn.set` capabilities (system apps only), which the Shell passes to telephonyd as they are (`shell/apn.go`); the log has the operations and ids only.
- The cellular interface's addressing (`shell/cellnet.go`): on the device (root, with systemd-networkd) the Shell writes a runtime networkd file for the interface from `data_ip`, `/run/systemd/network/10-kario-cell-<interface>.network`, and after `networkctl reload` has it reconfigured: static IPv4 and IPv6 addresses as they are, the gateway as a `[Route]` (`GatewayOnLink`), and for IPv4 without a gateway (point to point) a default route over the interface itself; `dhcp` IPv4 through networkd's DHCP; IPv6 always listens to router advertisements (SLAAC), and with only a link-local address given its interface identifier becomes `Token=static:`; the DNS servers go in, and networkd hands them to systemd-resolved for that interface; the MTU as given (not below 1280 with IPv6); the routes' metric is 2048, after iwd's Wi-Fi routes and networkd's DHCP default (1024), so Wi-Fi and a wired link come first while connected. Every value written is one parsed and written back in its own form and the interface's name is checked, so nothing telephonyd passes on reaches the file as text; PPP and a link without addresses yet are not configured. When the link goes (mobile data off, international roaming without data roaming, the bearer down) the file becomes `Unmanaged=yes` (which keeps a catch-all configuration such as QEMU's `ip=dhcp` off it), and the interface's addresses are flushed and the interface set down (networkd leaves an interface it does not manage as it was); a restarted Shell takes over the files the previous one left in `/run`; a Shell on the simulated modem (the selftest's, telephonyd reporting the `backend` `sim`) takes over only the simulated `simwwan0`'s and leaves what the phone's own Shell wrote for the real modem's interface alone (on the OnePlus 6T the selftest's Shell had taken `qmapmux0.0` and the default route down, [39](39-oneplus-6t.md) §16.10). A developer machine (not root, no networkd) configures nothing. The generated files and the teardown are unit-tested; the emulator case (a veth standing in for `simwwan0`) ✓ with both images; **not verified on hardware**. The MMS bearer (`mms_link`, with mobile data on) gets a file of its own with the same prefix: only its IPv4 address (a static one: the rule below matches the address; one that is not static is not configured, with a log line), IPv6 off, `DNSDefaultRoute=no`, no DNS servers (none reach systemd-resolved); its route goes into a table of its own, 2049, and a policy rule (`From=<address>/32`, priority 29999, before the VPN's 30000 and 30001, so MMS leaves over its access point with a tunnel up too) sends what leaves from that address to that table: only phone-smsd's connections from that address use the MMS bearer, and the main table and the default route stay as they are; once the bearer is let go its file turns `Unmanaged=yes` the same way. On the data bearer's own interface it is not configured apart. The generated file is unit-tested, **not tried on a phone**; whether the VPN's lockdown (traffic only through the tunnel) blocks it is **not verified**.
- 「设置 › SIM 卡锁」 (Settings › SIM lock) turns the PIN lock on or off and changes the PIN: the Settings app only makes the request (`sim_pin_lock`, `sim_pin_change` of `settings.set`); the PIN is entered on the same kind of system screen (for a change: the current PIN, the new PIN, and the new PIN again) and is handed only to telephonyd and the SIM; the Settings app receives its reply only once there is a result (succeeded, wrong PIN, canceled by the user). After three wrong entries the SIM locks itself, and the system switches to the unlock screen that asks for the PUK.

**ModemManager backend** (`src/mm.cpp`): implements the same `Modem` interface and calls `org.freedesktop.ModemManager1` on the system bus via sd-bus (the interface as of 1.20), adding only libsystemd as a dependency. Yocto builds compile it in unconditionally (a missing libsystemd fails the build rather than silently leaving only the simulated modem); on a dev machine without libsystemd it is not compiled.
- **Tracking**: ModemManager starting and exiting (`NameOwnerChanged`), modems appearing and being removed (ObjectManager); the first modem reported is used. If the modem is disabled, telephonyd enables it (ModemManager does not enable it by itself). When the modem or ModemManager disappears, calls in progress end as 「断开」 (Disconnected) and the status becomes unregistered.
- **Status**: taken from the Modem and Modem3gpp properties — home, roaming and SMS-only all count as registered; operator name; the access technology is grouped from AccessTechnologies into 2G–5G; the signal percentage is converted to 0–4 bars; own phone number; the IMEI from the Modem's `EquipmentIdentifier`. Any change emits a `status` event.
- **Calls**: `Voice.CreateCall` plus `Call.Start` to dial out, `Accept` to answer, `Hangup` to hang up. ModemManager has no single-call hold, so both hold and resume use `HoldAndAccept`, which for a single call does exactly hold and resume; answering a second incoming call during a call (call waiting) also uses it; dialling a second call during a call first calls `HoldAndAccept` (with no waiting or held call it only holds the connected one) and `CreateCall` once that is done, tested against the mock ModemManager in `mm_test.py`'s `outgoing_call` (`HoldAndAccept` before `CreateCall`, no third call, swapping back to the first), **not run on a real phone**. `Call.StateChanged` is mapped to telephonyd states; the end reason is classified, based on who hung up, whether the call was ever connected and the cause given by the network, as hung up / rejected / busy / missed / failed / remote hung up. Ended calls are deleted from ModemManager. A call that fails is never left as it was: the `call` event ends it with reason `failed` and an `error` saying why in ModemManager's words, and telephonyd logs `call cN failed: <why>` (the Shell and the Phone app show "Call failed: <why>"). That covers a refused `CreateCall`, `Start` or `Accept`, an `Accept` unanswered after 30 s, a `HoldAndAccept` refused while answering or dialling, and a call the network ends with an error or without audio. ModemManager ends a call it could not start or answer before replying, so that end waits up to 2 s for the reply, and an answered call that fails is `failed`, not `missed` (`missed` in the log). A `Hangup` the modem refuses deletes the call (which hangs it up in ModemManager): a call left behind would refuse every later dial. `dial` without a modem says `ModemManager is not running` or `ModemManager has no modem yet`. Refused dials and answers, and each call's states, go into the journal without the number. All of this is tested against the mock ModemManager in `mm_test.py` (`answer_refused`, `answer_refused_still_ringing`, `dial_refused`, `call_audio_failed`, `hangup_refused`, `modemmanager_late`), **not run on a real phone**. Mute belongs to the audio path (audio service, R29); the backend only records the state.
- **SIM card**: while the card is locked, ModemManager stays in LOCKED, `UnlockRequired` says whether a PIN or PUK is needed and `UnlockRetries` gives the remaining attempts; `sim.unlock` calls `SendPin` / `SendPuk` on the Sim object; after unlocking, the modem returns to the disabled state and telephonyd then enables it. While the card is locked, dialing and sending SMS are rejected outright. Turning the PIN lock on or off calls `EnablePin`, changing it calls `ChangePin`; whether the PIN lock is on is read from `EnabledFacilityLocks` on the 3GPP interface (bit 0 is the SIM).
- **SMS**: `Messaging.Create` (asking for a delivery report) plus `Sms.Send` to send; first reported as 「发送中」, and after `Send` returns as 「已发送」 or 「发送失败」; then, when its `DeliveryState` changes, as 「已送达」 or 「发送失败」 (nothing while the network still retries), and it is deleted from the modem; at most 64 wait for a report. A received message counts as arrived only once all its parts have been received (state RECEIVED); its id is computed from the number, the SMS center's timestamp and the text (the same after a restart); it stays on the modem and is deleted only once phone-smsd acknowledged it (`sms.ack`), so the few dozen slots on the SIM never fill up and a restart of either side loses nothing; messages already on the modem or SIM before telephonyd started are handed over the same way. A delivery report that matches no sent message is deleted. The timestamp is the SMS center's timestamp.
- **Cell broadcast**: ModemManager 1.24's `Modem.CellBroadcast`: channels 4352–4359 and 4370–4400 are set, `Added` and the `Cbm` objects (complete ones only) become `cb` events, and once smsd acknowledged, `Delete` ([32](32-messaging.md) §7); tested against the mock ModemManager (the `cell_broadcast` case), **not verified on hardware**.
- **USSD**: `Initiate`, `Respond` and `Cancel` of `Modem3gpp.Ussd` on the modem object. After `Initiate` / `Respond` return the network's answer, the session's `State` is read once more (its PropertiesChanged may arrive after the answer): 3 (waiting for the user's reply) is reported as `input`, anything else as `done`. USSD the network sends by itself arrives as changes of the `NetworkNotification` and `NetworkRequest` properties and is reported as `ussd` events `notify` and `input`; when `State` returns to idle while waiting for a reply (the network ended the session), or the modem or ModemManager disappears, `done` is reported. Without a Ussd interface on the modem, with the SIM locked or when not registered, requests are rejected outright.
- **Radio and mobile data**: turning the radio off calls `Modem.Enable(false)` (with which ModemManager ends the calls and the data bearers), then `SetPowerState` to low power (2); turning it on calls `SetPowerState` to on (3), then enables the modem as usual. While the radio is off telephonyd no longer enables the modem by itself. An emergency number dialed with the radio off turns it on that way and calls `CreateCall` once the modem is enabled. With mobile data on, the modem registered, an APN from the Service, the roaming switches allowing it and no bearer connected, `Modem.Simple.Connect` connects with `apn`, `ip-type` (`MMBearerIpFamily`: IPv4 1, IPv6 2, IPv4v6 4; left out for the network's default, empty APN, so ModemManager chooses), `apn-type` (internet, 2) and `allow-roaming` (true for a bearer connected while roaming, which telephonyd connects only where the switches allow; for one connected at home true only with both roaming switches on, otherwise ModemManager drops it itself as roaming begins, and telephonyd connects again by its rule), plus `allowed-auth` (`MMBearerAllowedAuth`: PAP 2, CHAP 4, both 6), `user` and `password` when the authentication is not `none`; after a failure it tries again when the registration, a switch or the APN changes. Turning it off, roaming where a switch says no, and a connected bearer that is not the link wanted call `Simple.Disconnect` of that data bearer alone (its path, not `/`, which would take the IMS bearers down with it), after which it connects with the new APN: a bearer telephonyd connected itself (the path `Simple.Connect` answered) is compared with the APN it connected with (APN, IP type, authentication, user and password; not the name), any other (one connected before telephonyd restarted, say) by the `apn`, `ip-type`, `allowed-auth` and `user` of its `Properties`; while the bearer is not the link wanted `data_state` is `idle`. Nothing connects before the SIM (its APN) and the bearers already there have been read, and before the SIM is read no bearer is disconnected for another APN: a bearer up when telephonyd restarts stays, rather than a second one connecting first with the network's default APN. The SIM's SPN and GID1 come from the Sim's `OperatorName` and `Gid1` (bytes, written in hex), the network's MNC from `OperatorCode`; another SIM, or the modem going away, forgets the APN until the Service gives one again. `data_ip` comes from the connected bearer's `Interface`, `Ip4Config` and `Ip6Config` (`method` 1 PPP, 2 static, 3 DHCP; `address`, `prefix`, `gateway`, `dns1`–`dns3`, `mtu`). `data_ifaces` are the modem's network ports (the `Ports` of type net) and the data and MMS bearers' `Interface`. The cases against the simulated ModemManager `mobile_data` (the database's `cmnet`, the bearer's addresses; turning data off disconnects that bearer alone), `apn_change` (a changed APN disconnects and connects again, `reset`; so does only another IP type or authentication added, not a new name alone), `data_roaming` (no link on international roaming, connected with `allow-roaming` once data roaming is on, national roaming as usual, disconnected with national roaming off, connected again once it is on) and `airplane_mode` pass (`make mm-selftest`); another IP type while roaming (Android's `roaming_protocol`) is **not implemented**; bearers and addresses on live networks are **not verified on hardware**.
- **Bearers other programs bring up**: telephonyd manages only the bearers it connected (the paths `Simple.Connect` answered) and internet bearers. Other bearers are told apart by `mm::bearer_role`: a `BearerType` of default attach (2) is the LTE attach bearer; with an `apn-type` in its `Properties`, that says (IMS 4 or emergency 64 is IMS, internet 2 data, MMS 8 MMS, anything else is left alone); without one its APN does (ModemManager lists `apn-type` only when the request gave one, and 81voltd brings up its IMS bearers with an APN, one IP family and a profile id only): the internet APN is data, the SIM's IMS and emergency APNs and the well-known `ims` and `sos` (GSMA IR.92, 3GPP TS 23.003) are IMS, the MMS APN is MMS; failing those, one with a profile id (`profile-id`, which telephonyd never gives; 81voltd passes the one the modem asked with, its APN possibly empty) is left alone, and the rest is data (as before: a data bearer on another APN is the one to replace). Only data bearers count as "mobile data connected" and are disconnected; IMS, emergency and attach bearers do not count as data, are never disconnected, and their interfaces stay out of `data_ifaces` (the firewall does not close them with mobile data off). The case `ims_bearer_left_alone`: with an IMS bearer brought up as 81voltd does and one marked IMS connected, the data bearer connects as usual and `data_ip` is its, turning mobile data off disconnects the data bearer alone while the IMS bearers stay connected, turning it on again connects a data bearer beside them, and a telephonyd restart leaves them alone. Airplane mode (`Modem.Enable(false)`) still has ModemManager take every bearer down. 81voltd is not in the image yet, **not tried on a phone** ([39](39-oneplus-6t.md) §11.1).
- **The LTE initial attach APN**: when the APN plan has an attach APN (`ia`), telephonyd first reads `Modem3gpp`'s `InitialEpsBearerSettings` (what the modem asks for when it attaches) and the `Properties` of `InitialEpsBearer` (the bearer the network attached with): if either is that APN already (the APN in any case, also with the `.mncNNN.mccNNN.gprs` a network appends; the IP type, authentication and user the same where they say) nothing changes, otherwise it calls `Modem3gpp.SetInitialEpsBearerSettings` (`apn`, `ip-type`, plus `allowed-auth`, `user` and `password` when the authentication is not `none`). ModemManager applies it by taking the radio down and up again (the phone attaches anew and the bearers drop), so it is not set during a call (an emergency call waiting for the radio included) but after it, nor with the radio off or the modem not enabled; while it is being set the data bearer waits for it rather than connecting once before; an APN is set once (not tried again after a failure, until the APN plan changes). The cases `attach_apn` (`cmnet` set once at start-up, the data bearer connected only after it), `unacknowledged_sms_survives_a_restart` (the settings already the same: not set again after a restart) and `apn_change` (the changed cmnet is the attach APN too: the attach first, then the data bearer replaced; a new name alone changes neither) pass. **Not tried on a phone** on live networks: whether the modem keeps the settings (if it does not, telephonyd sets them again at every start and the radio restarts with them) is to be checked on the 6T ([39](39-oneplus-6t.md) §14.6).
- **SIM phone book**: ModemManager has only an enumeration of storage locations, no interface that reads the phone book, so the backend sends AT commands (3GPP TS 27.007) through `Modem.Command`: it notes the character set from `AT+CSCS?`, switches to `UCS2` (names in any script come through intact), selects the SIM's phone book with `AT+CPBS="SM"`, asks for the record range with `AT+CPBR=?`, reads it with `AT+CPBR=<first>,<last>`, and finally sets the character set back. For modems that send the number in UCS2 too, the decoded form is used when it is a number; numbers of type 145 get their `+`; a modem reporting not found for an empty book counts as one with no contacts. ModemManager takes `Modem.Command` only when run with `--debug`, otherwise the answer is `the modem takes no AT commands (ModemManager needs --debug)`; the image does not ship ModemManager yet (it comes with the hardware model's recipes, which must then turn on `--debug`), **not tried on a phone**. A Qualcomm modem could also read EF_ADN through QMI's UIM service, **not implemented**.
- **Not held up by the modem**: all D-Bus requests are asynchronous, so the event loop never blocks on them; requests that wait on the network (sending SMS, answering, enabling, USSD) time out after 120 seconds; if the system bus disconnects, telephonyd exits and is restarted by systemd.
- **Tests**: `make mm-selftest` starts, in a Debian container, a private D-Bus and a mock ModemManager written in Python (`test/mock_mm.py`, which exports the same objects, properties and signals, plus a control interface that plays the role of the network), and runs 39 cases through telephonyd's socket: enable and register, the LTE attach APN (set once, the data bearer waiting for it), an old SMS on the SIM deleted only once acknowledged, IMEI, outgoing call, busy, incoming call answered / rejected / missed, hold and resume, mute, keypad tones, the SIM phone book (an error without `--debug`, reading it, the character set set back, an empty book), call waiting, sending SMS with its delivery report, a message without a report kept waiting, network refusing to send, multipart SMS delivered only once, an unacknowledged SMS kept across a telephonyd restart (the bearer up staying too, the attach APN not set again), cell broadcasts, signal and access-technology changes, USSD queries (answered at once, menu and reply, a notification and a question sent by the network, cancel, the network ending the session), SIM PIN (wrong, correct), PUK, changing the PIN and turning off the PIN lock in Settings (wrong, changed), mobile data (the database's APN, the bearer's addresses), IMS bearers neither counted as data nor disconnected, changing the APN (the attach APN with it), data roaming, the MMS bearer (a second one connected, shared by a second transfer, let go, none with mobile data off, the data link when the MMS APN is the internet one), airplane mode, the modem disappearing during a call and coming back, ModemManager restarting, invalid parameters, and last the backend contract (no status telephonyd reported in all the cases before breaks `contract_problems`, [24](24-sku-framework.md) §8.8).
- **Emergency numbers**: by default 112, 110, 119, 120, 122, 911, 999, plus the SIM's (ModemManager's `Sim.EmergencyNumbers`; the simulated baseband reads `emergency_numbers` in `sim-network.json`), which `status`'s `emergency_numbers` tells the Shell; with the SIM locked emergency numbers are still dialled (3GPP TS 22.101) and other numbers are refused; on the Shell's SIM PIN screen typing an emergency number and pressing Call dials it, as on the lock screen and in airplane mode. ✓ in unit tests and against the simulated ModemManager, **not run on a real phone**; what a real baseband does without a SIM inserted is **not run on a real phone**.
- **VoLTE (IMS)**: the Snapdragon modem runs IMS itself (SIP, RTP, the voice codecs), so telephonyd needs no calls of its own for it: ModemManager dials through QMI Voice with the number alone and no call type, the modem decides between CS and IMS, and `All Call Status` reports every call, so a VoLTE call is an ordinary `Call` object; dialling, answering, hold, DTMF, hanging up and the call's audio (q6voiced, phone-audiod) work as before (from ModemManager 1.24.2's sources). The IMS bearer the modem asks for is opened by 81voltd through ModemManager, and the modem's carrier configuration is activated by `phone-qcom-pdc` for the SIM, both only in the images of boards with `ims` (the OnePlus 6T); telephonyd recognises the IMS bearer, takes it for no mobile data and never disconnects it ([39](39-oneplus-6t.md) §11.1). All **not run on a real phone** ([39](39-oneplus-6t.md) §14.6).
- **Not implemented**: the IMS registration state (a VoLTE or HD voice mark: ModemManager 1.24 has no interface for it, it would mean asking the modem's IMSA service over QMI directly), a VoLTE switch, Wi-Fi calling, video calls; integration of ModemManager with the Qualcomm userspace (QRTR, rmtfs, modem firmware) on real hardware, tracked with R16.
