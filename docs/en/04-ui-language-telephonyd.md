# telephonyd · UI

## telephonyd

> Status: **prototype ✓** (`telephonyd`, C++23). Two backends: a simulated modem (dev machine, QEMU) and ModemManager (tested against a mock ModemManager, **not yet run against a real baseband**, tracked with R16). Implementation: [19](19-core-apps.md) §2.

An in-house telephony daemon in **C++23**, responsible for calls, sending and receiving SMS (stored by phone-smsd, [32](32-messaging.md)) and network status.

```
App ──phone.Ui req (tel.* / sms.*)──► Shell broker ─────────────JSON lines─────────────► phone-telephonyd ──► Modem interface
                                            ▲                                                    │   ├─ SimModem (dev machine, QEMU)
System incoming-call screen · status-bar signal · SMS notifications ◄── event subscription ──────┘   └─ MmModem ──D-Bus──► ModemManager
```

| Item | Implementation |
|----|----|
| Language and build | C++23 (`std::expected`, `std::print`, `std::format`, designated initializers); CMake; GCC 14 on the dev machine, GCC 15 in Yocto |
| Structure | Single-threaded event loop (`poll` + timers): `loop`, `server` (Unix socket), `service` (methods and storage), `modem` (interface and simulated modem), `mm` (ModemManager backend), `json` (bundled small JSON codec) |
| Backend selection | `--modem sim` / `modemmanager`; if not given, it reads the `modem` setting of the board configuration in the `sku.json` pointed to by `--sku` ([24](24-sku-framework.md)), which is how the service starts on the device: QEMU uses the simulated modem, Snapdragon boards use ModemManager |
| Protocol | Same as the other system services: one JSON object per line, `{id, method, params}` → `{id, ok, err, result}`; after a client calls `subscribe` it also receives event lines. `ussd.initiate` and `ussd.respond` reply only once the network has answered, possibly after the replies to later requests; replies are matched by `id` |
| Methods | `status`, `calls`, `dial`, `answer`, `hangup`, `hold`, `mute`, `log`, `sms.send` (`to`, `text`, optional `id`: the id its later events carry), `sms.pending` (the events phone-smsd has not acknowledged), `sms.ack` (`keys`: acknowledge these events, telephonyd lets go of them), `sms.legacy` / `sms.legacy_drop` (hand over, then delete, the messages it used to store), `sim.unlock` (PIN, or PUK plus a new PIN), `sim.pin_lock` (`pin`, `on`: turn the PIN lock on or off), `sim.change_pin` (`pin`, `new_pin`, while the PIN lock is on), `ussd.initiate`, `ussd.respond`, `ussd.cancel` (see the USSD row); test hooks `sim.ring`, `sim.sms` (`held`: only queued for smsd, without an event, as if telephonyd died right after storing it), `sim.cb` (a cell broadcast: `channel`, `serial`, `text`), `sim.lock`, `sim.ussd` (simulated modem only) |
| Events | `call` (state changes), `sms` (received messages; an outgoing message is first reported as 「发送中」 (Sending), and once done it is reported again with the same id as 「已发送」 (Sent) or 「发送失败」 (Failed to send), and on its delivery report as 「已送达」 (Delivered); all but Sending carry a `key` and wait for smsd's acknowledgement), `cb` (a cell broadcast, with a `key`), `status` (registration, signal, SIM state and remaining attempts, `pin_lock` whether the PIN lock is on, `imei` the modem's IMEI, empty while unknown), `unlock` (whether the PIN / PUK was correct), `pin` (whether turning the PIN lock on/off or changing the PIN succeeded), `ussd` (see the USSD row) |
| USSD | `ussd.initiate` (`code`, which must match `^[*#][0-9*#]{1,30}#$`, e.g. `*100#`) sends a code, `ussd.respond` (`text`) answers the network's menu or question; both return `{state, text}`: with `state` `done` the network has ended the session and `text` is its final answer; with `input` the network waits for a reply and `text` is its prompt or menu. `ussd.cancel` ends the session and returns `{}`; without a session it does nothing. There is one session at a time. Errors: `invalid code` (the code does not match), `ussd session open` (a session is already open), `no ussd session` (no session waits for a reply), `the SIM is locked` (as for dialing); the ModemManager backend adds `no modem that can send USSD`, `not registered on the network` and the errors ModemManager returns. Event `{"event":"ussd","state":…,"text":…}`: a notification (`notify`) or a question (`input`, answered with `ussd.respond`) the network sent by itself, and the network ending a session that waited for a reply (`done`, empty `text`) |
| Radio and mobile data | `radio.set` (`on`) turns the radio on or off (off is airplane mode), `data.set` (`on`) mobile data; both return `{}`. The two switches are kept in `<state-dir>/telephony/radio.json` and applied when telephonyd starts, before the modem reaches the network, so a phone started in airplane mode never registers first. `status` gains `radio`, `data` (the two switches), `data_state` (`connected` / `idle`: on, not connected yet / `off`: the switch or the radio is off) and `data_ifaces` (the network interfaces the data link can use, which the Shell closes in its firewall while mobile data is off). With the radio off, dialing, SMS and USSD answer `the radio is off` and no calls come in; turning it off ends the calls in progress as dropped, and is refused during an emergency call with `an emergency call is in progress`. Emergency numbers (112, 110, 119, 120, 122, 911, 999, the ones the Shell's lock screen dials) do not depend on the switch: with the radio off telephonyd powers it up before dialing, the call has `emergency` true, and the Shell leaves airplane mode when it sees that. The list of emergency numbers is fixed; the lists the SIM and the network give are **not implemented** |
| Storage | The call log (200 entries) and the events phone-smsd has not acknowledged (at most 1000) are stored in `<state-dir>/telephony/telephony.json` (0600), written to a temporary file, `fsync`ed and then renamed; the messages it used to store stay in it until smsd takes them ([32](32-messaging.md) §3) |
| Permissions | Socket mode 0600; only the Shell (root) can connect; apps can only go through the broker |
| Simulated modem | Registered on 「中国移动 4G」 (China Mobile 4G), signal 3 bars; dialing → ringing (0.3 seconds) → in call (1.2 seconds); numbers ending in 000 return busy; an incoming call unanswered for 30 seconds is logged as missed; every SMS is reported delivered after 0.5 seconds and gets a reply after 0.8 seconds (10086 replies with the account balance), messages to numbers ending in 999 fail to send, and messages to numbers ending in 998 are sent but get no delivery report; `sim.cb` sends a cell broadcast; `sim.lock` makes the SIM require a PIN, and three wrong entries switch to PUK (12345678); the card's PIN is initially 1234 with the PIN lock off; wrong entries while toggling or changing the PIN also use up attempts, and after three it likewise switches to PUK; the IMEI is 860123456789014 (a test value with a Luhn check digit); USSD answers at once: `*100#` answers 「话费余额 25.80 元，本月剩余流量 3.2 GB。」 (balance 25.80 yuan, 3.2 GB of data left this month), `*101#` gives a three-line menu 「1 查话费」「2 查流量」「3 退出」 (1 balance, 2 data, 3 quit) and waits for a reply; replying 1 answers 「话费余额 25.80 元。」, 2 answers 「本月剩余流量 3.2 GB。」, 3 answers 「已退出。」 (Quit.), anything else gives the menu again after a line 「输入有误，请重新选择：」 (Invalid input, choose again:); any other code answers 「网络不支持这个代码。」 (The network does not support this code.); `sim.ussd` (`text`, `request`) simulates USSD sent by the network, which with `request` true waits for a reply, and any reply ends it with 「已收到。」 (Received.); locking the SIM ends a session that waits for a reply. The operator name, the SMS auto-replies and the USSD menus and answers are data, not code: `telephonyd/sim-network.json`, given with `--network FILE`, otherwise `share/phone/sim-network.json` under the install prefix (on the device the `phone-telephonyd` package installs it in `/usr/share/phone/`), and English defaults when there is neither (operator Kario Mobile); the C++ tests and the ModemManager mock read the same file |
| Tests | `telephonyd_test`: JSON codec, dialing state machine, busy, answer, missed, call log, SMS replies and delivery reports, the unacknowledged queue (kept across a restart, let go of once acknowledged, the same message queued once), handing over the old store, cell broadcasts, the Luhn check digit of the simulated IMEI, USSD (query, menu and reply, malformed codes, replying without a session, cancel, network-initiated, locking the SIM ending the session), conversion of ModemManager values; time is advanced with the event loop's fake clock; runs during `make build`. `make mm-selftest`: the ModemManager backend against a mock ModemManager (below) |

Shell side (`shell/telephony.go`, `broker_phone.go`):
- Keeps one subscription connection open and reconnects automatically after telephonyd restarts; without telephonyd the status bar shows 「无服务」 (No service) and everything else works as usual.
- A SIM incoming call is always taken over full screen by the system, no matter what is in the foreground; once answered it is handed to the Phone app; missed calls go to the notification center.
- SMS do not come through this subscription: phone-smsd takes them from telephonyd and stores them, the Shell subscribes to smsd, received messages are notified under the name of the 「短信」 (Messages) app, and the app also receives `sms` events while it is running (`shell/messaging.go`, [32](32-messaging.md)).
- When an app without the `phone` permission requests to dial, the system first shows a dialog asking the user to confirm; the call screen always belongs to the Phone app.
- For messages that could not be sent, the Messages app marks them 「未发出」 (Not sent) and they can be resent; the system also posts a notification under the Messages app's name.
- When the SIM requires a PIN (or a PUK plus a new PIN), the system draws a screen of the same kind as the payment confirmation to ask for the code; the digits go only through the Shell to telephonyd and the SIM, and apps never get them; a wrong entry shows how many attempts remain, and the Back key lets you enter it later (it reappears when the SIM state changes or someone dials); the status bar and the idle screen show 「SIM 已锁」 (SIM locked) and 「无 SIM 卡」 (No SIM card).
- Airplane mode and mobile data are the Shell's to decide (`shell/airplane.go`, [11](11-platform-architecture.md) §16): each time the Shell connects to telephonyd it brings telephonyd's two switches in line with the system settings; in airplane mode the Shell itself refuses a non-emergency number (「飞行模式已打开，关闭后才能打电话」, Airplane mode is on; turn it off to call).
- 「设置 › SIM 卡锁」 (Settings › SIM lock) turns the PIN lock on or off and changes the PIN: the Settings app only makes the request (`sim_pin_lock`, `sim_pin_change` of `settings.set`); the PIN is entered on the same kind of system screen (for a change: the current PIN, the new PIN, and the new PIN again) and is handed only to telephonyd and the SIM; the Settings app receives its reply only once there is a result (succeeded, wrong PIN, canceled by the user). After three wrong entries the SIM locks itself, and the system switches to the unlock screen that asks for the PUK.

**ModemManager backend** (`src/mm.cpp`): implements the same `Modem` interface and calls `org.freedesktop.ModemManager1` on the system bus via sd-bus (the interface as of 1.20), adding only libsystemd as a dependency. Yocto builds compile it in unconditionally (a missing libsystemd fails the build rather than silently leaving only the simulated modem); on a dev machine without libsystemd it is not compiled.
- **Tracking**: ModemManager starting and exiting (`NameOwnerChanged`), modems appearing and being removed (ObjectManager); the first modem reported is used. If the modem is disabled, telephonyd enables it (ModemManager does not enable it by itself). When the modem or ModemManager disappears, calls in progress end as 「断开」 (Disconnected) and the status becomes unregistered.
- **Status**: taken from the Modem and Modem3gpp properties — home, roaming and SMS-only all count as registered; operator name; the access technology is grouped from AccessTechnologies into 2G–5G; the signal percentage is converted to 0–4 bars; own phone number; the IMEI from the Modem's `EquipmentIdentifier`. Any change emits a `status` event.
- **Calls**: `Voice.CreateCall` plus `Call.Start` to dial out, `Accept` to answer, `Hangup` to hang up. ModemManager has no single-call hold, so both hold and resume use `HoldAndAccept`, which for a single call does exactly hold and resume; answering a second incoming call during a call (call waiting) also uses it. `Call.StateChanged` is mapped to telephonyd states; the end reason is classified, based on who hung up, whether the call was ever connected and the cause given by the network, as hung up / rejected / busy / missed / failed / remote hung up. Ended calls are deleted from ModemManager. Mute belongs to the audio path (audio service, R29); the backend only records the state.
- **SIM card**: while the card is locked, ModemManager stays in LOCKED, `UnlockRequired` says whether a PIN or PUK is needed and `UnlockRetries` gives the remaining attempts; `sim.unlock` calls `SendPin` / `SendPuk` on the Sim object; after unlocking, the modem returns to the disabled state and telephonyd then enables it. While the card is locked, dialing and sending SMS are rejected outright. Turning the PIN lock on or off calls `EnablePin`, changing it calls `ChangePin`; whether the PIN lock is on is read from `EnabledFacilityLocks` on the 3GPP interface (bit 0 is the SIM).
- **SMS**: `Messaging.Create` (asking for a delivery report) plus `Sms.Send` to send; first reported as 「发送中」, and after `Send` returns as 「已发送」 or 「发送失败」; then, when its `DeliveryState` changes, as 「已送达」 or 「发送失败」 (nothing while the network still retries), and it is deleted from the modem; at most 64 wait for a report. A received message counts as arrived only once all its parts have been received (state RECEIVED); its id is computed from the number, the SMS center's timestamp and the text (the same after a restart); it stays on the modem and is deleted only once phone-smsd acknowledged it (`sms.ack`), so the few dozen slots on the SIM never fill up and a restart of either side loses nothing; messages already on the modem or SIM before telephonyd started are handed over the same way. A delivery report that matches no sent message is deleted. The timestamp is the SMS center's timestamp.
- **Cell broadcast**: ModemManager 1.24's `Modem.CellBroadcast`: channels 4352–4359 and 4370–4400 are set, `Added` and the `Cbm` objects (complete ones only) become `cb` events, and once smsd acknowledged, `Delete` ([32](32-messaging.md) §7); **tests not run, not verified on hardware**.
- **USSD**: `Initiate`, `Respond` and `Cancel` of `Modem3gpp.Ussd` on the modem object. After `Initiate` / `Respond` return the network's answer, the session's `State` is read once more (its PropertiesChanged may arrive after the answer): 3 (waiting for the user's reply) is reported as `input`, anything else as `done`. USSD the network sends by itself arrives as changes of the `NetworkNotification` and `NetworkRequest` properties and is reported as `ussd` events `notify` and `input`; when `State` returns to idle while waiting for a reply (the network ended the session), or the modem or ModemManager disappears, `done` is reported. Without a Ussd interface on the modem, with the SIM locked or when not registered, requests are rejected outright.
- **Radio and mobile data**: turning the radio off calls `Modem.Enable(false)` (with which ModemManager ends the calls and the data bearers), then `SetPowerState` to low power (2); turning it on calls `SetPowerState` to on (3), then enables the modem as usual. While the radio is off telephonyd no longer enables the modem by itself. An emergency number dialed with the radio off turns it on that way and calls `CreateCall` once the modem is enabled. With mobile data on, the modem registered and no bearer connected, `Modem.Simple.Connect` connects with the network's default APN (`apn` empty); after a failure it tries again when the registration or a switch changes; turning it off calls `Simple.Disconnect` (every bearer). `data_ifaces` are the modem's network ports (the `Ports` of type net) and the `Interface` of connected bearers. The two cases against the simulated ModemManager (`mobile_data`, `airplane_mode`) pass (`make mm-selftest`); choosing an APN and configuring the cellular interface's address (DHCP or the bearer's) are **not implemented**, so on hardware mobile data does not reach the internet yet (**not verified on hardware**).
- **Not held up by the modem**: all D-Bus requests are asynchronous, so the event loop never blocks on them; requests that wait on the network (sending SMS, answering, enabling, USSD) time out after 120 seconds; if the system bus disconnects, telephonyd exits and is restarted by systemd.
- **Tests**: `make mm-selftest` starts, in a Debian container, a private D-Bus and a mock ModemManager written in Python (`test/mock_mm.py`, which exports the same objects, properties and signals, plus a control interface that plays the role of the network), and runs 31 cases through telephonyd's socket: enable and register, an old SMS on the SIM deleted only once acknowledged, IMEI, outgoing call, busy, incoming call answered / rejected / missed, hold and resume, mute, call waiting, sending SMS with its delivery report, a message without a report kept waiting, network refusing to send, multipart SMS delivered only once, an unacknowledged SMS kept across a telephonyd restart, cell broadcasts, signal and access-technology changes, USSD queries (answered at once, menu and reply, a notification and a question sent by the network, cancel, the network ending the session), SIM PIN (wrong, correct), PUK, changing the PIN and turning off the PIN lock in Settings (wrong, changed), the modem disappearing during a call and coming back, ModemManager restarting, invalid parameters.
- **Not implemented**: dialing emergency numbers without a SIM or while the SIM is locked (R30); VoLTE / IMS registration state; integration of ModemManager with the Qualcomm userspace (QRTR, rmtfs, modem firmware) on real hardware, tracked with R16.

## UI

| Surface | Technology |
|------|------|
| Open-source TUI | Go + Bubble Tea (`phone.Ui` text renderer) |
| Closed-source GUI | **Rust + Slint** (`phone.Ui` pixel renderer, prototype ✓, [06](06-gui-architecture.md) §8) |
| Store apps | Semantic apps via `phone.Ui` (default); canvas apps hand over graphics in a `canvas` node and the system draws them (exception) |

No in-house UI language: `phone.Ui` is a data structure (content + actions), not a new language; system UI uses **Slint's declarative language** + the design system. Architecture: [06-gui-architecture.md](06-gui-architecture.md); interaction grammar: [10-keyboard-interaction-model.md](10-keyboard-interaction-model.md).
