# Platform architecture: a keyboard-first system at super-app level

> Status: architecture design + code prototype. Parts already implemented in the prototype ([kario repository](../../), described in [13](13-prototype.md)) are marked **prototype ✓**; the rest is design, **not implemented**.
> For the item-by-item capability list see [12-super-app-capabilities.md](12-super-app-capabilities.md); for the interaction grammar see [10](10-keyboard-interaction-model.md).

## 0. Vision and boundaries

**Vision**: a keyboard-first, text-first ("TUI-native") mobile platform. The platform layer provides all the system capabilities a super app (at the level of WeChat or Alipay) needs — messaging, voice and video calls, push, code scanning, trusted payment, device attestation, hosting mini-programs — so that such vendors can use our SDK to release `phone.Ui` versions of their apps.

**Boundaries (to be honest)**: a complete set of capabilities is a **necessary condition for vendors to release, not a sufficient one**. Whether vendors invest depends on the user base, financial-grade security certification and business terms. The architecture can do two things: bring the vendors' **technical porting cost down to a minimum**, and **design the certification path in from the start** (TEE, Chinese national cryptography, biometric authentication standards). In the near term the positioning is still a second phone / focus phone (D1); the platform vision is D4 (see [09](09-ui-feasibility-review.md) §8).

## 1. Terminology: what a "TUI app" is

**TUI app = an app written with `phone.Ui`**: the app only declares its content and what each element can do, and the system renders it. The same app binary runs in:

| Runtime environment | Renderer | Media (video / camera / QR codes) |
|----------|--------|------------------------------|
| Dev machine terminal, SSH, serial console | Text renderer | Half-block character pixels (two pixels per cell, top and bottom, true color); low resolution but real |
| Production device | Pixel renderer (GPU) | Full resolution; video goes straight to a DRM hardware plane |

So "video calls in a TUI system" holds: the video is a **media surface composited by the system**, not characters drawn by the app. The prototype already runs video calls in a terminal (see [13](13-prototype.md)).

## 2. Architecture principles

1. **Apps describe, the system renders.** Focus, keys, menus, the back stack and system dialogs all belong to the Shell; every app can naturally be operated completely with keys.
2. **Sensitive interactions always go through system UI.** Permissions, payment confirmation, code scanning and incoming calls are drawn by the system; the app gets the result, never the input or the picture.
3. **Identity is determined by the connection.** An app's identity = the connection the Shell hands it when launching it, which cannot be forged; the broker attaches the caller's identity to every service call.
4. **Four separate planes**: the UI plane, the capability plane, the media plane and the trust plane (§4).
5. **Least capability.** Code scanning gives only the result, not the picture; calls give only stream handles, not pixels; signing gives only proofs, not private keys.
6. **Degradable.** The same app still works under the text renderer, only with lower media resolution.
7. **A stable narrow waist.** `phone.Ui` and the capability catalog are versioned independently (§11), following the major / minor rules of 56 (internal document).
8. **No big all-encompassing HAL.** Only our own BOM is supported (the principle from 07 is unchanged).

## 4. The four planes

| Plane | Transport (prototype → production) | Content | Status |
|------|---------------------|------|------|
| UI | JSON lines over the socketpair the Shell hands the app (fd 3) → binary serialization + incremental updates | Screen / Node / Action; push / replace / update / pop | Prototype ✓ |
| Capability | req / res on the same connection, relayed through the Shell's broker | Capability name + parameters; the broker checks the manifest declarations and runtime grants and attaches the caller's identity | Prototype ✓ |
| Media | RGB frames over a Unix socket → dmabuf handed to a DRM plane or a GPU texture | Camera, the remote side of a call, the code-scanning preview; **subscribed only for surfaces visible on screen** | Prototype ✓ (synthetic picture source) |
| Trust | keystored process → OP-TEE trusted application + secure storage + trusted input | Device certificate chain, app keys, PIN, device attestation, signatures | Prototype ✓ (pure software emulation) |

Why media is a plane of its own: the pixel volume is several orders of magnitude larger than the UI tree, and for privacy it should not pass through the app. The app puts a `media` node with a stream handle into its UI; frames go directly from mediad to the compositor. In the prototype the app process never sees a single frame from start to finish.

## 5. Processes and identity

- One process per app, launched by the Shell, **inheriting only one fd** (the UI + capability connection). The sockets of the system services are 0600, and in production they also get separate uids, so apps cannot bypass the broker and connect directly to mediad / keystored.
- App identity = the manifest id in the signed package (signed by the store in production) → bound to this connection → the broker attaches the app id when it calls services. keystored isolates keys by app id, so the wallet cannot get the chat app's keys.
- **Sandbox**: a separate uid per app, mount / pid / ipc / uts namespaces, Landlock, seccomp, rlimit, cgroup, and network access switchable per app (**prototype ✓**, [17](17-app-sandbox.md)). On a dev machine where the Shell is not root, only the layers that need no root are in place.
- **System helpers**: code that parses data from outside and needs no privilege stays out of the Shell. File sharing with a computer (HTTP, WebDAV, MTP) runs in `phone-usbshared`, the way Android's MTP runs in the MediaProvider process and not in system_server: the Shell starts it once the computer is trusted; it has its own uid and an empty network namespace, Landlock lets it run only its own program, and seccomp forbids exec, new sockets and file operations by path; the listening socket and the files are opened by the Shell and handed over as fds (§14), and it ends when the cable is pulled or the Shell exits ([27](27-usb-typec.md) §3.2, development machine and emulator ✓).
- **Process ownership**: apps, renderers and the services the Shell starts itself all have a parent-death signal (`SIGKILL`) set, so when the Shell is killed they end with it, frozen ones included; on the device, when systemd stops the Shell it also cleans up its whole cgroup. Services the Shell starts itself are restarted 1 second after they exit; on the device systemd takes care of this.
- **Memory**: in Yocto, Go programs are built as static PIE and do not link the shared `libstd.so`; otherwise every process would pay about 6 MB of extra private memory for its pointer tables ([15](15-web-vs-semantic-benchmark.md) §5). The Shell and all processes it starts do not use transparent huge pages (`prctl(PR_SET_THP_DISABLE)` plus `GODEBUG=disablethp=1`), and Go services started by systemd set the same variable in their unit files: with THP enabled in the kernel, a small heap that touches one corner of a 2 MB region takes up the whole huge page. The last step of the selftest prints the PSS of every process (`mem-report`).

## 7. Security and trust (payment grade)

**Chain of trust (design)**:

```
Verified boot: BootROM → bootloader → kernel + initramfs → rootfs (dm-verity, root hash signed by the update key; implemented on QEMU, [25](25-system-update.md))
   → TEE (OP-TEE)
      → device key (injected at the factory; certificate issued by the vendor root)
         → app keys (generated inside the TEE; certificate issued by the device key, stating whether user verification is required)
            → trusted confirmation (system UI collects the PIN / fingerprint, verified inside the TEE; the signature covers the displayed text)
               → server verifies level by level: vendor root → device certificate → app key certificate → signature → content check
```

Implemented parts (software emulation, interfaces designed for a TEE):
- **Factory provisioning**: the key service provides the device ID and two device public keys (Ed25519 and SM2, `csr`); the certification body's CA signs two device certificates, each with its own root (`phone-provision`, `keystore.Provision`), and they are installed back on the device together with the root public keys (`install_cert`, which first checks that the certificates really are for this device). Once they are installed, the device no longer uses the development root it generated itself at boot.
- **Two certificate chains**: the Ed25519 chain (root → device key → app keys) is the default; the national-cryptography chain is SM2 all the way from the root to the signature: the certification body's SM2 root signs the device's SM2 key, the device's SM2 key signs the certificates of SM2 app keys, and the app keys sign SM3 digests. The first line of `root.pub` is the Ed25519 root and the second line, `sm2:<public key>`, is the SM2 root; `keystore.LoadRootPub` reads both, and verification picks the chain by the `alg` in the proof. Device attestation can also use the SM2 chain (`attest.get` with `alg: "sm2"`).
- **Unlocking**: after the owner confirms in 「设置 › 解锁设备」 (Settings › Unlock device), the key service wipes all app keys (push keys included; the Shell sends `push.key_changed` to running apps so that they hand the new public key to their servers, [21](21-push.md) §4.1), and the boot state reported by device attestation changes to `unlocked`; a self-built renderer can then be swapped in (`renderer` in the state directory), with the renderer shipped in the image kept as a fallback. Locking again wipes everything once more. Payment services that see `unlocked` can refuse.

| Stage | Prototype | Still needed for production |
|------|------|-----------|
| Device keys and certificates | ✓ An Ed25519 key and an SM2 key generated at first boot; the factory signs one certificate for each | Injected at the factory, root keys in the vendor's offline HSM |
| App keys and certificates | ✓ Isolated by app id, marked `user_auth`; algorithm Ed25519 or the Chinese SM2 (`alg: "sm2"`, SM3 digest), with the algorithm written into the certificate; certificates of SM2 app keys are signed by the device's SM2 key, so the whole chain is SM2 | Generated and used inside the TEE |
| Device attestation (for risk control) | ✓ nonce against replay, verifiable by the server; optional SM2 chain | Add the measurements from verified boot |
| Trusted confirmation | ✓ A system overlay collects the PIN, which the app cannot read; the signed digest covers "prompt text + order"; a fingerprint can confirm too: `bio_key` is a fingerprint-bound key that signs only after a match and is voided when a finger is enrolled or removed ([31](31-lock-and-biometrics.md) §5) | A TEE-controlled trusted input path for keyboard and screen |
| PIN brute-force protection | ✓ The payment PIN locks after 5 failures; the lock-screen PIN is kept as a slow hash, and from 5 wrong in a row each costs a wait by the count (from 30 seconds), not reset by a restart ([31](31-lock-and-biometrics.md) §3) | Counting and time backoff inside the TEE |
| Server-side verification | ✓ `keystore.VerifyConfirm` and others | The vendor's own server implementation |
| Chinese national cryptography | ✓ SM2 signatures, SM3 digests, SM4 block cipher (`cipher.Block`; combined with GCM it gives SM4-GCM). `gm` is a thin wrapper over `github.com/emmansun/gmsm` (MIT): curve arithmetic and the block cipher are constant-time (with assembly on amd64 and arm64), and signature nonces are hedged (derived from randomness together with the private key and the message, so a broken random number generator does not leak the private key); tests check against the examples in the national standards and against the independent implementation gmssl. SM2 device certificate chain ✓; Chinese national TLS (TLCP, GB/T 38636) ✓, optional for the push channel ([21](21-push.md) §2), interoperable with `tlcp_client` from the independent implementation GmSSL 3.1. The compatibility test suite checks SM2 signatures, SM2 device attestation and the whole SM2 certificate chain | Implemented in the TEE or a secure chip |
| Biometrics | ✓ Fingerprint unlock and fingerprint payments: templates and matching are in keystored, a match yields only an authentication token (after Android's HardwareAuthToken), which the Shell passes on; the sensor is simulated ([31](31-lock-and-biometrics.md)) | In the TEE (R15); the FPC and Goodix sensors of phones have no mainline driver and need the vendor's TEE, **not implemented** |
| Integration with standards such as IFAA (led by Alipay) / Tencent SOTER, financial-grade security testing | ✗ | None of it implemented; needs hardware |

| 2. The broker checks the manifest (microphone, camera) and shows the system grant dialog the first time | System permission dialog ✓ | — |

## 9. Scan-to-pay and payment codes end to end

1. `scan.qr` → system scanning screen (the app cannot see the picture) → returns the recognized text.
2. The app shows the order → `auth.confirm{key, prompt, payload}`.
3. System trusted confirmation screen (the status bar shows 「安全模式」 (Secure mode); the app can neither overlay it nor read the input) → PIN → the keystore verifies it and signs, with the digest covering `prompt + payload`.
4. The app hands the proof to its server → the server verifies the certificate chain and checks that the signed content is exactly the text shown in the confirmation dialog, and only then charges.
5. Payment code: `keystore.sign` (a `paycode` key that does not need confirmation each time) + **secure screen**: masked by the system in screenshots, screen recordings and casting. In the prototype's automated snapshots the payment code is masked.

The prototype runs all of it (the selftest cases in [13](13-prototype.md)). Recognition is simulated: the scanning picture simply draws that text, and recognition returns it directly.

## 10. Where mini-programs and H5 fit

`phone.Ui` is **data, not code**. A super app can hand a UI tree delivered by its server (a mini-program page) straight to the Shell for rendering, which amounts to "server-driven UI", and it is keyboard-usable by nature.

| Part | Status |
|------|------|

## 11. Versioning and compatibility

- `phone.Ui`: `"phone.ui/0"` is exchanged at the handshake; minor versions only add fields (unknown fields are ignored), and major changes are deprecated one version in advance.
- Capability catalog: each capability is versioned independently (for example `media.call.start@1`), and the SDK hides the version differences.
- Platform version + manifest `min_platform`; the store distributes accordingly.

## 12. Key architecture decisions and trade-offs

| # | Decision | Rejected alternative | Rationale | Cost and follow-up |
|---|------|-----------|------|-----------|
| A1 | Semantic UI: apps hand over content + actions, the system renders | Apps draw themselves (the Android / iOS model) | Keyboard usability, trustworthy system UI, the same app under both text and pixel rendering, mini-programs can reuse it directly | Free-form UI is restricted → canvas apps as the exception ([07](07-ecosystem-and-store.md)) |
| A2 | One connection per app, identity = connection | A global bus (D-Bus) + apps reporting their own identity | Identity cannot be forged; apps cannot touch other services; a natural fit for sandboxing | All capabilities are relayed through the Shell, so the Shell has to be stable; the broker can later be split out into its own process |
| A3 | The broker lives inside the Shell for now | A separate broker daemon | System UI (grants, confirmation) and the broker have to stay in sync, and keeping them together is simplest | A Shell crash has a large blast radius; the interface is already designed to be "splittable" |
| A4 | Media as a separate plane | Frames over the UI protocol | Large pixel volume, privacy (apps cannot see the picture), hardware planes possible | Needs handle lifecycle management (prototype: subscribe only to visible surfaces) |
| A5 | Sensitive interactions drawn by the system | In-app payment dialog + SDK | Prevents overlays and reading the input, what you see is what you sign | Vendors' brand expression is limited; a limited set of style parameters can be opened up |
| A6 | JSON lines for the v0 protocol | protobuf / Cap'n Proto from the start | Writable from any language with zero dependencies (the Python example proves it), easy to debug | Size and parsing overhead → binary + incremental in production, with the version negotiated at the handshake |
| A7 | Linux + our own runtime | AOSP base / Android container | Lean, controllable, keyboard-first carried through from the bottom (D1, D2) | No existing app ecosystem → D4: win vendors with the capability catalog and low porting cost |
| A8 | Chain of trust emulated in software first, interfaces designed for a TEE | Build the TEE first, then the upper layers | Validate the end-to-end flow and the server-side verification model first | Not secure until the TEE lands (the prototype is only a demo) |
| A9 | Semantic first; the browser only as a controlled tier-4 component (D5 decided, measurements in [15](15-web-vs-semantic-benchmark.md)) | A browser engine as the app foundation (the KaiOS / Firefox OS model) | The browser does not provide the platform capabilities (push, trusted payment, incoming calls, key handling); the text renderer needs semantics; resource and spoofing risks ([14](14-tui-route-and-app-framework.md) §4) | Existing H5 content has to wait for the web view component; rich layout is covered by the `doc` node first |
| A10 | Third-party apps isolated in their own processes; in-process plugins only for OEM system extensions | A DSH-style in-process plugin ecosystem | In-process plugins are fully trusted and cannot carry payments or untrusted code | Third-party extensions cannot change the Shell's behavior; system extensions go through the product configuration layer and capability provider services ([14](14-tui-route-and-app-framework.md) §2.1), not into the Shell process |
| A11 | The input method belongs to the system (the same layer as secure confirmation), and apps only receive committed text; input fields declare a keyboard type ([16](16-input-method.md)) | Apps bring their own input methods; Android-style replaceable third-party input methods | Third-party input methods can see every key press (chat and search included); on a small screen the candidate bar has to be laid out together with focus and soft keys; the T9 keypad and the full keyboard have to behave the same in every app | No third-party input methods such as Sogou or iFlytek at first; later they can plug in as a system service: the input method already is a separate process, `phone-imed` ([16](16-input-method.md)), so changing the implementation only means replacing this service |
| A12 | There is only one Shell core (Go), and the pixel renderer is only a projection: the Shell sends "frames" and the renderer sends back key presses; the renderer is a replaceable slot, phone-paint by default, phone-gui as the alternative ([06](06-gui-architecture.md), [23](23-renderer-protocol.md)) | Writing a second Shell with focus, menus and the broker in Rust | System UI behavior, security rules and the selftest are naturally identical under both renderers; only one copy to maintain | One extra inter-process hop to the renderer; video frames currently go through the Shell (dmabuf in production) |
| A13 | The app sandbox uses the launcher `phone-sandbox`: namespaces + separate uid + Landlock + seccomp + rlimit, frozen 10 seconds after going to the background ([17](17-app-sandbox.md)) | SELinux policy; container runtimes (bubblewrap / runc) | All of it is built-in kernel mechanisms, with no MAC policy to write and maintain; degrades by kernel version | One cgroup per app (resource limits and freezer); network policy and traffic accounting tell apps apart by uid with nftables |
| A14 | Phone, alarm and contacts are system services: incoming calls and alarms are taken over full-screen by the system, and work even when the app is frozen or not running; when a third-party app dials, the user has to confirm in a system dialog ([19](19-core-apps.md)) | Each app stays resident in the background and handles them itself | Consistent with background freezing (A13); incoming calls and alarms are events that must not be missed; dialing is an operation with a cost / harassment risk | The UI details of the phone and alarm screens are decided by the system; apps cannot fully customize them |

## 14. File descriptor passing: permissions checked at setup, data flows directly

Linux can hand an open file descriptor (a file, socket, shared memory, device) to another process over a Unix socket (`SCM_RIGHTS`). The receiver gets "an object that is already open"; it does not need to, and cannot, open it again by path.

This fits our structure exactly:
- The Shell is the only arbiter, but it should not become the data channel.
- Apps live in a sandbox where Landlock does not let them access any system resource by path, but an fd handed to them works normally. So an fd is a "capability token": the Shell checks the permissions and sends it out, and from then on the data flows directly between the two ends.

Implementation in the `wire` layer (`wire/wire.go`):
- A message states how many fds it carries (the `fds` field). The receiver queues fds in arrival order and takes the corresponding number when it gets to that message. Even if the JSON decoder has read ahead into later messages, fds are not mismatched (covered by a unit test).
- Every received fd is set close-on-exec (CLOEXEC), so it does not leak into apps the Shell launches later. After sending, the Shell closes its own copy.

| Scenario | Approach | Status |
|------|------|------|
| An app's UI connection | The Shell creates a socketpair, which the launched app process inherits as fd 3 | ✓ Already in place |
| An app's own sound and recording ([20](20-audio.md)) | audiod creates a piece of shared memory (memfd) as a ring buffer and hands it to the app through the Shell; after that the PCM does not pass through the Shell. The memfd's size is sealed, so the app cannot truncate it and make audiod crash with SIGBUS | ✓ |
| Media picture passthrough | mediad draws each video stream into a piece of shared memory (memfd, two alternating buffers, size sealed) and hands the fd to the Shell over the frame socket; the Shell passes it on unchanged over the renderer's side channel (fd 3 inherited at startup, `SOCK_SEQPACKET`), after which only a frame number is forwarded per frame and the pixels do not pass through the Shell ([23](23-renderer-protocol.md) §4.2). In production this becomes dmabuf, going straight to a DRM plane | memfd ✓ (phone-paint); dmabuf depends on hardware |
| Photo picker (`media.pick`) | The user picks in the system picker, and the system opens a read-only fd and hands it to the app. The app cannot see any other files; this is the powerbox pattern, the same idea as Flatpak's document portal and Android's photo picker. The user's own choice is itself the grant, so no photo library permission is needed | ✓ |
| Photo capture results | mediad encodes the photo as PNG into a memfd and hands it to the Shell, which saves it in the system photo library | ✓ |

The app only gets a stream name | ✓ |

**The Shell restarts, the apps do not.** An app's UI connection (the Shell's end) is handed to the next Shell, which takes over the connection and has the app resend its pages:

- **Handing over connections**: when the service has the fd store enabled (`PHONE_FDSTORE=1`), every time the Shell launches an app it stores the app's connection in systemd's fd store (`FDSTORE=1`, named `app-<app id>-<pid>`). After a Shell crash, systemd restarts it and hands these connections back through `LISTEN_FDS`. When the Shell is upgraded, or in the selftest, it restarts in place: it execs itself, keeps the connections open, and writes their numbers into `PHONE_HANDOFF`.
- **Taking over**: the new Shell finds the apps by name, thaws frozen ones first, then sends `resync`. The Go SDK remembers the page stack on the Shell's side and resends it when it receives this (reset, then push page by page); calls the old Shell never answered return an error. The C SDK leaves `resync` to the app itself, which redraws. An app that was taken over is not a child process of the new Shell, so its exit is detected by the connection closing (becoming a zombie in `/proc` also counts as exiting).
- **Processes must not die along with it**: the parent-death signal is sent when "the thread that forked the child" ends, and exec ends every thread except the calling one. So all of the Shell's child processes are started from the same locked system thread that never exits, and in-place restarts also exec from this thread. When the fd store is in use, apps do not set this signal (the sandbox launcher would normally set it again after switching uid; `survive` in the policy turns this step off); the unit uses `KillMode=process`, so a restart ends only the Shell itself, and on a normal stop the Shell itself first thaws and then ends all the apps.
- **Unit configuration**: `FileDescriptorStoreMax`, `NotifyAccess=main` (without it systemd does not accept fd store messages), `KillMode=process`, restart after a crash.
- **Apps go into their own scopes**: when systemd restarts a service, it always puts the new process into the service's main cgroup first (the systemd 259 source says so explicitly, and `DelegateSubgroup=` also moves it there only afterwards). If the apps' groups were created under the Shell's service group, the main cgroup would have to enable controllers for its child groups, and under the cgroup v2 rules it could then no longer hold processes, so the restart would fail (`Device or resource busy`). So in the display service each app is in its own systemd scope (`phone-apps.slice/app-<id>-<pid>.scope`, [17](17-app-sandbox.md) §5), and the Shell's service group contains only the Shell itself.
- **Verification**: in the selftest, after the Shell restarts in place, the calculator's process ID is unchanged and its page is restored as it was, and the following cases and the whole compatibility test suite run on the new Shell (passes on both the dev machine and the device). For the fd store path: the device boot selftest starts a check service configured the same way as the display service (`phone-fdstore-check.service`, app scopes + fd store); the Shell crashes deliberately, systemd restarts it, the new Shell takes the calculator over from the fd store, and the calculator is still in its own scope, with its memory and process limits unchanged and background freezing working as usual (`fdstore.script`).

**There is no need to restrict messages to "only one fd at a time"**; what really needs to be controlled is the following:
- **Direction**: files flow only from the system to apps. The Shell's connections to apps, and each system service's connection to the Shell, immediately close any fds sent from the other end (`Conn.RefuseFiles`). Otherwise an app could keep stuffing in fds and exhaust the Shell's file descriptor table, which would affect every app. Covered by a unit test.
- **Count**: at most 8 fds per message; at most 4 audio streams and 1 recording per app; audiod also has an overall cap of 32 streams, so apps cannot keep requesting shared memory.
- **Type**: the system only sends objects it has verified itself, such as size-sealed memfds and files opened read-only. The receiver checks again as well; for example, an unsealed ring buffer is refused for mapping.

There is also `pidfd_getfd`, which can "take" an fd directly from another process; it needs debugging privileges. Our seccomp filter forbids this call for apps ([17](17-app-sandbox.md) §4).

## 15. Cloud services: where the device connects

The store, the push gateway and the update server are in the cloud; their addresses and trust are provided by the product layer, and the platform hard-codes no addresses. The product layer points the Yocto variable `PHONE_SERVICES` at a directory, and the `phone-services` recipe installs it into the image:

| File | Installed to | Content |
|------|------|------|
| `services.env` | `/usr/share/phone/services.env` | `PHONE_STORE_SERVER` (store backend), `PHONE_PUSH_GATEWAY` (push gateway) and `PHONE_PUSH_GATEWAY_CERT` (the gateway certificate to pin), `PHONE_UPDATE_URL` (update server) and `PHONE_UPDATE_KEY` (the signing public key for `latest.json`, [25](25-system-update.md) §0); any of them can be omitted |
| `*.pem`, `*.pub` | `/usr/share/phone/services/` | Gateway certificate, signing public key for `latest.json` |
| `trust/<store>.pub` | `/usr/share/phone/trust/` | Store roots the device trusts; the file name is the name in the store certificate (for `phone-storesrv` it is `store`) |

- The units of phone-pushd, Hongyan's simulated server and the display service (Shell) first use local defaults, then read `services.env` to override them (systemd's `EnvironmentFile`).
- For each item that is set, the recipe leaves a marker (`services/store`, `services/push`, `services/update`). The simulated store backend and push gateway on the device start only when the corresponding marker is absent, so you can put only the store and the update server in the cloud and keep using the simulated gateway on the device for push.
- Without `PHONE_SERVICES` the package is empty and the image is the same as before, using the simulated services on the device for everything.
- **Verification**: `make yocto-cloud-test` starts a store backend, a push gateway and an update server in the build container (seen from inside QEMU as 10.0.2.2), writes this directory from the store root and the gateway certificate they generate, builds an image with it and boots it on an A/B disk. On the device, `cloud-test` first confirms that the simulated store and gateway did not start, then runs three steps: an app that a developer published through the cloud store installs from the catalog; a Hongyan reply is pushed to the phone through the cloud gateway; 「设置 › 系统更新」 (Settings › System update) reads the cloud `latest.json`. Finally the image is built once more without this directory.
- **Not implemented**: the cloud gateway does not yet require the device's certificate to chain to the certification body's root: beta phones are not provisioned, and their root is one they generated themselves at first boot; this can only be turned on once production phones are provisioned on the production line ([22](22-developer-api.md) §11).

So "a counterpart implementation" does not mean building one copy of every layer: the virtual machine, Zygote and the general HAL are layers we deliberately leave out; windows, permissions, package management, app invocation, push, keys, updates, and Wi-Fi and Bluetooth management are all in place; the remaining gaps are sensors, GPU compositing, power policy on real hardware and vendor back ends, all of which need real hardware.

**Why there is no HAL.** Android's HAL exists so that one system release can run on thousands of vendor kernels and drivers: vendors put their own closed-source implementations behind the HAL, and system upgrades do not have to wait for the vendor. We only support hardware that runs on the mainline kernel (the premise of the R16 hardware choice); the kernel already abstracts the hardware into standard interfaces, and an extra layer would have nothing to hold. Take keys as an example. The delivery path is: the keyboard chip's driver (the TCA8418 matrix keypad, GPIO keys) reports standard `KEY_*` codes according to `linux,keymap` in the device tree → evdev → the renderer (only it can read `/dev/input`; apps cannot) → the renderer protocol's `key` message → the Shell. The differences between models are in the SKU's keypad configuration (`sku/keypads/*.toml`; `keys.toml` lists the code of every key, and a test checks that the renderer recognizes each one, [24](24-sku-framework.md)); vendor-specific scan codes are turned into standard codes by the device tree (or by the keycode table that udev hwdb writes into the kernel), so no user-space HAL is needed. Other hardware works the same way, with one system service managing each kind of hardware: display and keys belong to the renderer (DRM, evdev), sound to audiod (ALSA), the camera to mediad (V4L2), the baseband to telephonyd (ModemManager), networking to iwd / BlueZ, and future sensors to a service that reads IIO. The only things that need to connect to a vendor's Android BSP are those without a mainline driver, such as the baseband, and the way to do it is to add a back end in that service (telephonyd speaking the radio interface HAL through libgbinder, **not implemented**, R2), rather than putting a layer under the whole system.

**Then what is `hal/`.** Reading and writing the device classes (LED, backlight, power supply, USB device mode) from each service would mean writing the same sysfs code in each of them, with no way to simulate it on a developer machine, so it is gathered into a thin layer: `hal/led` (the LED class: the timer trigger's slow blink, the channel intensities of a multicolor LED; on QEMU a uleds LED stands in), `hal/backlight` (the backlight class), `hal/power` (the power supply class: the battery level, and whether the charger is USB PD fast charging) and `hal/usbgadget` (USB device mode: a CDC-NCM network function in configfs), `hal/pm` (suspending the whole system: `/sys/power/state`, the `wakeup_count` handshake, the RTC wake alarm, [28](28-battery.md) §3), `hal/nfc` (the NFC controller: a simulated backend and an NCI one; the NCI backend speaks to the raw NCI device node that Android vendor drivers such as `nxpnfc` and `pn5xx_i2c` offer, since mainline's `nxp-nci` keeps NCI in the kernel and offers no card emulation to user space, [30](30-nfc.md)), `hal/fingerprint` (the fingerprint sensor: reading, enrolling, matching; used only inside phone-keystored, simulated on the developer machine and QEMU; the FPC and Goodix sensors of phones have no mainline driver and need the vendor's TEE, **not implemented**, [31](31-lock-and-biometrics.md) §4.1). It defines no new interface; it is the kernel's device classes written in Go (`hal/fingerprint` and `hal/nfc` are the exceptions: the kernel has no device class to use directly, so the interface is our own), with a simulated backend for each. The only difference between models is which instance to use: the board's configuration names it (`[leds]` and `backlight` in `sku/boards/*.toml`), `sku.json` hands it to the Shell, and the same binaries drive every board ([24](24-sku-framework.md)). Take the notification light: on the F(x)tec Pro1 X it is the PMIC's RGB LED `rgb:status` (its driver blinks it by itself, so the slow blink wakes no CPU); the OnePlus N100's mainline device tree has no LED, so none is configured and new notifications light the screen instead. Keys do not go through it: the renderer reads evdev directly, along the path described above.

**On phones with only a vendor kernel.** The backends above all target the mainline kernel's device classes. To use Android's HALs on phones such as KaiOS ones, which have only a vendor kernel (libhybris loading vendor libraries linked against bionic, or libgbinder speaking HIDL directly), the backends go into: the classes of `hal/` (lights, backlight and battery are mostly still sysfs device classes on vendor kernels and work as they are; those that need vendor libraries go into a separate HAL host process with dropped privileges, whose client the `hal/` backend is, so vendor code stays out of the Shell), telephonyd (a RIL backend implementing the `Modem` interface, speaking the rild socket or HIDL `IRadio`), the renderer (a framebuffer output, or hwcomposer through the host process), and audiod (an output that calls the audio HAL through the host process). Keys need no change: vendor kernels report evdev too. The NFC NCI backend already targets the raw device node of vendor drivers, so it needs no second implementation on vendor kernels (**not verified on hardware**). We do not recommend this path; the reasons and the cost item by item are in [24](24-sku-framework.md) §7.

### 16.1 How keys reach apps (compared with Android)

Android: InputReader reads events from evdev, and InputDispatcher delivers them only to the focused window; background and frozen apps have no focused window and get no keys. When an app has just started and has no window yet (a focused application but no focused window), keys wait in InputDispatcher's queue for at most that app's dispatching timeout (5 seconds by default), after which it reports "application not responding" and the keys are dropped; keys are delivered one at a time in order, so a new window that a previous event opened gets the next key (`findFocusedWindowTargetLocked` in [InputDispatcher.cpp](https://android.googlesource.com/platform/frameworks/native/+/refs/heads/main/services/inputflinger/dispatcher/InputDispatcher.cpp)). KaiOS's Gecko carries a copy of the same code ([24](24-sku-framework.md) §7.1).

| Step | Android | Kario |
|------|------|-------|
| Reading the devices | InputReader in system_server reads `/dev/input` | The renderer reads them: an input helper that phone-paint forks before dropping privileges opens the keyboards and mice under `/dev/input` and hands it the fds ([23](23-renderer-protocol.md) §5); apps cannot open `/dev/input` ([17](17-app-sandbox.md) §6) |
| Who decides | InputDispatcher and the window manager's policy | The Shell: the renderer reports keys as they are in the renderer protocol's `key` message ([23](23-renderer-protocol.md) §3) and interprets nothing |
| The system first | The power key, the volume keys and the like are handled first by `PhoneWindowManager` | The Shell's `Key`: while the screen is off a press only lights it; the volume keys and media keys always belong to the system; while a system overlay (menu, dialog, incoming call, alarm) is on top, keys go only to it; with the keypad locked, or in a call on the secure lock screen, they reach only the lock screen or the call screen; the end, call and task keys are interpreted by the Shell; the power key goes to `PowerKey` instead |
| Which app | The focused window | The "current" app: the foreground app, or the Shell's own idle screen and menus when there is none (`current()`). Background, frozen and tombstoned apps get nothing |
| What the app receives | The raw `KeyEvent` | Usually not keys: focus movement, the back stack and the text in input fields are handled in the Shell, and the app receives actions (which action of which node) and the input fields' `changed`; only canvas nodes that declare they want keys get key names, and the arrow keys and OK on a web node go to the web process ([22](22-developer-api.md) §3) |
| The app is not ready yet | Waits in the queue for at most 5 seconds, then "application not responding" and the keys are dropped | Held, see below |

**Held keys** (`shell/tomb.go`, `shell/core.go`):
- When they are held: while the current app has no usable page yet, i.e. after a cold start before its first page arrives (the page stack is empty), or when it is restored from a tombstone and its old pages only show (their actions belonged to the process that is gone, [17](17-app-sandbox.md) §5.3). The keys pressed then (what is left after the system's first steps above) are kept in this app's `heldKeys`, at most 32 (`maxHeldKeys`), and any more are dropped; Back is not held but goes to the idle screen at once. The Shell's own idle screen and menus always have a page and hold nothing.
- When they are delivered: every page the app sends (`push`, `replace`, `reset`) restarts a timer; 150 ms (`keysSettle`) after the last page, if the app is still running and its pages are no longer the old ones, the held keys go through `Key` again in the order they were pressed, along the same path as keys just pressed. So a system dialog that opened in the meantime (a permission dialog the app asks for as soon as it starts, for example) gets them first, which is what Android means by "a window that a previous event opened gets the next key".
- When they are thrown away: if at replay the app is no longer in front (the user went back to the idle screen or switched to another app), all held keys are dropped and never go to another app; they are cleared when the process exits (crash, ended). Leaving the foreground does not clear them: coming back before the new pages arrive, the keys held earlier are still delivered to it at replay.
- No timeout: if the new process never sends a page, the keys stay held; the Shell sends no ping while holding keys, so it does not report "not responding" ([17](17-app-sandbox.md) §5.2), and the user goes back to the idle screen with Back. This differs from Android.
- Thawing needs no held keys: the Shell thaws an app as it comes to the foreground (writing `cgroup.freeze` or sending SIGCONT, `shell/freeze.go`); its pages stay in the Shell's hands all along, so focus movement and typing take effect at once, and the actions meant for the app are queued in its send queue (256 messages per app, dropped when full) and the socket buffer, and processed in order once the app runs again.
