# 生态与应用商城

## 0. 应用的档次（D2、D5 已定）

应用框架是「语义优先」的四档（[14](14-tui-route-and-app-framework.md) §5，依据实测 [15](15-web-vs-semantic-benchmark.md)）：

| 档 | 界面怎么来 | 按键可用性 | 适用 |
|----|------------|------------|------|
| **原生语义应用**（默认） | 经 `phone.Ui` 交出内容 + 动作，Shell 渲染（[10](10-keyboard-interaction-model.md) §4） | 系统保证；文本与像素界面都能显示 | 电话、短信、通讯录、设置、阅读、IM、大部分第三方 |
| **系统渲染文档** | 应用交出 Markdown / Mermaid，系统排版 | 系统保证 | 帮助、协议、说明书 |
| **JS 小程序** | JS 逻辑 + `phone.Ui` 视图，在宿主里运行 | 系统保证 | 便民服务、轻量业务 |
| **Web 视图组件** | WPE WebKit 承载存量 H5，作为受控组件嵌在语义页面里 | 由系统的焦点导航兜底 | 存量网页 |
| **画布应用**（例外） | 页面里放一个画布节点（`canvas`），应用给的是图形（矩形、线、圆、点、多边形，坐标用自己的单位），由系统画成像素，文本和像素界面都显示得出；文字仍用普通节点 | 画布聚焦时 OK、方向键、数字、字母交给应用，返回、软键、挂断仍归系统；上架人工审核按键可达 | 游戏、地图、图表（示例：贪吃蛇） |

## 1. 厂商发布（D4）

目标：微信、支付宝这类厂商能用平台能力发布 `phone.Ui` 版应用。能力目录、移植路径与技术之外的门槛见 [12](12-super-app-capabilities.md)；可运行的样例（类微信聊天含视频通话、类支付宝钱包含可信支付）见 [13](13-prototype.md)。SDK：Go SDK、C ABI SDK（`sdk/c`）与「任意语言直连协议」都已有（[22](22-developer-api.md) §9）。

## 2. 不做的事

| 不做 | 原因 |
|------|------|
| Android 应用兼容 | 内存、功耗、触屏依赖；微信对容器环境有封号风险（[09](09-ui-feasibility-review.md) §5） |
| 微信 / 支付宝 / B站客户端（逆向或非官方 API） | 违反服务条款、随时失效；支付还需要金融认证 |
| 把「大厂适配」当作计划前提 | 大厂只为有规模的平台适配；平台按 D4 把能力和移植成本准备好，但产品路线不依赖它 |
| 原生动态库插件 | 第三方一律独立进程，不以 `.so` 形式加载进 Shell（崩溃隔离） |
| PC 低代码设计器 + 脚本引擎 | 推迟到 v2 之后；语义模型冻结后再评估 |

## 4. 应用包 `phoneapp/1`

实现在 `pkg`（打包、验签）和 `shell/install.go`（安装服务），安装策略见 [22](22-developer-api.md) §12。

```
notes.phoneapp                 # tar
├── manifest.json
├── META/signature.json        # 每个文件的 SHA-256 + 开发者 Ed25519 签名 + 商店签发的开发者证书
├── main / main.js / ...       # 任何语言的 phone.Ui 程序（Go SDK、Python、小程序）
└── icon.png
```

| `manifest.json` 字段 | 含义 |
|----------------------|------|
| `id` | 反向域名，如 `com.example.notes`（`system.` 开头的留给系统） |
| `name`、`description`、`version` | 显示名称、简介、版本 |
| `exec`、`args` | 入口程序与参数 |
| `permissions` | 要用的能力，如 `contacts.read`、`network`、`camera`；`system`、`install` 只给系统镜像里的应用，安装器拒绝 |
| `background` | 后台模式，如 `voip`（不推荐，消息和来电应靠推送） |
| `share` | 从分享面板接收的类型：`text`、`image` |
| `icon`、`icon_image` | 文本界面的图标字符、像素界面的 PNG（≤ 256×256） |

规则：
- **安装**：验签和证书链 → 检查清单（应用 ID 格式、不许声明系统权限、不许预先授权）→ 系统弹框确认（列出来源和权限）→ 代码解到 `packages/<id>/`（应用只读），数据在 `apps/<id>/`。
- **更新**：必须是同一开发者签名。商店在后台装的更新（自动更新）还要版本更高、不多要权限，否则等用户自己点。
- **启动前**：签名清单随代码保存；开机后第一次启动、开发者模式变化之后，按当时信任的商店根重新核对全部文件，改过的、多出来的、商店不再受信任的，都不让启动。
- **卸载**：删代码和数据，撤销授权和使用记录、定时任务、闹钟、照片授权，删除密钥服务里这个应用的全部密钥，并作废推送令牌（[21](21-push.md)）。
- **开发者模式**（设置里的开关）：只有打开时，设备才信任开发商店，它签名的包才能装、能运行。
- **信任的商店**：镜像自带的商店根（`share/phone/trust`）和产线灌装的商店根（`factory/stores`）一直受信任；开发商店只在开发者模式下受信任。

### 4.1 商店后台：开源核心和模拟后台

商店后台分两层（D11）。开源的核心是 `appstore` 包，实现设备和开发者打交道的全部接口（下表）；`cmd/phone-storesrv` 是用它搭的模拟后台，和模拟的推送网关一样跑在设备旁边，给设备测试用。正式运营的商店后台不开源，用的是同一个核心，再加上运营要的东西：工作人员各自的令牌和审计日志、APP 备案号的规则、举报处理、网络日志、给人看的网页目录、设备认证和工厂签发、给支付后台核对设备的接口，以及开发者门户和审核台（63（内部文档））。核心为它留了扩展点：谁是工作人员（`Staff`）、审计（`Audit`）、提交的额外规则（`Accept`）、审核队列里多列的内容（`Queue`），路由可以在 `Routes()` 上添加。开发者一侧的工具是 `cmd/phone-pkg`。

| 环节 | 做法 |
|------|------|
| 开发者注册与身份核验 | `phone-pkg keygen` 生成 Ed25519 密钥；`phone-pkg register` 交公钥、名字和证件号：企业填统一社会信用代码（GB 32100，MOD 31 校验位），个人填居民身份证号（GB 11643，MOD 11-2 校验位）。校验位不对当场拒绝；对的记为「待核验」，只存掩码后的号码。商店工作人员核验后（`POST /v1/admin/developers/<名字>`，量产时对接工商登记或身份证核验服务，**未实现**），商店根才签发开发者证书；再运行一次 `register` 取回证书。同一名字换了公钥的注册被拒 |
| 打包 | `phone-pkg build` 签名打包；小程序在这一步把 `app.ts` / `app.tsx` 编成 `app.js`，设备上只运行 JavaScript。网页门户里也能选应用的目录、在浏览器里签名打包（同一个格式；浏览器不给文件权限，清单里 `exec` 指的文件是可执行的；TypeScript 小程序还是用 `phone-pkg`） |
| 提交与审核 | `phone-pkg submit`。先自动检查：签名链到本商店根、开发者已核验、清单合法、应用 ID 不占用系统前缀、不声明 `system` / `install`、不预先授权、没被下架过；更新必须同一开发者、版本更高。**新应用**和**申请了新权限的更新**进人工审核队列（`GET /v1/admin/queue`，工作人员 `POST /v1/admin/reviews/<id>/<版本>` 通过或带理由驳回）；其他更新直接上架 |
| 上架与下载 | 审核通过即进目录（`GET /v1/catalog`，商店根签名，带签发时间：`phoneapp-catalog/1`，签的是商店名、签发时间和应用列表的原样 JSON），只提供最新版本的包（`GET /v1/packages/<id>/<version>`；分批发布中的应用还有上一个版本）。商店应用把取到的目录交给系统（`pkg.catalog`）：系统按信任的商店根验签，签发超过 7 天的、比上次从这个商店收到的还旧的都拒收（镜像站或 CDN 改不了开发者、备案号、版本，也藏不住更新），通过了才交回应用列表；商店应用在页面最下方列出目录：没装的「安装」，有新版本的「更新到 x」；下载后核对目录里的 SHA-256，再交给系统安装器，照常验签、弹框确认，来源显示「应用商店（已审核）」 |
| 增量更新 | 更新时商店应用带上已装的版本（`?from=1.0`），商店还留着那个版本就回增量包（响应头 `X-Phoneapp-Delta`）：新版本完整的签名清单加上摘要变了的文件。系统用已安装的文件补齐其余部分（逐个核对签名清单里的摘要），得到的是普通的完整包，照常全量验签，再核对目录里的 SHA-256（重组结果和完整包逐字节相同）。所以增量包不需要自己的签名，也夹带不了开发者没签过的文件；装的不是它起始的版本就拒绝。确认框注明「增量 N KB」 |
| 分批发布 | 更新可以先只给一部分设备：`phone-pkg submit -rollout 10`（`POST /v1/submissions?rollout=10`）。目录里这个应用带着 `rollout`（百分比）和 `previous`（大家都有的上一个版本：版本号、大小、SHA-256、权限），两个版本的包都留着可下载。每台设备自己决定在不在这一批：系统用只存在本机的分桶（和系统更新同一个，0–9999）混上应用 ID 算一次，不在的设备从 `pkg.catalog` 拿到的就是上一个版本，商店不知道哪台设备拿到了新版本。开发者用 `phone-pkg rollout`（`POST /v1/developer/rollout`，带名字、时间和对 `phone-rollout/1\|<名字>\|<时间>\|<应用>\|<版本>\|<百分比>` 的签名）调高、调到 0 暂停、调到 100 全量。分批中的版本，下载过它的设备里有 10% 报了崩溃（至少 5 份），后台把比例调到 0 并记下原因（`halted`），等开发者处理 |
| 自动更新 | 商店应用登记两个后台任务（[22](22-developer-api.md) §4.7）：每 6 小时取一次吊销清单；充电时每 6 小时查一次更新（「只在充电时」的任务每次有 1 分钟，比一般唤醒的 3 秒长）。查到的更新带 `auto` 交给系统安装器（`pkg.install`），系统只在不改变用户同意过的东西时不问就装：已安装、同一开发者、版本更高（旧的签名包不能被塞回来）、不多要权限、不在前台也没在后台工作（通话、播放）；冻结或闲着的先结束再换。其余的回「需要用户」，留在商店里「可更新」等用户自己点。装好后商店发一条「已自动更新」通知。商店的应用设置里可以关掉（「自动更新应用（充电时）」） |
| 下架 | 工作人员 `POST /v1/admin/takedowns/<id>`（必须写理由）：应用出目录，进吊销清单（`GET /v1/revocations`，商店根签名，带签发时间）。商店应用刷新时和后台任务里（每 6 小时，不用打开商店）取清单交给系统（`pkg.revocations`）；系统按信任的商店根验签，比手里的旧就忽略（防回放），然后不让清单上的已安装应用启动（推送和定时任务唤醒也不行），正在运行的结束掉；打开时提示「已被商店下架：理由」。下架的应用 ID 不能再提交 |
| 崩溃报告 | 设置 › 关于本机 › 应用崩溃记录，选中一条按「发送给开发者」：系统弹框说明会发送什么（原因、版本、时间、最后几行日志），确认后才发；只有从商店安装的应用能发。只有应用的开发者能读（`phone-pkg crashes`）：请求带开发者名字、时间和用开发者密钥对 `phone-crashes/1\|<应用>\|<时间>` 的签名，后台核对开发者已核验、应用归他、签名有效、时间在五分钟内 |
| 开发者查看自己的状态 | `GET /v1/developer`：请求带开发者名字（可百分号编码，浏览器的请求头只能放 Latin-1）、时间和对 `phone-dev/1\|<名字>\|<时间>` 的签名，回核验状态、证书、已上架的和等待人工审核的应用；别人的看不到 |
| 状态 | 开发者、目录、审核队列、吊销记录、举报存在数据目录的 `state.json`，应用包在 `packages/`；都是写好临时文件再改名替换，崩溃或磁盘满时留下旧的，不会只写一半 |
| 公示与备案号 | 企业开发者的统一社会信用代码是公开信息，完整保存、随应用公示（目录里的 `developer_credit`）；个人的身份证号只存掩码。清单可以写 `filing`（APP 备案号），随应用公示；正式后台核对格式，国内公开的商店还要求必须有。商店应用里每个应用有「详情」页：开发者、信用代码、备案号、简介、权限 |
| 举报 | 应用详情页上的「举报」：`POST /v1/reports`（应用、理由，同一地址每小时最多 20 条）；工作人员在审核队列里看到没处理的举报（处理和记下处理人在正式后台） |
| 设备信任 | 后台启动时把商店根公钥写到设备的 `factory/stores/`，代表产线灌装 |

**未实现**：付费开发者账号、对接真实的工商 / 身份证核验服务和手机号验证（复合实名）、商店根和包签名放进 HSM、举报处理结果通知举报人、开发者门户里调分批比例的页面（现在只有 `phone-pkg rollout`）、按崩溃以外的信号（卸载率、差评）叫停。
- **限制**：包 ≤ 64 MB、≤ 1000 个文件；路径不许越出包目录、不许有链接文件。
- **生命周期**：初始化 → 前台 → 后台（10 秒后冻结）→ 销毁；单前台，其余挂起（[17](17-app-sandbox.md) §5）。

## 5. API 分层

```
应用（任何语言）──phone.Ui（JSON 行）──► Shell：渲染 · 按键 · 能力代理（broker）
                                           │  权限检查后转给系统服务
                                           ▼
                      telephonyd · audiod · mediad · pushd · keystored · …
```

应用只能经 Shell 的能力代理访问系统能力（[22](22-developer-api.md)）；**禁止**第三方直连 ModemManager 或任何系统服务，沙箱也不让它连（[17](17-app-sandbox.md)）。

## 6. 商城

- **信任链**：商店根密钥 → 开发者证书 → 开发者签名的包；设备里内置商店根，开发者模式下另外信任开发商店的根。
- **商店客户端**：平台里的「应用商店」是开源的参考实现，用仅系统应用可用的 `pkg.install` / `pkg.uninstall` / `pkg.list`。正式客户端闭源，只装在认证设备上。
- **后台**：开源核心和模拟后台见 §4.1（目录、审核、增量、下架、崩溃报告）；正式后台不开源；量产用对象存储放包，支付**未实现**。
